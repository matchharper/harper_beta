## 2. 이번 시퀀스의 시작과 가정

시작은 2026-11-13, 이미 가입과 `/career/onboarding`을 마친 Javier의 후속 대화다. `/jobs` 유입 여부는 확인하지 못했으므로 이 사례에 임의로 붙이지 않는다. 해당 유입자라면 구현 설계 2.5절에 따라 정확한 유입 공고를 먼저 이어간다.

**이하 대화, 선택, 검색 건수, 연락과 회신은 설계를 시험하기 위해 만든 가정이다. Javier나 회사가 실제로 했던 말이 아니다.** 시간은 경과 예상이며 benchmark가 아니다. 날짜만 정하고 기계 처리 시간과 사용자가 답하거나 상대가 회신할 때까지의 시간을 구분한다.

첫 시퀀스의 범위는 `기존 요청 재개 → 실제 검토할 후보와 근거 제시 → 사용자가 고른 대상의 준비와 허용한 연락 → 다음 확인 예약`이다. 여기서 오퍼를 얻는다고 가정하지 않는다. 3일·일주일 뒤에는 처음 결과를 다시 보내는 대신 새 사실에 따라 필요한 실행을 한다.

새 이름인 `search_resources`, `read_resources`, `research_resources`, `evaluate_resources`, `manage_result_sets`, `manage_views`는 **설계상 추가할 도구**다. 아래 인자는 핵심 계약을 나타내는 의사 호출이며 완성된 production schema나 실제 tool trace가 아니다. `read_document`, `write_talent_context`, `upsert_document`, `search_connected_gmail`, `write_email`, `upsert_schedule` 등은 기존 도구다. `S1`, `V1`, `D1` 같은 ID는 설명용 가상 ref다.

## 3. 첫 시퀀스를 끝까지 따라가기

### 3.1 다시 질문지를 시작하지 않고, 이미 받은 요청에서 출발

기본 context에 현재 Brief 다섯 행, Profile 요점, 이력서 ref, 이전 OpenAI/Gprnt 제안, Gmail 미연결 사실이 들어온다. 이미 받은 직무·지역·연봉을 다시 묻는 도구 호출은 없다. 원문을 읽기 위해 `read_document(document_id=기존 CV, revision=2)`를 호출한다.

Harper의 대화 예시:

> S$350,000 기본급을 목표로 하되 협의 가능하다는 점까지 반영해서 보겠습니다. 앞서 본 OpenAI 공고는 지역 운영 책임이 명확한 편이지만, 실제로 큰 운영 조직을 맡아본 경험을 요구한다는 점은 더 봐야 합니다.
>
> 지금 이력서에서는 사업 지표·운영 모델과 투자 경험이 강하게 보입니다. 다음에는 실제 사업 성과를 직접 책임지는 쪽으로 옮기고 싶은 건가요, 아니면 경영진과 일하는 전략·corp dev 역할도 비슷하게 보고 있나요? 기존 공고와 함께, 싱가포르에서 사업을 키우는 회사들도 살펴보겠습니다.

가정한 Javier의 답:

> 실제 결과를 책임지는 쪽이 좋아. 좋은 팀이면 전략 역할로 시작하는 것도 열려 있지만, 계속 조언만 하는 일은 피하고 싶어. 싱가포르에서 일하고 싶고, 기본급 목표는 그대로야.

원본 LLM은 새로 말한 역할 책임 선호만 기존 Brief에 보완한다. ‘기본급 목표 그대로’를 새로운 하한 숫자로 재해석하지 않는다. 이 답을 기다리는 동안 기존 요청으로 가능한 공개 후보 검색은 진행할 수 있다.

### 3.2 회사와 공고를 찾되, 이름 세 개를 미리 정답으로 넣지 않음

가정한 검색 규모는 다음과 같다. 이는 검색 상한·정답 개수·모든 사용자에게 수행할 절차가 아니다.

- 회사 DB 조회에서 82개, 외부 발견에서 22개. 겹친 8개를 정확한 identity로 합쳐 회사 96개.
- 별도의 Role 조회에서 공고 58개. 회사 집합과 관계를 연결하되 96개 모두에 공고가 있다고 만들지 않음.
- 가설은 싱가포르의 성장 기업 운영 책임, 해외 기업의 지역 사업 구축, corp dev가 실제 실행 책임으로 이어지는 역할. AI 업종만 필수 조건으로 두지 않음.

| 호출 | 주요 입력 | 가정한 반환·저장 | 다음 판단 |
| --- | --- | --- | --- |
| `search_resources` | `source=company_db`, Singapore 사업 기반과 성장 기업의 실제 설명 검색, `resultMode=set` | 회사 82개 `S-db`, 원본 정보 범위·누락 필드 | 이름/지역만 있는 회사와 실제 사업 설명이 있는 회사 구분 |
| `search_resources` | `source=roles`, Singapore strategy/ops/corp dev와 실제 책임을 찾는 질의, `resultMode=set` | 공고 58개 `S-role`, 현재성·source refs | 직함이 비슷하지만 junior/advisory 중심인 것과 책임 있는 역할 구분 |
| `search_resources` | `source=web`, Singapore regional expansion·operating leadership 등을 찾는 6개 질의 | 외부 회사 22개 `S-web`, 원문 링크 | 기존 DB 밖의 대상 발견. 반환된 이름을 곧 추천으로 취급하지 않음 |
| `manage_result_sets` | `union(S-db,S-web)`, exact identities | 회사 96개 `S1@1`, 실제 query/source manifest | 같은 회사 재검색·재평가의 기준점 확보 |
| `read_resources` | 기존 OpenAI 공고와 Gprnt 관련 refs, 최신 확인이 필요한 source | OpenAI 공식 본문, Gprnt는 기존 불명확한 상태 또는 새로 확인한 상태 | 이전 제안을 기억하고 재확인. Gprnt를 새 추천으로 다시 포장하지 않음 |

연 기본급을 공개하지 않는 회사는 많을 수 있다. `salary >= 350000`을 검색의 필수 SQL 조건으로 넣으면 좋은 회사까지 사라진다. 실제 공고가 명시적으로 크게 낮은 보상을 제시하는 경우와 보상이 미공개인 경우를 모델이 다르게 판단할 수 있게 한다.

### 3.3 96개를 메인 모델에게 하나씩 조사시키지 않음

`evaluate_resources(selection=S1@1, sourceRefs=현재 Brief·CV 관련 근거, questions=이번 기준)`를 호출한다. 이번 사례에서 작성할 수 있는 질문은 다음과 같다. 보편 rubric으로 고정하지 않는다.

1. 제공된 근거에서 Javier가 원하는 사업 책임·다음 경력에 의미 있는 역할을 논의할 이유가 있는가?
2. 회사의 실제 사업·팀·성장 근거는 무엇을 뒷받침하는가? 유명한 이름만 있는가, 읽을 만한 사실이 있는가?
3. Singapore 근무와 보상에 대해 확인된 충돌이 있는가, 아니면 중요한 조건이 미확인인가?
4. 현재 근거만으로 판단 가능한가, 추가 확인하면 결론이 달라질 수 있는가?

예를 들어 조건 상태는 `확인된 충돌 / 확인된 부합 / 미확인`처럼 이번 질문이 요구하는 값을 받을 수 있다. 평가값은 합격 확률이 아니다. 네 질문을 통해 384개 판단을 요청하지만, 모델 호출 수·과금은 adapter의 묶음 방식과 실제 usage로 계산한다.

메인 LLM은 모든 원문 96개 대신 평가 분포, 짧은 후보 목록, 정보가 부족한 대상 목록을 받는다. 이 가정에서는 근거가 유력한 12곳과 유력할 여지는 있지만 자료가 적은 4곳, 총 16곳을 더 읽기로 한다. 낮은 정보량만으로 자동 제외하지 않는다.

`research_resources(selection=16곳, questions=실제 팀·역할·지역 책임·공개 보상·현재 접근 경로)`를 호출한다. 첫 시퀀스 전체에서 외부 검색은 24회, 검색 결과에 포함되지 않았거나 재확인이 필요한 신규 본문 읽기는 48페이지로 가정한다. 검색 24회는 넓은 발견 6회, 회사·역할 확인 12회, 사람·접근 경로 4회, 행사 관련 2회다. 페이지 48개는 회사 공식 자료 21개, 공고 17개, 팀·발표 등 10개다. 검색에서 이미 받은 본문을 같은 비용으로 다시 가져오는 수를 포함하지 않는다.

원문 cache·batch 읽기·근거 발췌를 사용한다. 회사마다 조사 agent를 독립적으로 생성하지 않는다. 읽은 자료가 부족하면 그 범위를 반환하고 메인 모델이 추가 방향을 정한다. 16곳의 바뀐 근거에는 기존 기준 ref를 사용해 평가를 갱신할 수 있다. 이것은 초벌 평가 96회와 추가 평가 16회, 총 112개 대상 평가 실행이다.

### 3.4 실제로 사용자에게 무엇이 보이는가

`manage_result_sets`로 선택한 항목의 순서·개인 설명·근거 refs를 보존하고, `manage_views`로 `V1: Singapore operating roles`를 만든다. 96개 회사의 모든 개인 설명을 작성하지 않는다. 사용자에게 우선 보여주는 예는 다음과 같다.

| --- | --- | --- | --- |
| OpenAI — 공개된 Strategy & Operations Lead 공고 | 운영 지표·지역 실행·팀 리더십이 실제 업무에 포함. 투자자에서 운영자로 전환하려는 방향과 논의할 여지가 있음. 직접 운영 리더십의 증거는 현재 자료에서 약함 | SEA/ANZ와 India 표현의 모순, 역할 수준, 기본급, 실제 팀 책임 | 지원 자료 준비, 역할 범위 확인 |

이 문구는 출력 예시다. 인사·문단 수·추천 개수를 prompt에 넣지 않는다.

### 3.5 사용자가 고른 뒤 무엇을 실제로 준비하고 실행하는가

가정한 Javier의 선택:

> OpenAI는 지원 자료부터 준비해줘. 아직 제출하지는 말고. ElevenLabs는 내가 아는 전 Cisco 동료 A에게 소개 가능한지 물어보고 싶어. A의 이메일을 줄게. Cognition은 내가 전달할 수 있는 소개문을 만들어줘. Sierra는 참석 가능한지 문의해줘.

Harper는 현재 Gmail이 없다는 사실을 설명하고, 사용자 계정으로 발송하려면 연결이 필요하다는 실제 선택을 제공한다. 자료 작성은 기다리지 않는다. 이 주 시퀀스에서는 **Javier가 Gmail을 연결하고 발송 권한을 부여하며, 아래 범위도 맡긴다**고 가정한다.

> A에게는 공개 이력서와 짧은 소개를 보내도 돼. 포트폴리오사의 비공개 숫자는 빼줘. Sierra에도 내 경력과 참석 목적을 설명해줘. 관련 답장은 매일 확인하고, 그 범위의 질문에는 답해줘. 연봉 조건을 대신 수락하거나 지원서를 제출하지는 마. 새로운 회사는 3일마다 확인하고 중요한 변화가 있을 때 알려줘.

새 연락처는 사용자 원문으로 받은 정확한 주소다. 여기서 A의 실명·주소·소개 가능성은 가상이며, 기존 Gmail에 그런 관계가 있다고 확인한 것이 아니다.

또한 이 예시에서는 독립 agent를 위한 `manage_work(start)`가 필수는 아니다. 현재 대화에서 자료와 발송을 끝내고 기존 operation·schedule에 정확한 refs를 연결할 수 있다. 별도 긴 조사가 유리하면 기존 work로 위임하지만 회사별 agent를 자동 생성하지 않는다.

### 3.6 Gmail을 연결하지 않으면

실제 현재 상태에서 그대로 계속하면 이 분기가 된다. D1/D2/D3와 V1은 만들 수 있고 공개 시장 탐색도 예약할 수 있다. A와 Sierra에 보내는 두 메일은 발송되지 않는다. 복사 가능한 본문·자료·정확한 수신처와 사용자에게 남은 발송을 보여준다. 답장은 사용자가 붙여 넣거나 전달해야 한다.

Gmail이 없어도 Harper가 Javier에게 새 기회나 준비된 자료를 알려주는 자체 이메일은 별도 가능하다. `사용자에게 Harper가 보내는 알림`과 `사용자 Gmail로 외부 사람에게 보내는 연락`을 섞지 않는다. 미연결 상태에서도 자동 외부 후속이 된다고 주장하면 이 설계는 실패다.

사용자가 보지 않아도 시스템에는 회사 96개·공고 58개의 검색 범위, 평가 입력과 결과, 실제 읽은 공개 근거, 미확인 범위가 남는다. 이 저장이 다음 사용자의 공개 수집과 Javier의 다음 판단을 줄인다. 사용자에게 DB 행이나 ‘전략 문서 관리’를 할 일로 넘기지 않는다.

## 5. 3일 뒤와 일주일 뒤의 경험

### 5.1 11월 14–15일: 사용자가 앱을 열지 않아도 되는 일

R-mail이 두 thread를 읽는다. 이 가정에서는 새 답장이 없다. 확인 시점과 소비한 message ID가 남고 다음 예약이 유지된다. 검색하지 않은 외부 시장까지 변화가 없다고 말하지 않는다. 매일 ‘아직 답장이 없습니다’라는 이메일을 새로 보내지도 않는다.

Sierra 행사는 17일이므로 16일 확인에서 참석 여부가 미해결이면 그 사실이 실제로 중요하다. 3일 주기 시장 확인만 둬서 행사 후에 처음 답장을 확인하는 설계는 부적절하다. 날짜와 사용자 위임을 받은 원본 LLM이 관련 메일 확인 시점을 정한다.

### 5.2 11월 16일, 3일 뒤: 같은 추천 메일을 다시 보내지 않음

이번 실행에 공급되는 입력은 최신 Brief, 첫 검색 manifest, 평가 기준 ref, V1, E1/E2의 실제 thread, D1/D2/D3, 마지막 확인 이후의 사용자 메시지다. 모든 과거 페이지와 이력서를 다시 넣지 않는다.

다음 외부 반응을 **가정**한다. 실제 Sierra·ElevenLabs의 답변이 아니다.

- A가 ElevenLabs 쪽에 소개했고, 소개받은 상대가 Javier의 실제 운영 기여를 정리한 자료를 요청했다.
- Sierra는 이번 행사의 참석 대상에 맞지 않아 초대하기 어렵다고 답했다.
- 새 공개 검색에서는 처음 96개 외에 8개 회사가 발견되고, 기존 4개의 관련 근거가 바뀌었다. 따라서 12개를 새로 평가한다. 나머지 92개를 전부 재평가하지 않는다.

### 5.3 11월 17–20일, 일주일 뒤: 역할과 조건을 구체화

R-mail은 남은 thread를 확인하고, R-market은 19일에 새 시장을 다시 확인한다. 여기서는 새/변경 18개에 대한 평가, 외부 검색 8회, 신규 본문 12개를 가정한다. 20일에 아래 답변이 도착했다고 가정한다.

> 상대가 다음 주에 지역 책임자와 역할 범위를 논의해 보자고 제안했다. 실제 업무에는 파트너십 실행과 운영 지표 관리가 포함될 수 있지만, headcount 승인·보고 관계·기본급은 아직 확정되지 않았다.

Harper는 다음 일을 한다.

1. 기존 thread와 상대의 발신자·정확한 표현을 읽는다. 이를 면접 합격이나 오퍼로 표시하지 않는다.
2. D1을 재사용해 대화 준비 자료를 만든다. 확인할 내용은 실제 책임·의사결정 권한·팀/예산·성과 기준·기본급과 지분의 구분이다. 이 항목들이 모든 면접의 고정 질문지는 아니다.
3. 이미 받은 위임 범위에서 S$350,000 기본급 목표와 협의 가능성을 정확히 설명할 수 있다. 더 낮은 금액 수락이나 숫자 공개가 위임에 없으면 사용자의 판단을 요청한다.
4. 상대가 제시한 가능 시간과 사용자의 가용 시간을 확인한다. 둘 다 합의되기 전에는 ‘미팅 확정’이라고 표시하지 않는다. Calendar 연동이 없으면 메일 합의와 일정 제안을 준비하고, 캘린더 생성까지 했다고 하지 않는다.
5. OpenAI는 아직 ‘자료 준비’다. 사용자가 제출을 요청하지 않았으므로 일주일 지났다는 이유로 제출하지 않는다. Cognition 소개문도 사용자 발송 여부를 확인하기 전에는 연락했다고 기록하지 않는다.
6. 같은 V1을 업데이트하고 필요한 변화만 사용자에게 전달한다. 새 보고서와 새 추천 화면을 매번 따로 만들지 않는다.

일주일 뒤의 결과는 ‘좋은 회사 네 곳을 다시 추천받음’이 아니라 **하나는 실제 역할 논의로 진행, 하나는 참석이 불가능하다는 사실 확인, 하나는 지원 자료가 준비된 채 사용자 선택 대기, 하나는 전달 가능한 소개문과 미확보된 접근 경로가 남은 상태**다. 논의 중인 역할이 보상·책임에서 Javier에게 좋은 이동인지는 계속 확인해야 한다.

### 5.4 아무도 답하지 않으면

회신·미팅이 생기는 분기만으로 성공을 설명하지 않는다. A와 Sierra 모두 답하지 않으면 3일 뒤에 남는 것은 확인한 무응답, 행사 참석 미확정, 업데이트한 시장 조사다. 상대를 읽지 못한 실패는 무응답과 구별한다. 마감이 임박한 행사에는 승인 없이 참석하지 않도록 실제 상태를 전달할 수 있다.

일주일 뒤에도 역할 논의가 없다면 사용자에게 ‘연결 확률이 높아졌다’고 주장할 수 없다. 준비된 자료를 재사용해 다른 검증된 접근을 시도할지, 공개된 OpenAI 공고에 지원할지, 기다릴지 판단할 수 있다. 새 수신자·새 공개 범위는 실제 위임에 따라 처리한다. 반응이 없다는 이유만으로 목표 기본급을 낮추거나, 의미 없는 후속 메일을 계속 보내지 않는다.

사용자가 첫 제안 후 답하지 않은 경우에도 마찬가지다. 이미 맡긴 탐색은 계속할 수 있지만, 발송·소개가 승인됐다고 가정하지 않는다. 새로 중요한 발견이 있거나 실제 마감이 있을 때만 그 사실과 필요한 결정을 전달한다.

### 6.3 첫날 전체 처리량

Decisions 비용을 싸게 보이게 하려고 공통 입력 재사용을 보장된 것으로 계산하지 않는다. 초벌 `96개 × 4질문 × 질문당 입력 3,200 tokens`, 보강 `16개 × 4질문 × 입력 6,000 tokens`로 중복 과금되는 보수적 경우를 계산한다. 합계 입력 1,612,800 tokens, 질문 448개에 출력/추론 256 tokens씩인 114,688 tokens를 가정한다. native Decisions가 공통 state를 한 번만 과금하면 실제 값은 더 낮아질 수 있고, 추론이 길면 더 높아질 수 있다. provider의 실제 usage가 정본이다.

### 6.5 어디에서 이 계산이 크게 틀어질 수 있는가

- **메인 context가 커짐:** 15회에 평균 입력 100k가 들어가면 입력만 $1.50이다. 출력 28k와 나머지 같은 사용량을 더하면 첫날 소계는 $2.090624다. 모든 과거 본문을 매번 넣으면 소형 scoring만으로 해결되지 않는다.
- **모델을 바꿈:** 같은 사용량에서 메인만 Sol Standard이면 첫날 소계 $1.262624, Astra Standard이면 $4.510624다. 품질·지연 검증 없이 저렴한 모델로 바꾼다는 결론은 아니다.
- **조사를 대상별 Agent API로 바꿈:** Exa high는 공개 단가상 호출당 $0.50다. 96개에 한 번씩이면 그 부분만 $48이다. 첫날 $0.86 계산과 완전히 다른 실행이다. 구조화 tool 하나라는 외형으로 이 비용을 숨기지 않는다.
- **Jev를 사용함:** 위 보수적 입력량이면 평가 항목 비용은 $0.0677376이다. Luna 평가 $0.218624를 대체할 경우 첫날 소계 $0.7057376. 같은 질문에서 중요한 누락이 늘지 않는지 확인해야 한다.
- **검색이 빈약함:** 96개가 실제로 적절한 회사를 포함하지 못했다면 싸게 계산해도 실패다. 다른 source·질의·더 깊은 조사가 필요하면 비용을 추가한다. 24회 검색·16개 심층 검토를 강제해 비용 표에 맞추지 않는다.
- **사람의 답이 없음:** API 비용이 낮아도 실제 역할 논의가 생기지 않을 수 있다. 발송 수로 획득 가능성 개선을 증명하지 않는다.

## 8. Javier 밖의 요청에도 개선이 유효한가

| 다른 요청 | 같은 계약으로 처리하는 방식 | 복잡도가 늘지 않아야 할 부분 |

아직 확인하지 못한 것은 실제 검색 재현율, model의 후보 선택과 설명 품질, 대상별 조사 깊이, 15회라는 메인 호출 가정, 실제 토큰·지연·인프라 원가, 사용자의 연결·응답·선택률, 상대의 반응이다. 첫 구현에서는 Javier의 현재 자료를 고정한 개발 입력과 별도 합성 사용자/상대 반응으로 전체 흐름을 확인하고, 실제 사용자 계정에는 가상 회신·예약·지원 결과를 쓰지 않는다. 시뮬레이션의 이름 네 개를 정답으로 강제하지 않는다.

좋은 첫 결과의 기준은 **이미 아는 조건을 다시 묻지 않고, 실제로 가치 있는 대상과 중요한 미확인 조건을 보여주며, 선택한 기회를 얻기 위한 준비·허용된 실행을 끝내고, 다음 확인이 실제로 이어지는 것**이다. 합격·오퍼는 그 뒤 관측할 별도 결과다.
