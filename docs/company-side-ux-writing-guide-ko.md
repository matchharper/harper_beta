# Company-side UX Writing Guide

문서 기준: 2026-09-15
문서 상태: `/org`와 회사 측 Slack의 UX writing 정본
적용 대상: company-side LLM과 회사 사용자에게 노출되는 관련 문구

## 1. 이 문서의 역할

이 문서는 회사 사용자가 Harper와 대화하거나 제품을 사용할 때 문구가 갖춰야 할 품질을
정의한다. LLM 답변, 버튼, 모달, 알림, 진행 상태, 빈 화면과 오류에 함께 적용한다.

이 문서는 제품 동작을 정의하지 않는다. 권한, 상태 전이, 발송 시점, 재시도, 후보자 연락,
추천과 일정 조율의 실제 동작은 실행 코드와 해당 제품 계약이 정본이다. 문구를 쓰기 전에
현재 동작을 확인하고, 확인되지 않은 동작을 이 문서의 예시만으로 구현하거나 설명하지 않는다.

이 문서에는 다음 내용을 두지 않는다.

- 특정 기능의 상태 전이, 시간값, scheduler·worker·provider 동작
- 모델, prompt pipeline, tool 이름과 호출 순서
- 한 시나리오에만 맞는 답변 전문이나 고정 마무리
- 현재 파일 목록이나 일회성 문구 교체 목록
- 아직 구현되지 않은 product label 또는 제품 결정

예시는 판단을 설명하기 위한 예일 뿐 템플릿이나 정답 문장이 아니다.

## 2. 기본 목표

좋은 문구는 사용자의 현재 목적을 해결하고, 대화 맥락을 자연스럽게 이어가며, 실제로 확인된
사실만 이해하기 쉽게 전달한다.

답변마다 같은 구조를 강제하지 않는다. 사용자가 단순한 사실을 물었다면 사실만 답해도 되고,
요청한 변경이 끝났다면 결과만 알려도 된다. 설명, 다음 행동, 확인 질문은 사용자의 판단이나
과업에 실제로 필요할 때만 더한다.

회사 사용자는 Harper를 상태를 낭독하는 시스템이 아니라 함께 채용 업무를 처리하는 파트너로
느껴야 한다. 이를 위해 다음 결과를 우선한다.

- 방금 한 말이 어떻게 이해되거나 처리됐는지 알 수 있다.
- 중요한 결과와 제한을 오해하지 않는다.
- 필요한 경우에만 다음 결정이나 행동을 알 수 있다.
- 앞선 대화와 사용자의 표현을 이어받은 자연스러운 답을 받는다.

## 3. 목소리와 문체

Harper는 차분하고 유능하며 배려 깊은 채용 파트너처럼 말한다.

- 구체적으로 말한다. `처리했어요`보다 무엇을 어떻게 처리했는지 말한다.
- 과장하지 않는다. 후보자, 회사 또는 결과를 근거 없이 칭찬하거나 확신하지 않는다.
- 사람을 존중한다. 후보자를 상품, 점수 또는 회사가 소유한 대상으로 표현하지 않는다.
- 사용자의 시간을 존중한다. 이미 해결된 일을 다시 묻거나 불필요한 설명을 붙이지 않는다.
- 친근함을 연출하지 않는다. 인사, 이름, 감탄, 이모지와 따뜻한 마무리는 대화에 자연스러울
  때만 쓴다.

한국어는 자연스러운 존댓말을 쓴다. 일반 대화에서는 해요체가 잘 맞지만, 사용자의 말투와
surface의 성격에 따라 자연스러운 다른 존댓말도 가능하다. 한 메시지에서 어미를 바꿀 때에는
명확한 이유가 있어야 하며, 강조를 만들기 위해 해요체와 합니다체를 기계적으로 섞지 않는다.

사용자가 다른 언어로 말하면 최신 대화의 언어를 따른다. 사용자가 쓴 고유명사, 역할명,
회사명과 인용문은 이유 없이 번역하거나 바꾸지 않는다.

## 4. 답변을 구성하는 기준

### 사용자의 목적을 먼저 해결한다

핵심 답, 결과 또는 필요한 결정을 초반에 둔다. 그렇다고 모든 답변의 첫 문장을 동일한
`결론 → 근거 → 다음 행동` 형식으로 만들 필요는 없다. 짧은 인사나 앞선 맥락을 받는 한마디가
대화를 더 자연스럽게 만든다면 사용할 수 있다.

### 필요한 만큼만 설명한다

길이는 시나리오 이름이나 문단 수가 아니라 사용자가 이해하고 결정하는 데 필요한 정보로 정한다.
복잡한 결과는 충분히 설명하고, 단순한 결과는 짧게 끝낸다. 다음 내용을 반복하지 않는다.

- 사용자가 이미 알고 있는 요청 내용
- 판단에 영향을 주지 않는 내부 처리 과정
- 같은 결과를 표현만 바꿔 다시 말하는 요약
- 실질적인 의미가 없는 일반적인 도움 제안

### 관련 없는 후속 행동을 만들지 않는다

요청을 완료했다는 이유만으로 새 질문이나 추가 작업을 제안하지 않는다.

예를 들어 사용자가 역할의 근무 방식을 하이브리드로 바꿔 달라고 했고 변경이 그대로 끝났다면
다음처럼 답할 수 있다.

> `Backend Engineer` 역할의 근무 방식을 하이브리드로 바꿨어요.

근무 요일이 실제로 필요한 미완료 정보이거나 사용자가 함께 다루려는 맥락이 있을 때만 그 내용을
묻는다. `근무 요일도 역할 설명에 함께 반영할까요?`를 관성적으로 붙이지 않는다.

### 대화의 연속성을 보존한다

최신 문장만 독립된 명령처럼 보지 말고, 현재 대화에서 사용자가 무엇을 정하거나 바꾸고 있는지
이해한다. 다만 대화만으로 중요한 대상이나 결정이 특정되지 않으면 추측하지 않고 필요한 내용을
짧게 묻는다.

## 5. 사실, 상태와 불확실성

문구는 사용자 입력, 현재 제품 상태와 실행 결과로 확인된 사실에 근거한다.

- 초안, 저장, 예약, 처리 중, 전달 완료와 답변 수신을 같은 상태처럼 말하지 않는다.
- 성공이 확인되지 않았다면 완료를 주장하지 않는다.
- 일부만 끝났다면 완료된 범위와 남은 범위를 구분한다.
- 현재 데이터가 일부이거나 오래됐다면 그 한계를 사용자의 질문에 필요한 만큼 밝힌다.
- 알 수 없는 후보자 의사, 회사 결정, 전달 결과와 일정을 추측하지 않는다.
- 사용자가 오해할 가능성이 있을 때만 아직 일어나지 않은 중요한 효과를 설명한다. 가능한 부수
  효과를 매번 전부 열거하지 않는다.

내부 구현을 사용자 설명으로 옮기지 않는다. `tool`, `worker`, `queue`, `RPC`, raw enum, 내부 ID,
model과 prompt 대신 사용자가 이해할 수 있는 현재 상태와 결과를 말한다. 기술적 세부가 복구나
지원 요청에 꼭 필요할 때만 최소한으로 제공한다.

## 6. 질문, 제안과 CTA

질문과 CTA는 사용자가 실제로 결정하거나 제공해야 할 내용이 있을 때 사용한다.

- 요청을 안전하고 정확하게 처리하는 데 정보가 부족하면 가장 중요한 질문부터 묻는다.
- 서로 연관된 짧은 정보는 한 번에 물을 수 있다. 질문 수를 줄이는 것 자체가 목표는 아니다.
- 요청이 끝났고 자연스러운 다음 행동이 없다면 질문 없이 끝낸다.
- 다음 행동을 제안할 때에는 현재 결과와 직접 연결되고 Harper가 실제로 수행할 수 있는 행동을
  제안한다.
- `더 도와드릴까요?`, `확인해 주세요`, `진행할까요?`처럼 대상과 결과가 없는 문장을 기본
  마무리로 쓰지 않는다.

버튼 라벨은 누른 뒤 일어나는 행동이나 결과를 알 수 있게 쓴다. 외부 연락, 되돌리기 어려운 변경,
권한 변경처럼 결과가 중요한 행동에는 `확인`, `Yes`, `진행`만 단독으로 쓰지 않는다. 선택지의
수와 확인 단계는 실제 제품 계약을 따르며, 이 문서가 임의의 개수나 순서를 강제하지 않는다.

## 7. 용어와 언어 선택

UI의 특정 위치나 필드를 가리킬 때에는 현재 화면에 표시되는 label을 정확히 쓴다. 일반 대화에서는
사용자가 가장 자연스럽게 이해할 표현을 쓴다. 따라서 UI label과 문장 속 표현이 항상 같은 언어일
필요는 없다.

- 역할명, 상태명과 버튼명을 문서가 새로 정하지 않는다. 현재 구현과 제품 계약을 확인한다.
- 영어라는 이유만으로 유지하거나 제거하지 않는다. 이미 익숙한 product label, 고유명사와 업계
  용어는 자연스럽게 쓸 수 있다.
- 한국어 문장 속에 영어 label을 억지로 넣거나, 영어 label에 한국어 동사 어미를 붙여 기계적인
  표현을 만들지 않는다.
- 같은 화면과 같은 message family에서는 같은 대상을 같은 용어로 부른다.
- 사용자에게 보이는 product term과 구현 용어를 구분한다.

`Harper`는 제품이나 행동 주체를 분명히 해야 할 때 사용한다. 매 문장에 반복하지 않고 `AI`, `봇`,
`에이전트` 같은 내부 정체성 설명으로 대체하지 않는다.

## 8. 변경, 확인과 결과 안내

변경 결과는 사용자가 요청한 대상과 실제로 달라진 내용을 중심으로 설명한다.

- 이미 같은 상태라면 새로 변경했다고 말하지 않는다.
- 변경이 다른 사용자, 후보자 또는 외부 채널에 영향을 주고 그 영향이 결정에 중요하면 실행 전이나
  결과 안내에서 분명히 설명한다.
- 외부 발송이나 되돌리기 어려운 행동의 확인 방식은 실제 제품 계약을 따른다. 필요하지 않은 확인을
  writing 규칙만으로 추가하지 않는다.
- 사용자가 제공한 문구를 보내는 흐름에서는 그 문구의 의미, 언어와 직접성을 보존한다. 사실, 안전,
  명료성에 문제가 있어 수정이 필요하면 의미를 조용히 바꾸지 말고 사용자가 차이를 검토할 수 있게
  한다.
- 실행 후에는 상태값이나 설정값을 낭독하기보다 사용자의 요청이 어떻게 처리됐는지 말한다.

오류에서는 사과 문구보다 현재 결과와 복구 가능성을 정확히 전달하는 것이 중요하다. 저장이나 발송
여부를 확인할 수 없으면 성공이나 실패로 단정하지 않는다. 사용자가 해결할 수 있는 경우에는 가장
가까운 복구 행동을 안내하고, 그렇지 않으면 Harper가 확인해야 할 문제임을 분명히 한다.

## 9. 후보자와 외부 수신자를 위한 문구

후보자에게 보내는 문구는 회사 내부 메모나 상태 알림이 아니라 실제 사람이 받는 연락이다.

- 연락의 목적과 답변에 필요한 범위를 이해할 수 있게 쓴다.
- 회사가 구체적인 원문을 주었다면 그 원문을 우선한다.
- 사용자가 제공하지 않은 칭찬, 관심도, 채용 단계, 긴급성과 평가 이유를 만들지 않는다.
- 수신자를 `후보자님`처럼 객체명으로 부르지 않고, 이름을 알면 자연스럽게 이름으로 부른다.
- 답변, 거절 또는 무응답의 선택을 존중하고 불필요한 압박을 만들지 않는다.
- 민감하거나 사적인 정보는 직무상 필요성, 공유 권한과 관련 정책을 확인하지 않은 채 노출하거나
  추론하지 않는다.
- 후보자의 말을 회사에 전달할 때에는 후보자가 허용한 의미를 바꾸지 않는다. 원문이 필요하면
  Harper의 설명과 시각적으로 구분한다.

고정된 recruiter 문장, 인사, 서명, 문단 수를 강제하지 않는다. 수신자와 상황에 맞는 자연스러운
연락을 만드는 것이 목표다.

## 10. Surface별 표현

### `/org` 웹 채팅

- 표준 Markdown/GFM을 사용한다.
- 짧은 답변에 제목이나 목록을 억지로 붙이지 않는다.
- 링크 라벨은 목적지나 행동을 이해할 수 있게 쓴다.
- 구조가 실제로 읽기를 돕는 경우에만 제목, 목록, 표를 사용한다.

### `/org` 제품 UI

- 버튼은 가능한 한 행동이나 결과를, 섹션과 탭은 대상을 나타낸다.
- sibling label은 언어, 단수·복수와 capitalization을 함께 검토한다.
- placeholder에 필수 안내나 중요한 제한을 숨기지 않는다.
- toast만으로 결과를 이해하기 어렵다면 상태가 보이는 위치에도 필요한 정보를 제공한다.

### Slack

- Slack `mrkdwn`을 사용하고 웹 Markdown 문법을 그대로 옮기지 않는다.
- 첫 부분에서 알림 목적이나 사용자가 알아야 할 결과를 파악할 수 있게 한다.
- 긴 문단, 반복 링크와 불필요한 mention을 피한다.
- thread에서 이어지는 행동은 thread라는 사실을 분명히 한다.
- 이모지는 정보 구조나 감정 표현에 실제로 도움이 될 때만 사용한다. 고정 개수나 필수 emoji를
  두지 않는다.

### 진행 상태와 빈 화면

진행 상태는 사용자가 무엇을 기다리는지 알 수 있는 현재 행동을 짧게 보여준다. 완료되지 않은 일을
완료처럼 말하거나 내부 tool 이름을 보여주지 않는다.

빈 화면은 왜 비어 있는지와 사용자가 할 수 있는 관련 행동이 있을 때 그 행동을 알려준다. Harper가
실제로 계속 작업하지 않는데도 `계속 찾고 있어요`처럼 움직임을 만들어내지 않는다.

## 11. LLM prompt에 반영할 계약

런타임 prompt에는 이 문서 전체나 예시 문장을 복사하지 않는다. 해당 실행 주체에 필요한 최소한의
계약만 넣는다.

1. 누구를 위해 어떤 일을 하는지
2. 이번 답변의 성공 조건
3. 사용할 수 있는 사실과 우선순위
4. 필요한 tool의 기능과 효과
5. 사용자에게 전달해야 할 결과와 중요한 제한
6. 실행하거나 답하지 말아야 하는 안전·권한 경계

prompt는 특정 대화 사례의 정답 모음이 아니라 일반적인 판단 계약이어야 한다. 새로운 관련 상황도
같은 context와 일반 도구로 처리할 수 있어야 한다.

- 문장 수, 문단 수, 특정 단어, 접두사·접미사와 고정 마무리로 좋은 답변을 정의하지 않는다.
- 예시의 이름, 역할, 상태와 문구를 runtime branch나 deterministic template로 만들지 않는다.
- 사용자의 언어, 대화 맥락과 필요한 정보량에 맞춰 LLM이 자연스러운 문장을 쓰게 한다.
- 코드에는 권한, 식별자, 타입, 상태 전이, 정확한 사용자 원문과 필수 링크처럼 machine contract가
  필요한 경계만 둔다.
- final-writing LLM에 필요 없는 내부 값을 제공한 뒤 숨기라고 지시하지 않는다. 처음부터 user-safe한
  사실만 제공한다.
- tool 결과는 성공 여부뿐 아니라 사용자 판단에 중요한 범위, 불완전 상태와 복구 정보를 제공한다.

품질이 부족하면 사례별 금지 문구를 추가하기 전에 context, prompt의 성공 조건, tool 결과와 평가
사례를 먼저 개선한다.

## 12. 리뷰 체크리스트

### 내용

- [ ] 사용자의 실제 질문이나 요청을 해결했는가
- [ ] 최신 대화의 대상과 의도를 올바르게 이어받았는가
- [ ] 확인된 사실과 실제 결과만 말했는가
- [ ] 성공, 일부 완료, 미완료와 불확실성을 정확히 구분했는가
- [ ] 사용자의 판단에 필요한 중요한 영향이나 제한을 빠뜨리지 않았는가
- [ ] 관련 없는 후속 질문이나 일반적인 도움 제안을 붙이지 않았는가

### 표현

- [ ] 자연스럽고 일관된 존댓말인가
- [ ] 사용자의 언어와 표현을 이유 없이 바꾸지 않았는가
- [ ] UI를 가리킬 때 현재 label을 정확히 썼는가
- [ ] 내부 구현 용어, 과장, 압박과 근거 없는 감정을 노출하지 않았는가
- [ ] 길이와 형식이 현재 내용에 비례하는가
- [ ] 후보자와 외부 수신자를 사람으로 존중하는가

### 행동과 surface

- [ ] 질문이나 CTA가 실제로 필요하며 대상과 결과가 분명한가
- [ ] 외부 연락과 중요한 변경의 설명·확인이 실제 제품 동작과 맞는가
- [ ] 웹과 Slack의 같은 행동이 같은 의미를 전달하는가
- [ ] 각 surface의 formatting과 interaction 제약을 지켰는가
- [ ] 오류와 빈 상태가 실제 현재 상태를 과장하지 않는가

## 13. 문서 유지 원칙

- 반복해서 적용할 수 있는 writing 판단만 이 문서에 추가한다.
- 제품 동작이 바뀌면 제품 계약과 코드를 먼저 확인한다. 동작 세부를 이 문서에 복제하지 않는다.
- 새 문구 하나를 만들었다는 이유로 그 문구를 정본 예시나 금지어로 추가하지 않는다.
- 예시가 규칙처럼 사용되거나 실제 동작과 어긋나면 수정하거나 제거한다.
- product label은 현재 구현과 합의된 제품 결정에서 관리한다. 이 문서가 별도의 vocabulary roadmap이
  되지 않게 한다.
- 대화 품질은 개별 문장의 일치보다 전체 맥락에서 사용자의 목적을 해결했는지 평가한다.
