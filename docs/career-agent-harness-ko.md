# Harper Career harness: 맥락·기록·기억 구조

- 시작: 2026-11-19
- 다루는 질문: Career agent(Harper)가 매 턴 무엇을 보고, 무엇을 어디에 남기며, 다음 대화와 예약 실행에서 어떻게 이어 가는가. note, Memory·Brief, 회사에 붙인 기억, 회사 공유 자료, 실행 기록, 예약·팔로우·메일로 깨우는 경로, 매 턴 입력과 도구 결과의 모양을 다룬다.
- 다루지 않는 것: 좋은 기회를 어떻게 찾고 판단하는가는 [좋은 기회를 어떻게 추천할까](career-good-opportunity-recommendation-ko.md)가 다룬다. 두 문서가 겹치는 곳은 서로 링크한다.
- 성격: 이 질문에 대한 팀의 현재 생각을 담는 정본이다. 구조를 토론·설계·구현·리뷰할 때 먼저 읽고, 생각이나 구현이 바뀌면 고친다.

## 0. 이 문서를 쓰는 방법

- **본문은 늘 현재 생각이다.** 생각이 바뀌면 해당 절을 고치고 [10절](#10-바뀐-생각)에 날짜, 바뀐 내용, 이유를 한 줄로 남긴다. 옛 문장은 본문에 남기지 않는다.
- **주장마다 상태를 단다.** **합의**는 팀이 정한 것이다. **가설**은 믿고 있지만 아직 확인하지 못한 것이다. **열림**은 토론 중인 것이다.
- **의견을 낼 때는 근거가 되는 절을 밝힌다.** 구조에 관한 설계·구현·리뷰 의견은 이 문서의 어느 주장에 기대는지, 또는 어느 주장과 부딪치는지 함께 말한다. 부딪친다면 이 문서를 고칠지부터 묻는다.
- **코드·DB 사실에는 확인한 날짜와 경로를 붙인다.** 로컬 구현과 운영 반영을 구분한다. 운영 반영 여부는 [운영 적용 기록](agent-guidance/rollout-history.md)으로 확인한다.
- **구현하면 [3절](#3-지금-구조)과 [6절](#6-구현-상태와-다음-순서)을 고친다.** 문서만 고치고 구현했다고 적지 않는다.
- **runtime prompt에 통째로 넣지 않는다.** 이 문서는 팀과 개발 agent가 판단할 때 쓰는 기준이다.

## 1. 이 구조가 이루려는 것 — 합의(2026-11-19)

Harper는 원본 agent LLM에게 적절한 맥락과 범용 도구를 주고, LLM이 사용자 목적을 끝까지 수행하게 하는 제품이다([공통 설계 원칙](../../AGENTS.md)). 이 문서의 구조는 그 맥락이 대화와 실행을 넘어 이어지게 하는 방법이다. 이루려는 것은 다섯 가지다.

1. **같은 일을 반복하지 않는다.** 무엇을 왜 했는지 대화 기록과 따로 남겨, 다음 요청이 처음부터 다시 찾지 않게 한다. "어떤 기회를 찾아 줘야 이 사람이 좋아할까"처럼 한 번 깊이 고민한 판단을 다시 쓴다. 성능은 높이고 비용은 줄인다.
2. **판단을 스스로 고친다.** 예전 추천을 왜 했는지 기억하고, 사용자 반응을 보고 판단을 고친다.
3. **찾아 둔 것을 다시 꺼낸다.** 다섯 곳을 찾아 두 곳만 보여 줬다면, 나머지를 다음 요청에서 꺼낼지 Harper가 판단한다. 규칙으로 정하지 않는다.
4. **Harper의 생각이 남는다.** "이런 이유로 이 방향을 제시한다" 같은 판단을 한 번 정하면 다음에 참고하고, 새 근거가 생기면 고친다.
5. **찾은 것은 쌓인다.** 한 사용자를 위해 찾은 회사, 공개 공고, 회사 정보, 공개 연락 경로는 다른 사용자에게도 쓰인다.

## 2. 원칙

[공통 설계 원칙](../../AGENTS.md)과 [LLM 설계·입력·검증](agent-guidance/llm-engineering.md)을 따른다. 아래는 그중 이 구조에 직접 쓰이는 것과, 외부 사례에서 확인한 것이다.

### 2.1 사실은 서버가, 해석은 Harper가 쓴다 — 합의

검색, 열람, 추천, 반응, 발송처럼 실제로 일어난 일은 서버가 기록한다. Harper는 서버가 알 수 없는 것을 쓴다. 왜 그렇게 했는지, 무엇을 알게 됐는지, 다음에 무엇을 볼지다. 두 기록은 섞지 않는다. 섞으면 Harper가 자기 글을 고칠 때 서버 기록이 지워질 수 있다. Anthropic과 OpenAI의 장기 실행 harness도 같은 방식이다(9절).

### 2.2 범위와 경계는 코드가, 무엇을 남길지는 Harper가 정한다 — 합의

누구의 기록인지, 누구에게 보일지, 같은 알림을 두 번 보내지 않는지, 동시에 고친 내용이 서로 덮어쓰지 않는지는 코드가 지킨다. 무엇을 남기고 어떻게 쓸지는 Harper가 정한다. 남기라는 지시를 늘리지 않고, 남기는 이유(다음 요청은 이 기록에서 시작한다)를 알린다(2026-11-17 지침).

### 2.3 사실과 추정을 나눈다 — 합의

사용자가 말했거나 확인한 것은 Memory와 Brief에 둔다. Harper의 추정과 판단은 note에 둔다(4.1). 여러 행동에서 추론한 선호를 Memory 사실로 쓰지 않는다([Career Memory 계약](agent-guidance/career-memory.md)).

### 2.4 기본 맥락에는 목록을 넣고, 본문은 필요할 때 읽게 한다 — 합의

항상 넣는 글이 길수록 모델의 판단이 나빠진다(9절). 기본 맥락에는 최근 몇 개의 날짜·제목과 전체 개수를 넣고, 본문은 `read_*` 도구로 읽게 한다. Harper의 다른 자료(문서, 매칭, 예약)와 같은 방식이다.

### 2.5 통째로 다시 쓰기보다 고칠 곳만 고친다. 날짜를 보여 준다 — 가설

LLM이 긴 요약을 통째로 다시 쓰면 내용이 줄거나 어긋나는 사례가 반복해서 보고됐다. 버리지 않은 옛 기억이 틀린 추천을 만든다는 사례도 있다(9절). 그래서 기록은 고칠 곳만 고치고, 기억과 판단에는 날짜를 함께 보여 준다. 오래된 것인지는 Harper가 판단한다.

### 2.6 공개 사실은 회사 단위로 쌓고, 개인 맥락은 사용자 범위에 둔다 — 합의

회사 개요, 채용 신호, 공개 공고, 공개 출처가 있는 연락 경로는 `company_workspace`에 모아 모든 사용자가 쓴다. 사용자의 입장과 판단, Gmail이나 대화에서 알게 된 사실은 그 사용자 범위에 둔다([좋은 기회](career-good-opportunity-recommendation-ko.md) 2.7).

### 2.7 변화가 없으면 모델을 부르지 않는다 — 합의

매일 모든 사용자를 무조건 실행하지 않는다. 새 답장, 자료 변경, 회사 변화, 사용자와 정한 예약이 Harper를 깨운다([이상적 구조](career-ideal-architecture-ko.md) 12절).

## 3. 지금 구조

2026-11-19 로컬 checkout 기준이다. note와 Memory 회사 연결은 같은 날 로컬에 구현했고 운영에는 적용하지 않았다(6절). 운영 배포 여부는 따로 적은 것 말고는 확인하지 않았다. 저장소 24곳의 전체 지도는 [현재 구조 지도](../../research_notes/에이전트%20기억과%20작업%20기록%20설계/harper_current_state.md)에 있다.

### 3.2 이미 있는 장치

새 구조를 만들기 전에 먼저 쓸 수 있는 것이다.

- **변화로 깨우는 경로.** 공개 자료가 바뀌면 관련 예약을 깨운다(`target_refs.discovery`). 같은 사건은 멱등 키로 한 번만 만든다(`20261113153813_career_discovery_delivery.sql`).
- **메일 답장을 기다리는 경로.** 맡긴 일이 기다리는 Gmail 스레드에 답장이 오면 그 일을 찾는다(`career_mail_waiters_v1`).
- **사용자별 묶음 실행.** 새 사건은 그 사용자의 진행 중인 실행에 붙는다(`career_admit_discovery_events_v1`).
- **위임의 권한 경계.** 맡긴 일은 사용자 원문 참조가 없으면 시작하거나 바꿀 수 없다(`20261113155021_career_work_responsibility_routes.sql`).
- **회사 차단 설정.** `talent_setting.blocked_companies`로 Career 기회 검색과 회사 측 후보 조회를 모두 거른다. 회사명 부분 일치이고, Harper가 이 값을 쓸 도구는 없다.
- **회사 개요 캐시.** Exa로 만든 개요를 30일 동안 쓰고, 같은 회사를 동시에 두 번 만들지 않게 회사별 lease를 둔다(`resources/companyData.ts`).
- **테스트 계정 격리.** 테스트 계정은 Career 예약을 멈추고 외부 실행에서 빠진다(2026-11-19 지침). 새 깨움 경로도 같은 경계를 따라야 한다.

### 3.3 확인된 빈틈

코드에서 확인한 사실이다. 2026-11-19 로컬 구현으로 1·2·3·4·8·9·11번은 해소됐고 12번은 일부 고쳤다. 나머지는 고치지 않았다.

1. 자동으로 쌓이는 작업 기록은 매칭 노트뿐이다. 그마저 매칭이 정해진 요청에서 도구 일곱 개만 기록한다.
2. 노트에 반응을 남기는 trigger는 수정(UPDATE)에만 걸리고 `role_id`로 매칭을 찾는다. 처음 저장한 반응, 회사 추천에 대한 반응, 이유만 바꾼 반응이 노트에 남지 않는다(`20261117203000_career_matching_feedback_note_never_blocks.sql`).
3. 예약 실행은 마지막 글을 저장하지 않는다. 무엇을 확인했고 왜 알리지 않았는지 남지 않는다(`background/server.ts:139`).
4. 대상 매칭이 둘 이상인 예약 실행에는 노트를 넣지 않는다(`background/server.ts:117-121`).
5. 팔로우 변화를 감지하는 RPC(`read_career_follow_scan`)를 운영 코드에서 부르는 곳이 없다.
6. 순위를 매기는 평가는 노트를 읽지 않는다. 진행 중인 매칭은 만들 때 고정한 조건으로 평가한다(`matching/externalSearch.ts:215-244`).
7. 채팅에서 바로 검색할 때는 Behavior Context를 새로 만들지 않는다(`matching/externalSearch.ts:268`). 방금 남긴 반응이 평가에 반영되지 않을 수 있다.
8. 기본 맥락에서는 반응과 함께 그 기회를 왜 추천했는지가 보이지 않는다. 반응 요약을 만드는 함수는 추천 이유를 계산하고도 요약에 넣지 않는다(`talentOnboarding/activityEvents.ts:499-508`). 아직 다루지 않은 반응 블록의 추천 이유 자리도 채우지 않는다(같은 파일 672, 748-760행). 최근 추천 10개에도 추천 이유가 없다. 매칭 개요(`read_matching`)를 읽어야 추천마다 이유와 반응을 함께 본다(`matching/formatters.ts:81`).
9. 기회 검색은 검색 이력 조회(`read_talent_activity_events`)에 나오지 않는다.
10. 맡긴 일의 경과 메모(`result.note`)는 갱신할 때마다 덮어쓴다.
11. 노트 항목을 고치면 이전 글이 남지 않는다. 노트 테이블에는 revision 숫자만 있다.
12. 설명끼리 어긋난다. 팔로우가 하는 일, `write_talent_context`의 매칭 갱신 문구(그 trigger는 2026-10-15에 제거됐다), proactive handbook이 Gmail 검토를 'private Memory'에서 시작하라는 문구다.

### 3.4 매 턴 입력과 도구 결과

- **입력 순서.** 고정 지침(기본 프롬프트, 표시 규칙) → Profile과 최근 추천 10개 → Brief와 고른 Memory → 실행 맥락(할 일, 쓸 수 있는 기능, 매칭·예약·팔로우·문서·미해결 폼 색인, 최근 활동, 아직 다루지 않은 반응) → 현재 시각 → 대화(요약과 그 뒤 메시지) → 작업 대상 매칭의 노트 순서다(`prompts/promptCaching.ts`, `talentOnboarding/llm.ts`). 바뀌는 블록은 캐시가 유지되는 부분 뒤에 둔다(2026-11-18 지침).
- **이어지는 것.** 한 응답 안의 도구 결과는 다음 턴으로 넘어가지 않는다. 다음 턴이 이어받는 것은 DB에 남은 기록뿐이다. 그래서 이 문서의 구조가 필요하다.
- **도구 결과의 모양.** 모델이 바로 읽을 텍스트로 바꿔 판단에 필요한 사실만 준다. 점수는 가중 점수 하나만 주고, 맥락에 이미 있는 내용은 반복하지 않는다([LLM 설계](agent-guidance/llm-engineering.md), 2026-11-18 지침).
- **새 요소가 들어갈 자리(제안).** note 목록은 실행 맥락의 색인에, 작업 대상 note의 본문과 탐색 요약은 지금 노트 블록 자리에, 회사에 연결한 Memory는 그 회사가 나오는 도구 결과 안에 둔다.

## 4. 정한 것

### 4.1 note — 합의(2026-11-19)

**무엇인가.** note는 큰 단위의 주요 작업을 그 단위로 묶어 기억하고, 나중에 참고하려고 남기는 글이다. 보통 기회 탐색이나 지원 과정이 한 단위가 된다. 회사 한 곳을 조사한 정도는 note로 남기기에 작다. 단위를 미리 정하지는 않는다. 무엇을 한 단위로 볼지는 Harper가 정한다. 기회 탐색이든 지원·연결이든 Harper가 남기는 글은 note 하나에 쓴다. 예약·팔로우·맡긴 일의 연속성은 5절 13번에서 정한다.

**목적 — 합의(2026-11-19).** note는 했던 일을 기록해 나중에 같은 일을 다시 하지 않게 하려고 둔다. 매칭에 연결한 work note에는 그 탐색에서 얻은 교훈과 전체 작업의 요약을 남긴다.

**종류는 둘이다.**

- `think`: Harper의 생각. 왜 이 방향을 제안하는지, 어떤 가설을 세웠는지, 무엇을 보면 판단을 바꿀지.
- `work`: 작업의 기록. 무엇을 어디까지 찾았고 무엇을 알게 됐는지, 무엇을 왜 뺐고 무엇을 남겨 뒀는지.

**구조.** 종류(`kind`: `think` 또는 `work`), `title`, `content`, 그리고 기본 열(`id`, `talent_id`, `created_at`, `updated_at`)로 이루어진다. 채팅 턴과 예약 실행이 같은 note를 동시에 고칠 수 있으므로, 서로 덮어쓰지 않게 막는 revision도 기본 열로 둔다(2.2). 매칭(`matching_id`)이나 회사(`company_workspace_id`)에 연결할 수 있지만 연결하지 않아도 된다. 그 밖에는 Gmail 연결을 끊을 때 지울 note를 찾는 출처 참조(`source_refs`)만 둔다(아래 ‘연결한 메일 내용’).

**고치는 방식 — 합의(2026-11-19).** 본문은 통째로 바꿀 수도 있고, 덧붙이거나 일부만 바꿀 수도 있다. 긴 note를 통째로 다시 쓰면 내용이 줄 수 있기 때문이다(2.5). 고친 note의 이전 글은 따로 저장하지 않는다. 덧붙이기와 일부 교체로 고치므로 통째로 사라질 일이 적고, 읽는 곳이 분명하지 않은 저장은 만들지 않는다([LLM 설계](agent-guidance/llm-engineering.md)). 평가에서 note가 어떻게 바뀌는지 보려면 평가 기록에 턴마다 남긴다.

**모델에 닿는 방식.** 다른 맥락처럼 최근에 고친 note 10개의 날짜·종류·제목·연결 대상과 전체 개수를 기본으로 넣는다(10개는 합의 2026-11-19). 더 보고 싶으면 목록을 이어 읽고, 하나를 골라 본문을 읽는다. 도구는 다른 자료처럼 `read_*`와 `upsert_*`로 둔다.

**작업 대상이 분명하면 본문과 탐색 요약도 넣는다 — 합의(2026-11-19).** 매칭 카드에서 이어 찾을 때나 그 매칭을 대상으로 한 예약이 돌 때는 연결된 work note의 본문을 처음부터 넣는다. 어디까지 찾았는지를 처음부터 보게 하고, 도구 호출 한 번을 아낀다. 연결된 work note가 여럿이면 가장 최근 것의 본문과 나머지의 제목을 넣는다. 여러 일이 함께 깨어난 예약 실행에는 일마다 넣는다(3.3의 4번).

그 매칭의 탐색 요약도 함께 넣는다. 탐색 요약은 서버가 기록으로 계산하는 몇 줄이다. 이 매칭에서 평가한 후보 수, 추천·반응 수, 경로마다 몇 번 찾았고 새 후보가 몇 위까지 들었는지를 담는다. 이 계산은 이미 있다(`matching/poolRead.ts`의 `readPoolSummary`). 여기에 웹 검색 횟수와 마지막 검색 날짜를 더한다. work note가 Harper가 쓴 ‘왜’라면, 탐색 요약은 서버가 센 ‘얼마나’다. Harper가 찾은 범위를 빠뜨리거나 잘못 적어도 요약은 틀리지 않는다. Harper가 work note를 직접 읽을 때도 같은 요약을 붙인다. 요약은 note 본문에 저장하지 않는다(2.1).

기본 맥락에 들어가는 목록은 예를 들어 이렇다.

```text
note 14개 · 최근 고친 10개
11/11 [work] LLM 제품 백엔드 탐색 · 매칭 「LLM 제품 백엔드」
11/11 [think] AI 제품 백엔드부터 제안한다
11/10 [work] AI 인프라·ML 플랫폼 탐색 · 매칭 「AI 인프라」
11/08 [think] 첫 방향: 결제 경험을 살릴 수 있는 AI 쪽
11/07 [work] 온보딩 직후 첫 탐색
…
```

**쓰게 만드는 것.** note를 쓰라고 지시하지 않는다. note가 왜 있는지(다음 요청과 예약 실행은 note에서 시작한다)를 도구 설명과 목록 머리글에 사실로 적는다. Harper가 지시 없이 note를 쓰는지는 평가로 확인한다(7절).

**본문 — 합의(2026-11-19).** 사용자가 참고한 서비스의 note 화면을 기준으로 삼는다. 그 화면의 note는 이렇게 쓰였다.

- 제목은 그 일이 무엇이었는지 구체적으로 말하고, 날짜와 시각이 붙는다.
- 본문은 agent가 1인칭 과거형으로 쓴 이야기다. 사용자가 무엇을 말했는지(원문 인용), 그것을 어떻게 읽었는지, 무엇을 왜 하기로 했는지(하지 않기로 한 것도), 실제로 무엇을 했는지, 사용자가 어떻게 반응했는지가 이어진다. 응답하지 않은 것도 반응으로 적는다.
- 끝에는 기준 시각을 밝힌 열린 일 목록이 있다. 항목마다 지금 상태(답을 기다림, 등록됨, 아직 듣지 못함)와 다시 찾아갈 참조(카드·제안·파일의 ID)가 붙는다.

목표는 다음 요청이 note 하나만 읽고 이어 가는 것이다. 이 모양을 prompt에 양식으로 넣지는 않는다. 답변 대본이나 필수 항목 목록을 두지 않는다는 [공통 설계 원칙](../../AGENTS.md)을 따른다. 도구 설명에는 note가 왜 있는지만 적고, 이 모양에 가까운지는 평가로 본다(7절).

참고 화면의 note는 대화가 끝난 뒤에 쓴 것으로 보인다. 사용자가 앱을 닫은 시각까지 적혀 있다. Harper에는 대화 뒤에 따로 요약하는 모델을 두지 않는다([Career Memory 계약](agent-guidance/career-memory.md)). Harper가 대화 중에 쓰고, 그 뒤의 반응은 다음 턴에 보고 덧붙인다.

**예시.** 위 기준을 따랐다.

```text
[think] AI 제품 백엔드부터 제안한다 · 2026-11-11 14:05

온보딩에서 사용자는 결제 백엔드 5년 경력을 말하고 "AI 쪽으로 가 보고 싶다"고 했다.
나는 이것을 ML 연구로 옮기겠다는 뜻보다, 지금 경험을 살려 AI 제품을 만드는 팀으로
가고 싶다는 뜻으로 읽었다.

그래서 AI 제품의 백엔드를 만드는 팀부터 제안하기로 했다. API 설계와 안정성 경험이
바로 쓰이고, 연봉도 지금보다 높을 가능성이 크다. 앞서 추천한 인프라 쪽 두 건에는
"운영 일 같다"는 반응이 있어 뒤로 미뤘다. ML 연구는 경력과 거리가 멀어 이번에는 보지 않는다.

판단을 바꿀 신호: 연구 비중이 높은 팀에 관심을 보이면 ML 쪽을 다시 본다.
제품 백엔드 추천에 연달아 싫어요가 오면 방향을 다시 묻는다.
```

```text
[work] LLM 제품 백엔드 탐색 · 2026-11-11 14:10 · 매칭 「LLM 제품 백엔드」

사용자가 "괜찮은 데 더 찾아 줘요"라고 했다. 첫 추천을 보고 같은 방향에서 더 보고 싶다는
뜻으로 읽었다.

나는 방향은 그대로 두고 찾는 경로를 넓히기로 했다. 색인 공고를 두 번, 하는 일로 회사를
두 번 찾았고, 웹에서 찾은 회사 8곳을 등록해 함께 평가했다. A사와 B사를 추천했다.
E·F·G사는 최근 인원을 줄였다는 기사(11/05)가 있어 뺐고, 이 사실은 회사 자료에 출처와
함께 남겼다. D사는 시리즈 A라 지금 기준 밖이어서 남겨 뒀다.

사용자는 A사에 좋아요를 눌렀고, B사에는 아직 반응이 없다.

열린 일(2026-11-11 15:40 기준)
1. B사 추천(추천 ID 3f2a…)에 대한 반응을 기다린다.
2. D사(후보 풀 [7])는 사용자가 초기 단계 회사도 괜찮다고 하면 다시 본다.
3. 공개 채용 글 경로는 아직 쓰지 않았다.
```

두 번째 예시가 [좋은 기회](career-good-opportunity-recommendation-ko.md)의 두 문제를 겨냥한다. 어디까지 찾았는지 남아 있어 끝없이 찾거나 너무 일찍 멈추는 일을 줄인다(그 문서 2.4). 왜 뺐는지 남아 있어 같은 회사를 다시 조사하지 않는다(그 문서 2.8). 인원 감축 같은 공개 사실은 회사 자료에도 남겨, 다음 검색과 다른 사용자에게도 보이게 한다(2.6). 열린 일에 붙은 참조(추천 ID, 후보 풀 번호)로 다음 요청은 그 자리를 바로 읽는다.

**사용자에게 보여 줄지 — 합의(2026-11-19).** 지금은 개발 환경의 조회 화면에서만 보여 준다. 실제 note가 쌓인 뒤 사용자 화면에 둘지 정한다. 사용자가 읽는다는 전제가 붙으면 Harper가 쓰는 방식이 달라질 수 있다.

**연결한 메일 내용 — 합의(2026-11-19).** Gmail을 읽은 턴에 고친 note에는 서버가 그 연결의 참조를 붙인다(`source_refs`). 사용자가 Gmail 연결을 끊으면 그 note를 지운다. Harper에게 따로 시키지 않는다. 동의에 관한 경계이므로 코드가 지킨다(2.2). 그 note의 다른 내용도 함께 사라지지만, 연결을 끊은 사용자의 뜻을 확실히 지키는 쪽을 택한다.

#### 지금의 매칭 노트를 note로 옮긴다 — 합의(2026-11-19)

매칭 노트를 따로 두지 않는다. Harper가 쓴 생각은 그 매칭에 연결한 work note로 옮긴다. 서버 실행 기록과 사용자 반응은 note에 쓰지 않는다. 이 둘은 원래 자리에 이미 남아 있다(2.1).

| 지금 매칭 노트에 있는 것 | 옮긴 뒤 |
| --- | --- |
| Harper의 생각(`harper` 항목) | 그 매칭에 연결한 work note의 본문 |
| 서버 실행 기록(`activity` 항목) | note에 쓰지 않는다. 검색·열람·평가 영수증과 검색 실행 기록에 이미 남고, `read_matching(section=history)`와 검색 이력 조회로 읽는다 |
| 사용자 반응(`user` 항목) | note에 쓰지 않는다. 추천 행과 활동 기록에 남는다. 아직 다루지 않은 반응과 최근 추천 10개로 Harper에게 가고, 지난 반응은 `read_matching` 개요(그 매칭의 추천별 이유와 반응)와 활동 기록 조회로 읽는다. 앞의 둘에도 추천 이유를 보여 줘야 한다(3.3의 8번) |
| 후보 풀 | 그대로 매칭에 둔다 |
| `read_matching(section=note)`, `upsert_matching(action="edit_note")` | note 도구(`read_*`, `upsert_*`)로 바꾼다 |
| 도구 호출의 `note`·`revisitWhen` 인자 | 없앤다. `matchingId`는 영수증을 매칭에 잇는 데 남긴다(아래 ‘도구 호출의 메모 인자’) |
| 매칭 카드의 ‘기회 더 찾아줘’, 매칭을 대상으로 한 예약 | 그 매칭에 연결한 work note의 본문과 탐색 요약을 처음부터 넣는다(위 ‘작업 대상이 분명하면 본문과 탐색 요약도 넣는다’) |
| 개발 환경의 노트 조회 화면(`/career/history`) | 매칭에 연결한 note를 보여 준다 |
| 로컬 데이터 | 매칭마다 work note를 하나 만들고 Harper 항목을 시간순으로 본문에 옮긴다 |
| 운영 DB | 노트 테이블과 반응 trigger가 2026-11-17에 적용됐고, 코드는 배포되지 않았다([운영 적용 기록](agent-guidance/rollout-history.md)). 옮길 때 trigger와 노트 테이블을 거둔다. trigger가 쓴 반응 항목이 있더라도 추천 행에 이미 있으므로 옮기지 않는다 |

**함께 없어지는 것.** 단계 기록을 노트에 붙이는 부분(`matching/researchNoteActivity.ts`, `talentOnboarding/tools.ts`의 기록 hook), 노트 페이지를 다시 보내는 관리(`matching/researchNoteTranscript.ts`), 노트 블록을 고르는 부분(`matching/researchNoteContext.ts`의 노트 관련 부분)이다. 후보 풀 번호와 추천 목록 연결에 쓰는 작업 대상 추적은 남긴다.

**잃는 것과 메우는 방법.**

- **서버 기록이 note에 보이지 않는다.** Harper가 찾은 범위를 남기려면 직접 옮겨 적어야 한다. 서버가 계산하는 탐색 요약을 work note와 함께 넣어 메운다(위).
- **note를 쓰게 만들던 표시가 없어진다.** 2026-11-17 실험에서 Harper가 노트에 생각을 쓰기 시작한 계기는 도구 결과 끝의 "노트 [12]번에 기록됨" 표시였다([매칭 조사 노트](career-matching-research-notebook-design-ko.md)). note가 왜 있는지는 도구 설명과 목록 머리글에 사실로 적고, 쓰는지는 평가로 확인한다(7절).
- **문장별 번호 편집이 제목·본문 편집으로 바뀐다.** 2026-11-17 지침의 문장별 고정 번호 대신, 긴 note를 통째로 다시 쓰지 않도록 덧붙이기와 일부 교체를 함께 준다(위 ‘고치는 방식’).

**도구 호출의 메모 인자 — 합의(2026-11-19).** 사용자가 판단을 맡겨 이렇게 정했다. 검색·평가·회사·자료 도구에 붙은 `note`(이 단계에서의 생각)와 검색 도구의 `revisitWhen`(다시 볼 때)을 없앤다.

- 이 인자를 주로 읽던 곳은 매칭 노트였다. 옮긴 뒤에는 검색 이력 조회만 남는다(`resources/searchHistory.ts`).
- 생각이 호출마다 흩어지면 다음 요청은 영수증 여러 개를 모아 읽어야 한다. 이어 갈 생각은 note 한 곳에 둔다.
- 서버가 쓰는 영수증에 Harper의 해석을 섞지 않는다(2.1).
- `revisitWhen`은 아무것도 실행하지 않는다. 다시 볼 일은 work note에 적거나, 실제로 도는 예약으로 만든다.
- `matchingId`는 남긴다. 검색 영수증을 매칭에 이어 `read_matching(section=history)`와 탐색 요약(위)이 쓰게 한다. 설명은 ‘노트에 기록한다’에서 ‘이 매칭의 기록에 잇는다’로 바꾼다.

인자가 없어도 Harper가 이어 갈 이유를 note에 남기는지는 평가로 확인한다(7절).

**운영 DB의 반응 trigger.** 실패해도 반응 저장을 막지 않게 고친 수정(`20261117203000`)은 운영 적용 기록에 없다. 그래서 운영에서는 노트를 쓰지 못하는 경우(예: 탈퇴한 사용자의 매칭) 반응 저장까지 실패할 수 있다. 옮길 때 trigger를 거두면 이 위험도 없어진다. 운영 DB를 바꾸는 일은 따로 승인을 받는다.

**함께 고칠 지침·문서.** 2026-11-17 지침의 두 항목(문장별 고정 번호, 그 탐색의 유일한 작업 기록), [매칭 조사 노트](career-matching-research-notebook-design-ko.md), 탐색 handbook과 기본 프롬프트의 노트 문장, 관련 도구 설명이다.

### 4.2 Memory를 회사에 붙인다 — 합의(2026-11-19)

- Memory 행이 특정 회사(`company_workspace`)를 가리킬 수 있다(`company_workspace_id`). 연결 대상은 회사 하나다. 공고 하나에 대한 반응은 추천 행에 이미 남고, 사람은 제3자의 개인정보라 연결하지 않는다(합의 2026-11-19).
- Harper는 회사를 이름, 공식 사이트·LinkedIn 주소, workspace ID 중 아는 것으로 가리키고, 서버가 찾아 연결한다. ID를 먼저 검색시키지 않는다(2026-11-17 지침). note를 회사에 연결할 때도 같다.
- 연결해도 원래 보이던 곳(매 턴 Memory 선택, `read_talent_context`)에서 그대로 보인다.
- 회사 정보를 읽어 LLM에 줄 일이 있으면 그 회사에 연결된 Memory를 항상 함께 가져온다. 평가 입력에 넣을 때도, 검색 결과나 회사 정보를 돌려줄 때도 같다. 날짜를 함께 보여 준다(2.5).
- 회사 정보에는 그 회사의 기회에 사용자가 남긴 반응과, 그 회사에 연결된 note의 제목도 붙인다. note 본문은 붙이지 않는다. 검색 결과가 길어지기 때문이다(합의 2026-11-19).
- 추천 Worker의 평가도 회사 정보를 LLM에 주는 경로다. 내부 기회를 제안할지, 이번에 연락할지 고르는 Worker 단계가 이 정보를 받는다(`harper_worker/opp/matching/company_personal_context.py`, 2026-11-19 로컬). 외부 공고의 점수와 선택은 Worker가 부르는 웹 엔진(`externalRecommendationsV2/engine.ts`)이 맡는다. 새로 매기는 점수와 매번 새로 하는 최종 선택(rerank)이 회사마다 이 정보를 받는다. 이미 매긴 점수는 명시적으로 갱신할 때만 다시 매기므로, Memory가 바뀐 회사의 저장된 점수는 그대로이고 최종 선택에서 반영된다. 내부 적합도 평가 결과(`company_role_candidate_evaluations`)는 회사 측 검색도 함께 쓰므로 여기에는 넣지 않는다.
- 채팅의 평가 결과는 입력이 같을 때만 재사용된다(`matching/externalSearch.ts`의 입력 지문). 연결된 Memory를 평가 입력에 넣으면 지문도 바뀌므로, Memory가 바뀐 회사는 다음 검색에서 다시 평가된다.
- 지금 `talent_contexts`에는 출처 참조(`source_refs`)만 있고 연결 대상 열은 없다(2026-11-19 확인).

**경계(코드가 지킨다).** 이 join은 그 사용자의 Career 입력에만 한다. company-side LLM이나 다른 사용자에게 가는 회사 정보에는 붙이지 않는다. 다만 Behavior Context 빌더는 지금도 Memory를 읽고(`harper_worker/opp/agentic/behavior_context.py:871`), Behavior Context는 회사 측 company-first 검색도 읽는다(`harper_worker/opp/company_first_search/repository.py:956`). 그래서 Behavior Context 빌더는 회사에 연결된 Memory를 읽지 않는다(합의 2026-11-19). 추천 평가는 위의 join으로 그 Memory를 따로 받으므로 잃는 것이 없다.

### 4.3 찾은 것은 중앙에 쌓는다 — 합의(2026-11-17, 11-19 확장)

어떤 사용자를 위해 찾았든 새로 찾은 회사, 공개 공고, 회사 정보는 중앙에 모은다.

| 찾은 것 | 쌓는 곳 |
| --- | --- |
| 회사 | `company_workspace` |
| 공개 공고·채용 글 | `company_roles`(2026-11-17 지침) |
| 회사 개요 | `company_datas`의 `summary` |
| 채용 신호 | `company_datas`. 날짜가 있는 공개 출처를 한 건씩 쌓는다([신호 설계](career-opportunity-signals-design-ko.md) 4.2) |
| 연락 경로 | `company_datas`. 회사 공식 경로(채용 페이지, 공식 메일, 지원 폼)와, 담당자가 공개 글에서 직접 연락하라고 밝힌 계정만 출처와 함께 쌓는다. 개인 메일과 전화번호는 쌓지 않는다(합의 2026-11-19) |

공개 출처가 없는 것은 공유하지 않는다. 사용자의 Gmail이나 대화에서 알게 된 연락처, 그 사용자에게만 해당하는 판단은 그 사용자 범위에 둔다. `company_datas`는 행마다 출처 참조를 요구한다(`20261117123000_career_public_company_datas.sql`).

### 4.4 회사 정보는 평가 전에 준비하고 캐시한다 — 합의(방향), 로컬 구현(2026-11-19)

회사 정보의 기본은 개요와 채용 신호다. 연결된 열린 공고가 있으면 제목·지역 같은 기본 정보만 함께 넣는다. 평가하려는 회사에 개요나 채용 신호가 없거나 오래됐으면 평가 전에 최대한 병렬로 채운다.

지금은 이렇다(2026-11-19 로컬).

- 개요는 30일 동안 쓴다(`CAREER_COMPANY_SUMMARY_MAX_AGE_DAYS`, `resources/companyData.ts:99`).
- 이름 지정한 회사는 모두 평가 전에 개요와 채용 신호를 병렬로 채운다(40초 예산, 동시 6곳). 그 안에 끝나지 않은 회사는 있는 정보로 평가하고 뒤에서 마저 채운다(`companies/fill.ts`, `matching/tools.ts`).
- 회사 줄에는 열린 공고 수와, 검색 제목에 가장 가까운 공고 제목이 들어간다. 검색 제목이 없으면 Brief와 경력에서 만든 방향에 가까운 공고를 고른다(`companies/discovery.ts`의 `directionHint`).
- 넓은 평가가 끝나면 상위권에 들 수 있는 회사 가운데 개요나 채용 신호가 없거나 오래된 곳을, 점수 순위와 검색 단계의 가까움으로 골라 채우고 다시 평가한다(30초 예산 또는 남은 시간의 절반). 채운 정보로 입력이 바뀐 후보만 다시 평가한다(`matching/externalSearch.ts`).

**채용 신호 — 합의(2026-11-19).** 신호마다 날짜를 보여 주고, 오래된 신호인지는 Harper가 판단한다. 평가 전에는 마지막으로 확인한 지 2주가 지난 회사만 다시 본다. 2주는 시작값이고 써 보면서 조정한다. 어떤 회사를 몇 곳까지 채울지는 [좋은 기회](career-good-opportunity-recommendation-ko.md) 2.7이 정한다.

### 4.5 무엇을 어디에 남기나 — 예시

2.1, 2.3, 4.1, 4.2를 한 장면에 적용한 예시다. 규칙표가 아니며 prompt에 넣지 않는다. 무엇을 남길지는 Harper가 정한다.

사용자가 대화에서 "C사는 별로예요. 야근이 많다고 들었어요"라고 말했다.

| 무엇 | 어디에 | 누가 |
| --- | --- | --- |
| 사용자가 C사에 대해 한 말 | Memory. C사에 연결한다(4.2) | Harper |
| "야근이 많은 팀은 피하는 편" 같은 일반화 | think note. 사용자가 확인하면 Brief나 Memory | Harper |
| 지금 탐색에서 C사를 뺐다는 것 | 그 매칭에 연결한 work note | Harper |
| C사 야근 문화에 대한 공개 기사 | 회사 자료(출처 필수). 사용자가 들은 말은 올리지 않는다(2.6) | 기사를 찾았을 때 Harper |
| 다시는 보지 않기 | 회사 차단 설정. 지금은 Harper가 바꿀 도구가 없다(3.2) | 사용자 |

추천 카드에서 싫어요를 누르면 반응과 이유는 서버가 추천 행에 남긴다(2.1). 그 반응이 회사 전체에 대한 것인지, 그 공고에만 해당하는지, 따로 남길 필요가 있는지는 Harper가 이유를 읽고 판단한다.

다음에 C사가 검색 결과나 평가 입력에 나오면 연결된 Memory가 날짜와 함께 붙는다. 오래된 말인지는 날짜를 보고 판단한다(2.5). 평가는 아직 note를 읽지 않는다(3.3의 6번).

얼마나 오래 쓰는지로 보면, Memory와 Brief는 그 사용자에 대해 계속 쓰는 사실과 조건이다. work note는 한 작업의 기록이고, think note는 작업을 넘어 이어지는 Harper의 판단이다.

## 5. 열린 질문

2026-11-19에 사용자가 판단을 맡겨 14번을 뺀 모두를 정했다. 정한 내용은 괄호 안의 절에 있다.

**note**

1. **고친 note의 이전 글** — 저장하지 않는다(4.1 ‘고치는 방식’).
2. **기본 맥락의 목록** — 최근에 고친 10개와 전체 개수(4.1).
3. **작업 대상이 분명할 때 본문을 넣을지** — 넣기로 정했다(4.1, 2026-11-19).
4. **탐색 요약을 처음부터 넣을지** — 넣기로 정했다. 웹 검색 횟수와 마지막 검색 날짜도 더한다(4.1, 2026-11-19).
5. **도구 호출의 메모 인자** — `note`·`revisitWhen`을 없애기로 정했다(4.1, 2026-11-19).
6. **회사 정보에 무엇을 더 붙일까** — 그 회사의 기회에 남긴 반응과, 연결된 note의 제목(4.2).
7. **사용자에게 note를 보여 줄까** — 지금은 개발 화면에서만(4.1).
8. **note에 옮겨 쓴 Gmail 내용을 어떻게 지울까** — 서버가 출처 참조를 붙이고, 연결을 끊으면 그 note를 지운다(4.1).

**Memory**

9. **무엇에 어떻게 연결할까** — 회사에만 연결하고, 이름·주소·ID를 서버가 해석한다(4.2).
10. **회사 측으로 새는 경로** — Behavior Context 빌더는 회사에 연결된 Memory를 읽지 않는다(4.2).

**회사 자료**

11. **사람의 연락처를 중앙에 둘까** — 회사 공식 경로와, 담당자가 공개 글에서 직접 연락하라고 밝힌 계정만(4.3).
12. **채용 신호** — 날짜가 있는 공개 출처를 쌓고, 확인한 지 2주가 지난 회사만 다시 본다(4.4).

**깨움과 연속성**

13. **예약·팔로우·맡긴 일의 연속성** — 아래대로 한다(3.3의 3·10번).
    - 실행이 무엇을 확인했고 무엇을 알렸는지는 서버가 그 실행 기록에 남긴다. 같은 예약의 다음 실행에는 지난 결론을 보여 준다. 그러면 한 예약 안에 기록이 쌓인다.
    - 팔로우한 회사의 변화도 같은 깨움 경로(3.2)로 실행을 만들어 같은 방식으로 남긴다. 팔로우와 예약이 따로 움직이지 않게 된다.
    - 맡긴 일의 경과 메모는 덮어쓰지 않고 쌓는다. (아직 구현하지 않았다)
    - 판단과 새로 알게 된 것은 Harper가 note에 쓴다(2.1).

**문서**

14. **계약 문서 정리.** note와 회사 연결 Memory에 맞춰 고칠 곳이 있다. [LLM 설계](agent-guidance/llm-engineering.md)의 "일시적 판단을 위한 새 저장 금지"와 think note의 관계, [Career Memory 계약](agent-guidance/career-memory.md)의 ‘Worker prompt에 Memory 행을 넣지 않는다’는 문장(4.2), 기본 프롬프트(`mainPrompt2.ts` 63–71행)의 연속성 위치, proactive handbook이다.
15. **참고 서비스의 화면** — 받았다. 본문의 기준으로 삼았다(4.1, 2026-11-19).

2. ~~매칭 노트를 note로 옮기고(4.1의 표), 이어 찾을 때 work note 본문과 탐색 요약을 처음부터 넣는다.~~ 로컬 구현. 운영 DB의 trigger를 거두는 일은 승인을 받은 뒤 한다.
3. 작은 빈틈을 고친다. 반응 블록과 최근 추천의 추천 이유(3.3의 8번), 예약 실행의 마지막 글 저장(3번), 기회 검색 이력(9번), 어긋난 설명(12번)이다. 12번의 나머지 말고는 로컬 구현.
4. Memory를 회사에 연결하고, 채팅과 추천 Worker에서 회사 정보에 join하며, 회사 측 경계를 둔다(4.2). 로컬 구현.
5. 평가 전 회사 정보 준비와 채용 신호를 만든다(4.4, [좋은 기회](career-good-opportunity-recommendation-ko.md) 2.7·2.14). 로컬 구현.
6. 평가 입력을 보정하고(3.3의 6·7번), 팔로우 감지를 운영 경로에 연결한다(5번).

## 7. 좋아졌는지 어떻게 아는가

**합의.** 구조가 생겼다고 좋아진 것이 아니다. 실제 모델 입력과 출력, 최종 DB 상태로 확인한다. 답만 보지 않고 실제 입력에 들어간 note와 Memory도 본다. 답이 맞았더라도 오래됐거나 엉뚱한 대상에 붙은 기억이 입력에 있었다면 실패로 본다. 한 페르소나 결과만 보고 지침을 바꾸지 않는다([좋은 기회](career-good-opportunity-recommendation-ko.md) 5절). 로컬 페르소나 테스트(`career_persona_test_runs`)와 [평가 레지스트리 계약](agent-guidance/evaluations.md)을 따른다.

**가설.** 1절의 목적마다 아래를 본다.

| 목적 | 확인할 것 |
| --- | --- |
| 같은 일을 반복하지 않는다 | 같은 탐색을 이어 갈 때 이미 본 경로와 이미 뺀 회사를 다시 조사하는지. 최근 검색에서 새 상위 후보가 나오지 않았는데 같은 경로를 다시 찾는지. 도구 호출 수와 입력 토큰 |
| 판단을 스스로 고친다 | 같은 이력에서 반응 하나만 다르게 둔 두 경우의 다음 추천을 비교한다. 너무 약하게(같은 회사를 다시 추천) 또는 너무 넓게(같은 업계를 통째로 뺌) 반응하면 실패다 |
| 찾아 둔 것을 다시 꺼낸다 | 다섯 곳 중 두 곳을 보여 준 뒤 "더 줘"에서 남겨 둔 후보를 쓰는지, 그사이 마감된 후보를 빼는지 |
| Harper의 생각이 남는다 | 방향을 정하거나 바꾼 대화 뒤에 지시 없이 think note가 생기는지. 다음 대화가 그 근거를 쓰고, 근거가 바뀌면 고치는지. 도구 호출의 메모 인자 없이도 이어 갈 이유를 note에 남기는지 |
| 찾은 것은 쌓인다 | 다른 사용자가 같은 회사를 볼 때 웹 조회가 줄어드는지 |
| note 본문 | 다음 요청이 note 하나만 읽고 이어 가는지. 무엇을 듣고 어떻게 읽었는지, 무엇을 왜 했는지, 어떻게 됐는지, 열린 일과 그 참조가 남아 있는지(4.1의 본문) |
| 경계 | 회사에 연결한 Memory가 Behavior Context와 회사 측 입력에 들어가지 않는지. 테스트 계정에서 새 깨움이 멈추는지 |

## 9. 바깥 사례에서 가져온 것

2026-11-19 조사([1차](../../research_notes/에이전트%20기억과%20작업%20기록%20설계/), [2차](../../research_notes/에이전트%20기억%20구조%20보강%20조사/)) 가운데 Harper 판단에 쓰는 것만 적는다. 수치는 대부분 회사나 저자가 스스로 보고한 값이다.

- **서버 기록과 모델이 쓰는 기록을 나눈다.** Anthropic의 장기 실행 harness는 진행 파일과 기능 목록을, OpenAI는 진행·결정 기록이 있는 실행 계획을 모델이 쓰고, 새 세션은 그 파일에서 시작한다.
- **목록은 늘 보이고 본문은 필요할 때 연다.** Claude Code는 기억 색인 파일의 처음 200줄만 불러오고, Letta는 늘 보이는 기억과 필요할 때 여는 파일을 나눈다.
- **범위는 코드가 나눈다.** LinkedIn Hiring Assistant는 조직, 리크루터, 채용 프로젝트의 트리로 기억을 나누고 자기 범위만 읽게 한다. AWS·Google의 기억 서비스도 범위를 개발자 코드가 정한다.
- **통째로 다시 쓰면 무너진다.** ACE에서 기억 전체를 다시 쓰자 18,282토큰이 122토큰으로 줄었고, 정확도가 기억이 없을 때보다 낮아졌다. Factory 평가에서는 정해진 칸에 조금씩 합치는 방식이 가장 높았다.
- **옛 기억이 틀린 추천을 만든다.** Memora에서 추천 오류 25건 중 16건이 버리지 않은 옛 선호 때문이었다.
- **긴 입력은 성능을 떨어뜨린다.** Chroma가 18개 모델을 시험한 결과 입력이 길수록 성능이 떨어졌고, 비슷하게 생긴 방해 정보가 가장 해로웠다.
- **사실과 의견을 나눈다.** Hindsight는 세계의 사실과 확신도가 있는 의견을 따로 둔다. 관리형 기억 서비스는 대개 나누지 않는다.

## 10. 바뀐 생각

새 항목을 맨 아래에 붙인다.

- **2026-11-17** — 매칭마다 조사 노트를 두기로 했다. 서버가 실행 기록과 반응을, Harper가 생각을 남긴다. 그 탐색의 유일한 작업 기록으로 정했다.
- **2026-11-19** — 노트의 목적을 세 가지로 정리했다(1절 1~3).
- **2026-11-19** — 작업 기록만큼 Harper의 사고 과정도 남아야 한다고 정했다(1절 4).
- **2026-11-19** — 통합 ‘일’ 테이블안(1판)과 노트 주인 일반화안(2판)을 검토했고, 그대로 적용하지 않기로 했다(8절).
- **2026-11-19** — note(think/work) 개념과 회사에 붙는 Memory를 정했다(4.1, 4.2). 찾은 회사·공고·연락 경로를 중앙에 쌓고, 회사 정보는 평가 전에 준비한다는 방향을 정했다(4.3, 4.4).
- **2026-11-19** — 이 문서를 만들었다. 구조에 관한 토론 결과와 의견은 이 문서를 기준으로 한다.
- **2026-11-19** — 지금의 매칭 노트를 note로 옮기기로 했다. Harper의 생각은 그 매칭에 연결한 work note로 옮기고, 서버 실행 기록과 사용자 반응은 note에 쓰지 않는다(4.1). 2026-11-17의 ‘그 탐색의 유일한 작업 기록’과 ‘문장별 고정 번호’ 결정을 이것으로 바꾼다. 서버 기록과 Harper의 글을 한 본문에 섞으면 Harper가 고칠 때 서버 기록이 지워질 수 있고, 서버 기록은 이미 원래 자리에 남기 때문이다.
- **2026-11-19** — note 본문은 통째로 바꾸는 것 말고도 덧붙이기와 일부 교체로 고칠 수 있게 하고, 작업 대상이 분명하면 연결된 work note의 본문을 처음부터 넣기로 했다(4.1). 도구 호출의 `note`·`revisitWhen` 인자는 없애기로 했다(4.1). 이 인자는 사용자가 판단을 맡겼다. 옮긴 뒤에는 읽는 곳이 검색 이력 조회뿐이고, 이어 갈 생각은 note 한 곳에 모으는 편이 낫다고 봤다.
- **2026-11-19** — 사용자가 참고한 서비스의 note 화면을 받아 본문의 기준으로 삼았다(4.1). 이 모양은 prompt 양식으로 넣지 않고, note의 목적만 알린 뒤 평가로 확인한다.
- **2026-11-19** — 이어 찾을 때 work note 본문과 함께, 서버가 기록으로 계산한 탐색 요약을 처음부터 넣기로 했다(4.1). 요약에 웹 검색 횟수와 마지막 검색 날짜를 더한다. note에는 Harper가 쓴 이유가, 요약에는 서버가 센 범위가 남아 계속 찾을지 멈출지를 사실로 판단하게 한다.
- **2026-11-19** — 사용자가 판단을 맡겨 열린 질문을 정했다(5절). 고친 note의 이전 글은 저장하지 않는다. 처음에는 남기자고 제안했지만, 읽는 곳이 분명하지 않은 저장을 만들지 않는다는 [LLM 설계](agent-guidance/llm-engineering.md) 계약에 맞춰 바꿨다. 목록은 최근 10개, note는 개발 화면에서만 보인다. Gmail을 읽은 턴의 note는 연결을 끊으면 지운다. Memory는 회사에만 연결하고, 회사 정보에는 반응과 note 제목을 붙인다. Behavior Context는 회사에 연결된 Memory를 읽지 않는다. 연락처는 공식 경로와 공개적으로 연락을 청한 계정만 쌓는다. 채용 신호는 2주가 지나면 다시 본다. 예약·팔로우·맡긴 일은 5절 13번대로 이어 간다.
- **2026-11-19** — note(4.1)와 Memory 회사 연결(4.2)을 로컬에 구현했다(6절). 매칭 노트의 테이블·도구·자동 기록·노트 페이지 관리 코드를 지웠고, 도구 호출의 메모 인자를 없앴다. 반응 요약에 추천 이유를 넣었다. 구현 중 점검으로 두 가지를 바꿨다. Memory 쓰기는 기존 RPC가 migration 밖에 있어 회사 연결을 같은 도구 안의 별도 갱신으로 붙였다. Behavior Context는 회사에 연결된 Memory를 증분 갱신 때 철회된 행으로 보게 해, 전에 그 행에서 만든 추론도 빠지게 했다.
- **2026-11-19** — 예약 실행과 팔로우 변화 실행이 전달되지 않는 마지막 글을 결론으로 남기고, 같은 예약·팔로우의 다음 실행이 그 결론에서 시작하게 했다(5절 13번). 팔로우는 이미 별도 실행(`career_company_follow_changed`)으로 깨어나고 있었으므로, 새 경로를 만들지 않고 예약과 같은 연속성을 붙였다. 최근 추천 10개에 추천 이유를 넣어 3.3의 8번을 마저 고쳤다.
- **2026-11-19** — 채용 신호(4.3)와 평가 전 회사 정보 채우기(4.4)를 로컬에 구현했다. 채용 신호는 Exa 검색 결과에서 LLM이 날짜 있는 신호만 골라 출처 하나당 한 행으로 쌓고, 아무것도 찾지 못한 확인도 시각을 남겨 14일 동안 다시 보지 않는다. 회사에 연결된 Memory는 추천 Worker의 내부 기회 선택과 웹 엔진의 외부 공고 점수·최종 선택에도 붙였다. 이미 매긴 외부 공고 점수는 명시적으로 갱신할 때만 다시 매긴다는 기존 정책은 바꾸지 않았다.
- **2026-11-19** — 첫 추천 평가 중에 note 도구(`read_notes`·`upsert_note`)가 온보딩 뒤 채팅 도구 허용 목록(`llmTools.ts`의 `CAREER_CHAT_POST_ONBOARDING_TOOL_NAMES`)에 빠져 있어 실제 대화에서 모델에 닿지 않던 것을 찾아 고쳤다. 도구 등록과 기본 도구 목록만 확인하고, 모델이 받는 최종 도구 목록은 확인하지 않았던 탓이다.
