# 매칭 기준 저장 이력과 웹 저장 후 검토 요청

문서 기준: 2026-10-22. 로컬 구현 계약이며 배포 완료를 뜻하지 않는다. 실제 검증은 [회사 검색 평가 레지스트리](../evaluation/company-agentic-role-search/README.md)의 별도 frozen Brief-history 사례로 기록한다.

운영 DB에는 사용자 승인으로 migration `20261022123546`을 적용했다. 원장·trigger·서버 전용 함수와 저장 상한 제거를 확인했으며 적용 직후 이력은 0건이다. 웹·Worker·요약 consumer는 배포하지 않았다. 구 writer에서 이후 실제 수정이 발생하면 스냅샷은 보존되지만 수정자 context와 요약 처리는 새 runtime이 필요하다. 기존 데이터를 가짜 변경으로 만들거나 운영에서 검색·연락을 실행하지 않았다.

## 저장 단위와 원본

이 문서의 매칭 기준(Hiring Brief)은 `company_internal_roles.request` 텍스트와 `criteria` 배열을 합친 것이다. 둘을 한 번 저장하면 전후 상태를 한 이력으로 보존한다. 요약은 원본을 대체하지 않는다. 모델은 요약을 보고 수정 내역을 찾고, 필요하면 해당 이력의 전체 전후 원문을 조회한다.

새 이력 테이블이 필요한 이유는 현재 기준이나 검색 실행 기록만으로는 **검색하지 않은 수정의 이전 상태·수정자·저장 시각**을 복구할 수 없기 때문이다. 구체적 reader는 웹 History와 회사 LLM의 일반 추가 조회 도구다. 검색 실행이나 평가 이력 테이블에 이를 섞지 않는다.

- DB trigger는 실제 저장값이 달라졌을 때 전후 텍스트와 Criteria를 기록한다. 같은 트랜잭션에서 여러 물리적 갱신이 생겨도 역할별 한 행에 최초 이전값·최종 이후값을 보존한다. 변경 후 다시 원래 값으로 돌아온 트랜잭션은 이력이 아니다.
- 공통 저장 RPC는 Brief와 Criteria 변경을 하나의 트랜잭션에서 처리한다. 어느 필드든 동시 수정 충돌이면 둘 다 롤백한다. 텍스트의 `expectedRequest`와 Criteria의 `expectedCriteria`는 사용자가 편집을 시작한 상태다.
- 수정자 ID·표시 이름·경로는 인증된 서버 경계에서 제공한다. 모델에게 수정자 입력을 요구하지 않는다. 구 runtime이나 직접 SQL처럼 이 정보를 전달하지 않은 writer는 ‘기록 없음’으로 남긴다. 이름을 추정하지 않는다.
- 기존 기록을 가짜 변경으로 backfill하지 않는다. 도입 이전의 변경 횟수와 수정자를 알아냈다고 주장하지 않는다.
- DB 제약은 역할 소유권과 같은 저장의 중복 이력 방지에만 둔다. summary/source 등의 text에 허용값 CHECK를 추가하지 않는다.

### 역할 채용 온보딩의 저장 경로

2026-10-25 로컬 구현은 온보딩에서도 같은 저장 이력을 사용한다. 작성 중인 구조화 초안과 진행 상태는 `company_role_start_sessions`에 두고, 확정된 텍스트·Criteria를 `company_internal_roles`에 저장할 때 기존 trigger가 변경 이력을 남긴다. 초안의 내부 보완이나 동일 내용 재저장은 별도 이력을 만들지 않는다. `brief_source`는 구조화 초안의 작성 경로만 기록한다.

후보 재평가 캐시의 `briefVersion`도 검색이 쓰는 `company_role_search_brief_version_v1` 해시다. 결과 저장 시 현재 Brief 해시가 같아야 하므로 오래 걸린 평가가 이후 수정된 기준을 덮어쓰지 않는다. 온보딩 화면의 변경 이력은 기존 History 컴포넌트를 재사용하며 별도 숫자 버전 원장을 추가하지 않는다. 온보딩 작업·검색 캐시 5개 테이블은 운영 DB에 적용됐지만 이 웹 변경은 아직 배포하지 않았다.

## 가벼운 비동기 요약

저장 응답은 요약 모델을 기다리지 않는다. 이력은 즉시 조회되며, `gpt-6-luna` / reasoning `low`가 뒤에서 한두 문장으로 변경 내용을 요약한다. 저렴한 요약을 위해 다음 입력만 만든다.

| 실제 변경 | 모델에 제공하는 자료 |
| --- | --- |
| Criteria 수정·추가·삭제 | 바뀐 항목의 이전 원문과 이후 원문. 정확히 동일한 항목은 순서가 바뀌어도 제거 |
| Brief 텍스트 수정 | 전체 이전 Brief와 전체 이후 Brief |
| 두 필드 모두 수정 | 각각 위 규칙으로 만든 변경 자료만 |
| 순서만 변경 | 순서가 변경됐다는 구조적 사실. 다른 본문은 제공하지 않음 |
| 값이 동일 | 이력·요약 호출 없음 |

항목 비교는 정확한 구조 비교이며 의미 분류나 중요도 휴리스틱이 아니다. 해당 역할 전체, 회사 정보, 후보 정보, 과거 채팅, 기존 평가를 요약 모델에 추가하지 않는다. 의미·요구 강도·자연스러운 표현은 모델이 판단한다. 길이·문체를 정규식으로 검사하거나 고정 문장으로 덮어쓰지 않는다. 현재 공통 Responses adapter는 상한 생략 시 4,000을 넣으므로 이 호출에는 모델이 지원하는 128,000을 명시한다. 짧게 쓰라는 지시는 prompt의 목적이며 작은 출력 상한으로 강제하지 않는다.

출력은 저장에 필요한 `summary: string` 하나만 받는 provider의 구조화 계약이다. 별도 변경 분류·계획·정성 점수를 만들지 않는다. 서버는 JSON 구조와 비어 있지 않은 문자열만 확인하고 문장 의미·언어를 판정하거나 수정하지 않는다. 같은 실제 변경 입력 7개를 두 번 비교한 진단에서 의미·언어를 직접 확인했으며, 반복 선정 자료의 결과를 일반 정확도로 해석하지 않는다. 최종 계약의 실제 저장·목록·대화 검증은 별도 전체 6건으로 기록한다.

History 행이 작업의 내구성 있는 원본이다. queue는 그 ID만 전달한다. DB claim으로 중복 호출을 방지하며 처리 도중 중단된 작업은 잠금 만료 후 복구한다. 요약 오류는 원본 이력을 삭제하지 않고 재시도 시각과 오류를 보존한다. 정상 저장·목록 열기·원문 비교·회사 검색은 요약 실패와 독립적이다. 기존 회사 작업 dispatcher가 전송 실패와 미완료 요약을 복구한다.

## 웹 저장과 대화의 연결

인증된 `/api/org/role` 웹 저장에서 실제 Brief/Criteria 변경이 발생했을 때만 다음 사용자 메시지를 남긴다.

> 수정된 기준으로 인재풀을 다시 검토해주세요

이 문장은 사용자가 요청한 제품 동작의 정확한 입력이다. LLM의 답변을 고정하는 문구가 아니다. 공통 회사 작업 큐에 저장하며, History ID로 멱등 처리한다. 새로고침·중복 전달·클라이언트 이탈로 같은 메시지를 두 번 만들지 않는다. 저장된 이력에 검토 요청 의도를 남겨 enqueue 실패도 복구할 수 있게 한다.

LLM/Slack의 저장은 같은 이력을 보존하지만 이 웹 사용자 메시지를 만들지 않는다. 원본 회사 LLM은 기존 대화와 기준 변화에 따라 검색 여부·범위·시작 단계·추천 인원을 선택한다. 기본 prompt에는 기준이 분명히 바뀌었고 검색이 유용하며 추가 수정이 예상되지 않으면 바로 검색할 수 있다는 일반 권한을 둔다. 코드가 Criteria 변경을 stage 2, Brief 변경을 stage 1로 강제 매핑하지 않는다.

## 도구와 기본 인식

새 상황별 도구 대신 `get_more_data`에 `kinds=[hiring_brief_history]`, `hiringBriefHistory={roleId,historyId?,offset?,limit?}`를 추가한다. 기본 기능 목록에서 이 조회 능력을 알리고, 역할 대화 기본 context에는 최근 세 변경의 시각·수정자·요약/준비 상태만 넣는다. 전체 과거 스냅샷은 자동 주입하지 않는다. 페이지 번호는 기본 조회량일 뿐 총 이력 수를 제한하지 않는다.

목록 결과는 읽기 쉬운 텍스트로 변환한다. 상세는 원문 전체를 유지한다. 검색 이력은 ‘언제 어떤 평가를 실행했는지’, 매칭 기준 이력은 ‘무엇을 저장했는지’이며 서로의 실행 증거가 아니다. 저장 이력만 보고 재평가나 추천 변경이 이미 완료됐다고 주장하지 않는다.

## UI와 확인 범위

매칭 기준 탭 본문 안 오른쪽 위 History 아이콘에서 검색 기록과 같은 스크롤형 드롭다운을 열어 시간·수정자·짧은 요약을 볼 수 있다. 기존 매칭 기준과 작성 중인 내용은 유지된다. 준비 중 요약은 skeleton으로 표시하되 클릭하여 전후 스냅샷을 즉시 열 수 있다. 요약 오류나 재시도는 영구 skeleton으로 숨기지 않는다. 상세는 선택한 기록의 변경 후 Brief와 Criteria 원문·중요도를 먼저 보여주며 상단 변경 전·후 버튼으로 버전을 전환한다. 목록에는 상대 시각, 상세에는 분 단위의 정확한 시각을 표시한다. 요약 갱신 실패 때 읽던 원문을 유지하되 접근 권한이 사라지면 가린다. 닫기 버튼과 Escape로 닫을 수 있으며, 목록으로 돌아가면 스크롤 위치와 선택 행의 포커스를 복원한다.

검증은 실제 저장·인증/역할 범위·중복 저장·동시 수정·입력 최소화·실제 Luna 요약·일반 tool 조회·웹 채팅 한 번·LLM/Slack 추가 채팅 없음·브라우저 목록과 상세를 대상으로 한다. 원본 실제 역할 데이터는 로컬 격리 사본에서 사용하고 운영에 실험 메시지/검색/연락을 남기지 않는다. 원본과 raw 모델 출력은 평가 폴더의 무시되는 private/runs에만 보존한다.


웹 저장 뒤 회사 LLM 작업의 함수 실행 시간은 웹 대화와 동일한 1,800초로 맞춘다. queue visibility와 DB stale 판정은 1,860초로 맞춰 아직 실행 중인 작업을 이전 360초 기준으로 재점유하지 않도록 한다. 이는 도구 횟수 제한이 아니라 실제 플랫폼 실행 수명과 중복 처리 방지 경계다. [Vercel Node/Python 30분 지원](https://vercel.com/changelog/vercel-functions-can-now-run-up-to-30-minutes)과 [Queue visibility 범위](https://vercel.com/docs/queues/api)를 확인했으며 실제 배포 환경에서의 장기 HTTP 실행은 별도 운영 검증 대상이다.
