# 회사 검색 결과 설명과 read_search 도구 구현 계획

문서 기준: 2026-10-15  
상태: 설계안. 이 작업에서는 문서만 작성하며 코드·DB·평가 실행·배포를 수행하지 않는다.  
독자: company-side LLM과 회사 검색 조회 도구를 구현하는 팀원.

수정 원칙: 기존 평가 단계는 건드리지 않는다. fit·rerank의 prompt, 출력, 저장 계약을 바꾸거나 새 관찰 필드를 만들지 않는다. 이미 저장된 집계와 reason을 조회하고, 넓은 설명은 원본 company-side LLM이 작성한다.

## 1. 목표와 권장안

`read_search`는 특정 Role에서 **어디까지 탐색했고, 어느 단계에서 후보가 줄었으며, 실제 검토에서 어떤 종류의 간극이 관찰됐는지** 읽는 도구다. 회사가 채용 기준을 조정하거나 유입을 늘릴지 판단할 근거를 제공한다. 최종 설명과 다음 행동은 회사와 대화하는 원본 company-side LLM이 결정한다.

권장 반환값은 다음 네 묶음이다.

1. **검색 범위와 진행 사실:** 최근 실행, 사용한 Role 기준, 탐색 범위와 한도, 신규 평가·재평가·기존 평가 재사용, 실패·미완료.
2. **단계별 수량:** 1차 검토, 2차 검토, 최종 검토, 방향별 선정, 실제 회사 소개의 차이. 각 비율의 분모와 사람·pair 단위를 명시한다.
3. **기존 미선정 근거:** 최종 검토 미선정과 앞 단계 제외의 기존 reason 표본. 원본 company-side LLM이 이를 읽고 회사에 설명할 넓은 경향을 판단한다. 아래의 관찰은 새 평가 출력이 아니라 이 기존 근거를 뜻한다.
4. **탐색 가능한 프로필 규모:** 같은 정의로 측정한 현재 규모와 변화, 관련 경력 검색 조건에 잡힌 범위. 이 정보가 실제로 측정됐을 때만 제공한다.

첫 출시의 핵심은 **정확한 단계별 집계 + 넓은 관찰 + 근거 범위**다. 고득점 TOP N을 새로 만들지 않는다. 현재 공통 fit은 숫자 점수를 저장하지 않으며, 최종 검토 사례만으로 전체 탈락 이유의 비율을 추정할 수도 없다.

이유별 정확한 비율과 조건 변경 시 추가 탐색 인원은 후속 범위로 분리한다. 아래에서 필요한 데이터와 계산 계약까지 정의하되, 첫 구현에서 통계·분류·가상 재평가 시스템을 한꺼번에 만들지 않는다.

## 2. 사용자 경험과 질문의 범위

이 도구가 뒷받침할 질문은 다음과 같다.

| 회사의 질문 | 필요한 증거 |
| --- | --- |
| 왜 아직 추천이 없나 | 마지막 실제 검색, 단계별 감소, 선정과 전달의 차이, 운영상 제한 |
| 관련 경험을 가진 사람이 적은가 | 정의된 프로필 모집단, 관련 검색 조건의 포착 수, 미평가·검색 한도 |
| 어떤 점에서 기준에 못 미쳤나 | 실제 제외 단계와 그 단계에서 이미 저장한 reason |
| 거의 맞는 사람은 없었나 | 최종 검토에 들어간 미선정 집합과 관찰. 단순 고득점 순위로 대체하지 않음 |
| 경력 상한 등을 바꾸면 도움이 되나 | 관찰된 간극, 동일 모집단에서 해당 조건만 달리 계산한 범위, 남은 조건의 불확실성 |
| 계속 새 사람이 들어오나 | 같은 모집단 정의의 시점별 규모 또는 정확히 정의된 신규 유입 수 |
| 지금 무엇을 하면 되나 | 기존 채용 기준·홍보 허용·검색 설정과 이 도구의 근거를 함께 읽은 LLM 판단 |

회사가 불만을 표현했다는 사실만으로 채용 기준을 낮추거나 공개 공고를 게시하지 않는다. 반대로 이미 위임받은 유입 확대 업무가 있다면 회사 LLM이 기존 일반 도구로 이어서 실행할 수 있다. 이 도구는 권한이나 새로운 실행 승인을 만들지 않는다.

기존 [선제 채용 계획의 시장 근거 설계](company-side-proactive-recruiting-implementation-plan-ko.md)는 `read_role`의 선택적 확장을 제안했다. 이번 요청에서는 명시적으로 `read_search`를 사용한다. 후보·Role 조회는 기존 도구가 맡고, 검색 실행과 평가 범위의 근거를 읽는 책임을 이 도구에 모은다. 별도 숨은 분석 LLM이나 시장 판단 테이블을 추가하지 않는 원칙은 유지한다.

## 4. 모집단과 시간 기준

모든 숫자는 최소한 `무엇을 센 값인지`, `언제 기준인지`, `사람인지 pair인지`, `전체인지 제한된 조회인지`를 갖는다. 이 정보는 서버의 계산 계약이며, 사용자에게 매번 기술 용어로 낭독할 필요는 없다.

| 집합 | 정의 | 가능한 설명 |
| --- | --- | --- |
| 현재 탐색 가능한 공개 프로필 | 이 회사의 신규 회사 선공유 경계에 맞는 계정의 중복 없는 현재 집합 | 현재 회사 방향에서 탐색 가능한 프로필 규모 |
| 관련 검색 조건에 포착된 프로필 | 위 집합에 확인 가능한 역할 관련 retrieval 조건을 적용한 집합 | 현재 검색 조건이 포착하는 범위 |
| 이번 실행의 평가 대상 | 신규·갱신·재사용 등에서 이번 run의 해당 Role 평가에 실제 들어온 pair | 이번에 검토한 범위 |
| 해당 Role의 현재 유효한 평가 | canonical 계약으로 현재 입력과 호환됨을 확인한 fit의 중복 없는 pair | 현재까지 확보한 평가의 범위 |
| 최종 검토 미선정 | 실제 rerank가 읽고 해당 Role에 `no_action`을 기록한 일반 후보 | 최종 단계까지 검토했지만 이번에 선정하지 않은 사례 |
| 회사에 실제 소개된 후보 | 기존 공유·전달 정본으로 확인된 사람 | 소개·연락·진행 결과 |

회사 선공유 모집단과 후보자 선추천 모집단은 다르다. `exceptional_only` 등으로 후보자 방향에서만 검토 가능한 사람이 회사 선공유 모집단에 포함됐다고 설명하지 않는다. `active/passive/stopped`를 내부 기회의 일반 자격 필터로 새로 사용하지 않는다.

한 Role에서는 같은 사람의 pair가 하나지만 여러 Role을 합치면 사람 수와 pair 수가 다르다. 다중 Role run의 전체 집계를 특정 Role의 수치로 복사하지 않는다. Role별 기록이 없는 과거 run은 회사 전체 집계라고 표시한다.

시간 기준도 분리한다.

- 최근 검색 설명은 그 실행의 기준·관찰 시점과 완료 시점을 사용한다. `created_at`을 실제 시작 시각으로 바꾸어 설명하지 않는다.
- 현재 fit 집계는 조회 시점의 상태다. 과거 run에서 누가 왜 제외됐는지 증명하지 않는다.
- Role 기준이 바뀌었다면 당시 기준과 현재 기준을 구분한다. 이전 기준의 결과를 현재 기준의 실측 결과로 합치지 않는다.
- 최근 5회에 같은 후보가 반복 등장할 수 있다. run 집계를 더해 누적 고유 인원이나 전체 이유 비율을 만들지 않는다.
- 선정 fingerprint 재사용 run은 새로운 판단 표본이 아니다. 원래 실행과 연결해 보여 주고 한 번 더 판단한 것으로 세지 않는다.

## 5. 검색 퍼널에 필요한 수량

### 5.1 유입과 평가를 분리한다

현재 검색에는 기존 fit 재사용, 우선 검토 요청, 수락 후보 재검토가 합류한다. 따라서 아래 관계를 보존한다.

```text
새 검색에서 평가 예산에 들어온 pair ─┐
기존 평가를 갱신할 pair ──────────┼─ 실제 평가 대상
유효한 저장 fit 재사용 ───────────┤      ├─ 1차 제외
명시적 우선 검토 요청 ────────────┘      └─ 2차 평가
                                           ├─ 기존 fit 하한 미통과
                                           └─ 최종 검토 자격 있음
                                                ├─ shortlist 미포함
                                                └─ 실제 최종 검토
                                                     ├─ no_action
                                                     └─ 방향별 선정
                                                          → 현재성 확인
                                                          → 저장·실제 전달

이미 수락한 후보 재검토 → 별도 connect / reject / defer 집계
```

그림은 진입 경로를 보여준다. 집합이 겹치는 유입 수를 단순 합산하지 않는다. 내부에서는 exact pair 집합으로 중복을 제거한다.

### 5.2 수량 정의

아래는 집계의 의미와 원래 발생 지점을 설명한다. 이번 계획은 기존 저장 데이터로 확인 가능한 항목만 반환한다. 기록이 없는 항목을 채우기 위해 평가 단계에 계측이나 새 출력을 추가하지 않는다.

| 측정값 | 계산과 분모 | 기록 위치 |
| --- | --- | --- |
| 신규·갱신 평가 진입 | lane별 실제 admission된 unique pair. SQL에서 반환됐지만 예산 밖인 pair와 구분 | retrieval merge 직후 |
| 기존 평가 재사용 | 이번 run에서 실제 사용한 유효 fit pair | 공통 평가 반환 직후 |
| 평가 완료 | 이번 run에 사용 가능한 평가 결과가 확보된 pair. 신규와 재사용을 구분 | 공통 평가 반환 직후 |
| 새 평가의 1차 완료·통과 | 이번에 실제 1차를 실행해 유효한 응답을 받은 pair와 그중 2차 진행 결정. 2차 실패 여부와 독립 | 1차 결과를 확보한 시점 |
| 1차 제외 | 완료 결과 중 `evaluated_stage=1` 및 `stage_one_result=screened_out`인 pair | canonical 결과를 읽어 집계 |
| 2차 완료 | `evaluated_stage=2`인 pair | canonical 결과를 읽어 집계 |
| 2차 하한 미통과 | 2차 완료 중 실제 기존 구조적 하한에 못 미친 pair | 기존 floor 함수와 같은 판정 결과 |
| 최종 검토 자격 | fit 하한과 당시 route 경계를 함께 통과한 일반 pair | pool 생성 직후 |
| shortlist 미포함 | 자격 pool과 실제 shortlist 사이의 차이. 의미상 탈락 사유는 미기록 | `compact_pool` 전후 |
| 최종 검토 | 실제 rerank 입력에 들어간 사람·pair | rerank 호출 직전 |
| 미선정 | 최종 검토에서 해당 대표 Role의 `no_action`이 확인된 사람 | rerank 결과 |
| 방향별 선정 | candidate-first, company-first, both의 실제 결정. both는 양쪽 집계에 포함 | rerank 및 commit 결과를 각각 구분 |
| 선정 후 제외 | 역할·후보 상태 변경 등 현재성 확인에서 제외된 수 | live guard와 commit |
| 회사 소개 완료 | 기존 공유 사실 및 전달 receipt로 확인한 결과 | 기존 intro·outbox·대화 정본 |
| 평가 미완료 | 오류·입력 변경·미갱신 등으로 결과가 확보되지 않은 pair. 확인 못 한 항목은 미상 | 평가 결과와 admission 집합의 차이 |

핵심 비율은 코드가 분자·분모에서 계산한다. `1차 제외 / 유효한 평가 결과 전체`는 **확보된 평가에서 1차 제외 결과가 차지하는 비중**이다. 이번 실행의 1차 제외율은 신규 평가에서 측정한 `1차 제외 / 1차 완료`로 따로 계산한다. 1차를 통과했지만 2차가 실패한 pair도 후자의 분모에는 남아야 한다. 2차 하한 미통과율은 `2차 하한 미통과 / 2차 완료`다. 신규 평가와 재사용 결과의 비율은 구분하고, 서로 다른 분모의 비율을 합쳐 100% 퍼널로 표시하지 않는다. 분모가 0이면 비율은 null이다.

현재 공통 평가 반환값만으로 단계별 부분 성공을 확인할 수 없는 경우에는 해당 실행률을 미제공으로 둔다. 이번 범위에서 평가 단계의 추가 계측은 하지 않는다. 저장된 결과로 분모를 확인할 수 없는 단계는 미제공으로 남긴다. batch 오류 한 건을 한 명으로 세거나, 마지막 결과가 없는 pair를 전부 1차에서 제외됐다고 계산하지 않는다.

세 fit 축의 부정 판정은 겹칠 수 있다. 축별 집계를 모두 더하면 중복된다. 첫 버전의 회사 반환은 하나의 “추가 검토 기준 미충족” 수량과 넓은 관찰을 우선하고, private candidate-fit 축의 상세 분포를 직군·연봉 등으로 쪼개 공개하지 않는다.

shortlist 생략, 처리 예산, 오류, 이전 선정 재사용, 회사별 기존 진행·중복은 채용 기준 미충족과 다른 사실이다. 추천이 0명이어도 이 구분이 먼저 확인돼야 조건 완화가 타당한지 판단할 수 있다.

### 5.3 기존 run에서 읽을 수 있는 범위

과거 run에서는 실제 저장된 `counts`·retrieval metadata·matching review만 읽는다. Role별·단계별 값이 없으면 null과 짧은 이유를 반환한다. 오늘의 fit을 join해서 과거 단계 결과였던 것처럼 복원하지 않는다. 제한된 fit history와 private trace의 존재도 완전한 historical cohort를 보장하지 않는다.

첫 구현은 기존 run의 최근 실행·선정·운영상 제한과 실제 저장된 reason을 조회한다. 추가 평가 기록이 생겨야만 출시 가능한 구조로 만들지 않는다. 과거 전체 데이터 재평가나 운영 trace 일괄 수집을 기본 rollout 절차로 만들지 않는다.

## 6. 기존 reason을 조회하는 방법

### 6.1 평가 단계는 변경하지 않는다

기존 fit·rerank의 prompt, 출력 schema, 저장 필드와 cache version을 유지한다. `companySearchObservation` 같은 새 관찰 필드, 별도 요약 LLM, 조회 중 재평가를 추가하지 않는다.

`read_search`는 기존 단계 결과와 그 단계의 reason을 함께 읽는다. 원본 company-side LLM이 이 자료에서 반복되는 넓은 직무 관련 경향을 설명한다. tool 결과는 LLM의 판단 자료이며 회사에 그대로 표시하는 답변이나 공개 API 응답이 아니다.

### 6.2 원본과 귀속

- 최종 미선정은 해당 실행·대표 Role의 `matching_review`에서 실제 `no_action`과 기존 reason을 읽는다.
- 1·2차 결과는 기존 fit의 단계와 reason을 사용하되, 실행 당시 결과인지 현재 평가 재고인지 구분한다. 과거 실행과 연결할 수 없으면 현재 평가로 별도 표시한다.
- 최종 미선정 reason이 있으면 최종 결정의 설명으로 사용한다. 앞선 fit 이유로 마지막 결정의 이유를 대체하지 않는다.
- shortlist 제외는 사유가 저장되지 않았으므로 수량만 제공한다. reason 미기록은 미기록으로 남긴다.

`candidate_reason`·`company_reason`은 모두 내부 평가다. 필드 이름만으로 회사 공개 가능성을 판단하지 않는다. source별 회사 agent의 접근 권한을 확인해 필요한 reason만 읽고, 회사·후보 이름이나 상세 프로필을 추가로 붙이지 않는다. 읽을 권한이 없는 source는 누락과 coverage로 표시한다. 권한이 확인된 내부 근거를 읽는 것과 그 내용을 회사에 공개하는 것은 구분한다.

회사 답변에서는 개인의 private Brief·Memory·거절 원문·타사 진행 등 사적인 내용을 인용하지 않고 직무 관련 경향으로 설명한다. 이를 정규식으로 reason을 수정하거나 새 평가 출력을 생성하는 방식으로 해결하지 않는다. 읽을 수 있는 reason이 없으면 단계별 집계까지만 설명한다.

### 6.3 표본 선택과 저장

| 근거 집합 | 용도 | 선택 방식 |
| --- | --- | --- |
| 최종 검토의 no_action | 유력하게 검토했지만 선정하지 않은 맥락 | 해당 실행·대표 Role의 실제 미선정과 기존 reason |
| 2차 하한 미통과 | 구체 검토에서 드러난 간극 | 해당 Role의 기존 2차 결과와 reason |
| 1차 제외 | 초입에서 후보가 줄어드는 이유 | 해당 Role의 기존 1차 결과와 reason |

각 집합 최대 8개, 총 24개를 초기 반환 한도로 제안한다. 실제 점수가 없으므로 점수 순위를 만들지 않고, 집합 안에서 안정된 균등 표본을 사용한다. 최종 미선정 집합을 우선 읽되 세 집합의 비율을 전체 탈락 이유의 분포로 해석하지 않는다.

각 집합에 전체 인원, 기존 reason 존재 인원, 읽을 수 있는 인원, 반환 수, 표본 방식과 기준 시점을 붙인다. 후보를 식별하는 ID 대신 조회 범위에만 유효한 ref를 사용한다. 추가 페이지는 같은 원본 범위에서 읽으며, 현재 fit이 갱신되면 같은 과거 snapshot인 것처럼 이어 붙이지 않는다.

새 관찰 저장 필드나 판단 테이블, historical reason 복제는 추가하지 않는다. 기존 기록으로 재현할 수 없는 과거 결과는 미확인이다. 소수 집합의 상세 근거 반환은 기존 공유 경계에 맞추고, 관찰 몇 건으로 특정 사람을 드러내지 않는지 검증한다.

## 7. 이유별 비율의 범위

분모가 확인된 **구조적 단계 비율**은 첫 버전에서 제공한다. “업무 범위 부족 때문에 N%를 추천하지 않았다”와 같은 **의미상 이유 비율**은 그 문장에 속하는 관찰 집합과 분모를 별도로 확인해야 한다.

첫 버전에서는 company-side LLM이 관찰을 읽어 반복되는 넓은 경향을 정성적으로 설명한다. 표본 8개 중 5개가 비슷해 보인다는 이유로 전체의 62.5%라고 쓰지 않는다. 사유가 없는 사람, 비공개 사유만 있는 사람, shortlist에서 빠진 사람도 분모 밖으로 조용히 사라져서는 안 된다.

정확한 이유별 숫자가 제품상 꼭 필요해지면, 같은 `read_search`의 선택적 후속 집계로 확장한다.

1. 원본 company-side LLM이 이미 읽은 기존 reason을 의미상 묶는다. label은 자유 text이며 정규식·단어 목록이나 별도 분류 LLM은 사용하지 않는다.
2. 각 묶음에는 reader가 발급한 관찰 ref만 전달한다. ref는 조회 snapshot에만 유효하며 후보자 ID나 개인 상세 조회에 사용할 수 없다.
3. 서버가 해당 snapshot의 ref 소속·중복을 검증하고 unique pair 수와 분모를 계산한다. 이 필드는 실제 숫자 계산에 필요한 최소 입력이지 영구 판단 상태가 아니다.
4. 전수 관찰이 없는 경우 “조회한 reason 표본 중”의 비율만 반환한다. 전체 미선정 대비 비율은 전수 coverage와 사유 해석 범위가 확보된 집합에만 제공한다.
5. 같은 pair에 여러 이유가 있으면 중복 가능성을 명시한다. 100% 분할이 필요하면 LLM이 하나의 주된 이유에 배정하고 나머지는 미분류로 남긴다. 코드가 임의의 이유 우선순위를 정하지 않는다.

집계 결과는 “모델이 조회 가능한 기존 reason을 묶은 해석”이다. 숫자를 정확히 셌다는 사실이 분류의 진실성이나 인과성을 보장하지 않는다. 분류가 과도하거나 source와 다르면 의미 평가에서 실패로 판정한다. 이 후속 인자와 grouping 계약은 첫 구현에는 넣지 않는다.

## 8. 인재풀 규모와 조건별 감소

### 8.1 전체 규모와 성장

전체 가입자, 프로필 보유자, 회사 선공유 가능자, 해당 회사에 탐색 가능한 사람을 한 숫자로 섞지 않는다. 회사에 제공할 기본 모집단은 신규 공유·회사 차단·삭제·test-only 경계를 적용한 공개 프로필 aggregate로 제한한다. 후보자 선추천은 별도 경로의 집계다.

규모 변화는 같은 정의·계약으로 측정한 두 시점의 수량이 있어야 계산한다. 기존 run 결과에 작은 `poolSnapshot`을 남겨 정의 version, 관찰 시각, 수량을 보존하는 방안을 사용한다. 가입·프로필·공개 설정 변화로 현재 집합이 달라지므로 지금의 필터에 `created_at`만 붙여 과거 규모였다고 재구성하지 않는다.

시계열이 없으면 “최근 30일 가입했고 지금 이 모집단에 포함되는 사람 N명”처럼 실제로 계산한 유입 사실만 반환할 수 있다. 신규 가입 수는 순증이나 계속 증가하는 추세를 증명하지 않는다. 시점별 표본이 충분한지와 어떤 추세를 설명할지는 LLM이 주어진 수치를 보고 판단한다.

### 8.2 관련 직무 경험의 비율

현재 FTS의 직함·학력 검색 결과는 “Performance Marketer 역할을 수행할 수 있는 사람”과 동일하지 않다. 키워드 OR 조합, 인접 직무, 학교·학과 텍스트까지 포착될 수 있기 때문이다.

첫 측정은 **경력 source를 명시한 관련 검색 조건의 포착 수**로 제공한다. 기존 검색 recipe를 재사용하되, profile-only 조건과 새 평가·route·최근 non-fit 제외 조건을 구분한다. 개인별 평가 예산·LIMIT 이전의 count가 따로 필요하다. `roleCounts`를 재사용하거나 저장 SQL의 LIMIT만 지워 전체 분포라고 부르지 않는다.

원본이 직함 검색뿐이면 “관련 직무명으로 찾은 프로필”이라고 설명한다. 실제 수행 경험의 의미 판단이 필요하면 canonical 평가가 확보된 집합의 범위에서만 말한다. 모든 프로필을 새 LLM으로 직군 분류하거나 직무명별 고정 매핑 규칙을 이 도구에 추가하지 않는다.

프로필 count 조회가 timeout 또는 scan 한도에 걸리면 미완료·하한만 반환한다. 제한된 top-k를 정확한 총계로 반올림하지 않는다. 회사 LLM이 SQL을 입력하거나 실행할 수 있게 하지 않는다.

### 8.3 경력 범위 등 확인 가능한 조건

조건별 수량은 같은 기준 시각·모집단에서 계산한다. 경력 기간은 canonical 경력 구간의 중복 기간을 합친 월 수를 기본으로 하고, 누락·해석 불가 날짜는 미상으로 남긴다. 전체 경력과 해당 직무 수행 기간은 별개의 값이다. 학교 졸업일·나이를 경력으로 대신하지 않는다.

합성 예시: 관련 검색에 포착된 900명 중 전체 경력 기간 확인 가능자는 780명이고, 그중 5년 이하가 300명이라면 다음 값이 함께 필요하다.

- 경력 기간 확인 가능 집합에서의 비율: 300/780, 약 38.5%.
- 관련 검색 전체에서 확인된 해당 조건 충족 비율: 300/900, 약 33.3%.
- 경력 기간 미상: 120명. 이들을 경력 초과로 간주하지 않는다.

이 계산이 곧 300명의 적합 후보나 신규 소개 가능 인원을 뜻하지 않는다. 자유 형식 Brief를 코드가 keyword로 읽어 “최대 5년” 조건으로 변환하지 않는다. 비교할 기준은 회사 발화·저장된 기준을 원본 LLM이 해석하고, 필요한 수치만 구조적 조회 인자로 전달하는 후속 확장으로 설계한다.

### 8.4 기준을 넓혔을 때의 변화

세 수준을 구분한다.

| 증거 수준 | 가능한 설명 |
| --- | --- |
| 넓은 관찰만 있음 | 해당 기준을 넓혀 추가로 검토해 볼 가설과 그 근거 |
| 같은 profile 모집단에서 조건 하나만 변경한 정확한 집합 차이 | 새로 탐색 범위에 들어올 프로필 수. 다른 기준의 적합성·의향은 미확인 |
| 다른 핵심 요건·현재 자격까지 별도로 확인된 집합 | 추가 재검토 대상 수와 아직 남은 확인 사항 |

수치 비교는 두 조건의 count 차이보다 실제 집합 차이를 우선한다. 다른 필터·기준 시각이 바뀌면 단일 조건의 효과로 설명하지 않는다. 후보별 경력 상한만 통과했다고 전체 fit을 재평가한 것처럼 말하지 않는다. 기존 Role·Brief를 수정하지 않고 비교할 수 있어야 하며, 실제 변경은 기존 편집·확인 계약을 따른다.

조건 변경에 따른 신규 추천·연결 수나 확률은 이 도구가 예측하지 않는다. 실제로 더 연결될지는 이후 검색·선정·상호 의사에 달려 있다.

## 9. 도구 계약

### 9.1 첫 구현의 입력

```json
{
  "roleId": "접근 가능한 정확한 Role ID",
  "searchRef": "선택 사항. 이력 또는 이전 read_search가 반환한 실행 참조",
  "offset": 0
}
```

`roleId`는 필수다. `searchRef`가 없으면 그 Role의 최근 실제 검색 결과를 기본으로 하고, 더 최근 queued/running/failed/skipped 상태도 짧게 함께 표시한다. 성공한 옛 결과만 골라 최근 장애를 숨기지 않는다. 초기 탐색 범위는 최근 30일·최대 5개 실행으로 제한하고, 그보다 오래된 실행은 기존 이력 pagination으로 ref를 얻어 읽는다. 찾지 못하면 검색 없음과 조회 범위 밖을 구분한다.

`searchRef`는 항상 workspace·Role 접근 권한을 다시 확인한다. 혼합 Role run에서 해당 Role에 귀속할 수 없는 private 판단이나 집계는 반환하지 않는다. 추가 관찰 페이지는 같은 고정 실행 snapshot을 사용한다. 원본이 바뀌었으면 같은 offset에 다른 관찰을 조용히 반환하지 않는다.

페이지 기준은 해당 실행의 기존 review 또는 별도로 표시한 현재 fit 집합이다. 기존 원본이 달라지면 기준 시점 변경을 명시한다. 당시의 운영 집계와 현재 읽을 수 있는 reason의 수량은 별도 시각·범위로 표시한다.

첫 구현에 임의 SQL, 후보자 ID 검색, 자유로운 private 조건 조합, 분석 prompt, 기준 자동 변경 인자는 없다. 후속 프로필 조건 비교와 이유 묶음 계산은 7·8절의 별도 완료 조건을 충족한 뒤 추가한다.

### 9.2 반환 묶음

| 묶음 | 최소 내용 |
| --- | --- |
| 기준 | Role, 검색 ref, 관찰·시작·완료 시각, 당시 기준 fingerprint, 현재 기준과 같은지 |
| 현재 상태 | 더 최근 실행의 진행·실패·skip, 선정 재사용 여부, 기록된 운영상 제한 |
| 검색 범위 | 신규·갱신·재사용, 대상과 한도, partial·fallback 여부 |
| 퍼널 | Role별 확인 가능한 수량, 단위, 계산된 단계 비율과 분모 |
| 관찰 | 단계별 population·coverage·표본 설명, 익명 관찰, 다음 페이지 |
| 프로필 규모 | 측정된 경우에만 정의·시각·수량·과거 비교·검색 조건·미상 |
| 실제 효과 | 회사 방향 선정과 소개의 구분. 확인 가능한 전달 결과 또는 기존 read 도구 안내 |
| 미확인 범위 | 없는 값과 그 이유. 0·실패·legacy 미기록·비공개·표본 한도를 구분 |

서버 내부 객체는 계산에 필요한 구조를 갖되 모델에는 짧은 section·table 형태로 serialize한다. 자연어 판단을 수십 개 의미 필드로 분해하지 않는다. 이유와 해석은 작은 text에 남긴다.

### 9.3 합성 반환 예시

아래는 계약 설명용 가상 수치이며 실제 회사·후보 기록이 아니다. 예시는 전체 구조를 고정한 답변 템플릿이 아니다. 아래 reason 문장은 설명용으로 짧게 쓴 가상 원문이며, tool이 실제 reason을 별도 LLM으로 요약한다는 뜻이 아니다.

```text
대상: A사 퍼포먼스 마케팅 Role
검색 기준: 10월 14일 완료한 검색. 현재 채용 기준과 동일함.
새 검색: 10월 16일 정기 실행 예정. 현재 진행 중인 검색 없음.

이번 Role의 평가 범위
- 신규·갱신·재사용 합친 대상: 150명
- 평가 결과 확보: 140명 / 미완료: 10명
- 1차에서 추가 검토하지 않음: 80명 / 평가 완료 140명 중 57.1%
- 2차 평가: 60명 / 추가 검토 기준 미충족: 35명
- fit 하한 통과: 25명 / 실제 최종 검토: 18명
- shortlist 미포함: 7명. 개별 사유는 기록하지 않음.
- 최종 미선정: 18명 / 회사 선추천 선정: 0명 / 후보자 선추천 선정: 0명

최종 미선정의 기존 reason 표본
- 대상 18명, 조회 가능한 기존 reason 16명, 이번 반환 8명.
- 고정된 균등 표본. 전체 미선정 사유 비율을 추정하는 자료는 아님.
- 기존 reason: 채널 실행 경험에 비해 전략 전반의 책임 근거는 제한적임.
- 기존 reason: 요구한 사업 단계에서 독립적으로 성과를 만든 근거는 확인이 필요함.
- 나머지 항목도 해당 단계의 기존 reason을 제공하며 원문 길이와 누락 범위를 표시.

현재 프로필 규모
- 동일한 공개 프로필 모집단: 10월 7일 7,300명 → 10월 14일 7,500명.
- 관련 경력 검색 조건 포착: 900명. 실제 직무 적합성 평가 결과는 아님.
- 전체 경력 기간 확인 가능: 780명, 미상: 120명.
- 확인된 경력 5년 이하: 300명. 나머지 조건·의향은 이 수치로 확인되지 않음.

미확인 범위
- 표본 밖의 모든 미선정 이유와 shortlist 제외 이유.
- 기준을 바꿨을 때 실제 추천 또는 연결될 인원.
```

이 입력에서 회사 LLM은 “현재 탐색 범위가 늘고 있지만 이번 검토에서는 실행 경험에 비해 전략 전체를 책임진 근거가 약한 사례가 있었다”는 정도를 설명할 수 있다. 이어서 회사가 실제로 요구한 책임 범위와 연차 기대가 양립하는지 질문하거나, 인접 경험을 더 검토할지 제안할 수 있다. 관찰이 적거나 서로 다르면 “보통 이 이유”라고 요약하지 않는다.

## 10. 기존 회사 도구와의 연결

최근 5개 실행의 기본 요약은 가볍게 유지한다. 실행별 상세를 읽을 수 있는 ref와 `read_search` 안내만 추가한다. `get_more_data(kinds=["matching_runs"])`는 오래된 실행 목록, `read_search`는 특정 Role·실행의 근거를 맡는다.

`read_search`는 기본 read tool로 노출하는 것을 권장한다. 숨겨진 후보 시장을 직접 검색하는 기능이 아니라 제한된 회사용 근거를 읽는 기능이다. “왜 결과가 없나” 같은 질문에서 새 검색 요청 기능을 먼저 로드할 필요가 없다.

원본 LLM은 필요에 따라 다음 일반 도구를 조합한다.

| 필요 | 기존 도구와 책임 |
| --- | --- |
| 현재 Hiring Brief·역할 기준 확인 | `read_role` |
| 이미 공유된 후보와 진행 상태 확인 | `get_talents`, `read_talent` |
| 실제 연락·답변 확인 | `list_contacts`, `read_contact` |
| 회사가 요청한 새 탐색 실행 | `request_matching_search` |
| 합의한 기준 수정 | 기존 Role 편집 도구와 정확한 변경 확인 계약 |
| 이미 홍보가 허용된 Role의 추가 유입 수요 전달 | `job_posting_promote` |

`job_posting_promote`는 한정된 공고 슬롯 운영에 수요를 기록하는 도구다. 즉시 LinkedIn 게시나 특정 시각의 게시를 보장하지 않는다. 실제 게시가 확인되기 전에 “공고를 공개했다”거나 “바로 게시하겠다”고 도구 효과를 확대하지 않는다. 홍보가 꺼져 있거나 회사명 비공개 설정이 있으면 현재 권한·설정 계약을 따른다.

`read_search`가 `recommendedAction`, 고정 답변, 자동 기준 완화 명령을 반환할 필요는 없다. 검색 사실과 넓은 관찰만으로도 원본 LLM이 새로운 상황에서 같은 도구들을 사용할 수 있어야 한다.

## 11. 공유 경계와 오류 처리

- 실행 전과 반환 직전에 현재 workspace·Role·팀 접근 범위를 확인한다. 다른 Role이 섞인 run은 허용 Role의 분리된 증거만 제공한다.
- 후보자 ID·이름·연락처·프로필 링크·원문 이력·개인 설정을 별도 상세 필드로 붙이지 않는다. 내부 reason은 source별 agent 접근 권한이 확인된 범위에서만 읽으며, tool 결과를 회사 화면·공유 로그에 그대로 노출하지 않는다. 이미 공유된 후보의 상세는 기존 도구로 확인한다.
- 관찰 ref는 회사·Role·실행에 묶인 불투명 참조다. 관찰 페이지나 집계 요청으로 다른 후보 정보를 조회할 수 없어야 한다.
- 기존 reason을 그대로 회사에 공개 가능한 것으로 가정하지 않고 합성 privacy challenge와 실제 source 계약을 검증한다. 소수 표본 억제만으로 충분하다고 판단하지 않는다.
- 현재 계정 삭제·회사별 차단·test-only 경계는 별도로 유지한다. 과거 aggregate 운영 집계와 현재 개별 관찰의 공개 자격은 구분하고, 관찰 반환 시 현재 허용 범위를 적용한다.
- 내부 원본과 회사용 serializer를 분리한다. 로그·오류 응답에 SQL·private reason·원본 후보 데이터를 넣지 않는다.
- 전체 조회 실패는 “검색을 안 했다”가 아니다. section별 실패·미기록이면 확인한 section만 반환한다. 만료된 수치를 현재 사실로 대체하지 않는다.
- 도구는 읽기 전용이다. fit 생성·Behavior Context 갱신·검색 enqueue·공고 수요 저장·외부 연락을 숨은 부수 효과로 수행하지 않는다.

## 12. 성능과 저장 범위

기본 문맥에 전체 근거를 주입하지 않고 호출 시 읽는다. 첫 응답은 최근 실행 요약, 작은 퍼널, 최대 24개 관찰을 기준으로 약 8,000~12,000자 이내를 초기 목표로 둔다. 잘림·누락은 명시하고 문장을 중간에서 잘라 의미를 바꾸지 않는다.

첫 구현은 기존 run·review·fit을 읽으며 새로운 evidence 저장 계약을 요구하지 않는다. 원본 프로필·Brief·Memory·reason·LLM 전체 출력을 새로 복제하지 않는다. 선정 재사용 run은 원래 실행을 참조한다.

현재 fit 집계는 read-only로 canonical freshness 계약을 사용한다. TTL만 남았다고 fresh로 세지 않는다. 현재 입력 fingerprint를 싸게 확인할 수 없는 경우 “현재 입력 일치 미확인”으로 표시하고 tool 안에서 평가·context builder를 실행하지 않는다. 현재 평가 재고의 count를 과거 실행 퍼널에 합치지 않는다.

프로필 전체 count는 pair 평가 예산과 독립된 제한 시간 안에서 수행한다. 필요한 count를 묶어서 읽고 후보별 상세를 N번 조회하지 않는다. 최초 성능 목표는 검색 evidence 읽기 P95 2초, 선택적 profile aggregate 포함 P95 5초로 제안하며 구현 시 실측한다. 충족하지 못하면 확인된 evidence를 먼저 반환하고 aggregate는 미완료로 둔다.

새 cache table은 기본안에 없다. 반복 aggregate가 실제 병목일 때만 기존 실행 결과의 측정값을 재사용하며 as-of를 함께 반환한다. 캐시 사용 때문에 `read_search` 호출이 운영 데이터를 쓰는 경로가 되지 않게 한다.

## 13. 구현 순서와 변경 지점

### 1단계 기존 데이터만으로 상세 도구 제공

- beta에 `read_search` schema·executor·권한 범위가 적용된 reader를 추가한다.
- 기존 history에 실행 ref를 추가하고 기본 read capability에 등록한다.
- 기존 저장 값의 실제 의미·단위·누락을 반환한다.
- 최종 미선정, 2차 제외, 1차 제외의 기존 reason을 범위별로 읽는다.
- 원본 company-side LLM이 집계와 reason을 근거로 넓은 경향을 설명하도록 공통 tool 계약에 연결한다.

**이 단계가 첫 출시 단위다.** 평가 단계 수정이나 새 관찰 축적을 선행 조건으로 두지 않는다.

### 2단계 조회 범위 보완

- 현재 저장 데이터에서 계산 가능한 Role별 집계와 실제 전달 여부를 보완한다.
- 과거 실행에 귀속되지 않는 현재 fit 통계는 별도 표시한다.
- 저장되지 않은 단계 수량·이유는 미제공으로 남긴다. 이를 메우려고 평가 prompt·출력·계측을 변경하지 않는다.

### 3단계 프로필 규모와 변화

- 회사 방향의 aggregate 모집단을 명시하고 현재 count·snapshot을 기존 run에 기록한다.
- 관련 professional source의 검색 조건 count와 미상을 측정한다.
- 같은 정의의 과거 측정값이 쌓인 뒤 규모 변화를 제공한다.
- 숫자의 유용성·비용·공유 경계를 확인한 뒤 기본 반환에 포함한다.

### 4단계 필요가 확인된 정밀 비교

- 전수 또는 명시적 표본의 자유 이유 묶음 계산.
- 회사가 논의한 한 조건의 read-only profile 집합 비교.
- 계산 가능한 추가 탐색 범위와 실제 적합·소개 가능 인원을 분리.

이 단계는 기존 데이터 coverage가 충족되지 않으면 null로 남긴다. 정확한 숫자를 만들기 위해 별도 전수 LLM 재분류나 숨은 matching run을 추가하지 않는다.

예상 변경 파일은 다음과 같다. 실제 구현 시 checkout의 최신 상태를 다시 확인한다.

| 영역 | 파일과 책임 |
| --- | --- |
| beta reader | `src/lib/companyFirstSearch/history.ts`, 신규 같은 디렉터리의 evidence reader: workspace·Role 범위, 역사·현재 구분 |
| beta tool | `src/lib/org/agent/tools.ts`, `toolExecution.ts`, `promptFormat.ts`: 최소 계약과 회사용 projection |
| beta 문맥 | `context.ts`, `capabilities/registry.ts`: 짧은 발견 가능성, 기본 read 도구 |
| Worker 평가·선택 | 변경 없음. 기존 fit·rerank prompt, 출력, 저장 계약 유지 |
| DB | 첫 구현은 기존 데이터 조회만 사용. 새 reason·관찰 필드나 판단 table 없음 |
| 문서 | 현재 이력 계약, 선제 채용 계획의 8.3 도구 선택, 회사 agent 계약 중 영향받는 부분만 연결 |

DB migration은 구현·배포와 별도 실행 범위다. 이 계획 작성이나 이후 일반 코드 구현만으로 운영 적용·push·서비스 재시작을 승인한 것으로 해석하지 않는다.

## 14. 필요한 검증

변경 경로의 계산·공유 경계와 실제 원본 LLM 대화를 짧게 검증한다. 전체 테스트나 전체 matching benchmark를 기본 절차로 추가하지 않는다.

| 사례 | 확인할 결과 |
| --- | --- |
| 신규 검색은 작지만 재사용 fit이 많음 | pool 유입을 잘못된 단조 감소 퍼널로 설명하지 않음 |
| 1차 제외가 많고 최종 미선정은 적음 | 최종 검토 표본을 전체 탈락 이유로 확대하지 않음 |
| shortlist에서 제외됨 | fit 실패·회사 거절·특정 사유를 만들어내지 않음 |
| 새 평가 일부 실패 | 오류를 후보 부적합으로 세지 않고 정확한 확인 범위를 보존 |
| 같은 후보의 여러 Role·여러 run | 사람·pair·반복 판단의 중복을 구분 |
| 선정 fingerprint 재사용 | 같은 결정을 신규 검토 표본으로 다시 세지 않음 |
| Role 기준 변경과 legacy 기록 | 당시와 현재를 구분하고 없는 값을 0으로 바꾸지 않음 |
| 조회 가능한 기존 reason이 없거나 private 이유만 있음 | 이유 미확인을 유지하고 다른 사유를 만들어내지 않음 |
| 소수·희귀 경력·다른 Role 권한 | 개인 식별과 권한 밖 정보가 tool 결과·오류에 없음 |
| FTS 결과·경력 미상 | 키워드 포착을 직무 능력으로, 미상을 경력 초과로 바꾸지 않음 |
| 선정됐지만 전달은 미완료 | 채용 기준 문제로 원인을 돌리지 않고 실제 단계 설명 |
| 후보자 방향만 선정됐음 | 회사 0명을 전체 추천 0명으로 바꾸지 않음 |
| 수락 후보 connect/reject/defer 혼재 | 신규 검색의 탈락·선정 수에 섞지 않음 |
| 홍보 허용·미허용·비공개 회사명 | 기존 도구의 실제 효과와 승인 범위를 유지 |

LLM 평가를 실제 만들거나 실행하기 전 [evaluation registry](../evaluation/README.md)와 관련 task README를 읽는다. 회사 대화는 기존 [company-side-conversational-qa](../evaluation/company-side-conversational-qa/README.md)의 canonical runner를 확장하고, 공통 fit 계약은 변경하지 않는다. 새 입력은 새 dataset version, prompt 변경은 같은 frozen 입력의 새 run으로 기록한다.

소규모 합성 세트에는 다른 직군·경력 수준, 0명·일부 선정, 충분한 근거·미기록, sample·census, 공유 경계, 조건 완화 승인·거절을 포함한다. 구조 검증과 전체 대화 의미 검토를 구분한다. 원본 LLM이 필요할 때 도구를 읽고, 실제 근거의 수준에 맞춰 설명·질문·행동을 선택하는지 본다. 특정 표현·단어·문장 수를 정답으로 검사하지 않는다.

첫 gate는 선택한 사례의 수량·분모·귀속 정확성, private 정보 노출·허위 시장 비율·허위 완료·미승인 변경 0건, broad observation이 실제 근거와 맞고 회사가 다음 판단을 할 수 있는 답변이다. 평가 실행 성공만으로 이 gate를 통과했다고 하지 않는다. 운영 평균·채용 성과·전수 이유 coverage는 별도 한계로 남긴다.

## 15. 완료 판단과 설계 선택

다음이 확보되면 첫 구현의 목적을 달성한다.

- 회사 LLM이 `read_search`로 해당 Role의 실제 최근 검색 범위와 단계별 결과를 확인한다.
- 확인 가능한 퍼널과 누락을 구분하고, 운영 문제를 채용 기준 미충족으로 바꾸지 않는다.
- 최종 미선정과 앞 단계 제외의 넓은 관찰을 읽고 현재 대화에 필요한 만큼 설명한다.
- agent 접근 권한 밖의 reason과 불필요한 후보 상세를 반환하지 않고, 내부 근거를 회사 답변에 그대로 노출하지 않는다.
- 모든 비율에 확인된 분모가 있으며 표본의 이유를 전체 시장 비율로 확대하지 않는다.
- 현재 기준을 바꿨을 때의 추가 연결 인원·확률을 근거 없이 약속하지 않는다.
- 필요하면 기존 일반 도구로 기준 논의·새 검색·허용된 홍보 수요 전달을 이어간다.

핵심 선택은 **점수 TOP N 대신 실제 최종 검토 미선정 집합을 보고, 전체 병목은 단계별 정확한 수량으로 설명하며, 내용은 이미 저장된 reason을 원본 company-side LLM이 읽고 넓게 설명하는 것**이다. 이유별 전수 비율과 조건별 신규 연결 예측을 처음부터 약속하는 것보다, 무엇을 실제로 보았는지와 무엇을 바꾸면 추가 검토 가치가 있는지를 설명할 수 있는 도구를 먼저 완성한다.
