# Org 일정 조율 문구 품질 평가 — 2026-08-26

이 문서는 회사 측 Harper의 일정 조율 답변과 후보자 일정 선택 메일이 사람다운지
반복해서 확인하기 위한 기준과 실행 결과를 기록한다. 설계안만 읽고 판단하지 않고 실제
운영 모델을 호출한 출력을 사람이 읽어 평가했다. 이 작업은 로컬 코드 평가이며 배포나 실제
후보자 발송을 뜻하지 않는다.

## 1. 합격 기준

각 항목을 `0점(실패)`, `1점(아쉬움)`, `2점(충족)`으로 평가한다. 총점 12점 중 10점
이상이고, 사실과 다른 상태 설명이 없어야 합격이다.

| 기준 | 확인할 내용 |
| --- | --- |
| 대화의 자연스러운 연속성 | 직전 대화를 받아 말하며, 매번 인사하거나 양식처럼 시작하지 않는가 |
| 맥락을 먼저 설명 | 요청이나 버튼을 내밀기 전에 왜 지금 이 단계인지 이해시켜 주는가 |
| 시스템 영수증처럼 보이지 않음 | 초안, 상태, 프로세스, 저장 완료 같은 내부 표현과 설정값 목록을 피하는가 |
| 사실과 lifecycle이 정확함 | 제안, 회사 승인, 후보자 연락, 확정을 서로 앞당겨 말하지 않는가 |
| 다음 행동이 하나로 선명함 | 사용자가 지금 답하거나 눌러야 할 행동이 명확한가 |
| 고유 맥락을 자연스럽게 사용 | 회사, 역할, 후보자, organizer, 추가 요청을 문장 안에 억지 없이 녹이는가 |

다음은 총점과 무관한 즉시 실패 조건이다.

- 아직 제안만 만든 상태를 저장·연결·발송 완료로 말함
- 후보자에게 전달하지 말아야 할 내부 메모를 메일에 포함함
- 회사명, 역할, 사람 이름, 길이, 채널을 임의로 만들어냄
- 일정 선택 링크를 빼거나 중복으로 넣음
- 후보자에게 여러 시간을 받는 단계를 회사가 다시 고르는 단계로 설명함

## 2. 평가 시나리오

한 번의 평가 회차마다 다음 12개를 호출했다.

### 회사 측 Slack 답변 6개

1. 가능한 시간을 한 번도 정하지 않은 사용자가 바로 미팅을 요청함
2. 회사 사용자와 후보자 이름이 같은 대화에서 채팅으로 가능 시간을 설정함
3. 저장된 가능 시간을 바탕으로 기본 60분 미팅을 요청함
4. 빠른 시간을 원하지만 그 사정은 후보자에게 말하지 않으려 함
5. 회사가 기본안을 승인하여 연결과 미팅 정보 준비가 끝남
6. 승인 전에 45분, 참석자 추가, 후보자용 요청 문구로 기본안을 고침

### 후보자 일정 선택 메일 6개

1. 한국어, 가능한 가장 빠른 시간 요청 포함
2. 한국어, 추가 요청 없음, 영문 이름 organizer
3. 한국어, 내부식 축약 문장을 후보자용 한 문장으로 바꿈
4. 한국어, 특정 요일·시간 제외 요청 포함
5. 영어, 빠른 시간 요청 포함
6. 영어, 추가 요청 없음

## 3. 반복 결과

초기 prompt 반복에서는 실제 모델 호출을 총 45회 수행했다. 다만 이 실행 당시 회사 Slack
평가기가 모델을 `claude-sonnet-5`로 고정하고 있어, 현재 Slack runtime과 동일한 모델을 사용한
평가는 아니었다. 문구 구조를 개선한 반복 기록으로는 유효하지만 runtime parity 증거로 보지는
않는다. 이후 평가기는 `getSlackOrgAgentModel()`을 사용하도록 고쳤고, 실제 Slack worker로 별도
재검증했다.

| 실행 | 호출 수 | 수동 합격 | 발견한 대표 문제 |
| --- | ---: | ---: | --- |
| 최초 기준선 | 12 | 4 | 제목·길이·참석자 bullet 영수증, 제안을 완료형으로 표현, 기계적인 메일 도입 |
| 구조 개선 1차 | 12 | 8 | 일부 답변의 `업데이트했어요`, `반영해둘게요`, 추가 요청의 과장 |
| 구조 개선 2차 | 12 | 11 | 가능 시간 설정 직후 한 사례가 여전히 `등록했어요`로 시작 |
| 후보자 메일 모델 비교 | 6 | 비교 평가 | 같은 한국어 3개 시나리오를 Luna와 Claude로 각각 호출 |
| 최종 회귀 확인 | 3 | 3 | 위 잔여 사례와 대표 후보자 메일 2개 모두 통과 |

회차별 점수는 자동 문법 점수가 아니라 위 여섯 기준으로 출력을 직접 읽어 판정한 결과다.
문구의 미세한 취향보다 잘못된 lifecycle, 요청의 맥락, 다음 행동을 우선했다.

## 4. 효과가 있었던 구조 변경

### 원시 상태 대신 사용자 관점의 상태를 전달

LLM에 `status=updated`, version, draft 같은 내부 필드를 그대로 보여주면 모델은 자연스럽게
“저장했어요”, “초안을 업데이트했어요”라는 영수증을 쓴다. 일정 tool 결과는 이제 다음처럼
모델이 설명해야 할 사용자 효과를 먼저 제공한다.

- 이 결과가 단순 제안인지, 회사 승인이 끝난 상태인지
- 후보자에게 아직 연락하지 않았는지
- 설정한 시간이 앞으로 slot 계산에 사용된다는 점
- 지금 회사 사용자가 할 다음 행동

가능 시간 변경 결과에서는 status와 version을 아예 문구 입력에서 제외했다. 이는 금지 문장을
늘리는 것보다 안정적으로 “앞으로 이 시간을 기준으로 일정을 찾을게요”라는 답변을 만들었다.

### 후보자 메일은 사실과 서사를 분리

회사명, 역할, 이름, 길이, 추가 요청, locale은 구조화된 사실 JSON으로 전달한다. LLM은 다음
서사만 담당한다.

1. 자연스러운 인사
2. 후보자가 앞서 연결 의사를 전한 맥락과 회사 측의 만남 의사
3. Google Meet, 길이, 2~3개 시간 요청
4. 후보자에게 보여도 되는 추가 요청 한 문장
5. 일정 선택 링크
6. 자동 확정과 이후 캘린더·Meet 안내
7. 짧고 따뜻한 마무리

메일 제목은 창의적 생성의 이점이 작고 흔들릴 이유가 없어서
`{회사명} {역할}: 일정 선택 요청` 규칙으로 결정한다. 본문만 LLM이 작성한다.

### 단계별 시제를 입력 계약으로 고정

회사가 아직 승인하지 않은 기본안은 “준비할게요”로, 승인 후에는 “준비되어 있어요”로
구분한다. 이 구분은 특정 금칙어 목록보다 tool 결과의 `user_facing_state`와
`response_mode`에서 먼저 결정한다.

### 생성 후 최소한의 결정적 검증

LLM 출력은 일정 선택 링크가 정확히 한 번 있는지, 후보자용 추가 문장이 실제 본문에 있는지,
요청 locale인지 확인한다. 검증에 실패하면 같은 인간적인 서사 구조를 가진 고정 fallback을
사용한다. 한국어 이름은 전체 이름을 유지하고 `Daniel 님` 같은 띄어쓰기는 `Daniel님`으로
정규화한다.

## 5. 모델 비교 결론

- 이번 실제 Slack 검증 환경의 `SLACK_ORG_AGENT_MODEL`은 `gpt-5.6-luna`이며, worker 로그와
  저장된 assistant message metadata에서도 모든 일정 조율 호출이 `gpt-5.6-luna`였음을 확인했다.
- 코드의 환경변수 미설정 fallback은 현재 `claude-sonnet-5`지만, 이 값은 이번 실행에서 사용된
  모델이 아니다. 환경 설정과 실제 호출 로그를 구분해 판단한다.
- 후보자 메일은 `gpt-5.6-luna`가 기본 모델이다.
- 동일한 한국어 메일 세 사례를 두 모델로 비교했을 때 Claude는 더 길고 격식적인 경향이
  있었고, `김호진 님`, “연결되고 싶다는 의사”처럼 한국어가 더 번역투가 되는 사례가 있었다.
- Luna는 세 비교 중 두 사례에서 더 간결하고 자연스러웠고, 한 사례는 비슷했다. Claude가
  일관되게 낫지 않았으므로 후보자 메일 모델은 올리지 않았다.

따라서 현재 결론은 **회사 Slack과 후보자 메일 모두 현재 설정인 Luna를 유지**하는 것이다.
Claude 비교에서는 후보자 메일 품질이 일관되게 좋아지지 않았고, 실제 Slack에서 발견된 문제도
모델 급이 아니라 surface 이름, 링크 변환, 내부 식별자 보정 경계에 있었다.

첫 실행에서는 가능한 시간 없음 → 채팅으로 평일 08:00–19:00 설정 → 후보자용 추가 메시지
저장 → 회사 승인 → `preparing` schedule과 `draft` round 생성까지 네 turn을 진행했다. 승인 전에는

실제 Slack 화면에서 다음 세 문제를 발견해 수정했다.

1. 모델 보정 뒤 `[스케줄 열기](...)`가 Slack에서 문자 그대로 보일 수 있어, 최종 Slack 전달
   경계에서 HTTP Markdown link를 Slack mrkdwn으로 변환한다.
2. DB 이름과 Slack display name이 다를 때 organizer가 후보자와 같은 `김호진`으로 보였다.
   현재 요청자가 organizer이면 활성 surface의 이름 `Daniel`을 사용하고, 다른 organizer의 이름은
   편집자 이름으로 덮지 않는다.
3. 내부 식별자 제거기가 정상적인 URL query의 Workspace UUID도 leak으로 판정해 `조직ID`로
   바꾸고 있었다. HTTP link의 목적지는 검사 대상에서 제외하되, 같은 UUID가 본문에 노출되면
   계속 leak으로 탐지한다.

최종 실제 출력은 다음 상태였다.

> 가능 시간을 정해주시면 60분 미팅으로 준비하고, 참석자는 우선
> Daniel님(`khj605123@gmail.com`)으로 둘게요. 향후 2주 안에서 가능한 선택지를 추려
> 김호진님께 보내드리겠습니다.
>
> 스케줄 열기에서 설정하시거나, “평일 오전 8시부터 오후 7시까지 가능해”처럼 이 대화에서
> 편하게 알려주세요. 아직 김호진님께는 아무 연락도 보내지 않았어요.

확인했다. 이 turn은 `gpt-5.6-luna` 2회였으며 잘못된 URL leak 판정에 따른 correction 호출은
더 이상 발생하지 않았다.

## 7. 최종 대표 출력

가능 시간 설정 직후 회사 측 답변은 다음 수준으로 정리된다.

## 9. 현재 경계

- 45회 prompt 반복은 로컬에서 구성한 사실·tool 결과로 생성 품질을 본 것이다. 별도로 위 실제
  Slack 게시와 이전 후보자 메일 E2E를 수행했다.
- 생성형 문장은 매번 조금 달라질 수 있다. 사실과 lifecycle은 입력 계약과 검증으로 묶고,
  문장 리듬까지 고정하지 않는 것이 현재 제품 목적에 맞다.
- Career Harper에는 이번 작업으로 새 tool을 추가하지 않았다.
