# Harper Career Daily QA 실행 기준

- 적용 자동화: `Harper Daily Conversation QA`
- 기준 시간대: KST (`Asia/Seoul`)
- 결과 저장소: Notion `Debugging Logs`
- 긴급 알림 채널: Slack `C0BULQ5K5EJ`
- 마지막 개정: 2026-09-04

## 1. 이 문서의 역할

이 문서는 `Harper Daily Conversation QA` scheduled task의 유일한 실행 기준이다. 자동화에 긴 실행 지침을 직접 저장하지 않고, 매 실행마다 이 문서를 처음부터 끝까지 읽은 뒤 현재 체크아웃에 있는 내용대로 수행한다.

기존 `docs/harper-daily-conversation-qa-rubric.md`와 `docs/service-health-daily-report-plan-ko.md`는 배경 자료로 참고할 수 있지만, 이 문서와 충돌할 때는 이 문서를 따른다. 이후 운영 피드백은 특정 사례만 예외 처리하지 말고, 비슷한 새 상황에도 적용할 수 있는 일반 원칙으로 이 문서에 반영한다.

이 QA의 목적은 지정된 기간에 실제로 발생한 에러와 심각한 제품·운영 문제를 찾아내고, 사용자 영향과 현재 상태를 확인하고, 근본 원인과 가장 이상적인 해결 방향까지 이해하기 쉽게 보고하는 것이다. 단순히 에러 로그 개수를 세거나 매일 같은 지표를 나열하는 보고가 되어서는 안 된다.

## 2. 핵심 운영 원칙

1. 로그의 `error`나 DB의 `failed` 표기만으로 장애라고 결론내리지 않는다. 실제 실행 경로, 재시도, fallback, 최종 DB 반영과 사용자 전달 결과를 함께 확인한다.
2. 사용자에게 영향이 있었는지, 영향이 현재도 남아 있는지, 복구되었는지를 구분한다.
3. Harper가 저장·전송·수락·거절·연결·예약·재시도·완료했다고 말한 경우에는 대응하는 tool call과 영속 상태 또는 실제 전달 기록을 확인한다.
4. 불만, 언어 오류, 답변 품질은 키워드나 글자 비율만으로 확정하지 않는다. 후보를 찾은 뒤 앞뒤 대화와 실제 노출된 결과를 읽고 판단한다.
5. 같은 근본 원인의 여러 로그·run·사용자 사례는 하나의 문제로 묶되, 사건 수와 영향 사용자 수는 각각 적는다.
6. 확인된 사실, 가능성이 높은 가설, 아직 확인이 필요한 사항을 섞지 않는다.
7. 현재 상태를 말할 때는 사건 발생 시각, 관련 production 배포 시각, 배포 후 재발 또는 복구 근거를 구분한다. 로컬 코드나 commit만으로 production 문제가 해결됐다고 말하지 않는다.
8. 내부 테스트·QA 계정과 테스트 역할은 실제 사용자 지표에서 제외한다. `company_roles.information.testOnly = true`인 역할은 명시적으로 허용된 fixture talent 외에는 모든 matching·fit·추천 경로에서 제외되어야 한다.
9. 개인정보, 이메일 주소, 전화번호, 이력서 내용, raw payload, token, secret을 Notion·Slack·Git diff 요약에 남기지 않는다. 식별자가 필요하면 앞 8자리 이하만 사용한다.
10. 중요한 문제와 정상·참고 정보를 명확히 분리한다. 중요한 문제가 있는데 정상 수치에 묻히게 작성하지 않는다.

## 3. QA 기간 결정

QA 실행을 시작한 즉시 실행 시작 시각을 고정한다. 이후 조사 시간이 길어져도 종료 시각을 다시 움직이지 않는다.

```text
종료 시각 = QA 실행 시작 시각
기본 시작 시각 = 종료 시각 - 25시간
실제 시작 시각 = 기본 시작 시각과 마지막 성공 QA의 종료 시각 중 더 과거 시각
```

모든 시각 계산과 표기는 KST를 기준으로 한다.

### 3.1 마지막 성공 QA 찾기

1. Notion `Debugging Logs` 데이터베이스에서 최신 Daily QA 페이지들을 읽는다.
2. 페이지 생성 시각이나 사람이 확인한 checkbox만으로 성공 여부를 판단하지 않는다.
3. 이 문서 형식을 사용하는 페이지에서는 `실행 상태 = 완료`이고 필수 토픽이 모두 점검된 경우에만 성공 QA로 인정한다.
4. 이전 형식의 페이지는 본문에 기록된 `감사 창`, `점검 기간`, `Coverage`와 실제 완료 내용을 읽어 종료 시각을 복원한다.
5. `부분 완료`, `점검 실패`, 필수 데이터 소스 누락으로 전체 결론을 낼 수 없는 페이지는 마지막 성공 QA로 사용하지 않는다.
6. 마지막 성공 QA 이후 비어 있는 기간이 있으면 그 기간과 기본 25시간을 합쳐 하나의 연속된 점검 기간으로 감사한다. 예를 들어 마지막 성공 QA가 9월 1일에 끝났고 다음 실행이 9월 3일이라면 9월 1일 이후부터 9월 3일 실행 시각까지를 한 번에 점검한다.
7. 이전 성공 QA가 전혀 없다면 기본 25시간을 점검하고, 과거 coverage를 확정할 수 없다는 사실을 메타데이터와 제한사항에 적는다.

25시간 때문에 이전 QA와 겹치는 사건은 ID와 정규화한 문제 추적 키로 중복 제거한다. 감사 기간 이후에 일어난 재시도·복구는 실행 시각까지 읽을 수 있지만, 감사 기간의 신규 사건 수에 섞지 않고 해당 사건의 복구 상태로만 기록한다.

기간이 길어 한 번에 모든 정성 검토를 끝내지 못하면 우선순위가 높은 구조화 검사를 전수 수행하고, 실제로 완료하지 못한 범위를 숨기지 말고 `부분 완료`로 기록한다. 이 경우 다음 실행도 마지막으로 완전히 성공한 QA의 종료 시각부터 다시 이어받는다.

## 4. 실행 순서

1. 이 문서와 작업 대상 repository의 `AGENTS.md`를 읽는다.
2. 실행 시작 시각, 현재 문서의 Git commit과 파일 상태, 관련 repository의 현재 revision을 기록한다.
3. Notion 데이터베이스 schema와 최근 Daily QA 페이지를 읽고 실제 점검 기간을 확정한다.
4. 필수 데이터 소스에 접근할 수 있는지 확인한다. 접근할 수 없는 영역을 정상으로 간주하지 않는다.
5. 구조화된 run·delivery·fit·recommendation·scheduler·ingestion·runtime 오류는 점검 기간 전체를 조회한다.
6. 불만, 탈퇴, 강하게 잘못된 액션, 잘못된 언어, 추천 품질 후보는 실제 대화와 전달된 콘텐츠의 주변 문맥을 읽는다.
7. 문제마다 영향, 시간순 사건, 첫 번째로 깨진 단계, 복구 여부와 현재 상태를 재구성한다.
8. 심각한 문제는 원인을 끝까지 좁히고 가장 이상적인 해결책과 검증 방법을 작성한다. Scraping 코드 결함은 제8장의 범위 안에서 실제 코드 수정까지 수행한다.
9. 최종 판단을 고정한 뒤 Notion 페이지를 한 번 생성하거나 동일 실행의 미완료 페이지를 이어서 완성한다.
10. Slack 발송 조건을 만족하는 심각한 문제가 있을 때만 운영 채널에 한 번 알리고 전송 성공을 확인한다.
11. scheduled task의 최종 응답에는 Notion URL, Slack 발송 여부, 코드 수정 여부와 남은 제한사항을 짧게 적는다.

## 5. 증거, 확신도와 심각도

### 5.1 증거 우선순위

가능한 한 다음 순서로 직접적인 증거를 사용한다.

1. 영속된 DB 상태와 실제 side effect
2. tool 결과, worker/run/scheduler/ingestion 상태와 전달 기록
3. 사용자와 Harper의 메시지 및 주변 문맥
4. 서로 일치하는 여러 간접 신호에서 얻은 가설

오래된 snapshot이나 현재의 mutable 상태를 사건 당시 상태인 것처럼 사용하지 않는다. 현재 열려 있는 공고라고 해서 추천 당시에도 열려 있었다고 단정하지 않고, 현재 닫힌 공고라고 해서 추천 당시에도 만료였다고 단정하지 않는다.

### 5.2 확신도

- `확인됨`: 직접적인 DB·tool·delivery·runtime 증거 또는 명백한 사용자 노출 모순이 있다.
- `가능성 높음`: 여러 증거가 일치하지만 원인이나 최종 영향의 한 단계가 비어 있다.
- `확인 필요`: 의심 신호는 있으나 영향이나 원인을 결론내릴 근거가 부족하다.

### 5.3 심각도

심각도는 단어 매칭이나 고정 점수의 합으로 결정하지 않는다. 실제 사용자 영향, 영향 범위, 복구 여부, 재발 가능성과 신뢰·개인정보 위험을 함께 보고 판단한다. 아래 예시는 경계가 아니라 기준점이다.

| 심각도 | 의미 | 대표 사례 |
| --- | --- | --- |
| `S0 치명적` | 즉시 대응이 필요한 신뢰·개인정보·보안·대규모 무결성 위험 | 다른 사용자 정보 노출, 잘못된 수신자, 명시적 수신거부 위반, 광범위한 핵심 경로 중단, 파괴적인 데이터 손상 |
| `S1 심각` | 핵심 사용자 가치가 실제로 막혔거나 여러 사용자에게 중대한 오안내가 발생 | 미복구 onboarding/recommendation/delivery 실패, scheduler 장시간 정지와 backlog, 내부 기회 수락·거절 유실, 실행하지 않은 중요한 액션을 완료했다고 안내 |
| `S2 주의` | 제한된 범위의 저하 또는 workaround가 있는 사용자 영향 | 복구됐지만 사용자에게 나쁘게 보인 tool 오류, 일부 잘못된 추천·언어·반복 질문, 단일 사용자 전달 지연 |
| `S3 참고` | 직접 장애는 아니지만 개선 가치가 있는 반복 신호 또는 관측 부족 | 설명 품질 약화, 작은 추세 변화, 원인 판정을 막는 observability gap |

같은 원인이 여러 사용자에게 퍼졌거나 핵심 경로 전체를 막으면 개별 사례보다 높은 심각도로 본다. 반대로 로그상 실패라도 정상 fallback으로 기대 가치를 제때 전달했다면 미복구 장애로 부풀리지 않는다.

### 5.4 토글 상태

각 필수 토픽의 Notion 토글 제목은 아래 중 하나로 끝낸다.

- `[확인 필수]`: S0/S1이 있거나 즉시 사람이 판단·대응해야 한다.
- `[확인 필요]`: S2, 중요한 미복구 항목 또는 가까운 시일 내 후속 확인이 필요하다.
- `[급한 오류 없음]`: 경미한 문제·복구된 문제·참고사항은 있지만 현재 S0/S1은 없다.
- `[괜찮음]`: 필요한 범위를 충분히 확인했고 보고할 문제나 유의미한 이상이 없다.
- `[점검 불가]`: 필수 데이터나 도구에 접근하지 못해 결론을 낼 수 없다.

`[점검 불가]`를 `[괜찮음]`이나 `[급한 오류 없음]`으로 완화해서 표시하지 않는다.

## 6. 필수 점검 토픽

아래 토픽은 매 실행마다 모두 확인하고, 각 토픽을 Notion의 독립된 토글 하나로 만든다. 예시는 조사 범위를 설명하기 위한 것이며 체크 항목에 없는 비슷한 문제도 같은 원칙으로 찾아야 한다.

### 6.1 Scraping과 공고 데이터

실제로 운영 중인 공고 수집 repository, scheduler, workflow와 데이터 저장 경로를 확인한다. 단순히 process가 살아 있는지가 아니라 각 source의 최신 실행이 끝까지 완료되어 사용할 수 있는 공고가 저장됐는지 확인한다.

필수 확인:

- scheduled ingestion/scraping run의 마지막 시작·완료 시각과 `failed`, `partial`, stale 상태
- source별 수집량, 새 공고 수, 유효 공고 수가 직전 정상 기간이나 최근 7일 범위에서 비정상적으로 0 또는 급락했는지
- `401`, `403`, `429`, CAPTCHA, 로그인 벽, timeout, provider 응답 변화와 retry/fallback 결과
- parser와 schema 변화로 필수 필드, URL, 회사·직무 mapping, description이 비거나 잘못 저장됐는지
- duplicate, 잘못된 URL, 이미 만료된 공고, source freshness와 expiry 처리 이상
- 수집 성공 로그는 남았지만 downstream ingestion이나 추천 후보에 반영되지 않은 경계
- 특정 source 장애가 전체 scraping 장애인지, 해당 source만의 외부 문제인지

문제가 있으면 증상에서 멈추지 않고 scheduler → fetch → parse → normalize → store → downstream selection 순서로 첫 번째로 깨진 단계를 찾는다. 외부 서비스의 일시 장애, 인증 만료, rate limit처럼 코드 수정으로 해결할 수 없는 경우에는 억지로 코드를 바꾸지 말고 복구 방법·우회책·필요한 운영 액션을 구체적으로 적는다.

재현 가능한 scraping 코드 결함이면 제8장의 안전 규칙에 따라 최소 수정과 targeted test까지 수행한다.

### 6.2 Talent-side errors

#### Tool call과 대화 실행

- `career_tool_call`과 실패 로그를 tool별로 확인하고 영향 사용자와 최종 복구를 추적한다.
- JSON parsing, timeout, rate limit, provider, DB 오류가 사용자 응답이나 side effect에 실제 영향을 줬는지 확인한다.
- Harper가 성공을 말했지만 tool call이나 DB 반영이 없는 경우를 찾는다.
- 사용자 메시지에 실질적인 assistant 응답이 없거나, 오류 답변 뒤 약속한 retry가 실행되지 않은 경우를 찾는다.

#### Opportunity discovery run

- `opportunity_discovery_run`의 queued, running, completed, partial, failed 상태를 trigger와 run mode별로 전수 확인한다.
- 오래된 queued/running, 반복 실패, retry가 생성되지 않은 terminal failure를 확인한다.
- completed 상태만 믿지 말고 추천 생성, 저장, delivery, 실제 사용자 노출까지 이어졌는지 확인한다.
- 의도된 no-result, duplicate/idempotency guard, 정상 skip을 장애와 구분한다.

#### Scheduler와 worker

- dedicated scheduler가 예상 주기로 check를 남기고 있는지, due state와 backlog가 비정상적으로 누적되는지 확인한다.
- scheduler process가 살아 있어도 실제 check나 run 생성이 멈춘 상태를 찾는다.
- queue-consuming worker의 처리량, stale lock, retry, 반복 error와 scheduler→queue→worker 경계를 확인한다.
- worker의 일시 오류가 회복됐는지, backlog가 실제로 줄고 있는지 확인한다.

#### 신규 온보딩 사용자

점검 기간 중 1시간 SLA가 만료된 실제 신규 사용자를 전수 확인한다. 기준 시점은 deterministic `onboarding_completed` 시각이다.

- onboarding 완료 후 1시간 안에 `opportunity_discovery_run`을 통해 만들어진 사용자 가치가 있는 이메일이 실제 `sent` 상태가 되었는지 확인한다.
- 로그인·인증 메일, draft, queued, 생성만 된 이메일은 이 SLA의 성공으로 세지 않는다.
- 테스트·QA 계정과 SLA 전에 탈퇴 완료된 계정만 분모에서 제외한다. 잘못된 이메일 주소, provider failure, bounce는 조용히 제외하지 말고 미수신 원인으로 분류한다.
- 메일이 없으면 run 미생성, queued/running 지연, run 실패, 추천 0, delivery 미생성, delivery 실패 중 첫 broken stage를 찾는다.
- 늦게 전달된 경우에는 복구됨과 SLA 위반을 함께 기록한다.

#### Internal fit과 내부 추천

- 신규 사용자마다 활성·추천 가능·non-testOnly internal role에 필요한 `talent_opportunity_fit`이 모두 생성됐는지 확인한다.
- `company_roles.information.testOnly = true` 역할은 전용 fixture allowlist 외에는 fit·추천·후속 질문 대상이 아니어야 한다.
- fit이 생성되지 않았으면 대상 role 계산, fit job 생성, evaluator 실행, 저장 단계 중 어디서 빠졌는지 확인한다.
- 유효한 internal fit이 있고 추천이 나가야 하는 상태인데 `talent_opportunity_recommendation` 또는 실제 delivery가 없는 경우를 찾는다.
- fit label만 보고 무조건 미발송 장애라고 단정하지 말고 role 상태, 이전 추천·거절, 사용자 최신 의사, 회사 공유 가능 상태와 적용된 guard를 함께 확인한다.

#### 전달과 후속 처리

- recommendation delivery와 `career_email_messages`의 sent, failed, skipped, pending을 확인한다.
- inbound email이나 내부 기회 응답이 들어왔는데 reply job, tool call, 상태 반영 또는 필요한 후속 안내가 누락되지 않았는지 확인한다.
- 사용자가 받은 추천·메일·채팅 내용과 DB에 기록된 역할·상태·CTA가 서로 일치하는지 확인한다.

### 6.3 Talent-side quality issues

#### 명시적 불만과 대화 품질

- 사용자가 불만, 실망, 혼란, 반복 요청, 정정 또는 신뢰 저하를 명시한 후보를 찾고 앞뒤 대화를 읽는다.
- 추천 품질, 대답 품질, 정보 누락, action 실패, UI 혼란, delivery, human handoff 중 실제 원인을 구분한다.
- assistant가 답변은 했지만 사용자의 핵심 요청에 답하지 않았거나 질문만 반복한 경우도 확인한다.
- 한 사례를 일반적인 제품 문제로 확대하지 않는다. 단일 사례 자체가 심각하거나, 독립된 여러 사례 또는 정량 cohort가 있을 때 반복 문제로 보고한다.

#### 탈퇴 사용자

- 점검 기간에 탈퇴를 요청하거나 완료한 사용자의 남아 있는 대화·이벤트·오류 기록을 확인한다.
- Harper의 추천, 답변, 반복 질문, 잘못된 액션, 개인정보 우려, 연락 빈도나 delivery 문제가 탈퇴 의사에 영향을 주었는지 문맥으로 판단한다.
- 사용자가 이유를 말하지 않았으면 Harper의 잘못이라고 추정하지 않고 `확인 필요`로 남긴다.
- 삭제된 계정의 개인정보를 복구하거나 보고서에 복사하지 않는다. 감사에 허용된 최소한의 비식별 이벤트만 사용한다.

#### 강하게 잘못된 액션과 사실성

다음과 같은 문제는 높은 우선순위로 전수 확인한다.

- 사용자가 내부 기회를 이메일이나 채팅에서 수락·거절했지만 tool call 또는 DB에 반영되지 않은 경우
- Harper가 할 수 없거나 실행하지 않은 일을 할 수 있다고 설명하거나 이미 처리된 것처럼 말한 경우
- 저장·공유·전송·연결·재시도·상태 변경을 말했지만 실제 side effect가 없는 경우
- 회사의 수락·거절·검토 상태, 일정, 연락, 이력서 공유 여부를 근거 없이 단정한 경우
- 사용자의 최신 수정·선호·거절을 무시하고 과거 정보를 다시 적용한 경우
- 다른 사용자·회사·대화의 정보가 섞인 경우

#### 언어

- 실제로 사용자에게 전달된 chat, recommendation copy, email subject와 본문을 사용자의 발송 당시 유효 언어와 비교한다.
- 유효 언어는 최신 명시적 요청, 최근 지속적인 사용자 언어, 현재 요청 언어, 저장된 locale, 오래된 대화 언어 순으로 판단한다.
- 한국어 사용자에게 보내는 이메일에는 영문 회사명, 직무명, 기술명과 자연스러운 영어 표현이 섞일 수 있다. 혼용 자체를 오류로 보지 않는다.
- 영어 사용자 이메일은 의미 있는 본문에서 한글 문자가 약 20% 이상인 경우를 우선 검토 후보로 삼을 수 있다. 회사명·직무명·사용자 인용·공고 원문은 가능한 한 제외한다.
- 비율은 후보 선별용일 뿐 오류 판정 기준이 아니다. 영어 사용자가 이해해야 할 제목이나 핵심 문장이 실질적으로 한국어로 작성된 경우에만 명확한 언어 오류로 확정한다.
- 초안·저장 후보·queued 콘텐츠가 아니라 실제 sent/delivered 기록이 있는 콘텐츠만 사용자 노출 오류로 본다.

#### 추천 품질

- 명시적 불만·negative feedback·만료 신고·잘못된 링크·hard constraint 위반이 있는 추천은 전수 확인한다.
- 공고 가용성, role/company/URL mapping, 위치·비자·근무 형태·seniority 같은 hard constraint, 최신 요청과의 적합성, 중복·기거절 재추천을 확인한다.
- external과 internal 추천을 구분하고, 전체 분모와 실제 검토한 sample을 함께 적는다.
- 현재 상태만으로 추천 당시 품질을 단정하지 않는다. 사건 당시 증거가 없으면 `확인 필요`로 남긴다.

### 6.4 Company-side errors

회사에 응답하는 `/org` 및 Slack의 LLM은 `company-side LLM`이라고 부른다. 웹과 Slack의 사용자 경험과 실제 상태 변경을 함께 확인한다.

필수 확인:

- company-side LLM의 tool call 실패, timeout, parsing 오류, 무응답과 잘못된 fallback
- 회사 가입·인증·초대·workspace 연결, role 생성·수정·종료 흐름의 실패
- 회사가 요청하거나 확인한 role 정보와 실제 저장된 role 정보의 불일치
- 후보자 조회·추천·상태 변경·수락·거절·후속 연락에 대한 잘못된 완료 안내
- 회사의 명시적 수락 또는 거절이 기대한 상태에 반영됐는지, 응답이 없는 상태를 임의로 수락·거절로 해석하지 않았는지
- 후보자의 수락만으로 회사에 후보자 정보가 자동 공유되지 않았는지, Harper 사람의 최종 확인 전 개인정보나 이력서가 노출되지 않았는지
- 회사·후보자·role·workspace가 다른 대상과 잘못 연결되지 않았는지
- internal role의 상태, fit, recommendation, 후보자 응답과 회사-side 진행 상태가 서로 모순되지 않는지
- 같은 오류가 `/org`와 Slack 중 한 채널에서만 발생하는지

사용자에게 보인 응답은 tool 성공 여부만으로 정상 처리하지 않는다. 처음 사용하는 회사 담당자가 요청이 어떻게 반영됐고, 실제로 무엇이 바뀌었으며, 다음 단계와 아직 일어나지 않은 일을 이해할 수 있는지 확인한다.

### 6.5 개인정보·대상 무결성·핵심 인프라

- 다른 사용자나 회사의 이름, 프로필, 이력서, 추천, 대화가 노출된 경우
- 잘못된 이메일·Slack·conversation 수신자에게 전달된 경우
- 수신거부·privacy choice·company sharing 경계를 위반한 경우
- test-only 데이터가 실제 사용자 matching, fit, 추천이나 follow-up에 들어간 경우
- Vercel/Supabase/Auth/Storage/Realtime 등 핵심 경로의 5xx, 함수 실패와 사용자 side effect
- scheduler, worker, cron, queue가 살아 있는 것처럼 보이지만 실제 핵심 처리가 멈춘 경우
- 로그·상태·실제 데이터가 달라 장애 판정을 할 수 없는 observability 문제

확인된 cross-user 노출, 잘못된 수신자와 중대한 privacy 위반은 `S0 치명적`으로 본다.

## 7. 심각한 문제의 원인 분석과 해결안

모든 S0/S1과 중요한 S2는 최소한 아래 내용을 갖춰야 한다.

1. 기대된 정상 동작
2. 실제 사건의 시작 시각과 시간순 경과. 모든 시각은 날짜를 생략하지 않고 `YYYY-MM-DD HH:mm:ss KST`로 적는다. 사용자 단위 사건은 확인 가능한 범위에서 가입·온보딩 완료·문제 발생·불만 표출·복구·탈퇴 시각 중 해석에 필요한 시점을 함께 적고, "몇 분 뒤" 같은 상대 시간만 남기지 않는다.
3. 영향 받은 사용자·run·delivery의 수
4. 요청 → 판단 → 실행 → 저장 → 전달 중 첫 번째로 깨진 단계
5. 확인된 원인과 아직 가설인 원인을 분리한 설명
6. retry, fallback, 후속 처리와 최종 복구 여부
7. 현재도 영향이 남아 있는지
8. 즉시 가능한 안전 조치
9. 가장 이상적인 구조적 해결방법
10. 해결을 검증할 구체적인 확인 방법

원인을 끝까지 확인하지 못했으면 그럴듯한 단정을 만들지 않는다. 지금까지 확인된 마지막 정상 단계, 첫 의심 단계, 추가로 필요한 증거를 적는다. 해결책도 단순히 “확인 필요”로 끝내지 말고 어떤 코드·데이터·운영 경계를 어떻게 바꾸고 무엇으로 성공을 검증할지 제안한다.

## 8. Scraping 코드 수정 규칙

재현 가능한 scraping 코드 결함이 확인되면 감지와 제안에서 끝내지 말고 실제 코드 수정과 검증까지 수행한다.

1. 문제를 소유한 정확한 repository와 production 실행 경로를 먼저 확인한다.
2. 해당 repository의 `AGENTS.md`와 관련 운영 문서를 읽는다.
3. 수정 전 `git status`를 확인하고 사용자나 다른 작업의 변경을 보존한다.
4. 원인과 직접 관련된 최소 범위만 수정한다. 기존 변경과 겹쳐 안전하게 수정할 수 없으면 덮어쓰지 말고 blocker와 이상적인 patch를 보고한다.
5. 실제 운영의 개인정보·원문 payload·secret을 fixture나 test에 복사하지 않는다.
6. 수정된 parser·normalizer·scheduler 경로에 맞는 targeted test 또는 안전한 dry run을 실행한다.
7. 테스트가 실패하면 숨기지 말고 실패 원인과 미완료 상태를 적는다.
8. 변경 파일, 변경한 동작, 실행한 검증과 결과, 아직 남은 위험을 Notion의 Scraping 토글에 기록한다.
9. commit, push, PR 생성, merge, 배포, production service restart는 하지 않는다.
10. production DB나 수집 데이터를 임의로 수정·삭제·재수집하지 않는다. 별도의 명시적 권한이 필요한 실제 복구 작업은 다음 액션으로 남긴다.

외부 사이트 장애, credential 문제, rate limit, CAPTCHA, 일시 네트워크 실패처럼 코드가 원인이 아닌 문제는 코드 수정 의무의 대상이 아니다. 이 경우에도 파악된 원인, 안전한 우회책, 필요한 담당자 액션과 복구 검증 방법은 반드시 적는다.

- 비교 기준 기간
- 확인한 데이터 소스와 접근하지 못한 데이터 소스
- 구조화 전수 검사 건수, 직접 읽은 대화·메일 수
- 코드 수정 여부와 수정 repository·파일
- Slack 발송 여부와 성공·실패

현재 문서가 아직 commit되지 않았으면 임의의 SHA를 만들지 말고 `uncommitted working tree version`이라고 적는다.

### 9.4 읽기 쉬운 본문 구조

매일 아침 처음 읽는 사람이 바로 이해할 수 있게 다음 순서를 사용한다.

1. `오늘 바로 확인할 내용`: S0/S1과 사람이 해야 할 액션만 최대한 짧게 적는다. 없으면 `즉시 확인할 심각한 문제 없음`이라고 분명히 쓴다.
2. `중요하지만 급하지 않은 내용`: S2와 중요한 확인 필요 항목을 짧게 적는다.
3. 필수 토픽별 toggle
4. `Coverage와 제한사항`

필수 토글 예시:

```text
Scraping과 공고 데이터 [괜찮음]
Talent-side errors [확인 필수]
Talent-side quality issues [급한 오류 없음]
Company-side errors [괜찮음]
개인정보·대상 무결성·핵심 인프라 [점검 불가]
```

각 토글 안에는 해당될 때 다음 순서로 작성한다.

- 판정과 사용자 영향
- 중요한 문제
- 확인한 핵심 수치와 범위
- 근거와 시간순 경과
- 파악된 원인 또는 원인 가설
- 복구 여부와 현재 상태
- 해결방법과 다음 액션
- 코드 수정과 검증 결과
- 정상·참고 정보
- 해당 토픽의 제한사항

정상 수치와 중요하지 않은 세부 로그는 `정상·참고 정보`에 모으고, 중요한 문제보다 앞에 길게 나열하지 않는다. 내부 구현 용어가 필요한 경우에도 먼저 일반인이 이해할 수 있는 한글로 설명하고 괄호 안에만 정확한 기술명을 적는다.

각 문제에는 짧고 안정적인 `추적 키`를 붙여 다음 QA가 같은 근본 원인의 지속·재발·복구를 구분할 수 있게 한다. 개별 사용자나 run마다 새로운 추적 키를 만들지 않는다.

### 9.5 Coverage와 실패 보고

- 필수 데이터 소스가 일부 누락되면 확인한 범위만 사실대로 쓰고 실행 상태를 `부분 완료`로 한다.
- 핵심 데이터 소스에 접근하지 못해 결론을 낼 수 없으면 `점검 실패`로 한다.
- 보지 못한 데이터에 대해 에러가 없다고 추정하지 않는다.
- Notion 자체에 쓰지 못하면 scheduled task 최종 응답에 실패 원인, 보존된 결과와 재시도 방법을 남긴다.
- Notion 작성 실패 때문에 실제로 확인된 S0/S1 Slack 알림을 생략하지 않는다. 대신 Notion 링크를 만들지 못했다고 알림에 명시한다.

## 10. Slack 알림

Notion 페이지는 매번 만들지만 Slack `C0BULQ5K5EJ`에는 심각한 문제가 있을 때만 보낸다. 정상 보고, S2/S3, 단순 관측 부족, 복구 완료된 일시 오류 때문에 일반 알림이나 self-DM을 보내지 않는다.

### 10.1 발송 기준

다음 중 하나면 Slack으로 알린다.

- `S0 치명적`: 확인됨 또는 여러 직접 증거로 가능성이 높은 사건. 이미 복구됐어도 개인정보·잘못된 대상·신뢰 위험은 알린다.
- `S1 심각`: 확인됐고 현재 영향이 남아 있거나, 여러 사용자·핵심 경로에 영향을 주었거나, 사람이 즉시 결정해야 하는 사건.

단순 error log, 사용자 영향이 없는 정상 guard, 근거가 부족한 `확인 필요`, 단일 자동 복구 오류는 Slack 발송 근거가 아니다.

같은 추적 키의 같은 사건을 매 실행마다 반복 전송하지 않는다. 처음 확인됐을 때, 영향이 뚜렷하게 악화됐을 때, 원인·필요 액션이 중요하게 바뀌었을 때 또는 복구를 반드시 알려야 할 때만 다시 보낸다.

### 10.2 발송 형식

한 QA에서 보낼 운영 알림은 기본 한 메시지로 합치고 S0부터 정렬한다. 세부 정보는 Notion에 두고 Slack은 최대한 짧고 쉬운 한글로 쓴다.

```text
*[심각도] - 제목*

자세한 내용: 무엇이 언제부터 깨졌고 누구에게 어느 정도 영향이 있는지

파악된 원인: 확인된 원인. 가설이면 가설이라고 표시

다음으로 해야 하는 액션: 지금 담당자가 결정하거나 실행해야 할 한 가지

Notion: 전체 QA 페이지 링크
```

여러 심각한 문제가 있으면 같은 메시지 안에 문제별로 위 형식을 반복하되, 가장 중요한 내용부터 적고 불필요한 정상 수치를 넣지 않는다. PII, raw payload, secret과 긴 내부 ID는 포함하지 않는다.

연결된 Slack 도구로 실제 전송 성공을 확인한다. 실패하면 같은 실행에서 무한 재시도하지 말고 오류와 안전한 재시도 방법을 Notion 및 scheduled task 최종 응답에 기록한다.

## 11. 외부 변경과 안전 경계

이 QA가 기본적으로 허용하는 write는 다음뿐이다.

- 실행당 Notion QA 페이지 한 개 생성 또는 동일 실행의 미완료 페이지 완성
- 조건을 만족할 때 Slack 운영 알림 한 번
- 확인된 scraping 코드 결함의 로컬 최소 수정과 검증

별도 명시적 요청 없이 다음 작업을 하지 않는다.

- production DB 수정, 삭제, backfill, replay 또는 migration
- 사용자·회사에 이메일이나 메시지 발송
- Git commit, branch push, PR 생성 또는 merge
- `main` push, 배포, release, production service restart
- 다른 작업자의 변경을 되돌리거나 덮어쓰기

문제 해결에 위 작업이 필요하면 정확한 대상, 이유, 예상 영향, 안전 절차와 검증 방법을 다음 액션으로 적는다.

## 12. 완료 조건

다음이 모두 충족되어야 QA를 완료로 표시한다.

- KST 실행 시작 시각과 실제 점검 기간을 고정했다.
- 마지막 성공 QA를 근거와 함께 확인했다.
- 모든 필수 토픽을 점검하고 상태 suffix를 붙였다.
- 모든 S0/S1과 중요한 S2의 사용자 영향, 첫 broken stage, 복구와 원인·해결안을 기록했다.
- 확인된 scraping 코드 결함은 안전한 범위에서 수정·검증했거나 수정할 수 없는 blocker를 분명히 적었다.
- Notion에 중복 없이 한 페이지를 남기고 다시 읽어 필수 내용과 토글을 확인했다.
- Slack 발송 조건을 판단했고, 발송했다면 성공을 확인했다.
- 확인하지 못한 범위와 다음 액션을 숨기지 않았다.
