# 좋은 이력서 작성 기준과 Apply with Harper 프롬프트 점검

문서 기준: 2026-10-14. 대상은 이력서 작성·수정과 지원 역할에 맞춘 편집이다. 기업의 채용 담당자, 대학 커리어센터, 정부 취업 안내, UX 채용 연구와 ATS 공급자의 공식 자료 **17개를 14개 기관·회사에서 교차검토**했다. 출처와 적용 범위는 마지막 표에 정리했다.

**좋은 맞춤 이력서는 채용 담당자가 이 사람의 실제 역할, 중요한 기여, 지원 업무와의 연결을 쉽게 파악하게 한다.** JD의 기술 단어를 더 많이 넣는 것과는 다른 목표다. 필요한 기술은 확인 가능하게 드러내되, 그 기술이 핵심 역할·성과보다 과도하게 강조되지 않도록 내용과 위치를 선택해야 한다.

이 문서는 외부 권고, 그 권고를 결합한 편집 판단, 현재 로컬 코드의 점검 결과를 구분한다. 공식 안내의 반복되는 권고는 실무 기준으로 삼지만, 특정 형식이 모든 회사에서 합격률을 높인다는 인과적 증명으로 취급하지 않는다. 영미권 자료가 중심이므로 한국 기업의 지정 양식·지원 지침은 별도로 확인해야 한다. 프롬프트 변경이나 배포를 기록하는 문서는 아니다.

## 2 JD의 중요도와 이력서에서의 강조 수준

지원 자격을 충족하는 데 중요한 정보와, 이력서의 정체성·주요 성과를 설명하는 정보는 서로 다른 역할을 한다. 예를 들어 Python이 필수라면 이력서에서 사용 경험을 확인할 수 있어야 한다. 그렇다고 실제 경력 직함에 Python을 붙여야 한다는 결론은 나오지 않는다.

외부 자료는 핵심 역할과의 관련성, 실제 성과, 간결한 전달을 함께 강조한다. 이를 결합한 **Harper 편집 판단**은 다음과 같다. 아래 구분은 모델이 맥락을 읽는 데 쓰는 설명이며, 키워드 빈도·고정 점수·시나리오별 코드 분류를 위한 규칙이 아니다.

| 살펴볼 내용 | 판단할 질문 | 표현에 미치는 영향 |
| --- | --- | --- |
| 역할의 중심 책임 | 이 사람에게 실제로 맡기려는 문제와 결과는 무엇인가? | 가장 관련 있는 프로젝트·업무와 중요한 기여를 앞에 둔다. |
| 필수 기술이나 자격 | 채용 담당자가 충족 여부를 확인하려면 어떤 근거가 필요한가? | Skills, 관련 경험, 자격 항목 등에서 명확히 확인되게 한다. |
| 차별화하는 깊이 | 그 기술의 전문성이 이 역할의 주된 가치인가, 일반적인 실행 수단인가? | 실제로 역할을 구별하는 깊이가 있을 때 더 많은 공간과 구체적 근거를 배정한다. |
| 이미 있는 근거 | 원문만으로도 필요한 역량을 충분히 이해할 수 있는가? | 충분하면 그대로 둔다. 약한 재표현이나 반복으로 바꾸지 않는다. |
| 편집의 비용 | 정보 추가가 중요한 결과를 가리거나 문장을 길게 만드는가? | 덜 중요한 세부사항을 축소하거나 다른 위치에 두고, 순이익이 없으면 수정하지 않는다. |

근거: [Oxford의 core requirements·불필요한 세부사항 축소](https://www.ox.ac.uk/careers/careers-guidance/job-search-and-applications/writing-applications/cvs), [Amazon의 역할별 정보 우선순위](https://www.aboutamazon.com/news/workplace/amazon-job-application-resume-writing-tips), [MIT의 실제 경험 선별과 기술 사용 맥락](https://capd.mit.edu/resources/resumes/). **위 질문과 배치 방식 자체는 이 자료들을 결합한 편집 제안이다.**

필수와 우대를 정확히 구분하는 것은 필요하지만, 그 구분만으로 강조 수준이 정해지지는 않는다. 필수 조건인 어떤 도구는 Skills 한 줄로 충분할 수 있고, 우대 사항인 도메인 경험은 실제 차별성을 보여 주는 프로젝트에서 중요하게 드러날 수 있다. 실제 JD의 업무와 후보자의 증거를 함께 읽어야 한다.

## 3 Engineer를 Engineer Python으로 바꾸는 사례

다음은 사용자가 지적한 `Engineer → Engineer - Python` 제안을 검토한 것이다. 해당 제안의 원문 trace를 이번 조사에서 재현한 것은 아니며, 사용자가 설명한 상황을 전제로 한다.

### 세 가지 제목을 구분한다

- **과거 경력의 직함**은 실제로 어떤 역할을 맡았는지를 나타낸다.
- **지원 역할 이름**은 이번에 지원하는 채용 공고를 가리킨다.
- **지원용 헤드라인·요약**은 후보자의 관련 전문성을 짧게 소개하는 편집 영역이다. 해당 형식이 있는 경우에만 쓰며 경력 사실과 일치해야 한다.

지원 역할의 요구 기술을 과거 경력 직함에 붙이면, 기존 역할을 그 기술 중심의 전문 직무로 읽게 만들 수 있다. Python을 실제로 썼다는 사실이 있어도 그 사용 사실과 역사적 직함은 구분해야 한다. 이 판단은 직함·고용 이력을 정확하게 표시하는 권고와 기술을 경험·Skills로 설명하는 권고를 결합한 것이다. [Stanford 경험 항목](https://careered.stanford.edu/sites/g/files/sbiybj22801/files/media/file/resume_and_cover_letter_examples_1.pdf), [MIT 기술 표현](https://capd.mit.edu/resources/resumes/), [UK work history](https://nationalcareers.service.gov.uk/careers-advice/cv-sections).

### 같은 Python 정보도 위치와 분량이 달라진다

| 상황 | 적절한 표현 방향 | 피할 편집 |
| --- | --- | --- |
| 일반적인 엔지니어 역할이고 Python은 필요한 실행 도구 | 실제 직함 유지. 확인된 기술을 Skills에 적고, 관련 업무를 설명할 때 자연스럽게 언급 | JD에 있다는 이유만으로 `Engineer - Python`으로 변경하거나 모든 불릿에 Python 반복 |
| 핵심 업무가 Python 라이브러리·런타임·언어 생태계 자체 | 실제 해당 업무의 깊이와 결과를 주요 경력 문장에서 강조. 지원용 소개가 있으면 관련 전문성을 정확히 설명 | 관련 도구를 사용한 경험만으로 전문 직함·expert 수준을 만들어 냄 |
| 내부 직함이 독자에게 불명확함 | 사실에 맞는 일반 명칭·짧은 설명을 함께 제시하여 업무를 이해시키는 방안 검토 | 지원 공고에 맞춘 새로운 역할·직급·전문성을 기존 이력으로 바꿔 표시 |
| 이미 Skills와 경험에 Python 사용이 명확함 | 역할의 다른 중요한 결손이 없다면 수정하지 않음 | 이미 충족한 조건을 더 크게 강조하려고 좋은 원문을 변경 |

위 표는 **가상의 상황에 대한 편집 제안**이다. Google의 군 경력 전환 안내처럼 특수한 직함을 민간 독자가 이해하도록 원래 명칭과 사실에 맞는 대응 설명을 함께 쓰는 예외는 있다. 그러므로 모든 직함 수정을 막는 방식보다는, 수정 목적이 사실의 명료화인지 공고 단어의 삽입인지 구분해야 한다. [Google 직함과 군 용어 번역 안내, PDF 7쪽](https://services.google.com/fh/files/misc/resume-writing-tips-for-veterans-2021.pdf).

## 4 Skills와 숙련도 표기의 기준

기술 목록은 읽는 사람이 보유 역량을 빨리 찾는 데 유용하다. 반면 업무 문장은 적용 대상·문제·성과를 보여 준다. 같은 기술을 두 영역에 쓸 수 있지만 각각의 기능이 있어야 한다. Skills에는 식별이 쉬운 기술명을, 경력에는 구체적인 사용 근거를 두는 방식이 합리적이다. 모든 도구를 직함으로 끌어올리거나, 같은 설명을 여러 영역에서 반복할 이유는 없다. [MIT](https://capd.mit.edu/resources/resumes/), [Princeton 기술 구획](https://careerdevelopment.princeton.edu/advanced-degree-resume-guide/helpful-headings).

`Python (expert)`는 필수 형식이 아니다. Oxford는 기술·언어 등의 도달 수준을 명확히 하라고 권하지만, 모든 기술에 expert 라벨을 붙이라는 의미는 아니다. **사용자의 확인된 숙련도와 설명 가능한 증거가 있을 때만** 그 수준을 표시하는 것이 이 문서의 편집 기준이다. 사용 연수나 JD의 required 문구만으로 expert를 추론하지 않는다. 수준이 불명확하면 `Python`이라는 기술명과 관련 업무 경험만으로도 필요한 정보를 전달할 수 있다. [Oxford Other Skills](https://www.ox.ac.uk/careers/careers-guidance/job-search-and-applications/writing-applications/cvs).

UX 학생·신입 대상 NN/G 안내는 사용 맥락 없는 긴 Skills·도구 목록을 경계한다. 이를 모든 기술 이력서의 Skills 금지로 일반화하면 안 된다. UX에서는 문제 해결·사용자 연구·의사결정과 포트폴리오가 더 중요한 증거가 될 수 있으며, 기술 분야에서는 간결한 기술 목록이 빠른 확인을 도울 수 있다. [NN/G UX 신입 이력서](https://www.nngroup.com/articles/resumes-ux-students-and-graduates/), [MIT](https://capd.mit.edu/resources/resumes/).

### Summary와 objectives를 같은 것으로 취급하지 않는다

일반적인 “좋은 기회를 찾는다”는 objective는 후보자의 기여를 설명하지 못한다. 반면 확인된 전문성·중요한 경력을 짧게 연결하는 summary는 경력 전환 등에서 도움이 될 수 있다. Google은 선택적 career/impact summary를, 영국 National Careers Service는 짧은 introduction을 소개한다. NN/G의 UX 학생·신입 안내는 objective를 경계한다. **대상과 정보 가치에 따라 판단해야 하는 영역이지, 어떤 이름의 문단이든 무조건 넣거나 빼야 하는 영역이 아니다.** [Google](https://services.google.com/fh/files/misc/resume-writing-tips-for-veterans-2021.pdf), [UK National Careers Service](https://nationalcareers.service.gov.uk/careers-advice/cv-sections), [NN/G](https://www.nngroup.com/articles/resumes-ux-students-and-graduates/).

## 6 ATS 대응과 사람에게 읽히는 품질

Greenhouse 공식 문서는 이미지 형태의 이력서, 복잡한 표·머리글·바닥글·다단 구성과 불분명한 구획이 parsing에 문제를 만들 수 있다고 설명한다. 이는 정보 추출의 실패·부분 성공에 관한 안내다. “Python을 직함에 넣어야 자동 탈락을 피한다”거나 “특정 키워드를 몇 번 반복하면 통과한다”는 근거가 아니다. [Greenhouse parsing 문서](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse).

관련 기술이 확인 가능하게 쓰이고 읽기 순서가 명료한 구조를 우선한다. 제출 형식은 실제 ATS·기업 지시를 따른다. PDF와 Word의 우열을 모든 시스템에 일반화하지 않는다. Berkeley는 ATS별 기능 차이와 제출 지시 확인을 명시한다. [Berkeley ATS 안내](https://www.career.berkeley.edu/prepare-for-success/resumes/).

현재 제안 프롬프트에는 `Every change must add meaningful role-relevant evidence or resolve a real clarity problem.`라는 좋은 기본 기준이 있다. 그러나 “관련 근거가 추가됐다”는 사실만으로 역할의 제목이나 중요한 성과 문장을 바꾸는 편집이 유익하다고 판단할 여지가 남아 있다. **현재 지침의 빈틈은 관련성 판단을 중요도·배치·문서 전체의 순이익 판단으로 연결하는 부분이다.** 이는 코드 문구와 외부 권고를 비교한 해석이며, 해당 한 문장이 사용자 사례를 발생시켰다는 인과적 검증은 아니다.

후속 저장 prompt는 승인된 원문과 인라인 수정 내용을 그대로 반영하도록 한다. 이는 승인 보존을 위한 올바른 계약이다. 약한 최초 제안을 저장 단계에서 임의로 고치는 방식으로 해결하면 사용자 승인과 달라진다. 제안 생성 단계의 판단을 개선하는 것이 우선이다.

## 8 우선 보강할 편집 계약

아래는 최초 점검에서 도출한 보강 방향이다. 이후 반영 범위와 검증은 마지막 절에 기록한다.

1. **역할의 핵심과 실제 후보자의 강점을 먼저 파악한다.** 지원 공고의 단어를 모두 채우는 작업으로 이력서 편집을 해석하지 않는다.
2. **필수 조건을 확인 가능한 수준으로 표현하고, 차별성에 맞춰 강조한다.** 조건 충족의 중요도와 직함·문서 상단에서 차지할 비중을 구분한다.
3. **역사적 직함과 기술 사용 정보를 구분한다.** 실제 역할과 자격의 정체성을 유지하고, 추가 정보는 맥락이 가장 잘 전달되는 위치에 선별해 둔다.
4. **수정문의 순이익을 원문과 비교한다.** 채용 담당자가 중요한 역할·기여·성과를 더 빨리 이해하는지, 과도한 세부사항·반복·길이·전문성 과장이 생기는지 검토한다. 이익이 불명확하면 원문을 유지한다.
5. **Memory는 근거로 선별해 사용한다.** 관련된 새 사실이라도 더 좋은 원문이나 문서 전체를 위해 생략할 수 있다. 모든 회수된 사실을 넣는 것을 성공으로 삼지 않는다.
6. **분야·회사·경력 단계의 예외를 허용한다.** 정보 구성·분량·전문 자료의 역할을 맥락에 맞게 판단한다. 명시적인 기업 제출 요건은 따른다.

이 판단은 기존 LLM의 문장 작성과 `reason` 설명 안에서 수행하는 방향이 적절하다. 키워드 빈도로 JD 중요도를 정하거나, 기술명을 발견하면 직함 수정·Skills 추가로 분기하는 규칙을 만들지 않는다. 별도 중요도 enum·점수·편집 판단 상태 머신이나 새 persistence 테이블도 필요하지 않다.

수정 제안의 성패는 개수와 저장 성공에 더해 **관련 사실을 정확히 쓰면서 원문보다 좋은 이력서를 만들었는가**로 판단해야 한다. 사용자 사례는 Python 한 종류의 문제로만 좁히지 않고, 어떤 도구·자격·도메인 키워드든 과도하게 부각하여 실제 역할과 성과를 흐리는 동일한 편집 오류를 점검하는 데 활용할 수 있다.

## 10 범용 편집 기준 반영과 보관

2026-10-14 로컬 코드에 공통 편집 계약을 반영했다. 생성·최초 제안·후속 제안이 같은 기준을 사용한다. 직무별 분기나 특정 섹션 추가 규칙은 만들지 않았다. 핵심 책임과 실제 후보자의 강한 근거를 먼저 고르고, 개인 기여·판단·결과를 독자에게 명료하게 전달한다. 필수 자격을 확인하는 것과 이력서에서 강조할 비중은 구분한다. 수치는 정확하고 유용할 때 쓰며, 질적 결과와 전문적 판단도 가치 있는 근거로 인정한다. 메모/Memory의 사실은 문서 전체에 도움이 되는 만큼 선별한다.

원문보다 읽기 쉬워지고 의미 있는 근거가 늘었는지 비교한다. 불필요한 세부정보·반복·수식어·근거 없는 확대는 개선으로 보지 않는다. 실제 직함·소속·자격·성과 귀속을 지키며 수치는 원래의 집계 대상·단위·기간에 붙인다. 편집상 제약은 실제 지원서가 요구하는 경우 외에는 이력서 문구로 옮기지 않는다. 새 문서에는 확인된 연락처·전문 자료 링크를 포함하고, 분량을 경력과 실제 제출 요건에 맞춘다.

승인된 문구는 그대로 저장한다. 제안의 품질 판단을 저장 시점의 임의 재작성으로 해결하지 않는다. 같은 원문에 대한 연관 수정은 하나의 제안으로 묶고, 각 제안이 다른 제안의 승인에 의존하지 않도록 한다. 후속 대화의 기존 완료 계약은 앞쪽으로 옮겨, 말로만 새 문장을 제안하고 검토 도구를 호출하지 않는 실패를 줄이도록 했다.

[직군별 동일 입력 비교와 후속 저장 검증](../evaluation/application-suggestions/reports/2026-10-14-editorial-quality-ko.md)에 수정 전후 원문 검토와 실패를 기록한다. 엔지니어·디자인·PM·법무/법인·founder·sales와 이미 좋은 이력서의 frozen synthetic 입력을 사용한다. 이 점검은 작은 비맹검 challenge이며 전체 사용자 품질이나 실제 접수 성공률을 입증하지 않는다. 연구 근거는 앞의 17개 공식 자료를 유지한다. 코드 변경은 미배포이며 DB·운영 계정·회사 제출에는 적용하지 않았다. 기존 schema의 summary 제한과 고정 renderer는 이번 작은 편집 기준 변경의 범위 밖이다.
