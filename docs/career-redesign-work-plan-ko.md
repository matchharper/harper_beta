# Career 재설계 작업 계획

2026-11-12. 사용자의 전체 요청에서 출발해 설계 결론을 다시 만드는 작업 계획이다. 기존 세 가지·네 가지 변경안은 출발점으로 채택하지 않는다.

## 이번 작업에서 끝낼 것

각 talent_user에게 가능한 가장 좋은 커리어 가치와 경험을 제공하려면 **무엇을 제거·수정·추가해야 하는지**, 구현 가능한 소수의 결정으로 정리한다. 각 결정이 사용자에게 무엇을 새롭게 가능하게 하는지, 왜 그 변경이 여러 문제를 함께 푸는지, 무엇은 아직 해결하지 못하는지 설명한다.

목적을 다시 말하는 문서나 코드 결함 목록만으로 완료하지 않는다. 구체적 테이블·tool 이름을 붙였다는 이유로 설계가 됐다고 보지도 않는다. 필요한 경험과 능력을 먼저 정하고 실제 데이터·코드·실행 결과에 대입한다.

이번 작업은 조사와 설계 문서 개선이다. 코드·운영 데이터·설정·배포를 변경하지 않는다. 운영 자료는 필요한 범위에서 읽고, 개인 원문을 저장소의 공개 문서에 복사하지 않는다.

## 산출물

1. 이 계획: 진행 상태, 조사 범위, 각 검토에서 바뀐 판단을 기록한다.
2. [현재 근거와 설계 쟁점](career-redesign-evidence-ko.md): 관측·코드상 동작·추론·미확인을 구분해 결론에 필요한 근거를 정리한다.
3. [핵심 변경안](career-core-changes-proposal-ko.md): 검토가 끝난 뒤 다시 작성한다. 최종적으로 무엇을 개발할지와 사용자가 얻을 차이를 연결한다.

[목적 문서](career-value-and-agent-direction-ko.md)는 전체 범위를 확인하는 기준으로 사용하되 사용자 원문보다 우선하지 않는다. [기존 가상 사례](career-value-scenarios-ko.md)는 사고실험 자료이며 현재 사용자 데이터나 성과의 증거로 사용하지 않는다.

## 1. 사용자 가치와 검토 범위를 먼저 고정한다

질문은 ‘현재 도구를 어떻게 정리할까’가 아니라 ‘어떤 도움을 어떤 방식으로 제공할 수 있어야 하는가’다. 다음 영역을 빠뜨리지 않고 검토하되, 이 구분을 새 기능 목록이나 실행 순서로 만들지 않는다.

| 영역 | 답해야 할 질문 |
| --- | --- |
| 이해와 첫 가치 | 필요한 정보를 질문·기존 자료·연결·실제 선택 등에서 얻고, 충분한 부분부터 도움을 줄 수 있는가? |
| 방법 선택 | 사용자 목적을 공고 검색으로 미리 바꾸지 않고, 유효한 접근을 생각하고 검증할 수 있는가? |
| 탐색 범위와 규모 | 내부 inventory 밖의 회사·사람·다른 가능성을 발견하고, 큰 집합을 넓게 찾으면서 필요한 곳은 깊게 조사할 수 있는가? |
| 조사와 판단 | 사용자마다 다른 중요한 정보를 확보하고, 근거·대안·불확실성으로 판단할 수 있는가? |
| 표현과 상호작용 | 보여 줄 대상·양·묶음·순서·상세·선택과 후속 행동을 목적에 맞게 바꿀 수 있는가? |
| 실제 수행 | 좋은 제안 이후의 준비와 외부 행동까지 맡고, 사용자가 해야 할 일만 남길 수 있는가? |
| 능력의 발전 | 낯선 목적에서 방법·지식·도구의 부족을 구분하고 실제 도움을 개선할 수 있는가? |
| 효율화 | 이미 가진 데이터와 결과를 활용하되 탐색 가능성과 품질을 조용히 줄이지 않는가? |

검토용 사용자 상황은 직군별 기능을 만들기 위한 분류가 아니다. 목적의 명확성, 즉시성, 시장의 성격, 정보 부족, 실행 위임 정도가 다른 상황을 사용한다. 사용자 예시 밖의 상황도 포함한다.

## 2. 현재 제품을 데이터와 실제 경로로 확인한다

### 먼저 확인할 자료

- 사용자가 연결한 Notion 기획의 원문과 관련 제품 문맥.
- 기존 checkout의 원본 prompt, 도구 설명과 결과, 데이터 조회·검색·추천 경로, UI가 소비하는 계약.
- 연결된 DB의 관련 schema와 데이터의 규모·분포·연결·누락을 보여 주는 집계.
- 설계 판단에 필요한 실제 실행 기록과 사용자 출력. 먼저 집계·메타데이터로 대상을 좁히고 필요한 실행만 확인한다.

### 연결해서 확인할 경로

| 경로 | 반드시 구분할 사실 |
| --- | --- |
| 첫 입력 → 사용자 이해 → 첫 도움 | 모델이 선택하는 것과 시스템이 강제하는 것, 실제로 사용 가능한 입력·도구 |
| 목적 → 탐색 → 후보 확보 | 검색 대상이 만들어지는 위치, 내부·외부 정보원, 회사와 Role의 관계, 실제 검색 가능한 규모 |
| 후보 → 조사 → 판단 → 제안 | 어떤 정보가 모델에 도달하는지, scoring의 역할, 누락을 더 조사할 수 있는지 |
| 제안 → UI → 사용자 반응 | 실제 renderer가 표현·선택할 수 있는 범위, 대상과 행동의 제한 |
| 관심 → 준비·연락·지원·관찰 | 실제 외부 능력과 권한, 특정 절차에 묶인 부분, 수행 가능한 범위 |
| 반복 조사와 사용자 간 재사용 | 공유 원본과 개인 판단의 경계, 기존 비용과 중복, 최적화가 판단 범위를 제한하는 부분 |

‘코드에 존재함’, ‘운영에서 호출됨’, ‘사용자에게 유용하게 동작함’을 같은 사실로 취급하지 않는다. 운영 자료에 접근할 수 없으면 미확인으로 남기고, schema나 코드만으로 실제 규모·성능을 추정해 확정하지 않는다.

조사는 결론을 바꿀 질문에 집중한다. 모든 파일과 로그를 전수 조사하는 것이 목표가 아니다. 현재의 작은 결함을 많이 찾았다고 제품 재설계가 진전됐다고 계산하지 않는다.

## 3. 바뀐 경험을 먼저 그리고 여러 설계안을 비교한다

각 상황에서 사용자가 처음 들어와 무엇을 얻고, 무엇을 판단·선택하고, Harper에게 어디까지 맡길 수 있어야 하는지 구체화한다. 화면을 단순히 새로 그리는 것과 새로운 정보·판단·행동 능력이 생기는 것을 구분한다.

그 경험을 가능하게 하는 서로 다른 설계안을 비교한다. Documents·opportunities·views·strategy·범용 agent 중 하나를 먼저 중심으로 정하지 않는다. 사용자 예시에 나온 구조도 목적에 실제로 도움이 되는 이유를 확인해 채택·수정·제외한다.

각 후보안에는 다음 내용을 붙인다.

- 사용자에게 새로 가능해지는 일과 그것을 가로막던 원인.
- 실제로 바꿀 데이터의 의미와 소유 원본, 모델 입력, 도구의 능력, UI 상호작용.
- 기존 코드·데이터로 가능한 부분, 새 외부 정보원·서비스·실행 능력이 필요한 부분.
- 이 변경 하나가 여러 사용자 상황에 적용되는 이유와 적용되지 않는 범위.
- 성능·경험·시간·비용의 절충과 더 단순한 대안.

새 persistence가 필요하다고 판단하면 무엇을 지속해서 보존해야 하고 누가 읽는지 밝힌다. tool을 추가한다면 기존 수단으로 할 수 없던 어떤 읽기·쓰기·실행을 제공하는지 밝힌다. 세부 migration과 prompt 문구를 먼저 작성하지 않는다.

## 4. 최소 세 차례 서로 다른 기준으로 다시 검토한다

### 검토 A — 사용자 가치와 인과관계

‘이걸 구현하면 실제로 UI가 달라지는가, 더 넓은 시장을 찾는가, 필요한 사실과 접근 경로를 얻는가, 설명과 실행이 좋아지는가’를 연결해서 본다. 기반 개선만 있는데 사용자 능력이 확대됐다고 주장한 부분을 제거한다. 전체 범위에서 빠진 경험을 찾는다.

### 검토 B — 일반성과 반례

원래 예시에 없는 목적, 공고와 무관한 도움, 짧은 요청, 내부 데이터가 없는 대상, 큰 탐색 집합, 기존 접근이 통하지 않는 상황에 대입한다. 새 객체나 ‘전략부터 작성’ 같은 절차가 또 다른 고정 틀이 되는지 확인한다. 기능을 하나 제거하거나 합쳤을 때 무엇이 실제로 불가능해지는지도 본다.

### 검토 C — 실현 가능성과 최적화

실제 코드·데이터·외부 서비스 능력으로 구현 경로가 성립하는지 확인한다. 전체 데이터를 모델에 넣는 식의 숨은 비용, 누락되는 정보, 새로 필요한 권한과 외부 능력, 반복 작업을 검토한다. 자유도를 줄이는 선택은 얻는 품질·속도·비용 이득과 잃는 가능성을 함께 적는다.

각 검토에서는 문장을 다듬는 데 그치지 않고 유지·수정·폐기한 결정을 기록한다. 설계 사고실험과 실제 모델 실행 결과는 구분한다. 기존 실행 증거로 판단할 수 없는 중요한 가설은 필요한 최소 검증을 설계하고, 확인하지 못했다면 최종안에서 명시한다.

## 5. 소수의 구현 결정과 우선순위를 작성한다

최종안은 각 항목이 ‘그래서 무엇을 제거·수정·추가하는가’로 끝나야 한다. 항목 수를 미리 정하거나, 적게 보이려고 여러 독립 문제를 추상적인 이름 아래 합치지 않는다.

완료 기준:

- 각 결정이 사용자 가치 → 현재 제약 → 변경 → 실제 능력과 경험으로 이어진다.
- 데이터·LLM·도구·UI 중 필요한 변화가 빠지지 않는다.
- 사용자가 든 예시만 지원하는 해법이 아니며, 새 목적에도 적용할 수 있는 이유가 있다.
- 기존 기능으로 이미 가능한 것을 새 기능처럼 제안하지 않는다. 반대로 실제로 없는 능력을 ‘agent가 알아서 한다’고 가정하지 않는다.
- 품질 개선과 비용 최적화를 구분하고, 확인한 사실과 아직 남은 가설을 표시한다.
- 첫 구현 묶음만으로도 사용자가 체감할 변화가 생긴다. 기반 정리만 한 뒤 가치가 생겼다고 보고하지 않는다.

## 검토에서 바뀐 결정

1. **A — 가치와 인과관계:** 구성 가능한 화면만으로 실행까지 된다고 읽히는 공백을 발견했다. 실제 선택을 기존 follow·예약·Gmail·회사 연락 executor에 연결하도록 보강했다. 방법 자료 역시 추상적인 개선 목적 대신 실제 loader와 자료 추가·검토·비교 경로로 구체화했다.
2. **B — 일반성과 반례:** 모든 결과를 기회 테이블에 넣거나 모든 요청에서 전략/화면을 먼저 만드는 안을 제외했다. 이직하지 않는 사용자, 짧은 질문, 대규모 탐색, 내부 원본이 없는 대상 등에 대입했다. 메일·예약은 이미 범용이라는 코드 근거를 반영해 재개발 범위를 줄였다.
3. **C — 실현 가능성과 최적화:** 회사 원본을 읽고 갱신하는 능력의 누락을 추가했다. 검색 분리가 기존의 빠른 묶음 실행을 없애지 않도록 수정했다. 희소한 회사 설명, 제공자 검증의 범위, 공유 사실과 개인 판단의 구분, 실제 자원 한도를 반영했다.

결론은 [핵심 변경안](career-core-changes-proposal-ko.md), 사실과 미확인은 [근거 문서](career-redesign-evidence-ko.md)에 남겼다. 새로운 제품 경로의 모델 성능·UI 사용성·외부 실행 성공은 구현 후 확인할 항목이다.
