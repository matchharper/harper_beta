# Career 구현 방향과 데이터 도구를 추가하는 이유

**지금 Career에서 가장 중요하게 만드는 것은 두 가지다. 사용자에게 정말 좋은 기회를 찾아주는 것, 그리고 그 기회를 실제로 얻을 가능성을 높이는 것.**

첫 번째는 그 사용자가 원하는 보상·역할·동료·회사·다음 경력·생활 조건을 가진 기회를 발견하고 판단하는 일이다. 두 번째는 그 기회를 얻는 데 걸리는 문제를 찾아, 사용자의 기여를 입증하고, 적절한 상대에게 접근하고, 준비·지원·후속 진행·조건 협의를 실제로 수행하는 일이다. 채용에서는 합격이나 오퍼, 공고가 없는 접근에서는 구체적인 역할 합의, 프로젝트에서는 계약으로 나타날 수 있다. 지원하기 쉬운 곳만 골라 합격률을 높이면 첫 번째 목표를 놓친다.

사용자가 “지금보다 보상과 역할이 나은 곳으로 옮기고 싶다”고 맡기면, Harper가 현재 조건과 경험을 이해하고, 내부에 공고가 없는 회사까지 찾아보고, 실제 팀과 역할의 조건을 조사한 뒤 검토할 대상을 보여주려고 한다. 사용자가 몇 곳을 고르면 필요한 자료를 준비하고 위임받은 연락을 진행한다. 답장이 오면 처음 제안했던 역할과 조건이 실제로 가능한지 확인하고 다음 일을 이어간다.

`/jobs/...`에서 Talk to Harper를 눌러 들어온 사용자도 회원가입과 `/career/onboarding`을 거친다. **달라지는 것은 그 이후 대화의 출발점이다.** 보고 온 회사·공고와 온보딩에서 확보한 자료를 읽고, 아직 관심이 불명확하면 확인하고, 이미 연결을 요청했다면 필요한 준비와 연결을 이어간다. `apply_to_internal_role`은 개인 기회 저장, `contact_company`는 실제 회사 연락을 담당한다. 진행에 빠진 정보만 묻고, 다른 좋은 기회도 도움이 된다면 상황에 맞게 탐색을 제안한다. 이를 고정 순서나 인사 문구로 만들지 않는다.

유입 공고를 대화에 연결하는 이벤트와 온보딩 이후 context는 이미 코드에 있다. 새 테이블·전용 tool 대신 이 경로에 실제 요청과 해당 기회의 진행 상태를 연결한다. 가입·온보딩 완료나 Talk to Harper 클릭을 회사 소개 동의로 취급하지 않는다. 이미 맡긴 요청과 완료한 실행도 다시 반복하지 않도록 기존 기록을 읽는다.

UI의 자유도, 개인 경험의 저장, 회사 조사, 작업 관리는 이 두 목표를 위해 검토한 수단이다. 사용자가 좋은 대상을 놓치지 않고 판단하게 하거나, 선택한 기회를 얻는 과정을 개선하는 데 필요한 만큼 만든다. 면접 준비와 커리어 상담도 중요하며, 특히 좋은 기회를 얻는 데 필요한 경우 그 과정 안에서 수행한다. 독립적인 상담·코칭 제품이나 범용 화면 편집기를 같은 우선순위로 확장하려는 계획은 아니다.

**무엇을 할지는 원본 agent LLM이 판단한다. 팀은 그 판단에 필요한 맥락, 정보를 얻는 수단, 실제 실행 도구, 결과를 보여주고 이어가는 구조를 만든다.** 아래는 그 환경을 어떻게 구현할지에 대한 제안이다.

먼저 판단의 기준을 분명히 잡아야 한다. 결제 시스템을 오래 만든 사람에게 결제 회사가 많이 검색된다는 사실만으로 이동을 권할 수는 없다. 그 사람이 원하는 것이 더 높은 보상, 좋은 동료, 글로벌 시장에서 인정받을 경험이라면 그 변화가 가능한 회사·팀·역할을 찾아야 한다. 과거 경험은 그 역할을 얻을 근거로 쓰인다. 현재 직장을 유지하거나 내부에서 역할을 바꾸는 선택도 비교할 수 있어야 한다.

그래서 현재 보상·업무·권한·시간 부담, 원하는 변화, 이미 진행 중인 선택지를 필요한 판단 입력에 연결한다. 모든 사람에게 같은 질문지를 받는 방식으로 구현하지 않는다. 대화나 기존 자료에 있으면 읽고, 판단에 중요한 정보가 없으면 확인한다. 단기 수입이 급한 사용자의 프로젝트 탐색과 장기 정규직 탐색은 조건이 다를 수 있으므로, 각 의뢰의 목적도 구별해서 읽는다.

**개인 자료를 다시 읽는 능력은 좋은 역할을 발견하고, 사용자가 그 역할을 맡을 수 있다는 근거를 만드는 데 쓴다.**

예를 들어 ML Engineer가 FDE 지원을 맡겼는데 이력서에 고객 대응 경험이 충분히 드러나지 않을 수 있다. Harper가 관련 자료와 연결된 메일에서 고객 도입·문제 해결 경험을 찾았다면, 다음 지원 때 그 조사를 처음부터 반복하지 않아야 한다. 동시에 그 내용을 공개 Profile에 전부 넣는 것도 적절하지 않다.

기존 저장소의 역할을 유지한다. 공개 경력 표현은 Profile, 현재 조건은 Brief, 재사용할 개인 사실은 Memory, 긴 경험과 작업 자료는 비공개 Documents. 추가하는 것은 이 원본들의 본문을 검색하는 `career_resource_index`와 원문·버전 연결이다. index는 사실의 새 원본이 아니라, 필요한 자료를 찾기 위한 검색용 데이터다.

LLM에는 현재 요청과 관련 자료의 짧은 색인을 먼저 주고, 필요할 때 본문을 읽게 한다. 경험을 정리한 문서에는 근거가 된 메일이나 자료를 연결한다. 이후에는 그 문서를 재사용하면서 새 경험이나 정정만 확인할 수 있다. 사용자가 고친 성과 수치가 다음 이력서에 반영되는 것과, 이미 제출한 이력서에 어떤 수치가 들어갔는지는 버전으로 구별한다.

**탐색에서는 찾을 수 있는 대상과 한 번에 다룰 수 있는 규모를 함께 넓힌다.**

`search_resources`는 회사·공고·공개 사람 정보·개인 자료·웹 등 실제 검색 원본에 연결한다. LLM이 목적에 맞는 정보원과 검색 질문을 선택한다. 같은 엔지니어 경력에서도 현재 채용 중인 회사, 좋은 제품을 만드는 팀, 사업을 확장하는 조직처럼 여러 방향으로 탐색할 수 있다. 내부 DB에 없는 회사는 공개 URL로 조사와 후속 작업을 시작할 수 있다.

검색 결과가 많아지면 결과를 모델의 긴 입력 목록으로 전달하는 데도 비용이 든다. 회사 1,000개를 찾은 뒤 조사·평가·화면 도구마다 1,000개의 ID를 다시 작성하게 할 필요는 없다. 검색 결과의 구성원을 서버에 보존하고 `set_ref` 하나로 가리키게 한다. 이것이 `career_result_sets`와 `career_result_items`를 추가하는 이유다.

같은 집합을 대상으로 평가하거나 일부만 조사할 수 있다. 집합을 합치고, 필터링하고, 이전 결과와의 차이를 구하는 연산은 `manage_result_sets`가 처리한다. 화면도 그 집합을 직접 읽는다. 문서 한 개를 읽거나 몇 개의 사실을 확인하는 요청은 일반 도구 결과로 끝내고, 작은 요청까지 집합을 저장하지 않는다.

회사를 반복해서 사용할 필요가 생기면 `write_resource`로 공개 회사 원본에 추가하거나 갱신한다. 출처와 정확한 회사 식별자를 함께 보존한다. 공고가 없는 회사를 표현하려고 가짜 공고나 회사 계정을 만들 필요는 없다. 개인적인 회사 평가와 메모는 해당 사용자의 자료에 둔다.

**대량 판단은 메인 LLM이 기준을 정하고 Decisions가 항목별로 실행한다.**

메인 LLM에게 회사 1,000개의 본문을 모두 읽히면 비용과 시간이 커진다. `evaluate_resources`는 기존 Jev/OpenAI Decisions 연결을 일반 대상에도 사용할 수 있도록 확장한다. LLM이 이번 목적, 사용할 개인 맥락, 평가 질문을 정하면 서버가 대상별 근거와 함께 작은 요청으로 나누어 처리한다.

예를 들어 사용자가 원하는 역할을 맡을 여지가 있는지, 현재보다 나은 이동이라고 판단할 근거가 있는지 등을 여러 대상에 적용할 수 있다. 질문은 목적에 맞춰 정한다. 회사 정보가 없어서 판단하지 못한 항목, 실제 기준에 맞지 않는 항목, 호출에 실패한 항목은 구별한다. 결과를 읽은 메인 LLM이 무엇을 더 조사하고 무엇을 사용자에게 제안할지 결정한다.

여기서 평가 기준의 재사용도 필요하다. 정기 실행마다 같은 뜻의 기준을 조금씩 다시 작성하면 cache가 있어도 재평가가 발생한다. 이전 평가의 기준을 ref로 다시 사용할 수 있게 하고, 실제 개인 입력·대상 근거·기준·모델이 같은 계산은 재사용한다. 회사 하나의 근거가 바뀌면 그 항목을 다시 평가하고, 사용자의 중요한 조건이 바뀌면 영향을 받는 평가를 다시 수행한다.

계산 기록은 기존 operations에 보존한다. 기준과 공통 개인 입력은 한 번 저장하고, 각 항목은 그 입력과 개별 근거를 참조한다. 항목마다 별도 전략 agent를 만들거나, 평가가 하나 끝날 때마다 메인 LLM을 깨우지 않는다. 메인 LLM은 완료된 범위와 분포, 필요한 항목을 읽는다.

**조사는 사용자가 선택하는 데 필요한 질문을 중심으로 하고, 공개 근거는 다른 사용자에게도 재사용한다.**

어떤 사용자에게는 해당 팀의 야간 대응이 중요하고, 다른 사용자에게는 실제 의사결정 권한이나 지역별 보상이 중요하다. `research_resources`는 대상과 알아낼 질문을 받는다. 기존 근거를 먼저 읽고, 부족한 부분만 수집한다. 이미 있는 근거를 읽는 `read_resources`는 새 개인 보고서를 자동으로 생성하지 않는다.

이를 위해 `resource_observations`에 출처, 읽은 시점, 원문의 발표 시점, 본문 또는 발췌와 그 위치를 보존한다. 웹페이지가 나중에 바뀌어도 당시 무엇을 근거로 판단했는지 다시 읽기 위해서다. 회사의 공개 사업 확장 발표는 여러 사용자가 공유할 수 있다. 그 발표가 특정 사용자에게 어떤 의미인지는 개인 맥락에서 따로 판단한다. 개인 메일로 확인한 조건은 개인 범위에 남긴다.

같은 공개 페이지를 여러 실행이 동시에 요청하면 수집을 합친다. 알려진 URL은 묶어서 읽고, 새 출처를 찾아야 할 때 검색한다. 오래된 자료를 오늘 읽었다는 이유만으로 최신 사실로 취급하지 않도록 발표 시점과 관측 시점을 함께 제공한다.

실제 역할의 예산이나 원격근무 예외 승인처럼 웹에서 답을 얻기 어려운 질문도 있다. 이때는 LLM이 더 검색할지, 사용자 자료를 읽을지, 권한 있는 상대에게 물을지 판단한다. 기존 연락·메일 도구로 질문하고 답을 이어 읽을 수 있어야 한다. “협의 가능”이라는 답과 “이 조건으로 승인됐다”는 답은 이후 행동이 달라지는 근거다.

**사용자 화면에는 Harper가 조사하고 판단한 내용이 남아야 한다.**

기회 화면의 상위 탭은 **새 기회 / 내 기회**로 정리한다. 새 기회는 Harper가 구성한 view 단위로 보여준다. view마다 제목·설명·포함된 기회 미리보기가 있고, 전체 제안 또는 개별 기회를 열 수 있다. 파트타임/풀타임, 한국/미국, 조건을 조합한 묶음, 우선 추천할 대상 등 어떤 구성이 유용한지는 LLM이 정한다. 사용자가 지역별로 다시 보여 달라고 하면 이미 가진 집합으로 view를 수정할 수 있다. 화면 재구성을 위해 시장 조사부터 다시 하지 않는다.

내 기회는 사용자가 저장하거나 진행을 맡긴 기회 단위다. 동일한 기회가 여러 view에 들어가도 저장·지원·연락 기록은 하나로 이어진다. view의 구성과 노출을 바꾸는 일이 실제 진행을 취소하거나 사용자 선택을 초기화하지 않게 한다.

회사를 추천하면서 팀 확장, 보상 범위, 사용자의 관련 경험까지 고려했어도 상세에 JD와 일반 요약만 나오면 사용자는 그 판단을 이해하기 어렵다. `manage_views`와 `career_views`를 추가해, LLM이 어떤 집합을 보여줄지, 무엇부터 읽게 할지, 어떤 근거와 설명을 연결할지 정하도록 한다.

화면은 준비된 목록·카드·상세·본문·작업 상태·문서·입력 컴포넌트로 구성한다. LLM은 구성·내용·순서·묶음·메인 행동을 정하고 React renderer가 공통 조작과 모바일 배치를 담당한다. 개별 상세는 해당 사용자에게 제안하는 내용, 조건과 근거, 다음 행동을 중심으로 하며 JD·회사·인물·행사는 원본을 연결한다. 모든 검색 결과를 추천으로 등록하지 않는다.

메인 버튼은 현재 할 만한 구체적인 요청 하나다. 원본 LLM이 문구와 사용자에게 보이는 요청 내용을 정한다. 선택 후에는 정확한 대상과 그 요청을 기존 대화 LLM에 전달하고, 이미 충분히 맡긴 행동은 다시 관심을 묻지 않고 수행한다. 저장·숨김·페이지 이동은 LLM 없이 처리한다. 실제 발송·제출은 기존 executor가 담당한다. 버튼 자체에 임의 코드나 보이는 문구보다 넓은 공유 권한을 넣지 않는다.

기존 설계는 일반 대상을 집합과 view에 넣는 방법까지 설명했지만, view를 바꾼 뒤에도 공고 없는 제안을 저장하고 진행할 원본이 부족했다. 현재 저장·진행 조회는 Role에 묶여 있으므로 `career_opportunities`를 추가한다. 실제 게시한 일반 제안의 identity와 내용·사용자 선택을 보존한다. 기존 Role 추천은 기존 원본을 유지하고, 기존 `upsert_opportunities`와 save/feedback 경로를 두 원본에 연결한다. 검색한 회사 전부나 잠정 전략을 저장하는 새 테이블이 아니다.

view는 결과 집합을 참조한다. LLM이 공고마다 카드를 다시 작성하거나 ID를 복사하지 않아도 된다. 정렬·페이지 이동·선택은 일반 UI 코드가 처리하므로 클릭할 때마다 모델을 호출하지 않는다. 사용자가 선택한 대상과 당시 버전을 보존해, 목록 순서가 바뀌어도 다른 회사에 요청이 전달되지 않게 한다.

**선택한 뒤에는 실제 맡긴 일과 결과를 이어서 관리한다.**

여기서 목표는 작업 목록을 잘 유지하는 것보다 구체적이다. 사용자가 그 기회를 얻는 데 무엇이 부족한지 판단하고 바꾸는 것. 경험이 전달되지 않았다면 근거와 표현을 보강하고, 접근할 사람이 없으면 실제 연결 경로를 찾고, 맞는 공고가 없으면 상대의 수요에 맞는 역할을 제안하고, 채용 과정에서 평가받을 준비가 부족하면 필요한 준비를 수행한다. 어느 접근이 유리한지는 LLM이 현재 사실과 상대의 반응을 보고 판단한다. 연락·제출은 그 접근을 실행하는 수단이다.

사용자가 다섯 곳을 맡기면 한 곳은 현재 이력서로 충분하고, 한 곳은 고객 대응 경험을 더 확인해야 하며, 다른 한 곳은 먼저 역할을 논의하는 연락이 필요할 수 있다. LLM이 그 차이를 판단하고 공통 자료를 재사용한다. 같은 질문을 다섯 번 묻지 않고, 답을 기다리는 동안 독립적으로 할 수 있는 준비는 진행한다.

이를 위해 기존 `manage_work`와 operations를 확장한다. 맡긴 목적, 정확한 대상, 원래 의뢰, 사용한 자료, 완료 결과와 대기 중인 일을 연결하고 새 대화에서도 찾을 수 있게 한다. 책임을 기록하는 것과 독립 background 실행을 시작하는 것은 분리한다. 현재 대화에서 끝낼 수 있는 일은 그대로 수행하고, 별도의 실행이 유리할 때 위임한다.

제안한 할 일, 실제 맡은 책임, 준비·발송·제출 결과는 구별해서 읽는다. 메일 초안이 있다는 것과 실제 보냈다는 것은 다르며, 긍정적인 답장을 받았다는 것과 역할·조건이 확정됐다는 것도 다르다. 당시 보낸 문서와 후속 회신을 연결해야 지원·협상·내부 승진을 다음 판단으로 이어갈 수 있다.

좋은 기회의 다음 면접이 내일이라면 실제 답변 연습과 필요한 근거 준비에 집중한다. 사용자의 시간과 마감도 입력에 포함한다. 직접 요청한 짧은 수정이나 상담은 그 범위에서 돕는다. 모든 요청을 큰 탐색 프로젝트로 확대하는 것은 두 목표에 집중하는 방법이 아니다.

추가 데이터의 역할은 다음과 같다.

| 추가 데이터 | 필요한 이유 | 실제로 읽는 곳 |
| --- | --- | --- |
| `career_opportunities` | 공고 없는 제안을 view 밖에서도 같은 기회로 저장하고 진행 | 기회 상세·내 기회·작업 target. 기존 Role은 기존 추천 원본 유지 |
| `career_resource_index` | 공개 프로필에 없는 경험과 긴 자료를 다시 찾기 | 개인 자료 검색 |
| `career_result_sets` / `career_result_items` | 검색 당시 대상과 범위를 보존하고 큰 집합을 ID 하나로 처리 | 조사·평가·화면·다음 검색 |
| `resource_observations` | 그때 읽은 근거를 보존하고 공개 수집을 재사용 | 조사·추천 설명·변경 확인 |
| `career_views` | 어떤 결과를 어떤 순서와 설명으로 보여줬는지 보존 | 화면·사용자 선택 처리 |

기존 Profile·Brief·Memory·Documents, work·operations·예약·발송 기록은 계속 사용한다. 위 데이터도 실제로 읽는 기능과 함께 추가한다. 직군마다 별도 경험 테이블을 만들거나, 매번 떠올린 계획을 새로운 업무 상태로 저장하지 않는다. 실제 검색 범위와 실행 결과는 시스템이 남기고, 나중에도 필요한 판단 맥락은 agent가 작업 메모나 문서에 정리한다.

**prompt와 handbook에서는 판단에 필요한 내용과 실행 계약을 정리한다.**

좋은 리크루터처럼 메일을 쓰려면 수신자가 누구인지, 어떤 관계인지, 이전에 무슨 말을 했는지, 이번에 무엇을 얻으려는지, 어떤 경험을 근거로 말할 수 있는지가 필요하다. 이 입력을 제공한 원본 LLM이 본문을 작성한다. 인사·설명 순서·문장 수를 하나씩 지시하는 방식으로 해결하지 않는다.

기존 입력 중 검색 횟수나 연락 순서를 일률적으로 정하는 지침은 실제로 사용되는 원본부터 정리한다. 기본 prompt에는 사용자의 목적과 위임을 이해하고 수행하는 역할을 둔다. handbook에는 도구의 효과와 재개 방법, 역할·보상·접근 경로를 검토하는 데 필요한 방법 지식과 적용 조건을 둔다. 모르는 분야는 필요한 자료를 더 읽을 수 있어야 한다.

코드는 소유권, 공유 범위, 정확한 대상과 버전, 동시 수정, 중복 발송 같은 실행 경계를 책임진다. 어떤 회사가 좋은지, 어떤 질문을 먼저 할지, 어느 정도 설명할지는 현재 목적과 근거를 받은 LLM이 판단한다. 결과가 좋지 않으면 실제 모델 입력과 도구 결과부터 확인한다. 필요한 사실이 없었던 문제와 방법을 잘못 고른 문제는 수정할 곳이 다르다.

비용에서는 평가와 수집을 따로 봐야 한다. Decisions가 저렴해도 회사 1,000곳의 자료를 처음부터 모으면 수집비와 시간이 커질 수 있다. 이미 공개 근거가 있는 첫 개인 평가, 같은 기준의 반복 평가, 사용자 조건이 바뀐 평가, 공개 근거부터 없는 탐색을 나눠 측정한다. 데이터가 없다는 이유로 유력한 회사를 버리거나, 정해 놓은 조사 개수에 맞춰 중요한 질문을 생략하지 않는다.

정기 실행은 이전 검색 범위·결과·평가 기준을 읽고 필요한 변화와 새 대상을 확인한다. 공개 source의 변경은 공유해서 관측하고, 사용자의 위임과 확인 시점에 맞춰 판단한다. 모든 페이지 변경마다 모든 사용자의 LLM을 호출하지 않는다. 병렬 처리는 대기 시간을 줄이고, 원문과 계산의 재사용은 총비용을 줄인다. 사용자에게 반복해서 설명하거나 선택하게 만드는 부담도 함께 확인한다.

같은 제안의 후보·조건·순위가 달라지면 기존 view를 갱신하고 바뀐 내용을 전달할 수 있다. 새로운 목적의 제안이면 별도 view를 만든다. 정기 실행마다 새 view를 의무 생성하지 않는다. 외부 메일을 이어갈 때는 실제 발송 message/thread와 관련 예약을 연결한다. 자료 저장만으로 다음 실행이 생기지 않으므로 기존 schedule에 확인을 예약하고, 예약 실행의 결과는 기존 사용자 전달 도구까지 연결한다. [Javier 시퀀스 검토](career-agent-javier-sequence-review-ko.md)에 이 연결과 사용량별 비용 가정을 풀어 두었다. 실행 실측이나 실제 연락 결과는 아니다.

구현은 다음 순서로 진행하려고 한다.

1. **좋은 기회 발견과 획득을 위한 행동을 함께 연결.** 내부 공고가 없는 회사도 실제 역할·조건의 근거와 함께 검토하고, 선택한 대상을 얻는 데 필요한 접근과 준비를 판단해 기존 도구로 수행한다. UI는 우선순위·이유·선택·후속 진행에 필요한 범위부터 구현.
2. **대량 탐색과 개인 자료 재사용.** 큰 집합의 검색·Decisions 평가·부분 재개·기준 재사용을 연결하고, 반복해서 필요한 개인 자료의 본문 검색을 보강한다.
3. **상대의 응답에서 실제 역할·오퍼까지 이어가기.** 열린 책임과 원래 의뢰를 다시 찾고, 상대의 답에서 남은 장애물과 조건을 판단해 후속 진행. 여러 작업이 같은 자료를 덮어쓰거나 같은 메일을 중복 발송하지 않도록 실행 계약 확인.
4. **반복 실행의 원가 확인.** 같은 사용자와 여러 사용자의 다음 실행에서 무엇을 재사용하고 무엇을 새로 수행했는지 측정한다. 공개 변경 관측, 재평가 범위, queue와 보존 정책 조정.

각 단계에서는 발견한 기회가 사용자에게 왜 좋은지, 그 기회를 얻는 데 어떤 장애물을 줄였는지부터 확인한다. 경험이 비슷하다는 이유로 조건이 나쁜 곳을 권하지 않는지, 과거에는 드러나지 않았던 기여를 적절한 상대에게 전달하는지, 실제 반응에서 준비와 접근을 바꾸며 오퍼·역할 합의로 이어가는지를 본다. 답장 수와 지원 수는 중간 관측이고, 확보한 기회의 실제 조건은 별도로 확인한다. 같은 입력의 계산이 재사용됐는지와 중요한 조건이 바뀐 계산이 갱신됐는지도 함께 확인한다.

지도·공동 계정·영상 작업물의 깊은 평가 등은 별도 능력이 필요한 범위다. 이를 모두 첫 구현의 선행 조건으로 넣지는 않는다. 첫 출시에서는 실제로 연결한 정보원과 실행 도구로 어디까지 끝낼 수 있는지 확인하고, 반복해서 사용자 결과를 막는 능력부터 확장한다.
