# Career 기회 탐색: 공개 글·기사로 회사를 찾고, 찾은 것을 쌓기 (설계안)

2026-11-19 작성. 로컬 신규 가입자 실행 10회(2026-11-18)와 코드 확인에 근거한다. 아직 구현하지 않았다. 기존 탐색 설계는 [career-opportunity-finding-design-ko.md](career-opportunity-finding-design-ko.md)에 있다. 추천 방향에 대한 상위 정본은 [좋은 기회를 어떻게 추천할까](career-good-opportunity-recommendation-ko.md)다.

## 0. 요약

지금 Career 에이전트는 Harper 색인 안에서 거의 모든 결정을 끝낸다. 웹에서 회사를 찾거나, 공고 없는 회사를 추천하거나, LinkedIn 채용 글·적극 채용·국가 진출 같은 신호를 찾는 일이 드물다. 어쩌다 찾은 것도 다른 사용자에게 거의 이어지지 않는다.

해결의 뼈대는 세 가지다.

1. **공개 글·기사 탐색을 검색의 기본 경로로 만든다.** `search_opportunities`에 `posts` 경로를 추가한다. 이 경로는 LinkedIn 글과 뉴스에서 채용·팀 구성·진출 신호를 찾는다. 해당 회사를 등록하고 다른 후보와 같은 기준으로 평가해 한 목록에 올린다. 에이전트에게 "웹을 찾아라"라고 지시하지 않는다. 색인 검색만큼 쉬운 선택지로 만들고, 아직 시도하지 않은 경로를 사실로 보여 준다.
2. **찾은 것은 코드가 공유 지식으로 남긴다.** 회사 신호, 웹에서 찾은 공개 공고, 회사 확인 결과를 모두 회사 단위의 공개 기록으로 저장한다.
3. **남긴 지식이 결정하는 자리에 보이게 한다.** 회사 검색 색인, 평가 모델 입력, 검색 결과 줄, 회사 카드에 최근 신호를 싣는다. 다음 사용자는 같은 것을 다시 찾지 않고, 이미 알려진 것 너머를 찾는다.

## 2. 원인

### 2.1 탐색이 적은 이유

1. **웹 탐색이 별도 행동이다.** 색인 검색은 한 번 부르면 수백 개를 평가해 점수와 함께 돌려준다. 웹 탐색은 에이전트가 검색어를 만들고, 결과를 읽고, 회사를 골라 등록하고, 다시 평가를 요청하는 여러 단계다. 비용이 큰 쪽은 결과가 확실히 비어 있을 때만 쓰인다. 실제로 웹 탐색은 색인에 공고가 없던 해외 탐색에서만 나왔다.
2. **할 수 있는 일이 보이지 않는다.** 웹 검색 도구 설명은 "Search the web for information, using search engine." 한 줄이다. LinkedIn 글을 날짜로 걸러 찾을 수 있다는 것도, 뉴스 범주가 있다는 것도 적혀 있지 않다.
3. **신호가 데이터 어디에도 없다.** 공유 회사 개요는 제품·창업자·투자만 다룬다. 검색어도 "회사 정보 투자 창업자"다. 회사 줄의 사실(팀 규모·증감, 열린 공고 수, 리더 배경)에도 채용 확대나 진출은 없다. 에이전트가 직접 웹을 찾지 않으면 신호는 생기지 않는다.
4. **색인이 시장 전체처럼 보인다.** 첫 검색에서 600~1,200개를 평가하고 "가장 높은 새 후보"를 받는다. 팀을 새로 꾸리거나 시장에 들어오는 회사는 공고보다 LinkedIn 글과 기사에 먼저 드러난다는 사실이 입력에 없다. 아직 시도하지 않은 탐색 경로도 보이지 않는다.
5. **회사 자체 추천의 문턱이 높다.** handbook이 회사를 추천할 때 "그 회사 사람에게 닿는 확실한 길"을 함께 요구한다. 공고가 있는 쪽이 늘 쉬운 선택이 된다.

### 2.2 누적되지 않는 이유

1. 웹에서 찾은 공개 공고가 개인 공고로 저장된다. `suggest`는 공개 출처 확인 없이 개인 공고를 만든다.
2. 회사 확인의 최근 소식은 화면용 줄만 만들고 버린다.
3. 회사 정보로 저장해도 회사 검색 색인, 평가 모델, 검색 결과 줄 어디에도 내용이 들어가지 않는다.

## 3. 설계 원칙

워크스페이스 지침과 2026-11-17~18 사용자 지침을 따른다.

- 에이전트에게 특정 도구나 웹 검색을 쓰라고 지시하지 않는다. 능력과 사실, 목적을 주고 판단은 에이전트가 한다.
- 공고·채용 글·회사는 `search_opportunities`의 경로로 찾고 같은 평가 경로로 평가한다. 출처마다 다른 평가 도구를 만들지 않는다.
- 새로 찾은 채용 글은 `company_roles`에 저장한다. 회사의 중심은 `company_workspace`이고, 회사 자료는 `company_datas`에 둔다.
- 공개 출처의 회사 사실만 공유한다. 사용자별 판단과 추천 이유는 그 사용자의 기록에 둔다.
- 도구 결과는 짧게, 판단에 필요한 사실만 담는다.
- 새 persistence는 실제로 다시 읽히는 공개 사실에만 둔다.

## 4. 해결책

### 4.1 공개 글·기사 경로: `search_opportunities`의 `posts`

웹 탐색을 색인 검색과 같은 한 번의 호출로 만든다. 지금의 `postings`(공고), `companies`(회사 설명·유사 회사), `named`(이름·URL)와 함께 쓸 수 있는 네 번째 경로다.

**입력**

```json
{
  "posts": {
    "about": ["AI companies building an engineering team in Seoul", "서울에 지사를 여는 해외 AI 회사"],
    "places": ["KR"],
    "since": "2026-08-20"
  }
}
```

- `about`: 찾을 신호를 말로 적은 것. 에이전트가 쓴다. 여러 개를 줄 수 있고, 언어는 자유다.
- `places`: 나라 코드. 검색어에 나라 이름을 붙이고, 추출 결과의 위치 판단에 쓴다.
- `since`: 이 날짜 이후 글만 본다. 기본 90일 전.

**실행 단계 (코드)**

1. **저장된 신호부터 읽는다.** 회사 검색 색인(4.5)에서 `about`과 가까운 회사 중 `since` 이후 신호가 기록된 회사를 찾는다. 다른 사용자가 이미 찾은 것은 웹 검색 없이 들어온다.
2. **웹에서 새 글을 찾는다.** `about`마다 두 번 검색한다.
   - linkedin.com 한정 + 날짜 필터: 채용 글, 팀 구성 글.
   - 뉴스 범주 + 날짜 필터: 진출, 지사 설립, 투자, 대규모 채용 기사.

   같은 출처 URL이 이미 신호로 저장돼 있으면 건너뛴다.
3. **결과에서 회사와 신호를 뽑는다.** 저렴한 모델 한 번으로 결과 묶음 전체를 읽는다. 특정 조직에 대한 글만 남기고, 다음을 구조화해 뽑는다.
   - 회사 이름과 웹사이트·LinkedIn
   - 무엇을 하는지(누구를 뽑는지, 어떤 팀을 꾸리는지, 어디에 진출하는지)
   - 장소와 날짜, 원문 URL
   - 채용 글이면 직무명

   판단(좋은 회사인가)은 하지 않는다. 사실 추출만 한다.
4. **회사를 해석하거나 등록한다.** 기존 이름·URL 해석(`named`와 같은 경로)으로 `company_workspace`를 찾는다. 없으면 등록하고, 개요 준비와 색인 갱신을 뒤에서 돌린다. Harper 연결(내부) 회사는 지금처럼 제외한다.
5. **신호를 저장한다(4.2).** 직무명이 있는 채용 글은 공개 채용 글 Role로도 등록한다(4.3과 같은 공개 기준).
6. **평가한다.** 회사와 채용 글을 지금의 외부 평가 실행에 넣어 같은 기준으로 점수를 매긴다. 평가 입력에 신호가 들어간다(4.5).
7. **결과를 돌려준다.** 다른 경로의 후보와 한 목록에 번호를 붙여 올린다. 회사 줄 끝에 신호 한 줄을 붙인다.

**결과 예시**

```
Search 3 · posts · 41 evaluated (companies 37 · hiring posts 4), 29 new to this matching; 12 from Harper's saved signals
Best new option: [812], ranked #2 of 1,120 available options in this matching by score
Routes so far (best new option's rank when found): postings 2× (#1 in search 1, latest search 2: #57) · companies by description 1× (#9 in search 2) · posts 1× (#2 in search 3)
Not tried in this matching: similar companies, named companies

[812] Mistral AI · company · 82 · new · posts
  Applied AI Deployment team in Seoul — LinkedIn 2026-11-03 (linkedin.com/posts/…) · news 2026-10-09: began hiring technical staff in Korea
  open roles 0 indexed · 1001–5000 employees, founded 2023, Paris
```

**비용과 시간 (추정)**

- 웹 검색: `about` 하나에 Exa 2회, 약 $0.014.
- 추출: 약 $0.002.
- 평가: 회사 20곳에 약 $0.003.
- 합계: `about` 두 개 기준 한 번에 약 $0.03~0.05, 15~25초 추가.
- 저장된 신호가 쌓일수록 웹 검색이 새 글만 다루므로 줄어든다.

**실패 처리**

- 웹 검색이나 추출이 실패하면 저장된 신호와 다른 경로 결과만으로 끝낸다.
- 실패 사실은 결과에 한 줄로 남긴다.

### 4.2 회사 신호 기록

신호는 "날짜가 있는 공개 출처가 말하는, 그 회사의 채용·팀 구성·진출·투자·출시" 한 건이다. `company_datas`에 한 건씩 쌓는다. 개요(summary)와 달리 같은 회사에 여러 행을 둘 수 있다.

| 필드 | 값 |
| --- | --- |
| `label` | `public signal` |
| `content` | 한 문장. 예: "Building its Applied AI Deployment team in Seoul and hiring for it." |
| `facts` | `{ "kind": "hiring" \| "team" \| "market entry" \| "funding" \| "launch" \| …, "place": "KR", "publishedAt": "2026-11-03", "roleTitle": "…" }`. `kind`는 추출 모델이 정하는 짧은 말이고, 코드는 분기에 쓰지 않는다 |
| `source_refs` | 원문 공개 문서 참조. 웹 검색이 이미 공개 문서로 저장한다 |
| `checked_at` | 저장 시각 |

- **중복:** 같은 출처 URL은 한 번만 저장한다.
- **표시 기간:** 결과 줄·카드·평가 입력은 `publishedAt`이 최근 90일 안인 신호를 최신순으로 쓴다. 오래된 행은 지우지 않고 이력으로 남긴다.
- **에이전트가 직접 저장한 주제:** `upsert_company`로 남긴 투자·성장 같은 주제도 날짜가 있으면 같은 방식으로 보인다. 별도 분류표는 두지 않는다.

### 4.3 웹에서 찾은 공개 공고는 공개 색인으로

`save_job_posting`의 `suggest`가 공개 출처가 확인된 공고를 공개 Role로 등록하고, 그 Role을 이 사용자에게 추천하도록 바꾼다.

- **공개 출처 기준:** 지금의 `index` 모드와 같다. 웹 검색 결과로 저장된 공개 문서가 있거나, 공개 채용 사이트를 직접 읽었거나(Workday·Workable·Ashby 등), 독립 웹 검색으로 찾아지면 공개다.
- **개인 공고로 남는 경우:** 사용자가 직접 준 URL처럼 공개 근거가 없을 때만이다. 개인 기록을 몇 필드 지운다고 공개로 만들지 않는다는 기존 원칙을 지킨다.
- **효과:** 웹에서 찾은 공고가 다음 사용자의 `postings` 검색에 바로 나온다.

### 4.4 회사 확인 결과도 신호로 저장하고 재사용

`read_companies`의 `check`는 지금 최근 소식을 매번 웹에서 찾고 버린다. 이를 다음처럼 바꾼다.

1. **먼저 저장된 신호를 본다.** 그 회사의 신호가 최근 14일 안에 확인됐으면 웹 검색 없이 저장분을 보여 준다. 예: "최근 신호 3건, 2026-11-18 확인".
2. **오래됐거나 없으면 검색한다.** 회사 이름으로 linkedin.com 한정 1회, 뉴스 1회를 날짜 필터와 함께 검색한다. 결과는 4.1의 추출 단계를 거쳐 신호로 저장한다.
3. **바로 다시 보고 싶을 때:** 에이전트가 새로 확인하겠다는 뜻(`maxAgeDays: 0`)을 주면 검색한다.

### 4.5 저장된 지식이 보이는 곳

| 자리 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 회사 검색 색인 본문(`career_company_search`) | 이름, 설명, 개요 첫 단락, 전문 분야, 열린 공고 제목 | 최근 신호 몇 줄을 더한다. "서울에 팀을 꾸리는 AI 회사" 같은 회사 검색에 걸린다. 신호를 저장할 때 그 회사 색인을 바로 갱신한다 |
| 평가 모델 입력 | 개요 본문 + 다른 주제의 이름 | 개요 + 최근 신호 본문(최신 3건, 짧게). 진출하거나 채용 중인 회사가 관심 점수에 반영된다 |
| 검색 결과의 회사 줄 | 설명, 관련 직무, 팀 사실 | 최신 신호 한 줄(날짜·출처) |
| `read_companies` 카드 | 개요 첫 단락, 주제 이름 | 최근 신호(날짜·출처)와 마지막 확인 시각 |

에이전트는 이미 확인된 것을 보고 다시 찾지 않는다. 그리고 그 너머를 찾는 데 검색을 쓴다. 공고가 없는 회사도 "지금 사람을 모으는 중"이라는 사실이 보이면 회사 자체를 추천할 근거가 된다.

### 4.6 판단에 쓰는 사실 (지시가 아니라 사실)

1. **웹 검색 도구 설명:** 능력을 사실로 적는다.
   - 날짜 필터가 있다.
   - 뉴스 범주로 투자·진출 기사를 찾을 수 있다.
   - linkedin.com으로 한정하면 공개 LinkedIn 글(채용 글 포함)이 날짜와 함께 나온다.
   - X 글은 제공자 색인에 거의 없다.
2. **`search_opportunities` 설명:** `posts` 경로가 하는 일과 저장되는 것을 적는다. 기존 색인 범위 문장("자기 사이트·추천·SNS로만 채용하는 팀은 자주 빠진다")과 이어진다.
3. **검색 결과의 경로 기록:** "이 매칭에서 아직 시도하지 않은 경로"를 한 줄로 보여 준다(4.1 예시). 멈출지는 에이전트가 판단한다. handbook의 기준("다른 관점에서 봐도 추천이 바뀌지 않으면 충분하다")이 실제로 남은 관점을 볼 수 있게 된다.
4. **handbook 시장 사실:** "팀을 새로 꾸리거나 시장에 들어오는 회사는 공고보다 공개 글과 기사에 먼저 드러나는 경우가 많다."
5. **회사 자체 추천의 문턱:** "그 회사 사람에게 닿는 확실한 길" 요구를 뺀다. 추천 근거는 지금 그 회사가 매력적인 이유(팀 구성, 진출, 최근 채용)다. 사람에게 닿는 길은 Harper가 다음 단계로 찾을 수 있다. 2026-11-18에 handbook에 넣은 "Harper가 다음에 할 수 있는 일"과 이어진다.

### 4.7 2단계: 시장별 정기 수집 (1단계 결과를 보고 결정)

Worker가 일주일에 한 번, 활성 매칭이 많은 시장(KR, SG 등)과 방향으로 `posts` 경로와 같은 수집을 미리 돌린다. 신규 사용자는 첫 검색부터 저장된 신호로 시작한다. 1단계에서 신호 저장량과 재사용률을 보고, 비용 대비 효과가 있을 때만 켠다.

## 5. 흐름 예시

**Chris (서울, 성장·전략·창업)**

- **첫 검색:** `postings`(KR·SG·CA, 성장·사업 리더) + `companies`(마켓플레이스·AI 사업 확장 회사) + `posts`("해외 AI 회사의 한국 사업 책임자 채용", "서울에 지사를 여는 회사", places KR·SG)를 한 번에 돌린다.
- **결과:** 색인 공고(번개장터, 우아한형제들)와 함께 Cognition·Mistral·Cohere의 한국 사업 구축 신호가 같은 목록에 올라온다.
- **답변:** 공고가 있는 곳은 공고로, Mistral처럼 공고 없이 팀을 꾸리는 곳은 회사 자체로 추천한다. "한국 사업을 맡을 사람을 찾는 단계라, 리더에게 닿을 경로를 찾아볼까요?" 같은 다음 단계를 함께 제안한다.
- **다음 사용자:** 한국 진출 회사에 관심 있는 사람은 첫 검색에서 이 신호를 저장분으로 받는다. 웹 검색은 그 뒤에 나온 새 글만 찾는다.

**Javier (싱가포르, VC)**

- **첫 검색:** 지금은 색인에 싱가포르 VC 공고가 없어 웹 검색 9번을 따로 했다. 바뀐 뒤에는 `posts`("Singapore VC firms hiring principals", "corporate venture arms expanding in Southeast Asia")가 투자사 채용 글과 CVC 설립 기사를 회사·채용 글로 등록하고 바로 평가한다.
- **저장:** 찾은 공고(Hydra Host 등)는 공개 Role이 된다. 다음 싱가포르 투자 직군 사용자의 `postings` 검색에 그대로 나온다.

## 6. 개인정보와 공유 경계

- 공유하는 것은 공개 출처의 회사 사실(신호, 공개 공고, 개요)뿐이다. 사용자별 판단, 추천 이유, 매칭 노트는 지금처럼 개인 기록이다.
- 사용자가 직접 준 URL은 공개 근거가 없으면 공개하지 않는다(4.3).
- 신호는 회사 단위로 저장한다. 채용 글 작성자 이름은 지금의 채용 글 Role 계약(`hiringPost`) 범위에서만 둔다. 개인 프로필을 모으지 않는다.
- Harper 연결(내부) 회사와 공고는 지금처럼 이 탐색에서 뺀다.

## 8. 구현 순서와 파일

1. **신호 기록과 읽기:** 새 `src/lib/career/companies/signals.ts`.
   - 저장(중복 확인 포함)과 최근 신호 읽기.
   - 추출 모델 호출.
2. **`posts` 경로:** `src/lib/career/matching/tools.ts`(schema), `searchRoutes.ts`(실행), `externalSearch.ts`(평가 입력에 신호), `candidatePool.ts`(경로 이름, 미시도 경로 줄, 회사 줄의 신호), `src/lib/llm/toolDescriptions.ts`.
3. **공개 공고 등록:** `src/lib/career/saveJobPosting.ts`, `jobLinkImportServer.ts`. `suggest`가 공개 출처를 확인하면 공개 Role로 등록하고 추천한다.
4. **회사 확인 저장·재사용:** `src/lib/career/companies/readCompanies.ts`.
5. **색인:** `src/lib/career/companies/discovery.ts`. 색인 본문에 최근 신호를 넣고, 신호를 저장할 때 다시 색인한다.
6. **사실 문장:** `webDefinitions.ts`·웹 검색 설명, `handbooks/opportunitySearch.ts`(시장 사실, 회사 추천 문턱).
7. **DB:** 새 테이블은 없다. 신호 조회용 부분 인덱스(`company_datas(company_workspace_id, checked_at) where label='public signal'`)를 둘지는 측정 후 정한다.

## 9. 확인 방법과 지표

**단위 확인**

- 공개 출처가 있는 `suggest` 공고는 공개 Role이 되고, 없는 공고는 개인 공고로 남는다.
- 신호의 중복 저장, 90일 표시, 14일 재사용이 맞게 동작한다.
- 결과 줄·카드·평가 입력의 형식과 길이가 맞다.

**실제 실행**

1. **신규 가입자 4명을 다시 돌린다.** 직전 결과와 비교한다.
   - `posts`나 웹 탐색을 쓴 실행 비율. 목표는 절반 이상이다.
   - 회사 자체 추천 수, 신호를 근거로 한 추천 수.
   - 저장된 신호 수와 공개 공고 수.
   - 1인당 비용과 시간.
2. **재사용을 확인한다.** 같은 분야 두 사람을 차례로 돌린다. 예: 호진 → 다른 오디오 AI 연구자, Javier → 다른 싱가포르 투자 직군. 두 번째 사람에게서 다음을 본다.
   - 첫 번째가 찾은 공고·신호를 검색 결과에서 바로 받는가.
   - 웹 검색과 회사 확인 검색 횟수가 줄었는가.

## 10. 남는 한계

- **X 글:** 검색 제공자 색인에 거의 없다. 필요하면 X API(유료) 연결을 따로 검토한다.
- **LinkedIn 글 본문:** 검색 결과의 발췌로 판단한다. 로그인 없이 전문을 못 읽는 글이 있다.
- **비공개 채용:** 공개 글로 드러나지 않는 채용과 추천 기반 채용은 여전히 보이지 않는다.
- **로컬 검증의 한계:** 로컬 색인에는 한국 공고만 있다(운영에는 미국·싱가포르 등이 있다). 운영에서 다시 확인해야 한다.
