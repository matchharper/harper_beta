# 회사 요청의 후속 연락 일정

문서 기준: 2026-10-15. 운영 DB migration과 과거 완료 이력 10건 이관은 적용했다. beta·Worker 코드 배포는 아직 실행하지 않았으므로 회사 LLM의 새 관리 도구와 새 일정 소비 경로가 운영에서 활성화됐다는 뜻은 아니다.

## 동작

일반 내부 포지션 추천의 기존 후속 연락은 유지한다. 회사의 Intro 요청, 인터뷰 일정 요청, 질문·자료 요청은 최초 동작 때 개별 후속 일정을 저장한다. 정보 전달만 하는 연락에는 기본 후속 일정을 만들지 않는다.

| 원본 요청 | 회사가 별도 날짜를 정하지 않은 기본 일정 |
| --- | --- |
| Intro 요청 | 최초 이메일 실제 발송 이후 3일, 9일, 18일 뒤 |
| 인터뷰 일정 요청 | 최초 이메일 실제 발송 이후 3일 뒤 1회 |
| 질문·자료 요청 | 최초 이메일 실제 발송 이후 3일 뒤 1회 |

최초 이메일 발송 전에는 날짜 대신 발송 후 간격을 저장한다. 이메일이 실제 발송되면 날짜를 확정한다. 회사가 직접 지정한 날짜는 고정 날짜로 저장하고 최초 발송 이후에도 덮어쓰지 않는다. 모든 후속 연락은 최초 이메일이 실제 전달된 다음에만 실행할 수 있다.

예정일은 후보자의 다음 3일 주기 검토부터 후속 연락을 고려할 수 있는 날짜다. 정확히 그 시각에 이메일이 나간다는 약속은 아니다. 기존 orchestration LLM이 다른 연락과 함께 검토하고 선택한다. 선택하지 않은 일정은 남겨 다음 검토에서 다시 고려한다. 같은 원본 요청에 여러 날짜가 이미 지났다면 LLM이 처리할 일정 ID를 선택한다.

## 회사 LLM의 조회·변경

별도 관리용 agent를 만들지 않고 기존 도구를 확장했다.

- `list_contacts(kind="followup")`: 회사·역할·후보자·상태·날짜로 예정 및 과거 후속 연락 조회. 기본 날짜 기준은 예정일이고 실제 발송일로도 검색할 수 있다.
- `read_contact`: 정확한 후속 연락 참조로 원본 요청 요약, 예정일, 다음 검토 시각, 수정 가능 여부, 채널별 실제 결과, 변경 이력 조회.
- `read_talent`: 해당 후보자의 남은 일정에 대한 짧은 인덱스 제공.
- `contact_talent`: 기존 연락 도구에 `add_followup`, `reschedule_followup`, `cancel_followup` 추가. 시간대를 포함한 특정 날짜로 추가·변경하고, 현재 참조와 revision으로 남은 일정 취소.

“이 후보자 팔로업은 언제야?”, “10월 23일에 다시 연락해 줘”, “남은 팔로업은 다 취소해 줘”를 같은 도구로 처리할 수 있다. 전체 취소는 조회한 남은 일정별로 실행하고 각각의 결과를 확인한다. 취소는 원본 Intro·인터뷰·질문 요청이나 이미 전달된 기록을 지우지 않는다. 전달이 시작된 연락은 변경을 막고, 실패한 발송의 남은 재시도는 취소할 수 있다. 실제 이메일 전달 영수증이 남은 건은 발송 전 취소로 취급하지 않는다.

Tool result에는 예약된 일정의 사실만 제공한다. Intro·인터뷰 요청 성공 후 반드시 예약 사실을 말하거나 특정 문장을 출력하도록 강제하지 않는다. 회사 LLM이 대화 맥락에 맞게 언급 여부와 설명을 선택한다.

## 저장·전달

`company_talent_followups`에는 사용자가 수정해야 하는 지속적인 사실인 원본 요청, 예정일, 상태, revision, 실제 전달 run 연결만 저장한다. 모델 판단이나 대화 계획을 저장하는 표가 아니다. 상태·원본 종류는 확장 가능한 text이며 enum, 값 목록 CHECK, 횟수·순서 제약은 두지 않았다. PK와 초기화·명령 재시도용 멱등 키 외에 예방적 schema 제약을 추가하지 않았다. 회사·팀 권한과 실제 전달 경계의 동시 수정 방지는 기존 executor와 RPC가 확인한다.

`talent_progress`에는 일정 설정·날짜 확정·변경·취소·실제 채팅 전달·이메일 발송·실패를 기록한다. 회사에는 해당 pair의 공유 가능한 사실을 제공하고, 후보자에게는 실제 전달 사실을 보여 준다. 회사 조회에서 여러 회사나 후보자의 비공개 커리어 내용이 섞일 수 있는 전체 후보자 이메일 본문·제목은 공개하지 않는다.

발송 직전 일정 ID·revision·원본 요청을 다시 확인한다. 구성 중 날짜 변경이나 취소가 발생하면 아직 전달하지 않은 메시지는 새 상태로 다시 구성한다. 실제 이메일 payload와 멱등 키는 고정하며, 발송 실패 재시도는 새 3일 주기 판단과 분리해 같은 run으로 수행한다. Provider 접수 ID를 먼저 저장하므로 이후 이력 쓰기가 실패해도 실제 발송을 다시 실행하지 않는다. 자동 네트워크 재시도는 최초 시도 이후 23시간 안으로 제한한다. 그 범위를 넘거나 영구 실패하면 실패 사실을 남기고 자동 재발송하지 않는다.

## 운영 전환

관련 migration: `20261014180746_company_talent_followup_schedules.sql`. 운영 Harper DB의 같은 버전·이름으로 적용 완료했다. 원본 조회를 실제 연락 Worker 계정으로 확인했으며, 새 테이블 제약은 PK와 멱등 키 UNIQUE뿐이다. 기존 미응답 질문·자료 요청 10건은 모두 실제 후속 이메일 발송이 확인되어 완료 상태로 이관했다. 새 발송은 없고, 이관 결과에 pending 일정은 없다.

1. Migration과 beta·Worker 코드를 함께 릴리스할 대상으로 준비한다. 새 코드의 schema 없는 환경에서는 기존 동작을 유지하고, 회사 조회에서 새 일정 데이터가 없다는 사실을 구분한다.
2. 명시적인 배포 승인 후 새 코드를 배포한다. 위 migration은 이미 적용됐으므로 다시 적용하지 않는다. Opportunity Worker는 기존 6개 인스턴스 순차 교체 절차를 따른다. 실행 중인 run을 실패로 만들지 않는다.
3. 모든 Worker가 새 코드로 전환된 뒤 `harper_worker/scripts/backfill_company_followups.py`로 이전 미응답 요청을 읽기 전용으로 미리 본다. `--source-kind`와 `--source-id`로 특정 요청만 지정할 수 있다.
4. 검토된 대상에 `--apply`를 사용한다. 이 도구는 메시지를 보내지 않는다. 기존 실제 이메일 발송을 지난 회차에 연결하고, 남은 Intro 간격은 마지막 실제 후속 발송 시점에서 보존한다. 초기화된 일정은 재설정하지 않는다.
5. 실행 중인 run이 있는 후보자, 최초 이메일 전달이 확인되지 않은 요청, 실제 이메일 영수증보다 발송 이력 수가 많은 애매한 요청은 건너뛴다. 이를 새 미발송으로 추정해 재발송하지 않는다.

Worker 전환 전에는 `--delivered-only`로 모든 기본 회차가 실제 발송된 요청만 미리 이관할 수 있다. 남은 발송이 있는 요청은 이 옵션으로 건너뛰고, Worker 전환 뒤에 일반 이관으로 처리한다.

검증은 격리된 DB의 초기화·날짜 확정·변경·취소·중복 명령·인터뷰 원본 취소·전달 직전 revision 확인, 운영 DB의 실제 원본·권한·회사 목록 조회 및 이관 결과, 변경한 Worker 경로의 짧은 테스트·구문 확인에 한정했다. 일반 추천의 공개 설정과 외부 추천 간격 제한이 기존 회사 후속 연락을 누락시키지 않도록 보완했다. 실제 운영 후보자 연락이나 유료 LLM 전수 평가는 실행하지 않았다.

운영 DB에서는 기존 유효한 원본 요청을 사용해 추가·동일 명령 재시도·날짜 변경·취소·원본 요청 보존을 하나의 트랜잭션에서 확인한 뒤 전부 rollback했다. 검증용 일정과 진행 이력은 남지 않았고, 운영의 pending 일정도 0건이다.
