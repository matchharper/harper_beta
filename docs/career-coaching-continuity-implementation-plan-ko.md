# Career 코칭과 연속 대화 구현 설계

문서 기준: 2026-09-21

상태: **구현 전 설계. 제품 코드·DB·배포 변경 없음.**

조사 기준: 로컬 작업 트리, HEAD `1d18a9512e0a1414cd484cb8fe94e1d723949606`. 관련 파일에 미커밋 변경이 있으므로 HEAD만으로 조사 당시 코드를 재현할 수 없고, 이 문서를 production 동작의 증거로 사용하지 않는다.
범위: 온보딩 이후 Career의 텍스트 코칭, 일반 대화와의 전환, 통화 연속성, 재방문, 요약·기억, UX, 검증·도입.

## 1. 결정: 전용 코칭 지침과 서버에 저장되는 대화 목적을 함께 도입한다

**코칭용 프롬프트 모듈은 필요하다. 별도 코칭 에이전트나 채팅방은 필요하지 않다.** 같은 Harper가 같은 대화와 도구를 사용하되, 사용자가 지금 함께 다루기로 한 목적에 맞춰 대화 지침을 교체한다.

전용 프롬프트가 이론적으로 유일한 해법은 아니다. 모든 지침을 하나의 프롬프트에 넣어도 모델은 코칭할 수 있다. 그러나 Harper는 이미 일반 추천 안내, 미응답 피드백, 온보딩 이후 제안, 통화 진행 등 서로 다른 의제를 주입하고 있다. 이 조건에서 코칭의 성공 기준을 명확히 만들고, 종료 후 원래 역할로 돌아가며, 품질을 독립적으로 검증하려면 **공통 지침과 목적별 지침의 모듈화**가 가장 적합하다.

이 설계에서 바꾸는 제품 단위는 기존의 고정된 “커리어 고민 이야기하기” starter다. 이를 **사용자의 명시적 코칭 요청 → 현재 맥락에 맞는 구체적인 대화 제안 → 같은 채팅에서 깊이 있는 대화 → 사용자가 이해할 수 있는 마무리 → 다음 방문에는 현재 요청에서 새로 시작**하는 경험으로 교체한다.

핵심 결정은 다음과 같다.

1. 코칭 카드 제안·생성은 사용자가 코칭 버튼을 누르거나 자연어로 코칭을 명시적으로 요청한 경우에만 허용한다. “이 공고 어때?” 같은 평가·추천·정보·일반 조언 요청은 제외한다. 대화가 길거나 고민을 포함한다는 이유로 코칭 요청을 추론하지 않는다.
2. 활성 코칭에서는 일반 추천·피드백 수집 의제를 빼고 코칭 지침을 넣는다. 신원, 말투, 사실성, 권한, 도구 실행 규칙은 공통으로 유지한다.
3. 원본 대화 LLM이 의미를 읽고 시작·보류·종료를 판단한다. 별도 intent classifier, 턴별 extractor, 키워드 분기는 추가하지 않는다.
4. 도구는 그 판단을 저장된 카드의 실제 상태 변경으로 실행한다. 대화 판단 과정이나 감정·단계·확신 점수를 저장하지 않는다.
5. 상태가 바뀌면 **같은 사용자 턴 안에서 다음 모델 호출부터** 프롬프트를 다시 조립한다.
6. 종료된 코칭은 사용자에 대한 이해에 남지만, 현재 진행할 의제로 남지 않는다. 장기 기억, 과거 대화 요약, 현재 활동 상태의 역할을 분리한다.
7. 일반 대화와 코칭 모두 기존 점진적 스트리밍을 유지한다. 도구 호출 가능성 때문에 응답 전체를 보류하거나 사전 판단용 모델 호출을 추가하지 않는다.

### 검토한 대안

| 대안 | 얻는 것 | Harper에서의 문제 | 결정 |
| --- | --- | --- | --- |
| 일반 프롬프트에 코칭 설명만 추가 | 구현량이 적음 | 추천 의제와 경쟁하고, 언제 효력을 끝낼지 불명확 | 채택하지 않음 |
| 코칭 프롬프트를 항상 전체 주입 | 모든 턴에서 능력 안내 | 끝난 고민을 계속 파고들거나 일반 요청에도 상담 질문을 붙이기 쉬움 | 채택하지 않음 |
| 별도 코칭 agent·채팅방·탭 | 분리하기 쉬움 | 관계·맥락·도구 권한이 갈라지고 이동 비용 발생 | 채택하지 않음 |
| 6턴 또는 시작 후 20분만 활성 | 만료 구현이 쉬움 | 짧은 대화가 오래 남고 긴 대화는 도중에 끊김 | 채택하지 않음 |
| 전용 지침 + 지속되는 목적 카드 + 원본 LLM의 전환 | 품질·연속성·종료 경계를 함께 제어 | 서버 상태와 실행 루프 수정 필요 | **채택** |

전용 지침을 분리한다는 것은 기존 프롬프트 전체를 복사한다는 뜻이 아니다. 코칭의 목적·대화 판단·마무리 원칙만 별도 모듈로 두고, 나머지는 하나의 공통 원본을 사용한다.

## 2. 참고 서비스에서 확인한 경험과 적용 범위

[Jack & Jill Inbox](https://app.jackandjill.ai/jack/dashboard/inbox)의 로그인된 브라우저 화면과 기존 대화를 읽기 전용으로 확인했다. 메시지를 보내거나 통화를 시작하지 않았다.

확인한 것은 개인 맥락을 반영한 제안, 목표와 진행 내용을 설명하는 통화 카드, 통화와 채팅의 선택, 기존 대화 옆에서 이어지는 탐색 경험이다. 별도 Coaching 메뉴에는 유형 선택과 사용자 정의 목표 입력도 있었다.

여기서 가져올 것은 탭 구성 자체보다 **“지금 무엇을 함께 다루면 도움이 되는지 이해하고, 그 대화가 준비되어 있다는 느낌”**이다. Harper에서는 동일한 대화 안의 구체적인 제안 카드로 구현한다. Jack & Jill의 내부 프롬프트, DB, 종료 판단 방식은 확인하지 않았으므로 추정해서 모방하지 않는다.

| C20 | 검증·도입·복구 가능성 | 일반 대화를 깨지 않고 충분히 확인한 경험만 제공 | frozen v2·단계별 구현·호환·feature flag, §18·19 | V20 | 충족 |

## 5. 제품 경험: 하나의 채팅 안에 목적이 보이는 대화

### 5.1 명시적 코칭 요청만 같은 실행 경로로 받는다

**자연어 진입.** 사용자가 코칭·상담을 받고 싶다는 의사를 명시한 경우에만 코칭 카드 도구를 사용할 수 있다. 목적까지 명확하면 바로 시작하고, 막연하게 코칭을 요청했다면 맥락을 활용해 방향부터 제안한다. 명확한 요청 뒤에 “코칭 모드로 전환해도 될까요?”라는 추가 동의 절차를 만들지 않는다. 코칭이라는 단어 자체의 유무가 아니라 발화 전체의 요청 의미를 원본 LLM이 판단한다.

**요청 이후의 방향 제안.** 개인 맥락은 사용자가 요청한 코칭의 주제를 고르는 데 사용한다. 저장한 역할·이전 고민·현재 상황만으로 Harper가 먼저 코칭 카드를 제안하지 않는다. 명시적 요청 뒤에 만드는 offered 카드는 제안 상태이며, 수락 전에는 본격적인 coaching prompt를 활성화하지 않는다. 무응답을 수락으로 간주하지 않는다.

**버튼만으로 진입.** 사용자가 composer의 코칭 진입 버튼만 누르면, 별도 입력 없이 Harper가 먼저 현재 맥락을 읽고 이야기할 방향을 제안한다. “어떤 주제로 코칭을 원하세요?”라는 빈 입력 폼이나 주제·채널 선택 화면을 먼저 내놓는 흐름을 기본값으로 삼지 않는다. 사용자에게 제목·설명·목표를 작성하게 할 필요가 없다.

기존의 일반 전화 버튼, 지원 준비·모의 인터뷰·internal 요청 진입은 각각의 목적을 유지한다. 코칭 진입과 기존 통화 진입이 이름만 다르고 동일하게 실행되는 상태를 없앤다.

| 사용자 입력/행동 | 코칭 카드 도구 | 처리 |
| --- | --- | --- |
| 코칭 버튼 클릭 | 허용 | 개인 맥락에서 방향을 먼저 제안 |
| “코칭 받고 싶어”, “커리어 상담을 해줘”처럼 명시적 요청 | 허용 | 목적이 없으면 제안, 명확하면 바로 시작 |
| 명시적으로 요청한 코칭의 제안에 답하거나 수정 | 요청 범위 안에서 허용 | 매 턴 코칭 의사를 재확인하지 않고 이어감 |
| “이 공고 어때?”, “나랑 맞을까?”, “두 회사 비교해 줘” | 호출하지 않음 | 기존 평가·비교·조회로 직접 응답 |
| “요즘 일이 재미없어”, “이직할지 고민이야”처럼 고민만 언급 | 호출하지 않음 | 일반 대화로 적절히 답하고, 코칭을 원하는 것으로 확대 해석하지 않음 |

이 표는 허용 범위를 설명하는 예시다. 문자열·키워드 목록으로 runtime 분기하지 않는다. 모호한 일반 질문에 코칭을 유도하는 확인 질문을 붙이지 않는다. 이미 사용자가 요청해 진행 중인 코칭에서 공고를 함께 검토하는 것은 가능하지만, 그 질문을 근거로 새 코칭 카드를 생성하지 않는다.

### 5.1.1 주제 없는 클릭에서 Harper가 대화를 이끄는 기본 흐름

1. 사용자가 코칭 버튼을 누른다. 기존 채팅에서 즉시 Harper 응답이 시작되며 사용자의 추가 입력을 기다리는 폼을 띄우지 않는다.
2. 원본 대화 LLM이 최근 대화, 현재 Brief와 관련 Memory, 최근 저장·검토한 역할의 짧은 index, 현재/과거 활동 상태를 읽는다. 구체적인 근거가 부족하면 기존 일반 read tool로 해당 기록을 확인한다.
3. 지금 함께 다룰 만한 방향과 왜 그 방향이 유용한지 먼저 제안한다. 대개 가장 유용한 한 방향을 우선하며, 서로 다른 방향이 실제로 가능하면 선택지를 제시할 수 있다. 제안 개수나 주제 종류를 고정 분기로 만들지 않는다.
4. 목적을 제안할 만큼 맥락이 있으면 Harper가 제목·목적·함께 다룰 내용을 작성한 offered 카드를 만든다. 아직 목적을 좁히기 어렵다면 짧은 맥락 기반 질문으로 함께 정한 뒤 카드를 만든다. 목적을 사용자가 먼저 완성해야 한다는 요구는 없다.
5. 사용자는 카드에서 채팅·통화를 선택하거나 “좋아, 그 얘기 해보자”처럼 자연스럽게 답할 수 있다. 자연어 수락이면 현재 채팅에서 곧바로 시작하며 버튼 클릭을 다시 요구하지 않는다. “그것보다 다른 얘기”라는 수정도 같은 대화에서 반영한다.
6. 목적 수락 후 active로 전환하고 전용 coaching module로 이어간다. 별도 Coaching 화면이나 새 채팅방으로 이동하지 않는다.

합성 예시: 최근 저장한 역할 두 개와 이전 대화에서 확인한 성장 고민이 있다면 “최근 저장한 두 역할은 맡게 될 범위가 꽤 달라요. 전에 이야기한 성장 고민과 연결해서, 다음 역할에서 어떤 책임을 맡고 싶은지 같이 정리해 볼까요?”처럼 제안할 수 있다. 실제로 조회하지 않은 역할이나 과거 발언을 예시처럼 만들어내면 실패다. 저장 행동만으로 이직 의사·선호를 확정하거나 Memory에 쓰지 않는다.

참고할 맥락이 거의 없으면 그 한계를 자연스럽게 드러내고 시작하기 쉬운 질문을 한다. 맥락이 있는데도 일반적인 주제 목록만 보여주는 것과, 맥락이 없는데 개인화한 척하는 것을 모두 피한다. 끝난 코칭의 존재만으로 그 주제를 다시 제안하지 않으며, 사용자의 이번 코칭 클릭은 대화 방향을 제안해 달라는 의사로만 해석한다.

제안에 대한 반응은 별도의 승인 양식이 아니다. 사용자가 제안한 주제에 답하거나 자신의 고민을 이어 설명하면 원본 LLM이 그 의미에서 진행 의사를 이해한다. “네”라는 특정 표현이나 start 버튼을 기다리며 같은 제안을 반복하지 않는다. 반대로 사용자가 제안을 거절·교정하면 그 설명을 사용해 방향을 바꾸고, 저장한 역할을 근거로 원래 제안을 설득하지 않는다.

같은 목적을 다듬을 때는 기존 offered 카드를 수정하고, 다른 목적이면 이전 제안을 닫은 뒤 새 제안을 만든다. 매 응답마다 카드를 추가하지 않는다. 응답 생성 중 중복 클릭은 같은 요청에 연결하고, 이미 열린 제안이 있는 상태에서 다시 코칭 버튼을 누르면 그 제안과 최신 대화를 확인한 뒤 이어간다. 별도 질문 없이 무조건 새 활동을 만드는 동작을 기본값으로 삼지 않는다.

### 5.2 카드와 composer

카드에는 제목, 함께 다룰 목적 한두 문장, 현재 상태, 가능한 행동만 표시한다. 정해진 질문 목록·심리 점수·단계 진행률은 없다. 예를 들어 제목은 “다음 역할에서 더 중요하게 볼 것”이고 목적은 “현재 역할에서 아쉬운 점을 바탕으로 다음 선택의 기준을 정리한다”일 수 있다. 문구는 사용자의 맥락에서 생성하며 예시를 템플릿으로 고정하지 않는다.

| 상태 | 카드에서 보이는 것 | 가능한 행동 |
| --- | --- | --- |
| offered | 제안의 목적 | 채팅으로 시작 / 통화로 시작 / 제안 닫기 |
| active | 지금 함께 다루는 목적 | 통화 또는 채팅으로 전환 / 잠시 멈추기 / 여기서 마치기 |
| paused | 중단한 목적, 있으면 짧은 이어받기 메모 | 채팅으로 이어가기 / 통화로 이어가기 / 여기서 마치기 |
| closed | 다룬 목적과 실제로 남은 결과 | 내용 보기 / 이 이야기 다시 꺼내기 |

활성 중에는 composer 위에 작은 목적 표시를 둔다. 화면 대부분을 점유하는 대시보드나 별도 탭은 만들지 않는다. 목적 수정은 그 표시에서 접근할 수 있지만 일반적인 변경은 대화로 처리한다. 완료 카드는 접어 두며 새로 방문할 때 상단으로 자동 승격하지 않는다.

offered 카드는 수락 전까지 프롬프트를 활성화하지 않으며, 방문할 때마다 다시 띄우지 않는다. 원본 LLM에는 현재 보이는 미수락 제안의 짧은 index도 제공하여 같은 제안을 계속 만들지 않게 한다. 의미상 중복 여부를 제목 문자열 유사도로 판정하지 않는다. 오래된 제안을 사용자가 선택하면 당시 근거가 지금도 유효한지 최신 context에서 확인한다.

closed의 “다시 꺼내기” 버튼은 이전 결과를 참고하는 **새 활동**을 만든다. 과거 완료 기록을 active로 되돌리지 않는다. paused는 기존 활동을 재개한다. 종료 직후 사용자가 설명 하나를 더 물어보는 것은 다르다. 과거 맥락으로 바로 답할 수 있는 짧은 후속 질문에는 새 카드나 시작 승인을 요구하지 않는다.

### 5.3 사용자가 판단할 수 있는 마무리

마무리는 고정 양식이 아니라 대화 길이에 비례한 설명이다. 사용자가 무엇을 더 분명히 알게 되었는지, 결정하지 않은 것은 무엇인지, Harper가 실제로 변경한 것은 무엇인지 구분한다. 검색 조건 변경이나 과제를 결과로 강요하지 않는다.

사용자가 더 할 말이 있으면 같은 채팅에서 바로 말할 수 있다. “상담 종료” 화면이나 채팅 입력 차단은 없다. 종료 버튼은 자연어 종료 판단이 실패할 때의 유일한 수단이 아니라, 사용자에게 항상 제공하는 직접 제어 수단이다.

## 6. 최소 lifecycle: 대화의 생각 과정이 아니라 사용자 활동의 상태

저장하는 것은 `offered → active → paused/closed`라는 **실제 카드와 실행 범위**다. 탐색·공감·도전·계획·결론 같은 모델의 사고 단계를 enum이나 state machine으로 만들지 않는다.

| 현재 상태 | 전환 근거 | 결과 | 누가 의미를 판단하는가 |
| --- | --- | --- | --- |
| 없음 | 명시적 코칭 요청에 응답해 원본 LLM이 구체적인 목적 제안 | offered | 원본 LLM |
| 없음/offered | 명시적 코칭 요청의 목적이 명확하거나 요청한 제안을 수락/시작 버튼 클릭 | active | 자연어는 원본 LLM, 클릭은 명시적 UI command |
| active | 같은 목적의 질문·원문 조회·관련 사례 검토 | 유지 | 원본 LLM, 별도 상태 write 불필요 |
| active | 같은 목적이 구체화됨 | goal 수정, revision 증가 | 원본 LLM 또는 사용자 편집 |
| active | 지금은 다른 일을 하자거나 나중에 이어가자고 함 | paused | 원본 LLM 또는 사용자 버튼 |
| active/paused | 지금 다루기로 한 범위가 끝났거나 사용자가 그만하자고 함 | closed | 원본 LLM 또는 사용자 버튼 |
| offered | 사용자가 제안을 닫음 | closed | 사용자 버튼 또는 원본 LLM |
| paused | 같은 목적을 이어가겠다는 새 요청 | active | 원본 LLM 또는 사용자 버튼 |
| closed | 본격적으로 다시 다루겠다는 요청 | 새 활동 생성. 짧은 설명 보충은 일반 대화로 답함 | 원본 LLM 또는 사용자 버튼 |
| active | 연결된 통화가 끊겼고 명시적 채널 handoff가 없음 | paused | transport 사실에 대한 서버 처리 |
| active | 사용자 비활동 경계를 넘김 | paused | 아래의 수명 정책; 해결 여부는 판단하지 않음 |

### 6.1 텍스트에서 언제 끝내는가

원본 LLM은 현재 합의한 목적과 사용자의 마지막 말에서 종료를 판단한다. 사용자가 명시적으로 그만하겠다고 하면 도구로 바로 닫는다. 충분히 정리되었다고 사용자가 받아들이거나 다음 행동으로 넘어가면 닫을 수 있다. Harper가 혼자 요약문을 썼다는 사실은 종료 근거가 아니다.

사용자가 이해했는지 모호하면 결과를 짧게 정리하고 반응을 받는다. 매번 “끝내도 되나요?”를 묻지 않으며, 단순한 감사나 짧은 답을 키워드로 분류하지 않는다. 본래 문제가 완전히 해결되지 않아도 이번 대화 범위는 끝날 수 있다.

`closed`는 “사용자의 삶의 문제가 해결됨”을 뜻하지 않는다. 이 시간에 함께 다루기로 한 범위가 끝났다는 뜻이다. 그 차이를 `note`의 자연어와 실제 대화에 남긴다.

### 6.2 침묵과 시간의 역할

6턴 제한과 시작 후 20분 같은 총 길이 제한을 제거한다. 진행 중인 대화는 오래 걸려도 유지한다.

초기 제품 정책은 **마지막 사용자 상호작용 후 12시간 동안 입력·통화 활동이 없으면 실행 범위를 보류**하는 것이다. 기존 재방문 경로의 12시간 기준과 맞추되, 의미상 종료와 엄격히 구분한다. assistant의 인사·요약·카드 갱신은 시간을 연장하지 않는다. 새 메시지가 들어오면 먼저 이전 마지막 사용자 시각으로 만료를 검사한 뒤 이번 입력을 반영한다.

이 시간은 사용자 의도·만족도·해결 여부를 추정하는 점수가 아니다. 오래 방치된 실행 범위가 새 방문의 발화를 지배하지 못하게 하는 제품 수명 계약이다. 상태 변경 사유에는 `inactivity`를 서버가 기록하고, 해결되었다는 문구를 생성하지 않는다.

브라우저 reload, 짧은 탭 전환, 모바일 background 자체로는 상태를 바꾸지 않는다. 타이머 작업을 새로 만들지 않고 세션 조회·새 턴·통화 시작 시 동일한 resolver가 transaction 안에서 lazy expiry를 적용한다. 사용자 입력이 없는 화면은 다음 갱신 때 반영된다. 12시간을 넘겼어도 사용자가 “아까 얘기 이어서”라고 하면 같은 턴에 재개할 수 있다.

### 6.3 샛길과 새 목적

같은 고민을 판단하려고 채용 공고를 읽는 것은 코칭의 일부일 수 있다. 그 경우 기존 read tool을 사용하며 active를 유지한다. 사용자가 별도 업무로 초점을 옮겼다면 보류하거나 종료한 뒤 그 요청을 수행한다.

새로운 고민으로 바뀌었어도 본래 목적의 구체화라면 goal만 수정한다. 사용자와 합의한 범위가 달라졌다면 기존 활동을 보류/종료하고 새로 만든다. 무엇이 같은 목적이고 다른 목적인지는 원본 LLM이 판단한다. 주제 이름·회사명 변경으로 자동 분기하지 않는다.

한 conversation에 active는 최대 하나다. 새로운 active를 만들기 전에 기존 active를 명시적으로 보류하거나 닫아야 한다. 서버는 이를 자동으로 “해결” 처리하지 않는다.

사용자가 다른 목적의 카드에서 시작/이어가기를 직접 선택하면 그 선택 자체가 초점 전환의 명시적 요청이다. 표시된 기존 active와 대상 카드의 revision을 함께 검증하여 **기존 활동 pause + 선택한 활동 활성화**를 한 transaction으로 처리한다. 다시 전환 동의를 묻지 않는다. UI가 알고 있던 기존 active와 서버의 값이 다르면 최신 내용을 먼저 보여주고 stale 요청으로 임의 전환하지 않는다. 자연어 전환에서는 원본 LLM이 기존 pause/close와 create/start 도구로 같은 판단을 수행한다.

## 7. 프롬프트 계약과 실제 조립 방식

### 7.1 블록을 책임별로 재구성한다

`rawPrompts.ts`의 기존 core에도 일반 대화 의제가 섞여 있으므로 이름만 믿고 전부 공통으로 유지하지 않는다. 내용을 읽어 다음 책임으로 나눈다.

| 블록 | 일반 사용자 턴 | 활성 코칭 턴 | 재방문 인사 | 통화 마무리 |
| --- | --- | --- | --- | --- |
| Harper 정체성·언어·사실성 | 포함 | 포함 | 포함 | 포함 |
| 권한·공유·도구 결과 진실성 | 포함 | 포함 | 포함, write 차단 | 포함, 실제 allowlist |
| 현재 Profile·전체 Brief·관련 Memory | 포함 | 포함 | 필요한 최소 사실 | 통화 관련 사실 |
| 현재 활동 snapshot | 짧게 | 목적·상태·이어받기 메모 | 종료/보류 경계만 | 해당 call이 시작한 활동·revision |
| 일반 대화·추천 제안 가이드 | 포함 | 제외 | 전용 인사 지침 사용 | 제외 |
| post-onboarding 의제·mock interview offer | 조건부 | 제외 | 무차별 제안 제외 | 제외 |
| 코칭 목표·진행·마무리 지침 | 없음 | 포함 | 없음 | 없음 |
| 최근 대화·역사적 요약 | 포함 | 포함 | 필요 범위만 | 해당 transcript와 이후 변경 여부 |
| 채널 전달 지침 | 텍스트 | 텍스트/음성 | 짧은 텍스트 | 텍스트 산출물 |
| 전환 결과에 대한 이번 응답 지침 | 필요 시 | 필요 시 | 없음 | 필요 시 |

기회 상태나 도구 제한은 사실 정보로 계속 접근할 수 있다. 다만 “지금 이 피드백을 물어라” 같은 의제를 active 코칭 prompt에 기본 주입하지 않는다. pending feedback, followup opportunities, recent activities, internal hold question도 같은 관점에서 사실과 의제 부분을 분리한다. 진행 중인 실질적 승인·권한 제약을 숨겨서는 안 된다.

온보딩, 모의 인터뷰, internal 요청용 통화는 기존의 별도 목적 계약을 유지한다. 특히 mock interview의 context 격리를 이 변경 때문에 해제하지 않는다.

### 7.2 코칭 모듈에 넣을 내용

아래는 구현할 지침의 의미 계약이다. 정해진 순서나 고정 질문 문구로 변환하지 않는다.

> 사용자가 지금 함께 다루기로 한 목적을 진전시킨다. 이미 알려진 배경을 활용하고, 이해가 불완전한 지점을 드러낸다. 사용자의 말과 Harper의 해석을 구분하며, 중요한 해석은 반증·교정 가능한 가설로 다룬다. 질문뿐 아니라 비교, 관점, 구체적 피드백을 제공한다. 다음 질문은 앞선 답을 사용하며, 필요한 만큼만 묻는다. 사용자의 자율성을 존중하고 결정을 대신 확정하지 않는다. 충분히 정리되면 결과를 알아볼 수 있게 마무리한다. 별도 실행이 필요하면 실제 도구의 권한과 결과에 따라 수행한다. 지금의 목적을 더 이상 계속하지 않을 때는 활동 상태를 갱신한다.

추가 성공 기준:

- 질문을 계속 받는 경험보다 자신의 상황이 더 명확해지는 경험이어야 한다.
- 사용자가 해석을 부정하면 이전 가설을 고집하거나 Memory 사실로 저장하지 않는다.
- 구체적 조언이 가능한 순간에는 조언한다. 코칭이라는 이유로 모든 요청을 질문으로 되돌리지 않는다.
- 목표가 막연한 시작에서는 “지금 어떤 것을 정리하면 도움이 될지 알아본다”는 임시 목적도 허용한다.
- 후속 실행 없이도 선택의 기준이나 모르는 점이 분명해졌다면 유효한 결과다.
- 일정·연락·후속 알림은 실제 실행 능력과 승인 없이는 약속하지 않는다.
- 종료·보류 후 unrelated 요청에는 그 요청에 답한다. 과거 코칭에 대한 후속 질문을 관성적으로 붙이지 않는다.
- active는 목적을 이어갈 수 있다는 사실이며 매 응답을 상담 질문으로 끝내라는 지시가 아니다. 현재 발화가 인사·단발 확인·다른 요청이면 그 의미에 맞게 답하고, 필요한 목적 전환만 수행한다.

### 7.3 일반 지침에도 최소 능력 안내가 필요하다

일반 prompt에는 “코칭 카드의 제안·생성은 사용자의 명시적 코칭 요청에 응답할 때만 한다”, “공고 평가·비교·정보·일반 조언과 고민 언급은 일반 대화로 처리한다”, “현재 요청과 무관한 끝난 활동은 자동 재개하지 않는다”는 짧은 경계와 활동 도구 계약을 둔다. 일반 대화를 코칭으로 유도하는 지침이나 전체 코칭 지침은 넣지 않는다.

원본 대화 LLM은 명시적 코칭 요청에 응답할 때만 코칭 카드 생성 도구를 사용하고, 실제 시작 후에는 coaching module로 답한다. 기존 조회·추천·저장 도구의 일반 사용 조건은 그대로 유지한다. 자연어 코칭 요청을 받을 수 있게 tool schema가 제공된 것과 tool을 호출해도 되는 조건은 다르다. schema의 존재 자체를 코칭 제안·추가 질문의 근거로 삼지 않는다. 별도 탐지 LLM이나 키워드 classifier는 추가하지 않는다.

주제 없는 코칭 버튼 클릭에는 서버가 검증한 entry action을 바탕으로 이번 턴의 짧은 지침을 추가한다. 내용은 “사용자가 대화 방향을 함께 찾고 싶어 한다. 알려진 맥락을 활용하고 필요한 원문을 조회해서 유용한 방향을 먼저 제안하라. 사용자에게 주제를 먼저 작성하도록 떠넘기지 말라”다. 이 응답에서는 추천 피드백 수집 등 무관한 일반 의제를 제외한다.

entry 지침은 아직 특정 목적에 합의했다는 뜻이 아니므로 active 활동을 자동 생성하지 않는다. 제안과 사용자의 응답은 기존 대화·offered 카드에 남고, 이후 원본 LLM이 수정·수락을 이해한다. 별도 “주제 탐색 중” 상태, classifier, 세션 타이머를 추가하지 않는다.

**첫 클릭 다음 턴에도 아직 끝나지 않은 사용자 요청을 이어간다.** 예를 들어 맥락이 없어 Harper가 한 질문에 사용자가 “일이 재미없어졌어요”라고 답했다면, 일반 추천 안내로 돌아가지 않고 그 답으로 대화 방향을 좁힌다. 공통 대화 지침에 “직전 질문·미해결 사용자 요청을 우선하고, 새로운 의제를 덧붙이지 않는다”는 책임을 둔다. 클릭 사실과 이어진 발화는 recent history/summary에 보존한다. 서버가 매 턴 별도 모델로 ‘탐색 단계’를 판정하거나 mode를 저장하지 않는다.

### 7.4 서버 입력 타입

제안하는 내부 타입은 아래와 같다. LLM이 이 객체 전체를 출력하지 않는다.

~~~ts
type CareerExecutionContext = {
  origin: "user_turn" | "reengagement" | "call_wrapup" | "event_reply" | "onboarding_artifact";
  channel: "chat" | "voice";
  entryAction?: "coaching"; // 서버가 검증한 명시적 버튼 클릭, 추론한 intent가 아님
  activity: ConversationActivitySnapshot | null;
  transition: VerifiedActivityTransition | null; // 이번 실행의 실제 도구 결과
  anchorMessageId: number | null;
};
~~~

`origin`은 호출 경로에서 정하는 사실이다. `activity`는 DB에서 읽고, `transition`은 검증된 mutation 결과다. 클라이언트가 coaching prompt 본문이나 강제 mode를 넘겨 정할 수 없다.

`runCareerChatTurn`은 재접속·call-wrapup 외에도 추천 피드백, 회사 팔로우, Gmail 처리 후 안내에 사용된다. 이들은 `event_reply`로 기존 source instruction과 allowlist를 유지한다. 온보딩 완료 산출물처럼 같은 prompt builder를 직접 사용하는 경로는 `onboarding_artifact`다. 이 구분은 기존 호출 출처이며 LLM의 의미 분류가 아니다. 두 origin에는 코칭 진행 지침과 활동 변경 도구를 자동 상속하지 않는다. 명시적 사용자 코칭 요청이 없는 background 호출의 origin을 user_turn으로 기본 처리하지 않는다.

종료 도구 직후에는 coaching module을 제거하고, 이번 응답에 한해서만 “지금 닫은 대화를 비례해서 마무리하고 마지막 사용자 요청에 답한다”는 transition context를 넣는다. 이 턴에는 일반적인 추천·피드백 제안을 붙이지 않는다. 다음 사용자 턴부터는 평상시 일반 지침을 사용한다.

## 8. 저장과 도구: 새로운 기억 테이블 없이 목적 카드를 확정 사실로 남긴다

### 8.1 왜 저장이 필요한가

없으면 복원할 수 없는 사실은 **“사용자가 어떤 목적의 대화를 시작/보류/종료했고, 어느 변경까지 확정되었는가”**다. 이를 읽는 구체적인 소비자는 프롬프트 builder, 카드 UI, 다른 기기, 통화 시작·wrapup, 재접속 인사다. 모델이 과거 산문을 매번 재해석해서 이 사실을 결정하면 기기와 호출마다 달라진다.

별도 `coaching_sessions`나 추론 기록 테이블을 만들지 않는다. 기존 `talent_messages`에 nullable `payload jsonb`를 추가해 **사용자에게 보이는 활동 카드**를 저장한다. 기존 행은 null로 읽힌다. `thinking_logs`나 content의 접두사를 기계 상태 저장소로 사용하지 않는다.

### 8.2 카드 원본

~~~ts
type ConversationActivityPayload = {
  version: 1;
  kind: "coaching";              // 실제 지원 능력. 주제 분류 enum이 아님
  title: string;
  goal: string;
  status: "offered" | "active" | "paused" | "closed";
  revision: number;
  note?: string;                 // 사용자에게도 보여줄 결과 또는 이어받기 메모
  relatedActivityMessageId?: number; // 종료한 이전 대화를 다시 다룰 때
  startedAt?: string;
  updatedAt: string;
  lastUserInteractionAt?: string;
};
~~~

카드의 message ID를 활동 ID로 쓴다. `message_type = conversation_activity`이며 기존 `conversation_id`, `user_id`, `created_at`을 재사용한다. 별도 session UUID·현재 목적 pointer 테이블을 추가하지 않는다. `note`에는 숨은 추론·성격 판정·확신 점수가 들어가지 않는다.

title은 최대 160자, goal은 1,200자, note는 2,400자로 저장 상한을 둔다. 이는 UI·저장 계약이며 모델 답변의 문체나 적절성을 판정하는 규칙이 아니다. 긴 사용자 입력은 원문 메시지에 보존하고, 카드의 목적은 원본 LLM이 짧게 작성한다. 서버가 임의로 본문을 잘라 의미를 바꾸지 않는다.

`revision`은 goal/title/note/status가 바뀔 때 증가한다. `lastUserInteractionAt`의 기술적 갱신은 단조 증가로 처리하되 의미 revision을 올리지 않는다. 통화 중에는 실제 사용자 음성/확정 transcript 이벤트가 활동 시각을 갱신하며 단순 연결 heartbeat는 사용자 발화로 보지 않는다. 클라이언트 시각 대신 서버 수신 시각을 사용한다.

일반 메시지의 payload에는 필요한 경우 `activityMessageId`, 통화에는 `callId`, 재전송 제어에는 `clientRequestId`만 추가한다. 메시지가 특정 활동 중 발생했다는 연결은 의미적 분류가 아니다. 샛길 발화까지 Memory 사실이나 목표의 일부로 자동 해석하지 않는다.

### 8.3 변경 영수증과 transaction

카드의 최신 payload가 **현재 상태의 유일한 원본**이다. 기존 messages에 숨김 `conversation_activity_event` 행을 함께 써서 operation ID, 대상 카드, 이전/새 revision, 실제 command, 서버 시각, 근거 메시지/call ID를 남긴다. 이는 재시도 중복 방지와 과거 요약 경계를 위한 변경 영수증이다. 또 다른 editable 상태 원본이나 대화 계획 저장소가 아니다.

카드 갱신과 영수증 insert는 한 DB transaction/RPC로 처리한다.

1. 인증된 사용자와 conversation 소유권 확인.
2. conversation 행 잠금으로 active 생성/전환을 직렬화.
3. 동일 operation ID 영수증이 있으면 기존 성공 결과 반환.
4. 대상 카드 종류·소유권·expectedRevision·허용된 lifecycle transition 검증.
5. active는 한 conversation에 최대 하나인지 확인.
6. 카드와 영수증을 함께 commit. commit 이후에만 UI·모델에 성공 전달.

구조적 제약은 카드 행에만 적용한 active partial unique index, 영수증의 conversation+operation ID unique index로 보강한다. JSON 타입·필수 필드·revision의 정수 범위는 validation과 DB check로 검증한다. 자유 형식 title·goal·note는 문체·주제 기준으로 검열하지 않고 저장 크기만 제한한다.

영수증은 성공 시 결과를 재구성할 최소 snapshot을 포함한다. 같은 operation ID를 다른 입력으로 재사용하면 conflict다. 기존 active가 있으면 명시적 전환 없이 들어온 생성 요청으로 덮어쓰지 않고 현재 카드를 돌려준다. 자연어 요청은 원본 LLM이 보류/종료를 판단하며, 사용자가 다른 카드를 직접 선택한 UI command만 §8.5의 원자적 전환 계약을 사용한다.

### 8.4 도구 계약

활동 카드는 기존 도구에 없던 사용자 가시 산출물이며, 기기·채널을 넘어 지속되는 실행 범위를 만드는 외부 효과가 있다. 이 때문에 아래 두 도구를 추가한다. 단순히 “상담인지 판단하는” 도구를 추가하는 것이 아니다.

`create_conversation_activity`의 필수 호출 전제는 **현재 대화에서 사용자가 명시적으로 요청한 코칭을 제공하는 것**이다. prompt와 tool description에 동일하게 명시한다. 단순 공고 평가·추천·정보 질문, 고민 언급, 최근 저장 행동, 과거 코칭 기록만으로 offered/active를 생성할 수 없다. 서버 executor는 요청 사용자/원본 메시지·클릭의 출처를 연결하고 origin·권한·식별자를 검증한다. 자연어가 명시적인 코칭 요청인지에 대한 의미 판단은 원본 LLM이 담당하며 숨은 승인 분류기를 추가하지 않는다.

~~~ts
create_conversation_activity({
  title: string,
  goal: string,
  status: "offered" | "active",
  related_activity_ref?: number
})

update_conversation_activity({
  ref: number,
  action: "start" | "pause" | "close" | "revise",
  title?: string,
  goal?: string,
  note?: string
})
~~~

LLM에 전달하는 것은 짧은 ref다. 실제 message ID 매핑, expectedRevision, operation ID, 사용자/호출 채널, 근거 메시지는 executor가 현재 실행 context에서 붙인다. 도구 인자로 숨은 reasoning 객체를 요구하지 않는다.

- create active: 사용자가 명시적으로 요청한 코칭의 목적이 이미 명확할 때. 목적 확인을 새로 요구하지 않는다.
- create offered: 명시적 코칭 요청에 응답해 아직 합의하지 않은 대화 방향을 제안할 때. unsolicited 코칭 제안에는 사용하지 않는다.
- start: offered/paused를 활성화. closed는 start 불가.
- pause: 결론을 내지 않고 현재 실행을 멈춤.
- close: 이번 대화 범위를 닫음. 결과를 꾸며서 요구하지 않음.
- revise: 같은 목적을 구체화. active 수나 권한은 변경하지 않음.

처음의 명시적 요청은 그 코칭의 방향 선택·수정·진행 범위 안에서 이어진다. 종료 후 일반 질문까지 신규 코칭 제안의 상시 허가로 남기지 않는다. `update`도 요청한 기존 활동의 관리에만 사용하며, 일반 질문을 새 코칭으로 바꾸는 우회 경로가 아니다.

UI 버튼도 같은 mutation service를 사용한다. 제안 닫기는 offered→closed다. 카드 클릭으로 이미 start가 성공했다면 모델은 다시 start 도구를 호출할 필요가 없다.

### 8.5 UI command와 첫 응답의 API 연결

새 채팅 실행 endpoint를 만들지 않고 기존 `POST /api/talent/chat`에 `entryAction`과 `activityCommand` 입력을 추가한다. 일반 message, entry action, 기존 카드 command의 세 입력은 서로 배타적이다.

주제 없는 코칭 버튼은 `{ entryAction: "coaching", clientRequestId }`만 보낸다. goal·activity ref·채널 선택은 필요하지 않다. 서버는 인증·중복 요청 확인 후 클릭 사실을 기존 메시지 payload의 UI action으로 남기고, §5.1.1의 context와 §7.3의 entry 지침을 붙여 **같은 원본 LLM**을 실행한다. 클릭 기록을 사용자가 실제로 타이핑한 문장으로 위조하지 않는다. entry action은 새 활동 도구나 장기 상태가 아니다.

~~~ts
type ActivityCommand = {
  operationId: string;  // UI가 요청 재시도 때 유지하는 UUID
  ref: number;
  expectedRevision: number;
  replaceActive?: { ref: number; expectedRevision: number };
} & (
  | { action: "start" | "continue" | "revisit"; channel: "chat" | "voice" }
  | { action: "pause" | "close" }
  | { action: "revise"; title?: string; goal?: string }
);
~~~

처리 순서는 인증 → 소유권/command 검증 → 동일 mutation service commit → 최신 snapshot으로 context 구성 → 필요한 assistant 응답이다. chat start는 이 요청에서 바로 첫 질문을 생성한다. voice start는 검증된 목적과 call-start 결과를 반환하고 음성 연결 후 opening을 생성한다. 두 채널이 각각 첫 인사를 생성하지 않게 한다. 단순 목적 편집이나 offered 제안 닫기에는 확인 채팅을 강제로 생성하지 않는다.

| 사용자 행동 | command와 허용 상태 | 실제 효과 |
| --- | --- | --- |
| 제안 수락/보류한 이야기 재개 | start, offered/paused | 동일 활동 활성화 후 선택한 채널에서 진행 |
| 지금 이야기를 통화/채팅으로 이어가기 | continue, active | 목적 lifecycle 유지, transport만 인계. start를 다시 호출하지 않음 |
| 마친 이야기를 새로 다루기 | revisit, closed | 이전 결과를 참고하는 새 활동 생성, 원래 closed 보존 |
| 다른 카드 선택 | start/revisit + replaceActive | 사용자에게 보였던 active를 pause하고 대상을 활성화하는 원자적 전환 |

continue는 이미 요청한 채널이 연결되어 있으면 현재 연결을 반환하며 새 opening을 중복 생성하지 않는다. revisit는 이전 활동의 title/goal과 관련 ref를 바탕으로 새 카드를 만들되, 최신 context와 과거 note를 읽어 다음 대화를 시작한다. 오래된 결정이 지금도 유효하다고 자동 확정하지 않는다. 이것들은 실제 UI 동작을 실행하는 command이며 의미 판단 도구나 새 lifecycle 상태가 아니다.

`replaceActive`는 다른 active가 있을 때의 start/revisit에만 허용한다. UI는 실제 보여준 active ref/revision을 보내고 서버는 현재 값과 일치하는지 검사한다. 하나라도 달라졌다면 어느 카드도 변경하지 않는다. 같은 카드에 대한 중복 시작/전환은 해당 operation 결과 또는 최신 동일 활동을 반환하며 새 활동을 만들지 않는다.

UI의 start는 사용자가 누른 명시적 의사이므로 별도 시작 승인 질문을 만들지 않는다. 버튼 동작을 사용자가 실제로 타이핑한 문장인 것처럼 위조하여 저장하지도 않는다. command 영수증에 actor/source를 남기고, 모델에는 “사용자가 이 활동의 채팅 시작을 선택했다”는 검증된 실행 사실로 제공한다. 자연어 진입은 기존 user message와 LLM 도구 경로를 그대로 따른다.

목적이 없는 composer에서 사용자가 먼저 입력한 내용은 일반 사용자 메시지로 보내고, 선택한 채널은 별도 UI 의사로 함께 전달한다. 모델이 목적을 만들면 그 확정 카드로 채널 전환을 수행한다. 채널 선택을 다른 도구 실행이나 회사 공유에 대한 동의로 확대하지 않는다.

통화에 보충 텍스트를 보내는 입력은 일반 message에 `delivery: { channel: "voice", callId }`를 붙인다. 서버는 활성 call 소유권·binding을 검증하고 메시지 저장/전달 결과만 반환하며 이 경로에서 별도 chat 응답을 생성하지 않는다. 텍스트 입력이라는 사실로 lifecycle이나 transport를 전환하지 않는다. 오래된 client가 현재 call 상태를 모른 채 충돌하는 요청을 보내면 입력을 보존한 상태로 최신 연결 정보를 반환하고, 어느 한쪽을 몰래 종료하지 않는다.

tool result의 모델용 본문에는 사용자에게 설명할 수 있는 성공/실패 사실과 현재 목적을 제공한다. 내부 result envelope의 `contextChanged`, revision 등은 runner가 소비한다. 모델이 이를 사용자에게 낭독하도록 프롬프트에 그대로 쏟아 넣지 않는다.

### 8.6 기존 message reader에 미치는 영향

payload 추가 migration만으로 끝내지 않는다.

- select·row type·API DTO·client cache에 payload를 연결한다.
- 카드는 UI에서 렌더하지만 영수증은 일반 말풍선·알림·미읽음 수에서 제외한다.
- card update가 발생해도 다른 기기가 갱신되어야 한다. 현재 live sync는 assistant message insert 중심이므로 영수증 insert 후 invalidation을 일관되게 보내고 카드 snapshot을 다시 조회한다.
- 재접속 인사 시각·사용자 활동일·대화 길이·전환율 통계에 기술 이벤트를 대화 발화로 세지 않는다.
- Behavior Context trigger/reader는 기계 영수증을 새 사용자 선호 증거로 취급하지 않는다. 실제 사용자 발화와 기존 승인된 원본 경로는 유지한다.
- 실제 사용자 entry/start/close 클릭은 대화 요청의 근거이므로 모델/요약에 필요한 의미와 anchor를 제공한다. 영수증 자체를 사용자 발화처럼 세지는 않되, 클릭의 의미까지 숨겨 첫 요청을 잃지 않는다. 사용자 활동 시각은 원래 클릭 한 번만 반영하며 재시도·영수증 생성으로 연장하지 않는다.
- 과거 요약에는 mutable 카드의 최신 내용을 옛 시점의 발화처럼 넣지 않는다. 확정된 변경 영수증의 당시 사실과 원문 대화를 사용한다.
- 계정/대화 삭제 시 카드와 영수증도 같은 기존 삭제 범위에 포함한다. 별도 보존 사본을 만들지 않는다.

## 9. 한 사용자 턴에서 실제로 실행되는 순서

~~~mermaid
sequenceDiagram
    participant U as 사용자
    participant S as Chat 서버
    participant D as 기존 메시지 DB
    participant M as 원본 대화 LLM
    U->>S: 지금 커리어 고민을 코칭해 달라는 명시적 요청
    S->>D: 현재 활동과 대화 context 조회
    S->>M: 공통 + 일반 지침 + 요청
    M->>S: create_conversation_activity(active)
    S->>D: 카드와 변경 영수증 원자적 저장
    D-->>S: 확정 snapshot
    S->>M: 공통 + 코칭 지침 + tool 결과 + 같은 요청
    M-->>U: 해당 목적에 맞는 첫 코칭 응답
~~~

### 9.1 runner 변경 계약

두 실행 경로 모두 `resolveCareerExecutionContext`와 `buildCareerConversationPromptPlan`을 사용한다. helper 이름은 신규 제안이다. 다음 순서를 실제 runner에서 보장한다.

1. 요청을 인증하고 사용자 메시지를 한 번 저장한다. 현재 활동과 만료 경계를 읽는다.
2. 서버에서 origin·channel·activity를 구성하여 초기 prompt와 tool allowlist를 만든다.
3. 모델이 활동 도구를 호출하면 executor가 commit된 결과를 반환한다.
4. `contextChanged`가 있으면 현재 snapshot을 다시 읽고 system/developer blocks를 **교체**한다. 새 블록을 기존 지침 뒤에 계속 append하지 않는다.
5. 이전 assistant tool call과 대응 tool result, provider가 요구하는 reasoning/response item은 보존한다. 사용자 메시지는 중복 삽입하지 않는다.
6. 다음 모델 호출은 갱신된 prompt로 실행하고 생성되는 텍스트를 즉시 이어서 표시한다. 도구 실행 전에 이미 보여준 문장은 대화 맥락에 보존하며 반복하거나 미전달 문장으로 취급하지 않는다.
7. 최종 텍스트 저장·fallback·tool-budget 소진 후 응답도 마지막 확정 context를 사용한다.

활동 변경을 `stopAfterToolNames`에 넣어 빈 응답으로 끝내지 않는다. scope 변경 후에도 최신 도구 정책을 구성한다. 현재 continuation의 tool 축소 로직 때문에 필요한 활동 종료 도구가 사라지지 않는지 확인한다.

### 9.2 provider 별 작업

| 실행 경로 | 바꿀 부분 | 반드시 지킬 것 |
| --- | --- | --- |
| Career native Anthropic | loop 내부 systemBlocks를 재생성 가능한 값으로 전환 | tool_use/tool_result 대응, 캐시 블록 변경, stream/nonstream 동등성 |
| 공통 `runTalentAssistantToolLoop` | system message를 매 반복에 현재 plan으로 교체할 callback 추가 | 다른 onboarding caller는 기존 기본 동작 유지 |
| OpenAI Responses 등 공통 adapter | 원래 output item과 response 연결 유지 | reasoning item 보존, 중복 user turn 금지 |

| assistant-initiated `chatTurn.ts` | 동일 resolver 사용, origin별 allowlist 유지 | reengagement가 활동을 만들거나 재개하지 못함 |

### 9.3 기존 스트리밍 유지

**도구 호출 여부를 확인하기 위해 텍스트를 끝까지 보류하는 설계는 폐기한다.** 일반 대화와 코칭 모두 기존처럼 텍스트가 생성되는 대로 전달한다. tool schema가 있다는 이유로 전체 응답 완료를 기다리거나 별도 사전 판단 호출을 추가하지 않는다.

실행 순서는 텍스트 delta 전달 → 실제 tool call 실행 → commit된 결과로 카드 갱신 및 prompt 재조립 → 다음 모델 호출의 텍스트 delta 전달이다. prompt 교체는 다음 모델 호출에 적용하며 이미 보여준 문장을 되돌리기 위한 처리로 사용하지 않는다.

- 실행 전에는 의도와 필요한 설명을 말하고, 시작·종료·저장 완료 여부는 tool 성공 결과를 받은 뒤 설명하도록 공통 prompt와 tool continuation 계약에 명시한다.
- 카드의 실제 상태는 서버 commit 성공 후에만 갱신한다. 실행 중 표시는 가능하지만 성공 상태를 낙관적으로 표시하지 않는다.
- tool 실패 시 확정 상태를 유지하고 실패 결과를 반영한 응답을 이어간다. 이미 보여준 문장을 삭제하거나 deterministic 성공 문장으로 덮어쓰지 않는다.
- 사용자에게 전달된 pre-tool text도 실제 대화 기록과 다음 호출 context에 포함한다. 이어지는 응답이 앞선 설명을 불필요하게 반복하지 않게 한다.
- 응답 중 새로운 입력이나 상태 충돌이 확인되면 이후 생성을 중단한다. 이미 전달된 텍스트는 전달 사실 그대로 보존하며, 중단된 답변을 완결된 결과로 요약하지 않는다.
- 모델이 결과 전에 성공을 단정하는지는 원문 평가로 검증한다. 품질 문제는 prompt·도구 계약을 개선하며 전체 텍스트 보류를 복구하지 않는다.

### 9.4 실행 예산

활동 기능이 켜진 사용자 턴은 **기존 업무 도구 최대 4회 + 활동 변경 도구 최대 2회**, 전체 최대 6회로 제한한다. 이를 모두 순차 실행해도 최종 답변 기회가 남도록 최대 7번의 모델 호출을 허용한다. 최대치이며 일반 턴은 최종 응답 1회, 새 시작은 보통 2회다. 활동 없는 기존 경로의 예산은 이 변경만으로 늘리지 않는다.

예산은 prompt 재조립 시 초기화하지 않는다. timeout·출력 토큰 상한도 전체 요청에서 공유한다. 구조적으로 1회 허용한 재시도도 예산에 포함한다. 예산이 부족하면 성공하지 않은 종료나 실행을 완료했다고 말하지 않고 현재 확정 상태로 응답한다. 하나의 질문에 활동을 여러 번 열고 닫는 동작은 정성 평가에서 실패로 검토한다.

## 10. 대화가 어떻게 이어지는지 검토할 시나리오

아래 사례는 경험 확인용이며 runtime 분기나 enum으로 옮기지 않는다.

| 흐름 | 기대되는 경험 | 실제 실행 |
| --- | --- | --- |
| “지금 하는 일이 맞는지 모르겠어요. 커리어 코칭을 해주세요” | 명시적 요청에 알려진 배경을 반영하고 첫 질문/관점 제시 | create active → prompt 교체 → 코칭 응답 |
| “이 공고 어때?”, “나랑 맞을까?”, “요즘 이직할지 고민이야” | 요청한 평가·조언에 직접 응답 | 일반 대화 유지, 코칭 카드 도구 호출 없음 |
| active 중 “이 회사 공고 좀 보여줘” | 고민과 관련되면 자료를 함께 검토 | 기존 read tool 사용, 목적 유지 |
| active 중 “그건 나중에 하고 지금 지원 상태부터 알려줘” | 새 요청으로 바로 전환 | pause → 일반 목적 prompt → 기존 조회 |
| “오늘은 여기까지만. 더 생각해 볼게요” | 불완전한 결론을 존중하고 대화를 닫거나 보류 | 의미에 따라 pause/close, 결과를 과장하지 않음 |
| 다음 날 “안녕, 다른 얘기 좀 할게” | 지난 고민부터 재질문하지 않음 | 최신 상태 확인 → 현재 요청에 답함 |
| 다음 날 “어제 하던 얘기 이어서 하자” | 전체 배경 설명을 반복하지 않음 | paused start 또는 closed에서 새 활동, 필요한 원문 조회 |
| “아까 정한 기준은 취소하고 싶어요” | 오래된 요약보다 현재 정정을 우선 | 기존 Brief/Memory ref 수정, 현재 대화에서 이유 반영 |
| 설명만 듣고 떠났다가 3일 뒤 돌아옴 | 해결된 것으로 기록하지 않음 | inactivity pause, 재방문 인사는 자동 상담 재개 안 함 |

§20.1에는 이 초기 사례를 넘어, 실제 버튼·API·다음 턴까지 대입해 발견한 결함과 수정 여부를 기록했다. 설명상 기대와 실행 계약이 모두 맞아야 설계상 통과다.

## 11. 재방문과 re-engagement

### 11.1 새 방문의 기본값

사용자가 돌아왔다는 사실만으로 상담을 이어서 시작하지 않는다. 카드가 paused라면 조용히 접근할 수 있게 남기고, closed라면 과거 기록으로 둔다. 사용자가 보낸 새 메시지가 우선이다.

이 원칙은 12시간이 지나기 전에도 적용한다. 전날 밤 시작하고 몇 시간 뒤 돌아와 인사만 했다는 이유로 곧바로 지난 고민을 다시 질문하지 않는다. active가 남아 있어도 현재 발화의 의미를 우선하고, 사용자가 이어가는 말에는 자연스럽게 이어가며 다른 요청에는 답하거나 목적을 보류한다. 시간 기준은 방치된 실행 범위를 정리할 뿐 인사·재개·주제 변경을 판정하지 않는다.

재접속 인사는 active coaching prompt를 사용하지 않는다. 입력은 현재 유효한 활동 상태, 마지막 확정 결과의 짧은 맥락, 실제 새 기회·진행 상황처럼 지금 알려줄 근거로 제한한다. 오래된 코칭 transcript 전체와 일반 “후속 질문할 거리”를 동시에 넣지 않는다.

새로운 유용한 정보가 없으면 기존 no-message 경로를 사용한다. 기존 `__NO_SESSION_GREETING__`은 이 호출의 구조적 무출력 계약으로만 유지하며, 일반 사용자 응답의 품질을 키워드로 평가하는 데 쓰지 않는다.

### 11.2 두 경로와 경쟁 조건

`session/route.ts`와 `session/reengagement/route.ts` 모두 같은 resolver를 통과한다. 기존 자동 12시간, 사용자 요청 1시간, 개발 강제 실행 등의 호출 조건이 달라도 **끝난 활동을 재개할 권한은 생기지 않는다.** reengagement allowlist에 활동 변경 도구를 넣지 않는다.

인사를 생성하기 전 최신 사용자 메시지 anchor와 활동 revision을 잡는다. 저장 직전에 둘 다 다시 확인하여 새 대화나 상태 변경이 있으면 인사 insert를 취소한다. 기존 stale-message guard에 활동 revision도 포함한다. 카드/영수증/요약 생성 시각은 사용자 재방문 판단 시각으로 사용하지 않는다.

### 11.3 후속 약속의 범위

“나중에 다시 물어봐 줘”는 카드 note에 쓰는 것만으로 알림 예약이 아니다. 지원되는 scheduling capability가 없는 경로에서는 예약했다고 말하지 않는다. 이 설계는 새 scheduler·정기 코칭 메시지·이메일 캠페인을 만들지 않는다.

[온보딩 이후 위임 관계 기획](career-post-onboarding-agency-loop-product-plan-ko.md)의 “연락할 이유가 있을 때만 연락한다”는 원칙을 유지한다. 이 코칭 카드 기능은 **사용자가 명시적으로 요청한 코칭에만** 제공한다. 그 요청은 아직 진로를 정하지 않았어도 가능하다. 기존 후속 실행 기획이나 실제 새 기회의 존재가 요청하지 않은 코칭 카드를 생성하는 근거가 되지는 않는다.

## 12. 대화 요약, Memory, Search Brief의 연속성

### 12.1 세 원본의 책임

| 데이터 | 책임 | 해서는 안 되는 일 |
| --- | --- | --- |
| 활동 카드 | 현재 목적·실제 시작/보류/종료 | 성향·감정·추론을 장기 사실처럼 저장 |
| 대화 원문과 요약 | 무슨 이야기를 했고 어떻게 수정되었는지 | 현재 활동 상태나 최신 Brief를 덮어쓰기 |
| 기존 Brief/Memory | 현재 탐색 조건과 확인된 사용자 맥락 | 상담 transcript·가설을 통째로 복사 |

[Career Memory 설계 계약](talent-unified-memory-implementation-plan-ko.md)을 그대로 따른다. 원본 대화 LLM이 기존 `read_talent_context`/`write_talent_context`를 사용한다. 별도 coaching memory, 턴별 hidden extractor, write tool 안의 LLM은 만들지 않는다.

사용자가 “나는 규모보다 재량이 더 중요하네”라고 확인한 사실과, Harper가 “독립성이 중요한 것 같아요”라고 제안한 가설은 다르다. 후자는 사용자 사실로 저장하지 않는다. 현재 검색 조건 변경이 아니라 고민의 배경만 확인되었다면 Memory에 남길 수 있다. 일반 Brief 추가는 자유 label/content, 수정·삭제는 기존 ref를 사용한다.

활동 close는 Brief/Memory 저장을 자동 실행하지 않는다. 필요한 사실은 원본 LLM이 대화 중 기존 도구로 저장한다. close·Memory write·설정 변경이 서로 다른 결과라면 사용자에게도 각각 성공한 범위만 말한다.

### 12.2 기본 context와 추가 조회

기본 입력은 현재 Profile, 전체 Search Brief, 관련 Memory, 현재 활동 snapshot, 최근 대화와 누적 요약이다. 전체 과거 활동·모든 문서·모든 기회를 매번 넣지 않는다.

과거 정정을 확인해야 하거나 “지난번에 뭐라고 했지?”가 나오면 기존 일반 조회 능력을 확장한다.

- `read_talent_activity_events`에 소유 conversation의 활동 기록과 메시지 범위 조회를 추가한다.
- 모델은 짧은 activity ref 또는 검증된 source ref, cursor/limit로 원문을 읽는다.
- 조회 결과는 발화자·원래 시각·출처를 보존하며 페이지 끝 여부를 명시한다. 임의 문자열 SQL이나 다른 사용자 ID를 받지 않는다.
- call note는 기존 `list_documents`/`read_document`를 사용한다. 문서 원문을 새 Memory에 중복 저장하지 않는다.

이는 새로운 의미 판단 도구가 아니라 이미 있는 일반 read capability의 범위 확장이다. 큰 기록은 페이지 단위로 읽으며 필요한 원문이 없으면 불확실성을 설명한다.

### 12.3 요약 reader를 먼저 바로잡는다

목표 불변식은 다음과 같다.

> 입력에 사용되는 최신 summary의 cursor까지는 그 요약이 담당하고, cursor 이후의 메시지는 raw 또는 그 구간을 명시적으로 덮는 새 요약으로 제공한다. 조용히 빠진 중간 구간이 없어야 한다.

구현:

1. 최신 rolling `summary_text`와 `to_message_id`를 함께 조회한다. 최근 segment 3개만으로 대체하지 않는다.
2. cursor 뒤의 eligible 메시지를 ID 순서로 읽는다. “무조건 마지막 16개”로 잘라 미요약 구간을 버리지 않는다.
3. 최근 16개는 가능한 한 raw로 유지하되, 모델 context budget을 초과하면 이전 구간부터 기존 compactor로 압축한다.
4. 긴 backlog는 페이지 단위로 연속 처리한다. 전체 대화 fetch 후 일부만 잘라 쓰는 구조를 바꾼다.
5. 새 summary commit은 base cursor를 조건으로 한 CAS/RPC로 한다. 이미 더 새로운 summary가 있으면 오래된 결과를 적용하지 않는다.
6. compact 중 새 메시지가 와도 snapshot cutoff 이후 메시지는 다음 raw tail로 남긴다. 메시지 ID는 연속 숫자라는 가정 없이 실제 정렬·범위로 coverage를 검증한다.
7. compaction 실패 시 작은 gap은 raw로 포함한다. budget을 넘는 큰 gap은 조용히 생략하지 않고 이전 cursor를 유지한 채 재시도 가능한 오류를 반환한다. 사용자에게 기존 대화를 잃었다고 단정하지 않는다.

최근 raw 16개는 품질을 위한 기본값이지 전부 담겼다는 보장이 아니다. 매우 긴 단일 메시지는 source ref를 남긴 구간별 요약/조회로 처리하며 원문 끝을 조용히 잘라 버리지 않는다.

### 12.4 요약에 남겨야 할 의미

기존 background 요약 prompt에 다음 구분을 추가한다.

- 당시 목적, 사용자에게 확인된 이해, 제안에 그친 해석.
- 제안한 행동, 사용자가 받아들인 행동, 실제 도구로 완료된 행동.
- 논의가 끝난 범위와 아직 결정하지 않은 내용.
- 후속 발화에서 정정·철회된 사실과 그 시점.
- 마지막으로 논의하던 질문 또는 관점. 매번 동일 질문을 반복할 명령문으로 쓰지 않음.

새로운 감정·단계 JSON은 요구하지 않는다. 자연어 summary와 기존 cursor를 사용한다. 종료·재개 여부의 기계적 결정은 카드 snapshot을 읽는다. 요약 모델은 활동 상태를 변경하거나 Memory/Brief를 쓰지 않는다.

과거 요약은 `historical context`로 명확히 표시한다. 지금 assistant가 한 말처럼 synthetic assistant 메시지에 섞는 방식은 줄이고, 출처와 시점을 가진 데이터 블록으로 전달한다. 사용자가 과거에 쓴 지시문도 현재 system instruction으로 승격하지 않는다.

### 12.5 장기 압축의 현실적 한계

어떤 짧은 요약도 전체 대화를 손실 없이 보존하지 못한다. 이 설계는 모든 내용을 계속 압축해서 기억하겠다고 약속하지 않는다. 현재 상태는 카드, 현재 조건은 Brief, 중요한 확인 사실은 Memory, 자세한 경위는 원문으로 분담한다.

계속 요약된 내용만 다시 요약하며 생기는 왜곡은 원문 ref 조회와 정정 반영으로 줄인다. 최신 사용자 정정, 최신 Brief/Memory, 확정 tool 결과가 과거 요약보다 우선한다. 없는 출처를 모델이 만들어낸 경우에는 조회 실패로 처리한다.

## 13. 통화와 채팅의 연결

### 13.1 하나의 목적, 서로 다른 transport

통화 시작에는 기존 starterId 대신 검증된 `activityMessageId`를 전달한다. 서버는 사용자 소유권, 현재 revision, active/paused 상태를 확인하고 실제 목표를 불러온다. 클라이언트가 보낸 goal 문장을 곧바로 instructions로 신뢰하지 않는다.

일반 통화·internal 요청·모의 인터뷰·코칭 활동·기존 call note 재개를 모호하게 혼합하지 않는다. 요청에 상충하는 목적이 있으면 구조적으로 거부하고, UI에서 선택한 목적 하나로 다시 요청한다. call note를 다시 보는 것 자체가 과거 코칭 재개를 뜻하지 않는다.

call 시작 시 해당 활동과 revision, call ID를 연결한다. 이 연결은 기존 call/transcript message payload에 저장한다. 연결되지 않은 오래된 call-wrapup 요청이 현재 active를 닫을 수 없다.

통화 시작 시 transcript 행이 아직 없다면 시작 command의 영수증 payload에 call binding을 먼저 저장한다. binding에는 서버가 발급한 call ID, 활동 ref, 시작 revision, 마지막으로 해당 call이 확인한 revision, 종료/handoff 사실만 둔다. 연결 수립·handoff에 필요한 기술 기록이며 코칭 단계가 아니다. 같은 call에서 목표를 수정하면 mutation 성공 후 확인 revision을 함께 전진시킨다. 다른 채널에서 바뀐 revision은 오래된 call이 자동으로 받아들여 write하지 못한다.

한 conversation에 사용자에게 응답하는 활성 통화 연결은 하나로 제한한다. 다른 기기에서 새 통화를 시작하려면 기존 통화를 종료/인계하는 UI를 거친다. **텍스트를 입력하는 것과 통화를 채팅으로 전환하는 것을 구분한다.** 통화 중 공고 링크·정확한 회사명·짧은 설명을 입력해도 통화를 자동 종료하지 않는다.

활성 통화가 있으면 composer는 텍스트를 현재 통화에 보내는 기능과 명시적으로 채팅으로 전환하는 행동을 구분해 보여준다. 통화에 보낸 텍스트는 같은 conversation에 한 번 저장하고, 검증된 call binding을 통해 현재 음성 adapter로 전달한다. 원본 음성 대화가 그 맥락으로 답하며 별도 chat LLM 답변을 동시에 생성하지 않는다.

현재 공통 `useCareerVoiceSession`과 Realtime/Live adapter에는 `sendTextMessage`, `cancelResponse`가 있다. 이를 재사용하되 입력 순서와 응답 중복을 제어한다. 텍스트 전송이 음성 응답 중에 일어나면 기존 생성/재생을 안전하게 중단하고 새 입력을 반영한 음성 응답 하나만 생성한다. 마이크·통화 연결은 유지한다.

다른 기기에서 보낼 때도 서버에 저장한 message ID를 현재 call 소유 client로 전달하고 중복 전달을 막는다. 해당 adapter의 수신 확인 전에는 “통화에 전달됨”으로 표시하지 않는다. 연결된 client가 없거나 전달이 실패하면 pending/error를 표시하고 같은 메시지 재전송 또는 명시적 채팅 전환을 제공한다. URL을 전달했다는 것과 그 문서를 실제로 조회했다는 것은 다르므로, 원문 내용은 기존 read tool 성공 후에만 활용한다.

명시적 `continue(channel=chat)`를 선택하면 통화의 응답 권한을 인계하고 기존 음성 응답을 중단한다. 서버의 call binding 검증은 오래된 연결의 도구 write를 막고 live sync는 UI·음성 재생을 중단한다. 네트워크 지연 중 이미 재생된 음성은 회수할 수 없으므로 이 제한을 E2E에서 확인한다.

### 13.2 음성 provider별 전달

| 경로 | 코칭 목표가 들어갈 곳 | 구현 완료의 조건 |
| --- | --- | --- |
| Realtime | token endpoint가 만드는 instructions와 선택된 tools | opening, 매 턴 대화, 상태 변경 이후 instructions가 같은 목표 사용 |
| Live | `buildLiveFrontendInstructions`의 짧은 목적/위임 계약 + delegated backend의 전체 coaching prompt | frontend가 실질적 코칭 판단·도구·기억 조회를 backend에 맡기고 결과를 왜곡하지 않음 |
| 공통 voice hook | 현재 활동, call binding, 전환 결과 | UI·통화 adapter·서버 snapshot 일치 |

현재 `useLiveSession.updateSessionInstructions`는 delegated Responses instructions를 갱신한다. 이것만 호출하고 frontend의 목적도 바뀌었다고 간주하지 않는다. adapter의 인터페이스를 목적·frontend·backend instructions를 함께 다루도록 확장한다.

provider의 실제 update 지원과 ack 동작은 구현 시 검증해야 한다. 확인되지 않은 프로토콜 필드를 추정해 사용하지 않는다. **검증을 통과하지 못한 provider에는 새 코칭 통화를 노출하지 않는다.** 채팅 기능은 별도로 제공할 수 있지만, 통화 연결을 성공한 척하거나 사용자 몰래 다른 모델로 바꾸지 않는다.

### 13.3 통화 중 전환

활동 상태 도구가 성공하면 다음 응답을 요청하기 전에 서버가 만든 instructions를 adapter에 적용한다. 기존 생성/재생 중인 응답은 취소하고 update ack 뒤에 후속 응답을 시작한다. Live에서는 frontend와 backend 양쪽을 갱신한다.

코칭 중 실질적인 새 질문·해석·마무리는 backend 위임 대상으로 명시한다. frontend가 단독으로 “좋아요, 그러면…”을 이어가며 질문을 새로 만드는 문제를 실제 음성 E2E에서 확인한다. prompt 지시만으로 위임이 보장된다고 결론 내리지 않는다.

`useCareerOnboardingVoice.ts` 등에서 starter에 따라 주입하는 고정 opening이 서버의 목표를 덮어쓰지 않게 한다. 음성 opening은 현재 목적과 이미 알려진 맥락을 사용하며 채팅 내용을 다시 처음부터 묻지 않는다.

### 13.4 통화 종료와 handoff

`end_call`은 통화 transport 종료다. 코칭 목적 종료와 동일하지 않다.

- 목적을 마쳤다면 close를 성공시킨 후 마지막 음성 응답과 end_call을 진행한다.
- 채팅으로 계속하려는 명시적 handoff라면 같은 활동을 유지한다. 마지막 확정 발화와 결과가 서버에 저장된 뒤 chat 전송을 허용한다.
- 갑작스러운 끊김이나 사용자의 단순 hangup은 해당 call revision이 여전히 유효할 때 pause한다. 해결되었다고 쓰지 않는다.
- disconnect 이벤트는 짧은 재연결 유예 동안 동일 call binding을 복구할 수 있다. 초기 유예는 30초로 하며 완료 판단에는 쓰지 않는다.
- 명시적 채팅 전환을 눌렀다면 pending handoff를 기록하여 일반 disconnect cleanup이 pause로 덮어쓰지 않게 한다. handoff 실패는 사용자에게 보이고 재시도한다.

채팅에서 음성으로 갈 때도 마지막 assistant turn 저장 후 시작한다. 입력 중 draft는 보존하되 발화로 자동 전송하지 않는다. 마이크 허용 거절·연결 실패면 활동을 지우지 않고 채팅으로 돌아갈 수 있다.

### 13.5 늦은 call-wrapup과 call note

[call-wrapup route](../src/app/api/talent/chat/call-wrapup/route.ts)는 기존 transcript·call note·wrapup 산출물을 유지한다. 다만 call ID, 시작 당시 활동 ref/revision, transcript cutoff를 함께 받아 검증한다.

늦은 wrapup은 해당 통화 기록을 완성할 수 있지만 더 최근 채팅에서 수정한 활동·Brief/Memory를 과거 결론으로 덮어쓰면 안 된다. wrapup의 기본 역할은 통화 기록·요약이며 활동 lifecycle 도구는 허용하지 않는다. 원본 음성 LLM의 확인된 tool write와 겹치는 사실을 다시 저장하지 않는다. 기존 wrapup write를 유지해야 하는 경우에도 현재 ref/revision·출처 중복을 확인하고, 상충하면 write를 생략하여 다음 대화가 최신 사실에서 판단하게 한다.

call note 생성은 기존 [callNoteGeneration.ts](../src/lib/talentOnboarding/callNoteGeneration.ts)를 재사용한다. note 생성 실패가 이미 완료된 활동 종료를 되돌리지 않는다. note는 별도로 재시도 가능하며 실패 중에는 생성됐다고 표시하지 않는다.

## 14. UI 구현·접근성·번역

기존 [Design.md](../src/styles/Design.md)의 토큰과 component discovery 순서를 따른다. UI primitive는 `src/components/ui/`, `src/components/common/`, Career 도메인 순서로 찾는다.

새 도메인 component는 `ConversationActivityCard`, `CareerActiveActivityIndicator` 정도로 제한한다. 별도 modal infrastructure는 만들지 않는다. 목적 편집에 modal이 필요하면 [TalentCareerModal.tsx](../src/components/common/TalentCareerModal.tsx)를 사용한다.

필수 UX:

- 모바일에서도 title·현재 상태·핵심 행동을 읽고 누를 수 있다. hover 전용 제어를 두지 않는다.
- 키보드로 시작·보류·종료·재개 가능. 상태 변화는 접근성 live region으로 과도하지 않게 알린다.
- 카드가 갱신되어도 scroll·작성 중 draft·focus를 빼앗지 않는다.
- 진행 중 command의 중복 클릭을 막고 실패하면 실제 이전 상태와 재시도 행동을 유지한다.
- 낙관적으로 “완료”를 먼저 표시하지 않는다. 로딩은 표시할 수 있다.
- UI 버튼 성공 후 모델 생성이 실패해도 카드의 실제 상태가 보인다. 자연어 실패 메시지가 상태를 감추지 않는다.
- 통화/채팅 선택은 같은 목적에 대한 선택이며, 다시 설명을 작성하는 흐름이 아니다.
- 다른 기기에서 통화 중일 때도 composer에 그 사실을 표시한다. 텍스트를 통화에 보내는 행동과 통화를 끝내고 채팅으로 이어가는 행동을 분리한다.
- 상단에는 현재 active 하나만 보인다. 보류/완료 활동은 기존 composer 메뉴에서 열 수 있는 과거 이야기 목록으로 접근한다. 제목·목적·날짜·실제 상태를 보여 주고 원래 카드로 이동하거나 재개/다시 다루기를 선택할 수 있다. 오래된 대화를 찾으려고 긴 채팅을 끝없이 스크롤하게 하지 않는다. 목록은 같은 메시지 카드의 조회 결과이며 별도 코칭 탭이나 기억 저장소가 아니다.

문구 초안:

| 의미 | 한국어 | 영어 |
| --- | --- | --- |
| composer 진입 | 함께 생각해 보기 | Talk it through |
| 시작 | 채팅으로 이야기하기 | Talk in chat |
| 시작 | 통화로 이야기하기 | Talk on a call |
| 보류 | 잠시 멈추기 | Pause for now |
| 종료 | 여기서 마치기 | Wrap up |
| 재개 | 이어서 이야기하기 | Continue our conversation |
| 완료 기록 재사용 | 이 이야기 다시 꺼내기 | Revisit this conversation |

이 문구는 구현용 초안이며 번역 DB에 쓰지 않았다. 실제 코드 위치·공간을 확인한 뒤 [translation.md](../scripts/translation.md)에 따라 Codex가 영어를 직접 작성하고 변경 키만 동기화한다.

## 15. 실패·동시성·재시도 계약

| 상황 | 서버 동작 | 사용자 경험 |
| --- | --- | --- |
| 활동 생성 실패 | 상태 유지, 실패 tool 결과 | 시작됐다고 말하지 않고 같은 입력으로 재시도 가능 |
| close 성공 후 응답 생성 실패 | closed 유지, 카드와 receipt 보존 | 닫힌 상태 확인 가능, 마무리 문장만 재생성 |
| Memory 저장 실패, close 성공 | 두 결과를 별도로 유지 | 대화는 끝났지만 저장 실패 사실을 정확히 안내 |
| 동일 버튼/도구 재전송 | operation receipt로 동일 결과 반환 | 카드·이벤트 중복 없음 |
| 다른 기기가 먼저 목적 수정 | expectedRevision conflict, 최신 snapshot 반환 | 원본 LLM이 최신 요청에서 다시 판단, 자동 덮어쓰기 없음 |
| close와 새 활동 시작 경쟁 | conversation lock와 active unique constraint | 이전 요청이 새로운 활동을 닫지 못함 |
| 늦은 greeting/wrapup | anchor·activity revision 검사 | 새 대화 뒤에 오래된 상담 인사가 끼어들지 않음 |
| provider retry/fallback | 최신 확정 prompt로 재개, 예산 공유 | 종료한 모드가 되살아나지 않음 |
| summary 실패 | cursor 불변, 미요약 raw 보존 | 잃어버린 맥락을 안다고 주장하지 않음 |
| call permission/연결 실패 | start 결과와 transport 결과 분리 | 목적을 다시 적지 않고 채팅 지속 또는 통화 재시도 |
| 통화에 보낸 텍스트의 전달 실패 | 메시지는 보존, adapter 수신 상태를 성공으로 처리하지 않음 | 입력 유실 없이 다시 보내거나 명시적으로 채팅으로 전환 |

operation ID는 UI command의 request ID 또는 서버 실행 ID+provider toolCallId에서 만든다. 모델에게 생성시키지 않는다. runner가 toolCallId를 executor에 전달하도록 현재 누락된 경로를 보완한다. 중복 clientRequestId는 사용자 메시지 insert도 한 번만 되게 한다. 재생성된 다른 toolCallId는 revision/active 제약으로 중복 mutation을 막고, 모델에 최신 결과를 제공한다.

답변 생성 시작 시 사용자 anchor와 활동 revision을 확인하고, 도구 write·응답 저장 전에도 최신 상태를 검증한다. 텍스트 delta는 보류하지 않고 전달하되 새 입력·상태 변경으로 실행 무효화가 확인되면 추가 생성과 전달을 중단한다. 이미 전달된 문장은 회수하지 않고 기존 interrupted UI로 표시한다. 중단된 부분 응답을 완결된 결론으로 요약하지 않는다. 기기 간 변경 전달에는 지연이 있을 수 있으므로, stale 텍스트가 한 글자도 표시되지 않는다는 보장을 하기 위해 전체 응답을 숨기지 않는다. 확정 write의 권한·revision 검증과 사용자에게 실제 전달된 범위를 각각 보존한다.

자기 실행의 활동 mutation이 성공하면 검증 anchor의 activity revision을 그 결과로 전진시킨다. 자신의 start/close 때문에 매번 stale로 판정하는 버그를 피한다. 반대로 다른 실행의 새 revision은 자동 승인하지 않고 context를 다시 읽는다. 도구 실패나 conflict 뒤에 tool 결과를 성공으로 바꾸는 보정은 하지 않는다.

동일 사용자 턴의 재전송은 원래 request ID와 연결된 저장 결과를 반환한다. 실행 중 중복 요청은 별도 모델 실행을 만들지 않고 진행 중 상태를 반환한다. 이를 위한 실행 lease가 현재 경로에 없다면 사용자 메시지 또는 UI command 영수증 payload에 기술적 request/lease 정보를 둔다. lease는 서버 발급 token과 만료를 가지며 모든 후속 write가 token 소유권을 확인한다. takeover 이후 옛 실행이 commit하지 못하게 한다. 모델의 판단을 저장하는 새 테이블로 확대하지 않는다.

## 16. 권한·프라이버시·기존 기능 경계

서버는 모든 카드·원문 조회·도구 mutation에서 인증된 user와 conversation/card 소유권을 검증한다. service role executor에서도 클라이언트가 보낸 ref·call ID를 신뢰하지 않는다. tool execute endpoint는 voice binding과 purpose에 맞는 allowlist를 서버에서 다시 검증한다.

코칭은 기존 권한을 확장하지 않는다.

- Memory·Brief 저장은 회사 공유 동의가 아니다.
- 활동 종료·보류는 `talent_setting.status`나 추천 주기 변경이 아니다.
- 후보자의 수락만으로 회사 공유가 실행되지 않는다. 기존 팀원 최종 확인 경계를 유지한다.
- role availability, testOnly 격리, idempotency, 공유·연락 동의는 기존 hard guard를 사용한다.
- 온보딩 checklist·extraction 예외를 일반 코칭에 복제하지 않는다.
- 모의 인터뷰용 context·도구 격리를 유지한다.
- 활동 제목/목표/외부 문서/과거 메시지는 비신뢰 데이터다. 이를 system instruction 문자열에 무표식으로 삽입하지 않는다.
- 민감한 고민을 analytics·오류 알림 제목·외부 카드 preview에 그대로 넣지 않는다. trace는 식별자·revision·처리 결과 중심으로 남긴다.

## 17. 비용·성능·관측

추가 모델은 없다. 일반 사용자 턴은 기존 원본 LLM, 시작/종료는 같은 LLM의 tool continuation을 사용한다. 요약은 기존 background compaction 경로를 개선한다.

초기 context 예산:

| 입력 | 정책 |
| --- | --- |
| 공통 지침 | invariant만 캐시 가능한 공통 블록으로 유지 |
| coaching module | 일반 agenda를 대체. 두 모듈을 합산하지 않음 |
| 활동 snapshot | 현재 하나 + 관련된 종료/보류 기록의 짧은 index |
| Brief | 전체 유효 행 유지, 임의 항목 절삭 금지 |
| Memory | 기존 관련도·중요도 기반 compact context, 필요 시 read |
| 대화 | rolling summary + cursor 이후 연속 raw, 최근 16개 우선 보존 |
| tool 결과·문서 | 기존 페이지/길이 제한과 source ref, 추가 읽기 가능 |

정확한 토큰 상한은 실제 사용 모델의 context limit과 provider tokenizer로 계산한다. 최소 출력 여유·tool envelope를 예약하고, 초과 시 오래된 대화부터 compact한다. 전체 Brief가 실제로 한도를 넘는 계정은 조용히 일부를 빼지 않고 입력 한도 오류로 관측해 별도 개선 대상으로 처리한다.

계측할 구조적 사실은 prompt version/hash, origin/channel, activity ref/revision, 포함한 block ID, summary cursor와 raw 범위, tool 결과·중복 여부, model call 수, 토큰·비용, 첫 가시 응답/전체 완료 지연이다. 원문 감정 분석 점수나 모델 사고 기록을 추가하지 않는다.

목표는 일반 턴 p95 완료 지연·비용을 동일 모델 baseline 대비 20% 이상 악화시키지 않는 것이다. 시작/전환 턴은 추가 continuation 비용을 별도 보고한다. 이 수치는 출시 전 확인할 목표이며 현재 측정값이 아니다. 일반 질문을 코칭 판별용 추가 호출에 보내지 않고 기존 점진적 응답 표시를 유지한다.

완료 지연이 비슷해도 첫 가시 응답은 늦어질 수 있다. 따라서 tool progress, 카드 commit, 최종 내용의 첫 노출 시각을 따로 측정하고 빈 로딩 표시를 의미 있는 첫 응답으로 세지 않는다. 대기 때문에 대화의 흐름이 끊긴다는 원문/사용성 리뷰가 남으면 평균 성능 수치만으로 release gate를 통과시키지 않는다.

품질을 대화 길이·사용 시간·코칭 재진입률만으로 성공 판정하지 않는다. 사용자가 목적을 이해하고, 답을 반영받고, 원하면 끝낼 수 있는지를 원문 리뷰와 사용자 피드백으로 평가한다.

### 18.3 평가 데이터와 실행

v2는 synthetic 다중 턴 challenge set으로 만들고, 위 V01~V20의 의미 판단과 lifecycle 경험을 함께 덮는다. 테스트 사례를 새 상황별 runtime 분기로 바꾸지 않는다. 한국어·영어, 짧은·긴 대화, 명확한·모호한 종료, 긍정·정정·중단, 열린·닫힌 과거 활동을 포함한다.

실제 prompt builder/runner/tool schema를 import하는 [canonical runner](../scripts/evalCareerCoachingDialogue.ts)를 확장한다. 구조적 mutation 테스트는 격리 DB fixture로 별도 수행하고, 실제 브라우저/음성 E2E와 content-only 결과를 분리한다. 모델 설정은 runtime 설정을 읽고 실제 provider/model/reasoning·timeout·예산을 manifest에 기록한다. 새 provider 비교는 같은 frozen set의 새 run이다.

최소 release gate:

1. 구조적 계약·동시성·권한 테스트 전부 통과.
2. frozen v2를 같은 설정으로 3회 실행하고 모든 run에서 critical failure 0.
3. 모든 사례의 전체 대화를 사람이 읽어 해당 경험 rubric 통과. 문장 길이·키워드로 정성 판정하지 않음.
4. 실제 desktop/mobile 채팅에서 시작·보류·종료·재방문·압축 이후 재개 확인.
5. 노출할 각 음성 provider에서 실제 입출력·위임·중단·handoff E2E 통과.
6. latency/cost 목표 검토, 미해결 사용자 경험 blocker 0.

무단 write/공유, 잘못된 사용자 데이터, 명시적 요청 없는 코칭 카드 생성, 종료한 활동의 자동 재개, 실행하지 않은 성공 주장, stale write, 요약 구간의 조용한 누락은 critical failure다. 전체 텍스트 보류의 재도입도 이 설계 계약 위반으로 release를 막는다. 작은 challenge set 통과를 전체 사용자 성공률로 발표하지 않는다.

raw 출력·production 원문은 registry의 ignored private/runs에만 두고 0600 권한을 적용한다. 공유 fixture는 합성·비식별 자료와 frozen gold/manifest다. 실제 계정·역할을 쓰는 E2E가 필요하면 별도 승인 범위와 testOnly 격리를 지킨다.

| session 두 route, `lifecyclePrompts.ts` | neutral reentry, no-message, 활동 revision guard |
| realtime/token, live/session, tool/execute | 검증된 call binding·prompt·도구 권한 |
| `realtimeInstructions.ts`, `voiceSessionInstructions.ts` | 목적별 음성 전달과 Live 위임 |
| `useCareerVoiceSession.ts`, `useRealtimeSession.ts`, `useLiveSession.ts`, `useCareerOnboardingVoice.ts` | instruction 갱신·ack·opening·명시적 handoff·통화 보충 텍스트의 전달/응답 직렬화 |
| call-wrapup route, 기존 call note 경로 | stale revision/중복 source 방지, 산출물 재시도 |
| 신규 additive migration | nullable payload·구조적 index/check·mutation RPC·관련 trigger filtering |
| 기존 coaching 평가 registry/runner | frozen v2·manifest·구조/내용/E2E 보고 분리 |

### 19.3 호환과 도입

server feature flag `careerConversationActivities`를 도입한다. flag는 기능 사용 가능 여부만 결정하며 언어·종료·의미를 분류하지 않는다. provider별 voice 지원 gate는 별도로 둔다.

additive schema와 tolerant reader를 먼저 준비한다. 기존 메시지에 가짜 활동을 소급 생성하지 않는다. 과거 상담은 history일 뿐 active로 복원하지 않는다. 기존 브라우저에 남은 starterId는 새 활동 상태를 덮어쓸 수 없다.

전환 기간 동안 explicit legacy coaching 진입은 서버 adapter에서 동일 create/start 경로로 한 번 정규화한다. 단순 후속 요청에 자동 첨부된 starterId는 새 활동 생성 근거가 아니다. 이를 구별할 명시적 entry command가 없는 구버전 client는 새 기능을 활성화하지 않고 기존 호환 UI 또는 업데이트 안내를 제공한다. legacy ID를 매 턴 mode override로 유지하지 않는다.

flag off에서는 새 활동 시작을 막되 기존 카드 조회·보류·종료와 최신 상태 경계는 계속 지원한다. coaching prompt를 전체에서 갑자기 삭제하고 진행 중 상태를 방치하지 않는다. 문제가 생기면 진입을 닫고 진행 중 활동을 안전하게 pause할 수 있는 corrective build를 사용한다.

payload를 모르는 오래된 앱 binary로 무조건 되돌리는 것을 안전한 롤백으로 보지 않는다. 최초 schema 도입 이후의 롤백 대상도 payload를 읽고 closed를 존중할 수 있는 버전이어야 한다. 데이터를 지우거나 과거 prompt를 복구해 활동을 되살리지 않는다.

### 19.4 이번 문서 작업과 이후 실행의 경계

이번 작업은 설계와 코드 조사다. 제품 구현, migration 적용, 모델 평가 실행, 번역 DB write, commit/push/배포를 수행하지 않았다. 이 문서의 완료 조건을 충족하기 전에는 구현 완료나 production-ready로 표시하지 않는다.

향후 배포는 별도 명시적 요청을 받아 repository의 Git-triggered 배포 및 배포 후 문서 동기화 계약을 따른다. 구현 계획 문서를 작성했다는 이유로 Notion에 live 동작을 갱신하지 않는다.

### 19.5 기존 대화 경험에 대한 영향 범위

이 변경은 코칭 버튼만 추가하는 작업이 아니다. 공통 prompt, 도구 선택, 실행 loop, 요약 reader와 메시지 저장 형식을 바꾸므로 코칭을 한 번도 쓰지 않은 사용자도 영향을 받을 수 있다.

| 기존 경험 | 영향을 주는 변경 | 유지해야 할 기준과 검증 |
| --- | --- | --- |
| 단순 질문·추천 조회의 즉시성 | 활동 snapshot 조회와 공통 prompt 재구성 | 기존 text delta 즉시 전달 유지. tool 여부 확인을 위한 전체 응답 보류·추가 판별 호출 없음 |
| 직접 답하는 일반 대화 | 공통 지침 재구성과 명시적 코칭 요청 처리 계약 추가 | 공고 평가·비교·정보·고민 언급에는 카드 도구 호출 없음. 요청한 코칭 범위 밖의 일반 대화 지침 유지 |
| 일반 tool 사용과 권한 | 새 도구를 공통 registry에 등록 | schema 노출과 executor 권한을 모두 origin/channel/purpose로 제한. onboarding·mock·자동 event에 묵시적 확장 없음 |
| 추천 피드백·회사 팔로우·Gmail 안내 | 공통 chatTurn이 active 코칭 상태를 읽음 | event_reply는 자기 source instruction/allowlist 사용. 코칭 자동 시작/종료 금지. 실제 완료 안내를 코칭 때문에 일괄 누락하지 않음 |
| 코칭 중의 다른 기능 알림 | 별도 생성 경로가 동시에 채팅에 insert | 추가 질문·제안이 active 대화를 가로채지 않게 의미 계약과 최신 anchor로 검증. 필요한 처리 결과는 기존 표면에 전달하고 종료 후 알림을 한꺼번에 쏟지 않음 |
| 오래된 대화를 기억하는 방식 | rolling summary와 연속 raw로 공통 reader 변경 | 코칭 없는 계정도 context가 달라짐. 기존 일반/온보딩/internal-call 맥락 회귀를 별도로 확인 |
| 첫 방문과 재방문 인사 | no-message·closed 경계·activity revision 검사 | 상담 재개만 줄이고 실제 새 기회·처리 결과까지 숨기지 않음 |
| 채팅·통화 및 다른 provider | shared loop와 voice adapter 변경 | refresh callback 미사용 caller는 기존 동작 유지. call 목적별 context/tool 격리 보존 |
| 미읽음·활동일·기록·추천의 파생 context | messages에 카드/영수증/UI action 추가 | 기술 이벤트를 실제 발화·선호·사용 시간으로 집계하지 않음. 사용자 클릭은 정확히 한 번만 반영 |

구현을 검토할 때 세 범위를 나눠 보고한다.

1. **의도한 변화:** 명시적으로 요청한 코칭에서의 원클릭 방향 제안, 목적을 유지하는 대화, 종료 후 재질문 감소.
2. **기존 동작을 보존할 범위:** 명확한 일반 요청의 직접 처리, 기존 권한·온보딩·모의 인터뷰·회사 연결, 이벤트별 실제 결과 안내.
3. **별도 측정이 필요한 공통 변경:** prompt 재구성, tool 선택 변화, 기존 streaming과 prompt 교체의 연결, summary reader. 코칭 시나리오 통과만으로 이 범위까지 통과 처리하지 않는다.

feature flag off 경로에서는 기존 tool 노출·일반 prompt·streaming 동작을 유지한다. payload 호환 reader는 필요하지만, 활동 기능을 껐다는 이유로 공통 summary reader 변경까지 되돌려졌다고 가정하지 않는다. summary 변경은 독립적으로 검증·도입한다. 코칭 prompt on/off만 비교하는 실험으로 공통 실행기 변경의 영향을 측정했다고 주장하지 않는다.

### 20.2 사용자 지시에 따른 확정 제약 — 2026-09-21

- 전체 응답을 도구 호출 여부 확인까지 숨기는 설계를 제거했다. 코칭과 일반 대화 모두 기존 점진적 스트리밍을 사용한다.
- 코칭 카드는 버튼 클릭이나 명시적 자연어 코칭 요청에 응답할 때만 제안·생성한다. “이 공고 어때?”를 비롯한 공고 평가·추천·정보·일반 조언 질문은 전부 제외한다.
- 요청한 코칭 안에서 방향을 제안하고 답변·수정을 받아 이어가는 경험은 유지한다. 이미 종료한 코칭의 요청을 새 일반 질문의 생성 허가로 사용하지 않는다.
- 자연어 의미는 원본 LLM이 판단하고, tool 호출 조건을 prompt·tool description·원문 평가에 동일하게 적용한다. 새 classifier·키워드 분기·사전 확인 모델은 없다.

**20개 고려 사항과 13개 사용자 흐름의 검토에 위 확정 제약을 반영했다. 구현과 runtime 검증은 아직 수행하지 않았다.** 이 문서가 제안하는 변경의 핵심은 사용자가 명시적으로 원할 때 충분히 깊게 이야기하고, 일반 대화는 기존처럼 직접적이고 자연스럽게 이어가게 만드는 것이다.
