# Prepare_Content.md

버전: 1.0 · 적용일: 2026-09-16 · 상태: active (범위는 Connections 기준) · 관리: 아래 관리 역할

[AGENTS.md](AGENTS.md)를 먼저 읽는다. 이 문서는 해당 작업의 입력 파악부터 분석·실행·저장·결과 확인까지 소유한다. 외부 발송·게시·송금·플랫폼 API 연결은 문서만으로 생기지 않는다.

## 업무 계약

- **호출 상황:** ‘이 사람에게 줄 제작 가이드 만들어’, ‘캠페인·포맷 정해서 콘텐츠 준비해’, ‘기존 영상을 우리 계정에 다시 쓰게 준비해’.
- **입력·근거:** 협업 조건, 제품의 실제 기능·증거, 캠페인·포맷 가이드, 제작자의 실제 스타일, 배포 계정·언어·권리·기한.
- **소유하는 방법:** 구체적 콘텐츠 방향 선택 → 타깃·메시지·표현 흐름·필수 장면/근거·CTA·산출물·일정 작성 → 콘텐츠/플랫폼 행과 추적 링크 준비 → 랜딩·링크 확인 → 실제 제작자에게 전달할 한 묶음으로 정리. 재사용이면 사용권·수정 범위·추가 비용·이전 성과를 확인한다.
- **저장:** contents의 캠페인·포맷·브리프·당시 조건·링크·일정·이전 콘텐츠 참조. 실제 전달본 버전을 고정하고 요청된 전달이 수행됐을 때 전송 근거를 남긴다.
- **여러 플랫폼:** 공통 브리프·원본 파일은 같은 고정 참조를 쓰고 CTA·게시일·링크는 플랫폼별로 관리한다. 공통 수정은 적용할 미게시 콘텐츠를 확인해 함께 반영하며 이미 게시한 버전은 그대로 보존한다.
- **완료:** 제작자가 무엇을 언제 어떤 형태로 만들지 알 수 있고, 게시·검수 담당이 같은 기준과 링크를 사용할 수 있다. 제작자가 다시 여러 질문을 해야 하는 내부 메모는 완료본이 아니다.
- **예외·경계:** 새로운 재사용 포맷 자체가 필요할 때만 Develop_Campaigns_Formats.md으로 확장한다. 재사용한다고 새 원 제작비를 복사하지 않는다. 실제 촬영·편집을 수행한 것처럼 보고하지 않는다.
- **관리:** 콘텐츠 담당이 반복 질문·초안 수정 이유·제작 시간·실제 성과로 가이드를 개선한다.

## 현재 도구로 끝까지 수행하기

[Connections.md](Connections.md)의 Supabase plugin 및 `gtm_workspace` 호출 계약을 사용한다. 칼럼은 [data-model.md](data-model.md), 제품 사실은 [Business_Context.md](Business_Context.md), 계산은 [measurement.md](measurement.md)가 원본이다.

1. 협업 조건과 캠페인/포맷 가이드의 특정 버전, 제품 사실, 사용권을 읽는다. 제작자에게 필요한 대상·핵심 메시지·CTA·금지 주장·납기·산출물·통계 제출 기준을 한 브리프로 작성한다.
2. `save gtm_contents`로 계정별 게시 행을 만든다. 같은 제작물은 content_group_id를 공유하고 brief_ref/brief_version 및 asset_refs의 고정 파일 버전을 연결한다. 플랫폼마다 CTA·게시일은 따로 둘 수 있다.
3. plan_id와 campaign_id를 확정한 뒤 `issue_link`로 링크를 발급한다. 예: data={destination_url:"https://matchharper.com/career",source:"instagram",medium:"creator",scope:"content",placement:"story"}. 실제 공용 프로필 링크는 scope=`account` 또는 `plan`으로 발급하고 개별 콘텐츠 성과라고 약속하지 않는다.
4. 반환된 URL을 사용하고 UTM을 수기로 고치지 않는다. 같은 제작물의 브리프 변경은 적용할 미게시 행의 row_version을 읽은 후 `batch`로 갱신한다. 이미 게시된 행은 당시 버전을 보존한다.
5. 전달할 브리프·파일·링크가 서로 일치하는지 확인하고 `brief_prepared` 활동에 결과를 남긴다. 실제 전달은 기존 허용과 연결 범위에서만 수행하며, 미연결이면 전달 가능한 본문/자료를 제공한다.

## 중단·충돌·완료 확인

같은 쓰기를 재시도할 때 request_id와 본문을 유지한다. row_version 충돌은 최신 행을 읽고 실제 변경을 재판단한다. 애매한 외부 결과를 성공으로 기록하지 않는다. 외부 입력을 기다리면 기존 원장의 실제 할 일·담당·기한·재개 조건을 남긴다. 결과에는 사용한 문서 버전, 저장한 원장 ref/ID, 실제 완료 범위와 남은 사항을 포함한다.
