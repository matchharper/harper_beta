# Design_Experiments.md

버전: 1.0 · 적용일: 2026-09-16 · 상태: active (범위는 Connections 기준) · 관리: 아래 관리 역할

[AGENTS.md](AGENTS.md)를 먼저 읽는다. 이 문서는 해당 작업의 입력 파악부터 분석·실행·저장·결과 확인까지 소유한다. 외부 발송·게시·송금·플랫폼 API 연결은 문서만으로 생기지 않는다.

## 업무 계약

- **호출 상황:** ‘포맷 때문인지 CTA 때문인지 확인하자’, ‘이 조합을 더 크게 해도 되는지 검증하자’. 단순 재시도와 달리 비교로 배울 목적이 있는 작업이다.
- **입력·근거:** 바꾸려는 사업 결정, 현재 근거·불확실성, 비교 가능한 대상·기간·비용·실행 제약.
- **소유하는 방법:** 검증할 질문 → 바꿀 조건과 유지할 조건 → 비교/배정 단위·주지표·기간·손실 한도 → 실제 제작/연락 계획 → 결과 비교와 한계 해석. 무작위 비교가 불가능하면 그 한계를 명시한다.
- **저장:** plans의 실험 계획 버전, 실제 contents의 조건·참여/배정 근거, 결과 리뷰. 업무를 설명하기 위해 새 상태 머신을 만들지 않는다. 실제 실험이 필요로 하는 배정 사실만 보존한다.
- **완료:** 어떤 결과면 어떤 사업 결정을 할지 사전에 설명할 수 있고, 실행 후 결과로 무엇을 배웠는지 재현할 수 있다. 작은 표본의 우연을 확정 결론으로 쓰지 않는다.
- **경계·관리:** 실제 제작·게시·수집은 Prepare_Content.md~Collect_Performance.md를 사용하고 집행 책임자가 관리한다. 1차의 기본 재시도 기록은 Prepare_Content.md/Review_Performance.md로 가능하며 이 문서의 완성을 기다리지 않는다.

## 현재 도구로 끝까지 수행하기

[Connections.md](Connections.md)의 Supabase plugin 및 `gtm_workspace` 호출 계약을 사용한다. 칼럼은 [data-model.md](data-model.md), 제품 사실은 [Business_Context.md](Business_Context.md), 계산은 [measurement.md](measurement.md)가 원본이다.

1. 바꿀 사업 결정과 현재 불확실성을 한 문장으로 정한다. 관련 performance/비용/콘텐츠를 읽어 비교 단위와 실행 가능한 수량을 검토한다.
2. 가설·처치/대조·배정 단위·주지표·관측 기간·예산/손실 한도·중단 기준을 실행 전에 계획 문서의 고정 버전에 기록한다. 임의로 바뀐 조건은 추후 해석에서 드러내야 한다.
3. 실제 사용한 배정·처치 사실만 gtm_contents.execution_snapshot과 계획 참조로 보존한다. 임시 모델 사고를 테이블/상태로 만들지 않는다.
4. 같은 지표·관측 창으로 비교하고 작은 표본·겹치는 관객·비무작위 배정의 한계를 보고한다. 실제 선택은 채택 리뷰와 다음 행동으로 이어간다. 자동 통계 최적화/밴딧 실행은 현재 제공하지 않는다.

## 중단·충돌·완료 확인

같은 쓰기를 재시도할 때 request_id와 본문을 유지한다. row_version 충돌은 최신 행을 읽고 실제 변경을 재판단한다. 애매한 외부 결과를 성공으로 기록하지 않는다. 외부 입력을 기다리면 기존 원장의 실제 할 일·담당·기한·재개 조건을 남긴다. 결과에는 사용한 문서 버전, 저장한 원장 ref/ID, 실제 완료 범위와 남은 사항을 포함한다.
