# Outreach_Creators.md

> **팀원을 위한 한눈에 보기**
> 이 문서는 조사된 크리에이터 중 지금 연락할 사람을 고르고, 각 사람에게 가장 맞는 Outreach Template 하나를 선택해 실제로 보낼 메시지를 완성할 때 사용합니다. 각 결과에는 왜 이 사람인지, 어떤 템플릿을 왜 골랐는지, 어떤 콘텐츠와 보상 조건을 제안하는지, 정확한 메시지 원문이 포함됩니다. 맞는 템플릿이 없으면 한 사람 전용 문구가 아니라 다시 쓸 수 있는 템플릿을 먼저 추가합니다. Agent가 준비한 사람별 이메일은 팀원이 `Outreach Review`에서 한 건씩 최종 확인해야만 발송됩니다.

버전: 2.6 · 적용일: 2026-09-17 · 상태: active (사람별 Sheet 승인 발송·Gmail 회신 DB 동기화·Slack 알림 운영 중) · 관리: 크리에이터 Outreach 담당

[AGENTS.md](AGENTS.md)를 먼저 읽는다. 제품 사실은 [Business_Context.md](Business_Context.md), 실제 도구·권한은 [Connections.md](Connections.md), 저장 계약은 [data-model.md](data-model.md)가 원본이다. 이 문서는 새 협업의 최초 연락에서 **대상 한 명마다 Outreach Template 하나를 선택하거나 필요한 템플릿을 먼저 만든 뒤, 개인화된 메시지 한 개를 준비·검수·기록하고, 권한이 있으면 발송 결과까지 확인하는 일**을 소유한다.

> **완료 책임:** 팀원이 “N명에게 누구에게 뭐라고 연락할지 만들어”라고 맡기면 대상 선정, 템플릿 선택, 후보별 제안 전략, 정확한 메시지, 검수, DB 저장과 결과 보고까지 이 문서 하나로 끝낸다. “작성해”는 발송 권한이 아니다. 실제 발송은 팀원이 명시적으로 맡기고 발송 연결과 권한이 있을 때만 수행한다.

## 1. 결과 계약

요청한 각 대상에 대해 아래 결과를 한 번에 제공한다.

| 결과 | 완료 기준 |
| --- | --- |
| 누구에게 | creator ref, 동일인 플랫폼 계정, 최근 콘텐츠·반응 분포, 필수 조건 근거, 검증된 실제 연락 경로 |
| 왜 이 사람에게 | 이번 목표와 직접 연결되는 이유, 평소 반응과 outlier/추이, 반대 근거·불확실성, 기존 관계·성과 |
| 어떤 템플릿으로 | 선택한 outreach template ref·version·상태, 선택 이유, 검토했지만 선택하지 않은 가장 가까운 대안과 이유 |
| 무엇을 제안하는가 | 캠페인·포맷 또는 구체적인 제작 각도, 원하는 산출물·플랫폼·시기, 필요한 다음 행동 |
| 어떤 조건으로 | 단가 문의/승인 금액·범위/고정·성과·혼합 지급 등 실제 선택한 보상 전략과 미확정 조건 |
| 뭐라고 보낼지 | 대상·채널·언어에 맞는 정확한 최종 메시지 원문. 템플릿을 그대로 복사하거나 이름만 바꾸지 않음 |
| 어디까지 실행됐는지 | `draft_ready` / 실제 `sent` / 실패·미확인 구분, collaboration·activity ref, 다음 담당·기한 |

요청한 N명은 [Research_Creators.md](Research_Creators.md)에서 `outreach_score` 4 또는 5로 평가되고, 이번 요청에 맞으며, 실제 연락 경로까지 확인되어 **선택된 템플릿으로 검수 가능한 초안을 완성한 N명**이다. 1~3점·미평가·연락 불가·중복 대상이나 미완성 초안을 숫자에 섞지 않는다.

## 2. 한 사람을 처리하는 기본 단위

한 최초 연락은 아래 네 기록이 이어진 한 단위다.

1. **creator/contact:** 누구에게 어느 실제 주소로 보낼지.
2. **collaboration:** 이번 새 제안 한 건의 목적·현재 조건·후속 업무.
3. **outreach template 하나:** 재사용할 도입·가치·ask·보상·follow-up의 기준.
4. **message draft/sent:** 템플릿을 해당 사람에게 개인화한 정확한 원문과 실제 결과.

한 메시지에 여러 템플릿을 섞어 템플릿 효과를 알 수 없게 만들지 않는다. 가장 적합한 **기준 템플릿 하나**를 고르고 `outreach_template_id`로 연결한다. 일부 문구를 다른 자료에서 참고했더라도 기준 템플릿은 하나이며, 실제 원문과 선택·변경 이유는 draft payload에 남긴다.

템플릿은 메시지의 출발점이지 발송본이 아니다. 개인화된 정확한 원문은 반드시 `message_draft` 또는 `message_sent`의 body에 별도로 저장한다.

## 3. 시작할 때 읽을 것

1. 팀원의 목표, 요청 수, 대상 시장·관객, 기간, 허용 예산·보상 범위, 반드시 포함하거나 피할 내용.
2. 연결된 plan이 있으면 목표·남은 예산·기간과 팀원이 감당할 수 있는 예상 회신·협상량. plan이 없으면 임의로 만들거나 최근 plan을 자동 연결하지 않는다.
3. 최신 `research_result`의 원 요청, 플랫폼 조사 범위, 후보별 점수 이유·분석 기간·표본·source refs·contact ref, 제외/미확인과 cutoff.
4. `list gtm_creators`의 연락 점수, 주제·관객, 플랫폼별 최근 활동과 engagement 분포, 연락 상태, 열린 협업, 자료 최신성, 과거 비용·콘텐츠·제품 결과.
5. `list gtm_outreach_templates`의 active 템플릿과 채널·언어·대상·캠페인·ask·offer·version·사용 결과. 응답률의 분모·관측 기간·thread 결측도 함께 본다.
6. 제품의 실제 가치·한계와 관련 캠페인/포맷. 제공하지 않는 기능, 승인되지 않은 혜택, 보장할 수 없는 결과를 만들지 않는다.

모든 `refresh_fields`가 초안을 막는 것은 아니다. 빠진 정보가 대상 선정, 개인화 근거, 연락 경로, 제안 조건을 바꿀 수 있을 때만 필요한 필드를 Research 절차로 갱신한다.

## 4. 대상 gate

### 4.1 Research 인계 조건

최종 대상마다 다음이 있어야 한다.

- 최신 `outreach_score` 4 또는 5와 사람 언어의 점수 이유
- 요청의 필수 조건과 관객 적합성 근거
- 동일인 플랫폼 지도와 최근 활동일
- 최근 콘텐츠 분석 기간·표본, 중앙값·분포·추이·outlier 의존
- 실제 전송 가능한 contact item의 ref·channel·address·status·as_of·source
- 조사 cutoff와 개인화에 사용할 정확한 source refs

프로필 URL, 댓글 경로, `requires_manual_reveal`, `manual_route_only`, 공개 멘션만 가능한 계정은 곧바로 개인 이메일/DM 연락처로 간주하지 않는다. 점수나 핵심 근거가 없거나 오래됐으면 추측하지 않고 Research로 돌린다.

### 4.2 중복·중단·관계 확인

다음을 확인한 뒤에만 템플릿을 고른다.

- `do_not_contact`, invalid/bounced/revoked와 중단 근거
- 같은 목적의 열린 collaboration과 최신 draft/sent/reply
- 다른 팀원이나 Agent가 준비·발송한 동일 제안
- 새 회신이 들어와 기존 대화를 이어가야 하는지
- 이전 견적·합의·실제 협업 결과와 현재 유효성
- 남은 예산과 회신이 왔을 때 팀원이 처리할 수 있는 양

이미 회신이 있거나 무응답 follow-up이라면 [Manage_Collaborations.md](Manage_Collaborations.md)에서 같은 collaboration을 이어간다. 같은 사람에게 플랫폼만 바꾸어 최초 제안을 중복 발송하지 않는다.

## 5. Outreach Template 선택

### 5.1 먼저 후보 템플릿을 좁힌다

기존 템플릿을 다음 순서로 읽는다. 이는 자동 점수표가 아니라 선택에 필요한 evidence filter다.

| 확인 항목 | 판단 |
| --- | --- |
| 상태·버전 | 실제 최초 연락은 검토가 끝난 active 템플릿을 기준으로 한다. template version이 비어 있거나 의미가 불명확하면 먼저 정리한다. |
| 채널 | 실제 contact의 email/Instagram DM 등과 맞아야 한다. 채널이 다르면 메시지 길이·제목·CTA도 달라지므로 그대로 전용하지 않는다. |
| 언어·시장 | 상대가 실제 사용하는 언어와 시장 맥락에 맞는지 확인한다. |
| 대상 프로필 | 템플릿의 target creator profile과 이번 크리에이터의 관객·주제·관계가 맞는지 본다. |
| 캠페인·포맷 | 연결된 캠페인/기본 포맷이 이번 요청과 맞는지, 없으면 캠페인 비종속 템플릿인지 확인한다. |
| ask·offer | 원하는 회신 행동과 승인된 보상 전략이 이번 단계에 맞는지 본다. 단가를 물어야 하는데 확정 금액 템플릿을 쓰지 않는다. |
| 과거 결과 | 유사 cohort의 발송·회신·합의·게시·성과와 결측을 참고한다. 응답률 하나로 자동 선택하지 않는다. |

### 5.2 정확히 하나를 선택한다

남은 후보 중 Agent가 현재 사람·목표·채널·관계·제안 복잡도에 가장 자연스러운 하나를 선택한다. 선택 결과에는 다음을 남긴다.

- `selected_template_id`, template ref, `template_version`
- 이 사람에게 이 템플릿이 맞는 이유
- 가장 가까운 대안 템플릿과 선택하지 않은 이유
- 템플릿에서 유지한 핵심 계약과 개인화하면서 바꾼 부분

과거 응답률은 soft evidence다. 표본이 적거나 채널·대상·보상 조건이 다르면 우월한 템플릿으로 단정하지 않는다. 팔로워 수나 연락 점수로 템플릿을 기계적으로 매칭하지 않는다.

### 5.3 맞는 템플릿이 없으면 먼저 추가한다

아래를 모두 만족할 때 새 `gtm_outreach_templates` 행을 만든다.

- 이번 한 사람만이 아니라 비슷한 대상·채널·목적에 다시 쓸 수 있다.
- 기존 템플릿의 단순 개인화로 해결되지 않는 실제 차이가 있다. 예: email과 DM, 첫 관심 확인과 상세 rate 문의, 승인 금액 제안과 rate-first 문의.
- `channel`, `language`, `target_creator_profile`, `opening_template`, `value_proposition`, `ask`, `offer_structure`, `usage_notes`, `template_version`이 실제 선택에 충분하다.
- 개인 이름·특정 게시물·개별 단가처럼 후보 전용 정보가 템플릿에 들어가지 않는다.
- 승인되지 않은 금액·혜택·성과 보장을 포함하지 않는다.

기존 템플릿이 있는데 표현만 조금 다르게 쓰고 싶다는 이유로 새 템플릿을 늘리지 않는다. 일회성 변경은 draft의 개인화와 `strategy_snapshot`에 남긴다.

### 5.4 템플릿 변경과 버전

- 오탈자·설명 보완처럼 의미가 바뀌지 않는 수정은 같은 행을 갱신할 수 있다.
- 대상, ask, 보상, 약속, CTA처럼 비교·해석을 바꾸는 수정은 새 template version으로 만든다. 이미 발송에 사용된 템플릿의 의미를 덮어쓰지 않는다.
- 모든 draft/sent payload에 사용 당시 template ref·version과 선택 이유를 복제한다. 템플릿이 이후 바뀌어도 당시 판단을 재구성할 수 있어야 한다.
- 템플릿을 새로 만들었다는 사실만으로 active로 간주하지 않는다. 필드 완결성, 제품 사실, 보상 경계, 채널 적합성을 검수한 뒤 상태를 정한다.

## 6. 템플릿을 개인화된 발송본으로 바꾸기

메시지를 쓰기 전에 후보별 결정을 사람 언어의 `strategy_snapshot`으로 정리한다.

| 결정 | 판단 질문 |
| --- | --- |
| 개인화 근거 | 어떤 최근 콘텐츠·시리즈·관객 근거를 왜 언급하는가? URL·기준일이 있으며 평소 주제를 대표하는가? |
| 인사·도입 | 관계와 채널에 맞게 누구인지 얼마나 소개하고 어디서 본 근거를 연결할까? |
| 가치 연결 | Harper의 어떤 실제 가치가 이 사람의 관객과 자연스럽게 이어지는가? |
| 콘텐츠 각도 | 어떤 경험·질문·포맷으로 풀면 이 사람의 기존 콘텐츠 안에서 낯설지 않은가? |
| ask | 이번 첫 회신에서 꼭 필요한 한 단계는 관심 확인, rate/media kit, 일정 확인 중 무엇인가? |
| 보상 | 유료 여부, 승인 금액/범위 또는 rate 문의 중 무엇을 정확히 말할 수 있는가? |
| CTA | 상대가 가장 적은 부담으로 취할 수 있는 다음 행동 하나가 무엇인가? |
| 리스크 | 답변 전까지 약속하면 안 되는 금액·일정·권리·성과는 무엇인가? |

최종 메시지는 상대가 다음을 이해하게 한다.

1. 누가 왜 연락했는지.
2. 왜 다른 사람이 아니라 자신인지.
3. 어떤 콘텐츠나 협업을 함께 검토하고 싶은지.
4. 자신의 관객에게 어떤 실제 가치가 있는지.
5. 유료 여부와 조건이 지금 어디까지 정해졌는지.
6. 지금 무엇 하나를 답하면 되는지.

이름만 바꾼 문장, 근거 없는 친밀감, 과도한 칭찬, 제품 장문 소개, 여러 CTA, 오래된 바이럴 한 건의 과장은 완료가 아니다. 문장 수와 인사말을 고정 규칙으로 만들지 않고 채널과 관계에 맞게 쓴다.

## 7. 보상·가격

- 확인된 최근 견적·이전 합의·승인 한도가 있으면 기준일과 적용 범위를 확인한다.
- 현재 단가를 모르면 확정 가격처럼 쓰지 않는다. 첫 연락의 목적이 rate discovery라면 유료 협업임을 밝히고 단가 또는 미디어킷을 묻는다.
- 고정·성과·혼합·제품/비금전 혜택은 실제 가능한 조건일 때만 언급한다.
- 산출물·사용권·수정·통계 제출·지급 시기 중 미정인 항목은 무엇이 회신 후 협의인지 분명히 한다.
- 초안의 가격 문구는 약정이 아니다. 상대 회신과 팀원 승인 뒤 collaboration terms와 cost에 확정한다.

## 8. 실행 → 점검 → 개선 → 재실행

### 8.1 실행 1 — 초안 만들기

1. 대상·contact·중복 gate를 통과한다.
2. 기존 템플릿을 읽고 정확히 하나를 선택한다. 없으면 재사용 가능한 템플릿을 만든 뒤 선택한다.
3. collaboration을 생성하거나 같은 목적의 기존 draft collaboration을 재사용한다.
4. 선택 이유와 정확한 원문을 `message_draft` version 1로 저장한다.

### 8.2 점검 — 본문과 기록을 함께 본다

아래 질문에 하나라도 답할 수 없으면 아직 발송 준비가 아니다.

- 실제 contact와 선택한 template channel이 일치하는가?
- 템플릿의 target/ask/offer가 이번 사람과 목적에 맞는가?
- 개인화 문장이 source로 확인되며, 평소 콘텐츠를 대표하는가?
- 제안할 콘텐츠 각도가 상대 채널 안에서 자연스러운가?
- 유료 여부와 미정 조건이 오해 없이 드러나는가?
- 첫 회신에서 필요한 CTA가 하나로 읽히는가?
- 제목과 본문, 링크, 서명, 수신 주소가 일치하는가?
- draft body, template ID/version, 선택 이유, source refs가 DB에 모두 남았는가?
- 실제로 보내지 않았는데 `message_sent`나 발송 완료로 표시하지 않았는가?

### 8.3 개선 — 원인을 맞는 원본에서 고친다

- 특정 사람의 문구·각도 문제면 새 `message_draft` version을 만든다.
- 같은 템플릿을 여러 사람에게 쓸 때 반복되는 문제면 template의 새 version을 만든다.
- 제품 사실이 문제면 Business Context를, 후보 근거가 문제면 Research를 갱신한다.
- 구조·권한·중복 문제면 data model/Connections를 고친다.

이전 draft를 덮어쓰지 않는다. 무엇을 왜 바꿨는지 새 payload에 `revision_reason`으로 남긴다.

### 8.4 실행 2 — 재선택·재작성·재검수

개선된 템플릿 또는 같은 템플릿의 교정된 사용 방식으로 다시 선택 판단을 수행한다. 새 정확한 원문을 다음 `draft_version`으로 저장하고 같은 체크리스트를 다시 통과한다. 실제 발송은 그 다음 별도 단계다.

## 9. DB 기록 계약

### 9.1 단일 대상 초안

한 크리에이터의 한 새 제안은 `gtm_collaborations` 한 건과 append-only `message_draft` 활동들로 기록한다. draft payload에는 최소한 아래 의미를 둔다.

```json
{
  "recipient": {
    "creator_id": "...",
    "contact_ref": "...",
    "address": "..."
  },
  "channel": "email",
  "subject": "실제 제목",
  "draft_version": "initial-2",
  "document_version": "2.3",
  "template_selection": {
    "selected_template_id": "...",
    "selected_template_ref": 5,
    "template_version": "1.0",
    "reason": "이 사람·채널·ask에 선택한 이유",
    "closest_alternative": "선택하지 않은 대안과 이유"
  },
  "personalization_source_refs": ["..."],
  "strategy_snapshot": "왜 이 사람에게 무엇을 어떤 조건으로 제안하는지",
  "test_dimensions": {
    "opening": "의도적으로 선택한 도입",
    "ask": "이번 회신에서 요청한 한 단계",
    "compensation": "유료 명시·rate 문의",
    "cta": "이메일 회신"
  },
  "revision_reason": "이전 버전이 있다면 변경 이유",
  "delivery_status": "draft_only_not_sent"
}
```

`test_dimensions`는 작성 시점의 실제 의도를 사람 언어로 남긴다. 문구를 나중에 키워드나 정규식으로 재분류하지 않는다. 템플릿과 draft가 바뀌면 새 활동을 추가하고 이전 원문을 보존한다.

이메일 발송 연결에서는 같은 정확한 초안을 `gtm_outreach_dispatches`에 준비한다. 이 행은 수신자, 발신자, template ID/version, 제목·본문, 팀원 승인자·승인 시각, 예약 시각, Gmail message/thread ID, 시도·오류·발송·회신 시각을 보존한다. Agent의 일시적인 판단을 저장하려는 테이블이 아니라, 외부 발송을 중복 없이 실행하고 사후에 정확한 원문과 승인·provider 결과를 재구성하기 위한 실행 원장이다.

### 9.2 여러 명의 batch

여러 명을 한 번에 준비하면 `outreach_batch_planned` 활동 한 건에 요청 원문·목표·수량·가정, research result/cutoff, 선택된 creator/collaboration/contact, 후보별 template ref/version/선택 이유, 제외·Research 반환, 예산·팀 대응량과 문서 버전을 남긴다. 각 정확한 메시지는 대상별 `message_draft`에 따로 저장한다.

## 10. 실제 발송과 회신

현재 운영 배포본의 전용 발송·수신 동기화는 아직 미연결이다. 소스에는 아래 이메일 흐름이 구현·검증되어 있으며 [Connections.md](Connections.md)의 외부 계정 설정과 운영 배포가 끝난 뒤 활성화한다. DM은 계속 별도 수동 범위다.

1. Agent가 `gtm_outreach_prepare`로 사람별 수신자, `harper@matchharper.com` 발신자, active email template의 당시 version, 정확한 제목·본문을 준비한다. 준비는 발송이 아니다.
2. 팀원은 `Outreach Review`에서 한 행씩 최종 제목·본문·예약 시각을 읽고 `Approve & Send`, `Request Revision`, `Skip` 중 하나를 선택해 저장한다. 셀 선택만으로는 보내지 않는다. `Request Revision`이면 Agent가 같은 dispatch의 제목/본문을 `revise`로 고쳐 `ready_for_review`에 다시 올리고 이전 초안과 요청은 활동 이력에 남긴다.
3. 승인 시 do-not-contact, 최신 contact 상태, template active 상태, 동시 수정 버전을 다시 확인한다. 실패하면 보내지 않고 행에 오류를 표시한다.
4. 승인된 행만 Gmail로 발송한다. Gmail 결과가 불명확하면 고정 RFC Message-ID를 먼저 검색한 뒤 같은 logical send를 복구한다. 실제 성공 뒤에만 provider message/thread ID·시각·정확한 원문으로 `message_sent`를 만든다.
5. 5분 복구 작업이 전송 중 중단되거나 일시 실패한 행을 최대 횟수 안에서 이어간다. 팀원이 Sheet를 열어둘 필요가 없다.
6. Gmail push와 history cursor가 inbox 회신을 수집한다. 원 수신자·thread/reply header가 일치하는 dispatch에만 `message_received`를 추가하고 같은 Gmail message ID를 중복 저장하지 않는다.
7. 새 회신은 Slack에 한 번 알리고 같은 DB 활동에 알림 결과를 남긴다. 이후 협상과 다음 행동은 [Manage_Collaborations.md](Manage_Collaborations.md)가 맡는다. 무응답은 거절이 아니다.

팀원이 다른 메일 앱에서 수동 발송했다면 실제 원문·목적지·시각·증빙을 받은 뒤 `message_sent`로 기록한다. 자동 발송과 동일한 메시지를 별도로 수동 발송하지 않는다.

## 11. 템플릿과 메시지에서 학습하기

- 기본 분모는 한 collaboration의 최초 실제 `message_sent`다. draft·follow-up은 신규 outreach 분모에 넣지 않는다.
- 회신은 같은 thread에서 관측된 최초 `message_received`이며 분석 cutoff를 먼저 정한다.
- reply, 긍정적 관심, rate/media kit 제공, 합의, 게시, 제품 전환은 별도 결과다.
- template ref/version, 채널·시장·관객·기존 관계, 정확한 원문, 선언한 전략, 보상·시점과 downstream 비용·성과를 함께 본다.
- thread ID가 없거나 수동 발송/회신 기록이 누락되면 템플릿 화면의 response rate가 완전하지 않을 수 있음을 표시한다.
- 표본과 결측을 보이고 관찰 상관을 인과로 과장하지 않는다. 다음 batch의 가설은 soft evidence이며 새 후보의 맥락과 팀원 조건을 덮어쓰지 않는다.
- 반복 가능한 방법 변화는 문서·템플릿 새 version에, 특정 batch의 관찰과 채택 방향은 `review_adopted` 활동에 남긴다.

## 12. 결과 보고

팀원에게 아래 순서로 보고한다.

1. 요청 해석: 목표, 대상, 수량, 보상, 가정과 실제 발송 권한.
2. 입력 검증: research result·cutoff, 준비 완료 / Research 반환 / 제외 수.
3. 대상별 표: creator, 점수 이유, 플랫폼·반응, 선정/반대 근거, contact, 선택 template ref/version과 이유, 제안·보상, collaboration ref.
4. 대상별 정확한 메시지 원문과 draft version.
5. 점검 결과와 1차→최종 버전에서 달라진 점.
6. DB의 template/collaboration/draft/sent ref와 실제 완료 범위.
7. 다음 행동: 실제 발송에 필요한 승인·수동 처리, 담당·기한, 회신 후 이어갈 문서.

## 13. 품질 실패와 중단 조건

다음은 완료가 아니다.

- 대상에게 맞는 템플릿을 검토하지 않고 즉석 문구만 작성함
- 여러 템플릿을 섞고 기준 template ID/version을 남기지 않음
- 채널·언어·대상·ask·offer가 다른 템플릿을 response rate만 보고 선택함
- 한 사람 전용 문구를 재사용 템플릿으로 추가하거나 유사 템플릿을 무한히 늘림
- 사용된 템플릿의 의미를 덮어써 과거 발송을 재구성할 수 없게 함
- Research 근거·실제 contact·중복 확인 없이 템플릿부터 적용함
- 이름만 바꾼 메시지, 근거 없는 개인화, 승인되지 않은 약속, 여러 CTA
- 정확한 원문은 있지만 template ref/version·선택 이유·source refs가 없음
- draft와 sent를 혼동하거나 불명확한 외부 결과를 성공으로 기록함
- 요청한 N명을 낮은 점수·연락 불가·미완성 초안으로 채움

실제 발송 권한이나 연결이 없으면 검수된 draft까지 완성하고 정확히 그 상태에서 멈춘다. 필수 정보가 부족하면 준비된 대상은 끝까지 완성하고 부족한 대상만 Research 반환 또는 팀원이 결정할 구체적 선택지로 보고한다.
