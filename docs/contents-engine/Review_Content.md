# Review_Content.md

버전: 1.0 · 적용일: 2026-09-16 · 상태: active (범위는 Connections 기준) · 관리: 아래 관리 역할

[AGENTS.md](AGENTS.md)를 먼저 읽는다. 이 문서는 해당 작업의 입력 파악부터 분석·실행·저장·결과 확인까지 소유한다. 외부 발송·게시·송금·플랫폼 API 연결은 문서만으로 생기지 않는다.

## 업무 계약

- **호출 상황:** ‘초안 확인해’, ‘어디를 고치라고 할까’, ‘수정본이 게시 가능한지 봐’. 브리프 작성과 다른 독립 요청이므로 분리한다.
- **입력·근거:** 실제 파일·대본과 버전, 전달한 브리프, 제품 사실, 합의 범위·사용권, 이전 피드백.
- **소유하는 방법:** 원본 열람 → 브리프/주장/CTA·링크/표시·권리 확인 → 목표와 표현의 적합성 검토 → 수정 위치와 이유를 묶어서 제시 → 수정본 확인 → 실제 검수 결과 기록. 필수 수정과 선택 제안을 구분해 왕복을 줄인다.
- **저장:** contents의 검수 진행·해당 파일 버전과 activities의 구체적인 피드백·확인 근거. 새로운 계약 범위의 수정은 Manage_Collaborations.md에서 협의할 수 있게 표시한다.
- **재검수:** 검수한 파일·브리프·게시 문구 버전을 고정한다. 내용이 바뀌면 이전 검수 결과가 자동으로 새 버전에 적용되지 않는다. 변경된 범위와 관련된 검토를 수행하고 미변경 부분을 불필요하게 다시 작업하지 않는다.
- **완료:** 게시 가능한 버전 또는 제작자가 바로 고칠 수 있는 피드백이 남는다. 이미 해결한 피드백을 반복하지 않고 필수 문제가 미해결이면 확인 상태를 명확히 한다.
- **예외·경계:** 열람하지 못한 영상·음성은 검수했다고 쓰지 않는다. 창의적 판단을 단어 점수표로 바꾸지 않는다. 검수 완료는 실제 게시 완료가 아니다.
- **관리:** 콘텐츠 담당이 놓친 오류·불필요한 수정·후속 성과를 보고 기준을 다듬는다.

## 현재 도구로 끝까지 수행하기

[Connections.md](Connections.md)의 Supabase plugin 및 `gtm_workspace` 호출 계약을 사용한다. 칼럼은 [data-model.md](data-model.md), 제품 사실은 [Business_Context.md](Business_Context.md), 계산은 [measurement.md](measurement.md)가 원본이다.

1. 콘텐츠의 고정 brief_version과 제출 파일 버전, 캠페인/포맷 기준, 실제 제품 주장을 읽는다. 제출물을 실제로 열어 검토하고 확인 불가이면 그 부분을 남긴다.
2. 목표 전달·사실 정확성·CTA/링크·합의 조건을 기준으로 필요한 수정과 그 이유를 작성한다. 취향을 필수 조건으로 만들지 않고 수용 가능한 대안도 설명한다.
3. `content_review` 활동에 검토한 파일/브리프/문구 버전, 결과와 수정사항을 남긴다. 콘텐츠 production_status 및 실제 수정 업무를 같은 batch로 반영한다.
4. 수정본을 받으면 새 파일 버전을 확인한다. 이전 버전의 검수로 자동 통과시키지 않는다. 현재 게시 가능한 정확한 버전과 남은 사항을 보고한다. 피드백 발송 여부는 증거가 있을 때만 기록한다.

## 중단·충돌·완료 확인

같은 쓰기를 재시도할 때 request_id와 본문을 유지한다. row_version 충돌은 최신 행을 읽고 실제 변경을 재판단한다. 애매한 외부 결과를 성공으로 기록하지 않는다. 외부 입력을 기다리면 기존 원장의 실제 할 일·담당·기한·재개 조건을 남긴다. 결과에는 사용한 문서 버전, 저장한 원장 ref/ID, 실제 완료 범위와 남은 사항을 포함한다.
