# Contents Engine — 업무에서 바로 찾을 수 있는 구조

상태: 구조 검토안, 미구현 · 기준일: 2026-09-16 · Agent는 [AGENTS.md](AGENTS.md)부터 읽는다.

## 설계의 기준

팀원이 떠올린 일에서 기록까지 한 번에 찾아갈 수 있어야 한다. 기본 업무는 **크리에이터, 협업, 콘텐츠** 세 곳에서 한다. 캠페인·포맷은 재사용할 기준이고 집행 계획은 예산과 목표를 묶는다. Agent도 같은 이름으로 조회한다.

기존 설계는 거래·시도·소재·게시·링크를 모두 독립적인 업무 개념으로 만들었다. 당시 조건과 결과를 보존하려는 목적은 유지하되, 독립적으로 탐색할 필요가 없는 개념을 합친다.

| 떠올린 질문 | 갈 곳 | 같은 상세 안에서 확인할 것 |
| --- | --- | --- |
| 이 사람 누구지? 다시 맡길 만한가? | 크리에이터 | 계정·관객 근거·연락처·현재 협업·관련 과거 결과 |
| A에게 뭐라고 보냈지? 돈은 얼마나 약속했지? | 협업 | 대화·조건·진행·담당자·할 일·콘텐츠·비용 |
| 그 영상 준비됐나? 어디에 올라갔고 효과가 있었나? | 콘텐츠 | 브리프·파일·플랫폼별 게시·링크·비용·성과·다음 방향 |
| 어떤 주제/포맷을 반복할까? | 캠페인·포맷 | 가이드와 같은 조건의 콘텐츠 결과 |
| 이번 100만 원은 어디에 쓰고 얼마나 남았나? | 집행 계획 | 목표·예산·연결 협업·콘텐츠·공통 비용·결과 |

## 기본 원장 여섯 개

| 원장 | 한 행의 단위 | 기본 목록의 칼럼 |
| --- | --- | --- |
| 크리에이터 `gtm_creators` | 사람 또는 제작 팀 | 이름, 활동 지역·언어·주제, 플랫폼별 계정, 팔로워, 최근 365일 게시 수·최근 게시, 관객 근거, 연락 경로·상태, 진행 협업·다음 업무, 최신 채택 방향, 자료 최신성 |
| 협업 `gtm_collaborations` | 한 크리에이터와 진행하는 거래·협업 문의 | 크리에이터, 집행, 진행, 조건 요약, 약정/지급액, 콘텐츠 수, 최근 회신, 다음 행동·담당·기한 |
| 콘텐츠 `gtm_contents` | 한 계정에 게시할 콘텐츠 한 건 | 제목, 제작자, 캠페인, 포맷, 플랫폼, 제작·게시 진행, 예정/게시일, 비용, 성과, 측정 상태, 다음 방향·행동 |
| 캠페인 `gtm_campaigns` | 재사용하는 주제·가치 제안 | 이름, 대상·가치 설명, 가이드, 관련 콘텐츠·성과 |
| 포맷 `gtm_formats` | 재사용하는 표현 방식 | 이름, 표현 설명, 가이드·예시, 관련 콘텐츠·성과 |
| 집행 계획 `gtm_plans` | 목표·예산·기간이 있는 집행 | 이름, 목표·타깃, 기간, 예산·약정·지급·가용액, 진행·결과 |

기본 목록은 선택과 행동에 필요한 칼럼만 제공한다. 원문·조건·이력은 행을 펼쳐 읽는다. ‘최근 회신’, ‘관련 결과’, ‘지급액’은 연결 기록에서 계산하므로 팀원이 다시 입력하지 않는다.

집행을 정하기 전에 들어온 문의도 협업에 기록한다. 집행은 비용을 약속하거나 제작에 착수하기 전에 연결한다. 목록의 ‘다음 행동’은 대표 업무이며, 같은 건에 통계 제출·지급 확인 등 여러 일이 남아 있으면 각각 담당·기한을 가진다. ‘오늘 할 일’은 이 업무들을 모아 보여주므로 별도 장부를 작성하지 않는다.

## 다섯 개였던 실행 원장은 두 개로 합친다

| 이전 개념 | 바뀐 저장 위치 |
| --- | --- |
| engagements | 협업: 연락부터 조건 합의·제작 의뢰·정산까지 |
| attempts | 별도 원장 제거. 콘텐츠의 당시 조건·실행 이유·이전 콘텐츠 연결 |
| content_items | 콘텐츠의 브리프·파일·사용권·버전 |
| publications | 콘텐츠의 플랫폼·계정·게시 URL·게시일·상태 |
| tracking_links | 콘텐츠의 추적 링크 목록. 개별 링크마다 고정 ID 유지 |

**협업과 콘텐츠 두 개는 유지한다.** 한 번 합의한 거래에 콘텐츠 여러 개가 들어갈 수 있기 때문이다. 전부 한 행으로 합치면 콘텐츠마다 같은 계약금과 협의 내용을 반복하게 된다.

콘텐츠는 게시할 플랫폼 계정별 한 행이다. 같은 영상을 두 플랫폼에 게시하면 두 행이지만, 기본 화면은 자동 생성한 콘텐츠 묶음 번호로 함께 보여줄 수 있다. 펼치면 각 게시일·링크·성과가 나온다. 묶음 번호를 만들기 위해 별도 업무 원장을 만들지는 않는다. 묶음에서도 서로 다른 조건·미측정 값을 숨기지 않는다.

공통 브리프·파일은 같은 버전을 참조하고 플랫폼별 CTA·일정은 각 행에서 관리한다. 공통 브리프를 바꾸면 적용할 미게시 콘텐츠를 함께 갱신하며, 이미 게시된 콘텐츠에는 당시 사용 버전을 남긴다. 같은 게시물을 유료로 증폭한 경우에는 그 콘텐츠에 조건 변경과 추가 비용을 붙인다.

## 한 건이 흐르는 방식

가상 예시: A에게 영상 하나의 제작과 두 플랫폼 게시를 30만 원에 맡긴다.

1. A의 크리에이터 상세에서 과거 협업과 현재 계정 자료를 본다.
2. 협업 한 건을 만들고 대화·30만 원 조건·다음 행동을 붙인다.
3. 콘텐츠 두 행을 만든다. 같은 영상 파일을 참조하고, Instagram/TikTok 게시·링크·성과는 각 행에 둔다.
4. 비용 한 건 30만 원을 협업에 기록한다. 플랫폼별 원가가 필요하면 두 콘텐츠에 배분하며 총비용은 30만 원을 유지한다.
5. 콘텐츠 결과에서 당시 타깃·브리프·기간과 함께 Retry/Scale을 검토한다. 팀이 채택한 이유와 다음 행동을 해당 행에 연결한다.
6. 다시 맡기면 새 협업·콘텐츠를 만들고 이전 기록과 당시 채택한 리뷰를 연결한다. 과거 결과를 새 단가나 가이드로 덮지 않는다.

## 내부에 남길 반복 기록

기본 원장만으로 모든 기록을 한 행에 넣지는 않는다. 계정·대화·성과 시점·비용은 각각 반복되므로 내부 저장을 분리한다. 업무 데이터는 **6개 기본 원장 + 4개 보조 기록 = 총 10개 테이블**로 설계한다. 실행 인프라의 로그·권한 저장은 기존 구조를 확인한 뒤 필요한 물리 저장을 별도로 확정한다.

| 보조 기록 | 별도 저장하는 이유 | 팀원이 보는 위치 |
| --- | --- | --- |
| 계정 `gtm_accounts` | 여러 플랫폼의 안정 ID·관측 연결·Harper 계정 배포 | 크리에이터 상세의 계정들, 콘텐츠의 게시 계정 |
| 활동 `gtm_activities` | 메시지·견적·확정 리뷰 등 실제 발생 기록이 누적됨 | 해당 크리에이터·협업·콘텐츠의 타임라인 |
| 지표 이력 `gtm_metric_snapshots` | 현재값과 게시 후 7일/14일 결과를 구분 | 같은 상세의 기준일·성과 추이 |
| 비용 `gtm_costs` | 보수·도구비·시간·선금·잔금 등을 중복 없이 관리 | 협업/집행의 비용 내역, 콘텐츠의 배분 원가 |

SQL 테이블을 숨기는 것만으로 단순해지지는 않는다. 화면과 Agent의 첫 조회가 관련 요약과 원문 진입점을 함께 반환해야 한다. 다른 내부 원장으로 옮겨 다녀야만 질문에 답할 수 있다면 조회 구조를 고친다.

‘크리에이터를 더 찾아’처럼 집행 없이 수행한 조사도 결과 참조 번호로 찾을 수 있다. 조사 기준·진행 위치·후보·미확인 사항·비용을 활동 기록과 결과 파일에 남기므로 다른 팀원이나 Agent가 같은 기준으로 이어갈 수 있다.

## Markdown과 도구의 역할

Markdown은 Agent용이다. 최상위 AGENTS.md가 데이터 지도·문서 지도·공통 경계를 안내하고, Agent는 맡겨진 작업의 문서를 읽는다. Research_Creators.md는 조사·분석·저장·보고를, Outreach_Creators.md는 오늘의 대상 선정·메시지·요청된 발송 확인을 끝까지 책임진다. 데이터/운영/측정 문서만 읽고 작업 방법을 조립하게 하지 않는다.

전체 작업 문서의 범위·입출력·완료 조건·관리 계획은 [Document_Plan.md](Document_Plan.md)에 있다. 1차의 13개 작업 문서와 2차의 2개 문서를 기획했으며, 실행 본문은 아직 작성하지 않았다. 공통 참고는 제품 사실·데이터·측정·연결·공통 실행을 소유한다. Notion은 문서 편집 장소로 사용할 수 있으며 업무 데이터의 별도 복사본을 만들지는 않는다.

Supabase는 원장이다. Sheets는 정규화된 DB 구조를 그대로 복사하지 않고 여러 원장을 조인한 운영 화면이다. Creator Directory에서 전체 후보와 허용된 원본 필드를 다루고, Connected Creators에서 연결 이후 누적 협업·콘텐츠·비용·결과를 보고, Outreach Log에서 실제 메시지 흐름을 확인한다. 시트는 주기적으로 DB를 다시 읽으며 조인 화면은 읽기 전용이다. Metabase는 선택적 분석 화면이다. 화면에서 이름·설명·표시 순서를 바꾸는 일과 데이터 의미·권한을 바꾸는 일을 구분한다. 매일 사용하는 진입점에서 관련 화면으로 바로 연결한다.

## 유지할 학습 구조

이 구조가 보존할 것은 당시 실행 조건 → 같은 기간의 실제 결과와 비용 → 채택한 방향·이유 → 다음 콘텐츠다. 이를 위해 별도 ‘시도’나 ‘판단’ 메뉴가 필요하지 않다. 콘텐츠·협업·집행 상세 안에서 확인하고 고친다.

Pickle 참고 파일에서 가져올 아이디어는 포맷별 결과와 Decision/Next Action의 연결이다. 해당 파일의 구조를 그대로 복제하거나 수식으로 사업 판단을 고정하지 않는다. 숫자가 비어 있는 것과 실제 성과가 0인 것을 구분하고, 모든 화면이 같은 비용 정의를 사용한다.
