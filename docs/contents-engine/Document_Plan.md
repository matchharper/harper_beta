# 작업별 Agent 문서 기획

상태: 문서 구성·책임 범위 검토안 · 기준일: 2026-09-16

이번 산출물은 앞으로 만들 작업 문서의 범위·내용·입출력·관리 방식이다. 아래 15개 파일의 실행 본문을 모두 작성한 상태가 아니며 DB·도구·자동화도 미구현이다. 파일 이름만 정하거나 빈 파일을 만들지 않고 각 문서의 작성 계약을 이 기획서에 정의한다. 업무 데이터는 6개 기본 원장과 4개 보조 기록, 총 10개를 유지한다.

## 1. 무엇을 기준으로 문서를 나누는가

**팀원이 독립적으로 맡길 수 있고 완료 결과가 구별되는 작업 하나에 문서 하나를 둔다.** 문서에는 그 작업의 요청 해석부터 조사·판단·기록·결과 확인까지 담는다. ‘조사 방법은 여기, 분석 방법은 저기, 저장 방법은 또 다른 작업 문서’처럼 하나의 일을 조립하게 하지 않는다.

단가·국가·플랫폼·예산·신규/기존 여부·기간만 달라지면 같은 문서가 처리한다. 조회·수정·발송 같은 일반 도구는 공통으로 쓰고 문서가 늘었다고 전용 API·테이블·중간 판단 상태를 추가하지 않는다. 설명에 쓰는 요청 예시는 범위를 한정하거나 키워드 기반 분기를 구현하기 위한 것이 아니다.

작업 문서가 소유하는 것은 작업의 방법이다. 데이터의 칼럼 뜻·지표 공식·제품의 실제 사실·사용 가능한 도구는 공통 참고 문서가 소유한다. 각 작업 문서는 필요한 참고의 위치와 사용 시점을 직접 안내하고, 자체 업무 절차를 참고 문서에 떠넘기지 않는다.

Business_Context에는 실제 확인한 내용을 넣으며 목표로 하는 미래 기능을 제공 중인 기능으로 쓰지 않는다. 가격·혜택·사용 예시 등의 출처와 기준일, 관리 담당을 둔다. Connections에는 실제 연결 상태와 호출 계약, 새 팀원/Agent의 연결·권한 확인 방법, 최소 읽기/쓰기 확인 절차를 기입하며 토큰·비밀번호는 넣지 않는다. 플랫폼 이름만 나열하고 모두 자동화할 수 있다고 가정하지 않는다.

캠페인별 설명과 포맷별 제작 가이드는 DB에서 연결한 버전 있는 콘텐츠 문서다. 이는 실행 지침 D01~D15와 다른 자료다. 특정 캠페인마다 Research/Outreach 문서를 복제하지 않는다. 실제 실행 결과는 해당 원장·활동·보고서 참조에 남기고 매 실행마다 새 플레이북을 만들지 않는다.

## D01. Research_Creators.md

- **호출 상황:** ‘학생 대상 후보를 더 찾아’, ‘지난 목록의 관객·활동을 다시 확인해’, ‘이 계정들 중 누가 적합한지 조사해’. 신규 검색과 지정 목록 재조사는 같은 업무의 입력 차이다.
- **입력·근거:** 목적·시장·언어·관객·플랫폼·원하는 규모, 조사 시간/비용 한도. 기존 gtm_creators/gtm_accounts, 관련 gtm_collaborations/gtm_contents 결과, 이전 검색 brief·출처를 읽는다. 연결할 집행이 명확하면 조건을 가져오고 결론을 바꾸는 미확인 조건만 확인한다. 집행 없이 조사할 수도 있다.
- **소유하는 방법:** 기존 목록 재사용 → 검색 경로 선택 → 후보 수집·동일인 확인 → 최근 콘텐츠·관객·연락 경로 조사 → 목적에 대한 적합성과 불확실성 분석 → 저장 → 추가 조사할 대상과 한계 보고. 검색어·소스·기준일을 남겨 ‘같은 기준으로 더’에 이어갈 수 있게 한다.
- **분석 내용:** 플랫폼별 팔로워·정확한 최근 365일 게시 수와 기간·최근 게시·대표 콘텐츠·가능한 범위의 조회 분포, 콘텐츠 유형과 표현, 활동 지역/언어, 관객 지역/대상의 근거, 연락 경로, 확인된 조건·과거 협업 결과를 연결한다. 팔로워만으로 수익을 예상하지 않고 이번 목적에 어떤 근거가 유리하며 무엇을 더 확인해야 하는지 설명한다. 단가·전환 근거가 없으면 기대 리턴을 확정 수치로 쓰지 않는다.
- **갱신:** operations의 최신성 기준과 실제 출처 조건을 적용해 이번 작업에 필요한 자료만 다시 수집한다. 지난 조사의 결과 ref와 범위를 재사용하고 수집 실패·미확인을 기존 관측과 구분한다.
- **저장:** 확인된 소개·활동 지역·언어·주제·연락처는 gtm_creators, 플랫폼별 handle/URL·최근 게시·관객 근거는 gtm_accounts, 팔로워와 정확한 최근 365일 게시 수는 metric_snapshots에 기간·기준일·출처와 함께 남긴다. 집행이 없는 조사도 activities의 최종/부분 조사 결과 한 건에 목적·검색 범위/진행 위치·확보한 creator IDs·제외/미확인 요약·비용과 기준일을 연결해 다시 찾을 수 있게 한다. 이번 목적의 추천 이유는 그 결과에 남기며 사람의 영구 등급으로 쓰지 않는다.
- **완료:** 중복을 구분한 후보, 연락 가능 여부, 최근 콘텐츠와 관객 근거, 분석 이유, 미확인 정보, 사용 자원과 탐색 범위가 확인 가능하다. 단순 프로필 URL 목록은 완료가 아니다.
- **예외·경계:** 요청 수를 못 채우면 실제 확보 수와 한계를 보고한다. 비공개 관객 정보를 추측으로 채우지 않는다. 선정 자체가 연락이나 지출을 뜻하지 않는다. 오늘 보낼 최종 목록은 D04가 책임진다.
- **관리:** 발굴 담당이 검색 성과·중복·후속 협업 결과를 보고 개선한다. 소스 접근 방식이 바뀌면 Connections도 함께 검토한다.

## D02. Plan_Marketing.md

- **호출 상황:** ‘100만 원으로 학생 마케팅 준비해’, ‘미국에서 1만 명을 확보하려면 어떻게 해야 해’, ‘다음 달은 누구에게 얼마씩 맡길까’. 예산 고정과 목표 고정은 같은 계획 업무다.
- **입력·근거:** 무엇을 몇 명 얻으려는지, 기간·시장·예산·팀 시간·이미 약속한 비용. gtm_plans, 관련 후보·견적·과거 결과, 캠페인·포맷 가이드를 읽는다.
- **소유하는 방법:** 목표 정의 → 근거와 빈칸 확인 → 신규/재협업 후보 및 조합 비교 → 응답·합의·게시·전환 단계별 필요 수량과 비용 산정 → 일정·팀 대응량 검토 → 실행 가능한 선택지 제안. 시장 근거가 약하면 파일럿을 포함한다.
- **저장:** plans의 목표·한도와 계획 문서 버전. 계획 시점의 후보·조건·데이터 기준일·가정·예측 범위를 보존한다. 연락을 실행할 후보가 정해지면 D04에 같은 plan ID를 넘긴다.
- **완료:** 누구에게 어떤 캠페인·포맷·조건으로 접근할지, 필요한 연락/게시 수와 비용·기간·예상 결과 범위, 아직 확인할 정보가 결정 가능한 형태다. 목표 달성을 보장하는 숫자를 만들지 않는다.
- **예외·경계:** 후보가 부족하면 D01, 제작 방향이 없으면 D03의 해당 작업을 필요한 만큼 수행한다. 원래 목표와 예산을 다시 해석하거나 새 집행을 중복 생성하지 않는다. ‘계획만’이면 외부 실행까지 진행하지 않는다.
- **계획 변경:** 이미 진행 중인 약정·지급·게시 예정과 남은 팀 용량을 반영한다. 예산을 줄이거나 타깃을 바꿀 때 기존 의무를 없어진 것으로 계산하지 않는다. 당시 채택 계획은 보존하고 새 버전의 변경 이유·영향 범위를 남긴다.
- **관리:** 집행 책임자가 당시 예측과 실제 결과를 비교해 개선한다. 전환 공식은 measurement.md가 소유한다.

## D03. Develop_Campaigns_Formats.md

- **호출 상황:** ‘어떤 주제로 풀면 좋을까’, ‘잘된 영상 방식을 다른 사람에게도 맡기게 정리해’, ‘뉴스레터용 포맷도 만들어’. 기존 가이드 수정도 포함한다.
- **입력·근거:** 제품의 실제 가치·타깃 문제, 기존 캠페인·포맷, 원본 콘텐츠·결과·채택 리뷰. 성공 사례가 없으면 검증 전 가설임을 표시한다.

- **집행 미정:** 조사·메시지 초안은 알려진 조건으로 진행하고 모르는 조건을 표시한다. 집행이 여러 개면 최근 집행을 임의로 적용하지 않는다. 비용 약정·제작 착수 전 필요한 집행과 허용 범위를 확인하며, 초안을 만들기 위해 임의 예산이나 무의미한 집행을 생성하지 않는다.

- **관리:** Outreach 담당이 회신·합의·반송·팀 시간·메시지 품질을 함께 보고 개선한다.

## 4. 하나의 요청에서 문서가 연결되는 방법

AGENTS.md는 요청의 목적과 현재 상태를 보고 주 작업 문서를 고른다. 키워드 classifier나 고정 실행 그래프를 만들지 않는다. Agent는 현재 작업 문서가 소유한 일을 끝까지 수행하고, 독립적인 다른 업무가 필요할 때만 그 문서를 읽는다. 문서를 읽는 것 자체가 새 Agent 생성이나 별도 작업 실행을 뜻하지 않는다.

| 오늘 필요한 일 알아서 진행 | D12 | 기존 권한 안에서 해당 작업 문서 사용 | 처리 결과와 팀원 판단 필요 항목 |
| 집행을 정하기 전에 들어온 협업 문의 | D05 | 필요한 근거 D01, 약정 전에 집행 확인 | 미분류 협업·원문·후속 업무 |
| 두 플랫폼용 영상의 공통 브리프 수정 | D06 | 파일 변경 시 D07, 실제 게시 확인 D08 | 공유 문서의 새 버전과 적용된 콘텐츠 |
| 같은 협업에서 통계 제출·잔금 확인이 동시에 필요 | D12 | 요청된 답변 D05, 지급 대사 D10 | 해당 협업의 두 후속 업무 |
| 예산 축소 또는 진행 중 타깃 변경 | D02 | 기존 약속 변경 D05, 비용 정정 D10 | 이전/새 계획과 남은 실제 의무 |
| 조사만 마친 뒤 다른 Agent에게 같은 조건으로 더 찾기 요청 | D01 | 저장된 조사 ref를 읽어 이어서 수행 | 이전·후속 조사 결과와 신규 후보 |

작업을 이어갈 때 집행·크리에이터·협업·콘텐츠 ID, 확정한 조건, 근거/문서 버전, 남은 질문, 실제 허용 범위만 넘긴다. 동일 자료를 새로 조사하거나 새 거래를 중복 생성하지 않는다. 원래 요청이 초안이면 후속 문서를 읽었어도 발송 권한으로 확대하지 않는다.

작업을 시작할 때는 관련 집행·진행 중 연락·자료 기준일·다음 업무의 짧은 요약과 상세 참조부터 읽는다. ‘현재 집행’이 불명확하면 초안에서 가정을 표시하고 외부 약속 전에만 필요한 대상을 확정한다. 첫 실행에 기존 성과가 없으면 검증 전 가정과 확인할 일을 제시한다. 빈 데이터 때문에 가짜 성과를 만들거나 모든 작업을 중단하지 않는다.

### 다른 문서를 읽어도 원래 작업의 책임은 유지한다

피드백 전달은 D07, 브리프 전달은 D06, 처음 제안은 D04가 해당 작업의 결과로 확인한다. 모두 같은 일반 발송 도구와 대화 기록을 사용한다. D05는 대화 전체를 운영하거나 가격·권리·일정의 의미를 다시 협의할 때 읽는다. 단순 발송을 위해 D05로 넘겼다가 다시 원래 문서로 돌아오는 순환은 만들지 않는다. 읽은 문서 수와 무관하게 실제 메시지는 한 번만 보낸다.

‘수정 요청을 보내고 수정본도 확인해’처럼 외부 응답을 기다리는 작업은 한 실행에서 끝났다고 보고하지 않는다. 이번에 확인한 결과와 대기할 외부 입력, 다음 담당·기한을 원래 원장에 남긴다. 다음 실행은 같은 기록에서 이어간다. 실제 작업 재개 위치와 부작용 이력은 실행 기반이 보존하며 LLM의 중간 생각을 업무 상태로 저장하지 않는다.

## 6. 모든 작업 문서가 갖출 작성 계약

각 문서는 요청 예시만 모으지 않고 다음을 갖춘다.

1. 작업의 목표·책임 범위·완료 기준. 준비와 실제 실행 결과를 구분한다.
2. 요청에서 얻을 입력과 기존 기록에서 스스로 채울 입력. 꼭 필요한 질문과 가정 가능한 항목을 구분한다.
3. 읽을 원장·공통 참고·원본 근거와 최신성. 무엇을 먼저 읽고 언제 상세를 더 읽을지 정한다.
4. 조사·판단·실행·검증·기록의 전체 방법. 정성 판단은 목적과 증거 기준으로 설명하고 키워드 분기/점수표로 대체하지 않는다.
5. 실제 도구 사용과 저장 위치, 중복 실행·중단·동시 변경의 처리. 실행 단계에서 확인된 도구 이름을 명시한다.
6. 출력물과 후속 작업이 바로 쓸 수 있는 조건. 정확한 ID·본문·파일 버전·금액 등 실행에 필요한 값은 구조화하고 이유는 짧은 자연어로 둔다.
7. 자료 부족·권한 없음·실패·지연·조건 변경 때 남길 기록과 다음 행동. 부분 결과도 완료로 과장하지 않는다.
8. 문서 담당·버전·적용일·변경 근거와 실제 사용 결과의 확인 방법.

길이를 맞추기 위해 모든 문서에 같은 내용을 반복하지 않는다. 작업별 필수 판단과 실패 처리는 본문에 두고 공통 정의는 정확한 참조로 연결한다. ‘필요시 다른 문서 참고’만 쓰고 정작 누가 끝까지 책임지는지 비워 두지 않는다.

## 7. 문서가 오래되거나 모순되지 않게 관리하기

| 변경되는 것 | 고칠 원본 | 영향을 확인할 곳 |
| --- | --- | --- |
| 제품 기능·가격·혜택·브랜드 주장 | Business_Context | D02~D07의 관련 출력과 기존 미발송/미게시 초안 |
| 칼럼·조회·저장 계약 | data-model | 해당 필드를 읽고 쓰는 작업 문서·화면 |
| 목표 지표·귀속·비용 계산 | measurement | D02, D09~D11, D14와 관련 보고서 버전 |
| API 범위·권한·비용·도구 이름 | Connections | 그 연결을 쓰는 작업, 예약 실행·실패 복구 |
| 자료별 갱신 우선순위·운영 주기 | operations, 실제 연결 설정은 Connections | D01/D09/D12와 예약 작업. 문서만 바꿔 예약이 변경됐다고 보지 않음 |
| 조사·선정·협의·검수 방법 | 해당 작업 문서 | 같은 작업의 다음 실행과 직접 연결되는 출력 |
| 새 작업 문서 추가·통합 | AGENTS와 이 문서 | 요청 선택 경로·중복 책임·기존 링크 |

담당자는 역할로 먼저 정하고 운영 시작 시 실제 팀원에게 배정한다. 문서는 draft/active/retired 상태와 버전·담당·적용일·변경 요약을 가진다. 대화 중의 임시 아이디어가 active 지침을 자동으로 덮어쓰지 않는다. 일반적인 내용 수정과 예산/권한 변경은 별개다.

실행에는 사용한 문서/공통 정의의 버전을 남긴다. 실행 중인 작업이 수정된 지침을 조용히 섞지 않도록 한다. 잘못된 제품 주장·발송 권한 등의 중대한 변화가 생기면 영향을 받는 미실행 부분부터 다시 확인한다. 이전 결과와 당시의 기준은 보존한다.

Notion은 편집 장소로 사용할 수 있으며 Agent는 발행된 Markdown과 참조를 읽는다. 문서마다 수정 가능한 원본은 하나다. 팀원이 같은 설명을 여러 곳에서 고칠 필요가 없게 한다. 실행 결과의 문제에서 지침 변경까지 근거를 연결하고, 지침을 늘리는 대신 먼저 맥락·도구 결과·기존 기준이 부족했는지 확인한다.

## 8. 작성·검증 순서

- **기반:** AGENTS, Business_Context, 데이터 계약·측정 계약, 실제 Connections를 정리한다. 불명확한 실제 기능/권한을 문장으로 메우지 않는다.
- **첫 연락까지:** D01·D02·D04·D05를 작성해 후보 조사부터 대상/메시지·회신까지 이어지는지 확인한다. D13은 초기 이관과 정리부터 필요하다.
- **제작부터 회수까지:** D03·D06·D07·D08·D09·D10을 작성해 가이드·검수·게시·성과·비용이 같은 기록으로 이어지는지 확인한다.
- **반복 운영:** D11·D12를 작성해 이번 결과가 다음 협업과 오늘 할 일에 반영되는지 확인한다. 여기까지가 1차이며 단순 리포팅으로 끝내지 않는다.
- **2차:** D14·D15를 추가하고 D02/D11의 예측·비교를 고도화한다. 기본 학습 기록과 지침 정정은 1차부터 유지한다.

본문 완성의 기준은 새 Agent가 AGENTS와 해당 문서·지정 참고만으로 작업을 수행하고, 다른 Agent가 같은 ID와 남은 일을 받아 이어갈 수 있는가다. 실제 실행이 불가능한 도구/권한/자료는 명시하고 실행 가능으로 표시하지 않는다. 예시는 문서 책임을 점검하는 데 사용하며 별도 runtime 분기를 만들지 않는다. 이번 기획에서 실제 실행 검증이나 평가를 수행한 것은 아니다.

문서 active와 전체 시스템 준비 완료는 다르다. 문서별로 실제 가능한 범위(조회/준비, 외부 실행), 확인한 도구·연결, 담당·버전·검증일을 AGENTS의 문서 지도에 함께 표시한다. 초안 준비가 검증됐어도 발송·지급까지 가능한 것으로 표시하지 않는다. 실행 기반이 부족하면 그 기능을 켜기 전에 delivery-plan.md의 조건을 충족한다.
