# Settle_Costs.md

버전: 1.2 · 적용일: 2026-09-18 · 상태: active (범위는 Connections 기준) · 관리: 아래 관리 역할

[AGENTS.md](AGENTS.md)를 먼저 읽는다. 이 문서는 해당 작업의 입력 파악부터 분석·실행·저장·결과 확인까지 소유한다. 외부 발송·게시·송금·플랫폼 API 연결은 문서만으로 생기지 않는다.

## 업무 계약

- **호출 상황:** ‘이번 비용 정리해’, ‘이번 주 지급할 건 준비해’, ‘선금 보냈으니 반영해’, ‘API 비용과 우리 시간까지 계산해’.
- **입력·근거:** 실제 합의·변경·취소 조건, 산출물 이행, 청구서·지급 근거, 도구/모델 사용량과 팀 시간, 기존 비용·지급·배분.
- **소유하는 방법:** 누락 비용 확인 → 예상/약정/발생/지급 구분 → 통화·세금·환율의 확인된 기준 적용 → 지급 기한과 증빙 정리 → 공통 비용 배분 → 요청된 지급 준비 또는 허용된 재무 실행·대사 → 미지급/환불/미확인 표시.
- **저장:** costs와 해당 지급·배분 내역, 관련 협업/집행의 다음 행동. 확정한 계약 조건의 의미 자체를 임의로 바꾸지 않는다.
- **완료:** 총비용과 실제 지급액, 남은 의무, 비용 배분 근거가 맞아야 한다. 연락 실패·공통 도구·팀 시간도 빠짐없이 포함하되 추정과 실제를 구분한다.
- **미완성 비용:** 도구 청구나 팀 시간이 아직 없으면 미확인 항목을 남기고 알려진 비용만으로 완성된 CPA를 발표하지 않는다. 환불과 약정 감액은 서로 다른 근거·기록으로 처리한다.
- **예외·경계:** 지급 목록 생성은 송금 완료가 아니다. 이미 보낸 지급을 다시 실행하지 않는다. 분쟁·추가 보수는 Manage_Collaborations.md에서 조건부터 확인한다. 모든 세무 처리를 Agent가 추측하도록 만들지 않는다.
- **관리:** 비용/정산 담당이 미지급·누락·대사 차이와 입력 부담을 보고 개선한다.

## 현재 도구로 끝까지 수행하기

[Connections.md](Connections.md)의 gtm_api 호출 형식을 사용한다. 칼럼은 [data-model.md](data-model.md), 제품 사실은 [Business_Context.md](Business_Context.md), 계산은 [measurement.md](measurement.md)가 원본이다.

1. 협업 조건과 비용·지급 증빙, 집행 한도, 실제 작업 시간을 읽는다. 누락 도구 비용·공통 작업도 찾되 미확인은 null로 남긴다.
2. `save gtm_costs`로 expected_amount/agreed_amount/incurred_amount와 currency/base_currency/fx_rate/fx_source를 구분한다. labor_minutes/hourly_rate/measurement_basis로 팀 시간을 기록한다. 비용 항목에 지급액을 다시 더하지 않는다.
3. 실제 지급 증빙이 있을 때만 `patch_item payments`를 쓴다. item에는 id, kind=payment/refund, amount, occurred_at, source_ref, provider, connection_ref, external_id를 넣는다. 잘못 기록된 지급은 덮어쓰지 말고 별도 정정 근거/환불로 대사한다.
4. `patch_item allocations`에서 content_id 또는 plan_id와 share, 배분 근거/버전을 기록한다. 합계는 1이며 여러 비중 변경은 items 배열 한 번으로 적용한다. 직접 plan_id 소속 비용은 그 집행에 한 번만 귀속하고 콘텐츠 배분은 해당 집행 안에서 한다.
5. `get gtm_plans`에서 발생·약정·순지급·가용 예산, 협업에서 미지급과 기한을 재확인한다. 송금 연결은 미설정이며 지급 준비나 장부 기록을 실제 송금으로 보고하지 않는다.

## 조회수 연동 크리에이터 가격 전략

가격 전략은 `fixed` 또는 `base_plus_views` 버전으로 관리한다. 후자는 `기본 업로드 비용 + (측정 조회수 ÷ N × M)`을 원 단위로 반올림한다. 기본비·측정일수·N·M은 새 실험 버전에서 바꿀 수 있다. 연락 전에 최근 측정 콘텐츠 최대 10개의 조회수 중앙값으로 사람별 예상 비용을 계산하고, 이력이 없으면 비용을 지어내지 않고 근거 부족으로 표시한다.

콘텐츠에 전략을 지정하면 그 버전의 네 값과 통화·계산법을 스냅샷으로 고정한다. 측정일이 지난 뒤 수집한 조회수를 기준으로 비용 한 건을 만들고 콘텐츠에 100% 배분하며, 같은 콘텐츠·버전의 재실행은 같은 비용을 재사용한다. Slack 알림은 지급 예정 금액이 장부에 확정됐다는 뜻이며 실제 송금 완료가 아니다. 실제 지급은 별도 증빙을 `payments`에 기록해야 한다.

## 측정일 비용 확정과 Slack 보고

1. 조회수 연동형은 측정일 이후 처음 성공한 성과 스냅샷의 조회수를 사용한다. `기본비 + 조회수 ÷ N × M`을 원 단위로 반올림한다. 고정비는 게시 확인 시 조회수 없이 확정한다.
2. 확정된 비용에는 사용한 가격 전략 스냅샷과 조회수·좋아요·작성자 제외 댓글·각 기준 시각과 출처를 남긴다. 계산에 쓰지 않은 좋아요와 댓글도 당시 결과를 설명하는 근거로 보존한다.
3. 비용 행과 성과 결론이 준비된 뒤 콘텐츠 한 건당 Slack 메시지 한 건을 보낸다. 재시도는 같은 비용 ID를 사용하며 이미 성공 기록이 있으면 다시 보내지 않는다.
4. 메시지는 내부 ref·ID·수집기 이름·긴 계산식을 빼고 다음 네 줄을 기본으로 한다. 이모지는 최대 두 개만 쓴다.

```text
💰 크리에이터명 · <콘텐츠 링크|콘텐츠 제목>
조회 85,484 · 좋아요 290 · 댓글 1,314
지급 예정 577,420원
🟢 좋음 · 조회수와 댓글 반응이 비교 대상에서 강함
```

5. `지급 예정`은 확정된 발생 비용이며 송금 완료가 아니다. 실제 지급 증빙이 들어오면 Sheet의 `Paid Amount`가 별도로 갱신된다. 성과 결론을 만들 근거가 부족하거나 모델 처리가 실패하면 임의 판정을 만들지 않고 `판단 보류 · 확인할 근거가 부족함`으로 보낸다.

## 중단·충돌·완료 확인

같은 쓰기를 재시도할 때 request_id와 본문을 유지한다. row_version 충돌은 최신 행을 읽고 실제 변경을 재판단한다. 애매한 외부 결과를 성공으로 기록하지 않는다. 외부 입력을 기다리면 기존 원장의 실제 할 일·담당·기한·재개 조건을 남긴다. 결과에는 사용한 문서 버전, 저장한 원장 ref/ID, 실제 완료 범위와 남은 사항을 포함한다.
