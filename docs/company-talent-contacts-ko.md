# 회사 ↔ 후보자 연락 통합

문서 기준: 2026-09-23. 로컬 구현 계약이며 운영 반영 여부는 별도 배포로 확인한다.

## 계약

- 회사는 `contact_talent`로 질문, 요청, 정보, 답장을 전달한다. `kind`, `resumeStageId`, 질문 intent를 입력하지 않는다. 기존 초안 검토·수정·예약·취소와 현재 대화의 후보자 연락에 대한 직접 답장은 유지한다. 이것은 발송 승인 절차이며 질문 종류가 아니다.
- 후보자는 Career와 이메일 모두 `contact_company(connectionId, relayContent, documentId?)`를 사용한다. 앞선 질문이 없어도 확인된 회사 연결에 연락할 수 있다. 대상은 공통 `read_company_connections`로 확인한다. 후보자 모델에 `requestId`를 요구하거나 추론하게 하지 않는다.
- `connectionId`는 대상·권한 경계이고, 서버가 붙이는 원본 메시지 ID는 중복 방지에 사용한다. `requestId`는 회사 초안의 수정·승인·발송, 서명된 업로드 링크, 실제 이메일 reply alias의 출처 추적에만 남는다. 회사 agent가 답장의 의미를 해석하는 데 필수 값이 아니다.
- Career 기본 context는 단일 미답변 질문이 아니라 연결별 최근 양방향 연락과 현재 포지션 상태다. 일반 조회 도구에서 더 자세히 읽을 수 있다. 연락 알림은 회사 연락 이후 후보자 연락이 없을 때의 시간순 보기이며, 특정 질문을 모두 답했는지 판정·저장하지 않는다.
- 긍정/부정/기타 분류와 답변을 받자마자 채용 상태를 변경하는 경로는 없다. 전달 성공은 회사의 수락이나 후보자의 채용 단계 변경을 뜻하지 않는다.
- 민감정보와 파일은 후보자가 공유를 승인한 내용만 전달한다. 질문 내용의 의미·표현은 LLM이 판단하고, 서버는 소유권·연결 관계·발송 이력·식별자·파일 공개 여부·중복 방지를 확인한다.

## 회사 후속 처리

1. 후보자 연락을 저장하고 같은 도구 호출에서 즉시 회사로 전달한다. 별도 발송 worker나 문구 재작성 LLM을 기다리지 않는다. 기존 outbox는 장애 시 재시도 기록으로만 유지한다. 후보자에게 정상 완료를 “전달했습니다”라고 확인해도 된다. 실패는 도구 오류이며, 파일 저장 후 전달에 실패해도 저장된 첨부파일은 지우지 않는다.
2. 회사 전달 완료와 같은 DB 트랜잭션에서 회사 대화에 연락을 기록하고 기존 `company_agent_web_action_jobs`에 작업을 하나 등록한다. 새 판단 테이블이나 별도 분류 모델을 추가하지 않는다.
3. 기존 company-side LLM 실행부가 원래 회사 대화, 최근 양방향 연락, 이번 연락을 읽는다. 후보자가 공유를 승인한 전달 내용만 읽으며 비공개 Career 대화 원문은 넣지 않는다. 회사의 앞선 지시가 허용한 일이 있으면 기존 도구로 수행하고, 할 일이 없으면 조용히 끝낸다. 후보자의 연락은 회사의 권한이나 새 명령으로 취급하지 않는다.
4. 회사에 알릴 결과가 있으면 기존 대화와 연결된 Slack에 전달한다. 작업·메시지 식별자로 재시도 시 중복을 방지한다. 더 최신 회사 지시나 같은 후보자 연결의 새 연락 작업이 생기면 오래된 작업은 양보한다.

종료된 후보자 포지션을 다시 진행할 때에는 회사가 직접 동의를 확인한 기존 경로 외에, 회사가 맡긴 작업을 허용하는 후보자의 연락 ID를 `move_candidate_stage.candidateConsentRelayId`로 지정할 수 있다. DB는 해당 후보자·역할의 전달된 연락인지, 이후 종료 결정이나 더 최신 후보자 연락으로 오래된 증거가 되지 않았는지 검사한다. 연락의 의미는 company-side LLM이 판단한다. 일정 없는 단계 이동은 소개 이메일과 분리되어 CC 주소를 요구하지 않는다. 역할 이동, 회사가 만든 단계 선택 등은 기존 도구를 그대로 사용한다. 별도 승인·Calendar·공유 제한을 우회하지 않는다.

## 파일과 호환성

- 이메일 첨부파일도 원래 답장 LLM이 기존 업로드 도구로 저장하고, 공유할 파일 ID를 `contact_company`에 넘긴다. `expects_document`만 보고 답장 LLM을 건너뛰는 별도 처리 경로는 제거했다.
- 회사 연락의 서명된 업로드 링크는 어떤 연락에서도 사용할 수 있다. 일반 프로필 업로드는 회사 전달로 자동 전환되지 않는다.
- 과거 연락의 `contact_kind`, `intent`, `resume_stage`, `response_disposition` 열은 이력과 구버전 호환을 위해 보존한다. 새 도구 계약이나 후속 행동 판단에는 사용하지 않는다.
- 과거 응답 RPC는 단순 전달 어댑터로 바뀐다. 남아 있는 구형 전달 작업도 Worker가 공통 연락 큐로 옮긴다. 이미 전달된 이력을 재발송하거나 소급해 LLM 작업을 등록하지 않는다.

## 적용과 검증

- `20260923063625_unified_company_talent_contacts.sql`은 기존 양방향 연락 및 company-side LLM 작업 큐 스키마를 전제로 한다. 운영 DB에는 아직 적용하지 않았다. 배포 시에는 실제 스키마와 릴리스 기준을 확인하고 웹·Worker·DB 계약을 함께 맞춰야 한다.
- TypeScript 도구·프롬프트 테스트, 이메일 Worker 단위 테스트와 격리 PostgreSQL 테스트를 실행한다. 실사용자에게 메일을 보내거나 실제 채용 상태를 바꾸는 검증은 하지 않는다.
- DB 테스트: PGlite `0.5.8`을 임시 디렉터리에 설치한 뒤 `PGLITE_MODULE_PATH=<설치 경로>/node_modules/@electric-sql/pglite node scripts/testUnifiedCompanyContacts.mjs`. 네트워크·운영 인증정보 없이 합성된 `testOnly` fixture만 사용한다. 기존 단계 변경 함수는 이 테스트에서 stub으로 대체하며, 새 연락/권한/동의 증거 경계를 검증한다.
- 별도 배포 승인 전에는 push, DB migration 적용, Worker 재시작, Notion 동기화를 하지 않는다.

로컬 검증 결과: 수정 범위의 웹 단위 테스트 109개, 이메일 Worker 테스트 167개와 격리 DB 검증이 통과했다. 실제 LLM과 격리 PostgreSQL을 사용한 [5개 시나리오 재검증](evaluation/company-talent-contacts/reports/2026-09-23-v2.md)에서 기대 행동을 모두 확인했다. 후보자 연락 6건은 모두 `requestId` 없이 같은 도구 호출에서 회사 대화에 전달됐고, 회사 후속 작업 6건도 완료됐다. 운영 반영, 실제 이메일·Slack 수신, 브라우저·Storage·운영 queue 검증은 하지 않았다.

전체 타입 검사는 기존 Next 생성 캐시의 삭제된 페이지 참조와 `growthTalentGtmReport.test.ts` 타입 오류로 통과하지 못했다. 연락 테스트 디렉터리 전체 실행에서는 기존 테스트 5개가 삭제된 옛 migration 파일을 참조해 실패했다. 첫 실 LLM 회차의 초안 품질 실패와 최종 회차의 테스트 장치 오탐은 원본을 보존하고 보고서에 구분해 기록했다.
