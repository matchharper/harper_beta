Harper 에이전트 자율성 — 설계와 구현 검증

2026년 11월 5일 · 로컬 제품 코드 구현 및 격리 데이터 검증 · 운영 미배포

1–6절은 설계, 7–11절은 당시 구현·평가 기록이다. 최신 원인 조사·구현·실험 수치는 후속 결과 보고서에 정리했다. 사용자의 정정에 따라 질문은 의무가 아니며, 추가 확인의 가치와 적절한 전달을 함께 평가한다. 아래의 이전 실패·성공 기록은 해당 코드와 당시 기준의 결과로 보존한다.

범용 도구를 주고, 누구를 위해 무슨 일을 하는지 분명히 하고, 판단에 필요한 맥락을 이어 준다. 행동은 원본 LLM이 선택한다.

이번 Marketing Manager 사례는 이 구조가 제대로 작동하는지 살펴볼 사례다. “경력 차이를 발견하면 질문하고, 프로필을 고친 뒤 소개하고, 회사가 재질문한다”는 순서를 제품 지침으로 만들지 않는다.

앞선 문서의 조건별 행동표, 긴 소개 절차 프롬프트, 새로운 출처 인자와 상세한 소개문 revision 설계는 제거했다. 변경의 중심을 기존 지시 삭제, 목적 정리, 일반 도구의 가용성, 대화 맥락 연결로 바꾼다.

1 먼저 행동을 좁히는 지시를 뺀다

지금도 역할 불일치를 알아차릴 수 있고 상대 에이전트에게 질문할 도구도 있다. 그런데 특정 경로를 구체적으로 안내하는 문장이 선택을 좁힌다. 이 문장들 위에 반대 지시를 쌓지 않고 원본을 정리한다.

현재 지시 또는 입력 변경 남길 내용
“최초 internal 요청은 저장 → 역할 설명 → 소개 제안으로 시작” 모든 요청의 시작 순서로 읽히는 지시 삭제 비공개 기회 저장과 회사에 자료를 공유하는 소개는 다른 효과라는 계약
“준비를 먼저 요청했으면 준비하고, 아니면 기본 프로필 공유” 준비를 별도 사용자 요청에 종속시키는 문장 삭제 사용자가 명시한 자료 선택과 공유 범위
“소개를 수락하면 contact_company로 수행”을 여러 곳에서 반복 system·handbook·capability·도구 설명의 중복 절차 제거 연락 도구의 대상, 인자, 실제 효과, 필요한 동의
버튼 입력 안의 “Use contact_company …” 다음 행동 명령 삭제 사용자가 어떤 기회와 자료를 선택했는지, 아직 무엇이 실행되지 않았는지
회사의 추가 행동은 먼저 도움을 제안하고 승인받는 것으로 읽히는 지침 기존 위임 안의 자율적 수행을 허용하는 의미로 수정 새로운 채용 결정·지출·공유 범위 확대에 필요한 권한
관계 유형만 보고 “역할을 검토한 뒤 요청했다”고 붙이는 설명 근거 없는 대화 경위 해석 삭제 실제 기록된 추천 제시, 사용자 요청, 회사 Intro 사실

수정 위치: 후보자 메인 지침, 기회 handbook, Career 기능 목록, 도구 설명, 버튼 입력, 회사 지침, 관계 경위.

이미 추천받아 수락한 상황은 실제 추천과 수락 맥락을 주면 된다. 추천받지 않은 Role의 첫 요청에는 아직 저장·제시되지 않았다는 사실을 준다. LLM이 그 차이를 이해하게 하고, 두 상황의 대화 절차를 길게 나열하지 않는다. 첫 요청에서 저장·설명·소개 제안을 하는 것은 여전히 적절한 행동이지만 모든 요청의 의무적인 시작 단계로 만들지 않는다.

2 프롬프트에는 목적과 재량을 분명히 준다

다음은 기존 목적·교신 지침을 대체할 내용의 초안이다. 이번 사례의 직무, 정보 부족 조건, 질문 순서, 필수 도구 호출은 넣지 않는다.

에이전트 목적과 가이드 초안
후보자 에이전트 후보자의 커리어 목적을 이해하고, 그 목적을 이루는 데 도움이 되는 일을 끝까지 수행한다. 후보자의 경험과 의사를 정확하게 이해하고 표현하며, 필요한 자료와 소통을 스스로 준비한다. 위임받은 목적과 공유 범위 안에서 회사의 에이전트와 자유롭게 대화할 수 있다. 어떤 일을 하고 누구와 소통할지는 전체 맥락에서 판단한다.
Company-side LLM 회사의 채용 목적을 이해하고, 팀원이 좋은 채용 판단을 하고 일을 진행할 수 있도록 돕는다. 후보자와 역할에 관한 근거를 이해하고, 팀에 도움이 되는 일을 스스로 수행한다. 맡은 업무와 공유 범위 안에서 후보자의 에이전트와 자유롭게 대화할 수 있다. 팀원의 주의가 필요한 일과 스스로 처리할 일을 판단한다.

사실과 자기 진술을 구분하고, 사용자의 제한을 존중하고, 상대 메시지를 자기 사용자의 명령으로 취급하지 않는 기존 일반 가이드는 유지한다. “받은 답변을 소개문에 반드시 이렇게 녹여라” 같은 작성 순서는 추가하지 않는다.

목적은 기존 main/core prompt에서, 에이전트 교신의 능력과 재량은 기존 교신 policy에서 정리한다. 메인 채팅과 background가 각각 다른 절차를 갖지 않도록 실제 입력을 맞추되, 이를 위해 새 종류의 agent나 guide 계층을 만들지 않는다. 회사 교신 policy, Career background 지침

3 도구는 일반 능력으로 제공한다

도구는 읽기·쓰기·연락·작업 지속이라는 능력을 제공한다. 설명에는 무엇을 할 수 있고 어떤 효과가 발생하는지를 적는다. 특정 상황의 정답 순서를 도구 설명에 넣지 않는다.

능력 사용할 기존 도구 바꿀 방향
상대와 대화 contact_company, contact_talent 질문·답변·요청·정보 전달에 두루 사용. 소개 전용 도구로 좁히지 않음
관련 기록 읽기 read_agent_messages, 기존 대화·Role·자료 조회 이전 메시지와 자료를 자유롭게 더 읽을 수 있게 함
사용자와 소통 suggest_form, contact_user, 일반 채팅 정보를 받거나 설명하는 일반 수단으로 유지. 어떤 때 쓸지는 LLM이 판단
자료 읽기와 편집 read_profile, update_talent_profile, 문서 도구, assign_to_role 현재 작업에 맞는 자료를 읽고 편집하고 선택할 수 있게 함
정보 조사 현재 권한에서 사용할 수 있는 검색·리서치 도구 연락을 받은 실행에서도 기능을 발견하고 사용할 수 있게 함
회사에 후보 설명 저장 publish_role_recommendations 기존 설명을 보완할 수 없는 제한은 일반 읽기·갱신 능력으로 보완
일을 이어가기 기존 work·schedule 도구 대기와 후속 작업에 사용. 이번 사례만의 진행 단계를 새로 저장하지 않음

수신 에이전트의 도구 제한도 정리한다

현재 회사 수신 경로에는 8개 도구를 나열한 별도 eventTools 목록이 있다. 후보자 background도 일반 채팅과 다른 초기 기능 구성을 사용한다. 이 경로가 에이전트를 단순 전달 담당자로 만들지 않도록 한다.

수신 실행에서도 공통 기능 목록과 로더를 사용하고, 현재 실행 주체의 권한으로 사용할 수 있는 일반 도구를 제공한다. 핵심 읽기·연락은 바로 사용할 수 있게 하고, 다른 능력도 존재를 알 수 있고 로드할 수 있게 한다. 도구를 숨기는 기준은 “이 메시지에서는 필요 없을 것 같다”는 업무 추측이 아니라 실제 접근 권한이다.

회사 수신 실행은 팀원 계정과 같은 권한을 갖지 않으므로 eventTools 배열을 지우기만 하지는 않는다. 공통 도구 executor가 현재 Role·후보자 관계의 실행 권한을 받아 처리하도록 연결하고, 지원되는 도구를 공통 registry에서 가져온다. 다른 후보자의 비공개 자료 등 현재 관계 밖의 접근을 열어 주는 변경은 아니다.

수정 위치: 회사 receiver, 회사 도구 실행부, Career 실행부, Career 기능 목록.

이번에 새 도구나 복잡한 자료 체계가 필요한가

양방향 대화, form, 프로필 편집, 자료 배정은 이미 있다. 이 사례를 위한 새 도구는 필요하지 않다.

현재 회사 소개문은 한 번 저장되면 같은 root로 다시 호출해도 새 본문을 무시한다. 이 부분은 기존 설명을 읽고 수정하는 일반 능력으로 확장할 이유가 있다. 다만 재질문의 필수 후속 단계로 만들지는 않는다. 실제 저장 시 기존 동시 수정·멱등성 계약을 재사용하고, 그 계약으로 해결되지 않는 부분만 보완한다. 현재 소개문 저장

자료를 공유할 때 지켜야 하는 소유권·선택 버전·동의 검사는 유지한다. 앞선 안의 별도 출처 인자, 새 자료 승인 체계, 상세한 소개문 revision API는 이번 설계에서 제외한다.

4 수신할 때 이전 대화가 기본으로 이어지게 한다

가장 분명한 context 문제는 새 연락을 받을 때 이전 교신이 기본으로 함께 들어오지 않는 것이다. 회사 receiver는 현재 introductionRootId와 messageId를 함께 넘기며, SQL은 정확히 그 메시지 한 건만 고른다. 후보자 background도 해당 한 메시지를 읽도록 안내한다.

변경 후에는 두 수신 경로가 같은 일반 reader를 사용해 다음 사실을 함께 제공한다.

기본 context 필요한 이유
이번 메시지와 직접 답하는 대상 메시지 무엇에 대한 연락인지 이해
해당 후보자·회사·Role의 최근 양방향 교신 이전 질문·답변·약속을 이어서 이해
관계가 시작된 요청과 현재 사용자 위임 누구의 어떤 목적을 수행 중인지 이해
관련 Role과 실제 공유된 자료 지금 판단할 대상과 근거를 이해
자기 사용자와의 관련 대화, 이미 한 행동과 전달 이미 알고 있는 내용을 다시 묻거나 같은 일을 반복하지 않도록 함
관련 정보의 기존 출처와 시점 자료가 어떻게 생겼는지 이해하고 필요하면 원문을 더 읽음

최근 N개는 기본 입력의 창 크기다. 이번 메시지의 답변 대상과 최초 요청은 그 창 밖이어도 포함하고, 더 오래된 대화는 기존 조회 도구로 이어 읽을 수 있게 한다. 현재 30건 페이지는 오래된 순서이므로 최신 페이지를 먼저 읽도록 바꾸고, 페이지 경계와 원문 참조를 유지한다. 숫자를 대화 횟수나 이력 접근의 상한으로 만들지 않는다.

회사에는 해당 관계에서 공유된 정보와 자기 회사 맥락을, 후보자에게는 자기 기록과 허용된 회사 교신을 준다. 서로의 비공개 대화 전체를 공유하지 않는다. 과거 취소된 소개는 과거 맥락이며 새 실행 권한이 되지 않는다.

출처도 우선 기존 기록을 연결한다

프로필 revision에는 이미 수정 실행의 source가 있고, form 응답에는 원래 질문과 답이 저장돼 있다. 먼저 이 사실을 관련 조회와 후보자 context에 연결한다. read_profile이 지금처럼 revision 번호와 시점만 반환해 출처를 잃지 않도록 한다.

단, 수정 실행의 source가 “보내봐”라면 그것은 수정 경위일 뿐 경력 주장의 근거는 아니다. 에이전트가 원래 대화·form·문서를 읽을 수 있게 하고, 기록이 없으면 없다는 사실을 유지한다. 새로 주장별 신뢰도나 검증 상태를 저장하지 않는다.

회사에 설명할 수 있는 출처는 후보자 에이전트가 기존 연락 도구의 본문으로 전달한다. 그 설명은 다음 수신 context에도 교신 원문으로 남는다. 별도 출처 요약 필드나 이를 작성하는 추가 LLM을 만들지 않는다.

수정 위치: 공통 교신 reader, 교신 조회 SQL, 회사 receiver, 후보자 background, 프로필 reader, 프로필 formatter.

5 이번 변경의 범위를 작게 유지한다

한다 이번 안에서 뺀다
행동을 한 경로로 몰아가는 기존 지시 삭제 정보 부족·경력 불일치·추천 수락별 상세 행동표
기존 목적과 교신 가이드를 짧고 명확하게 수정 질문 → 대기 → 소개를 지시하는 프롬프트
수신 실행에도 공통 범용 도구를 연결 이번 사례 전용 도구·에이전트·guide 계층
관련 교신과 기존 출처를 실제 입력에 연결 새 claim 원장·출처 스키마·검증 상태
기존 도구에서 실제로 빠진 일반 편집 능력 보완 사례를 실행시키기 위한 새 승인·진행 체계
실제 입력과 행동을 보고 품질 확인 특정 도구 순서·질문 횟수·출력 문구를 강제하는 검사

구현은 지시 정리 → 공통 도구 연결 → context 연결을 중심으로 한다. 소개문 갱신처럼 일반 능력의 결손이 확인된 부분만 함께 보완한다. 기존 미커밋 작업은 보존했다. 아래 구현 기록은 로컬 코드에 관한 것이며 운영 배포를 의미하지 않는다.

6 그러면 자율적으로 재질문할 수 있는가

그 결정을 원본 LLM이 내리도록 만드는 것이 이 설계다. 목적을 알고, 상대와 대화할 재량이 있고, 앞선 대화와 자료가 보이며, 일반 도구를 사용할 수 있으면 이번 사례의 질문도 그 안에서 선택할 수 있다.

원하는 질문이 나오지 않았을 때도 곧바로 그 사례의 행동 규칙을 넣지 않는다. 원본 입력에서 목적을 좁히는 지시, 누락된 맥락, 사용할 수 없는 능력이 있는지 먼저 확인한다. 그 조건이 충분한데 판단이 나쁘다면 모델 판단의 문제로 평가한다.

이번 Marketing Manager 사례와 함께, 자료가 충분한 소개·다른 직무의 경력 전환·일정 협의·이미 답한 질문도 살펴본다. 질문이 필요한 상황과 불필요한 상황에서 목적에 맞는 행동을 선택하는지, 상대 답변을 실제로 이해하고 이어가는지를 확인한다. 특정 왕복을 매번 재현해야 성공이라는 기준은 두지 않는다.

이번 사례의 성공은 개별 규칙의 추가가 아니라, 같은 도구·목적·context로 처음 보는 상황에서도 적절하게 일할 수 있다는 증거여야 한다.

7 실제로 바꾼 것

새로운 사례 전용 도구, 주장 검증 상태, 별도 심사 LLM, 응답 재작성기는 추가하지 않았다. 수정한 것은 원본 모델이 받는 목적·도구 계약·사실의 연결이다.

영역 삭제·수정·추가한 내용 원본 위치
후보자 목적 사용자 요청의 즉시 실행을 앞세우던 문장을 커리어 목적과 정확한 준비·표현으로 수정. 소개 권한과 자료 준비 정도를 별개로 판단하게 함. 필요한 답을 기다리는 것도 위임 업무로 인정하고, 충분한 근거가 있으면 불필요한 완벽함을 요구하지 않음 career/prompts/mainPrompt2.ts, rawPrompts.ts
소개 수락 이미 제시된 추천의 수락 맥락을 유지. 첫 탐색 요청과 구별할 사실을 제공. 버튼 입력의 도구 호출 명령과 여러 곳에 중복된 준비·소개 절차를 제거 opportunityFeedbackNote.ts, toolPolicyPrompt.ts, handbooks/opportunitySearch.ts
회사 목적·위임 조사와 판단 정리를 회사 에이전트의 책임으로 명시. 기존 관계 안에서 에이전트 간 대화는 매번 팀원 승인이나 보고가 필요한 일이 아님 org/agent/prompts.ts, capabilities/policies.ts
숨은 전달 압력 background의 미통지 이벤트를 반드시 설명하라는 문장, 기본 연락 policy의 답변 전달·다음 도움 제안 지시 제거. 사건 수신 자체와 실제 알림 의무를 구별 같은 회사 prompt·policy
도구 가용성 회사 receiver의 별도 8개 목록을 공통 registry·loader 기반으로 교체. 현재 Role 서비스 권한에서 조회·공개 조사·교신 사용. 후보자 background에는 교신 기능을 기본 로드 agentContacts/companyReceiver.server.ts, companyScope.ts, org/agent/toolExecution.ts, career/chatTurn.ts
기능 인식 company_contact 개요에 새 소개 시작과 계속되는 교신 모두를 명시. suggest_form은 위임 업무의 질문·검토·답변을 이어 가는 일반 수단으로 설명 career/capabilities/registry.ts, llm/toolDescriptions.ts
교신 context 양쪽 수신 경로에 같은 reader 적용. 후보자·회사·Role의 최신 30건, 현재 메시지·최초 요청·직접 답변 대상 포함. 더 오래된 이력은 일반 조회로 접근 agentContacts/read.ts, store.ts, career/background/server.ts
과거 form 원문 원문 formatter에 끼어 있던 “사용자 사실을 저장·수정하라”는 후속 행동 명령 삭제. 과거 답변을 조회할 때 이미 끝난 작업을 다시 활성화하지 않도록 함 career/forms/format.ts
출처 read_profile에 revision 수정 출처·시점, 소유권을 확인한 원래 사용자 메시지와 form 질문·답변 연결. 수정 출처를 주장 전체의 검증으로 취급하지 않음 career/profiles/store.ts, tools.ts
편집 도구 프로필 row의 실제 필드명을 schema에 공개. 모델이 company/title 등을 추측하며 실패하던 문제 수정 career/profiles/tools.ts
소개문 갱신 회사가 현재 소개문을 읽고 같은 게시물을 갱신 가능. expectedPresentation으로 동시 수정 보호. 공유 자료와 채용 진행 상태는 유지 agentContacts/companyTools.ts, org/agent/tools.ts
게시 효과 게시 자체가 팀에게 검토를 요청하는 전달이라는 효과를 명시. 알림이 없어도 사람에게 공개되는 행위이며 비공개 조사 메모 저장이 아님 회사 tool·policy

회사 비공개 대화와 후보자의 비공개 원문 전체를 상대에게 넘기지는 않는다. 후보자 에이전트가 자기 원문을 읽고, 공유 권한 안의 설명을 일반 교신 본문으로 전달한다. 새 source 필드나 출처 요약 LLM은 없다.

8 반복 실행에서 드러난 중요한 원인

아래 순서는 코드 조사와 실제 입력·출력을 보고 판단한 중요도다. 통제된 대규모 A/B 실험으로 기여율을 측정한 순위는 아니다.

순서 원인 실제 실행에서 확인한 영향
1 성공의 의미가 ‘요청을 바로 처리하고 전달하기’에 가까웠음 준비가 명시적으로 요청되지 않았다는 이유로 AI 엔지니어 프로필을 그대로 보냄. 회사도 background·연락 policy의 전달 지시를 따라 불확실성을 팀에 넘김. 목적 문장뿐 아니라 실제 함께 주입되는 지침을 제거해야 했음
2 수신 LLM에게 대화의 연속성과 사실의 출처가 충분히 연결되지 않았음 한 메시지·최종 프로필만 보면 새로 받은 자기 진술인지, 예전 자료인지 판단하기 어려움. 원래 form 답변과 revision을 읽을 수 있게 하자 후보자 에이전트가 출처와 증빙 부재를 설명함
3 기능이 있어도 일부 경로에서 발견하거나 정확히 쓰기 어려웠음 별도 제한 목록, 새 소개가 잘 보이지 않는 기능 개요, 프로필 row 필드가 비어 있는 schema가 실제 행동을 막거나 잘못된 불가능 판단을 유발함
4 게시를 저장으로, 알림만 사람에게 전달하는 행위로 읽을 여지가 있었음 질문을 보낸 뒤 회신 전에 공개 카드를 게시함. 게시 자체가 팀에게 평가를 전달하는 행위라고 계약을 고친 뒤 최종 2회는 회신 전 게시하지 않음. 기존 소개문 갱신 결손도 보완

이 변경만으로 모든 실행이 동일한 질문을 선택한다는 뜻은 아니다. 같은 근거를 보고도 회사 모델이 직접 조사할지, 불확실성을 설명하고 팀에 넘길지는 여전히 평가해야 하는 판단 품질이다.

9 검증 방법과 경계

  • 실제 사용 모델: Career gpt-6.1-sol / high, Company google/gemini-3.8-flash. 별도 평가용 모델로 대체하지 않았다.
  • daniel@matchharper.com과 실제 Wonderful 운영 자료는 변경하지 않았다. 같은 경력 차이를 가진 합성 후보자·Role·form 답변·프로필을 격리 DB에서 생성·수정했다.
  • 프로필 수정·자료 선택·공유 snapshot은 실제 PostgreSQL 함수와 제품 executor로 확인했다. 에이전트 간 전달·회사 게시·사용자 연락은 기록용 경계로 대체해 외부 발송을 막았다. 실제 모델 호출은 실행했고 provider 입력과 전체 출력을 보관했다.
  • 별도 로컬 PostgreSQL 통합 검사는 교신 저장·페이지·권한·게시 갱신·철회·재실행·이메일 중복 방지를 실행한 뒤 transaction을 rollback했다.
  • 실제 회사·후보자 수신 queue와 사람에게 도착하는 이메일·Slack까지 검증한 것은 아니다. 브라우저 UI 변경도 없다. 이번 변경은 운영 배포 전 상태다.
  • 입력과 gold는 실행 전에 동결했다. 테스트 환경 결함과 모델 실패를 구별하고, 실패한 결과도 보존했다. 모델 응답의 의미는 별도 심사 LLM 없이 전체 출력으로 직접 검토했다.

평가 정본과 재실행 명령은 평가 README에 있다. 아래 결과는 이 작은 합성 사례 집합의 관측이며 운영 성공률 추정이 아니다.

10 실제 관측 결과 — 성공과 미해결 구분

후보자 준비와 출처 이용, 회사의 자율 질문·회신 후 전달을 실제로 확인했다. 마지막 수정 후 2회 모두 회사가 회신 전에 게시하지 않았다. 다만 전체 왕복에서 질문 범위가 넓어져 후보자에게 새 질문을 보내는 행동이 남았으므로, “양쪽 모두 자기 사용자 연락 없이 종료”까지 안정적으로 달성했다고 판정하지 않는다.

검증한 상황 실제 결과 판정
추천받은 AI 엔지니어가 마케팅 역할 소개 수락 → 과장된 답변 제공 먼저 form 질문. 답변 뒤 실제 프로필 수정 → 자료 선택 → 소개 1회. 경력·수치를 자기 진술로 전달하고 외부 증빙 부재도 설명 후보자 준비 흐름 확인
관련 경험이 충분한 후보자 추가 자료를 필수 조건으로 만들지 않고 소개 대조 사례 확인
경험이 없다고 답한 뒤 그대로 진행 요청 경험을 만들지 않고 기존 프로필 그대로 소개 대조 사례 확인
처음부터 질문·수정 없이 그대로 소개 요청 사용자 제한을 지키고 소개 대조 사례 확인
추천받지 않은 공개 Role의 첫 요청 기회를 저장하고 설명·소개 제안. 다음 수락에서 공유. 작업 종료 revision 충돌은 읽기·재시도로 복구 의미상 흐름 확인, 구조 검사에는 복구된 오류 1건 남음
회사에 출처가 빠진 과장된 소개 전달 — 최종 2회 2회 모두 자율적으로 질문만 보내고, 회신 전 게시·팀 알림 없이 대기 핵심 ② 최종 반복에서 확인
이미 받은 답으로 해결 가능한 출처 질문을 후보자에게 전달 원래 form·프로필을 읽어 “소개 준비 중 새로 받은 자기 진술, 외부 증빙 없음”으로 답함. 사용자 연락 0회 핵심 ③의 회신·출처 이용 확인. 회사의 최초 질문 결정은 이 테스트 입력으로 고정했으므로 그 성공 증거는 아님
회사가 위 출처 답변 수신 출처·증빙 부재·확인할 실행 범위를 녹여 팀에 전달. 최종 전체 왕복 2회 중 1회는 전달, 다른 1회는 후보자 측이 추가 설명을 받겠다고 하자 후속 예약만 저장하고 대기 답변 종합 확인, 추가 정보 대기 경로도 관측
실제로 모르는 조직·기여도 세부 질문 알고 있는 범위는 먼저 답하고 후보자에게 추가 질문한 실행이 있음 모든 교신의 무조건 무알림을 성공 기준으로 삼지 않음
일정 교신 / 단순 확인 / 비공개 정보 요청 팀의 실제 일정 판단을 요청 / 추가 발송 없이 종료 / 비공개 정보는 넘기지 않고 거절 범용 동작 대조 확인

같은 v15 입력으로 게시 도구의 의미를 고치기 전·후를 비교했다. “Role inbox에 저장”을 “채용팀 검토를 위해 전달”로 고치고, 알림이 없어도 게시 자체가 팀과의 소통이라는 효과를 분명히 했다. 이것은 실행 계약의 수정이며, 먼저 질문하라는 사례별 절차는 아니다. 작은 반복 실험이므로 안정성 수치로 일반화하지 않는다.

실행 첫 회사 턴 회신 이후
수정 전 1·2 질문과 팀 공개 게시를 같은 턴에 실행 답변을 소개문에 반영하거나 추가 설명 대기
수정 후 1 교신 조회 → 후보자 에이전트 질문. 게시·알림 없음 받은 자기 진술·증빙 부재·조직 구조 미확인을 종합해 게시하고 팀에 알림
수정 후 2 후보자 에이전트 질문만 실행. 게시·알림 없음 후보자 에이전트가 추가 답변을 받겠다고 해 후속 예약을 저장하고 대기. 팀 공개 없음

남은 편차: 최종 2회 모두 회사 질문이 출처 확인을 넘어 공식 직책·보고 체계·업무 비중 등으로 확장됐다. 후보자 에이전트는 기존 답으로 알 수 있는 사실을 먼저 전달했지만, 새로운 세부 정보를 얻기 위해 사용자에게 연락했다. 한 실행에서는 소개용 프로필의 오래된 문구도 수정했다. 출처만 묻는 별도 v14 입력에서는 이미 받은 답만 이용하고 사용자에게 연락하지 않았다.
