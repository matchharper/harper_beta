## 첫 화면 재점검

기존 Harper 채팅 UI의 매칭 결과를 브라우저에서 확인했다. 회사·역할·근무 조건과 추천 근거가 한 카드 안에서 읽혔다. 이전 프리뷰는 같은 카드 컴포넌트를 썼지만 추천 근거를 빼서 역할 이름만 나열됐다. 첨부 랜딩의 왼쪽 대화는 최대 560px이고 최근 결과물과 입력창이 가까이 있다. 이 구조를 적용해 클릭할 결과물과 지원 선택을 대화 흐름 안에 놓았다. [Harper 채팅 UI 프리뷰](http://localhost:3000/career/preview/chat-ui)

| 화면 | 첫눈에 확인할 정보 | 바로 이어가는 행동 | 펼쳤을 때 |
| --- | --- | --- | --- |

## 1. 먼저 바꿔야 할 것

이전 프리뷰는 단순한 화면과 좋은 경험을 혼동했다. 카드와 버튼을 줄였지만, 사용자가 다음에 무엇을 판단하는지는 설계하지 않았다.

- 기회 지도부터 표로 열어 처음부터 비교 작업을 요구했다.
- 추천 방향을 드롭다운에 감춰, 어떤 새로운 가능성이 있는지 발견하기 어려웠다.
- 전체 탐색도 기존 추천 목록과 같은 밀도로 보여, 넓게 탐색하는 이점이 없었다.
- 지원 준비는 접힌 문서 목록이었다. 준비된 결과와 사용자에게 필요한 결정이 구별되지 않았다.
- 숫자를 숨기는 것과 판단 근거를 제공하는 것을 같은 문제로 취급했다.
- 자료와 면접을 오가며 같은 기회라는 연속성이 약했다.

이번 기본 구조는 **왼쪽은 계속 대화, 오른쪽은 지금 함께 보고 있는 결과물**이다. Harper가 찾아보고 준비한 결과가 오른쪽에 남고, 사용자의 선택·질문은 왼쪽 대화로 이어진다. 대화가 단순 도움말 창이거나, 오른쪽이 별도 잡플랫폼처럼 느껴지지 않아야 한다.

## 2. 조사한 패턴과 Harper에 적용할 범위

공식 제품 문서와 공개 화면을 확인했다. 실제 계정의 모든 동작을 재현하거나 사용자 조사를 한 것은 아니다. 아래의 ‘적용’은 관찰한 패턴을 Harper에 맞게 해석한 설계 판단이다.

| 참조 | 확인한 패턴 | 적용 | 그대로 가져오지 않을 것 |
| --- | --- | --- | --- |
| [Linear · Display options](https://linear.app/docs/display-options) | 목록의 그룹·정렬·표시 속성을 구분한다. 공식 화면은 우측의 작은 Display 진입점 안에 상세 설정을 모은다. | 자주 바꾸는 관점은 밖에, 덜 쓰는 열·표시 옵션은 안에. 필터와 정보 표시를 구분한다. | 처음부터 많은 프로젝트 관리 속성·상태·설정 메뉴를 노출하기 |

## 3. 공통 정보 구조와 상호작용

### 대화와 작업 공간

- 대화와 입력창은 왼쪽에 항상 남는다. 오른쪽을 열어도 대화의 폭·입력 위치를 바꾸지 않는다.
- 오른쪽은 추천 목록 → 비교/탐색 → 기회 상세 → 기회 안의 자료로 이어진다. 별도 채용 플랫폼이나 새 브라우저 페이지로 이동하지 않는다.
- 대화에 나온 결과물은 작은 문서 행으로 다시 열 수 있다. 채팅에서 ‘16곳’이라고 말하고 오른쪽에는 3곳만 있는 불일치를 만들지 않는다.
- 오른쪽에서 ‘이 기회들 비교해줘’를 누르면 선택한 회사가 들어간 대화 초안으로 연결한다. 선택 없이 일반적인 도움말을 덧붙이지 않는다.
- 상세에서 돌아오면 관점·검색어·필터·선택·스크롤을 보존한다. 자료/면접을 전환해도 메모와 연습 기록은 보존한다.
- 읽기만 해도 채팅에 자동 메시지가 쌓이지 않는다. 사용자의 요청이나 실제 새로운 결과가 있을 때만 대화가 진행된다.

### 보여주기와 숨기기의 기준

| 계속 보여줄 것 | 필요할 때 열 것 | hover/focus에서만 보여도 되는 것 |
| --- | --- | --- |
| 현재 기회, 현재 상태, 다음 중요한 결과물, 돌아가기 | 원문 공고, 긴 조사 자료, 상세 조건, 이력서 diff | 보조 편집 아이콘, 개별 행 저장 단축 동작 |
| 비교/전체 탐색 입구의 이름, 선택한 필터 | 드문 필터, 근거/출처, 이전 진행 기록 | 보조적인 chevron 강조 |
| 이번 지원에 포함할 항목의 체크 상태 | 실제 보낼 전문, 선택적 보강 질문 | 이미 글 제목으로 열리는 문서의 추가 열기 버튼 |

‘심플함’을 버튼 수만으로 평가하지 않는다. 사용자가 행동을 찾는 데 필요한 텍스트 링크는 유지한다. 원문/편집/복사/삭제를 모든 행에 늘어놓지 않는다. 한 장면에서 채움이 강한 버튼은 최종 진행처럼 우선순위가 명확한 경우에만 사용한다.

### 세 종류의 상태를 섞지 않는다

1. **기회의 진행 상태:** 저장, 지원 준비, 제출, 면접, 결과. 실제로 발생한 사실이다.
2. **Harper가 준비한 자료:** 초안, 검토할 변경, 확인이 필요한 근거. 실행 완료가 아니다.
3. **이번 실행에 포함할 선택:** 체크박스. 선택은 발송이나 제출이 아니다.

진행 타임라인의 완료 표식과 실행 전 체크박스는 위치·문구가 달라야 한다. 사용자가 체크했다고 ‘지원 완료’가 되지 않는다.

## 4. 기능별 결정

### 01. 적극적으로 찾는 사람에게 충분한 선택지 주기

**목적:** 추천 10개라는 숫자에 갇히지 않으면서, 가입 직후 사람에게 큰 표를 읽는 숙제를 주지 않는다.

| 대안 | 장점 | 문제 | 선택 |
| --- | --- | --- | --- |
| 처음부터 전체 비교표 | 선택지의 폭을 즉시 인지 | 초기 탐색 부담, Harper의 우선 판단이 희미함 | 기본으로 사용하지 않음 |
| 추천 목록만 계속 늘리기 | 기존 UI와 동일 | 방향 사이의 차이와 전체 폭을 보기 어려움 | 초기 목록에만 사용 |
| 짧은 추천 목록 + 요청 시 기회 비교표 | 먼저 볼 곳과 넓은 선택지를 함께 제공 | 비교 입구를 발견할 수 있어야 함 | 채택 |

**처음:** 기존 목록으로 선별한 3개 예시를 보여준다. 제목 옆에 ‘16곳 비교’ 링크를 둔다. 추천 이유는 각 카드에서 읽을 수 있다. 대화에도 같은 결과물 링크가 있다. 3개는 프리뷰의 초기 분량이지 제품의 고정 추천 제한이 아니다.

**열었을 때:** 오른쪽을 비교표로 사용한다. 회사·역할 / 나와 연결되는 이유 / 확인할 점 / 근무 조건이 핵심이다. ‘많이 있다’보다 서로 어떤 선택인지 읽히는 표다. 몇 곳 선택하면 ‘Harper에게 비교 요청’가 나타난다. 미리 준비된 질문을 대화 입력에 넣고 사용자가 고칠 수 있다.

**돌아왔을 때:** 추천 목록은 그대로다. 선택한 항목과 비교 조건은 유지한다. 첫 방문 이후에는 마지막으로 연 상태를 세션 내에서 이어간다.

**전체 탐색과의 차이:** 01은 Harper가 이 사람의 목적을 놓고 정리한 집합, 06은 아직 개인별로 검토하지 않은 공고까지 포함한 목록이다. 두 개의 독립 제품이 아니라 같은 읽기 도구에 서로 다른 범위와 열을 준다.

**논의할 것:** 적극 구직 의사를 밝힌 경우에도 최초 목록을 거칠지, 대화에서 표 열기를 요청한 경우 바로 표를 보여줄지. 전자는 기본안, 후자는 명시적 의도에 따른 진입으로 유지한다.

### 02. 기회 상세를 자료와 진행의 집으로

**목적:** 내가 어디까지 왔는지, Harper가 뭘 준비했는지, 내가 남긴 자료가 어디 있는지 한 기회 안에서 알 수 있어야 한다.

**대안:** 단계별 탭은 찾기 쉽지만 자료가 여러 탭에 흩어진다. 모든 것을 타임라인에 넣으면 최근 사건은 좋지만 준비 문서를 찾기 어렵다. 파일 저장함만 만들면 현재 중요한 일이 보이지 않는다.

**채택**은 개요·자료·기록과 같은 기회 안에서 열리는 문서 읽기 화면이다.

- 개요는 기존 기회 카드 아래에 다음 일정과 면접 준비 버튼을 강조한다. 제출한 자료와 최근 통화 메모를 아래에 둔다.
- 자료에서는 지원할 때 제출한 파일을 날짜와 채널로 묶는다. Harper 조사와 직접 추가한 자료는 별도 준비 자료 그룹에 둔다.
- 파일을 선택하면 오른쪽 패널이 문서 읽기 화면으로 바뀐다. 돌아가면 이전 화면의 위치와 선택을 복원한다.
- 기록에서는 메모를 수정하고 제출·통화·일정 확정 이력을 시간순으로 읽는다.

자료 전체를 단계별 칸반으로 나누지 않는다. 동일한 조사 자료는 지원과 면접에서 같이 쓸 수 있다. 실제 구현에서는 자료의 출처·수정 시점·관련 기회를 보존하고, 현재 문서를 변경했다고 과거 제출 파일을 바꾸지 않는다.

**프리뷰 범위:** 텍스트 자료 추가·메모 수정·면접 준비 왕복. 업로드·외부 링크 수집·자동 조사·영구 저장은 구현하지 않는다. 원문이나 근거는 예시 자료임을 표시한다.

### 03. 면접 준비와 반복 연습

**목적:** 조사 → 내 경험 선택 → 답변 → 피드백 → 다시 답변 → 직전 복습의 연결을 느끼게 한다.

**대안:** 큰 ‘모의 면접’ 버튼은 진입은 쉽지만 준비가 비어 있다. 조사·질문·연습·평가를 별도 도구로 만들면 자료를 옮겨야 한다. 하나의 긴 문서만 있으면 실제 연습으로 이어지기 어렵다.

**채택:** 기회 상세 안에서 면접 준비를 연다. ‘개요’로 같은 기회에 돌아간다. 질문 목록에서 항목을 고르면 오른쪽에 질문 근거와 연습 시작 버튼이 열린다.

- 첫 화면은 이번 면접의 초점과 지난 연습에서 이어갈 점을 보여준다. 문서 수·완료율·추정 준비도 점수를 대시보드로 만들지 않는다.
- 예상 질문은 공고와 조사에서 왜 나왔는지, 어떤 내 경험을 연결하는지 함께 읽는다. 확정 출제 질문처럼 표현하지 않는다.
- 질문을 골라 연습하면 오른쪽 자료를 그대로 둔 채 왼쪽 채팅에 질문이 열린다. 입력창에 ‘노바랩스 · 면접 연습’ 맥락을 표시한다.
- 답변과 피드백은 기회의 연습 기록에 남는다. 다시 연습은 이전 답변을 덮어쓰지 않는다.
- 직전 요약은 아래까지 스크롤하지 않아도 상단에서 열 수 있다. 자기소개, 꺼낼 경험, 이번에 확인할 질문을 짧게 읽는다.
- 연습 후 다른 질문으로 가거나 연습을 마칠 수 있다. 일반 대화를 연습 답변으로 계속 오인하지 않는다.

**프리뷰 피드백:** 실제 답변 평가를 흉내 낸 칭찬을 하지 않는다. 예시 회차에는 구체적인 피드백을 제공하되, 새로 입력한 답변에는 ‘기록 저장’과 별도 표시한 피드백 예시만 제공한다. 실제 제품에서는 원본 답변과 관련 자료를 모델에 제공해 평가해야 한다.

**논의할 것:** 다음 연습을 Harper가 먼저 하나 제안하는 방식과 질문 목록을 고르는 방식의 비중. 사용자가 돌아왔을 때 ‘이어서 연습’ 한 개를 먼저 제안하는 기본안을 채택한다.

### 04. 지원 전에 준비된 변경안을 선택하기

**목적:** 사용자가 ‘지원해주세요’라고 했는데 숙제 목록을 받는 경험을 피한다. 실제 지원에 무엇이 달라지는지는 알 수 있어야 한다.

| 대안 | 문제/이점 | 결정 |
| --- | --- | --- |
| 알아서 전부 수정하고 즉시 지원 | 편하지만 수정 내용·추가 연락을 알기 어렵다 | 외부 실행 전 구체적 결과를 검토할 수 있게 함 |
| 사용자 투두 체크리스트 | 일이 사용자에게 넘어오고 완료 체크가 실행 동의처럼 보임 | 채택하지 않음 |
| 문서마다 ‘적용’ 버튼 | 선택은 명확하지만 버튼이 많고 전체 상태가 안 보임 | 체크 선택과 변경 내용 열기로 통합 |
| 준비된 제안 + 포함 여부 + 최종 요약 | 준비와 결정이 분리되며 일부만 써도 진행 가능 | 채택 |

**첫 화면**의 Harper 답변 아래에 맞춤 이력서와 채용팀 소개 메일의 체크리스트와 ‘지원 내용 확인’ 버튼을 둔다. 변경 보기와 초안 보기는 오른쪽 읽기 화면으로 연결한다. 체크는 해당 항목을 이번 지원에 포함한다는 뜻이다.

**기본 선택:** 맞춤 이력서는 포함한 제안으로 시작한다. 기존 사실의 순서·표현을 바꾼 안이며 사실을 추가하지 않는다. 소개 메일은 선택하지 않는다. 서로 다른 채널의 외부 연락을 이력서 선택에 묶지 않는다. 모든 항목을 해제해도 원래 이력서로 진행할 수 있다.

**추가 경험:** ‘있으면 더 보강할 수 있는 것’은 체크리스트 밖에 둔다. 답변 전에는 보강 완료로 표시하지 않는다. 답변이 없어도 유효한 기존 이력서로 진행한다. 답변이 들어오면 미확인 성과를 자동 삽입하지 않고 반영할 문장으로 보여준다.

**맥락 요청:** 기억이 안 나면 우선 짧은 대화로 구체화한다. 자료 업로드/연결은 필요한 자료와 쓰임이 있을 때 선택지로 제안한다. Gmail 전체 연결을 의례적 준비 단계로 넣지 않는다. ChatGPT에 프롬프트를 복사하고 결과를 가져오라는 과정도 기본 경로로 만들지 않는다. 외부 대화에만 정보가 있으면 필요한 부분만 가져오는 선택을 제안할 수 있다.

**추가 연락:** 수신자·주소 출처·제목·본문·첨부를 별도로 검토한다. 이메일을 모르면 보내기 초안이 준비됐다고 하지 않는다. 커피챗도 특정 상대와 목적이 있을 때만 제안한다. 지원할 때마다 의무적으로 추가 연락을 권하지 않는다.

**최종 확인:** 제출 경로, 선택된 이력서의 실제 내용, 부가 경험 반영 여부를 확인한다. 소개 메일을 골랐다면 수신자와 본문도 함께 확인한다. 왼쪽 카드에는 제출할 항목을 요약하고 선택 수정과 지원 후 화면 보기 버튼을 둔다. 제외한 항목은 제출 요약에 남지 않는다. 최종 결과 화면은 각 채널의 실제 결과를 구분해야 한다. 프리뷰는 ‘지원 후 화면 보기’로만 전환하고 실제 제출·발송은 하지 않는다.

**실패/부분 완료:** 실제 제품에서 지원 성공·메일 실패라면 지원은 제출 기록으로 남기고 메일만 재검토/재시도한다. 전체를 다시 보내는 동작이 되어서는 안 된다. 이 동작은 이번 화면 프리뷰의 구현 범위 밖이다.

내부의 면접 도달 가능성 추정은 사용자에게 숫자·등급·확률 문구로 노출하지 않는다. 지원 제안은 필요한 근거와 실행할 결과를 보여준다. 프리뷰에서도 이 확률을 생성하거나 저장하지 않는다.

### 05. 추천을 보는 여러 관점

**목적:** 내가 아직 이름 붙이지 못한 커리어의 방향을 발견한다. 조건 필터와 역할이 다르다.

**대안 비교:** 드롭다운은 공간을 아끼지만 가능한 방향이 숨어 있다. 큰 카테고리 카드는 몇 개 안 되는 추천에 입구만 과해진다. 긴 카테고리 탭은 화면을 넘기기 쉽다. 선택지가 보이는 작은 칩/텍스트 그룹이 현재 패널에 가장 적합하다.

**채택:** 목록 위 두 줄 이내의 조용한 관점 버튼을 보여준다. ‘전체 / 고객과 가까이 / ML에 깊게 / 초기 팀 / 큰 조직 / 파트타임’. 역할의 방향과 회사의 성격이 겹칠 수 있으므로 폴더가 아니라 목록을 보는 관점으로 취급한다. 한 번에 하나를 택해 탐색한다. 복합 조건은 06의 필터에서 다룬다.

선택한 관점 아래에 해당 방향의 구체적인 의미 한 줄을 둔다. 예: ‘고객의 문제 정의부터 실제 배포까지 맡는 역할’. 같은 회사가 여러 관점에 나와도 다른 기회로 복제하지 않는다. 전체 수는 중복 합산하지 않는다. 저장 상태는 모든 관점에서 같다.

**색:** 관점별 무지개 색, emoji, 카드 일러스트를 붙이지 않는다. 선택한 하나만 기존 밝은 선택 표면으로 구분한다. ‘최고의 초기 스타트업’처럼 검증하지 않은 가치 판단을 카테고리 이름에 넣지 않는다.

**논의할 것:** 실제 사용자의 목표에 따라 관점 수·이름이 달라져야 한다. 이번 5개는 이 예시 사용자의 관심을 표현한 것으로 운영 분류 체계나 고정 분기 규칙이 아니다.

### 06. 전체 공고 탐색

**목적:** 적극적으로 찾는 사람은 더 많은 공고를 빠르게 훑고, 몇 곳을 Harper와 깊게 살펴볼 수 있다.

**진입:** 기존 추천 목록 상단의 작은 ‘전체 공고 탐색’ 텍스트. 항상 찾을 수 있지만 기본 추천보다 강하게 보이지 않는다. 열면 오른쪽 가용 폭을 쓰는 표로 바뀐다. 왼쪽 대화는 고정한다. 채팅을 덮는 전체화면 모달은 사용하지 않는다.

**왜 표인가:** 여기서는 회사별 긴 추천 이유보다 조건 비교와 빠른 스캔이 중요하다. 카드 3개를 보는 높이에 한 번에 약 12개 행을 읽을 수 있도록 약 48px의 두 줄 행을 기본으로 한다. 32px 한 줄은 긴 역할명을 희생하므로 사용하지 않는다. 좁은 화면에서 필수 열을 몰래 삭제하지 않고 표 내부 가로 스크롤을 허용한다.

| 기본 열 | 표시할 정보 | 선택 이유 |
| --- | --- | --- |
| 선택 | 체크박스 | 몇 곳을 묶어 저장하거나 대화로 가져가기 |
| 회사 · 역할 | 회사, 정확한 역할명 | 가장 중요한 식별 정보. 클릭해 같은 기회 상세 열기 |
| 근무 | 위치 + 원격/하이브리드/대면, 파트타임이면 표시 | 실제 선택의 제약을 빠르게 판단 |
| 보상 | 공개/추정 범위 또는 미확인 | 출처가 다른 값을 같은 사실로 읽지 않게 함 |
| 회사 | 단계 + 팀 규모 | 조직 맥락 비교. ‘좋은 회사’라는 등급으로 압축하지 않음 |
| 확인 | 마지막 공고 확인 날짜 | 오래된 정보인지 판단. 실제 게시일과 혼동하지 않음 |

‘직접 지원’은 전체 행에 반복하지 않는다. 대부분의 행이 같은 값이면 비교 가치가 없다. Harper 연결이 가능한 경우에만 상세에서 알린다. 개별 적합도를 아직 평가하지 않은 공고에는 가짜 점수나 자동 등급을 붙이지 않는다.

**검색/필터:** 회사·역할 검색은 항상 보인다. 근무 방식·고용 형태·보상 조건은 필터에서 펼친다. 선택된 조건은 접힌 뒤에도 지울 수 있는 칩으로 남긴다. ‘1억원 이상’은 확인된 범위의 상단 기준임을 명시하며, 미확인 공고 포함 여부를 별도로 선택한다. 값이 없다는 이유로 부적합처럼 취급하지 않는다.

**정렬:** 최근 확인순 기본. 보상순과 회사명순을 지원하며 미확인 보상은 마지막이다. 최신 게시순이라고 잘못 부르지 않는다. 전체 미평가 공고를 ‘추천순’으로 정렬하지 않는다.

**선택:** 선택한 행이 있을 때만 저장/Harper와 살펴보기 도구가 나온다. 헤더 체크는 현재 필터 결과를 선택한다. 필터를 바꾸면 선택 집합은 새 결과에 한정해 다시 선택하도록 해 보이지 않는 행을 일괄 처리하지 않는다. 일괄 지원은 넣지 않는다.

**상세/복귀:** 같은 오른쪽 패널에 상세가 열리고, 뒤로 가면 검색/필터/정렬/스크롤이 그대로 남는다. ‘관심 있음’ 표시와 일괄 작업용 선택은 다른 상태다.

**빈 결과:** 결과 0개와 현재 필터를 함께 표시한다. ‘조건 초기화’로 복구한다. 검색 중/오류/페이지 로딩은 실제 데이터 연결 때 추가해야 하며 프리뷰에서 가짜 로딩 연출은 하지 않는다.

### 07. 적합도와 연봉 표시

| 표현 | 이점 | 위험 | 이번 선택 |
| --- | --- | --- | --- |
| 94 / 100 | 빠른 비교 | 94와 91의 차이가 의미 있어 보임, 확률처럼 오해 | 비교 실험에서만 선택 가능 |
| 높음 / 중간 / 낮음 | 숫자의 정밀함은 줄어듦 | 근거 없는 등급 문제는 그대로 | 기본으로 사용하지 않음 |
| ‘고객 배포 경험 연결’, ‘전문성 확장’ | 무엇이 맞는지 바로 알 수 있음 | 서로 단일 순위를 매기기 어려움 | 기본 채택 |
| 이유 한 문장만 | 가장 구체적 | 많은 행을 볼 때 밀도 증가 | 추천 목록에 라벨과 짧은 근거 병행 |

기본은 **연결되는 경험의 짧은 라벨 + 이유 한 줄**이다. 라벨은 숫자를 임계값으로 잘라 만드는 것이 아니다. ‘아직 살펴보지 않음’은 낮은 적합도와 구분한다. 실제 제품에서는 원본 사용자 맥락과 공고에 근거한 모델 설명이어야 한다.

07 프리뷰의 목록 위 ‘적합도 표시’에서 이유와 점수 예시를 바꿔 같은 목록을 비교한다. 사용자 제품의 영구 설정으로 제안하는 것이 아니다. 숫자안도 %·합격 가능성 표현을 쓰지 않는다. 근거는 상세에서 읽을 수 있다.

연봉은 공개 범위, Harper 추정, 미확인을 구별한다. 프리뷰의 모든 금액은 가상이다. 실제 제품은 기준 통화/연간 기본급 여부/주식 포함 여부/출처/확인 시점을 가져야 한다. 파트타임의 시급·월급과 정규직의 연봉을 환산 없이 같은 정렬에 넣지 않는다. 프리뷰의 파트타임 보상은 미확인으로 남긴다.

**논의할 것:** 숫자를 본 사용자가 이유를 덜 읽는지, 라벨만 보고 회사 간 차이를 충분히 이해하는지. ‘보기 좋아 보인다’ 외에 실제 선택을 설명할 수 있는지 확인해야 한다.

## 5. 시각·접근성 구현 기준

- 기존 Career sky 토큰, Typography, BareButton/MuteButton, Input/Textarea, Checkbox, Table, ChatComposerFrame을 재사용한다. 새로운 전역 디자인 시스템을 만들지 않는다.
- 1440px 기준 왼쪽 대화 560px, 사이 간격 약 72px, 오른쪽 남은 폭. 일반 상세는 약 580px 읽기 폭, 비교표는 오른쪽 전체 폭. 목록을 표로 바꿔도 왼쪽은 이동하지 않는다.
- 기본 본문 14–15px, 표 12–13px, 메타 11–12px. 작은 회색 글자만으로 핵심 정보를 전달하지 않는다.
- 회사·문서·행을 각각 큰 카드로 감싸지 않는다. 반복 항목은 구분선과 정렬로 구획한다. 카드 외관은 결과물 입구나 현재 집중하는 작업에만 제한한다.
- 핵심 클릭 대상은 텍스트와 chevron으로 인지된다. 키보드 focus도 hover와 동일하게 보인다. 체크와 행 열기는 독립된 클릭 대상이다.
- 상세 전환 뒤 제목/뒤로가기에 포커스를 옮기고 복귀하면 원래 진입점으로 돌아간다. 페이지 전체 스크롤 대신 각 영역을 스크롤한다.
- 화면 폭이 좁아져도 채팅이 사라지지 않는 데스크톱 검토가 우선이다. 모바일은 이번 검토 범위 밖이며, 데스크톱을 축소해 모바일 제품 UX라고 주장하지 않는다.
- 7개 컨셉 이동은 프리뷰 띠에서 한다. 07의 표시 비교는 평가할 카드 목록 바로 위에 둔다.

## 6. 프리뷰에서 확인할 흐름

| 기능 | 직접 해볼 것 | 성공 기준 |
| --- | --- | --- |
| 01 | 기본 목록 → 정리한 기회 표 → 2곳 선택 → 대화로 가져오기 → 돌아가기 | 표가 자동으로 열리지 않음. 회사 맥락을 다시 입력하지 않아도 됨 |
| 02 | 자료 열기 → 메모 수정/추가 → 면접 준비 → 자료 복귀 | 같은 기회 헤더와 편집한 내용 유지 |
| 03 | 예상 질문 → 채팅 답변 → 기록 확인 → 다시 연습 → 직전 요약 | 자료가 사라지지 않고 회차가 쌓임 |
| 04 | 이력서 diff 확인 → 메일 선택/해제 → 모두 해제 → 제출 내용 확인 | 준비·선택·실행이 구별됨. 미선택 내용이 제출 요약에 포함되지 않음 |
| 05 | FDE/ML/초기 팀 관점 전환 → 같은 기회 저장 | 관점이 보이고 겹치는 기회의 상태가 일치함 |
| 06 | 전체 탐색 → 검색·필터·정렬 → 상세 → 뒤로 → 일괄 저장 | 여러 행을 한 화면에서 읽고 조건과 위치를 잃지 않음 |
| 07 | 이유 중심/점수 중심 비교 → 연봉 조건 → 미확인 포함/제외 | 표시 형식과 대상 필터가 별개이며 결측이 드러남 |

팀 논의는 각 흐름을 직접 수행한 뒤 한다. ‘버튼을 줄일까’보다 ‘처음에 판단할 것이 너무 많은가’, ‘지원된 줄 알았는가’, ‘원하던 문서를 다시 찾았는가’, ‘왜 이 기회를 골랐는가’를 확인한다. 아직 사용자 연구 수치나 개선 효과를 주장할 근거는 없다.

## 7. 구현 경계

로컬 `/career/preview/concepts`에서만 동작한다. 회사·공고·연봉·점수·면접·대화는 가상 데이터다. 화면 조작은 세션의 React 상태만 변경하며 새로고침하면 초기화된다. 실제 사용자 정보·운영 DB·이메일·지원 도구를 호출하지 않는다. 개발 모드 밖에서는 404다.

전체 탐색은 48개 가상 공고로 밀도를 검토한다. 16개 개인화 예시와 32개 미검토 예시를 구분한다. 반복된 회사 행이나 실제 없는 수천 개의 카운트를 사용하지 않는다. 실제 pagination, 검색 인덱스, 동기화, 권한, 발송, 자동 조사와 모델 판단은 이 프리뷰에서 구현하거나 검증하지 않는다.

실제품으로 옮길 때 이 화면의 예시를 상황별 고정 분기나 모델 답변 대본으로 구현하지 않는다. 원본 사실·사용자 맥락·일반 도구와 실제 실행 계약을 제공하고 모델이 준비할 자료와 제안을 판단하게 한다. 화면은 그 결과와 사용자 선택을 표현한다.
