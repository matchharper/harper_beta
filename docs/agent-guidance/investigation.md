# 로그·장애 원인 조사 계약

## 원인 조사·장애 설명의 구체성 — 필수

- 사용자가 로그나 오류 원인을 물으면 오류명이나 추상적인 내부 처리 설명으로 끝내지 않는다. 대상과 기능 종류(예: internal Role인지 외부 공고인지)를 실제 데이터로 확인하고, 사용자가 하려던 일과 완료되지 않은 결과를 먼저 설명한다.
- 핵심 경로를 `사용자 발화·클릭 → 실제 tool/API 호출과 주요 인자 → 실행 결과 → 사용자에게 표시된 응답·오류`로 연결한다. 필요한 사용자 원문과 한국 시간, tool 이름을 제공하고, LLM의 실행 의사 표현과 실제 호출·완료를 구분한다. 무관한 전체 대화나 개인정보는 복사하지 않는다.
- 사용자에게 보이는 상태를 단계별로 구분한다. 문서라면 본문 저장, 화면 미리보기, 다운로드용 파일 생성·영구 저장, 다운로드 응답, 사용자 기기 수신을 섞지 않는다. 지원·연락이라면 준비, 외부 화면 입력, 제출·발송, 상대방 수신 확인을 구분한다. 파일명·카드·성공 문구·상태값만으로 후속 단계 완료를 추정하지 않는다.
- “기존 시도”, “기록”, “상태”, “큐”, “검증 실패” 등을 원인으로 들 때는 무엇을 시도한 것인지, 어느 테이블·필드/시스템에 어떤 값으로 남았는지, 어떤 조건문·reader가 이를 읽어 어느 행동을 막았는지까지 설명한다. 사례를 재확인할 수 있는 최소 record ID와 코드 위치를 함께 제시한다. 실패 후 재시도와 새 작업 시작의 차이도 실제 구현으로 확인한다.
- 당시 배포 revision의 코드와 실제 로그를 대조하고, 최초 장애·복구를 막은 후속 문제·잘못된 LLM 안내를 분리한다. 고객에게 한 설명을 기술적 사실로 취급하지 않는다. 관측 사실, 코드로 확인한 동작, 추론, 아직 확인하지 못한 세부 원인을 명시하며, 확인 범위를 넘는 “원인 확정”이나 “미제출/전달 완료” 주장을 하지 않는다.
- 사용자가 다시 “정확히 무엇이 안 됐고 왜 그런가”를 묻지 않아도 이해할 만큼 구체적으로 답한다. 간결함을 이유로 위 인과관계와 증거를 생략하지 않는다. 조사 요청만으로 수정·재시도·발송·배포를 실행하지 않는다.
