# Company-side LLM 도구 정보 설계 가이드

문서 기준: 2026-10-22. 도구와 입력을 설계·수정·리뷰할 때 따르는 개발 계약이다. 이 문서 작성 자체는 런타임 변경이나 운영 반영을 뜻하지 않는다.

company-side LLM은 도구를 호출하기 전에도 어떤 도움을 줄 수 있는지, 무엇을 확인해야 하는지, 이미 어떤 일이 진행 중인지를 알아야 한다. 상세 실행 계약은 필요한 때 불러오되, **그 계약이 필요하다는 것을 알아차리게 하는 정보까지 숨기면 안 된다.** 반대로 도구의 존재를 안다는 사실이 현재 실행 가능성·사용자 승인·실행 완료를 뜻하지도 않는다.

정보의 위치는 “어느 도구에 속하는가”보다 **모델이 어느 판단을 하기 전에 알아야 하는가**로 정한다. 도구가 만든 사실은 그 도구를 이번 대화에서 호출했는지와 관계없이 필요한 판단 시점에 제공한다. 모든 정보를 제공하거나 모든 사실을 답변에 언급하라는 뜻은 아니다.

## 적용 범위와 기존 정본

이 가이드는 tool policy, description/schema, result, 기능 목록, 기본 context, 지연 로딩, 이전 실행의 후속 대화 및 백그라운드 결과 입력을 함께 다룬다. 사용자가 말하는 `loader_tools`는 이 지연 로딩 계층을 가리키며, 현재 저장소의 실제 도구 이름은 `load_capabilities`다.

- 전체 책임 배분과 변경 절차: [company-side agent 변경 정본](company-side-agent-engineering-contract-ko.md)
- 사용자에게 어떻게 설명할지: [company-side UX writing 가이드](company-side-ux-writing-guide-ko.md)
- 개별 업무의 권한·승인·효과: 해당 제품 계약과 현재 실행 코드

이 문서는 정보 배치의 정본이다. 개별 제품 정책·가격·승인 절차를 새로 정의하지 않으며 기존 정본을 복제하지 않는다. 구현 문서와 코드가 다르면 실제 동작은 코드로 확인하고, 목표 계약과 구현 차이는 구분해 기록한다.

## 먼저 구분할 여섯 가지

| 구분 | 모델이 알아야 할 것 | 이것만으로 알 수 없는 것 |
| --- | --- | --- |
| 기능의 존재 | 어떤 문제를 해결할 수 있고 어디서 자세히 알아보는가 | 현재 대상에게 실행할 수 있는가 |
| 현재 노출 | 이번 completion에서 어떤 도구를 실제 호출할 수 있는가 | 사용자가 그 행동을 승인했는가 |
| 대상별 자격 | 현재 조직·팀원·Role·후보자에게 허용되는 효과와 알려진 제한 | 사용자가 지금 그 효과를 원하는가 |
| 사용자 위임 | 원문 대화에서 맡긴 대상·목적·범위와 이후 수정·철회 | 실행이 성공했는가 |
| 실행 결과 | 실제 저장·전달·접수된 효과와 불확실한 부분 | 상대방의 열람·응답·의사·미래 성과 |
| 지속되는 사실 | 현재 남아 있는 초안·예약·진행 작업·결정과 확인 시점 | 과거 승인과 상태가 지금도 유효한가 |

이 구분은 설계·리뷰용 질문이다. 여섯 단계의 상태 머신이나 모델의 중간 판단 JSON을 만들라는 요구가 아니다. 서버는 권한·식별자·동의·revision·멱등성 같은 실제 실행 경계를 검증하고, 원본 LLM은 문맥에서 필요한 조회·제안·행동을 판단한다.

## 정보를 배치하는 기준

| 정보 계층 | 맡는 질문과 내용 | 제외할 내용 | 책임 원본 |
| --- | --- | --- | --- |
| 공통 core | 어떤 파트너인가, 어떤 근거를 믿는가, 도구 없이도 알아야 할 서비스 의미·공통 안전 경계 | 모든 기능의 인자와 세부 절차 | `prompts.ts`, `serviceKnowledgePrompt.ts`, 공통 문체 계약 |
| 기능 목록 | 어떤 도움을 제공할 수 있는가, 언제 관련 있는가, 효과의 범주와 중요한 한계, 불러올 capability 식별자 | 상세 schema, 사용자별 상태, 긴 금지 목록 | `capabilities/registry.ts`와 `resolver.ts` |
| 기본 동적 context | 지금 누구와 어떤 범위에서 대화하는가, 관련 대상의 현재 상태·진행 중인 일·부족한 정보 | 모든 프로필·과거 사건·상세 정책 | `context.ts`, `input.ts`, `contextBudget.ts` |
| 상세 policy | 어떤 근거·위임을 확인하고 어떤 일반 도구로 일을 이어가는가, 실행과 복구의 조건 | 말투 복제, 고정 답변, 사례별 대화 시나리오 | `capabilities/policies.ts`와 연결된 공통 업무 계약 |
| description와 schema | 이 호출의 목적·효과·인자 의미·필수값·식별자·revision·반환 의미 | 업무 철학 전체, 답변 템플릿, 이미 서버가 아는 값의 재추정 | `tools.ts` |
| 실행 결과 | 이번 호출로 무엇이 실제 바뀌었고 무엇이 미완료인가, 다음 판단에 필요한 근거와 참조 | 근거 없는 성공, 새 사용자 승인, 정해진 성공 문장 | executor 결과와 `promptFormat.ts` |
| 후속 사건과 재조회 | 다른 경로·이전 시점의 변화 중 지금 알아야 할 사실, 이미 안내한 범위, 현재 남은 일 | 원본 결과 전체 누적, 새로운 업무 위임으로 둔갑한 사건 | 기존 일반 reader·대화 입력·`companyUpdate.server.ts` |

한 사실이나 규칙에는 한 책임 원본을 둔다. 여러 계층에서 필요하면 그 원본을 서로 다른 깊이로 표현한다. 예를 들어 목록에는 “새 후보 탐색을 요청할 수 있다”, policy에는 실행 전 필요한 조건, result에는 해당 요청의 실제 접수 결과가 들어간다. 세 문구를 각자 관리해 서로 다른 동작을 약속하게 만들지 않는다.

정책을 작성한 위치와 provider가 실제 지침으로 지원하는 위치도 대조한다. HTTP 성공은 임의의 message role이나 필드가 의도한 지침으로 적용됐다는 증거가 아니다. 예를 들어 [Decisions 공식 계약](https://developers.openai.com/api/docs/guides/decisions#how-decisions-work)의 현재 문서는 공유 `input`과 질문별 `instructions` 외에 developer/system 메시지도 지원한다. 과거 실험에서 확인한 제약을 영구적인 API 제한으로 고정하지 않는다. 대화 기반 검색의 로컬 v60은 공통 정책을 developer 입력에 한 번, 원문 근거를 user 입력에 한 번 두고 각 질문은 해당 판단만 요청한다. 다른 API의 message 역할을 옮길 때도 해당 API의 현재 계약을 확인한다. 수정 시 실제 전송 payload와 동결 입력의 결과를 함께 보존하며, 지원 형식 준수와 의미 품질 개선을 별도로 검증한다.

## 로더 호출 전에도 제공할 정보

### 기능을 발견하는 데 충분한 개요

각 capability는 사용자의 목적과 연결되는 능력, 적용 대상, 효과의 범주, 다음에 불러올 식별자를 짧게 설명한다. 도구 이름만 나열하면 모델은 사용자의 새로운 표현을 기존 능력에 연결하기 어렵다. 사례를 늘리는 대신 일반 능력을 설명한다. 질문 전달·자료 전달·회신·후속 연락은 공통 연락 능력의 사용이며, 각각 별도 상황 도구가 필요한 것은 아니다.

개요에는 **빠뜨리면 실행 전에 이미 잘못 설명하거나 제안하게 되는 경계**를 포함한다. 새 검색과 저장된 후보 조회의 차이, 연락과 연결 수락의 차이, 일정 기록과 실제 초대의 차이, 게시 수요 접수와 실제 게시의 차이가 여기에 해당한다. 내부 처리 순서 전체를 옮기지는 않는다.

기능 목록에 없다는 이유만으로 서비스 전체에 그런 기능이 없다고 단정하지 않는다. 현재 surface나 trusted caller가 제한한 실행 범위와 서비스의 일반 능력을 구분한다. 현재 대화에서 실행할 수 없는 기능을 제공한다고 약속하지도 않는다. 확인된 다른 경로가 있을 때만 그 경로를 안내한다.

### 도구를 쓰지 않는 답변에도 필요한 서비스 의미

“이렇게 하면 누구에게 무엇이 전달되나”, “이 상태는 무엇인가”, “다음에는 누가 결정하나”에 대한 핵심 설명이 숨겨진 policy에만 있으면 호출 없는 답변이 추측에 의존한다. 자주 필요한 안정적인 서비스 의미는 공통 core에, 기능별 중요한 효과 경계는 목록에 둔다. 정확한 조건이 필요한 질문에는 상세 policy를 로드하거나 일반 조회를 사용할 수 있다. 실제 변경 도구를 실행해 정책을 알아보지는 않는다.

일반 정책과 이 회사의 현재 계약·잔액·설정을 분리한다. 일반 정보 reader가 해당 값을 돌려주지 않았다는 사실은 무료 계정·잔액 없음·기능 꺼짐의 증거가 아니다. 권위 있는 조회가 없으면 확인 범위를 설명한다. 가격이나 사용량 같은 변동값을 기능 목록에 복사해 고정하지 않는다.

### 현재 판단에 필요한 작은 상태 색인

도구가 아직 로드되지 않았더라도 현재 대상, 접근 범위, 진행 상태와 관련 작업의 존재를 기본 context에서 알아볼 수 있어야 한다. 기본 정보만으로 충분한 답에는 조회를 강제하지 않는다. 상세 원문이 필요한 경우 정확한 참조와 일반 reader로 확장한다.

현재 대화의 대상이나 서버가 확인한 사건 범위를 기준으로 다음 중 판단에 필요한 것만 제공한다.

- 현재 Role·후보자·연락의 정확한 참조와 회사에 공개 가능한 상태.
- 관련 초안·확인 대기 변경·예정된 연락·진행 중인 검색의 존재와 상태, 상세 조회 위치.
- 현재 동작에 영향을 주는 확인된 접근 제한·설정·자격. 숨겨진 대상의 존재까지 노출하지 않는다.
- 언제, 어느 범위를 읽었으며 누락·오래됨·조회 실패가 있는지.

현재 대상 밖의 후보·과거 연락·모든 예약을 매 turn 넣지 않는다. “관련성”을 판정하는 새 분류 모델이나 키워드 라우터를 만들지 않는다. 알려진 대화 범위와 권한 있는 작은 색인을 제공하고, 추가 정보가 필요한지는 원본 LLM이 판단하게 한다.

### 자동 효과를 예상하게 하는 최소 설명

사용자가 행동을 선택하는 데 영향을 주는 후속 효과는 실행 전에 알 수 있어야 한다. 어떤 결정이 실제 연락·공유·사용량 차감·후속 연락을 일으키는지, 무엇은 별도 효과인지 관련 policy와 필요 시 개요에 설명한다. 이는 **일반 동작 조건**이며 특정 건에서 이미 발생했다는 증거가 아니다.

실제 예약·차감·전달 여부와 시점은 result 또는 현재 상태가 확인한다. 기본적으로 후속 연락이 있다는 정책만으로 이번 건도 예약됐다고 말하지 않는다. 반대로 이번에 다른 경로로 예약된 사실을 관련 도구를 부르지 않았다는 이유로 숨기지도 않는다. 모든 자동 효과를 매번 사용자에게 고지하도록 강제하지 않고, 비용·공유·취소 가능성 등 해당 결정에 중요한 영향은 이해할 수 있게 한다.

### 넓은 조회와 깊은 조회

`profileSections`로 bio·experience·education·extras 중 필요한 원문 구획을 선택할 수 있다. 선택한 구획의 모든 행과 상세 내용은 유지한다. 업무 근거만 필요한 경우 원본 LLM이 experience를 선택하면 학력·기타 소개문을 반복 주입하지 않는다. 생략한 구획은 비어 있다는 뜻이 아니며 다시 조회할 수 있다. 후보 수나 원문 길이의 제한은 아니다.

일반 reader는 같은 대상의 구조적 개요와 전체 원문을 구분할 수 있어야 한다. 경력 흐름·목록 비교에
모든 소개문과 업무 설명이 항상 필요한 것은 아니다. `read_talent.profileView=outline`은 현재 위치와
전체 경력·학력·기타 활동의 구조적 사실을 제공하고, 생략한 서술 원문은 명시한다. 실질 수행 내용·성과·
세부 적합성을 설명하려면 필요한 사람의 `profileView=full`을 선택한다. 이 선택은 원본 LLM이 맡으며
서버가 질문의 키워드를 보고 상세 수준을 바꾸거나, 후보 수를 제한하거나, 원문을 잘라내지 않는다.

특정 기준으로 좁힌 후보 목록은 해당 기준의 점수·근거와 전체 fit을 먼저 제공할 수 있다. 다른 기준을
삭제한 것으로 해석하지 않도록 표시 범위와 전체 평가 reader를 함께 알려준다. 조회 결과의 반복되는
설명은 공통 안내로 한 번 제공하되 실제 후보 ID·관계·점수·버전·시각·페이지는 보존한다. 검증에서는
입력 토큰 감소와 실제 대상 누락·근거 정확도를 함께 확인한다.

## 로딩과 실행 계약

로더는 상세 지식과 호출 가능한 schema를 함께 제공한다. 로딩은 읽기 성격의 준비 작업이며 사용자 승인도 업무 실행도 아니다. 이미 위임된 일을 진행하기 위해 로딩 허락을 다시 받지 않는다.

- 실행에 필요한 policy는 해당 schema와 같은 completion에 제공한다. schema만 먼저 열거나 정책만 주고 호출 경로를 누락하지 않는다.
- 현재 구현에서 로딩한 기능은 **다음 completion**부터 사용한다. 같은 batch에서 로더와 아직 노출되지 않은 도구를 함께 호출해 실행하지 않는다.
- trusted caller의 제한, surface 지원 범위와 서버 권한을 로딩으로 넓히지 않는다. 로더의 성공 메시지보다 실제 다음 요청의 tool 목록과 실행 검증이 호출 가능성의 기준이다.
- 직전 작업의 연속성을 위해 도구를 다시 노출하는 것과 과거 승인을 재사용하는 것을 구분한다. 최신 정정·철회와 현재 대상·revision을 확인한다.
- 핵심 업무는 처음부터 schema와 policy를 제공할 수 있다. 빈도뿐 아니라 숨겼을 때 모델이 일을 못 알아보거나 저장되지 않은 초안을 만들었다고 말하는 문제가 있는지로 판단한다. 무거운 기능 전체를 항상 넣는 방식으로 해결하지 않는다.
- 도구가 제한된 작성 전용 실행에는 확인된 사실과 설명에 필요한 서비스 의미를 제공한다. 수정 도구가 없으면 수정·발송을 한 것처럼 표현할 수 없으며, 필요하면 지원되는 실행 경로로 이어간다.

로딩 실패는 업무 실패나 기능의 영구 부재가 아니다. 잘못된 식별자·현재 채널 제한·일시 실패를 구분할 수 있는 사실만 돌려주고, 가능한 조회나 안내로 이어간다. 도구 사용 예산이 끝났을 때도 미실행 업무를 완료로 처리하지 않는다.

## Policy와 schema를 작성하는 방법

Policy는 같은 능력을 새로운 상황에도 적용할 수 있는 실행 판단 계약이다. 필요한 근거, 위임 범위, 부수 효과, 기존 작업을 이어갈 방법과 불확실한 실행의 복구를 다룬다. “특정 문장이 나오면 특정 도구” 같은 키워드 규칙이나 특정 대화의 정답 흐름으로 쓰지 않는다. 개별 도구를 선택하는 모델의 판단을 별도 review·decide 도구나 중간 의미 상태로 복제하지 않는다.

Description은 호출 선택에 필요한 차이를, schema는 executor가 실제 소비하는 인자를 설명한다. 자유 텍스트의 목적과 수신자, preview와 실행의 차이, 생략값의 의미, 현재 ID·revision의 출처를 모호하게 두지 않는다. 서버가 이미 아는 조직·작성자 정보를 모델이 추정하게 하지 않는다. enum은 실제 허용 identifier·명령 같은 machine contract에 한정한다. 말투·의도·감정·선호·판단을 enum이나 검증 규칙으로 제한하지 않는다.

조회라는 이름만으로 무효과라고 취급하지 않는다. 열람 권한을 새로 부여하거나 사용량을 차감하거나 상대에게 알림을 만드는 호출은 그 효과와 필요한 사용자 선택을 드러내야 한다. 일반 후보 비교 요청을 유료 열람·공유 승인으로 확대하지 않는다.

서버는 구조와 실행 경계를 책임진다. prompt의 주의 문구를 권한 검사 대신 쓰지 않는다. 필요한 확인은 기존 업무 계약만 따른다. 모든 write에 새로운 확인 단계를 붙이지 않으며, 로딩·기능 제안·일반 조회를 승인 절차로 바꾸지 않는다.

## Result는 다음 판단을 가능하게 하는 사실이다

### 성공 여부보다 실제 효과

결과는 모델이 전체 요청 중 무엇을 완료했고 무엇이 남았는지 판단할 수 있어야 한다. 필요한 정보는 효과에 비례해 제공하며 모든 도구에 동일한 거대 envelope를 강제하지 않는다.

| 필요한 정보 | 포함할 때의 기준 |
| --- | --- |
| 대상과 범위 | 어느 조직·Role·후보자·원본 요청에 대한 결과인지 혼동을 막는 정확한 참조 |
| 실제 변화 | 저장·초안 준비·승인 대기·접수·전달 등 executor가 확인한 효과와 중요한 전후 차이 |
| 실제 산출물 | 사용자가 검토·수정할 저장본, 승인할 정확한 본문과 revision, 검증된 링크 |
| 함께 발생한 효과 | 실제 생성·변경된 예약·알림·사용량·공유 범위 중 다음 판단에 필요한 사실 |
| 미완료와 불확실성 | 실패 항목, 적용 여부 미확인, 조회 불완전함, 아직 일어나지 않은 중요 단계 |
| 후속 조회와 복구 | 기존 작업 참조, 안전하게 읽을 대상, 이미 실행됐을 가능성과 재시도 조건 |

`ok=true`나 요청 접수만으로 전달·상대 열람·답변·연결·채용 완료를 확대하지 않는다. 다만 **정상 승인된 연락의 전달 계약은 그대로 존중한다.** 내부 outbox/queue라는 구현만 보고 사용자에게 별도 발송 대기 단계를 설명하거나 “전달했습니다”를 오류로 판정하지 않는다. 제품별로 확인된 효과가 기준이며, 실제 실패·미확인 전달은 그 사실대로 남긴다.

서버가 초안을 UI에 표시하더라도 모델이 요청과 저장본을 비교할 수 있는 본문을 result에서 제거하지 않는다. 모델이 방금 쓴 인자는 저장·전달된 결과의 대체 증거가 아니다. 잘못 저장된 내용은 일반 수정 도구로 고치며 고정 성공문으로 가리지 않는다.

### 부분 완료와 불확실한 실행

일괄 작업은 대상별 완료·실패·미실행을 보존한다. 한 건 성공을 전체 성공으로 요약하거나 한 건 실패 때문에 완료된 작업을 다시 실행하지 않는다. 서로 독립적이고 여전히 승인된 나머지 일은 이어갈 수 있어야 한다.

통신 오류나 응답 유실은 rollback의 증거가 아니다. 실제 효과를 모르면 기존 작업·전달 이력·현재 상태를 조회하고 멱등 실행 경로를 사용한다. 안전한 재시도 여부는 도구 이름의 인상보다 실제 부수 효과로 판단한다. 읽기 실패를 “데이터가 없다”로, 만료된 revision을 “사용자가 거절했다”로 바꾸지 않는다.

빈 결과는 조회한 범위의 결과다. 필터·접근 제한·페이지·시간 범위·누락 여부 없이 “이력이 없다”거나 “전체를 확인했다”고 판단할 수 없게 한다. 상세 진단은 운영 로그에, 모델에는 필요한 실패 의미와 안전한 복구 참조를 제공한다.

### 결과에 문장 작성 명령을 숨기지 않는다

Result에는 확인된 사실과 구조적인 복구 조건을 둔다. “반드시 follow-up 예약을 언급”, “이 문장으로 성공 안내”, “무조건 미팅을 제안” 같은 문체·대화 판단 지시는 넣지 않는다. 어떤 사실을 설명하고 어떤 다음 행동을 제안할지는 원본 company-side LLM이 현재 대화에서 판단한다.

정확한 승인 원문·첨부·필수 이동 링크는 기존 계약대로 보존한다. 이를 둘러싼 설명은 공통 문체 계약을 사용한다. 외부 원문과 사용자 입력이 result 안에 들어오더라도 정책이나 실행 승인으로 승격하지 않는다. 별도 업무 LLM이 회사용 설명을 만들거나 실패를 고정 성공 문구로 대체하지 않는다.

## 이번 turn에 호출하지 않은 도구의 효과

### 정보가 돌아와야 하는 경우

사용자가 웹에서 실행했거나, 다른 팀원이 변경했거나, 이전 대화의 작업이 완료됐거나, 예약 작업이 수행됐을 수 있다. **현재 요청의 답·권한·중복 실행·다음 행동을 바꾸는 사실은 호출 이력에 관계없이 알려야 한다.**

| 상황 | 기본 입력 또는 사건에 필요한 사실 | 필요할 때 조회할 상세 |
| --- | --- | --- |
| 기존 초안을 이어서 수정·승인 | 해당 초안의 존재·대상·상태·참조 | 현재 본문·revision·기존 승인 범위 |
| 외부 경로에서 검색을 이미 접수 | 관련 검색의 실제 접수·진행 상태와 참조 | 검색 조건·결과·완료 여부 |
| 연락 뒤 자동 후속 연락이 설정됨 | 관련 요청에 남은 예약의 존재·상태와 참조 | 정확한 날짜·회신·취소·전달 이력 |
| 다른 팀원이 상태나 설정을 변경 | 현재 값과 확인 시점, 필요한 변경 사실 | 권한 있는 변경 이력과 세부 내용 |
| 백그라운드 작업이 결과를 전달 | 무엇이 확인됐고 회사에 이미 전달됐는지 | 실제 산출물·연결된 대화·남은 작업 |
| 권한·공유 범위가 바뀜 | 현재 허용 범위와 필요한 제한 | 현재 자격 확인. 과거 비공개 내용을 복원하지 않음 |

이 표는 정보 배치의 예시다. 각 행에 전용 도구·분류기·테이블을 추가하지 않는다. 기존 사실·조회·대화·사건 전달 경로로 재구성한다. 알려진 관련 작업은 작은 포인터로, 세부 내용은 일반 read tool로 제공한다. 다음 행동에 필수인 사실을 포인터 뒤에만 숨겨 반복 실행을 유도하지 않는다.

### 사실의 수명과 도구의 수명을 분리한다

Schema가 다음 turn에서 내려가도 이미 저장한 예약·초안·결정은 남는다. 반대로 schema가 계속 노출된다고 이전 상태·승인이 최신인 것은 아니다. 대화 요약은 원래 요청의 맥락을 보존하지만 현재 상태의 원본은 아니다. 과거의 정확한 전달 사실은 보존하고, 취소·수정·권한 같은 가변 상태는 필요한 실행 전에 다시 확인한다.

쓰기 도구가 요구하는 대상 ID는 일반 조회에서 발견할 수 있어야 한다. 예를 들어 팀 Memory를 쓸 수 있어도 역할 목록으로만 팀을 찾게 하면 역할이 없는 실제 팀은 사용할 수 없다. 기존 일반 조회의 `teams`처럼 대상 자체의 권한 있는 색인을 제공하고, 그 조회의 존재를 기능 안내에 포함한다. 관련 하위 행이 없다는 사실을 상위 대상이 없다는 뜻으로 해석하게 하지 않는다.

같은 turn에서 write 뒤 초기 context와 결과가 충돌하면 확인된 최신 결과를 사용한다. 결과에 없는 영향받는 값은 새로 읽는다. 최신 결과가 단지 일부 필드를 다룬다면 그 범위 밖까지 최신이라고 간주하지 않는다. 다음 turn에는 기존 reader가 현재 사실을 공급하도록 하고, 모든 result 원문을 영구 prompt에 쌓지 않는다.

서로 다른 출처의 사실이 충돌하면 대상·범위·확인 시점을 대조한다. 항상 가장 최근 텍스트를 믿거나 대화 요약을 권위 있는 현재 상태보다 우선하지 않는다. 해소되지 않은 중대한 충돌은 변경 전에 조회하거나 필요한 질문으로 좁힌다.

### 백그라운드 결과는 새 명령이 아니다

회사에 전달할 새 소식은 기존 `enqueueCompanyUpdate` 경로에 목적과 최소한의 회사 공유 가능 사실을 넘긴다. 이미 전달된 소개·결과는 실제 전달 근거에 따라 `messageAlreadyDelivered=true`로 전달해 중복 설명을 피한다. 정기 후보 소개의 Worker 작성 예외 등은 기존 상위 계약을 유지한다.

사건의 발생은 새로운 연락·거절·공유·요금 지출의 승인이 아니다. 원래 위임과 최신 대화를 읽고 그 범위에서 계속할 일만 수행한다. 도구 전체를 주는 백그라운드 실행도 동일하다. 미전달 결과를 안내해야 하는 사건과 이미 안내된 뒤 선택적 후속 판단을 하는 사건은 구분하되, 별도 의미 상태 머신을 추가하지 않는다.

## 날짜·시각: 원본 timestamp 직접 주입 금지

**LLM에 시스템 날짜를 넣을 때 초·밀리초·마이크로초·ISO 구분자와 offset을 그대로 전달하지 않는다.**
`2026-10-22T07:06:29.344088+00:00`은 한국 시간 기준 `2026-10-22 16:06`으로 제공한다.
시각이 필요 없으면 `2026-10-22`만 제공한다. 문자열을 앞에서 자르는 방식으로 UTC를 한국 시간처럼 표시하지 않는다.
시간대는 context에 `time_zone=Asia/Seoul`처럼 한 번 명시하고 각 행에 반복하지 않는다.

- 공통 정본: `src/lib/llm/promptDateTime.ts`의 `formatLlmDateTime`. 기존 `formatPromptKstDateTime`도 이 정본을 사용한다.
- 기본 context, 검색·평가 이력, Memory, 변경 이력, 대화 metadata, tool result, 백그라운드 사건 모두 같은 계약이다. JSON 안에 들어 있다는 이유로 예외가 되지 않는다. 구조화된 날짜 metadata는 `projectLlmDateTimes`/`stringifyLlmDateTimes`를 사용한다.
- 새 날짜 필드는 명시적으로 formatter를 호출한다. 공통 projection은 구조적 날짜 필드만 처리하며, 자유 텍스트 안의 날짜를 정규식으로 바꾸는 후처리가 아니다.
- DB 원본과 로그, 정렬·동시 수정·멱등성·cursor 등 executor의 정확한 값은 보존한다. 사용자/후보자 원문, 승인 본문, URL, ID와 revision은 임의로 변경하지 않는다. 날짜가 execution token으로 필요하면 표시용 시각과 분리한다.
- 날짜만 아는 원본에는 시간을 만들어 붙이지 않는다. 시간대 없는 불명확한 시각을 서버의 로컬 시간대로 추측하지 않는다. 표시 실패 시 원본 ISO를 fallback으로 노출하지 않는다.
- 검증은 실제 입력 조립 결과에서 날짜 변환·자정 경계·중첩 결과와 원문/실행 참조 보존을 확인한다. 모델에게 “초를 무시하라”고 지시하는 것으로 대신하지 않는다.

2026-10-23 로컬 변경: 회사 공통 입력·결과 및 검색/Memory/변경 이력 formatter를 연결했다. 운영 배포나 다른 런타임 전체의 전환 완료를 뜻하지 않는다.

## 정보량과 공개 범위

모델에 전달할 필요성과 사용자에게 말할 필요성은 다르다. 모델에는 정확한 대상 선택·중복 방지·판단에 필요한 참조를 제공할 수 있지만, 사용자 답변에는 제품 의미를 전달한다. 내부 ID·queue 상태·provider 진단을 사용자에게 말하지 말라는 긴 지시보다 불필요한 원문을 먼저 제외한다.

조회 결과·기본 context·이전 대화·백그라운드 사건은 같은 회사 공유 경계를 따른다. tool 경로에서 숨긴 개인정보가 다른 경로로 다시 유입되지 않게 한다. 비공개 정보를 모델에 주고 출력하지 말라고 하는 방식으로 권한 경계를 대신하지 않는다. 다른 Role에서 얻은 신원이나 비공개 자료로 현재 조회의 공유 권한 경계를 우회하지 않는다. 플랜별 제한의 존재를 가정하지 않고 현재 제품의 실제 공유 계약을 따른다.

토큰을 줄일 때는 중복 설명·과거 세부·불필요한 진단부터 줄인다. 정확한 대상·결정에 중요한 효과·미완료 범위·현재 revision·불확실성은 보존한다. 줄인 결과가 충분하지 않다면 불완전함과 조회 경로를 표시한다. preview 원문 같은 필수 내용이 잘렸는데 완전한 확인 자료처럼 사용하게 하지 않는다. 고정된 작은 출력 상한으로 구조화 결과나 설명이 중간에 끊기지 않게 한다.

## 변경할 때 남길 설계 근거와 확인 범위

도구 또는 도구 관련 정보를 바꿀 때는 아래 질문에 짧게 답할 수 있어야 한다. 모든 질문의 답을 새 runtime 필드로 만들 필요는 없다.

1. 모델이 어떤 판단을 못 하고 있으며, 그 판단 **이전** 어느 계층에서 정보가 필요한가?
2. 로더를 한 번도 호출하지 않은 첫 답변에서도 기능을 발견하고 중요한 효과를 정확히 설명할 수 있는가?
3. 현재 capability의 policy/schema만으로 충분한가, 기존 일반 reader·result·작은 context 확장이 필요한가?
4. 다른 경로에서 동일한 효과가 발생했거나 다음 turn으로 넘어가도 현재 사실을 찾을 수 있는가?
5. 실행 자격·사용자 위임·실제 효과를 구분하고, 부분 성공과 응답 유실에서도 중복 실행을 피할 수 있는가?
6. 필요한 사실을 제공하면서 공개 범위를 지키고, 사용자에게 말할 문장·언급 항목을 과도하게 고정하지 않는가?
7. 처음 보지 못한 비슷한 요청도 같은 능력·조회·계약으로 처리할 수 있는가?

검증은 변경한 경로에 집중한다. 정보 배치만 확인한다면 실제 입력 조립 결과에서 첫 completion, 필요한 기능을 로드한 completion, 관련 결과 뒤의 입력을 대조한다. 호출 없이 설명하는 경우, 관련 작업이 이미 있는 경우, 영향받는 오류·부분 완료 경계 중 변경에 해당하는 것만 확인한다. 기능 목록의 문자열 존재만으로 모델이 올바르게 판단했다고 보고하지 않는다.

실제 모델 평가를 새로 만들거나 변경·실행·비교한다면 먼저 [평가 레지스트리](evaluation/README.md)와 해당 task README를 읽고 기존 계약을 따른다. 문서만 작성한 작업에서 모델 평가·전체 테스트·운영 발송을 자동으로 수행하지 않는다. 실제 실행 경계 검증과 모델의 대화 품질 확인은 각각의 증거로 구분한다.

아래는 2026-10-22 로컬 checkout에서 확인한 연결 지점이다. 현재 진행 중인 미배포 변경을 포함할 수 있으므로 운영 상태 증거로 사용하지 않는다.

### 도구를 아직 로드하지 않아도 알아야 하는 것

로드하지 않은 capability는 **할 수 있는 일**을 숨기는 장치가 아니다. 기능 목록에서 원본 LLM이
“검색 결과를 더 읽을 수 있다”, “이전 평가를 재사용해 추가 추천할 수 있다”, “회사·팀·역할 맥락을
기억할 수 있다”를 알아야 한다. 반대로 해당 업무를 시작하지 않은 매 turn에 인자 전체와 긴 정책을
넣을 필요는 없다. 현재 저장된 기준과 실행 효과는 loader 호출 여부와 무관하게 필요한 context다.

새로운 상황을 검토할 때 먼저 다음을 확인한다.

1. 기능 목록만 보고 필요한 일반 기능을 발견할 수 있는가?
2. 지금도 유효한 사실, 과거 실행 효과, 사용자가 변경한 조건을 구분할 수 있는가?
3. 다음 결정을 위해 부족한 정보가 정확히 어떤 일반 read로 얻어지는가?
4. 그 read의 범위·완전성·다음 페이지·재조회 식별자가 실제로 제공되는가?
5. tool을 하나 추가하는 대신 기존 read의 필터나 결과를 확장할 수 있는가?

### 통계와 이유의 정직성

현재 기준의 전체 누적 통계는 같은 Brief version에서 후보·단계별 최신 평가를 사용한다.
이후 1차 재평가에서 제외된 사람의 오래된 2차 점수를 현재 추천 가능한 결과로 취급하지 않는다.
단일 실행 통계와 누적 통계의 분모를 섞지 않고, 미측정·미실행·0명을 구분한다.

기본 context에 통계를 넣을 때도 이 구분을 생략하지 않는다. 이번 실행에서 새로 평가한 수,
이전 평가를 재사용한 범위, 같은 기준의 누적 수, 실제 추천 추가·제외는 각각 다른 사실이다.
평가 라벨의 분포는 기준별 판단 분포이며, 그 인원이 실제로 제외됐다는 기록이 아니다.
실패한 실행도 일부 평가를 저장했을 수 있다. 최종 요약이 없다는 사실로 원장도 없다고 말하지 않는다.
이 계약은 상세 검색 capability를 로드하지 않고 통계를 설명할 때도 필요하다.

동일한 숫자 이름도 비교 시각이나 모집단이 달라지면 다른 관측이다. ‘직전 검색 이후 신규 가입’처럼 기준점이 움직이는 값에는 실제 기준시각과 실행 참조를 함께 제공한다. 새 관측값이 달라졌다는 이유만으로 과거 관측을 잘못된 설명으로 취급하지 않는다. 실행의 요청 메시지 ID와 등록·시작·종료 시각은 기존 실행 원장에 보존하고 일반 이력에서 읽는다. 후속 대화는 최신 발화 이후의 일과 처음 위임한 업무 전체의 완료를 구분할 수 있어야 한다. 별도 완료 판정 모델이나 대화 상태 테이블은 필요하지 않다.

회사에 공개 가능한 저장 점수와 기준 의미를 일반 평가 조회에서 함께 제공한다. 숫자·라벨·근거는 서로 대체하는 값이 아니며, 사용자가 요청한 수치가 존재하면 이를 숨긴 제품 제한을 만들어 설명하지 않는다. 답변의 상세도와 표현은 원본 LLM이 결정한다.

### 평가·현재 관계·실행 가능성을 함께 읽기

높은 평가 점수만으로 신규 추천 가능성을 추론할 수 없다. 후보 목록에는 현재 회사에 보이는
추천·진행 기록이 있는지와 신규 추천에 필요한 구조적 자격을 작은 사실로 함께 제공한다.
후보 평가 당시의 상태와 지금의 상태는 구분한다. 이미 연결된 사람의 좋은 점수를 다시 읽는 것은
유용하지만, 그것이 새 추천을 만들라는 뜻은 아니다. 일반 목록에는 기존 회사 기록 유무 등
재사용 가능한 필터를 두고, 다음에 어떤 후보를 읽거나 선택할지는 원본 LLM이 판단한다.

서버가 확인한 실행 가능 여부를 알려 주기 위해 비공개 거절 사유나 다른 회사 관계를 공개하지
않는다. 회사에 보이는 기존 pair가 있으면 그 사실과 일반 reader를 연결하고, 공개할 수 없는
제한은 현재 실행할 수 없다는 최소 사실만 제공한다. 점수·관계·권한은 별개이며 하나로 합친
휴리스틱 점수나 새 대화 상태 머신을 만들지 않는다.

명시적 조건을 요약할 때는 범위·강도·조건부 여부와 기록 시점을 보존한다. 배타적인 조건을
단순 선호로 약화하거나, 불확실하다는 표현으로 이미 알려진 충돌을 지우지 않는다. 원본의
상대 날짜에는 확인된 기록 시점을 함께 제공하며, 오래된 계획을 현재 일정이나 완료 사실로
옮겨 쓰지 않는다. 이런 의미 보존은 prompt와 근거 제공으로 다루고 문장 후처리 규칙으로
강제하지 않는다.
확률분포의 기대 인원은 실제 최빈 라벨별 인원과 이름을 달리한다.

Decisions API가 반환하지 않은 이유는 저장된 이유인 것처럼 만들지 않는다. 점수/분류는 당시
관측값, 추천 단계 설명은 그 단계의 저장된 문장, 회사 LLM의 해설은 현재 공개 근거에 대한 해석이다.
비공개 후보 Memory를 원문으로 회사에 전달하거나 비공개 사유를 설명의 근거로 노출하지 않는다.

회사가 후보를 직접 지정했더라도 추천 설명을 생략하지 않는다. 추천 단계에서 공개 가능한 근거로
역할에 검토할 가치와 중요한 한계·미확인을 함께 작성하고, 일반 조회와 후보 상세에서 같은 저장
문장을 읽게 한다. 내부 선정 추론을 그대로 공개하거나, 선택됐다는 사실을 적합성의 증명으로
쓰지 않는다. 이 설명은 새로 작성한 해석이며 과거 점수의 미기록 추론을 복원한 것이 아니다.

기준이 바뀐 뒤 유지하는 기존 추천도 설명의 기준 버전을 갱신한다. 새 평가가 1차에서 끝났다면
현재 기준의 근거와 판단은 설명할 수 있지만, 새 2차 점수가 없다는 사실을 보존해야 한다. 과거
점수를 현재 점수처럼 복사하거나 누락을 0점으로 바꾸지 않는다. 추천 유지 여부는 LLM의 판단이고,
유지하기로 한 카드의 기준·설명 일치는 저장 계약이다.

### 긴 체인과 압축

횟수 20·30을 의미 있는 업무 종료 조건으로 삼지 않는다. 실제 취소·lease 상실·실행시간 경계와
업무 완료는 구분한다. context 크기는 성능·정확도 관리 대상이지 성공을 주장할 이유가 아니다.

원본 tool/result trace는 그대로 보존하고 completion에 보내는 복사본만 축약한다. 오래된 읽기 결과의
본문·표를 줄일 때 조회 식별자, 버전, 필터, 범위, 불완전 상태와 다시 읽는 경로를 남긴다. 마지막 결과,
실패와 불확실성, 실제 쓰기 효과, 확인할 초안 원문·revision, 수정용으로 읽은 전체 문서는 임의로
삭제하지 않는다. 보호할 내용만으로 목표 크기를 넘으면 그 사실을 진단에 남기며 결과를 성공 문구로
대체하지 않는다. 압축의 목표는 짧음 자체가 아니라 원본 LLM이 다음 일을 정확하게 이어가는 것이다.

여기서 최신 결과는 마지막 도구 하나가 아니라 직전 모델 응답이 요청한 전체 도구 묶음이다. 병렬 조회의 일부 결과를 모델이 처음 읽기 전에 압축하지 않는다. 그 묶음이 soft 목표를 넘더라도 전부 전달한 뒤, 이후 모델 응답에서 과거 조회의 본문을 축약할 수 있다.


### 전체 결과 프레임과 재조회 가능한 본문

페이지·batch 응답을 고정 문자 수에서 통째로 자르지 않는다. 반환된 후보 ID, 기준 version, 점수, 관계, 실제 효과, 다음 페이지 참조는 하나의 유효한 프레임으로 모두 전달한다. 명시적 상세 프로필 조회의 첫 결과에는 공개 가능한 원문을 제공한다. 긴 체인에서는 오래된 순수 조회의 bio·경력 설명 같은 재조회 가능한 본문만 구조에 따라 축약하고, 생략 사실과 원래 조회 참조를 남긴다. 본문이 생략됐다는 사실을 해당 경력이나 근거가 없다는 뜻으로 바꾸지 않는다. 원본 tool trace는 축약하지 않는다.


### 매칭 기준 변경 이력 적용

Hiring Brief는 텍스트와 Criteria를 합친 저장 단위다. 현재 저장값·저장 변경 이력·검색 실행·평가 결과를 구별한다. 기본 context에는 최근 변경의 시간·수정자·짧은 요약 또는 준비 상태, 기능 목록에는 일반 조회 도구의 이력 능력을 제공한다. 전체 전후 스냅샷은 명시적 상세 조회에서 읽는다. 변경 요약용 보조 Luna는 바뀐 필드만 읽고 이력 설명만 작성하며 기준·검색·연락의 의사결정을 맡지 않는다. 웹 저장에서 생긴 정확한 사용자 검토 요청은 사용자 메시지로 보존한다. LLM/Slack 저장은 그 웹 메시지를 새로 만들지 않는다. [구현 계약](company/company-hiring-brief-history-ko.md)을 참고한다.
