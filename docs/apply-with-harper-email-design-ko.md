# Apply with Harper 이메일 흐름 설계

작성일: 2026-10-13. 상태: 로컬 구현 및 코드·회귀 테스트 완료. 운영 DB 변경은 2026-10-14 적용했고, 이 작업에서 웹/Worker 코드는 배포하지 않았다. 현재 checkout의 코드를 근거로 하며 운영 배포 상태를 뜻하지 않는다.

## 설계의 중심

이메일에서도 웹과 같은 Apply with Harper를 사용한다. 이메일은 화면 조작과 잦은 왕복이 어려우므로, 시작 도구를 호출하면 곧바로 필요한 자료를 읽고 충분한 제안을 한 통에 보낸다. 이후 사용자의 자연어 답장을 이해해 준비를 마무리하고, 사용자가 맡긴 범위에서 가능하면 제출까지 이어간다.

**특정 답장 표현은 제품 계약이 아니다.** 동의·수정·질문·보류가 섞인 어떤 자연어 답장도 현재 요청, 앞선 제안, 저장된 사실과 함께 원본 Career LLM이 이해한다. 예시 문구를 감지하는 코드, 긍정 단어 목록, 별도 intent classifier, 답장 유형별 상태 머신을 만들지 않는다. 도구의 accept·ignore 등은 모델의 해석을 실행하는 기존 명령이며 사용자 표현의 분류표가 아니다.

공유의 중심은 코드와 업무 계약이다. 자료 읽기, 제안 생성, 답변 반영, 이력서 저장, 지원 실행을 공통으로 유지한다. 사용자에게도 판단에 필요한 실제 수정 문구와 지원 내용을 충분히 보여준다. 이메일 전용 제안 엔진·이력서 작성기·지원 봇은 만들지 않는다.

왕복은 충분한 제안 뒤에 사용자가 의사를 밝히고 결과를 받는 정도를 목표로 한다. 메시지 수를 고정하지 않는다. 이미 충분히 맡긴 일은 다시 묻지 않고, 필수 정보나 새로운 중요한 결정이 있을 때만 필요한 내용을 묶어서 확인한다.

## 원하는 경험

### 준비 요청을 받으면

원본 대화 LLM이 기존 도구로 대상 역할과 이력서를 식별한다. 기존 대화나 현재 첨부로 알 수 있는 선택은 다시 묻지 않는다. 요청 대상이 실제로 모호하거나 읽을 이력서가 없을 때만 필요한 확인을 한다.

시작 도구는 `simulate_application`이다. 입력은 기존의 `document_id`와 `roleId` 또는 `official_job_slug`를 유지한다. 이메일에서는 이 호출이 즉시 준비로 이어진다. 사용자에게 시작 버튼을 누르게 하거나, 시작하겠다는 말만 담은 메일을 먼저 보내지 않는다.

JD 링크와 실제 지원 양식의 읽기를 끝낸 후 그 결과를 함께 사용해 제안을 만든다. 확인에 실패한 부분은 미확인으로 남기되 읽을 수 있는 자료를 바탕으로 준비를 계속한다. 이 단계에서는 사용자 원본을 수정하거나 회사에 파일을 전송하지 않는다.

### 첫 유용한 답장을 보낼 때

메일 본문만으로 어떤 작업을 제안하는지 판단할 수 있어야 한다. 필요한 내용은 다음과 같다. 모든 메일에 같은 목차나 순서를 강제하지 않는다.

- 대상 포지션과 사용할 이력서, 준비 방향에 영향을 주는 JD 요건.
- 수정할 위치, 실제 수정 문구, 그 수정이 필요한 이유. 변경 전 문장은 비교에 필요한 만큼 포함한다.
- 관측된 필수 작성물이 있으면 해당 질문과 준비한 답변 원문. 없는 경험이나 자격을 채워 넣지 않는다.
- 꼭 필요한 미확인 정보. 이미 아는 사실은 재사용하고 선택 항목을 채우기 위한 질문은 줄인다.
- 다음에 무엇을 할지. 이력서를 준비하는 범위인지, 준비 후 해당 회사에 제출까지 하는 범위인지 분명히 설명한다.
- 대신 제출이 어려운 경우 그 이유와 직접 지원 경로.

수정안과 작성물을 웹에서 다시 검토해야만 답할 수 있게 하지 않는다. 전체 프로필과 JD를 옮겨 적는 대신 사용자의 결정에 필요한 내용에 집중한다. 원본 Career LLM이 메일 전체의 설명·질문·순서를 정한다. 코드로 title/reason/question을 뒤에 조립하지 않는다. 수정 문구·작성물·질문·링크도 현재 자료를 읽은 LLM이 본문에 직접 작성한다. 코드의 passage ref 치환, 별도 검토 내용과 링크 뒤붙임은 없다. 후속 답장은 실제 대화와 기존 발송 내역을 읽어 작성하며, 출력 문구를 판정하는 별도 검토 fingerprint를 저장하지 않는다.

사용자는 자유롭게 답할 수 있다. 지정된 승인 문구, 번호 입력, 이메일용 체크박스 문법은 요구하지 않는다.

### 답장을 받으면

원본 Career LLM이 최신 답장, 실제로 전달한 제안, 기존 결정과 현재 준비 상태를 읽는다. 사용자가 허용한 부분을 진행하고 수정 요청을 반영한다. 설명을 묻는 답장에는 설명하며, 의미가 불명확한 경우 그 불명확한 부분만 확인한다.

직접 지정한 수정은 같은 내용을 다시 승인받지 않고 저장한다. 새 사실을 바탕으로 중요한 문구를 새로 제안해야 하면 그 내용만 보여준다. 이미 승인한 수정과 답변을 다시 묻지 않는다. 전체 제안을 수락했다고 해서 답하지 않은 필수 사실이 생기는 것은 아니다.

이력서 저장은 기존 `ready_for_role`로 수행한다. 원본은 보존하고 승인된 변경만 사본 또는 기존 작업본에 적용한다. 저장 결과 원문을 확인해 승인된 수정이 빠졌다면 같은 턴에서 바로잡는다. 변경이 필요 없으면 기존 파일을 그대로 사용한다.

사용자가 맡긴 범위에 제출이 포함되고 실제 지원이 가능하면 기존 `apply_for_role`로 이어간다. 그 의사가 이미 분명한데도 파일 선택이나 제출 의사를 반복 확인하지 않는다. 이력서 준비만 요청했다면 준비까지만 수행한다.

### 결과를 전달할 때

| 실제 결과 | 사용자가 알아야 할 내용 |
| --- | --- |
| 직접 지원 필요 | 준비한 이력서와 실제 변경 요약, 작성물, 지원 링크, 본인이 해야 하는 남은 조치. 추가 수정은 답장으로 요청할 수 있다. |
| 제출 확인 | 어떤 포지션에 제출됐는지와 제출한 자료. 사이트에서 확인된 접수 근거가 있을 때만 완료로 표현한다. |
| 새로운 필수 정보 필요 | 완료한 준비를 보존하고, 새로 필요한 정보와 그 용도를 함께 묻는다. |
| 실패 또는 접수 여부 불명 | 확인된 사실과 사용할 수 있는 준비 자료, 확인 또는 직접 진행할 경로. 불명확한 접수를 자동으로 재시도하지 않는다. |

제출 후의 이력서 수정과 이미 전송된 지원서 수정은 구분한다. 사이트의 수정 기능을 실제로 사용하지 않았다면 제출한 내용까지 바뀌었다고 말하지 않는다.

## 현재 구현과 연결해야 할 부분

| 영역 | 현재 checkout에서 확인한 사실 | 설계 변경 |
| --- | --- | --- |
| 시작 | `simulate_application` 최초 호출은 카드만 만들고 웹 Start가 준비를 실행한다. 새 활동에는 `startOfferId`가 필요하다. | 카드 표시와 준비 시작을 분리한다. 이메일은 현재 인증된 요청으로 공통 준비를 실행한다. |
| 자료 순서 | JD는 제안 전에 읽지만 저장본이 있으면 외부 링크 조회를 생략한다. 지원 양식은 첫 제안 뒤에 별도로 읽는다. | 이메일은 JD 링크와 양식 결과를 첫 제안 전에 확보한다. |
| 검사 조건 | `needsApplicationInspection`은 분석 완료 상태를 요구한다. | 검사 자체의 실행 자격과 각 채널의 호출 시점을 분리한다. |
| 대화 실행 | 웹 chat route가 지원 활동 context와 도구 dispatch를 관리한다. 서버용 `runCareerChatTurn`은 별도 경로다. | 제안 결정·이력서 저장 실행을 공통 모듈로 추출하고, 이메일 adapter가 기존 세션 context·응답·브라우저 서비스를 직접 사용한다. |
| 이메일 도구 | 이메일 adapter는 일반 업무 도구 allowlist만 제공한다. | 시작과 활성 지원 도구를 현재 활동에 맞게 노출한다. |
| 브라우저 답변 | 웹은 별도 batch 제출 경로로 답한다. 준비 모드의 `manage_simulation_session`은 `respond`를 노출하지 않으며, legacy 도구의 답변 schema도 현재 브라우저 선택 계약과 같지 않다. | 기존 일반 응답 동작을 최소 입력으로 공통화해 자연어 답변도 같은 batch 처리에 연결한다. |
| 외부 전송 | 브라우저는 실제 전송 요청을 보류하고 fingerprint·파일 revision·실행 영수증을 검증한 뒤 해제한다. | 기존 사용자 지시에 근거해 현재 요청을 실행하는 경로를 추가하되 이 검증을 유지한다. |
| 이메일 완료 | 이메일은 저장된 assistant message가 있으면 발송으로 진행한다. | 준비나 브라우저가 미완료면 재개하고, 유용한 답변이 준비됐을 때만 저장·발송한다. |

새 Next 이메일 runtime의 [운영 문서](email-vercel-runtime-ko.md)는 미배포 구현으로 설명한다. 이 설계는 해당 Career adapter 경로를 대상으로 한다. 적용 시 활성 runtime을 별도로 확인해야 하며, legacy Python 경로에 같은 지원 로직을 복제하지 않는다.

## 공통화 범위

### 공통 업무 모듈과 얇은 채널 adapter

`src/lib/career/simulation/`의 기존 서비스들을 공통 업무 계층으로 유지하고 웹 route에 남은 연결부만 추출한다. 새로운 범용 workflow 프레임워크를 만들지 않는다.

공통 연결부의 책임은 현재 활동 읽기, prompt context 생성, 제공할 도구 선택, 도구 실행, 변경 후 context 갱신, 비동기 결과 재개다. 웹과 이메일 모두 이 연결부를 사용한다. 이메일 adapter에 업무 함수를 복사하거나 전체 웹 chat route를 내부 HTTP 호출로 우회하지 않는다.

| 공통 업무 | 웹 표시·입력 | 이메일 표시·입력 |
| --- | --- | --- |
| 역할·이력서 식별과 준비 시작 | 시작 카드와 버튼 | 요청을 이해한 뒤 바로 시작 |
| JD·양식 검사와 제안 writer | 기존처럼 첫 제안 뒤 양식 검사 가능 | 양식 검사까지 기다린 뒤 제안 |
| 같은 actions·batches와 승인된 내용 | composer와 버튼 답변 | 본문 제안과 자연어 답변 |
| 같은 이력서 저장·지원 실행·결과 사실 | 카드, 진행 상태, 결과 게시 | 문서 전달, 질문 또는 결과 메일 |

채널은 인증된 서버 context가 정한다. 모델에게 화면 표시 여부, 확인 생략 여부 등 실행 정책 플래그를 선택하게 하지 않는다. 채널별 차이는 시작, 자료 대기 시점, 전달 방식에만 둔다. 이력서 품질, 사실 판단, 사용자 지시 해석은 같은 계약을 사용한다.

### 시작과 읽기

카드의 `offerId`는 웹의 시작 출처로 남기고, 활동 시작의 필수 조건을 카드 존재에서 인증된 시작 요청으로 바꾼다. 이메일은 현재 source message와 job을 사용하며 가짜 카드를 저장하지 않는다. 기존 웹 데이터와 UI는 호환한다.

이메일의 순서는 `역할·이력서 확인 → JD 링크 읽기 → 실제 양식 읽기 → 동일 writer로 제안 → 본문 답장`이다. 읽기를 제안 뒤로 미루지 않는다. 같은 준비 요청에서 이미 읽은 원문은 재사용하고 중복 조회하지 않는다. 저장본만 있는 경우 링크를 확인하며 실패하면 저장본과 그 한계를 제공한다.

현재 양식 검사의 lease·run ID·revision 충돌 처리는 유지한다. 웹과 이메일이 같은 활동을 확인해도 브라우저 검사를 중복 시작하지 않는다. 검사 실행 조건을 공통으로 분리하되 웹의 기존 호출 시점은 유지한다.

writer에는 완료된 `applicationForm` 또는 확인 실패 사실을 전달한다. 실패는 관측의 한계이지 필수 항목이 없다는 뜻이 아니다. 로그인·접근 제한이 있더라도 가능한 이력서 준비는 마친다. 이미 완료한 검사를 초기 제안 뒤에 다시 예약하지 않는다.

### 대화 context와 기존 도구

공통 context는 현재 역할과 문서, 현재 제안·답변, 저장본, 지원 가능 여부, 브라우저가 기다리는 입력을 담는다. 활동 전체 원장이나 모든 과거 메일을 매번 넣지 않고, 필요한 원문은 기존 읽기 경로로 가져온다.

이메일의 최근 메일 요약만으로 승인 대상을 복원하지 않는다. 현재 runtime은 최근 outbound 본문을 잘라 넣으므로 긴 수정안이 누락될 수 있다. 실제 발송 메시지에 연결된 batch의 변경·작성물 원문을 공통 context에서 읽고, 사용자에게 보이지 않은 문구를 승인된 것으로 취급하지 않는다.

초기 writer와 후속 대화 모델은 기존 역할을 유지한다. 새로운 메일 전용 writer, 답장 분류기, 도구 내부의 숨은 승인 판단 LLM을 추가하지 않는다. 일반 대화 LLM이 현재 context와 공통 도구로 계속 처리한다.

`manage_application_suggestions`는 제안 수정과 결정을, `ready_for_role`은 이력서 저장을, `apply_for_role`은 지원 실행을 소유한다. 브라우저의 대기 중 질문에는 기존 `manage_simulation_session`의 일반 응답 동작을 필요한 범위만 노출해 재사용한다. 입력은 현재 batch/item 식별자와 답변 또는 선택값이며, 기존 검증과 `resumeApplicationBrowser`로 연결한다. 새로 의도·승인·재개를 각각 판단하는 도구를 만들지 않는다.

질문 응답의 선택값은 현재 서버가 제공한 선택지와 매칭한다. 자연어에서 어떤 선택을 뜻하는지는 원본 LLM이 판단하고 코드는 식별자·소유권·현재 batch 여부만 검증한다. legacy 도구의 큰 action schema를 이메일에 통째로 노출하지 않는다.

현재 웹 지침의 ‘composer가 보여주므로 본문에 반복하지 않는다’는 표현만 채널별로 분리한다. 이메일에서는 실제 제안을 본문으로 전달하고 사용자의 답장을 기다린다. 도구 루프를 끝내는 것과 최종 본문을 쓰지 않는 것은 다르므로 종료 처리도 분리한다. 같은 제안 도구를 불필요하게 반복 호출하게 하지 않는다.

## 이미 받은 지시로 실제 전송까지 이어가기

핵심은 새로운 ‘이메일 승인 시스템’을 만드는 것이 아니라 **현재 사용자 지시가 이 작업을 허용하는지 원본 LLM이 판단하고, 동일한 실행기가 정확한 요청을 실행하게 하는 것**이다.

### 의미 판단과 실행 검증

원본 Career LLM은 사용자가 받은 제안과 최신 지시를 함께 보고 수정·파일 준비·해당 회사 전송 중 어디까지 맡겼는지 판단한다. 특정 긍정 표현이 등장했는지로 정하지 않는다. 처음 요청과 이후 정정을 함께 보므로, 첫 제안 메일의 문구 하나만으로 사용자 권한을 좁히거나 넓히지도 않는다.

브라우저가 외부 전송을 보류하면 현재 요청의 검증 가능한 내용과 파일, 해당 사용자 지시를 **기존 Career 대화의 continuation**에 제공한다. 원본 LLM은 이미 맡긴 작업이면 기존 응답 명령으로 계속하고, 새로운 중요한 정보·동의가 필요한 경우에만 사용자에게 묻는다. 이것은 별도 승인 심사 모델 호출이 아니라 같은 대화의 일반 도구 사용이다. 제출 executor나 browser agent가 스스로 사용자 동의를 만들어내지 않는다.

현재 서버용 turn의 입력은 사용자 메시지 중심이므로, 비동기 재개는 기존 source message를 보존한 내부 도구 결과로 연결하는 진입점을 마련한다. 브라우저 결과를 새 사용자 발화로 저장하거나 자동으로 ‘승인했다’는 사용자 답변을 만들지 않는다. 모델이 이미 받은 지시로 대기 요청에 응답한 경우에도 근거는 실제 사용자 메시지이며, 그 전송 판단은 일반 tool trace에 남는다.

서버는 다음 hard boundary를 유지한다.

- 인증된 사용자와 활동, 현재 source message 및 대기 요청의 연결.
- 실제 사용자 지시와 전달된 제안을 가리키는 근거 참조. 사이트 원문이나 인용문을 사용자 지시로 취급하지 않음.
- 현재 batch, 요청 ID·fingerprint, 파일 소유권·revision·hash 일치.
- 취소·종료·권한 변경과 동일 요청의 이미 실행된 영수증 확인.
- 요청을 한 번만 해제하고, 결과 불명 시 자동으로 재전송하지 않음.

코드가 사용자 지시의 의미를 완전히 증명한다고 주장하지 않는다. 의사 해석의 품질은 공통 prompt·충분한 context·대화 평가로 개선한다. fingerprint는 해석이 옳다는 증거가 아니라 판단한 바로 그 요청을 실행한다는 보장이다.

### 필요한 기록만 추가

현재 actions·batches에는 제안 원문과 답변이, 문서에는 revision이, browser approval에는 실제 요청의 fingerprint와 receipt가 있다. 이 사실을 복제한 제출 manifest나 문항별 의미 매핑 표를 만들지 않는다.

추가로 필요한 지속 사실은 ‘이 외부 전송을 어떤 실제 사용자 지시에 근거해 실행했는가’다. 기존 응답·실행 기록에 사용자 message와 필요시 제안 batch의 참조를 연결한다. 비동기 재개 시 현재 지시를 확인하는 Career context와 executor가 이를 읽는다. 웹 클릭과 이메일 답장을 같은 근거 계약으로 취급하고 이메일용 별도 권한 테이블은 만들지 않는다.

승인 전 최종 PDF의 hash는 존재하지 않는다. 제안과 지시를 반영해 `ready_for_role`로 저장한 뒤 실제 파일 hash를 기존 지원 실행에 연결한다. 최종 파일이 바뀌면 이전 요청의 fingerprint를 새 파일에 재사용하지 않는다. 새 저장본으로 현재 지시가 여전히 충족되는지 원본 LLM이 확인한다.

### 전송과 접수 구분

현재 실행기는 최종 제출뿐 아니라 파일 업로드 등 앞선 전송도 보류할 수 있다. 동일한 사용자 지시가 이 지원을 위한 자료 전송을 허용하면 매번 추가 메일을 보내지 않고 같은 경로로 진행한다. 업로드 성공을 지원 완료로 표현하지 않는다.

`submission.status=supported`는 공개 양식 접근이 가능하다는 관측이다. 조건부 질문, 실제 업로드 또는 최종 접수의 성공까지 보장하지 않는다. 새로운 중요한 요구가 드러나면 필요한 부분만 확인하고, 접근 제한이면 준비 자료와 직접 지원 경로를 제공한다.

사이트별 의미 규칙, 일반적인 ATS 요청 해석 엔진, control ref별 새 승인 상태를 이번 변경의 필수 조건으로 만들지 않는다. 기존 실행기가 내용을 보여주거나 정확한 요청을 보류·해제할 수 없는 경우 그 한계를 해결하거나 직접 지원으로 안내한다. 알 수 없는 요청을 포괄 승인하지 않는다.

웹의 기존 최종 확인 화면은 유지한다. 공통 실행 검증을 추출하는 과정에서 웹의 확인 UX를 의도치 않게 없애지 않는다.

## 오래 걸리는 작업과 메일 전달

현재 준비 timeout은 420초이고 이메일 callback 최대 시간은 480초다. 읽기·모델·브라우저·메일 발송을 반드시 한 callback에서 끝낸다고 가정하지 않는다. 사용자 관점에서 끊기지 않는 작업과 서버의 한 번 실행은 구분한다.

기존 application activity에 읽기·제안·브라우저 결과를 저장하고, 기존 reply job에는 연결된 활동과 재개 참조만 둔다. 완료된 읽기나 파일 저장을 다시 실행하지 않는다. 추가 테이블이나 대화 단계 enum을 만들지 않는다.

현재 assistant 본문이 저장되면 바로 발송하는 경로에는 명시적인 미완료 반환 계약이 필요하다. 준비나 브라우저가 진행 중이면 본문을 미리 확정하지 않고 같은 durable job을 재개한다. 정상 대기는 오류 재시도 횟수를 소모하지 않고, lease를 놓을 때 재개 예약을 durable하게 남긴다. 전체 실행 deadline을 넘으면 준비한 자료와 현재 한계를 전달한다.

브라우저의 질문 또는 결과 도착은 해당 reply job의 continuation을 깨운다. 웹 polling이나 새 이메일이 있어야 결과가 나오는 구조를 피한다. 결과 사실을 공통 Career LLM에 전달하고 채널 adapter가 같은 thread로 발송한다. 웹용 결과와 이메일용 결과를 별도 모델로 중복 작성하지 않는다.

첫 메일을 보낸 job은 그대로 완료한다. 사용자의 다음 답장은 새 inbound job이며 같은 application activity를 이어받는다. 한 inbound에서 맡은 미완료 작업은 같은 job으로 재개한다. 새 답장이 도착하면 먼저 LLM이 해석하고, 중단되지 않은 진행 작업은 새 job이 이어받는다. 이미 발송된 첫 제안 job의 본문을 결과 메일로 덮어쓰지 않는다.

기존 provider checkpoint, 발송 idempotency, reply alias와 thread header를 재사용한다. 동일 결과를 중복 발송하지 않고, provider가 이미 받은 메일은 새로 생성·전송하지 않는다. 도구 결과 cache 저장 전에 중단되는 경우도 있으므로 각 side effect의 기존 source 기반 멱등성을 유지한다.

새 답장이나 웹 수정은 최신 source message·활동 revision으로 확인한다. 단순 내부 진행 revision 증가와 승인 대상 자료 변경을 구분해 불필요하게 사용자에게 재승인을 요구하지 않는다. 오래된 메일 답장을 최신 제안 전체에 적용하지 않으며, 같은 역할이라고 다른 스레드의 승인을 합치지 않는다.

## 파일 전달과 범위

메일에는 `getCareerDocumentHref`에서 만든 인증된 문서 경로의 절대 URL을 제공한다. 로그인 후 해당 문서로 복귀하는지 확인한다. `documentId:` 같은 앱 전용 링크는 이메일에 사용하지 않는다.

지원용 파일은 기존 export를 재사용해 최종본을 첨부할 수 있다. 이 경우 저장본과 동일한 revision인지 확인하고 재전송도 같은 파일을 사용한다. 첨부가 제공되지 않으면 실제 확인·다운로드 가능한 링크를 전달한다. 별도 공개 저장소나 영구 공개 URL은 필요하지 않다.

외부 지원서 제출과 Harper 내부 Role 연결 수락은 기존 계약대로 구분한다. 준비 요청 자체를 회사 소개 동의로 바꾸지 않는다. 기존 소유권, 역할 가용성, test-only 격리와 공유 권한 검증은 공통으로 유지한다. 이 설계는 추천·Memory 저장 정책이나 회사 측 메시지 경로를 변경하지 않는다.

## 검증 계획

로컬 구현의 코드 기반 검증 결과는 [검증 기록](testing/apply-with-harper-email-20261013-ko.md)에 정리했다. 실제 모델의 다중 턴 의미 판단과 메일·브라우저 통합 검증은 별도이며, 이를 실행할 때는 [평가 registry](evaluation/README.md)와 관련 태스크 계약에 따라 신규 입력·gold version을 등록한다. 기존 frozen 평가를 덮어쓰지 않고 [제안](evaluation/application-suggestions/README.md), [이메일](evaluation/email-channel-reply/README.md), [지원 실행](evaluation/agents-hosted-resume-upload/README.md)의 canonical runner를 확장한다.

평가는 특정 답장 단어를 맞히는 시험이 아니다. 같은 의사를 다른 언어·말투·길이로 표현해도 같은 결과가 나오는지, 비슷한 표현도 문맥과 제한이 다르면 그 차이를 지키는지 확인한다. 질문과 수정이 섞인 답장이나 처음 보지 못한 후속 요청을 같은 도구로 처리할 수 있어야 한다. 평가 사례를 runtime 분기로 옮기지 않는다.

필수 검증 범위는 다음과 같다.

- 준비 요청부터 첫 메일까지 JD·양식 결과가 반영되고, 사용자가 볼 수정 원문이 빠지지 않는다.
- 충분한 정보와 위임이 있으면 반복 확인 없이 저장·제출·결과 전달까지 완료한다.
- 부분 수정, 준비만 요청, 질문, 철회, 미확인 필수 정보, 새 지원 요건을 문맥대로 처리한다.
- 저장된 수정과 원본 보존, 실제 제출 파일, 접수 증거가 일치한다.
- 지연, 중단, 중복 수신, 파일 변경, 오래된 답장, 동시 웹 수정, 발송 후 기록 실패에도 중복 제출이나 잘못된 완료 안내가 없다.
- HTML과 plain text 모두 카드 없이 이해할 수 있고 문서·지원 링크를 사용할 수 있다.
- 웹의 시작 카드, composer, 준비와 제출 확인 흐름이 유지된다.

의미와 표현 품질은 실제 원문과 실행 결과를 함께 읽어 판단한다. 문자열 일치나 키워드 점수로 사용자 의사를 채점·수정하지 않는다. 구조·소유권·revision·중복 실행 경계는 코드 검사로 검증한다.

왕복 수, 첫 유용한 메일까지 시간, 중복 읽기와 모델 호출, 완료까지 비용을 관측한다. 필수 확인을 생략해 왕복 수를 낮추지 않는다. 비운영 DB·메일 capture·합성 접수처에서 검증하며 실제 회사에 테스트 지원하지 않는다.
