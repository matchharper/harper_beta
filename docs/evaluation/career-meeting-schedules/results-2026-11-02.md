# Career 실제 일정 로컬 검증 — 2026-11-02

`meeting_schedules` 확장으로 외부 약속을 보관하고, 동일 Career agent가 원본 메일을 읽어 일정과 준비·리마인드 작업을 함께 관리하는 경로를 확인했다. 운영 DB 적용·배포·실제 사용자 이메일 발송은 실행하지 않았다.

## 실제 모델

고정 v1 사례 3개를 `gpt-6.1-sol / high`, 실제 capability runtime·prompt·도구 schema·일정 executor와 격리된 PGlite 함수로 실행했다. 기계적 검증 이후 전체 tool trace와 실제 이메일 subject/body를 직접 검토했다.

| 사례 | 확인 결과 |
| --- | --- |
| 신규 확정 | 메일 원문을 읽고 Role에 연결한 일정 1개 생성, 실제 준비 안내와 참석 링크를 담은 이메일 작성, 면접 전 작업 예약 |
| 시간 변경 | 기존 일정 ID를 유지하며 시각 수정, 기존 예약을 새 면접 전으로 이동, 변경 안내 작성 |
| 취소 | 기존 일정 및 연결 작업 취소, 대체 시간이 없음을 안내, 회사 연락이나 Calendar 변경을 주장하지 않음 |

첫 실행 `runs/2026-11-02T08-26-55-019Z/`은 DB 검증은 통과했지만, 가상 발송 receipt가 `sent`와 `No actual email sent`를 동시에 모델에 제공해 불필요한 재확인과 미래 지시 변경을 유발했다. 평가 fixture를 실제 제품의 `formatCareerEmailReceipt`와 동일한 관측 사실로 수정했다. 실제 메일 transport는 계속 capture-only다. 이는 출력 선별 재시도가 아닌 fixture 계약 수정이며 frozen 사례·gold는 그대로 유지했다.

수정 후 전체 실행 `runs/2026-11-02T08-33-47-895Z/manifest.json`에서 3개 모두 통과했다. 신규 사례는 fixture가 지원하지 않는 선택적 `read_talent_activity_events` 조회에서 오류를 받았으며, 이미 제공된 연락 이력으로 이어가 완료했다. 이 선택적 조회를 포함한 hosted 환경의 전체 통합 검증으로 해석하지 않는다. 원본 provider 입력·출력과 model 설정·소스 hash는 무시되는 owner-only runs 디렉터리에 보관한다.

## 코드·DB·화면

- 변경 경로의 자동 검증 39개 통과: 저장·취소·시각 변경, 소유권, 요청 멱등성, 중복 source key, 동시 수정, 기존 회사 trigger 격리, 72시간 context, 별도 예약의 실제 collector 실행, Gmail query·페이지·원문 thread, 취소/변경 후 발송 차단, 도구 가용성과 한국어·영어 UI.
- 전체 TypeScript 검사와 새 production 파일 ESLint 통과.
- 실제 AppointmentList와 프로젝트 CSS를 Playwright로 1280px/390px에서 렌더링하고, 일정 펼치기·정확한 미팅 URL·종료 시각 없는 표시를 확인했다. `output/playwright/appointments-desktop.png`, `appointments-mobile.png`는 무시되는 로컬 산출물이다. 인증된 전체 Career 브라우저 E2E는 아니다.
- 전체 tool 선택 테스트에는 기존 company follow action의 `read` 기대값 누락 1건이 남는다. 이번 일정 도구 테스트는 별도로 통과했다.
- 전체 번역 검사는 기존 `ApplicationStartCard.tsx`의 `career.apply.start`에 서로 다른 한국어 원문이 있어 실패했다. 새 일정 키 5개와 공통 재시도 키는 코드 원문/한영 사전 일치를 별도 검증했다. 번역 DB에는 쓰지 않았다.

실제 Gmail OAuth, hosted PostgREST, 회사 Calendar API 및 이메일 delivery provider는 이번 확인 범위에 없다. 회사 trigger 부작용은 기존 trigger의 호출 경계를 로컬 capture 함수로 검증했으며, 회사 기능 전체를 재평가한 것은 아니다. Migration은 기존 hosted 구조를 읽어 만든 뒤 로컬 DB에 적용해 확인했으며 운영 적용은 별도 배포 단계다.
