### ABC04·ABC05 empty output 진단

이 둘은 모델이 빈 JSON을 작성한 것이 아니라 선택된 OpenRouter upstream이 generation
중 error finish를 반환한 serving failure다. max run의 두 오류는 모두 router metadata상
`strategy=direct`, `attempt=1`, selected provider=`Together`였다. 비교용 high run의 유일한
동일 오류(ABC05 2차)도 Together였다. max에서 Together가 선택된 call은 이 두 건뿐이고
둘 다 실패했지만 표본이 너무 작으므로 Together 전체 장애율로 일반화하지 않는다.

정확한 provider 내부 원인은 이 artifact만으로 복원할 수 없다. response body에는 오류
detail과 usage가 없었고 evaluator가 OpenRouter generation ID/header를 보존하지 않았기
때문이다. 962.6초 뒤 실패한 ABC04와 25.8초 뒤 실패한 ABC05의 시간 차이는 같은 prompt
validation 오류보다는 queue/generation worker 등 upstream serving 경로의 변동과 맞는다.

평가 runner의 transport는 production prompt·판단 로직과 별개로 benchmark용
`call_once`를 쓴다. 이 함수는 SDK exception만 한 번 재시도하고, HTTP response object가
반환되면 `finishReason=error`와 empty content여도 attempt를 성공적으로 끝낸다. 따라서
두 call 모두 `attemptCount=1`이고 OpenRouter의 다른 endpoint나 worker의 configured
fallback을 실행하지 않았다.

Production 1차 availability와는 구분해야 한다. 실제 worker의 GLM prefilter는 malformed
JSON이나 empty output이면 configured direct DeepSeek fallback을 한 번 실행한다. 실제
2차 기본 모델은 Claude Sonnet 5다. 그러므로 이 두 실패는 GLM/OpenRouter/Together의 raw
serving reliability에는 포함해야 하지만, production에서 두 후보가 그대로 최종 결정
불가가 된다는 뜻은 아니다.

## 결론과 prompt 수정 계획

이 13개 challenge set에서는 `max`를 채택할 근거가 없다. 더 느리고 비싸면서
추천 recall과 output 안정성이 낮고, 핵심 hard-negative 오류도 해결하지 못했다.
두 건의 개선보다 네 건의 회귀(ABC04·06·09·10)가 더 컸다. 현재 비교만으로는
`high`가 상대적으로 낫지만 `high` 역시 release gate를 통과하지
못한다.

프롬프트는 이 run에서 수정하지 않았다. 다음 prompt 버전에서는 특정 사례나 회사명을
넣지 않고 아래 원칙을 일반화해 실험한다.

1. 역할 국가의 현재 거주·학업·근무 기록이 있으면 일반적인 현지 언어와 근무 조건을
   충족한 것으로 보고, JD가 시민권·clearance·license·무스폰서 자격을 명시할 때만
   별도 hold를 허용한다.
2. exact 도구명이 없어도 동일 기능을 production에서 end-to-end로 구현·출시·운영한
   구체적 인접 증거가 있으면 A를 hold로 낮추지 않는다.
3. C의 `unfit`은 일반적 불확실성과 구분하고, 회사가 명시한 높은 선별 bar를
   충족한다는 독립적 증거가 부족한 경우의 calibration 예시를 비식별적으로 보강한다.
4. 출력 계약은 입력 role을 정확히 한 번씩 전부 반환하도록 더 짧고 명확하게 만들고,
   coverage/empty-output retry는 prompt와 분리된 transport 실험으로 평가한다.

위 변경은 별도 prompt version과 새 run으로 검증하기 전 production prompt에 적용하지 않는다.
