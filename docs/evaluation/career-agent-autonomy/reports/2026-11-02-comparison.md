## 해석과 다음 우선순위

1. **도구 접근성만의 문제는 아니다.** 웹 도구가 항상 있는 기준에서도 짧은 경력 케이스는 질문에서 멈췄다. 수정 전후 모델과 selector 선택도 같았다. 입력 지침 묶음이 행동에 영향을 줄 수 있다는 관찰은 있지만, main/application/resume 중 어느 한 문장 때문인지는 이 비교로 분리하지 못한다.
2. **질문을 유효한 종착점처럼 만드는 설명을 제거하고, 사용자의 결과를 완료 기준으로 삼는 방향이 타당하다.** 원본 수정만으로 조사와 작성이 생겼다. 별도의 자동 fallback이나 상태 머신은 필요하지 않았다. 질문 도구 자체를 삭제할 근거도 없다.
3. **다음 확인은 도구 수가 아닌 산출물의 실질적 유용성이어야 한다.** 원본 수준의 초안 재저장, 권유만 하고 연락 초안까지는 준비하지 않는 행동, 외부 문서 언어 미준수가 남았다. 지금 사례에 맞춘 명령을 더 붙이기보다, 이번 케이스를 개발 집합으로 남기고 다른 업종·직무·요청 표현의 미관측 사례를 별도 고정해 확인하는 것이 우선이다.
4. **모델 변경은 이후 별도 비교 변수다.** 이번에는 모델 부족이 원인이라고 단정할 수 없다. 현재 가벼워진 동일 입력으로 새 사례를 비교해야 모델의 판단 차이와 입력 문제를 구분할 수 있다.

새 상태 머신, 질문 금지, ‘공고 0개면 회사 검색’, ‘회사 투자 이력을 이력서에 추가’ 같은 규칙을 구현할 근거는 이 결과에 없다. 사용자의 목표, 원본 근거와 실제 실행 수단을 제공하고 모델이 다음 행동을 결정하게 하는 방향을 유지한다.

실제 모델을 사용했지만 검색 결과·웹 페이지·계정·브라우저 관측은 고정 fixture다. 문서 작성·스키마·revision·조회는 제품 코드와 격리된 메모리 저장소를 사용했다. 인터넷 검색 품질, 실제 제출·발송, DB 운영 권한, PDF 생성, 실제 UI, 음성·백그라운드 대화는 검증하지 않았다. Memory 도구 설명을 정본에 맞췄지만 이번 실행에서 Memory 쓰기는 발생하지 않아 그 변경의 행동 효과는 별도로 확인하지 못했다. 반복 2회, 합성 사례 4개, 수정 묶음 한 종류로 일반화 성능이나 개별 지침의 인과 효과를 확정할 수 없다. 전체 원문은 개인정보 계약에 따라 로컬 `runs/`에만 저장하고 커밋하지 않는다.
