## ‘회사 조사·초안 저장 후 질문’ 지시를 넣었는가

**관련 지시를 넣었다.** 특정 회사명이나 ‘반드시 회사 조사→초안 저장→질문’ 순서는 없지만, 결과와 밀접한 아래 문장을 직접 넣었다. 이를 단순한 지침 삭제 효과 또는 새로운 상황에 대한 독립적인 일반화 증거로 설명하면 부정확하다.

현재 `handbooks/resume.ts:2`:

> 회사·제품·직무의 공개 자료도 경력의 맥락과 중요도를 이해하는 근거다.

현재 `handbooks/resume.ts:4`:

> 중요한 개인 기여나 결과가 알려져 있지 않으면 그 부분만 확인하고, 나머지 자료로 가능한 작업을 함께 제공한다.

현재 `handbooks/resume.ts:6`:

> 위임받은 작성·수정은 upsert_document로 저장한다.

공통 프롬프트에도 ‘공개 원본에서 필요한 맥락을 확보’, ‘모르는 사실은 그 사실에 의존하는 일만 막음’, ‘빈 결과나 실패한 경로 다음에도 가능한 일을 판단’이라는 지시를 명시했다. 회사 자료와 개인 성과를 구분하는 지시도 추가했다.

이것은 고정 분기 구현은 아니지만, 최초 사용자가 든 사례와 가까운 방향의 지침 보강이다. **첫 사례에서 나타난 행동 변화를 근거로 범용 자율성 개선을 강하게 주장한 것이 문제였다.** 새 평가에서는 A/B의 제품 지침을 그대로 고정했다.

## 새 평가와 데이터 수정 기록

새로운 12개 상황을 v2로 고정하고 A/B 각각 2회씩 48회 실행했다. v1과 회사명만 바꾼 복제 사례를 만들지 않고 문서 수정, 생각 정리, 면접 준비, 개인정보, 불확실성 등 다른 작업을 포함했다. 모든 자료는 합성이며 새 케이스 작성자는 이전 실험을 알고 있었다. 독립적으로 뽑은 blind holdout은 아니다.

v2 검토 중 `sufficient_resume_review`와 `missing_personal_fields`의 기본 프로필 회사·이메일이 첨부 문서와 다른 데이터 작성 오류를 발견했다. 모델이 그 차이를 묻는 것은 불필요한 질문으로 세지 않았다. v2와 결과를 보존하고, 그 프로필 값만 고친 v3를 별도 고정해 8회를 추가했다. 메시지·공개 페이지·gold의 판단 기준은 변경하지 않았다. 합계 56회다.

## 확인된 부작용과 남은 계약 문제

### 1. B의 불필요한 저장

Atlas 사례에서 A는 문장과 식별 질문을 제공하는 데 각각 19.2초·18.0초, B는 유사한 문장을 파일로 저장하고 같은 종류의 식별 질문을 하는 데 30.4초·33.8초를 썼다. B는 각 실행에서 문서 작성 오류도 한 번씩 복구했다. 호출 횟수가 많아졌지만 유용한 내용은 늘지 않았다.

가장 직접적으로 의심되는 지시는 `resume.ts:6`의 ‘위임받은 작성·수정은 저장한다’이다. 본문 작성과 파일 저장을 묶어, 저장이 요청 결과에 필요한지를 판단할 여지를 좁혔다. 이것은 원인 후보이며 한 문장만 제거한 ablation으로 인과를 분리한 결과는 아니다. 다음 수정이 필요하다면 ‘짧은 소개에서는 저장하지 말라’ 같은 예외 대신 이 무조건 저장 문장을 제거하는 것이 우선이다.

### 2. A/B 공통 문서 도구 계약 혼동

Markdown 작성에 이력서 전용 `source_document_ids` 등 필드를 보내 실제 `upsert_document`가 거절하는 오류가 반복됐다. 모델은 오류 결과를 읽고 정상 요청으로 복구했다. 별도의 품질 재시도는 없다.

- v2 A: 잘못된 구조화 읽기 2회, Markdown 필드 오류 4회.
- v2 B: Markdown 필드 오류 5회.
- v3 A: 도구 오류 없음.
- v3 B: Markdown 필드 오류 2회.

도구 계약을 맞추는 일이 남아 있다는 증거다. 상위 프롬프트에 ‘더 적극적으로 하라’를 반복해 해결할 성질이 아니다. 이 작업에서는 제품 schema나 도구 설명을 추가 수정하지 않았다.

### 3. 지침을 줄인 뒤에도 지켜진 경계

전화번호 수정 4회 모두 최종 저장 본문을 원본과 비교했다. 전화번호 외 본문·파일 이름·영어·비공개 상태는 같았고, 동일 문서 revision만 3→4로 바뀌었다. 모든 업로드 원본도 보존됐다.

성과 정정, 공개 소개문, 일회성 해외 탐색, 답장 준비, 충분한 이력서 검토에서는 불필요한 문서·프로필·Brief 쓰기 요청이 없었다. 56회에서 외부 발송·지원 시도도 없었다. 개인정보·권한·필수 개인 질문의 경계가 이번 축약으로 무너지는 현상은 관찰되지 않았다.

실제 발송이 승인된 후의 연속 실행, 회사 소개 수락 후 자료 pinning, 일정 재개, 외부 원본의 Memory 저장, 음성·백그라운드 경로는 이 케이스들로 확인하지 않았다. 그 영역의 품질이 보존됐다고 확장해 주장하지 않는다.

56회 모두 끝까지 완료했고 provider 요청 207회는 전부 HTTP 200이었다. 실제 오류 결과를 받은 도구 호출은 원본 모델이 복구했다. DB·메일·브라우저 외부 네트워크는 차단했고, 차단 로그는 합성 DB 주소의 telemetry 기록뿐이다. 문서 작성·조회·수정은 제품 코드를 격리된 메모리 저장소에 연결했다. Memory 쓰기는 fixture에 요청 인자를 기록했으며 운영 DB 저장을 검증한 것은 아니다.

## 결론과 다음 수정의 우선순위

1. **새 사례의 범용적인 과제 수행은 같다.** B가 전반적으로 더 자율적이라는 결론은 유지하지 않는다. 명확한 이점은 입력 축소이며, 일부 상황에서 준비 자료가 늘었고 일부에서는 불필요한 저장이 늘었다.
2. **무조건 저장 지시부터 제거할 대상이다.** 작성과 저장을 하나의 필수 동작으로 만들지 않고, 사용자가 위임한 결과에 필요한지를 모델이 판단하게 해야 한다. 사례별 예외를 추가할 이유는 없다.
3. **문서 도구의 실제 입력 계약 혼동을 해결할 대상이다.** Markdown과 resume의 적용 필드를 도구 입력에서 명확히 해야 한다. 상위 프롬프트를 다시 늘리는 해법은 맞지 않는다.
4. **최초 회사 조사 사례는 개발에 사용한 예시다.** 관련 지시를 넣고 같은 사례를 재실행한 결과를 새로운 상황에 대한 일반화 증거처럼 취급하지 않는다. 이번 새로운 케이스도 이제 관찰한 개발 자료이므로, 이후 변경은 별도의 미관측 사례와 구분해 평가해야 한다.

이번 요청에서는 제품 지침을 추가 수정하지 않았다. 평가 자료·runner·보고서만 저장했으며 push·배포·실제 발송은 없다.
