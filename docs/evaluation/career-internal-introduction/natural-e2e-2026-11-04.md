# 자연스러운 입력으로 실행한 internal 소개 E2E

2026-11-03 밤–11-04 새벽 KST. 핵심 소개 흐름은 실제 브라우저 → 인증된 API → 로컬 PostgreSQL → 원본 Career/company LLM → 상대 agent → 회사 화면과 메일 수신함까지 확인했다. 운영 배포의 성공률 평가가 아니라, 실패를 재현하고 수정한 개발 E2E다. 운영 변경·배포·실제 사람 대상 발송은 없었다.

## 시작 전에 확인한 사항

1. 운영과 checkout의 구현/스키마 차이: 운영에는 새 agent contact 테이블·함수가 없었다. 기존 운영 Harper workspace는 조회만 했고, 새 동작은 로컬에서 검사했다.
2. 격리: `testOnly=true`, `testFixture=agent-introduction-natural-v1`, 전용 합성 talent allowlist. 합성 회사 팀원 1명·후보자 1명·역할 5개를 사용했다.
3. 전달 대상: DB/API는 loopback, 회사 Slack 연결 없음, 메일은 `capture` 모드. 모델 provider만 실제 호출했다.
4. 입력: 사용자에게 agent 구조·tool 이름·profile ID를 말하게 하지 않는다. 직전 역할/질문을 자연스럽게 이어받는 짧은 발화를 사용한다.
5. 효과: 저장, 평가, 동의, agent 접수, 회사 목록 등록, 팀 알림, 최종 양측 소개를 별도 영수증으로 확인한다. 답변 문장만으로 성공 판정하지 않는다.
6. 반복·충돌·정리: 요청 재전송, 다른 역할의 질문과 버튼 수락이 겹치는 상황, 자료 revision, paused, 임시 데이터 정리를 확인한다.

원래 다섯 대화의 입력과 기대 효과는 실행 전에 [natural-e2e-v1.json](natural-e2e-v1.json)에 동결했다. 추가 paused 역할/짧은 영어 동의, 이메일, 회사 최종 수락과 프로필 질문은 실행 중 범위를 넓힌 탐색적 확인이다. 원래 gold를 바꾸거나 이 추가 확인을 사전 동결 평가로 계산하지 않았다.

## 발견해 수정한 제품 문제

- **Career 요청 실행:** Supabase `from`을 떼어 호출해 `this.rest`를 잃었다. 인스턴스에 bind했다. 같은 요청 ID를 재개해 중복 사용자 메시지 없이 성공했다.
- **신규 사용자 평가:** 아직 derived Behavior Context가 없으면 직접 관심을 표시한 역할도 평가 전에 실패했다. 직접 요청은 이미 저장된 원본 profile/Brief로 평가할 수 있게 했다. 일반 자동 매칭의 Behavior 전제는 유지한다. 실제 모델 평가와 별도 DB 테스트로 확인했다.
- **회사 receiver 권한:** notification reader가 전달받은 scoped admin을 버리고 전역 client를 만들었다. 같은 인증 scope를 하위 reader까지 전달했다. 이후 실제 receiver의 notification 조회가 성공했다.
- **대화 후 화면 갱신:** 비동기 소개가 완료돼도 새 기회/할 일 목록이 남았다. 기존 work polling의 완료 변화에서 관련 query를 갱신한다.
- **잘못된 검색 표시:** 일반 agent 연락·비공개 평가 run이 검색 카드로 직렬화됐다. 실제 run 계약에 따라 검색 표시에서 제외했다. 새 trigger의 TypeScript 타입도 반영했다.
- **회사 조회의 관계 누락:** 회사 `read_talent`에는 agent 소개 관계가 없어 최초 질문에서 legacy 연락을 시도한 뒤 복구했다. 이미 권한을 확인한 recommendation의 root 참조를 읽어 전용 텍스트 projection에 넣었다. 실제 provider 입력에 정확한 root가 전달되는 것을 확인했다. 수정 후 첫 호출부터 올바른 경로를 고르는지의 반복 성능 평가는 별도로 하지 않았다.
- **공유 자료와 근거 없는 재직 단정:** 프로필 formatter의 없는 제목과 종료일 표시를 보완했다. 최종 양측 소개 메일은 공유 자료 대신 일반 경력을 읽던 경로를 역할별 고정 자료로 연결했다. 종료일 누락을 재직 중으로 바꾸는 요약을 제거하고, 공유된 경력의 원문 성과와 날짜를 writer에게 제공한다. 실제 두 번째 메일 입력에는 revision 3 성과와 ‘현재 재직 여부 미확인’이 들어갔고, 출력은 재직 여부를 단정하지 않았다.
- **오류 관측:** 회사 job의 plain Supabase error에서 실제 message를 보존해 누락된 의존성을 진단할 수 있게 했다.

어떤 입력에도 문구별 intent 분기, 고정 성공 답변, 결과를 덮어쓰는 재작성, 별도 심사 모델을 추가하지 않았다.

## 실패와 테스트 환경 보완

처음부터 모두 성공한 실행은 아니다. 원본 trace와 실패 run은 삭제 전 영수증에 보존했다.

- 첫 두 평가 run은 `Current Behavior Context unavailable`로 실패했다. 위 제품 수정 뒤 합성 프로필 그대로 새 역할 평가를 완료했다.
- 다음 두 평가 run은 fixture의 `company_roles` trigger가 빈 internal row를 먼저 만든 탓에 Hiring Brief가 없는 상태였다. fixture의 `ON CONFLICT DO NOTHING`을 기존 빈 request 보완으로 고쳤다. 운영 정책의 오류로 분류하지 않는다.
- 로컬 schema에 locale, role-start/history, contact history, notification/email, company update 함수 등 기존 의존성이 일부 없었다. `introductionConversation.mjs prepare`에 원본 migration의 필요한 의존성을 명시했다. 기존 다른 로컬 환경을 reset하지 않았다.
- 첫 회사 수락의 HTTP 500은 소개 메일과 connected 저장 **이후**의 후속 회사 알림 함수 누락이었다. 따라서 ‘메일 실패’나 ‘연결 미실행’으로 취급하지 않았다. 새 paused 역할에서 수정 후 전체 완료를 확인했다.
- 탐색적 회사 질문 “이분 경력에서 최근에 개선한 성과가 뭐야?”는 필요한 profile/root 정보가 실제 모델에 들어간 것까지 확인했지만, 3.9분 후 `ResponseAborted`와 테스트 회사 탭 종료가 관측됐다. 최종 assistant 답변이 저장되지 않아 **이 추가 질문은 통과로 계산하지 않는다**. 중단의 정확한 원인이나 회사 일반 질문의 지연 개선을 검증했다고 주장하지 않는다.
- 테스트 실행의 최초 일부 실패는 API key 없이 import된 OpenAI client와 예전 JSON formatter 기대값이었다. provider 호출 없는 테스트에는 dummy key를 사용했고, notification 테스트는 현재 텍스트 projection의 정확한 ID/상태를 검증하도록 바꿨다.

## 검증·증거·정리

변경 경로의 테스트 **96개 통과**: scoring/runtime 5, profile/tools 3, company prompt formatter 68, opportunity run projection 9, role notification 2, intro email 9. 마지막 `pnpm exec tsc --noEmit` exit 0, 변경 파일 `git diff --check`와 세 로컬 helper의 `node --check` 통과. 전체 테스트 suite를 실행했다고 주장하지 않는다.

`runs/natural-e2e-v1/`에는 원본 provider 입력/출력, DB 영수증, 테스트 로그, 화면 캡처와 cleanup 영수증을 owner-only로 보존했다. 파일은 gitignored다. 실제 model은 기본 Career `gpt-6.1-sol`, company `google/gemini-3.8-flash`, 기존 최종 intro writer `claude-sonnet-5-5`였다. 모델 선택을 테스트 답에 맞춰 바꾸지 않았다.

1440×1000에서 후보자 기회/소개 modal과 회사 후보 목록/connected pipeline을 시각적으로 확인했다. 최종 양쪽 페이지의 document 크기도 1440×1000으로 viewport와 일치했다. 공개 `/jobs`에서 testOnly 역할은 노출되지 않으므로 실제 Career 진입 query와 생성되는 composer를 사용했다. 공개 공고 게시/검색 버튼 E2E까지 검증한 것은 아니다.

테스트 종료 후 task-owned 앱 3041·메일 3211·브라우저를 종료했다. 역할 5개, 합성 auth 계정 2개와 파생 데이터, capture 메일 3개, 임시 session 파일을 정리했다. exact ID 재조회에서 역할·계정·agent 메시지·회사 job 잔존이 각각 0건이었다. 다른 기존 로컬 앱과 DB는 유지했다. 운영 fixture는 생성하지 않았다.

재현 도구: `scripts/localE2e/introductionConversation.mjs`의 `prepare`, `company-queue`, `career-queue`, `inspect`; `scripts/localE2e/introductionEvidence.mjs`; `scripts/localE2e/cleanupIntroductions.mjs --apply`. 기존 로컬 stack 설정을 재사용하며 prepare만으로 앱/메일 서버를 띄우지는 않는다. 큐 소비는 이 fixture의 exact workspace/talent job만 원본 executor에 전달했다. 배포 큐 서비스 자체는 검증 범위가 아니다.

남은 범위: 운영 migration/배포, 실제 외부 이메일 수신·열람, Slack, 업로드 이력서 파일 선택, 미래 시각의 예약 실행, 모바일 viewport, 위 중단된 일반 회사 질문. 이 보고서의 완료는 로컬 핵심 소개 흐름에 한정한다.

## 결과 보고 전 재점검 — 2026-11-04

최종 DB/cleanup 영수증과 테스트 로그를 다시 대조했다. 테스트 96개는 수정 경로별 최종 성공 실행의 합계다. 최초 묶음에는 API key 없이 import된 검색 projection 테스트 파일 실패가 있었고, 해당 파일의 9개 테스트는 dummy key로 별도 재실행해 통과했다. 실패 로그도 보존했다. 보고 직전 `pnpm exec tsc --noEmit`을 다시 실행했고 exit 0이었다.

중단된 회사 질문은 profile revision 3과 장애 복구 시간 45분→18분 성과가 실제 provider 입력에 들어간 것을 재확인했다. 동일 질문의 초기 context(v1), 원래 두 번의 프로필 조회를 받은 context(v2)를 각각 동결하고 원본 회사 loop/provider로 진단 재생했다. 다만 두 실행 모두 저장된 조회와 다른 인자를 선택하여 replay fixture가 결과를 제공하지 못했다. 이는 운영 도구 오류가 아니므로 성공·실패율이나 제품 수정의 근거로 사용하지 않는다. replay runner는 이런 fixture 누락 후 불필요한 모델 호출을 계속하지 않도록 보완했다.

v1은 인위적인 조회 실패 후 최종 답변까지 진행했으나 판정에서 제외했다. v2는 누락된 조회 4건 이후 진행 중이던 task-owned 실행을 직접 중단했고 이유를 해당 run의 `review.json`에 보존했다. 두 실행 모두 DB·브라우저·메일 효과는 없다. runner 보완은 TypeScript 변환으로 확인했으며, 보완 후 모델 재실행까지 했다고 주장하지 않는다.

따라서 회사 질문의 최종 응답·지연 문제는 여전히 미확인이다. 브라우저 종료가 원인이었다고 단정하지 않으며, 이 사례를 통과시키기 위한 문구별 분기나 새 강제 지침은 추가하지 않았다. 이번 재점검에서 추가 제품 수정이 반드시 필요하다고 확정할 수 있는 새 원인은 찾지 못했다. 소개 핵심 경로의 수정·통과 결과와 이 별도 제한을 함께 보고한다.
