## 최종 Career 대화

모델 선택·reasoning은 원본 `resolveCareerTextChatModel`을 사용했다. frozen v5 입력과 gold는 변경하지 않았다. 원본 profile/material SQL, schemas, capability loader, prompt builder, formatter를 사용한다. `manage_work` 경로는 실제 SQL·work reader/context와 원본 Career loop로 독립 invocation까지 실행했다.

최종 두 run의 구조 assertion은 각각 4/4, 3/3이다. 실제 사용자 답변과 회사 agent에 전달하는 메시지도 읽었다. “회사 agent 접수”와 “팀원이 읽었음/연결 완료”를 구별한다. 일부 답변은 미확정 상태를 별도 문장으로 다시 설명한다. 현재 제품 의미를 잘못 전달하는 실패로 보지는 않았으며, 고정 답변 대본으로 문장을 덮어쓰지 않았다.

raw provider 요청/응답·대화·도구 인자·snapshot·source hash는 각 ignored `runs/<run>/` 아래 owner-only 파일에 보존했다. 자동 runner의 `semanticReview: pending`은 자동 채점하지 않았다는 뜻이다. 이 문서가 별도로 수행한 의미 검토 기록이다.

## 실패를 통해 수정한 부분

실패한 출력과 입력은 삭제하거나 성공 run으로 덮어쓰지 않았다.

1. `2026-11-03T13-27-18-614Z-agent-introduction-first`: 최초 Jobs 관심에서 소개를 바로 접수하는 실패를 재현했다. 원본 main prompt의 최초 관심/이미 제시된 소개 선택 계약을 수정했다. 같은 frozen 사례 반복과 최종 두 턴에서 apply→후속 contact를 확인했다.
2. `2026-11-03T13-28-56-081Z-agent-introduction-materials`: 자료 관련 네 사례를 검증했다. 이후 concurrent-work 코드가 추가되어 실제 도구 구성이 변했으므로 이 초기 통과만으로 최종 완료를 주장하지 않았다.
3. `final-contract`, `final-initial-contract`, `final-direct-handoff`, `work-compatible`: 평가 adapter가 실제 새 `manage_work` 또는 그 query predicate를 지원하지 않는 문제가 있었다. 합성 성공을 반환하지 않고 오류를 기록했다. 실제 general/concurrent-work SQL, source message, work context와 독립 원본 invocation을 fixture에 연결했다.
4. `2026-11-03T14-36-22-086Z-implementation-final`: 7개 중 구조상 4개만 통과했다. 준비된 자료를 기본본의 정보 누락과 혼동해 다시 확인하려는 동작, 작업을 넘긴 원래 대화가 `wait/finish`까지 하려는 실행 책임 충돌, query adapter의 `neq` 및 원본 source 참조 설명 부족을 발견했다.
5. 원본 main prompt의 개인 사실 근거를 **후보자의 진술과 선택한 프로필/문서 버전 및 실제 정정**으로 명확히 했다. 독립 작업을 시작·갱신하면 그 invocation이 효과와 완료를 소유하도록 기존 문단을 수정했다. `manage_work` 설명에 실제 실행자만 wait/finish 가능하다는 DB 계약, 생략한 source_refs는 현재 인증된 사용자 메시지를 사용한다는 계약을 반영했다. adapter의 predicate/list 인자, 완료된 작업·cleanup invocation 처리도 실제 reader에 맞췄다.
6. 최종 수정 후 실패 세 사례 및 나머지 네 사례를 각각 다시 실행했다. 준비한 자료를 그대로 공유하고, 준비가 필요한 두 사례는 실제 독립 원본 invocation이 한 번만 소개를 접수했다.

## 실행 경계 통합 검증

`scripts/localE2e/agentIntroductions.mts`는 loopback DB만 허용하고 localE2e의 합성 fixture를 사용한다. 실제 migration과 coordinator/reader/scheduler를 실행한 뒤 전체 rollback한다. 오래된 로컬 snapshot에 없는 기존 migration 전제도 같은 트랜잭션 안에서 실제 DDL로 보완한다.

확인한 결과:

- 실제 voice tool call을 기존 원장에 기록하고 replay에서 인자를 바꾸거나 다른 사용자의 대화로 사용할 수 없음. 가짜 발화 저장 없음.
- paused Role의 공개 projection과 평가 이전 카드 저장. 비공개 회사 request/status 없음.
- stale material, 공유 비활성화, intake pause는 부분 수락·메시지를 남기지 않음. intake를 멈춰도 기존 소개의 영수증 재조회 가능.
- 동의·자료 pin·회사 inbox job 원자적 저장, immutable 원문 재사용, 새 소개에 대한 기존 accepted Worker 제외.
- 회사 이벤트의 다른 후보자 관계 접근 차단, 후보 게시/자기 사용자 알림 분리 및 멱등 저장.
- 한 번짜리 일정, 중복 occurrence 방지, revision conflict, 자기 미래 실행 pause와 외부 변경의 차이, 다른 책임의 일정 변경 차단.
- 역방향 Career event와 exact receiver source, 공유 실행 예산 상속 및 lease fencing.
- 동시 실행 예약과 예산 소진을 구별하고 실제 사용 시간을 정산.
- 회사 이메일 timeout의 `delivery_unknown` 유지, 원문 보존, 자동 중복 전송 없음. 회사 차단 후 보류 메일은 실제 전송하지 않음.
- 회사가 자기 메일 원문/영수증을 다시 읽을 수 있고 후보자에게는 회사 내부 메일이 노출되지 않음.
- 숨기기만 하면 소개 유지. 명시적 철회 뒤 새 메시지·due 일정은 차단하고 과거 공유 snapshot 보존.

합성 이메일 transport를 사용하여 제출 후 timeout을 재현했다. 실제 메일이나 Slack 메시지를 보내지 않았다. provider acceptance와 사람이 읽었음은 동일하게 취급하지 않았다.

## 재현과 남은 운영 확인

Career는 README의 canonical command를 사용한다. 회사는 `pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/evalCompanyAgentCorrespondence.ts`다. 실제 모델 provider 호출 비용이 발생하며 운영 DB/연락 transport는 사용하지 않는다.

DB 통합 시험은 기존 localE2e stack과 합성 `private/fixture.json`을 먼저 준비한 환경에서 실행한다. production 환경 변수를 사용하지 않는다. 실행할 프로세스에는 `scripts/localE2e/env.mjs`의 `stackEnv().env`를 전달하고, `pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/localE2e/agentIntroductions.mts`를 실행한다. 마지막 `All integration effects rolled back; no messages sent.` 및 모든 assertion 성공을 확인한다. 실패해도 트랜잭션은 rollback된다.

최종 로컬 로그는 `/tmp/harper-agent-introduction-implementation/`의 `final-tests.log`, `integration-final.log`, `tsc-final.log`, 모델 run별 log에 있다. 이 경로는 지속적인 배포 증거 저장소가 아니므로 상세 입력/출력은 위 ignored run artifact와 manifest를 기준으로 해석한다.

실제 브라우저 렌더링·portal focus, 운영 migration/backlog·혼합 버전, 실제 Slack/메일 전달, 운영 비용·지연·처리량은 이 검증으로 확인했다고 주장하지 않는다. 적용 순서, 신규 접수 중단, unknown 메일 복구 및 read-only 관측 쿼리는 [설계/구현 문서 21절](../../internal-role-agent-introduction-design-ko.md#21-구현-결과와-검증-기록--2026-11-03)에 있다. 운영 적용은 별도 명시적 배포 승인 이후 수행한다.
