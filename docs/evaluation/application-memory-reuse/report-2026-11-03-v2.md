# 일관된 사용자 정보로 재검증한 지원 Memory 흐름

2026-11-03 한국 시간. **첫 지원 접수는 성공했지만, 자연스러운 폼 답변의 자동 저장과 새 대화에서의 재사용은 이번에도 실패했다.** 제품 prompt·도구·Memory writer를 변경하지 않은 로컬 실제 UI/LLM/Browser Use 실행이다.

## 변경한 테스트 조건

v1의 계정·대화·접수증을 보존하고 새 전용 계정과 외부 공고 두 개를 만들었다. 이름·이메일·경력·이력서만 미리 저장했다. 생년월일·전화번호·병역·보훈은 Profile, Memory, 이력서나 대화에 미리 넣지 않았다. 최초 Memory 0건, 전화번호 null, 메시지 0건을 확인했다.

페이지와 후보자 소개에서 가상 개인 값을 요구하는 표현을 없앴다. 페이지에는 외부 채용사로 전송되지 않는 독립 검증 환경이라는 안내만 유지했다. `testOnly`, stable `testFixture`, 전용 `testTalentIds`, 로컬 DB 제한과 수신 서버의 전용 지원자/PDF 검사도 유지했다.

원본 Career LLM에는 정상 UI의 지원 요청을 보냈다. 모델이 격리 환경으로 계속 진행할지 확인하여 “네, 이 페이지로 진행해주세요.”라고 답했다. 모델의 첫 질문 폼 574는 **Date of birth / Mobile phone number / Military service status / Veteran status**였고, 가상 값을 넣으라는 설명은 없었다. 실제 폼에 아래 답만 작성했다.

| 질문 | 사용자 답변 |
|---|---|
| 생년월일 | 1994-06-15 |
| 휴대폰 | 010-0000-1234 |
| 병역 | 군필입니다. |
| 보훈 | 보훈 대상이 아닙니다. |

“기억해줘”, “다음 지원에도 사용해줘”, Memory 도구 호출 지시는 한 번도 입력하지 않았다. 폼 답변 저장 이후 원본 LLM의 브라우저 요청도 이를 사용자에게 확인된 정보로 전달했다. `fictional virtual-candidate values`로 전달했던 v1과 다르다.

새 대화에서 원본 모델은 `read_talent_context`를 실제 호출했다. 질의는 Alex Example의 생년월일·전화번호·병역·보훈에 대해 이전에 명시적으로 제공된 사실을 찾는 내용이었고, 결과는 `items: []`, `hasMore: false`, `truncated: false`였다. 이어 `suggest_form`으로 폼 593을 만들었다. 검색을 생략하거나 결과가 잘린 사례가 아니다.

두 번째 브라우저 실행 결과에도 이름·이메일·원본 이력서만 입력됐고, 생년월일·전화번호는 공란, 병역·보훈은 미선택이라고 남았다. 두 번째 질문에는 답하지 않아 실패 상태를 보존했다. 따라서 **두 번째 지원은 미제출**이며 접수증도 없다.

## 저장 판정

- `talent_contexts`: 계정의 전체 행 0건. 삭제된 행도 조회에 포함했다.
- `talent_users.phone_number`: null.
- `career_tool_call:write_talent_context`: 0회.
- `career_tool_call:update_talent_profile`: 0회.
- 첫 폼 응답 턴 577은 정상 완료됐고, 저장 도구가 제공됐지만 호출하지 않았다. 이 누락은 이후 제출 결과 관측 시간 초과보다 앞서 발생했다.
- 네 값의 원문은 폼 응답·대화·브라우저 실행 기록에 남았다. 그 기록의 저장과 다음 대화에서 사용할 Memory 저장은 구분한다.
- 이름·이메일·이력서는 기존 Profile/Documents 원본을 정상 사용했다. 이를 Memory에 중복 복사하지 않은 것은 실패로 세지 않는다.

v1에서 제시한 “가상 값을 요청하는 표현이 저장 생략에 영향을 줬을 가능성”만으로는 이번 결과를 설명할 수 없다. 일반적인 질문과 사용자 사실로 답했는데도 원본 모델이 저장을 선택하지 않았다. 다만 독립 검증 환경이라는 맥락은 여전히 존재하며, 단일 실행으로 실제 서비스의 일반적인 실패율이나 모델 내부 판단 이유를 확정하지 않는다.

## 실행 환경과 한계

- 현재 제품 기본 GPT-6.1 Sol high / Browser Use 기본 모델. prompt override 없음. 시작 시 저장한 관련 소스 11개의 hash는 종료 확인에서도 모두 같았다. 시작 전 다른 작업의 미커밋 UI 변경이 있었으며 이를 수정하거나 되돌리지 않았다.
- 로컬 실제 앱 port 3012, 로컬 Supabase, 전용 수신 서버 port 8778. 임시 터널은 수신 폼만 노출했다. 운영 DB 수정·배포·실제 회사 전송 없음.
- 두 역할 모두 `source_type=external`, `testOnly=true`, `testFixture=application-memory-reuse-v2`, 전용 talent allowlist. fit 0건, 다른 talent 추천 0건.
- Exa 키가 없어 공개 페이지 읽기/검색은 실패했고, 실제 Browser Use로 공고와 폼을 읽었다.
- 브라우저 미리보기가 동의 버튼의 포인터 클릭을 가렸다. 같은 버튼에 포커스 후 Enter로 정상 UI 이벤트를 보내 승인했다. 정상 포인터 클릭 성공으로 세지 않는다.
- 제출은 수신됐으나 브라우저 결과 관측이 시간 초과됐다. 이후 사용자 확인 질문에서 기존 실행 결과를 읽어 완료를 확인했다. 접수증 개수는 네트워크 POST 시도 횟수의 증거가 아니다.
- 실행 중 로컬 Playwright 세션이 더 이상 열려 있지 않아 같은 계정으로 다시 열었다. 대화나 답변을 삭제·교체하지 않았다.
- 원격 브라우저 세션은 결과를 보존한 후 제품의 close API로 종료했다. 로컬 계정·공고·접수증·실패 폼은 재확인할 수 있게 보존했다.
