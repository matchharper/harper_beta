## 저장·입력 경로

관측: 원본 Career LLM은 두 차례 제출까지 진행하면서 Memory writer를 호출하지 않았다. 새 대화에서는 `read_talent_context`에 이전 지원과 지원자 정보를 조회했지만 해당 사실을 얻지 못했다. 같은 대화의 브라우저 실행 요청에는 첫 지원에서 사용한 네 값이 그대로 포함됐다. 따라서 같은 대화의 성공은 Memory 검증 성공으로 세지 않는다.

코드상 동작: `src/lib/career/forms/server.ts`의 `respondToCareerForm`은 폼 응답과 user message를 저장한다. 자동으로 Memory를 추출하는 경로가 아니다. `src/lib/career/agentTurnRuntime.server.ts`의 `readCareerAgentResourceContext`는 저장된 폼·브라우저 목록을 현재 `conversationId`로 제한한다. 장기 사실 저장은 원본 LLM의 `write_talent_context` 판단에 맡겨져 있다. 이번에 그 호출이 없었으므로 새 대화에 전달될 Memory도 없었다.

미확인: LLM이 저장하지 않은 내적 판단의 이유를 확정하지 않았다. 첫 대화에서는 폼과 값을 명시적으로 가상 테스트 자료로 인지했다. 따라서 이 결과를 모든 실제 사용자 개인정보에서도 동일한 실패율이 난다는 주장으로 확대할 수 없다. 제품 prompt·Memory writer·폼 동작은 이 테스트를 통과시키기 위해 수정하지 않았다.

## 부수적으로 관찰한 문제와 한계

- 브라우저 미리보기 패널이 제출 승인 버튼을 가려 포인터 클릭이 실패했다. A에서는 닫기 버튼을 사용했는데 실제 브라우저 세션도 종료되어, Harper가 새 세션으로 복구한 뒤 제출했다. B에서는 동일 버튼에 키보드 포커스를 주고 Enter로 승인했다. 이 조작을 정상 마우스 클릭 성공으로 세지 않는다.
- UI에 React 중복 key 경고가 반복됐다. 현재 다른 미커밋 UI 변경이 있는 작업트리이며, 본 작업에서 해당 코드를 수정하지 않았다.
- 로컬 DB에 제품 reader가 요구하는 `talent_documents.description`이 없어 로컬에만 nullable text 열을 추가하고 스키마 캐시를 갱신했다.
- 로컬 환경에 Exa 키가 없어 `open_url`이 실패했지만, 실제 원격 브라우저로 페이지를 읽고 계속했다.
- 합성 PDF의 seed 추출문에 실제 PDF보다 `experience` 한 단어가 더 있었다. 새 대화의 브라우저가 이를 보고했다. 실제 제출은 원본 PDF 바이트를 사용했고 두 수신 hash가 같았다. 이 fixture 차이는 개인 사실 재질문의 직접 증거와 분리한다.
- 추천은 수동 생성한 fixture다. 추천 순위 모델 품질을 검증한 결과는 아니다. 각 역할은 `source_type=external`, `testOnly=true`, stable `testFixture`, 전용 `testTalentIds`를 가졌다. 두 role의 fit 0건, 다른 talent 추천 0건을 확인했다.
- 서버는 역할마다 접수증 하나를 보존하도록 멱등 처리한다. 접수증 두 개를 네트워크 POST 시도 횟수의 증거로 사용하지 않는다.
