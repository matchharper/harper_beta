# Memory 기본 저장·검색 지침 수정 후 실제 지원 검증

2026-11-03 한국 시간. **새 테스트 계정에서 자연스러운 폼 응답이 자동 저장됐고, 과거 대화를 복사하지 않은 새 대화에서 다른 공고를 개인 정보 재질문 없이 작성·제출했다. 두 지원 모두 수신 서버의 접수증과 실제 필드·PDF 바이트를 확인했다.** 로컬 변경이며 운영 배포·운영 DB 수정·실제 회사 전송은 하지 않았다.

## 변경 내용과 원인 경계

이전 [v2 실행](report-2026-11-03-v2.md)은 원본 모델이 폼 답변과 저장 도구를 받았지만 저장 도구를 선택하지 않았다. 새 대화의 Memory 검색은 실제 실행됐고 빈 결과를 반환했다. 따라서 관측된 실패 경계는 검색 오류나 DB 저장 실패보다 앞선 **저장 실행 누락**이었다. 모델 내부 이유나 개별 문장 하나의 인과 효과를 단정하지 않는다.

- Career 공통 지침에서 Memory를 사용자에 대해 알아두고 다음 대화·작업에 재사용할 사실과 맥락의 기본 저장소로 명시했다. 기존 Profile·Documents·Brief·설정이 소유하는 정보는 원본을 사용한다.
- 정보를 묻기 전에 관련 대화·저장 기록·문서·연결 서비스·공개 자료를 사용자 권한 범위에서 찾아보도록 기존 작업 지침을 수정했다. 현재 보이는 context에 없다는 이유만으로 정보가 없다고 판단하지 않는다.
- 자연스럽게 받은 유용한 사실과 정정을 현재 작업 중 저장·수정하도록 했다. 정확한 값, 적용 범위, 불확실성, 보존 제한을 유지하며 기존 정보 조회로 반복과 정정을 구분한다.
- `suggest_form` 계약에 폼 응답은 대화 기록일 뿐 Profile/Brief/Memory 갱신 자체가 아님을 명확히 했다. 단일 응답과 일괄 응답 모두의 **모델용 후속 입력**에 기억할 만한 사실을 적절한 도구로 저장하라는 안내를 넣었다. 사용자 작성 내용과 화면에는 이 안내를 넣지 않았다.
- 지원 가이드와 브라우저 관측 계약을 수정해 원문의 질문·선택지·도움말을 보존하고, 확인된 사실을 실제 질문의 뜻에 맞게 적용하도록 했다.

별도 추출 모델, 필드별 저장 분기, 새 DB 컬럼, 강제 도구 호출, 의미 기반 중복 검사 규칙은 추가하지 않았다. 이 작업 시작 전 사용자 변경으로 삭제돼 있던 민감 정보 문구의 삭제를 이번 작업의 성과로 세지 않는다. 그 삭제를 유지하고 남아 있던 문장 조각만 정리했다. 기존 미커밋 UI·대화 버전 변경도 보존했다.

## 실패 실행 보존과 최종 테스트 조건

v3는 새 계정에서 첫 폼 답변 후 휴대폰을 Profile, 생년월일·병역·보훈을 Memory에 저장했다. 그러나 브라우저가 `병역 이행 여부`를 더 넓은 의미의 `Military service status`로 보고한 뒤 원본 모델이 이미 받은 `군필입니다.`를 Yes에 대응시키지 않고 다시 선택하게 했다. 저장은 성공했지만 불필요한 재질문이므로 UX 실패로 기록했다. 이 실행은 제출하지 않았으며 접수증도 없다.

원본 라벨·선택지 보존과 확인된 사실 적용 지침을 수정한 뒤 **다시 새 계정으로 v4를 실행했다.** v3의 DB·대화·실패 출력은 보존했다. v4에서도 모델이 질문 폼을 직접 만들었으며, 이번에는 병역·보훈을 Yes/No 선택지로 제시했다. 따라서 v4 성공을 `군필입니다.`라는 자유 입력의 모든 매핑 상황을 검증한 결과로 해석하지 않는다.

v4는 기존 로컬 Supabase 안의 새 전용 계정·회사·외부 공고 두 개·빈 대화·별도 앱 빌드 디렉터리·별도 수신 서버를 사용했다. 전체 DB를 초기화한 것은 아니다. 시작 시 해당 계정의 **Memory 0건, 휴대폰 null, 메시지 0건**을 확인했다. 이름·이메일·일반 경력과 이력서만 미리 저장했다. 테스트 대상 네 사실은 Profile, Memory, 문서, 대화나 prompt에 미리 넣지 않았다.

두 공고는 `source_type=external`, `testOnly=true`, `testFixture=application-memory-reuse-v4`이며 전용 `testTalentIds`만 허용한다. 최종 DB 조회에서도 추천 두 건은 이 계정에만 연결돼 있었다. 추천은 fixture로 생성했으므로 추천 순위 품질은 평가하지 않았다. 실제 Career UI·기본 모델·도구·DB·Browser Use를 사용했다. 사용자 입력에 “기억해줘”나 저장 도구 지시를 넣지 않았다.

## 기본 context에서 누락될 때도 찾는가

실제 두 번째 지원의 provider 입력에는 부분 Memory라는 안내와 함께 관련 Memory 세 건이 모두 자동 선택돼 있었다. 전화번호도 Profile에 있었으며 과거 폼 응답은 포함되지 않았다. 이 E2E만으로는 “초기 context에서 빠진 사실도 찾아오는가”를 증명할 수 없다.

이를 별도로 확인하기 위해 같은 로컬 계정의 실제 DB와 Memory 검색 도구를 쓰는 단일 모델 시험을 실행했다. 첫 입력에는 관련 없는 실제 Memory 세 건만 주고, 생년월일·병역·보훈은 의도적으로 제외했다. 현재 제품의 원본 prompt·모델·capability runtime·도구 schema를 그대로 사용했다. Profile의 전화번호는 제공했고, 이전 대화·폼은 제공하지 않았다. 부작용을 막기 위한 읽기 전용 실행 경계만 둔 **통제된 context 누락 시험**이며 실제 UI 초기 선택기의 실패 사례는 아니다.

요청은 “지원서에 적을 제 생년월일, 휴대폰 번호, 병역 이행 여부, 보훈 대상 여부를 확인해 주세요.”였다. 모델은 `read_talent_context`에 다음 자연어 query를 보내 실제 의미 검색을 수행했다.

> 지원서 개인 정보: Alex Example 사용자가 직접 밝힌 생년월일, 휴대폰 번호, 병역 이행 여부, 보훈 대상 여부. 이전 정정 및 최신 정보 포함.

검색 결과에 목표 세 행이 포함됐고, 이어 `read_profile`로 전화번호를 확인했다. 네 값을 모두 정확히 답했고 재질문·쓰기 시도는 없었다. 이 시험은 정정 전 실행했으므로 답한 값은 `1994-06-15`와 `010-0000-1234`였다.

최종 정리 중 같은 prompt 파일에 다른 작업의 대화 버전·말투·결과 설명 변경이 추가된 것을 확인했다. 기존 실행 증거를 그대로 두고 최신 코드로 이 읽기 시험을 별도 디렉터리에서 1회 더 수행했다. 초기 context에는 여전히 목표 Memory를 넣지 않았다. 모델은 같은 두 조회 도구를 호출했고, 이번에는 **정정된 `1994-06-16`과 `010-0000-5678`** 및 병역·보훈을 정확히 답했다. 생년월일은 이전 값보다 최신 정정이 우선함을 설명했다. 재질문·쓰기 시도는 없었다.

## 변경 경로 검사와 한계

- 관련 단위 검사 48개 고유 테스트 통과: forms/presentation, main prompt/prompt caching, capability runtime, 대화 입력 projection, browser lifecycle/tool projection. 반복 실행된 항목은 고유 개수에서 제외했다. 최종 합쳐진 prompt·폼·capability 경로 22개도 통과했다. 모델용 안내가 실제 provider 입력에 있고 사용자 content/UI에는 없음을 확인했다. v4의 실제 단일 폼 응답에서도 provider 입력을 확인했다.
- 기존 자율성 평가 두 사례를 각 1회 실행하고 전체 출력을 수동 검토했다. `ambiguous_employer`는 문서·Profile·Memory를 확인한 뒤 식별 안 되는 회사만 질문했다. `missing_personal_fields`는 문서·Memory·공개 자료를 조회해 가능한 지원 자료를 만들고, 확인되지 않은 입사 가능일·근무 자격·해당 포지션의 근무 의사만 질문했다. 후자는 첫 문서 쓰기 인자 오류를 받은 뒤 같은 실행 안에서 올바르게 수정했다. 이 두 평가는 고정 도구 관측을 사용하는 모델 평가이며 실제 외부 제출 E2E가 아니다.
- 배경 임베딩 테스트 도구의 최초 실행은 내부 20건 처리 한도로 48건 중 20건만 색인됐다. 테스트 도구를 20건씩 호출하도록 수정하고 동일 멱등 요청으로 완료했다. 최초 오류와 결과를 보존했으며 제품 코드는 바꾸지 않았다.
- 브라우저 미리보기 창이 일부 폼 버튼의 포인터 클릭을 가렸다. 처음 Close를 눌렀을 때 실제 브라우저 세션도 닫혔고, 원본 모델이 새 브라우저에서 준비를 복구했다. 이후 포커스·Enter와 정상 채팅 입력으로 승인했다. 모든 포인터 조작이 원활했다고 판정하지 않는다. 이 UI 문제는 별도 남은 과제다.
- 제품 소스 snapshot과 실제 provider 입력·출력을 보존했다. 두 실제 접수까지의 원본 모델 입력은 snapshot의 결과 설명 지침을 사용했다. 16:53 이후 반복·정정·보존 제한 후속 대화에는 다른 작업에서 바꾼 결과 설명 문장이 들어간 것을 provider 입력에서 확인했다. 최종 파일 대조에서는 `mainPrompt2.ts`/`mainPrompts.ts`의 대화 버전·말투 변경과 테스트용 배경 색인 도구 변경도 확인했다. 이번에 바꾼 Memory·찾고 질문하기 문단은 snapshot과 동일했다. 동시 변경을 덮어쓰지 않고 최신 상태의 관련 단위 검사와 위 실제 조회 시험을 추가했다. 최신 합쳐진 prompt 전체로 두 외부 지원 E2E를 다시 실행한 것은 아니다.
- 실제 모델·브라우저 제공자를 사용한 단일 합성 계정의 집중 검증이다. 외부 페이지의 모든 질문 방식, 모든 저장·검색 상황에 대한 성공률이나 통계적 보장은 아니다. 키워드 품질 판정기, 별도 심사 모델, 성공 출력을 고르는 숨은 재시도는 사용하지 않았다.
- 결과 보존 후 v3/v4 원격 브라우저를 제품 close API로 종료했다. 테스트용 임시 터널·로컬 앱·수신 서버도 정리하고, DB·접수증·실패 실행·모델 입력 증거는 로컬에 보존했다.
