# 원래 요청 대조와 미응답 추천 목록 교체

2026-10-23. 첨부한 원래 요청과 현재 로컬 코드를 대조했다. **전체 재평가 후 미응답 목록 교체는 이번에 수정했다. 원래 요청 전체가 실제 대화에서 모두 검증됐다고 말할 수는 없다.** 이 문서가 이전 보고서의 포괄적인 ‘구조 마무리’ 표현보다 우선한다. 과거 실행 결과는 당시 관찰로 보존한다.

사용자가 이번 점검 중 제외한 **미추천 후보의 이름 검색**, **수락한 사람 전부 표시**는 아래 완료 판정과 앞으로의 자연어 평가에서 제외한다. 기존 평가 원문을 지우지 않고 새 [natural-v3 평가 목록](cases-natural-v3.json)을 사용한다. 후보 ID로 카드를 여는 원래 기능은 제외 요청에 포함되지 않는다.

## 이번에 고친 문제

기존 코드는 새 상위 N명을 뽑은 뒤, 순위 밖에 있는 기존 미응답 후보를 다시 붙였다. 따라서 새 기준으로 평가해도 예전 목록이 계속 남고, 설명 작성 인원도 N명을 넘었다. 이것은 사용자가 요청한 목록 교체가 아니었다.

이제 회사 LLM이 전체 재평가와 추천을 요청하면 다음과 같이 처리한다.

1. 기존 미응답 추천도 모두 평가한다. 새 검색 조건에 안 잡히거나 조회 예산 밖이어도 포함한다. 2차부터 재평가할 때도 같다.
2. 추천 가능한 후보들의 저장된 2차 점수로 상위 N명을 고른다. 기존 후보와 새 후보가 같은 목록에서 비교된다.
3. 선택된 N명의 현재 기준 설명만 병렬 작성한다.
4. 평가와 설명 작성이 끝나면 기존 미응답 목록을 그 N명으로 한 번에 교체한다. 중간 실패 때는 기존 목록을 유지한다.
5. Save·Pass·Accept·Intro·진행 단계 등 실제 결정이 있는 후보는 교체 대상에서 제외한다. 평가 도중 새 결정이 생긴 경우에도 저장 직전 다시 확인한다.
6. 순위 때문에 빠진 후보의 기록은 보존한다. 회사의 거절로 취급하지 않으며, 이후 다른 기준에서 상위권에 들면 다시 추천할 수 있다. 조회 도구도 이 재추천 가능 여부를 알려준다.

**가상 예시:** 기존 미응답 목록이 A·B·C이고 새 상위 3명이 B·D·E라면, 변경 전에는 A·B·C·D·E가 남을 수 있었다. 변경 후에는 B·D·E만 미응답 추천 목록에 남는다. 별도로 Save한 F와 Intro를 요청한 G는 그대로 유지한다. A·C의 과거 추천·평가 기록도 삭제하지 않는다.

‘더 보여줘’ 같은 추가 탐색, 특정 후보만 재평가, 평가만 하고 추천하지 않는 요청은 전체 목록을 교체하지 않는다. 어떤 범위를 실행할지는 회사 LLM이 현재 요청과 기준 변경을 보고 선택한다. 특정 문장·회사·후보를 인식하는 분기는 추가하지 않았다.

‘구현 확인’은 현재 로컬 코드에서 실행 경로를 확인했다는 뜻이다. 과거 실험 관찰, 이번 구조 검사, 최신 코드의 실제 대화 검증을 구분했다. 이 표는 운영 배포 확인표가 아니다.

## 이번 검증의 정확한 범위

- Worker: `test_company_requested_search.py`와 `test_company_requested_replacement.py` **50개 통과**. 전체 재평가, 2차부터 시작, 조회 예산 밖 기존 후보 포함, 추가 검색, 평가-only, 평가/작성 실패, 동시 목록 변경을 확인했다.
- 실제 로컬 PostgreSQL: `test_company_requested_replacement_postgres.py` **3개 통과**. 새 Top N 교체·Save/Pass/Accept/Intro/진행 보존·이전 후보 재추천, 후보 0명일 때 미응답 목록만 비우기, 저장 오류 때 기존 목록 복구를 실제 SQL로 확인했다. 전용 임시 DB와 합성 계정만 사용했고 역할은 생성 시 testOnly로 표시했다. 프로필/역할 reader는 대체했으므로 운영 인증·전체 DB trigger 검증은 아니다. 실제 후보를 사용하는 LLM 평가의 대체 결과로 세지 않는다.
- 웹 reader/검색 adapter **23개 통과**, 검색 도구 계약 대상 **1개 통과**. 재평가 때문에 빠진 후보가 다시 추천 가능하다는 사실, 회사 결정·공개 중단은 계속 보호한다는 사실을 확인했다.
- 함께 실행한 기존 `tools.test.ts` 전체에는 이번 변경 밖의 실패 2개가 있다. Role 이동 도구 기대값과 프로필 읽기 필드 기대값이 현재 코드와 다르다. 전체 테스트가 통과했다고 보고하지 않으며, 이번 작업에서 그 테스트를 고쳐 통과시키지는 않았다.
- 새 LLM API 호출 0, 운영 DB 쓰기 0, 후보자/회사 발송 0, 배포 0. 최신 자연어 4사례의 전체 재실행은 이번 검증에 포함되지 않았다.
