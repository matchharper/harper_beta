# Harper 추천과 대화 품질 검토 · 2026-11-16

이전 16개 서비스 시나리오에서 가입·도구·저장 경로를 확인했다. 그 결과를 추천과 대화의 품질까지 검증한 것으로 보고한 것은 잘못이었다. 사용자가 지적한 운영 메시지를 실제 대화에서 확인했다. 일정을 설명하고, 같은 공고를 걸렀다고 알리고, 공고 확인을 사용자에게 돌려주고, 의뢰받지 않은 지원·공유의 상태까지 덧붙였다. 후보에 관해서도 투자 규모·직함 외에 **현재 일보다 무엇이 좋아지는지**가 약했다. 해당 메시지의 당시 모델 요청 원본은 복구되지 않았다. 아래 원인 판단은 현행 원본 입력과 재현 실험에 근거한다.

## 기준 대화와 실제 응답

- [이상적인 대화 19개](../ideal-dialogues-v7.md)에는 사용자가 실제로 할 말, 앞서 알려진 사실과 Harper가 건넬 완성 답변이 있다. 같은 가상 시장에서 제품 주도권, 기술적 깊이, 현금 보상, 출근 불가를 바꿔 서로 다른 판단이 나오는지 본다. 세 경우는 기존 16개를 만든 뒤 추가한 전이 사례다.
- [실제 출력 38개](2026-11-16-actual-replies.md)는 같은 입력을 두 번씩 실행한 결과다. 채팅 답변과 실제 이메일 도구에 넣은 본문을 확인했다. 모범 답변은 모델 요청에 넣지 않았다. 도구로 여섯 기업을 모두 찾을 수 있게 해 후보 간 판단을 검토했다. 이 층에서는 검색 누락률을 측정할 수 없다.
- [실제 시장 기준 대화](../../career-opportunity-discovery/ideal-dialogues-v3.md)와 별도로, 로그인한 로컬 계정에서 제품 API를 통해 웹 조사·공고 저장·후속 대화를 실행했다. 후속 질문에는 직전 제품 답변 전체가 들어간다. AI 창업자 사례의 기준 답변은 첫 실행 전에 작성했다. 두 번째 사람의 실제 회사 비교는 앞선 실험에서 발견한 포트원과 Cheiron의 공고 원문을 직접 읽고 다음 실행 전에 고정했다. 두 번째 비교는 독립적인 시장 정답에 맞춘 발견율로 계산할 수 없다.

## 어떤 원본을 바꿨나

기본 프롬프트에서 저장·진행 상태 설명 요구와 과도한 반복을 덜었다. 조사한 분량과 사용자가 읽을 분량을 구별하고, 결정을 바꾸는 사실을 대화에 쓰게 했다. UI 용어는 화면 표시를 담당하는 지침에 두고, 예약 지시에는 사용자가 맡긴 목적과 범위를 담는다. 공고 저장 영수증은 실제 성공·실패, 공고 ID, 이번에 읽은 위치·근무 형태·공개 보상을 돌려준다. 아무도 의뢰하지 않은 작업을 하지 않았다는 문장은 제거했다. 원본을 열어 확인할 수 있는 게시·접수 상태는 Harper가 확인한다. 사후 답변 교정기, 금칙어, 특정 회사 우선순위, 정성 점수에 따른 발송 차단은 사용하지 않았다.

정기 추천에는 기본적으로 채팅과 같은 `gpt-6.1-terra` high를 사용한다. 기존 구성인 Haiku는 검색한 속성과 제외 목록을 메일에 옮겨 쓰는 경향이 컸다. 한국어 문체 개선을 위해 비교한 Sol과 Sonnet은 이번 표본에서 긴 보고서·불필요한 고지·추정이 줄지 않아 채택하지 않았다. 38회 본 실행에서 채팅 30회 중앙값 27.1초, 예약 8회 중앙값 27.6초였다. 공급자 호출 188개 합계 입력 3,420,683토큰(캐시 2,685,899), 출력 60,899토큰이다. 한 턴에 같은 입력을 다시 쓰는 도구 후속 호출과 선택기 호출을 포함한다. 별도 구성으로 실행한 Haiku 예약 4회의 중앙값은 13.6초였다. 검색 호출도 달라지므로 모델 교체만의 비용 차이로 볼 수 없다.

## 판정을 재현할 때

표의 점수 외에 세 가지를 더 확인했다.

- 긴 첫 추천을 줄이려고 조사 노트와 대화를 구분하는 가이드 문단을 추가로 시험했다. `recommendation-vs-research-notes` 6회 중 첫 추천 2회 모두 여전히 제외한 회사까지 보고서처럼 정리했다. 이 문단은 원복했다. 짧게 하나를 고르는 후속 답변과 첫 목록의 품질 차이를 그대로 남긴다.
- `priority-change-real-market`에서 첫 질문은 자연스러웠지만, 경력을 받은 두 번째 턴은 포트원·올리브랩스 등을 웹 링크로 설명하고 개인 기회를 하나도 게시하지 않았다. 실제 DB에는 추천 0개였다. 발견 경로와 무관하게 사용자가 나중에 열고 행동할 수 있게 권하는 기회는 개인 기회 화면에 게시한다는 실행 계약을 기회 검색 가이드에 명시했다. `delivered-recommendations`의 같은 입력에서 다시 경력을 먼저 물은 뒤 포트원 두 역할·핑크패커·알고케어를 제시했다. 답변의 공고 카드 4개와 해당 계정의 추천 행 4개가 일치했다. 후순위 두 곳은 기술 전환, 고객 접점, 보상 하한의 근거가 약해 우선순위를 더 좁힐 여지가 있다. 시장 후보는 매번 달랐다.
- 3000번의 실제 계정에서 중단한 대화 뒤 기회 저장이 이어지자 미공유 설명이 붙은 이전 응답도 확인됐다. 중단했던 사용자 입력의 선택 모델은 `gpt-6.1-sol-ultrafast-low`였고 후속 답변에는 모델 ID가 기록되지 않았다. 따라서 그 답변이 기본 Terra의 검증과 같은 모델이라고 단정할 수 없다. 같은 선택 모델로 공고 유입과 짧은 선택을 추가 실험했다. 짧은 선택은 적절했다. 공고 유입은 미공유 설명을 반복하지 않았지만 이력서 본문을 끝까지 읽거나 소개 의향을 묻는 데 이르지 못했다. 기본 모델의 18/19 판단을 이 설정까지 일반화하지 않는다. 첫 실행은 평가기가 앱의 선택 ID와 공급자의 기본 모델 ID·서비스 등급을 혼동해 두 요청을 막았다. 실제 어댑터 기준으로 비교하도록 고친 뒤 `local-selection-wire-contract`에서 두 응답을 얻었다.

변경된 공고 읽기·저장·프롬프트·모델 구성 테스트 45개와 기회 리소스 DB 시나리오 22개가 통과했다. DB 테스트의 최소 스키마에는 기존 `talent_integrations` 테이블이 빠져 있어 첫 시도에 실패했다. 해당 선행 테이블을 포함해 원본 migration을 실행한 결과가 22개다.

고정 자료에 실제 배치 저장 도구의 `postings[]`와 추천 이력 표현을 반영했다. 가상의 `.example` 주소를 실제 회사로 오해하는 문제는 평가 환경의 전제로 분명히 했다. 한 곳을 고르는 후속 질문에는 축약하면서 사라졌던 조건을 되살리기 위해 앞서 생성한 제품 답 전체를 넣었다. v1~v6 결과를 덮어쓰지 않았다. 실행 중 네트워크 장애로 19개 중 16개가 완료되지 못한 시도는 품질 성공 집계에서 제외했다. 실제 시장 실행은 별도의 로컬 계정과 DB를 썼으며 공개 원문 캐시는 공유됐다. 사용자 계정에서 발생한 이메일이나 지원 결과를 품질 점수로 사용하지 않았다.

소스·도구·모델 요청은 owner-only `runs/`에 있다. `01-26-52-799Z-release-candidate-review`가 38개 본 실행, `02-10-48-144Z-declared-priorities`가 가이드 수정 후 6개 재검증이다. 앞선 경과와 실패도 같은 디렉터리에 보존돼 있다. 실제 사용자 대화·토큰은 공개 평가 자료에 넣지 않았다. 추천 문체와 공고 해석은 로컬 변경이다. 기존 운영 예약 하나에는 이전 도구 사용 지시와 미실행 사항이 남아 있어 그 예약의 기존 문구까지 교체됐다고 판단하지 않았다. 3000번 로그인 화면을 위해 운영 DB에 별도로 적용한 범위는 [DB 적용 기록](../../../agent-guidance/rollout-history.md)에 있다.
