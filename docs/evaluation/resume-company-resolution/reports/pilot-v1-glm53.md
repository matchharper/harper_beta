# Resume company resolution GLM 5.3 Flash pilot

## 결론

29개 경력을 모두 실패·성공 대상으로 보면 안 된다. manual gold 26개 중 기존 `company_db`에 연결할 회사가 실제로 있는 경력은 14개였고, 12개는 연결할 내부 행이 없었다. 나머지 3개는 원문만으로 회사가 모호해 평가에서 제외했다.

production 기본 경로를 내부 exact/candidate 조회와 GLM 5.3 Flash 검증으로 바꿨다. Exa는 호출하지 않는다. 내부 검색 1위 후보를 이력서 단위로 batch하고, GLM low 검증 2회를 병렬 실행해 두 응답이 같은 ID에 동의할 때만 연결한다.

정상 완료한 동일 입력 4회 반복에서 false link는 모두 0건, precision은 모두 100%였다. recall은 78.6~100%, exact accuracy는 88.5~100%였다. 평균 비용은 이력서 5개당 $0.000330, 이력서당 $0.000066이었다.

## 방식 비교

| 지표 | DB exact only | DB + Exa max 3 | DB + GLM 합의 |
| --- | ---: | ---: | ---: |
| 자동 연결 | 6/29 | 11/29 | 12~15/29 |
| precision | 100% | 100% | 100% (4/4회) |
| recall | 42.9% | 78.6% | 78.6~100% |
| exact accuracy | 69.2% | 88.5% | 88.5~100% |
| false link | 0 | 0 | 0 (4/4회) |
| Exa 호출 | 0 | 12 | 0 |
| GLM 호출 | 0 | 0 | 10 |
| 5명 비용 | $0 | $0.084 | $0.000296~$0.000357 |
| resolver 평균/이력서 | 0.566초 | 4.200초 | 2.505초 |
| resolver 최대/이력서 | 0.862초 | 5.070초 | 3.885초 |

GLM 정상 실행 4회의 비용 평균은 $0.000330/5명이다. Exa 최종 실행 $0.084와 비교하면 약 99.6% 낮다. resolver 평균 latency도 4.20초에서 2.50초로 약 40% 줄었다. GLM 두 호출은 순차가 아니라 병렬이라 latency가 호출 수에 비례해 두 배가 되지 않는다.

이번 GLM 구조·prompt 보정 과정 전체에서 성공 응답 metadata로 확인한 누적 비용은 $0.007920이다. timeout 응답의 실제 청구 여부는 포함하지 않았다. 이 값은 개발 실험 누계이며, production 1회 비용은 위의 $0.000330/5명 평균이다.

| `v2b` | 12/29 | 100% | 78.6% | 88.5% | 0 | $0.00033590 |
| `v2c` | 13/29 | 100% | 85.7% | 92.3% | 0 | $0.00035716 |

| `v2e` | 15/29 | 100% | 100% | 100% | 0 | $0.00033165 |

네 실행은 각각 GLM 10회, 입력 7,540 token을 사용했다. 출력은 644~887 token이었다. 응답 cache 적용 여부가 달라 token 수가 같아도 관측 비용은 조금 달랐다.

별도 `v2a` 실행에서는 한 이력서의 병렬 호출 중 하나가 12초 timeout되어 해당 batch 전체를 미연결로 유지했다. 이 실행도 false link 0건·precision 100%였지만 resolver 최대 latency가 13.8초였고, timeout 호출의 실제 청구 여부를 응답 metadata로 확인할 수 없어 정상 실행 비용 범위에서는 제외했다. production도 같은 방식으로 fail-open한다.

## 왜 GLM 앞에 내부 후보 검색을 두나

- 고유 exact name, LinkedIn ID·URL, 공식 도메인은 모델 없이 바로 연결한다.
- 미해결 회사는 내부 `company_db`만 검색해 후보를 1개로 제한한다.
- 단순 substring만 겹치고 정확한 이름 token이나 정규화 identity가 겹치지 않는 결과는 LLM에 보내지 않는다.
- GLM은 회사 ID를 새로 찾지 않고, 주어진 후보가 같은 실제 회사인지 승인하거나 `null`로 기각한다.
- 두 응답이 같은 후보 ID에 동의하지 않으면 연결하지 않는다.

이 구조는 모델의 자유 탐색 범위를 없애고, 잘못된 ID 생성과 모회사·동명사 과신을 보수적으로 막는다. 회사 행이나 workspace를 새로 만들지 않는다.

## 비용·latency 판단

- 모델: OpenRouter `z-ai/glm-5.3-flash`, reasoning `low`
- repository 단가: 입력 $0.075/M token, cache read $0.015/M token, 출력 $0.25/M token
- 예상 production 비용: 이번 정상 반복 평균 기준 이력서 1개당 약 $0.000066
- 외부 검색 비용: $0, Exa 0회
- typical resolver latency: 이력서당 평균 2.50초, 최대 3.89초
- timeout 경계: 호출당 12초, 오류 시 전체 온보딩을 실패시키지 않고 미연결 유지

## 해석 한계

- 구현과 prompt를 보정한 같은 5명으로 점수를 냈으므로 독립 holdout이 아니다.
- 26개 label은 매우 작고 국가·산업·언어를 대표하지 않는다.
- 4회 반복은 모델 변동성을 추정하기에 부족하다.
- `company_db` 중복 행 때문에 의미상 같은 회사여도 strict ID가 다르면 오답으로 계산된다.
- 다음 release 판단 전에는 최소 50개 경력의 blind gold와 별도 holdout에서 같은 2회 합의 설정을 평가해야 한다.
- 이번 작업은 로컬 구현과 read-only 평가까지이며 배포하지 않았다.
