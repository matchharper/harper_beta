# Resume company resolution pilot v1

## 결론

회사명·위치만 입력하고 기존 `company_db`에만 연결하는 보수적인 resolver는 5명·29개 경력 pilot에서 잘못된 자동 연결 없이 11개를 연결했다. 사람이 판정한 26개 기준 precision은 100%, recall은 78.6%, exact accuracy는 88.5%다.

최종 설정은 이력서당 Exa 검색을 최대 3회로 제한한다. 최대 5회 설정과 같은 정확도·연결 수를 유지하면서 비용을 $0.119에서 $0.084로 29.4% 줄였다. LLM은 호출하지 않는다.

## 표본과 판정

| 항목 | 값 |
| --- | ---: |
| 이력서 보유 eligible 사용자 | 3,773명 |
| 고정 seed 무작위 표본 | 5명 |
| 평가 경력 | 29개 |
| manual gold 포함 | 26개 |
| 회사가 모호해 제외 | 3개 |
| gold상 기존 `company_db` 연결 가능 | 14개 |
| gold상 기존 `company_db` 연결 없음 | 12개 |

사용자 ID, 이력서 원문, 역할·기간, 실제 회사 경력 조합은 보고서와 gold에 넣지 않았다. gold는 같은 pilot 출력과 저장된 링크·내부 회사 행을 본 뒤 판정한 unblinded 결과다.

## 최종 결과

| 지표 | DB exact only | DB + Exa max 3 |
| --- | ---: | ---: |
| 자동 연결 | 6/29 (20.7%) | 11/29 (37.9%) |
| precision | 100% | 100% |
| recall | 42.9% | 78.6% |
| exact accuracy | 69.2% | 88.5% |
| false link | 0 | 0 |
| Exa 호출 | 0 | 12 |
| 비용 | $0 | $0.084 |
| resolver 평균/이력서 | 0.566초 | 4.200초 |
| resolver 중앙값/이력서 | 0.534초 | 4.285초 |
| resolver 최대/이력서 | 0.862초 | 5.070초 |

최종 비용은 이력서당 평균 $0.0168, 경력당 $0.00290, 실제 연결 1개당 $0.00764다. 서로 다른 미해결 회사 검색은 병렬 실행하므로 호출 수를 5회에서 3회로 줄여도 이 작은 표본에서는 latency 차이가 크지 않았고, 비용만 직접 줄었다.

구현 보정용 반복 실행과 두 번의 단일 검색, 중단된 비교 실행에서 성공 응답으로 확인된 Exa 비용까지 합치면 이번 개발 과정의 측정 가능 누적 비용은 $0.882다. fetch 실패 호출의 실제 청구 여부는 응답 metadata가 없어 이 합계에 포함하지 않았다. 이는 개발 비용이며, 위 $0.084가 최종 설정의 5명 1회 실행 비용이다.

## 어떤 연결이 추가됐나

DB exact only가 찾은 6개 외에 Exa 공식 도메인 재매칭으로 5개가 추가됐다. 대표 유형은 다음과 같다.

- 같은 이름의 중복 내부 행 중 공식 홈페이지가 있는 canonical 행 선택
- 회사명 뒤에 고객사/사업부 설명이 괄호로 붙은 경력
- `& Co.`, `Inc.`, `Ltd.` 같은 법인 접미사와 공백·구두점 차이

Exa가 반환한 URL을 곧바로 저장하지 않는다. URL이 기존 `company_db.linkedin_url` 또는 `website_url`과 정확히 맞고, 내부 회사명도 입력 이름이나 보수적으로 정규화한 이름과 일치할 때만 `company_db.id`를 기록한다.

## 발견하고 막은 오연결

첫 진단에서는 검색 provider 자체의 회사 페이지가 결과에 섞여 전혀 다른 회사로 연결되는 사례와, 한국 회사와 이름이 같은 폴란드 회사를 선택하는 사례가 있었다. 최종 구현은 다음 조건을 추가해 둘 다 미연결로 바꿨다.

- Exa URL이 내부 회사와 연결돼도 회사명이 맞지 않으면 거부
- 동명 내부 후보 중 입력 위치와 더 잘 맞는 다른 행이 있으면 Exa가 고른 행을 거부
- 한 검색의 URL들이 둘 이상의 내부 회사로 매핑되면 거부
- 공식 도메인이 여러 자회사 행에 공유되면 root URL path가 같은 행을 우선하고, 여전히 하나가 아니면 거부
- 검색 timeout이나 DB 오류가 나면 온보딩 전체를 실패시키지 않고 미연결로 유지

## 남은 미연결 3개

gold상 연결 가능한 14개 중 3개는 의도적으로 놓쳤다.

1. 국가가 다른 동명사가 있어 위치 충돌을 우선한 사례
2. 과거 브랜드명과 현재 내부 회사명이 의미상 연결되지만 문자열이 크게 다른 사례
3. 회사명에 프로젝트·고객 조직이 함께 적혀 어느 조직을 연결할지 해석이 필요한 사례

이 세 유형을 더 잡으려면 후보만 모아 이력서당 한 번의 소형 LLM 판정을 추가할 수 있다. 다만 현재 표본에서는 precision을 낮추지 않는 편이 낫다. 먼저 최소 50개 경력 blind gold로 alias miss 비율을 확인한 뒤 LLM 필요성을 판단한다.

## 비용·latency 판단

- 현재 추천안: DB exact + Exa fast 최대 3회, LLM 없음
- 사용자 submit 응답: 기존 onboarding background 작업 안에서 실행되어 직접적인 제출 응답 latency에는 추가되지 않음
- 프로필 완성 시간: 이 표본에서 resolver가 평균 약 4.2초 추가
- 예상 비용: 현재 표본 분포라면 이력서 1개당 약 $0.017
- 비용 상한: Exa list price 기준 3회면 이력서당 약 $0.021

외부 검색을 완전히 끄면 평균 0.6초·비용 0이지만 recall이 42.9%로 내려갔다. 반대로 5회까지 늘려도 이 표본에서는 recall이 더 오르지 않았다. 따라서 현재 3회 상한이 비용 대비 가장 낫다.

## 해석 한계

- 구현을 고치는 데 사용한 같은 5명으로 최종 점수를 냈으므로 독립 holdout 성능이 아니다.
- 26개 label은 매우 작고 국가·산업·언어를 대표하지 않는다.
- Exa 결과 변동성과 일시적 fetch 실패가 있었다. 최종 구현은 검색당 8초 timeout과 fail-open을 둔다.
- `company_db` 자체의 중복·잘못된 홈페이지·위치 누락이 resolver 성능 상한을 만든다.
- 이번 작업은 로컬 구현·read-only 평가까지이며 배포하지 않았다.
