# Career 실제 공고 지원 준비 완료 검증

## 목적과 평가 단위

사용자가 쓰는 Chrome, 기존 Career 계정, 저장·추천된 실제 외부 공고를 사용해 지원 준비가 실제로 어디까지 진행되는지 확인한다. 목표는 서로 다른 공고 10개가 아래 수동 종료 기준 중 하나에 도달하는 것이다. 제출·메일 발송·고용주 수신은 범위 밖이다. 브라우저 실행 성공이나 문서·질문 카드 생성만으로 완료라고 부르지 않는다.

한 case는 **동일한 실제 공고 하나**다. 다른 수집 URL·Role ID가 같은 공고를 가리키면 같은 case로 묶는다. 같은 공고의 후속 발화·재시도는 해당 case의 attempt로 계속 기록한다. 전체 시도와 실패를 보존하고, 최근 10건은 처음 시도한 순서가 가장 최근인 서로 다른 case 10개를 뜻한다. 10건에 못 미치면 실제 개수를 그대로 보고한다.

## 입력과 버전

- `input-contract-v1.md`: 새 case의 고정 첫 요청. 변수 치환 후 실제 전송한 원문은 private 원장에 남긴다. 이미 실행된 과거 사례는 원래 발화를 보존하며 이 요청으로 실행됐다고 간주하지 않는다.
- `gold-v1.json`: 사용자에게서 받은 A–E 수동 종료 기준. 자동 채점이나 제품 실행 분기로 사용하지 않는다.
- `manifest-v1.json`: 입력·gold·초기 로컬 소스 fingerprint와 실행 조건. 사이트의 현재 HTML, 로그인 상태, 모델 출력은 동결되지 않으므로 controlled benchmark가 아니다.
- `private/candidate-catalog-v1.json`: 기존 계정의 실제 추천·저장 공고를 읽기 전용으로 캡처한 목록. 실행 전에 선택한 공고와 원문 URL을 case에 고정한다. 마감·오류가 나도 시도를 지우거나 다른 공고의 성공으로 바꾸지 않는다.
- `private/case-ledger-v1.json`: 계정과 공고 매핑, 전체 발화·실행 ID, 실패·재시도·현재 판정. 후속 시도는 추가하고 이전 판정의 당시 근거를 보존한다. 원문 증거는 별도 capture에 둔다.

이전 Kakao/Anthropic 두 사례는 최초 검증을 소급 검토한 것으로 blind gold가 아니다. 입력/gold 기준을 바꾸면 새 버전을 만들고 이유와 reviewer를 남긴다. 소스 수정·모델 변경은 입력/gold를 덮어쓰지 않고 새 run으로 기록한다.

## 수동 종료 기준

| 유형 | 인정에 필요한 실제 결과 | 결과 분류 |
| --- | --- | --- |
| A | 해당 공고 지원 폼의 모든 필수 항목과 요구 첨부까지 준비 완료. 제출 직전 화면·입력값·첨부 표시를 직접 확인. 필수값이 비었거나 유효하지 않으면 미완료. | 지원서 작성 완료·미제출 |
| B | 웹 지원 불가인 작은 회사의 실제 담당 이메일과 출처, 전송 가능한 본문·첨부 준비. Gmail 미연결이면 연결 요청 UI도 확인. | 이메일 발송 준비 / Gmail 연결 대기 |
| C | 웹·이메일 경로를 사용할 수 없다는 근거와 함께 실제 다운로드 가능한 준비 이력서, 정확한 직접 지원 URL 전달. 파일 수신·열기까지 확인. | 직접 지원 인계 |
| D | 실제 로그인 화면이 보이는 살아 있는 브라우저를 보존하고 자동 조작을 멈춤. 사용자가 로그인 후 알려 달라는 안내를 받으며 같은 세션에서 재개 가능함을 확인. | 사용자 로그인 대기 |
| E | 이메일 인증을 Gmail에서 읽어 이어서 진행했거나, 미연결이면 연결 UI를 요청하고 작업을 보존. 연결 대기는 작성 완료와 구분. | 인증 후 계속 진행 / Gmail 연결 대기 |

스피너·빈 iframe·닫힌 세션, 실행 상태 `completed`, 모델의 성공 안내, 카드·질문 초안, 일부 입력·첨부만으로는 위 조건을 입증하지 못한다. E에서 인증만 끝났다면 계속 진행해 최종 A–D 또는 보존된 사용자 행동 대기 결과를 기록한다. D/E 대기는 지원서 작성 완료 수에 합산하지 않는다.

## 정본 실행 경로와 관측

실행자는 Chrome의 기존 `/career` 화면에서 일반 대화를 사용한다. 자동화용 별도 prompt·tool·fixture·새 내부 Role을 만들지 않는다. 정본은 [chat route](../../../src/app/api/talent/chat/route.ts), [Career LLM](../../../src/lib/career/llm.ts), [browser tool](../../../src/lib/career/browser/tool.ts), [browser worker](../../../src/lib/career/browser/worker.ts), [external continuation](../../../src/lib/career/externalOperationContinuation.ts), [agent reply worker](../../../src/lib/career/agentReplyWorker.ts)다. 별도 평가 runner로 제품 실행을 복제하지 않는다.

각 attempt에 실제 사용자 발화/시각, 모델·provider·reasoning·sampling(확인 불가는 unknown), tool 호출과 주요 인자, 외부 실행·문서·form ID, 실제 관측 결과, 최종 답변, 스크린샷 경로, 판정 근거를 남긴다. 브라우저 사용자 handoff와 자동 후속 메시지의 화면 수신도 확인한다. DB 저장과 화면 전달을 별도로 기록하며 새로고침으로만 보인 답변을 자동 전달 성공으로 세지 않는다. 첨부 UI 표시는 전송 준비의 증거이며 고용주의 영구 저장·수신을 입증하지 않는다.

현재 소스의 모델 기본값 대신 **해당 run의 실제 설정**을 기록한다. Decisions·대화 모델·browser agent를 분리한다. 로컬 실행은 실제 서비스의 development queue/worker 및 deadline/continuation 경로를 사용한다. 평가 전용 step limit·semantic 검사·숨은 품질 재시도는 추가하지 않는다. 코드 수정 후 재시도는 별도 attempt이며 수정 전 실패도 남긴다.

## 집계와 완료 판정

전체 distinct case 수, 사용자 attempt 수, 실제 browser run 수, A/B/C별 완료 수, D/E별 사용자 행동 대기 수, 미완료·실패·증거 부족 수를 함께 보고한다. 최근 10개 case의 각 종료 유형과 근거를 별도 표로 보여 준다. 스크린샷은 전체 과정이 아닌 종료 판정에 필요한 화면을 중심으로 남긴다.

이 작업의 목표 달성은 서로 다른 공고 10개의 근거 있는 인정 종료이며, 지원서 작성 완료와 사용자 행동 대기를 분리해 보고하는 것이다. 외부 제출·메일 발송, 잘못된 공고, 다른 사용자의 정보 노출, 원본 사실과 불일치한 최종 필수 답변은 별도 핵심 실패로 기록한다. 운영 배포 승인을 의미하지 않는다. 표본이 작고 의도적으로 골라졌으므로 전체 지원 성공률로 일반화하지 않는다.

## 실행 버전 기록

`manifest-v1.json`은 초기 15개 후보와 첫 소스 캡처를 기록한다. 실제 진행 중 추가로 다른 공고를 요청해, 같은 읽기 전용 32개 원본 목록에서 4개를 더 고른 `private/selected-candidates-v2.json`과 `manifest-v2.json`을 추가했다. v1 원본과 gold는 유지한다. v2의 소스 hash는 busy reply 큐 인계·모델 선택 보존·번역 reader 수정 이후 시점이며, 앞선 시도가 이 코드로 실행됐다는 뜻이 아니다. 구체적 시도와 화면 관측은 private 원장에 계속 추가한다.

`manifest-v3.json`은 외부 실행의 원래 요청과 최신 대화 이력을 함께 보존하고, 열린 브라우저의 최근 실행 결과를 context에 제공하는 수정 이후의 소스 캡처다. 입력·gold 버전은 유지한다. 같은 시점에 발견한 과거 합성 경력의 혼입과 별도 복구 경계를 명시하며, 이전 결과를 복구된 입력으로 실행한 결과처럼 바꾸지 않는다.

`manifest-v4.json`과 `private/selected-candidates-v3.json`은 실제 회사의 공식 지원 페이지에서 확인한 두 공고를 추가해 후보를 21개로 확장한다. 원본 소스 hash는 v3 캡처를 유지한다. DB Role이 없는 공식 공고도 URL을 식별자로 사용하며 별도 Role을 만들지 않는다. 후보 추가만으로 case나 종료 수를 늘리지 않고 실제 UI 요청이 전송됐을 때 원장에 시작을 기록한다.

`manifest-v5.json`은 공식 공고 한 개를 더해 후보 22개인 `private/selected-candidates-v4.json`을 기록한다. 지원 조건을 사용자 사실로 간주하지 않으며, 앞선 입력 버전과 수동 종료 기준을 보존한다.

복구 후에는 `input-contract-v2.md`의 실제 사용자 정정 한 문장으로 현재 이력서·프로필을 다시 읽도록 요청한다. `manifest-v6.json`이 이 입력 변경과 당시 소스, 후보 23개의 `private/selected-candidates-v5.json`을 기록한다. 정정은 제품 내부 prompt에 추가하지 않으며 종료 gold는 그대로다. 이전 입력과 결과는 별도 버전으로 보존한다.

`manifest-v7.json`은 공식 이메일 지원 경로를 확인한 두 공고를 더한 후보 25개(`private/selected-candidates-v6.json`)를 기록한다. 입력 v2·종료 gold v1과 v6 소스 캡처는 유지한다.

`manifest-v8.json`은 application handbook v3와 로그인 화면 이동·callback 관측 입력 계약을 수정한 뒤의 소스 캡처다. 실제 재시도에서 provider에 v3가 공급된 메타데이터를 private 증거로 보존했다. v2 lease로 실행된 직전 메일 재시도는 v3 결과에 섞지 않는다.

`manifest-v9.json`은 브라우저 재개·조회 카드, 현재/과거 실행 projection, 카드의 LLM 이력, 간결해진 일반 응답 가이드와 브라우저 색인을 기록한다. `manifest-v10.json`은 같은 소스에서 개발 모델 선택을 Haiku에서 제품 기본값 Sonnet으로 바꾼 후 실제 세 공고를 다시 읽은 실행이다. 동일한 외부 상태·대화를 동결한 모델 비교는 아니다. 이전 실패는 유지하며, 상세 후속 보고는 `private/report-2026-10-30-phone-continuation-ko.md`다.

전화번호 제공 후 11:36 기준 누적은 18개 공고·53회 공고별 요청·32개 사용자 원문·36개 browser run이다. 관측한 인정 종료 11개는 A1/B3/D7이며, 미완료 7개·최근 시작한 10개 중 인정 종료 9개다. 실제 제출·메일 발송은 0건이다. Haiku의 다른 공고 질문 혼입은 수정 후에도 재현됐고 Sonnet 재조회에서 정정됐으므로 모델 품질 문제가 전부 해결됐다고 해석하지 않는다. 세 재개 브라우저는 11:35 사용자 닫기로 종료됐으며, 완료 수는 종료 전 관측 결과다.

## 개인정보와 한계

2026-10-30 08:09 당시 실제 UI 검증 집계는 서로 다른 공고 18개, 공고별 시도 39회, 사용자 지원 원문 26개(별도 중지 요청 1개), browser run 29개다. browser run에는 사용자 새 요청 없이 잘못 반복한 7개를 포함한다. 인정 종료 10개는 이메일 준비 후 Gmail 연결 대기(B) 3개와 로그인 인계(D) 7개이며, 모든 필수 답변·첨부가 완성된 지원서(A)는 0개다. C·E도 0개이고 나머지 8개는 미완료다. 최근 시작한 서로 다른 10개 중에서는 8개가 인정 종료다. 이메일 두 사례는 각각 5회의 사용자 요청·정정이 필요했으므로 최초 요청 성공이나 일반 성공률로 해석하지 않는다. 실제 Gmail 초안 저장·첨부 및 사용자 로그인 후 지원서 재개는 미검증이다. 전체 시도·실패·수정 후 관측·스크린샷을 담은 최종 상세 보고서는 비공개 `private/report-2026-10-30-ko.md`, 정본은 `private/case-ledger-v1.json`에 보존했다.

기존 계정·이력서·외부 사이트를 사용하는 테스트는 사용자가 명시적으로 요청했다. 조사자는 DB를 읽기 전용으로 캡처하고, 실제 지원 검증은 사용자가 승인한 제품 UI에서 실행한다. 최종 지원 제출과 메일 발송은 하지 않는다. 기존 제품 경로의 LLM provider와 Browser Use에 필요한 내용이 전달되며 provider 보관 설정을 이 평가에서 변경하거나 독립 검증하지 않는다. 실제 endpoint·model은 확인 가능한 실행 자료에 남긴다.

검증 도중 과거 E2E 작업의 합성 경력이 실제 계정에 남아 파생 문서에 사용된 사실이 드러났다. 해당 자료의 원인 복구는 지원 검증과 별도 작업으로 구분한다. 원래 E2E manifest와 현재 행·문서 본문을 대조하고, 확인된 합성 자료만 비공개 백업 후 정확한 식별자로 복구하는 범위다. 복구 전후 자료, 실제 변경 여부와 시점은 private 원장에 기록하며 진행 중인 복구를 완료로 간주하지 않는다. 이 예외는 새 fixture 생성이나 실제 지원 실행의 DB 우회를 허용하지 않는다. 혼입된 문서는 내용 승인이나 지원 준비 완료의 근거로 인정하지 않는다.

별도 담당자가 2026-10-30 07:34 한국 시간에 해당 복구를 검증했다. 원본 이력서와 무관한 기존 사용자 자료는 보존했고, 합성 경력을 사용한 파생 문서 11개를 비공개 백업 후 숨겼다. 이전 출력과 실패 기록은 지우지 않는다. 복구 후 실제 실행은 새로운 attempt로 기록한다.

계정 식별자, 사용자 원문, 이력서, 공고와 계정의 관계, raw model 출력, 브라우저 화면·로그는 ignored `private/` 또는 `runs/`에만 저장한다(디렉터리 0700, 파일 0600). 자격증명·인증 헤더는 저장하지 않는다. 공개 파일에는 비식별 계약·집계·hash만 둔다. 기존 삭제된 평가 registry 파일은 복원하지 않는다. 로컬 private 자료가 없으면 Git clone만으로 재현할 수 없다.

## ChannelTalk 최종 확인 재검증

사용자의 2026-10-30 추가 요청은 `input-contract-v3.md`와 `gold-v2.json`으로 별도 등록한다. 같은 공고의 준비·수정·재개 5회를 평가하며 이전 distinct 공고 수에 더하지 않는다. 실제 UI를 정본 실행 경로로 사용하고 실패·재시도를 private 원장에 보존한다. 제품 실행에 자동 의미 판정기를 추가하지 않는다. 로그인·Gmail 인증은 이 공고에 없으면 실증했다고 보고하지 않는다.


`manifest-v12.json`은 ChannelTalk 재검증의 artifact-only 응답 수정과 모델 설정을 기록한다. 폼/브라우저 카드도 대화 이력에 포함하고, 실제 도구가 카드나 폼을 전달한 턴은 추가 텍스트 없이 완료할 수 있게 했다. 같은 이름의 첨부 재전송 충돌, 실패 결과의 상태 projection, 브라우저 유휴 종료와 현재 재직 표기도 수정했다. 확인 폼은 기본 도구이며 별도 apply mode나 의미 판정기로 호출을 강제하지 않는다. 텍스트 기본 모델은 GPT-6.1 Sol high로 변경했다. 기존 개발 모델 선택과 원래 요청에 저장된 모델은 존중한다. Sonnet에서 관측한 긴 반복 설명과 GPT에서 관측한 폼 단독 응답은 동일한 고정 입력의 대조 실험이 아니므로 일반적인 모델 우열이나 성공률로 해석하지 않는다. 상세 원문·시각·실행·스크린샷은 `runs/channel-final-review-v11/`에 보존한다. 웹 배포는 하지 않았다.
