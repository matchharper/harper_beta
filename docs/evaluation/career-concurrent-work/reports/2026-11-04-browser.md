# Career 동시 지원 — 실제 브라우저 반복 검증

2026-11-04 KST. 로컬 구현 검증이며 운영 배포 기록이 아니다. 실제 Career UI, 실제 모델과 Browser Use, 로컬 Supabase를 사용했다. 받는 쪽은 독립된 가상 공고 5개와 POST 수신기다. 실제 회사에 지원하거나 이메일을 보내지 않았다.

## 조건과 증거

정본은 [평가 계약](../README.md), 실행기는 `scripts/localE2e/concurrentApplications.mjs`다. 두 공고만 입사 가능일을 요구한다. 모든 지원에는 이름, 이메일, 전화, 지원 동기, 원본 PDF, 개인정보 제공 동의가 필요하다. 수신기는 모든 POST를 별도 기록하며 중복을 숨기지 않는다. PDF는 원본 SHA-256과 바이트 수를 대조한다.

원본 사용자 입력, 전체 모델 요청/응답, DB 기록, 수신 영수증, 수정 전후 코드 hash/diff는 `.local/full-stack/private/concurrent-applications-v1/`에 비공개로 보존했다. 화면은 `output/playwright/concurrent-*`에 저장했다. 매 초기화 전 해당 계정의 기록을 보존하고 그 계정의 원격 브라우저를 정지한 뒤, 테스트 계정의 Career 데이터만 삭제하고 같은 가상 프로필·이력서·공고를 다시 만들었다. 공용 개발 서버와 다른 계정은 유지했다.

## 첫 회차: 연속 버튼, 검토, 순차 승인

- 다섯 개의 실제 저장 공고에서 지원 버튼을 각각 눌렀고 다섯 요청과 독립 작업이 모두 저장됐다.
- Pine 검토에서 2026-12-01을 한 번 입력했다. Orbit 검토는 그 값을 재사용했다. 이후 채팅으로 모든 회사에 같은 날짜를 적용하라고 명시했다.
- 승인한 검토는 목록에서 빠지고 다음 검토가 열렸다. 앞 지원이 제출 중이어도 다음 지원을 승인할 수 있었다.
- 검토 중 원격 브라우저를 해제하고 승인 후 새 브라우저로 내용을 복원해 제출했다. 채팅 페이지를 새로고침한 뒤에도 작업이 이어졌다.
- 수신 순서 Pine, Moss, Orbit, Luma, Cedar. 각각 정확히 1회 접수, 총 5 POST. 첨부는 모두 원본 PDF 1,727바이트 및 동일 SHA-256이었다.
- **이 회차는 정상 통과가 아니다.** 중간에 제품 코드를 수정했고, Luma와 Cedar에 사용자 재개 지시가 한 번 필요했다. 아래 결함의 재현과 복구 증거로 보존한다.

## 실제로 발견해 수정한 문제

1. **연속 지원 도중 상세 화면으로 이동.** 지원 요청을 보내면 매번 공고 상세로 이동했다. 목록에서 시작하면 목록을 유지하고 상세에서 시작하면 현재 상세를 유지하도록 수정했다.
2. **동일 공고 상세의 중복 React key.** 공고 카드와 하단 행동 영역이 같은 key를 사용해 렌더링 경고가 반복됐다. 각 형제 영역에 서로 다른 식별자를 적용했다.
3. **다른 채팅 때문에 모든 작업 도구가 중지.** 새로운 채팅을 처리할 때까지 각 작업의 읽기·준비 도구까지 전부 보류했다. 이 포괄적 차단을 제거했다. 실제 외부 효과를 시작하는 지점의 사용자 지시·작업 revision·실행 claim 검증은 유지한다.
4. **이미 맡긴 작업을 대화에서 다시 실행.** 원본 실행 지침의 우선순위를 바로잡았다. 기존 위임 작업부터 확인하고 해당 작업에 후속 지시를 전달하며, 준비·질문·제출은 작업의 실행 주체가 이어간다.
5. **빈 최종 응답 뒤 잘못된 재작성.** 도구가 없는 별도 호출에 원래 실행 결과도 없이 답변을 강제해, 이미 준비가 끝난 지원을 ‘도구에 접근할 수 없다’고 설명했다. 온보딩 이후 일반 대화의 빈 응답을 이 경로로 재작성하지 않는다. 기존 진행 안내·폼·작업 결과는 그대로 남긴다.
6. **입력 영역 뒤로 대화가 비침.** 하단 투명 배경 때문에 검토와 채팅 텍스트가 겹쳐 보였다. 하단 입력 영역의 배경을 불투명하게 바꿨다.
7. **같은 검토의 접근성 ID 중복.** 대화 이력과 현재 검토에 동일한 폼이 렌더링될 때 label이 다른 입력을 가리킬 수 있었다. 화면 인스턴스별 ID를 부여했다.
8. **다른 작업의 상태를 오래된 맥락으로 설명.** 재개한 작업에 같은 대화의 다른 작업 상태·결과·관측 시각을 제공했다. 자세한 내용은 아래 두 번째 회차에 기록했다.
9. **같은 검토의 수정값이 화면마다 달라짐.** 세 번째 회차에서 하단 검토의 지원 동기를 고쳐도 대화 이력 카드에는 이전 값이 남았다. 폼 revision별 초안을 공유하고 변경을 구독하도록 수정했다. 두 화면의 즉시 동기화, 닫기·재열기·새로고침 후 보존, 다른 인스턴스에서 저장한 값 및 실제 수신 값을 확인했다.
10. **승인 기록이 채팅을 과도하게 차지함.** 입력값 전체·파일 UUID·true/false가 승인마다 긴 말풍선으로 쌓였다. 폼 제목과 선택한 행동을 먼저 표시하고, 펼치면 정확한 입력값·실제 선택 파일명·선택 여부를 읽게 했다. 원본 응답과 모델 입력은 바꾸지 않는다. 새 목록이나 할 일 화면을 추가하지 않았다. 확인 UI의 한·영 번역 키도 실제 reader가 읽는 `career` 영역으로 옮겼다.

수정 중 `isOnboardingDone` 변수명을 잘못 참조한 일시적 오류도 첫 회차에 발생했고 즉시 올바른 기존 변수로 수정했다. 해당 실행은 작업 재시도 기록에 남았다. 초기 UI 단위 검증은 환경 설정과 오래된 테스트 전제가 맞지 않아 실패했다. 로컬 테스트 환경과 현재의 단일 폼 응답 API 계약에 맞게 수정해 재실행한다.

## 반복 검증

두 번째 회차: 초기화 후 5개 URL, 기존 이력서, 공통 입사일을 한 메시지로 주고 작성·동의·최종 제출까지 위임했다. 추가 사용자 메시지 0회, 검토/질문 폼 0개로 5개 작업 모두 완료됐다. 다섯 지원처가 각 1 POST를 수신했고 PDF는 모두 원본과 일치했다. 실행 중 페이지 새로고침도 수행했다. 수신 시간은 00:26:25–00:27:03 KST다.

완료 메시지 중 Luma가 이미 끝난 다른 지원까지 ‘나머지 네 공고 진행 중’으로 설명한 문맥 문제가 있었다. 각 작업 재개 시 원본 작업 context에는 자기 작업만 있었으므로, 같은 대화의 다른 작업 상태와 실제 결과를 관측 시각과 함께 제공하도록 수정했다. 답변 문구나 개수를 강제하지 않고, 기존 manage_work 조회를 통해 더 읽을 수 있게 했다. 각자 완료 보고만으로 실시간 전체 진행 상태를 추론하지 않도록 사실을 보완한 것이다.

세 번째 회차: 다시 초기화한 뒤 검토 후 제출을 요청하고, 실제 공고 목록에서 다섯 지원과 Luma 재클릭까지 **6회 요청**했다. 목록 화면을 유지했고 독립 작업은 **5개**, 열린 검토도 **5개**였다. 검토가 모두 준비된 시점에 수신은 **0 POST**, 원격 브라우저 5개는 모두 정지 상태였다. 검토를 기다리는 동안 브라우저를 유지하지 않았다.

Cedar 지원 동기를 직접 수정하고 다음·닫기·재열기·새로고침을 수행했다. 위 9번 결함을 수정한 뒤 대화 카드와 하단 검토가 같은 최신 값을 표시하는 것을 브라우저에서 확인했다. 이후 채팅으로 입사일을 한 번 전달하자 Pine·Orbit의 기존 폼 revision만 갱신됐고, 열린 검토 개수는 5개로 유지됐다. 날짜가 필요 없는 카드와 Cedar의 사용자 수정은 그대로 남았다.

검토 5건을 3.16초 동안 연속 승인했다(00:49:11.848–00:49:15.008 KST). 승인 요청은 앞 작업 완료를 기다리지 않고 각각 저장되고 다음 검토가 열렸다. Orbit은 동의를 체크하지 않은 채 승인한 응답이 저장됐는데, 모델이 이를 구분하여 **Orbit만 필수 동의 확인 대기**로 남겼다. 이 대기 중 나머지 네 지원처는 모두 접수했다. Orbit의 남은 동의에 답한 후에는 이미 검토한 내용으로 제출을 완료했다. 이 추가 응답은 누락된 동의를 제공한 것이며, 작업을 복구하라는 재개 지시는 하지 않았다.

최종적으로 5개 work 모두 completed, 실행 중 browser 0개, 미해결 확인 0개였다. 새로고침 후에도 완료 상태를 유지했다. **각 지원처 1 POST씩, 총 5회**, 원본 PDF hash·1,727바이트가 모두 일치했다. Orbit·Pine의 날짜는 2026-12-01, Cedar 수신 지원 동기는 직접 수정한 문자열과 완전히 일치했다. 승인 기록을 실제 화면에서 펼쳐 파일명이 표시되고 선택하지 않은 동의가 그대로 보존되는 것도 확인했다. 이 회차에는 UI 수정이 포함되어 있으며, 배포된 동일 버전의 무개입 반복 시험으로 표현하지 않는다.

## 변경 경로 확인

- 최종 폼·제안·초안 공유·이력 표시 UI 검사 9개 통과. 이전 준비 모드의 스트리밍을 기대하던 검사는 현재의 과거 기록 reader 계약으로 수정했다. 과거 기록이 별도 실행을 다시 시작하지 않는지도 확인한다.
- 이번 회차에서 변경한 일반 runtime 관련 검사 7개 통과. 전체 `tsc --noEmit` 통과. 마지막 변경 경로 lint 오류·경고 0개. 앞선 넓은 lint에서는 이번 수정과 무관한 HistoryPanel effect 경고 1개가 있었다.
- 실제 개발 브라우저에 Next 개발 middleware manifest MIME 오류·HMR 경고와 가상 tunnel favicon 404, 이미지 경고가 있었다. 이를 제품 콘솔 오류 0건으로 보고하지 않는다. 최초 재현한 중복 React key 경고는 수정 후 재현되지 않았다.
- `open_url`은 이 로컬 환경의 EXA 키 부재로 실패했으나, 실제 agent가 브라우저로 원문을 확인해 이어갔다. 이 복구에 사용자 지시는 필요하지 않았다. 작업 revision 경합의 재시도 기록도 남았으며 최종적으로 미소비 실행은 남지 않았다.

테스트 종료 후 이 fixture의 원격 브라우저 5개를 확인·정리하고 제공자 workspace 파일을 삭제했다. 테스트 앱·수신기·임시 터널도 종료했다. 로컬 마지막 회차 데이터와 검증 증거는 보존한다.

## 범위

가상 지원처의 실제 수신과 원본 파일 전달을 확인한다. 실제 ATS별 로그인, CAPTCHA, 서로 다른 업로드 규칙, 운영 Queue 및 운영 동시 사용자 부하는 이 시험의 검증 범위가 아니다. ‘지원 완료’는 이 문서에서 가상 지원처 접수를 의미한다.
