# Career context list completeness

Objective: compare scheduled Career tool use with identical source facts before and after compact list-completeness metadata. Unit: a complete isolated original-model turn. Production renderers, capability runtime, schemas and provider loop are reused. No new behavioral instruction to avoid tools.

Canonical runner: `node --import tsx scripts/evalCareerContextCoverage.ts capture|render|run baseline|updated`.

Reproduction needs the ignored owner-only `private/selection.json` (selected run IDs), `baseline-sources.json` (pre-change working-tree sources), `reads.json` and frozen input files. `capture baseline` is read-only production access and refuses an existing frozen case set; `render updated` reuses captured HTTP receipts; `run baseline` and `run updated <output-label>` call the original provider loop against the corresponding frozen inputs and refuse to overwrite outputs. Provider credentials come from `.env.local` and are never saved in the registry. Read fixtures accept only their captured argument sets; arbitrary filters, IDs or pagination are unsupported unless explicitly represented.

Dataset v1: seeded random sample of five distinct talents' most recent completed scheduled runs in the preceding seven days, seed `context-coverage-20261111-c7f83`. Capture current read-only source facts, not reconstructed historical state. Freeze the sample, HTTP read receipts and rendered inputs before either model arm. Baseline is the pre-change working tree, including existing unrelated edits, not the historical production commit. Never overwrite the frozen source/data capture.

Production capture uses GET/read-only RPCs only; `ensure_career_check_in` is replaced by a read of the existing reservation. Model runs use frozen reads and isolated mutation receipts; they never dispatch queues, send messages or update production. External execution is simulated, so this is a tool-use comparison, not a delivery test. Unavailable fixture operations must be reported, not counted as successful completions. Raw production inputs and outputs are restricted to ignored owner-only `private/` and `runs/` files. Public cases/gold/manifest contain no candidate details.

Same scheduled model, reasoning configuration, tools and frozen facts in both arms; five pairs, one sample per arm, no cherry-picked retries or semantic grader. Record all model tool calls (including capability/guide loaders), business read calls, empty read calls, input/output tokens, completion/errors and candidate-facing draft actions. Review full transcripts for preserved task completion; fewer calls alone is not success. This small stochastic sample does not establish a population effect. Changes to source data require a new dataset version.

Run configuration: `getScheduledCareerModelOptions()` from the captured working tree; progressive Career capabilities with schedules/delivery preloaded and the proactive handbook. This runner assembles scheduled context using production readers and renderers, but does not replay queue dispatch, live inbox preparation, follow-specific branches, delivery, persistence or a historical database snapshot. It cannot establish live scheduled-work completion. Fixture writes return isolated receipts, not real execution or simulated durable transitions; a multi-step write-dependent task therefore needs an extended fixture before it can be evaluated.

[Results](results.md), [reproducibility manifest](manifest.json), [de-identified cases](cases.json), [review criteria](gold.json). The README declared the review criteria before model generation; `gold.json` materializes those same criteria afterward and does not add retrospective expected tool counts. The initial and token-trimmed updated variants are retained separately. Final boundary fixes produced byte-identical inputs for all five measured cases, so no additional model trials were needed.
