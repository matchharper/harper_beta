# Apply with Harper 프롬프트 책임 정리

2026-10-29 로컬 변경. **사용자 경험 전체 통과로 판정하지 않음. 미배포.** 원본 모델의 입력과 도구 결과를 정리했으며 출력 검열기, 별도 재작성 모델, 추가 운영 재시도 루프는 만들지 않았다.

## 변경한 책임

| 위치 | 맡는 일 |
| --- | --- |
| `suggestionWriter.ts` / `suggestionSchema.ts` | 첫 이력서 검토와 중요한 경험 질문. 필드별 표시 역할과 실제 편집 명령 설명을 해당 schema에 둔다. 일반 지원 자료 작성과 최종 안내 지침은 첫 질문 모델에서 제거한다. |
| `applicationWritingContract.ts` | 위임받은 작성 범위, 사실·사용자 선택의 우선순위, 일반 작성물과 실제 원본 자료의 구분. 웹/이메일 전달 위치를 반영하는 최종 안내 계약도 이 파일이 소유한다. |
| `preparationPrompt.ts` | 답변 반영 → 필요한 작성 → 저장 → 결과 전달의 실행 순서와 제출·로그인·종료 경계. 초기 편집 판단과 실제 작성에 공통으로 필요한 사실 정밀도는 RESUME_FACT_CONTRACT 한 원본을 재사용하고, 새 이력서 검토를 유도하는 지침은 반복하지 않는다. |
| `resumePolicy.ts` / 준비 도구 설명 | 원본 보존, 사본/현재 수정본, revision, 첨부 ID 등 명령에 필요한 계약. 최종 응답을 다시 작성하라는 지시는 제거한다. 일반 이력서 기능의 정책은 유지한다. |
| `conversationPlan.ts` / `toolPolicyPrompt.ts` | 활성 지원에서는 일반 Career 정보 수집·추천 안내·형식 지시 대신 실제 준비에 필요한 정책을 제공한다. 준비 종료 후에는 현재 활성 문맥을 기준으로 일반 정책을 복원한다. 대화 언어와 이력서/지원 자료 언어의 적용 범위를 구분한다. |
| `llm.ts` | 도구 후 일반 대화 지침을 덧붙이는 대신 활성 작업의 동일한 전달 계약을 재사용한다. 같은 원본 LLM이 계속 작업하고 답변한다. |
| 제안·문서·지원서 결과 projection | 저장 사실, 정확한 ID/revision, 현재 선택과 본문에 필요한 정보만 모델에 전달한다. raw 결과와 저장 데이터는 실행·UI·trace용으로 유지한다. |

## 확인한 충돌과 제거

- 짧은 최종 안내와 동시에 이력서 저장 도구가 수정 내용을 설명하라고 요구했다. 초기 질문 작성 모델에도 최종 제출 안내가 포함되어 있었다.
- 지원 준비에도 일반 Career 소개·추가 정보 수집·제목과 목록 형식 지침이 들어갔다. 도구 뒤에는 다시 별도의 일반 응답 지침이 붙었다.
- 처리된 제안의 현재 상태와 함께 생성 당시의 `needsConfirmation` 등 코칭용 속성이 전달됐다. 준비 모델에는 ID, 종류, 현재 상태와 실제 편집 텍스트를 별도 projection으로 제공한다. 이메일 reader가 사용하는 ID/status는 유지한다.
- 저장 결과가 실제 본문 전체와 안내 지침을 다시 반복했다. 모델에는 저장 영수증과 준비된 필드/첨부 정보를 주고, 본문 재확인은 기존 `read_document`가 맡는다.
- `preparationComplete`는 이력서 제출 버전 고정 여부이지 모든 요건 완료가 아니다. 모델용 영수증에서는 이를 `resumeVersionPinned`로 표현한다. 관측 필드가 없는 결과는 준비된 파일로 표시한다.
- 사용자 언어를 모든 출력에 적용하던 상위 지침이 영문 이력서 보존과 충돌했다. 지원 문맥의 언어 지침을 대화/진행 안내와 문서로 구분했다.

기존 질문 저장·건너뛰기, 문서 소유권/revision, 원본 보존, 인라인 지원서 저장, 제출 동의와 브라우저 실행 경로는 바꾸지 않았다. Exa 검색/URL 선택과 브라우저 엔진 자체의 성공률은 이번 프롬프트 변경으로 검증하거나 해결했다고 주장하지 않는다.

실제 provider 입력의 고정 지침 블록 합계는 이전 약 41,163자에서 정리 후 약 13,281자로 줄었다(`chat_core`, 준비 계약, 전달 계약, 도구 정책). 도구 schema·사용자 데이터는 제외한 문자 수이며, 토큰/비용/품질 향상률이 아니다.

## 검증과 한계

- 실제 Haiku 5.5 호출: 기존 frozen `editorial-v1` 7직군, `delegated-v2/v3` 준비 4/5종, `inline-v1` 답변 후 저장. 원본 prompt builder/tool loop/문서·지원서 저장 로직을 쓰고 DB만 기존 메모리 adapter로 격리했다. 실제 회사 제출은 없다.
- 핵심 저장·선택·첨부 검사 28/28 통과. 관련 prompt 검사를 포함한 46개는 44개 통과이며 기존 legacy 종료 문구 및 내부 Role priority-review 문구 assertion 2개는 실패 상태를 유지했다. 이를 맞추려고 범위 밖 제품 문구를 바꾸지 않았다.
- 변경한 제품 파일 lint 통과. 전체 TypeScript 확인은 기존 빈 database types 및 오래된 Next 생성 경로 등으로 실패했다. 변경 경로를 지목한 진단은 없었다. 전체 빌드 성공을 뜻하지 않는다.
- 실제 provider의 `tool_result`가 읽을 수 있는 전용 텍스트인지 확인했다. 저장된 원본/사본, 입력 필드와 첨부 매핑, 빈 동의 항목을 별도로 읽었다.
- 고정 사례에서 일반 프로젝트 문서를 작성·저장·연결하고, 건너뛴 질문을 다시 묻지 않으며, 제외한 새 경력을 다른 문서에 넣지 않는 흐름을 확인했다. 원본 포트폴리오는 만들지 않고 나머지를 준비한 뒤 요청했다. 사용자 답변의 반영에 별도 문구 승인 질문을 다시 만들지 않았다.

**남은 실패:** 최종 답변의 필드/자료 요약과 로그인 화면 설명이 일부 계속 나온다. 로그인 사례에서 향후 자동 제출 가능성을 덧붙이거나, 접근 미확인 사례를 실제 페이지 접근 실패처럼 표현한 결과도 있다. 초기 제안의 reason이 편집 과정과 사실 확인을 장황하게 설명한다. 일부 작성물에서 확인된 설계 경험에 구현·운영 범위를 덧붙인 사례가 있어 사실 정밀도 역시 전면 통과가 아니다. 이러한 결과는 도구 실행 성공과 별도로 실패로 기록한다.

초기 디자인 사례에서 같은 원문에 두 개의 replacement 명령을 만든 실행은 실패로 남겼다. 편집 명령 schema에 한 원문 구간의 변경을 하나의 replacement로 합치는 계약을 명확히 한 뒤 같은 frozen 사례에서 한 명령으로 합쳐지는 것을 확인했다. 운영 중 의미 판정 validator를 추가하지 않았다.

## 재현 기록

원문·provider 요청·실제 저장 결과·manifest는 ignored `runs/`에 0700/0600으로 보관한다.

- 이전 비교 기준: `journey-2026-10-29T03-08-33-947Z`
- 전체 재구성 중 실패: `journey-2026-10-29T03-21-32-313Z`, `journey-2026-10-29T03-24-06-241Z`, `journey-2026-10-29T03-26-06-346Z` 및 이후 중간 run. 삭제하지 않는다.
- 초기 7직군: `2026-10-29T03-28-45-683Z`; 편집 명령 보완 후 디자인: `2026-10-29T03-33-54-427Z`.
- 전체 delegated-v3: `journey-2026-10-29T03-39-26-468Z-b18d0dea-64ed-4037-a860-3a2cbc7c5e3d`.
- 답변 반영: `journey-2026-10-29T03-39-26-468Z-6e869897-1032-4b39-bc63-2ffa11607b64`.
- 언어 범위 분리와 공통 사실 계약을 함께 적용한 최종 답변 반영: `journey-2026-10-29T03-47-27-724Z-bc394f8d-c8f6-4b31-aed5-3bb5ab65c42d`. 원본은 보존되고 사본에 사용자가 확인한 성과만 영어로 추가됐으며 재승인 질문 없이 필드/첨부가 저장됐다. 최종 답변의 내용 요약은 아직 남았다.
- 파일 전용 영수증 정리 후 로그인: `journey-2026-10-29T03-43-55-614Z-e7d9091c-5f93-4ce9-b0dc-53dbd510caa9`. 문서 저장과 skip 처리는 정상이나 로그인 화면 설명과 재개 제안은 남아 NO-GO다.

평가 adapter가 live `inspect`나 일부 일반 조회를 제공하지 않아 생긴 오류는 실제 제품 실패로 단정하지 않는다. 반대로 불필요한 재조사는 모델의 비효율로 기록한다. 한국어 fixture에서 builder의 기본 영어 설정이 섞였던 초기 실행은 언어 평가에 쓰지 않으며, runner에 실제 한국어 선호를 명시했다. 동시 실행의 millisecond 기반 폴더 충돌도 발견해 run ID에 UUID를 추가했다. 충돌한 `journey-2026-10-29T03-38-03-376Z`의 provider trace는 최종 근거에서 제외하고 다시 실행했다.

작은 합성 사례의 수동·비맹검 검토이며 실제 사용자 브라우저/ATS/production의 전체 품질이나 독립 human 평가를 대신하지 않는다. 이번 작업에서는 사용자 DB, 배포 및 Notion을 변경하지 않았다.
