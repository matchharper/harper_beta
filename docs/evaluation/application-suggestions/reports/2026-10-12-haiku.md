# Apply with Harper — Haiku 5.5 로컬 검증

2026-10-12, 배포하지 않은 작업 트리 기준. 실제 후보자·회사·지원 데이터를 쓰지 않았다. 이 검증의 모든 모델 요청은 `claude-haiku-5-5`이며, 다른 모델 fallback은 네트워크 경계에서 차단했다. 제품 기본 모델을 영구 변경한 작업은 아니다.

## 범위

- 첫 제안: 실제 suggestion writer와 frozen `cases-v1` / `gold-v1`, 3건.
- 후속 대화: frozen `conversations-v1` / `conversation-gold-v1`, 3건.
- 저장과 다음 대화까지: frozen `journeys-v1` / `journey-gold-v1`, 8사례·11턴. 전체 Career prompt와 12개 실제 도구 schema, 실제 문서 read/생성/수정 service, 준비 완료와 apply 시작 검증을 사용했다. 소유권·revision을 검사하는 in-memory 저장소로 실제 DB만 대체했다.
- 로컬 Chrome: 실제 Haiku가 작성한 JSON을 개발 전용 preview에 불러와 composer/답변 기록을 직접 조작했다. 실제 인증·외부 ATS·Agents API 모델 판단은 이 평가의 범위가 아니다. apply는 queued 상태까지이며 dispatcher와 실제 외부 제출은 차단했다.

## 반복 실행에서 발견해 고친 내용

1. 공통 프롬프트의 지원 대행 불가 문장이 실제 기능과 충돌했다. 현재 제공된 도구와 검증된 결과에 맞춰 행동하도록 수정했다.
2. `ready_for_role`의 nested resume wrapper를 모델이 JSON 문자열로 보내 저장이 실패했다. 모델에 노출하는 입력을 기존 resume command와 같은 평평한 JSON으로 바꾸고, 기존 in-flight wrapper는 호환한다. 잘못된 입력은 필드별 오류로 거절하며 임의로 복구하거나 사실을 보충하지 않는다. 변경 없는 준비 완료에서 `{}`를 action 문자열로 보내는 반복 실패가 있어, 모델에는 필수 action=`reuse`를 제공한다. 기존 빈 객체 호출은 호환한다.
3. 최초 수정에서 원본 update를 시도했다. generated 원본은 copy, 업로드 원본은 create, 이후 working copy는 update라는 저장 계약을 명시했다. 서버는 원본 수정을 계속 차단한다.
4. 버튼으로 확정된 적용을 모델이 취소한 사례가 있었다. 서버가 확인한 제출 batch의 적용/거절은 같은 continuation에서 변경할 수 없다. 동일 결정은 no-op이며, 자유 응답·skip과 이후 별도 사용자 수정 요청은 정상 처리한다.
5. 과거 제안과 편집된 승인 문구가 중복되어 사용자가 문구를 다시 보내야 한다는 답변이 나왔다. 모델 context에는 버튼의 실제 최종 응답을 보존하면서 이전 제안 본문의 중복을 줄였다. 화면의 원래 질문·답변 기록은 보존한다.
6. Haiku가 UI의 ‘적용’을 실제 지원서 제출로 혼동했다. 적용은 제안 승인이고 제출은 별도의 실제 실행이라는 UI 의미, 편집 응답의 출처를 prompt에 명확히 정의했다.
7. 문서만 읽은 뒤 수정하겠다는 약속으로 끝낸 사례가 있었다. 작업 종료 기준을 실제 저장/지원 시작, 신규 제안 표시, 또는 구체적인 blocker로 명확히 했다. 정성적 판단을 키워드 분기로 대체하지 않았다.
8. 추가 작성물 수정 뒤 준비 완료 도구를 생략한 사례가 있었다. production과 평가가 같은 suggestion 결과 builder를 사용하고, 해결 후 같은 턴에서 ready로 이어지도록 했다.
9. 공통 문서 지침이 사용할 수 없는 generate_resume을 가리키거나 업로드 원본의 structured JSON을 요구하던 충돌도 수정했다. 기존 섹션은 승인된 변경 대상이 아니면 유지한다.

## 질문·수정 개수 조정

사용자 요청에 따라 질문 최대 3개, 이력서 수정 제안 최대 7개, 추가 작성물을 포함한 전체 최대 10개로 조정했다. 최소는 두지 않는다. 서로 다른 유용한 정보가 비어 있으면 질문 2~3개를 함께 제시하도록 최초·후속 프롬프트를 가볍게 바꿨다. 유형별 개수는 의미 판정 없이 공통 구조 검증으로 처리하며, 후속 제안 초과 시 기존 상태를 변경하지 않는다.

동일 frozen cases-v1 / gold-v1을 Haiku 5.5로 재실행한 `2026-10-12T13-07-57-839Z`는 구조 3/3 통과. 원문 대조에서 각 사례의 질문은 2/2/1개, 전체 제안은 3/3/1개였다. 필수 연락 정보 외에 역할 관련 규모·성과 또는 개발자 피드백 사례를 묻고, 알려진 정보를 재질문하거나 사실을 지어내지 않았다. 세 번째 사례는 핵심 경험 질문 하나로 끝내 최소 개수를 강제하지 않았다. 초안은 실제 요구된 지원 동기만 작성했고 600자 이내였다. 일부 제안 제목의 명령조·긴 이유는 남아 있으므로 표현 품질의 완전한 개선을 뜻하지 않는다.

개수 경계·추가 작성물 포함·기존 제안 재표시·초과 시 원자적 거절을 포함한 관련 테스트 10개, 전체 타입 검사, 변경 파일 ESLint 통과. UI나 실제 회사 제출을 다시 실행한 검증은 아니다.
