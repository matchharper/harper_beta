# Adaptive Career check-in 로컬 검증 — 2026-11-02

사용자별 지속적인 Career check-in을 유지하고, 최초 생성 시에만 3일 간격을 넣는다. 이후에는 원본 Career agent가 현재 대화, Brief, 연락 이력, 저장된 일정과 변경 근거를 읽고 일반 schedule 도구로 주기·지시·중단·재개를 결정한다. 중단/취소는 행을 삭제하지 않으며, 컨텍스트 조회나 재개가 기존 주기를 3일로 되돌리지 않는다.

## 실제 모델 검증

고정 synthetic 사례 6개를 현재 Career runtime, 실제 prompt/tool schema, 실제 schedule executor 및 격리된 PostgreSQL(PGlite) 함수로 실행했다. Chat은 `gpt-6.1-sol / high`, background는 `gpt-6-luna / high`를 사용했다. 추가 심사 LLM이나 출력에 따른 재시도는 없다. 전체 응답과 tool 호출을 직접 검토했다.

| 사례 | 관측 결과 |
| --- | --- |
| Harper가 중단한 뒤 사용자가 공고 검색 요청 | 기존 일정 ID를 재사용해 7일 간격으로 재개 |
| Harper가 중단한 뒤 사용자가 지원 요청 | 기존 일정 ID를 재사용해 7일 간격으로 재개 |
| 중요한 정보만 달라는 요청 | 연락 가치에 관한 지시를 수정하고 7일 간격으로 변경 |
| 사용자가 정기 연락을 명시적으로 중단한 뒤 일회성 검색 요청 | 기존 9일 설정과 중단 상태 유지 |
| 장기 무응답 및 반복된 빈 평가 결과 | 이메일을 보내지 않고 14일 간격으로 변경 |
| 기존 13일 주기를 유지하라는 요청 | 13일 설정 유지 |

7일·14일은 해당 실행에서 모델이 선택한 값이다. 평가 정답이나 제품 분기에 지정한 값이 아니다. 6개 모두 기계적 검증과 수동 의미 검토를 통과했다. 운영 성공률을 추정하는 표본은 아니다.

- 전체 실행: `runs/2026-11-02T07-03-24-109Z/manifest.json`
- Background 보강 검증: `runs/2026-11-02T07-09-48-404Z/manifest.json`

보강 실행은 실제 collector가 로컬 DB에 만든 occurrence를 `handed_off`로 전환하여 실행했다. 모델의 미래 주기 수정 뒤에도 현재 invocation의 source revision은 유효했고, 이메일 발송 없이 14일로 변경했다. 각 manifest에 실행 당시 소스·입력 hash가 있다. 마지막의 동일한 timing 값 재전달 처리 보완은 아래 계약 테스트로 확인했다.

## 코드 및 DB 계약 검증

관련 테스트 43개가 통과했다. 처음에는 schedule 계약/adaptive, delivery, agent runtime, capability provider의 42개를 실행했다. 마지막으로 지시만 수정할 때 다음 실행 시각을 보존하는 테스트를 추가하고 영향받는 schedule 테스트 19개를 다시 실행해 통과했다.

검증한 경계:

- 온보딩 시 최초 기본값 생성과 기존 중단/사용자 지정 주기 보존.
- 소수 일 간격, 월 경계의 실제 경과 시간, 기존 cron 지원.
- 최근 일정 12개 밖의 오래된 중단 일정과 원래 사용자 중단 요청도 컨텍스트에 포함.
- 연락하지 않은 정상 완료 뒤 다음 occurrence 유지.
- 자신의 미래 일정을 중단/수정해도 현재 실행은 유지하고, 외부 사용자 취소는 현재 실행을 무효화.
- 중복 실행, 소유권, 변경 revision 충돌, browser payload의 실행 출처 위조 차단.
- 재개가 현재 연락 거부 설정을 바꾸거나 우회하지 않음.
- 같은 주기·시간대를 재전달한 지시 수정은 예정 시각을 미루지 않음.

변경한 TypeScript 파일의 ESLint와 변경 범위의 whitespace 검사는 통과했다. 전체 TypeScript 검사는 변경 범위 밖 오류로 통과하지 못했다:

- `src/components/career/CareerWorkspaceScreen.tsx:606`: 비교 대상 union에 `home`이 없음.
- `src/components/career/chat/CareerSuggestionComposer.test.tsx:482`: `formSnapshot` 누락.
- `src/components/career/chat/InternalCallAnswers.test.tsx:91`: `allowedToolNames` 속성이 없음.

## 적용 범위와 한계

이번 결과는 로컬 구현과 검증이다. `20261102064501_career_adaptive_check_in.sql`은 격리된 DB에 적용해 검증했고, hosted DB 적용·기존 사용자 일괄 전환·배포·실제 이메일 발송은 실행하지 않았다. 기존 사용자의 baseline 생성/기존 legacy 행 채택은 컨텍스트 조회 시에도 멱등적으로 수행되며, 별도 일괄 전환 함수와 기존 script는 기본 dry-run을 유지한다.

모델 검증에서 검색·지원 등 schedule 외 도구 결과는 synthetic receipt다. 실제 외부 지원, 이메일 수신, 배포 UI까지 확인한 E2E 테스트는 아니다. 원본 모델 출력과 provider 요청은 무시되는 `runs/`에만 보관한다.

## 후속 코드 점검 및 수정

대화·이메일·음성의 일정 입력, 저장/재개, collector와 Worker handoff, source 취소, 연락 권한, dev controls 실행·로그 경로를 연결해서 점검했다. 주기를 판단하는 정책은 유지하고 아래 오류를 먼저 실패하는 테스트로 재현한 뒤 수정했다.

1. **Worker 온보딩 권한 누락:** `harper_worker`로 온보딩 완료를 저장하면 새 trigger 내부의 `ensure_career_check_in` 실행 권한 오류가 발생했다. 최초 생성과 legacy 행의 key 연결에 필요한 권한을 부여했다. 기존 일정의 주기·지시·상태 수정 권한과 클라이언트 실행 권한은 부여하지 않았다. 실제 제한된 DB 역할로 생성·채택 및 무단 주기 수정 거부를 검증했다.
2. **중단 시 일회성 예약 시각 유실:** pause가 `next_run_at`을 삭제해, 미래의 일회성 작업도 UI의 resume 요청으로 재개할 수 없었다. inactive status로 실행을 막으면서 저장한 시각은 보존한다. 모델에는 이 시각이 활성 예약이 아님을 표시한다.
3. **실행되지 않는 활성 일정:** update로 `next_run_at: null`을 저장하면 활성 상태지만 collector가 영구히 찾지 못했다. 활성 일정의 시각만 지우는 요청은 저장 전에 오류로 반환하며, 중단은 기존 pause 동작을 사용한다. 특정 주기나 임의의 대체 시각을 넣지 않는다.

관련 DB·일정·발송 테스트 47개, dev controls API/로그 모달 테스트 2개, 도구 연결·질문 UI 테스트 15개가 통과했다. 도구 테스트의 Node 환경에는 synthetic 설정과 Next의 `server-only` marker 대체를 제공했고 외부 네트워크는 차단했다. 추가로 발견된 테스트 fixture의 누락된 form snapshot/router context, 제거된 속성의 검사, 기본 제공으로 바뀐 form tool의 오래된 기대값을 현재 제품 계약에 맞췄다. 제품 동작을 테스트에 맞춰 변경하지 않았다.

중단 일정의 입력 projection이 바뀐 두 frozen 사례를 실제 모델로 다시 실행했다: `runs/2026-11-02T07-26-01-404Z/manifest.json`. Provider 입력에 `Saved execution time (inactive)`가 포함되는 것을 확인했고, 전체 응답과 schedule 호출을 검토했다. Harper가 중단한 일정은 공고 요청 후 같은 ID로 7일 간격 재개, 사용자가 중단한 일정은 기존 9일 설정과 중단 상태 유지로 두 사례 모두 통과했다. 3일 최초 기본값과 원본 agent의 주기 판단 계약은 유지한다.

후속 점검의 최종 전체 TypeScript 검사(`tsc --noEmit`)와 이번에 수정한 파일의 ESLint도 통과했다. 위 최초 검증 시 기록한 타입 오류는 현재 작업 트리에서 해소됐다.

후속 점검에서도 운영 DB 적용·배포·실제 발송은 하지 않았다.
