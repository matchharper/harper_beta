# 답변 끝맺음 지침 전후 비교 (2026-11-23, 로컬·미배포)

## 문제

11월 5일 이후 운영 Career 채팅에서 Harper 답변 뒤 사용자가 다음 행동을 되물은 사례를 읽었다. 대표 사례의 `talent_messages.id`는 502548→502549, 502961→502991, 488497→488516, 492379→492380이다. 결과 보고, 분석 결론, 회사 결정 알림, 사과로 끝난 답변 뒤에 "so what next?", "그래서 어떤 액션을 하고 있니?" 같은 질문이 이어졌다. 되물으면 Harper는 바로 다음 일을 내놓았다. 반대로 Harper 답변의 약 41%는 이미 질문으로, 약 13%는 "원하시면 ~해 드릴게요"로 끝났다. 그래서 "항상 질문이나 제안으로 끝내라"는 규칙을 넣으면 바로 할 일을 허락받는 질문만 늘어난다고 판단했다.

## 바꾼 것

`src/lib/career/prompts/mainPrompt2.ts`의 main prompt 끝에 `## Ending a reply` 절을 더했다. 답을 마치기 전에 이 답이 사람을 어디에 두고 끝나는지 보게 하는 내용이다.

- 현재 요청과 기존 위임 안의 다음 일은 제안하지 말고 한다.
- 사람이 필요하면(선택, 그 사람만 아는 사실, 외부 실행 승인) 그 요청으로 끝내고, 채널의 답변 수단으로 쉽게 답하게 한다.
- 결과·소식·정정·새 정보를 받으면 무엇이 바뀌고 다음에 무엇이 오는지 말한다. 아직 열려 있는 관련 작업, Harper가 할 일과 소식이 올 때, 사람이 지금 할 수 있는 일이 여기에 든다.
- 마무리하는 대화는 닫는다.

UI 이름(카드·선택지 버튼·폼)은 이 절에 넣지 않았다. 예약 실행 메일도 같은 main prompt를 쓰기 때문이다. 각 수단의 사용법은 채널의 표시 지침에 이미 있다.

## 시험한 안

같은 11개 사례(이어 가기 6개, 부작용 점검 5개)를 돌렸다. 기준선(before)은 각 2회, 각 안(after)은 2~3회다.

| 안 | 위치와 문장 | 결과 |
| --- | --- | --- |
| 1 | Communication 첫 문단 안에 끝맺음 문장 | CV 사례 2회 중 1회만 개선, 거절 소식 사례 변화 없음 |
| 2 | 1에 "제안하고 yes를 기다리면 결정을 떠넘긴다", "열려 있는 관련 작업"을 더함 | CV 0/2, 거절 소식 0/2. 1보다 나아지지 않음 |
| 3 (채택) | main prompt 끝의 별도 절 `## Ending a reply` | 아래 표 |
| 3 + 범위 문장 | 첫 문단의 "A clear small request can finish within that scope"를 "Keep a clear small request within its scope"로 | CV 1/3. 효과가 분명하지 않아 되돌림 |

## 채택안(3)과 기준선 비교

| 사례 | before | after(3) |
| --- | --- | --- |
| c1 CV 수정 보고 | 2/2 결과 보고로 끝남 | 2/2 결과 보고로 끝남. 범위 문장 실험에서 1/3이 탐색으로 이어짐 |
| c2 거절 소식 | 0/2가 남은 일 언급. 위로나 "원하시면 피드백 요청" | 2/2가 제출 실패한 지원 건이나 저장 공고를 꺼냄. 1회는 여전히 "원하시면" |
| c3 3+3 분석 | 2/2 질문으로 끝남, 선택지 버튼 0 | 2/2 질문 + 선택지 버튼, 예약된 준비 언급 |
| c4 정보 답변 | 4회 모두 고쳐 쓸 문장 제시, 이력서 반영은 사람에게 맡김 | 같음(사용자가 직접 고치겠다고 한 사례라 실패로 보지 않음) |
| c5 정정 | 1/2가 탐색 상태 보고로 끝남 | 2/2가 다음 탐색에 필요한 질문으로 이어짐 |
| c6 선호 답변 | 2/2 저장·탐색 후 경력 질문 | 같음 |
| g1 탐색 위임 | 검색함, 묻지 않음 | 같음 |
| g2 단순 질문 | 도구 없이 답만 함 | 같음 |
| g3 마무리 | 짧게 닫음 | 같음 |
| g4 짧은 글 검토 | 고친 글 제시, 발송 질문 없음 | 같음 |
| g5 제출 승인 | 2/2 제출하지 않고 질문, 버튼 0 | 2/2 제출하지 않고 질문 + 선택지 버튼 |

부작용 점검 사례에서는 쓸데없는 질문, 바로 할 일의 허락 구하기, 범위 밖 작업, 무단 제출이 늘지 않았다.

## 남은 문제

- **CV 수정 보고(c1)는 고쳐지지 않았다.** 요청 범위가 수정 하나라서 모델은 수정 결과를 말하는 것으로 끝낸다. 다음 일(지원할 역할 찾기)은 요청 범위 밖이다. "작은 요청은 그 범위에서 끝날 수 있다"는 기존 문장은 비용이 큰 탐색이 저절로 번지는 것도 막고 있어서 지우지 않았다.
- **"원하시면 ~할게요"는 줄었지만 남아 있다(c2 1회, g1 1회).** 회사 에이전트에게 묻는 일은 기존 위임 안이지만, 모델이 여전히 제안으로 남긴다.
- fixture의 검색 결과에 공고 원문 링크가 없어 "원문을 확인하지 못했다"는 문장이 거의 모든 탐색 답변에 붙는다. 이것은 평가 환경이 만든 것이다.
- professional 버전과 웹 채팅만 확인했다. 친근한 버전, 예약 실행 메일, 운영의 실제 도구 결과에서는 돌리지 않았다.

## v2 추가 비교 (같은 날)

운영에서 평서문으로 끝났던 유형으로 [cases-v2.json](../cases-v2.json) 16개를 만들었다. 카드 저장·보관, 지시 반영, 새 사실, 설명 질문, 소개 요청, 파일 수신, 공고 상세, 부작용 점검 4개가 들어 있다. 수정 전, 채택안, 가벼운 안(runner의 `light`: "평서문으로 끝날 답이면 짧은 질문, 다음에 할 일 제안, 선택지로 끝내라" 두 문장)을 1회씩 돌렸다. 가짜 도구 결과 때문에 꼬인 3건(s3, s9, s11)은 셈에서 뺐다. 이어 가기 9건 중 평서문으로 끝난 답은 수정 전 7, 채택안 4, 가벼운 안 5였다. 이력서 확인(s6)과 개인 프로젝트 답변(s12)은 두 안 모두 나아졌다. "기억해 둘게요", "등록했어요", "보관했어요"처럼 짧게 받아 주는 끝맺음(s1, s4, s7)은 세 안 모두 그대로였다. 부작용 점검 사례(질문 금지 요청, 3줄 요약, 짧은 감사, 하소연)에서 문제는 없었다. 사용자는 채택안을 유지하기로 했다. 실행 기록: `runs/2026-11-23T10-10-25.911Z`.
