# 메일 답장으로 지원하기 — 로컬 구현 및 검증

배포하지 않았다. 운영 후보자·회사·지원서·메일은 변경하지 않았다. 아래 결과는 로컬 코드와 합성 데이터 검증 결과다.

## 구현

- 메일도 웹의 기본 모델(`gpt-6.1-sol`, reasoning `high`), Career agent, capability/handbook loader 및 공통 도구 목록을 사용한다. 메일의 별도 모델과 누락된 브라우저 도구 허용 목록을 수정했다.
- 공통 역할 prompt에서 웹 표시 계약을 분리하고, 메일에는 실제 전달 계약만 적용한다. 카드·중간 발화는 메일로 전달되지 않으므로 최종 본문이 필요하다. `suggest_form`은 같은 원본과 revision을 저장하고, 모델이 검토 내용·질문을 Markdown 본문으로 작성하면 기존 HTML/plain-text renderer가 처리한다. 사용자의 자연어 답장은 앞선 검토와 공통 도구로 처리한다.
- 브라우저 실행은 기존 서버 도구를 사용한다. 요청 시간이 끝나면 실행을 취소하거나 다시 제출하지 않고 기존 실행 결과와 transcript를 checkpoint에 저장하고 동일 메일 작업을 이어간다.
- 사람의 로그인이 필요하면 소유권을 확인하는 `/career?browserSession=<operation ID>`로 안내한다. 해당 세션을 펼치며 모바일에서는 채팅 화면도 연다. URL에는 provider 인증 정보가 없고, 링크 열기는 브라우저 실행·제출 승인이 아니다.
- application handbook의 개인 사실 추측 지침을 수정했다. 확인된 사실로 작성하고 빠진 실제 정보는 사용자에게 확인한다. 이메일의 기존 ‘field values를 보고하지 말라’는 지침도 제거해 실제 지원서 검토와 충돌하지 않도록 했다.

## 실제 모델 검증

입력·판정 기준: `cases-v2.json`, `gold-v1.json`, `manifest-v2.json`. 실행: `node --import tsx scripts/evalEmailApplicationAgent.ts`.

최종 run: `runs/2026-11-02T06-29-46-212Z`. 실제 `gpt-6.1-sol/high` provider 요청 38회, 사용자 답장 8개, 최종 메일 8개. 저장한 원본 provider 입력에서 웹 표시 계약·choice marker·Gmail UI marker가 빠지고 메일 전달 계약이 들어간 것을 확인했다. run manifest에 기록한 runtime source hash는 검토 당시 소스와 모두 일치했다.

| 흐름 | 확인 결과 |
| --- | --- |
| 지원 준비 → 전화번호만 수정해 제출 → 접수 확인 | 메일 본문에 실제 입력·기존 이력서 링크·필수 동의 표시. 답장 뒤 같은 브라우저에서 전화번호만 변경하고 제출. 이후 상태 질문에는 기존 결과만 조회. 브라우저 실행 2회, 세션 1개. |
| 로그인 필요 → 로그인 완료 답장 → 검토 후 승인 | 정확한 인증 링크 제공. 로그인 답장 후 같은 세션에서 작성하고 메일로 검토. 자연어 승인 뒤 한 번 제출하고 사이트의 접수 기록 보고. 브라우저 실행 3회, 세션 1개. |
| 제출 직후 접수 확인 불가 | 검토 후 승인된 제출 한 번. 후속 브라우저 작업은 제출·POST 재전송을 금지한 조회. Gmail 조회 실패를 성공으로 표현하지 않고 최종 본문에 접수 여부 미확인이라고 명시. 브라우저 실행 3회, 세션 1개. |

Codex가 전체 메일 본문, 저장된 폼, 실제 모델이 작성한 모든 브라우저 작업 지시를 직접 읽고 위 기준을 판정했다. 표현의 정규식 검사나 별도 평가 LLM은 사용하지 않았다. `manual-review.json`과 raw 요청·응답·HTML/text는 owner-only ignored run 폴더에 보관한다.

### 실패 및 검증 환경 수정 기록

- `06-16-14-610Z`: 모듈 mock이 실제 브라우저 transport를 가로채지 못했다. 네트워크 차단 장치가 외부 호출을 막았고 중단했다. 이후 실제 executor 아래의 fetch 경계에서 합성 provider를 사용했다.
- `06-18-20-839Z`: 초기 전화번호 수정 흐름 확인. 모델이 form ID를 사용자 승인 메시지 ID로 넣었다가 executor에서 거절된 사례를 확인하여, `authorization_refs` 설명에 정확한 사용자 메시지 ID 및 생략 시 현재 메시지를 사용하는 기존 계약을 명시했다.
- `06-19-37-689Z`: v1 fixture가 호출마다 다음 관측 결과로 넘어가 읽기 전용 재확인에도 제출 완료를 반환했다. 이 run을 성공 결과에서 제외했다. v1은 보존하고, 사용자 턴별 관측과 전체 입력·동의 원문을 가진 v2를 새로 동결했다. 제품의 상황별 분기나 재작성은 추가하지 않았다.
- `06-25-58-648Z`: v2 전체 대화 확인. 문서 조회 fixture의 URL이 실제 라우트와 달라 공통 `getCareerDocumentHref`를 사용하도록 runner를 수정했다. 위 최종 run에서 실제 URL 계약으로 재검증했다.

## 코드 검증과 한계

메일 prompt·tool·renderer·저장 경로, browser lifecycle/projection/link, 웹 prompt 테스트 54개; transport 테스트 4개; browser UI 테스트 6개; 메일 링크 인증·정확한 세션 선택 통합 테스트 1개가 통과했다. 총 65개다. 수정 후 deadline/checkpoint, prompt, 링크 테스트를 필요한 범위에서 다시 확인했다. 관련 ESLint와 변경 파일 whitespace 검사도 통과했다.

실제 모델, 공통 form/browser executor, 소유권·revision 검사, HTML/plain-text renderer는 실행했다. DB는 메모리 fixture, browser provider는 사용자 턴별 합성 관측이다. 브라우저 작업 지시가 옳은지는 수동으로 별도 검토했다. 실제 원격 사이트 탐색·접수, 이메일 consumer/Queue의 운영 실행, Resend/Gmail 발송이나 받은편지함 도착을 검증한 것은 아니다. 긴 브라우저 작업의 checkpoint 및 재조회는 코드 테스트로 확인했다. 이 3개 사례로 임의 사이트 호환성, 일반적인 품질이나 지연 시간을 보장하지 않는다.

전체 TypeScript 검사의 작업 범위 밖 오류는 `CareerWorkspaceScreen.tsx`의 tab 비교, `CareerSuggestionComposer.test.tsx`의 `formSnapshot` 누락, `InternalCallAnswers.test.tsx`의 `allowedToolNames` 참조다. 해당 파일은 이 작업에서 수정하지 않았다.
