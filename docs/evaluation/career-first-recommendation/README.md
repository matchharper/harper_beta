# 첫 추천 품질

2026-11-19. 사용자가 가입 직후 첫 추천을 여러 번 받아 보고 네 가지 문제를 말했다. 이 평가는 그 문제가 고쳐졌는지를 같은 입력으로 반복해 본다. 정본은 [좋은 기회를 어떻게 추천할까](../../career-good-opportunity-recommendation-ko.md) 3절(첫 추천)과 5절이다.

## 사용자가 말한 문제 (2026-11-19)

1. 공고를 하나씩 설명하고 끝난다. 무엇을 왜 찾아봤는지가 없어 특별한 기회로 느껴지지 않는다.
2. 적절하지 않은 회사를 대충 추천한다.
3. 개수가 고정적이다. 늘 3~4개다.
4. 말이 템플릿 같다. 짧은 문장 두 개, 공고별 설명, 끝맺음 문장의 순서가 늘 같다.

사용자가 든 이상적인 예시는 [reference-2026-11-19.md](reference-2026-11-19.md)에 그대로 둔다. 이 예시는 품질의 방향을 보여 주는 참고다. 문장, 회사 이름, 숫자, 문단 수를 정답으로 삼지 않는다.

## 좋은 첫 추천의 기준

모든 기준은 실제 최종 답변과 게시된 기회, 도구 기록을 사람이 읽고 판단한다. 키워드나 길이로 채점하지 않는다.

| 기준 | 통과 | 실패 |
| --- | --- | --- |
| 1. 찾은 이야기 | 이 사람의 이력에서 무엇을 눈여겨봤는지, 그래서 어느 방향들을 왜 살폈는지를 그 사람의 사실로 말한다. 실제로 본 범위(회사·공고 수 등)는 도구 결과에 있을 때만 쓴다 | "프로필을 바탕으로 찾아봤어요" 같은 일반 문장, 이력과 연결되지 않는 방향, 도구 결과에 없는 숫자 |
| 2. 적합성 | 추천한 모든 기회가 이 사람의 조건(지역·원격·직무·수준·명시한 제외)에 맞고, 왜 옮길 만한지가 현재 자리와 비교해 설명된다. gold에서 맞지 않음으로 둔 기회를 넣지 않는다 | 조건과 어긋난 기회, 유명하다는 이유만 있는 기회, 수를 채우려 넣은 기회 |
| 3. 개수 | 찾은 것과 이 사람의 상황에 따라 달라진다. 좋은 것이 많으면 많이, 적으면 적게 주고 그 이유가 드러난다 | 페르소나가 달라도 3~4개로 같다 |
| 4. 글 | 방향이나 이야기로 기회를 묶어 자연스럽게 이어 간다. 기회마다 이 사람에게 왜 특별한지가 다르게 쓰인다. 다음 행동(지원 준비, 연락 경로, 팔로우)을 구체적으로 제안한다. 필요하면 마크다운이나 카드를 쓴다 | 페르소나가 달라도 첫 문장·목록·끝맺음의 뼈대가 같다 |
| 5. 사실 | 연봉·투자·인원 같은 주장은 도구 결과에 근거가 있다. 모르는 것은 꾸미지 않는다 | 근거 없는 숫자나 사실 |

**통과 조건.** 모든 페르소나가 1·2·5를 통과한다. 3은 페르소나 사이에 개수가 달라야 한다. 4는 두 답변의 뼈대가 같으면 실패다. 한 번의 좋은 결과로 결론 내지 않고, 같은 입력을 두 번 이상 돌려 본다.

기준과 별도로, 이 턴이 work note를 남겼는지도 본다. note는 한 일을 기록해 나중 요청과 예약 실행이 같은 일을 다시 하지 않게 하는 것이다. matching의 work note라면 탐색에서 배운 점과 전체 작업의 요약이 들어 있어야 한다.

## 평가 단위와 입력

- 단위: 온보딩을 마친 뒤의 background 턴(`conversation_completed`) 한 번. 실제 production prompt plan, 도구 정의, 모델 기본값을 쓴다. 도구 실행은 frozen 결과로 대신한다.
- 입력: `cases-<버전>.json`의 합성 페르소나(실존 인물 아님)와 페르소나별 frozen 검색·회사 결과. `gold-<버전>.json`은 리뷰어 전용이며 모델에 주지 않는다. 생성 전에 SHA-256 manifest를 고정한다.
- 실행 기록은 runs/에 둔다. git이 무시하는 로컬 폴더다. 공개 보고는 reports/에 둔다.

## 데이터 (v1, 2026-11-19 고정)

- `cases-v1.json`: 합성 페르소나 4명이다. 대형 IT 회사 번역 제품의 ML 엔지니어(해외 대학, 원격 가능, 가상자산 제외), Python 백엔드 6년(주말 근무·주말 온콜 불가), 핀테크 프로덕트 디자이너(AI 제품, 서울 출근만, 최소 7,000만), 회사가 문을 닫아 한 달 안에 옮겨야 하는 시니어 PM이다. 온보딩 대화, 프로필·이력서, Brief·Memory, 설정이 들어 있다. 가상의 회사 42곳의 개요·팀·채용 신호와 페르소나별 후보 24~30개(공고와 공고 없는 회사), 웹 기사 24건, 채용 페이지를 함께 둔다. 후보에는 잘 맞는 것, 그럴듯하지만 약한 것, 조건과 어긋나는 것이 섞여 있다. URL은 모두 `.example` 도메인이다.
- `gold-v1.json`: 후보마다 strong·acceptable·unfit과 그 이유를 적었다. 리뷰어 전용이며 모델에 주지 않는다.
- `manifest-v1.json`: 두 파일의 SHA-256이다. runner는 실행 전에 이 값을 확인한다. 후보나 판정을 바꾸려면 v2를 만든다.

## 데이터 (transfer-v1, 2026-11-19 고정)

v1으로 prompt를 고친 뒤, 고친 내용이 다른 상황에도 통하는지 보려고 따로 만든 페르소나 2명이다. 첫 생성 전에 manifest를 고정했다.

- `cases-transfer-v1.json`: 고등학교 수학 교사 5년 뒤 데이터 분석 부트캠프를 마치고 PM·운영 쪽 첫 직무를 찾는 사람(직접 관련 경력이 거의 없음, 서울, 최소 4,500만, 실적 영업 제외)과, 엔지니어링 리더 15년 차로 VP·Head of Engineering 자리 몇 개만 사실대로 받고 싶어 하는 사람(시리즈 C 이상이거나 흑자인 회사, 기본급 2.5억 이상, 초기 스타트업 CTO 제외)이다. v1의 회사 목록을 그대로 쓰고 회사 4곳과 웹 문서 4건을 더했다. 후보는 각각 16개와 12개다.
- `gold-transfer-v1.json`, `manifest-transfer-v1.json`: v1과 같은 방식이다.

## 실행

harper_beta에서 실행한다.

```sh
NODE_PATH=./node_modules/next/dist/compiled NODE_OPTIONS=--conditions=react-server \
  pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/evalCareerFirstRecommendation.ts --dataset v1 --repeat 2 --label <이름>
```

- runner: [scripts/evalCareerFirstRecommendation.ts](../../../scripts/evalCareerFirstRecommendation.ts). `--dataset`은 `v1`(기본값)이나 `transfer-v1`이다. `--only id,id`로 페르소나를 고른다. `--render-prompt <id>`는 모델을 부르지 않고 이 턴의 system 입력을 출력하고, `--validate-only`는 도구 결과 렌더링만 확인한다.
- 이 턴의 입력은 `processCareerBackgroundRun` → `runCareerChatTurn`이 만드는 prompt 인자를 fixture로 다시 만든 것이다. 실제 Decisions preload 선택, capability runtime, 도구 schema, 운영 기본 모델(`resolveCareerTextChatModel()`)을 그대로 쓴다. 모델·reasoning을 바꾸는 인자는 없다.
- 도구 결과는 fixture에서 현재 운영 형식으로 렌더링한다. 검색 결과 줄·장부·경로 기록, 회사 카드, 공고 상세, 웹 검색과 페이지, 게시 영수증과 검색 작업 요약이 여기에 해당한다. 순수 formatter는 운영 코드를 그대로 불러 쓴다. 준비하지 않은 도구는 오류로 돌려주고 결과의 `unknownTools`에 남긴다.
- DB와 외부 실행은 없다. 네트워크는 OpenAI·Anthropic 모델 API만 허용하고, 나머지 요청은 막아 `blocked-network.json`에 남긴다.
- 실행마다 `runs/<시각>-<이름>/`에 manifest(fixture와 source 파일 SHA-256, 모델, git revision), 모든 provider 요청·응답, 페르소나·회차별 결과(도구 호출과 합성 결과, 게시한 기회, 최종 답변, 토큰·비용)와 리뷰용 md를 owner-only로 저장한다.
- 판정은 사람이 답변·게시 목록·도구 기록을 읽고 한다. 문구 수 집계는 참고로만 쓴다.

## 한계

- 검색 결과가 frozen이라 실제 시장에서 좋은 회사를 찾는지(2번의 절반)는 이 평가로 알 수 없다. 그 부분은 [live discovery](../career-opportunity-discovery/README.md)로 본다. 로컬 Supabase가 필요하다.
- 합성 페르소나 몇 개로 일반적인 품질을 단정하지 않는다.
- 도구 결과가 즉시 돌아오므로 실제 첫 추천까지 걸리는 시간과 비교하지 않는다. Decisions preload 선택은 실제 호출이라 회차마다 달라질 수 있다.
- 같은 검색 경로를 다시 쓰면 같은 후보가 돌아온다(새 후보 0). 직무명을 바꿔 다시 찾는 효과는 이 평가로 볼 수 없다.
- note 도구(`read_notes`·`upsert_note`)는 메모리 안에서 실행한다. 이 턴이 남긴 note를 다음 요청이나 예약 실행이 실제로 이어 쓰는지는 이 평가로 볼 수 없다.
- 회사·공고 주소는 모두 `.example`이고 실제 사이트는 막혀 있다. 모델이 실제 회사 사이트를 열어 보다가 자료 전체를 실재하지 않는 것으로 보고 아무것도 추천하지 않은 회차가 있었다(2026-11-19 5회차 ML). 이런 회차는 평가 환경의 한계로 따로 적는다.
