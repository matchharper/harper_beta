# 이메일 Apply with Harper 실제 모델 대화 검증

2026-10-14. 배포 없이 로컬 DB와 캡처 메일을 사용했다. frozen `application-v1`의 3개 대화·5개 발화를 실제 이메일 consumer, Career LLM, 제안 writer, 공통 도구 executor, 이력서 저장, 재개 처리, 이메일 renderer로 실행했다. 외부 JD/양식과 지원 사이트 접수만 합성 adapter다. 운영 데이터·외부 수신자·실제 회사 지원을 사용하지 않았다.

## 확인한 경험

| 대화 | 결과 | 실제 모델 실행 시간 |
| --- | --- | --- |
| 앞선 추천에 지원 요청, 이력서 있음 | 기존 추천과 이력서를 읽어 바로 준비. 수정안·원문·이유와 질문이 첫 메일에 포함됨. 자연어 승인 후 원본을 보존한 사본 저장, 지원 도구 호출, 합성 접수 1회, 결과와 문서/접수 링크 메일. | 첫 메일 27.27초, 승인 후 결과 18.29초 |
| 로그인 때문에 대신 제출 불가 | 제안은 정상 준비. 직접 지원 요청을 지키며 승인한 문구로 사본 저장. 로그인 제한과 직접 지원 경로를 안내하고 접수 완료를 주장하지 않음. | 첫 메일 24.25초, 승인 후 결과 15.95초 |
| 저장 이력서 없음 | 문서 조회로 없음을 확인. 첨부 또는 기존 프로필로 생성하는 방법을 안내. 원문 없이 준비 활동을 만들거나 지원을 실행하지 않음. | 7.62초 |

최종 기준 run은 `runs/application-20261014-g`와 `runs/application-20261014-h`다. 메인 모델과 제안 writer는 기존 기본 `claude-sonnet-5-5`. 실제 provider 응답은 모두 200이었으며 기본 모델에서 끝났다. 첫 사용자 요청부터 결과까지 메시지를 추가로 꾸며 넣지 않고 실제 원본 inbound job을 재개했다. 모든 발화에 한 통씩 총 5통이 캡처됐고, 실행/발송 오류는 없었다.

캡처된 답장 원문과 저장 이력서 전체를 읽어 검토했다. 확인하지 않은 경험은 추가하지 않았고 성과 수치·학력·경력 기간을 보존했다. 수동 지원 대화에서는 프로필과 이력서의 근무 종료일 불일치를 모델이 발견했다. 답을 받지 못한 뒤에도 날짜를 임의 수정하지 않고 원문을 보존하며 확인할 점을 안내했다. 같은 공통 도구와 context로 처리했으며 이 사례를 runtime 분기로 만들지 않았다.

## 실제 실행에서 발견해 수정한 문제

1. 이메일 시작 도구에 언어 설정이 전달되지 않아 제안이 영어로 생성됐다. 현재 사용자 설정을 기존 tool context에 전달해 저장 활동과 제안 언어를 맞췄다.
2. 준비 완료 후 같은 수신 메시지를 재개할 때 내부 진행 메시지가 대화 끝에 놓여 기본 모델이 assistant prefill로 거부했다. 대화 입력을 실제 source message 시점까지로 구성하고 이후 진행은 현재 application context에서 제공한다. 원래 source가 최근 창에서 빠져도 같은 실제 source를 사용하며 새로운 사용자 지시를 만들지 않는다.
3. 진행 중에는 답장을 보낼 수 없는데 빈 본문 복구 모델을 먼저 호출해 문구를 만든 뒤 폐기했다. transport의 finalization 전 hook에서 미완료 작업을 넘겨 불필요한 복구 호출을 제거했다. 실제 본문 저장 시점에는 소유권/진행 상태를 다시 확인한다.

초기 실패 run은 삭제하거나 덮어쓰지 않았다. harness 자체의 문서 필드, checkpoint 재개, 동시 실행 capacity 문제도 별도 기록돼 있다. 마지막 실행은 이 문제를 해소한 상태다. 예시 답장을 감지하는 코드나 언어·문장 판정 후 덮어쓰는 코드는 추가하지 않았다.

## 구조 검증과 한계

- 실제 저장 원본의 revision·텍스트가 유지됐고 지원에 넘긴 사본 ID가 저장 문서와 일치했다. 합성 접수는 정확히 한 번, 직접 지원/이력서 없음은 0번이다.
- 캡처 HTML의 본문 영역과 절대 링크, plain text의 앱 제어 payload 미노출을 확인했다. raw 결과는 ignored 디렉터리 0700/파일 0600이다.
- 실행한 fixture 계정·역할을 정확한 ID로 정리했고 잔여 talent/role 행과 test-only role fit 행이 0임을 확인했다.
- 관련 회귀 테스트 76개, TypeScript, 변경 실행 경로와 runner ESLint가 통과했다. 기존 v1 frozen 12개·13발화 검증도 유지한다.
- 지원 사이트 adapter는 실제 승인 후 queued 상태와 문서 ID를 요구하지만, 브라우저의 폼 입력·PDF bytes 업로드·외부 접수는 실행하지 않는다. 이번 결과는 이메일 대화/준비/저장/지원 orchestration 확인이며 실제 접수 E2E 증거가 아니다.
- 일부 답장은 질문 요약과 상세 검토가 겹치고, 최종 안내가 길거나 응답 표현을 예로 들기도 한다. 의미를 제한하는 keyword 로직은 없지만 답장 길이·자연스러움은 더 넓은 평가가 필요하다. 작은 합성 challenge의 Codex 원문 검토이며 모든 입력에 대한 정확도나 독립 사람 평가를 뜻하지 않는다.
- Vercel Queue 재전달은 harness가 같은 consumer를 재호출해 재현한다. 운영 queue, DNS, 실제 mailbox 표시, 문서 로그인 복귀는 검증하지 않았다. 이번 작업에서 코드 배포와 운영 DB 변경을 하지 않았다.


사용자는 이후 이 run의 첫 검토 메일을 작성 품질상 부적합하다고 지적했다. 위 결과는 실행 흐름의 확인이며 자연스러운 작성 품질 통과를 의미하지 않는다. 원인을 추적해 코드의 review 조립을 제거하고 [작성 구조 수정](2026-10-14-application-writing.md)을 진행했다.
