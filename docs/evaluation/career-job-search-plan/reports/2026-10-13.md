## 출력 품질 검토

전체 9개 출력의 JSON과 구조는 유효했다. 고용 형태 제외, 한국·미국, 원격의 soft preference, 30일 cutoff를 모두 보존했다. 현재의 일회성 모델 개발 방향을 과거 인프라 방향으로 되돌리는 출력은 없었다. 실제 검색과 추천은 실행하지 않았다.

- **Sol low**: 도메인·학습·평가의 검색어 그룹을 가장 일관되게 분리하고 영어·한국어 직무명 별칭을 제공했다. 요청하지 않은 최신 공고 가중치를 3회 모두 추가하지 않았다. 한 번의 한국어 직무명 중복은 production normalizer에서 제거되는 작은 결함이었다.
- **Luna low**: 핵심 의도와 필수 필터를 잘 보존했고 가장 빨랐다. 다만 3회 모두 한국어 직무명 별칭이 없어 한국어 제목만 있는 공고의 recall이 낮아질 위험이 있다. FTS 동의어 그룹에 관련은 있지만 다른 기술·방법을 섞었고, 3회 모두 요청하지 않은 최신 공고 가중치를 추가했다.
- **GLM high**: 3회 모두 직무 제목 hard gate에 직무명이 아닌 도메인 이름을 섞어 무관한 직종이 통과할 위험이 있다. FTS에서 더 넓은 영역·기술·방법을 섞었고, 일부 반복은 생성보다 인식 영역까지 추가했다. 최신 공고 가중치도 3회 모두 추가했다. 이번 입력에서는 Luna보다 빠르다는 이점이 없었다.

최신 공고 가중치의 window는 cutoff와 같은 30일이어서 이 사례에서는 통과 공고에 동일 bonus가 붙는 설정이다. 실제 순위가 나빠졌음을 확인했다는 뜻은 아니다. Rubric 점수는 모델명이 보이는 상태에서 Codex가 각 출력 원문을 읽고 평가한 주관적 점수이며, 독립적인 사람의 정확도 평가가 아니다.

## 실행 조건과 한계

- 합성 1건의 동일 production legacy `buildSearchPlan` messages를 9회 재사용했다. 입력은 약 7,588자이며 provider tokenizer 기준 1,981/2,258 tokens다.
- GLM은 Z.AI 고정 OpenRouter Chat Completions high, Luna·Sol은 OpenAI Responses low다. 모델·API·reasoning이 달라 순수한 모델 계산 속도 비교는 아니다.
- 비스트리밍 전체 응답 완료 시간이다. SDK retry·fallback·warm-up 없이 3round에서 순서를 순환했다. 실제 model/provider와 정상 종료를 확인했다.
- Luna·Sol은 첫 회 cache read=0, 이후 두 회=1,978 tokens다. GLM은 첫 회64, 이후 두 회=2,240 tokens다. 자동 prompt caching과 provider 부하를 포함한 측정이다.
- 실제 공고 retrieval precision/recall, 현재 production Sol high와의 차이, production 평균 latency, 최종 추천 품질은 측정하지 않았다.
- 제품 모델·동작은 변경하지 않았다. Production DB·usage log 쓰기, 추천 저장, 메시지·이메일 발송은 실행하지 않았다.
