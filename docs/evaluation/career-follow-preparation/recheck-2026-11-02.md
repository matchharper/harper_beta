# 회사 팔로우 준비 재검증 — 2026-11-02

사용자의 재검증 요청에 따라 현재 checkout에서 다시 실행했다. 운영 DB 쓰기·배포·실제 이메일 발송 없이, 로컬 SQL/도구/큐 계약과 실제 모델 및 공개 웹 검색을 확인했다.

## 발견·수정한 문제

평가 작업은 DB에 저장됐지만 큐 응답을 받지 못한 경우, `prepareFollowedCompanies`가 예외를 기록하고 `ready`로 끝낼 수 있었다. 즉, 이미 실행 중인 유료 평가가 있는데 원본 agent가 먼저 시작되거나 다음 준비가 시작될 수 있었다.

실제 PostgreSQL fixture에 자식 run을 먼저 넣은 뒤 enqueue 응답 오류를 발생시키는 테스트로 재현했다. 수정 전에는 `ready === false` 검증이 실패했고, 수정 후 통과했다.

수정 사항:

- 외부 평가의 `(talent_id, operation_id)`와 내부 평가의 기존 `dedupe_key`에서 정확한 자식 run을 복구한다. 새 테이블·별도 재시도 ID를 만들지 않았다.
- 실행 중인 자식 평가가 있으면 같은 부모 실행에서 기다린다. 이미 시작한 평가를 다시 만들지 않는다.
- 외부 평가 등록 뒤 중단되어 내부 평가가 등록되지 않은 경우에는 빠진 내부 요청만 이어서 등록한다.
- 복구된 통신 오류는 다음 정상 확인에서 지워 현재 실패처럼 전달되지 않게 했다.
- 자식 실행 저장소 자체를 읽지 못한 경우에는 준비 완료로 간주하지 않는다. 기존 실행 재시도 경로를 따른다.

## 실제 공개 검색

기존 `runWebSearch`와 `refreshHiringNews`를 실제 Exa 검색 서비스에 연결하고, DB 및 문서 캐시 쓰기는 로컬 PGlite/메모리에 격리했다. 회사는 공개된 네이버와 토스 identity를 사용했다. 테스트 스크립트는 `/tmp/harper-follow-live-search.ts`, 원본 근거는 ignored `runs/live-search-2026-11-02T08-41-05-036Z/`에 저장했다.

- 회사 2곳 모두 검색 성공, 회사마다 10개 출처 반환.
- 같은 회사의 다른 팔로워를 가정한 두 번째 호출에서 검색 결과를 그대로 재사용. **총 유료 검색 호출은 2회**였다.
- 회사 채용 페이지와 실제 채용 행사 자료가 반환되었지만, 과거 마감 행사·날짜 없는 채용 안내 페이지도 섞여 있었다. 검색 문구의 ‘최근 한 달’은 결과의 날짜를 보증하지 않는다.
- 이 관측을 바탕으로 v1 입력은 보존하고, `cases-v2`에 마감된 행사와 일반 채용 페이지의 합성 사례 2개를 추가했다. 날짜/관련성 판정을 코드의 키워드 필터로 구현하지 않았다.
