# 2026-11-08 Career 지원 준비 평가 (로컬, 미배포)

사용자가 지정한 계정의 빈약한 프로필에서 두 지원 시나리오를 실제 Career 원본 모델과 도구로 반복했다. 기대 행동은 실행 후 검토 기준으로만 사용했다. Codex가 전체 응답·폼·문서와 DB 상태를 읽어 개발 검토했으며, 별도 자동 판정 LLM이나 키워드 품질 점수는 사용하지 않았다. 발송·제출·예약·위임은 실행 경계에서 막았고, 실제 공개 자료 조회와 비공개 문서/폼/기회 상태 저장은 수행했다.

## 원인과 수정

1. **직접 연락에 쏠린 목적.** application 원본은 지원 목표를 ‘실제 채용 대화 시작’으로 두고 담당자 이메일 조사와 공식 지원 외 연락 준비를 반복 강조했다. 회사/제품/채용 상황의 조사가 자료와 전략을 개선하는 목적을 먼저 설명하고, 직접 연락의 가치를 맥락에서 판단하도록 기존 문장을 수정했다. startup/공채 예시는 판단을 설명하며 회사별 분기로 구현하지 않았다.
2. **다음 턴에 조사 사실이 빠짐.** 이전 turn record에는 도구명·성공 여부만 남았고 웹 질의/결과는 다음 대화 입력에 없었다. 기존 record에 질의·조회 시점·결과 수·URL·발췌/저장 문서 참조를 저장하고 메시지 projection으로 전달한다. 실패와 0건을 구분한다. 새 판단 테이블이나 반복검색 금지 규칙은 만들지 않았다.
3. **문서 기능과 이력서 지침의 선택이 독립적.** 문서 도구를 받아도 selector가 resume handbook을 선택하지 않을 수 있었다. documents capability를 제공할 때 작성 전에 resume handbook도 제공한다. 원본 handbook의 개선 중심/개인 기여만 질문하던 범위를 생성과 자료 발굴로 수정했다. 공개 회사 사실과 개인 기여는 분리한다.
4. **실제 실행 능력이 빠짐.** 아모레퍼시픽 수정 전 두 실행 모두 종료를 확인했지만 저장함에 그대로 남았다. LLM의 추천 membership archive는 saved stage를 바꾸지 않고, feedback dislike는 사용자 거절이라는 다른 의미다. 기존 Jobs UI의 소유권·현행 추천 검증과 stage RPC를 `upsert_opportunities(action=set_stage)`에 연결했다. 새 공고 분류 규칙이나 만료 전용 도구는 없다.
5. **최소 준비·잘못된 가이드·할 일 카드의 편향.** main의 질문/준비 범위가 너무 좁았고 action guide는 적극적으로 사용자의 할 일을 저장하도록 했다. 결과에 필요한 준비와 정보의 가치로 원본 문장을 수정했다. background guide는 실제 예약/이벤트 invocation에만 제공하며 전달 계약은 background prompt에 둔다.

“유저에게 최대한 도움이 돼라”만으로 2~4의 누락을 해결할 수 없다. 목적은 간결하게 두되 원본 사실의 연속성, 필요한 지침과 실행 능력을 함께 제공해야 한다. 특정 도구를 매번 호출하거나 고정 답변을 요구하지 않았다.

## 가이드가 있던 이유

`opportunity_search`는 기회 탐색·평가 결과 해석·추천 목록 관리 계약이다. 지원한 기회의 유효성이나 대안을 검토할 때 관련될 수 있다. `proactive_career`는 예약된 확인, 회사의 업데이트, 남은 후속 의무 같은 이벤트에서 사용자가 대화 중이지 않아도 일을 이어가는 지침이다. 둘을 동일한 ‘적극적으로 도와라’ 가이드로 취급하면 안 된다. 원본 기록에서 “뭐 좋은 게 있으면 알려줘” 턴(472746)은 두 가이드를 함께 로드했다. 가이드는 세 번의 delivered reply 동안 유지되며, 채널톡 지원 턴(472824)은 application만 새로 읽고 이전 opportunity_search/proactive_career를 이어받았다. 이전에는 공통 카탈로그/selector/잔여 lease를 통해 foreground에도 들어올 수 있었고, background 전제의 문장이 일반 대화에 섞였다. 현재는 카탈로그, selector, lease 복원, 수동 loader까지 실제 invocation 범위에 맞춘다.

일반 도구 수정 후(`2026-11-08T07-58-22-307Z-general-capabilities`): 아모레퍼시픽은 90초/146초, **2/2 종료 이동**, 2/2 회사 관련 공고 웹 조회, **0/2 팔로우 제안**. 기존 관심 표시를 거절로 바꾸지 않았다. 대안 탐색은 부분 달성, 전체 품질은 불합격이다.

같은 run의 Harper 두 번(286초/296초)은 기존 이력서 질문과 다음 턴 조사 연속성은 개선됐지만 회사 맥락 보강과 연락 준비는 미흡했다. 이후 UI와 대조해 실행기가 Apply 버튼의 선행 저장 작업을 빠뜨린 것을 발견했다. 실제 UI는 먼저 관심/저장 상태를 기록하고 메시지를 보내므로 실행기를 수정했다. 이 두 Harper 실행은 완전한 UI 재현 결과로 집계하지 않으며 같은 frozen v1을 다시 두 번 실행했다. 아모레퍼시픽은 초기 상태가 이미 like/saved여서 빠진 동작이 상태상 no-op이었다.

최종 비교는 main의 첫 목적 문장만 ‘사용자가 방법이나 제공할 자료까지 알아야 하는 것이 아니라, 에이전트가 목표에 가장 도움이 되는 일을 판단한다’로 바꿨다. 회사별 행동 순서나 평가 기준을 프롬프트에 복사하지 않았다. 동일 v1에서 두 시나리오를 두 번씩 실행했다.

Harper에서 문서 기능 제공 전에 resume guide가 들어가는 실제 provider 입력을 확인했다. 두 후속 턴 모두 이전 질의/결과 기록을 입력으로 받았고 웹 검색을 반복하지 않았다. 다만 이것만으로 이후 모든 반복 검색을 방지한다고 일반화하지 않는다. 아모레퍼시픽은 두 번 모두 `feedback=like`를 유지하고 `saved_stage=closed`가 DB에 저장됐다. 같은 공고 재확인을 넓은 유사 직무 탐색 성공으로 세지 않았다.

최종 네 실행의 provider 사용량 합계는 input 935,343 tokens (cached 429,235 포함), output 12,135 tokens다. Harper 후속 질문과 selector 호출을 포함하며, 앞선 실험은 제외한다. 공급자 원본 usage를 보관했고 금액은 계산하지 않았다.

마지막 아모레퍼시픽의 최초 setup은 `career_email_onboarding_leads` 잠금 충돌로 세 번 실패했다. 복원 transaction이 롤백됐고 모델 호출 전에 중단됐다. 이를 품질 실패로 세지 않고 누락된 한 번만 동일 설정에서 다시 실행했다. 완료 조회 중 DB 오류도 같은 source의 작업을 관측/재개하며 새 지원을 중복 시작하지 않도록 실행기를 수정했다. 복원은 다른 DB 작업과 충돌하면 실패할 수 있다.

**결론:** 연락 강제 지침 제거, 조사 사실의 연속성, resume guide 연결, 누락된 종료 단계 도구는 개선됐다. 그러나 넓은 목적 문장 하나로 자율적인 자료 보강과 다음 기회 탐색이 안정됐다는 근거는 없다. 이미 아는 역할에서 질문 하나를 고르거나 원래 접수 경로만 재확인한 뒤 돌아오는 행동이 남아 있다. 다음 실험은 이 실패 출력과 실제 입력을 기준으로 남은 최소 준비/경로 중심 지침을 더 줄이는 방향이어야 한다. 회사별 필수 행동이나 합격 답변을 production prompt에 복사하지 않는다.

[harper_eval Draft PR #9](https://github.com/matchharper/harper_eval/pull/9)에 버전 고정 시나리오와 반복 실행·검토 계약을 추가했다. 제품 실행기는 이 checkout의 `scripts/evalCareerScenarios.ts`이며, 실행하지 않는 목록 확인이 기본이다. 명시적 실행 시 고정 상태 복원 → 실제 Apply 선행 저장 → 동일 대화 실행 → 후속 질문 → 원본 기록/사후 상태 → 기준별 개발 검토를 수행한다. 케이스를 추가해 확장하며, 기대 행동은 모델 입력으로 주입하지 않는다.

## 재현 및 경계

정본 [평가 설명](../README.md), `harper_eval/scenarios/career/v1/cases.json`, canonical `scripts/evalCareerScenarios.ts`. 각 run은 원본 provider 입력/출력, 도구 기록, 전후 상태, source revision/diff, 모델 설정을 비공개 ignored 경로에 보존한다. gold는 변경하지 않았다. 고정 기준은 실제 ChannelTalk 지원 직전 메시지/문서를 복구한 재구성본이며 모든 mutable row의 과거 시점 백업은 아니다.

Harper fixture는 실제 공개 회사 정보를 사용하는 **테스트 지원 페이지**이고 검색으로 찾은 같은 제목의 실제 LinkedIn 공고는 닫혀 있었다. 따라서 실제 채용 접수 가능성은 테스트 성공과 별개다. 다만 평가자가 별도로 확인한 [공식 소개 페이지](https://matchharper.com/about)에는 창업자 연락처와 채용 링크가 있었다. 테스트 페이지/LinkedIn 종료만으로 직접 연락 조사 실패를 정당화하지 않는다. 웹은 live이며 같은 입력이 같은 웹 결과를 보장하지 않는다. 최종 출력의 품질을 도구 호출 성공과 혼동하지 않는다.

## 실제 화면과 최종 상태 확인

로컬 `/career`에 대상 계정으로 로그인한 격리 브라우저에서 세 버튼(채널톡 지원 전, 아모레퍼시픽, Harper)을 각각 확인 창을 거쳐 실제 실행했다. 복원 후 전체 페이지 재로딩과 DB를 확인했다. 기본 복원은 메시지 32개/문서 0개/경력 5개, 아모레퍼시픽은 같은 기준에 해당 추천 like/saved, 마지막 Harper 복원은 같은 기준에 새 Harper 추천(feedback/saved_stage null)이었다. 계정은 마지막 Harper 상태로 남겼다. 기본 브라우저의 다른 계정 세션은 바꾸지 않았다. 복원 확인 중 무관한 자동 재인사 요청은 격리 브라우저에서 차단했으며, 전체 Apply UI 클릭 평가를 했다는 뜻은 아니다. Apply 모델 실행은 위 canonical runner로 검증했다.
