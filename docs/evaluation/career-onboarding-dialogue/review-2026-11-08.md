# Career onboarding dialogue review — 2026-11-08

Local implementation only; not deployed. Fixtures are synthetic and frozen before evaluation. No real user data, production completion, recommendation, outbound call or DB write was performed by these runners.

## Root cause and implemented boundary

The old extractor treated a saved Brief under a topic key as coverage, even when its content only said compensation mattered. Covered topics lost their follow-up guidance. Both text and voice also used the count of covered topics to override completion, independently of the conversational model. Voice additionally had prefix-clipped history and two models with question-selection instructions.

The conversation model now receives profile, saved facts, actual questions/answers and topic purposes, and owns meaningful follow-ups and completion. The extractor stores facts only. Historical coverage flags do not suppress chat/voice topics or decide completion. Explicit uncertainty, no constraints and refusal are usable context; current/past compensation disclosure is optional. The existing text completion marker and voice end_call command remain execution contracts. Persistence, ownership and idempotency remain enforced.

The existing reasoning backend receives the shared onboarding purpose plus actual profile, saved facts and recent conversation. The audio model delegates substantive onboarding turns and speaks the backend handoff. Saved-context updates refresh the backend, without replaying full transcripts through the speaker append endpoint (which has a 500-token limit). end_call receives a factual acknowledgement that ending is scheduled and persistence is pending, then the backend supplies a closing handoff. Playback drains before the existing save/disconnect owner runs. Duplicate response events cannot trigger the transition twice. No canned goodbye or semantic output filter was added.

## Voice review

Voice uses gpt-live-1 with the production gpt-6.1-sol/xhigh delegation configuration and Korean macOS Yuna audio through the real Live WebSocket endpoint. The multi-turn compensation case sends a second audio answer after the first response settles.

During development, actual end_call commands exposed an unanswered-tool protocol defect: the backend never received a tool result, so the speaker often stopped at an interim acknowledgement. Returning a scheduled-action result and allowing the backend's final handoff fixed that delivery path. Early iterations also exposed independently selected frontend questions. Several voice configurations were evaluated. Giving ordinary onboarding decisions to the audio model caused repeated known topics and missed completion, so that candidate was rejected. Having the backend write literal replies also left unsolicited interim speech. The selected implementation keeps question/completion judgment in the reasoning backend, with a focused audio-model delegation policy. The existing runner additionally replayed history as frontend input unlike production startup; it now uses the production instruction-based context path. Earlier failing runs remain in ignored artifacts. They are not hidden or counted as clean acceptance evidence.

The required Live policy headings were retained per the [official prompting guide](https://developers.openai.com/api/docs/guides/live-prompting#recommended-prompt-structure); scheduled end_call results follow the [documented tool continuation flow](https://developers.openai.com/api/docs/guides/live-delegation#return-tool-results-and-approvals). Native Live speech remains independent of delegated work. We did not add semantic keyword filters, a second reviewer, or a new persistence state to hide unwanted speech.

### Remaining voice quality limitation

In the selected five scenarios, the backend issued the expected commands for incomplete compensation followed by an amount, explicit uncertainty/refusal, sufficient context and early stop. However, the live audio model sometimes invents interim speech while waiting: an extra question, an inaccurate announcement that it is preparing a question/starting onboarding, or a repeated closing. This is a known unresolved output-quality issue, not a passed test. Removing coverage gates and fixing completion transport does not by itself guarantee every spoken turn. The implementation remains local and has not been deployed.
