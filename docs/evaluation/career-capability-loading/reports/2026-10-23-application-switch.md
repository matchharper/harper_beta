# 지원 준비 전환 — 로컬 검증 (2026-10-23)

## 원인과 변경

읽기 전용 운영 대화에서 사용자가 새 공고 준비와 전환을 반복 요청했지만 종료 확인이 계속 이어진 것을 확인했다. 마지막 사용자 메시지 ID로 pending switch가 다시 저장됐고, 동일 메시지 ID의 전환 요청이 있으면 end를 거부하는 runtime 조건과 일치했다. 사용자 의사를 해석하는 원본 LLM보다 메시지 순서 조건이 우선한 것이 원인이다.

- 해당 순서 조건을 제거했다. 명확한 다음 작업 요청은 기존 준비 저장·종료 후 같은 턴에 이어간다. 가능 여부 질문은 실행하지 않는다.
- 현재 지원 대상 식별자를 compact context에 제공하고, 새 공고 요청과 기존 작업을 구분하는 계약을 preparation prompt 앞에 배치했다. 구형 session prompt의 반복 확인 지침도 정리했다.
- 종료 결과는 저장·재개 가능 여부와 기존 문서 ID를 작은 사실로 반환한다. 웹 브라우저의 `not_started`를 준비 상태처럼 안내하지 않도록 불필요한 raw 상태는 제거했다.
- 기존 `simulate_application`의 선택적 `introduction`을 저장하고 카드 위에 렌더링한다. 카드가 일반 응답을 대체해도 원본 LLM의 안내가 남는다. 고정 성공 문장·키워드 판정·새 도구·DB 변경은 없다.

새 공고의 기존 이력서 선택/Start 카드 계약은 유지한다. 같은 턴에 도구로 그 카드까지 제공하며, 새 분석은 기존 Start 버튼 동작으로 시작한다. 저장한 준비 복귀는 기존 session 도구의 list/resume를 사용한다.

## 검증

동결 v9, 실제 활성 모드 모델 `claude-haiku-5-5`, progressive loader, production prompt·assistant loop·session mutation·종료 결과를 사용했다. 지원 사이트와 DB 효과는 합성 stub이며 운영 계정에 작업을 실행하지 않았다.

| 항목 | 확인 |
| --- | --- |
| 처음 다른 공고 요청 | 같은 턴 end → simulate_application, 기존 문서 유지, 저장/재개 안내 |
| 이미 확인한 전환 | 같은 턴 end → simulate_application, 추가 종료 질문 없음 |
| 가능 여부만 질문 | 도구 호출·상태 변경 없음, 현재 역할과 제출 구분 |
| 저장하고 그만하기 | end만 수행, 나중에 요청해서 재개하는 방법 안내 |

2026-10-23T03-11-40-973Z는 구조 4/4 통과. 안내 의미에서 발견한 두 문제를 수정하고 2026-10-23T03-13-18-665Z에서 해당 2사례를 다시 확인했다. 최종 4개 의미 기준은 두 run의 관련 결과를 합쳐 확인한 범위이며 마지막 run 자체는 2사례 부분 실행이다. 이전 실패와 harness 수정 이력은 각 ignored run의 review.json에 보존했다. 독립 human review나 운영 성공률을 뜻하지 않는다.

관련 회귀 22개 통과 후, context/안내 변경과 연관된 session·closure·resume·카드·미전송 답변 보존 17개를 추가 확인했다. 실제 RPC를 사용하는 PGlite에서 A 저장 → B 진행 → A 재개 시 답변·질문·문서 보존과 소유권을 확인했다. 실제 지원 접수나 시각적인 브라우저 E2E를 실행한 검증은 아니다.

TypeScript 검사에서 변경 경로 오류는 없었고, 범위 밖 기존 테스트 2개(OpportunitySwipeRow.test.tsx, jobTitleSimilarityServer.test.ts)의 오류가 남았다. 관련 diff whitespace 검사 통과.

## 반영 범위

로컬 코드만 수정했다. 배포·운영 사용자 상태 변경은 하지 않았다. 운영에서 실제 사용할 수 있게 하려면 별도 웹 배포가 필요하다.
