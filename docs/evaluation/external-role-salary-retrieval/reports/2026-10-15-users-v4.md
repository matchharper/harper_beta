# 실제 사용자 3명 초기 검색 평가

문서 기준: 2026-10-15. 중단됐던 v4 평가의 저장된 응답과 SQL 결과를 정리했다. 이번 이어받기에서는 유료 모델 호출·추천 저장·발송·배포를 하지 않았다. 원본 입력과 gold는 변경하지 않았다.

## 결과

동일한 검색 계획 안에서 연봉 가중치 0과 0.35를 비교했다. 목표는 모델이 추론한 잠정 검색 기준이며 사용자가 확정한 최저 연봉이 아니다.

| 고정 사례 | 검색 방향 | 잠정 연봉 목표 | 후보 pool → 반환 | 급여 미상: 전→후 | 기존 목록 유지 |
|---|---|---:|---:|---:|---:|
| user-1 | 한국 AI·제품 엔지니어링 | 1억 2,000만원 | 695→500 | 240→248 | 492/500 |
| user-2 | 일본 소프트웨어·솔루션 엔지니어링 | 7,500만원 | 98→98 | 29→29 | 98/98 |
| user-3 | 호주 고객 배포·솔루션·데이터 엔지니어링 | 사용 안 함 | 77→77 | 22→22 | 77/77 |

user-1의 상한이 목표의 60%보다 낮은 추정 급여 역할은 29→25개다. 상위 20개에서 급여 구간 중간값의 중앙값은 8,465만원→10,107.5만원이고, 급여 미상은 8개로 유지됐다. user-2는 전체 pool이 98개이므로 포함 역할은 같고 순서만 달라졌다. 같은 상위 20개 통계는 약 10,886.5만원→11,691.9만원이다. 이 통계는 알려진 구간만 계산했다.

user-1·user-2에는 구조화된 공개 급여가 없어 이 변화는 **추정값을 사용한 순위 동작**을 확인한 것이다. 실제 연봉 정확도나 사용자 만족도 개선의 증거가 아니다. user-3은 다른 조건이 충족되면 보상 무관이라는 명시적 기준에 따라 목표가 null이며, 연봉 반영 전후 목록과 순서가 같다.

## 목록 생성과 실제 도구 연결

1. Profile·전체 Search Brief·기존 Behavior Context로 직무명, 키워드, 국가, 근무 형태, 잠정 연봉 목표를 생성한다.
2. 제목 임베딩 근접 검색과 키워드 순위를 80:20 RRF로 결합한다. 활성 외부 공고, 국가, 기존 추천 제외, 차단 회사 및 testOnly 제외를 적용한다.
3. 공개 급여와 원문 hash가 일치하는 준비된 추정값을 이용해 직무 점수에 `0.65 + 0.7 × 연봉 만족도`를 곱한다. 미상은 만족도 0.5이므로 배수 1이며, 목표가 없으면 모든 역할의 배수가 1이다.
4. 국가 할당을 유지해 최대 500개를 반환한다. 이번 평가는 Worker 기준이다. V2 웹은 최대 200개, 기존 웹 검색은 최대 150개다.

`recommend_job_postings`는 `talentOnboarding/tools.ts` → `externalRecommendationsV2/web.ts`로 들어간다. 기존 경로는 `jobPostingRecommendations.ts`, V2는 `engine.ts` → `retrieval.ts`에서 연봉 목표와 정렬을 사용한다. 기존/full-JD 및 V2 모두 추정 급여를 역할 카드와 후속 LLM 입력에서 제외하며, 누락 급여 보충은 이후 검색에서 사용하도록 저장한다. **코드 연결 확인이며 운영 배포 완료 주장은 아니다.**

## 첫 실행에서 발견한 문제와 수정 후 결과

- user-2는 처음에 엔화 규모의 숫자를 KRW에 넣었고 하이브리드 허용을 원격 전용으로 좁혔다. 공통 prompt의 환산·근무 형태 지침을 보완한 뒤 목표는 1,000만원→7,500만원, 목록은 9→98개로 바뀌었다. 이 목록 크기 변화는 연봉 가중치만의 효과가 아니다.
- user-3의 첫 계획에는 다른 국가도 포함됐다. 수정 후 호주만 77개다. 비자 지원은 초기 SQL에서 검증하지 않았으며 후속 JD 판단이 필요하다.
- 원격·하이브리드 선호, 도시, 경력 수준 등의 세부 적합성은 초기 목록 전체에서 확정하지 않는다. 최종 fit·rerank·추천 발송은 이번 평가에서 실행하지 않았다.
- 일부 수집원/법인에 같은 공고가 중복되는 사례가 남아 있다. 별도 회사명 보정 규칙은 추가하지 않았다.

## 재현 근거와 비용

canonical runner는 `scripts/evalExternalSalaryUserRetrieval.ts`다. 입력은 `manifest-v4-users.json`의 frozen hash, 판단 기준은 `gold-v4-users.json`을 유지했다. 최종 결과의 engine/retrieval/prompts/salary hash는 보고서 작성 시점의 로컬 코드와 모두 일치한다.

| 사례 | 최종 결과 run | 계획·응답 run | 실행 방식 |
|---|---|---|---|
| user-1 | users-2026-10-15T01-22-32-434Z | users-2026-10-15T01-09-57-836Z | 확보된 운영 pool + 로컬 SQL 순위 replay |
| user-2 | users-2026-10-15T00-32-45-355Z | 동일 | 운영 읽기 전용 SQL + SELECT 추정값 overlay |
| user-3 | users-2026-10-15T01-23-13-560Z | users-2026-10-15T00-32-45-355Z | 확보된 운영 pool + 로컬 SQL 순위 replay |

user-1·user-3은 DB 연결 지연 후 기존 모델 응답과 확보된 pool을 재사용했다. 로컬 순위 replay 시간과 운영 SQL 왕복 시간을 서비스 성능처럼 섞어 보고하지 않는다. 최초·수정 모델 응답 6회의 저장된 usage 기반 비용 합계는 **$0.00582770**이며 임베딩 비용은 별도다. 수정 후 최종 계획 호출은 각각 약 15.03초, 13.76초, 9.71초다.

역할명·원문 URL·각 상위 20개·실제 SQL·artifact hash는 ignored owner-only `runs/users-v4-completed-20261015/`의 보고서와 manifest에 보관했다. raw candidate/company 데이터는 이 보고서에 넣지 않았다. 사례 3개를 보고 prompt를 보완한 작은 목적 표본이며 독립 holdout·사용자 관심·지원·오퍼 성과 평가는 아니다.

## 운영 DB 재확인과 남은 실행

운영 DB를 읽기 전용으로 확인했다. `salary_is_predicted` boolean은 존재하고 `opportunity_quality_score`는 없다. 추정 급여 저장, summary 저장, 재수집 시 추정값 보존 함수 본문이 반영돼 있다. 연봉 함수는 미상 0.5, 목표 이상 구간 1, 상한만 5천만원/목표 1억원에서 0.125를 반환했다. 추가 schema 변경은 필요하지 않았다.

추정 급여 저장은 **0건**이다. pre-fill 64,144개 중 64,139개는 준비됐고 5개는 미상이다. 기존 준비 비용은 $14.05841, 실패 비용 예약을 포함하면 $19.42437이다. 웹·Worker의 새 reader 배포 확인 후 준비된 결과를 저장해야 하며, 저장 시 원문 변경이나 새 공개 급여가 있으면 해당 행을 건너뛴다. 현재 요청에서 배포하지 않았다.

관련 검사 `salary.test.ts`, `jobPostingRecommendations.sql.test.ts`, `engine.test.ts` **17/17 통과**. 전체 테스트·실제 추천 발송은 실행하지 않았다.
