# 회사 자랑으로서의 온보딩 Pitch 재검증

2026-10-09. 사용자가 Pitch의 목적을 정정한 뒤, 같은 Haiku 5.5 high 설정으로 실제 저장본과 완료 답변을 다시 검토했다. 로컬 코드와 격리 DB의 검증이며 미배포 상태다.

## 무엇을 검증했는가

Pitch는 Harper가 후보자에게 회사를 소개할 때 활용하는 회사의 강점과 근거다. 공개 광고 문구나 직무 설명의 작성이 아니라, 어떤 회사이고 왜 합류할 만한지 설명할 수 있는 회사 자료를 저장하는 단계다.

[frozen v2](../README.md)는 v1의 세 사례를 그대로 유지하고, 실제 성과·조건부 혜택·직무 설명이 잘못 들어간 Pitch의 정리 사례를 추가했다. 여섯 입력과 새 gold는 첫 v2 실행 전에 동결했다. v1과 앞선 실행은 덮어쓰지 않는다. 문장·단어 매칭이나 다른 LLM의 자동 채점 없이 전체 저장본, 답변, tool 효과와 provider 요청을 자체 검토했다.

## 확인한 문제와 변경

기존 저장본은 원격 근무·제품 의사결정·엔지니어의 책임을 정확히 보존했다. 이를 직무 요건으로 저장한 문제는 관측되지 않았다. 앞선 설명과 평가가 사실 보존에 치우쳤다는 점을 바로잡는다.

확장 사례에서는 실제 개선할 문제가 드러났다.

- Pitch 입력을 팀 규모나 투자 단계 등 다른 회사 항목을 자동으로 채울 요청으로 확대했다. 입력의 수정 범위를 Pitch에 한정했다.
- 완료 후 투자 금액을 더 알려 달라는 불필요한 질문을 붙였다. 화면의 다음 이동과 함께 제출을 마무리하는 결과 계약을 명확히 했다.
- 개선 과정에서 완료 답변이 일상적인 제품 결정의 자율성을 더 넓은 투자자 압박 부재로 설명하거나, 고객 피드백 반영에 입력에 없는 즉시성을 더했다. 완료 답변도 실제 저장 내용의 범위·조건·확실성을 보존하도록 수정했다.
- 저장과 후보자에게 소개하는 시점을 혼동하는 표현이 나왔다. 입력 맥락을 Harper의 소개에 활용하는 내부 회사 자료로 명확히 하고, 공유 제한은 해당 사실과 함께 보존하도록 했다.

수정 원본은 `src/lib/org/agent/onboardingPrompt.ts`다. 같은 일반 read/update 도구를 유지하고, 출력 후처리·키워드 품질 판정·별도 추출 모델·시나리오별 실행 분기를 추가하지 않았다. 모델은 Haiku 5.5 / OpenRouter / high 그대로다.

## 검증 범위와 한계

- 실제 production 모델 loop·공통 저장 executor·격리 로컬 DB의 저장본을 확인했다. 브라우저·HTTP·실제 후보자 소개 전달의 검증은 아니다.
- 변경 prompt와 canonical runner의 targeted ESLint와 해당 변경의 whitespace 검사 오류 0. 모델 설정·도구 계약은 변경하지 않았으며 앞선 코드 회귀 49개 통과를 새로운 Pitch 품질 성공률에 합산하지 않는다.
- 이번 다섯 run에서 만든 합성 회사·계정 30개를 exact ID로 정리했다. Role fixture는 만들지 않았다. 운영 DB·메일·Slack·검색 worker는 사용하지 않았다.
- 기존 로컬 검색 이력 reader의 `scheduled_role_ids` 누락 경고는 저장과 별개로 남았다. schema나 migration을 변경하지 않았다.
- 마지막 모델 실행 이후 canonical runner에는 task·sampling·prompt hash·artifact 경로 등 기록 필드만 보강했다. production prompt·모델·저장 실행은 변경하지 않았다. 원래 실행 소스는 snapshot으로 보존한다.
- 여섯 합성 개발 사례이며 운영 대표 표본·독립 팀원 검토·매 실행의 품질 보장이 아니다. 처음 세 입력은 이전 결과를 본 뒤 만든 정답 기준이고, 새 세 사례도 자체 작성 gold다. 중간 실패와 최종 사용성 경고를 보존한다.
