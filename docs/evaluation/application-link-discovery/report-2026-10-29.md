## 실제 실패와 수정

1. 최초 실행은 Wanted를 먼저 열고 로그인 제한을 확인하는 데 브라우저 호출 1회를 썼다. 라이너 검색 결과 1번에는 공식 채용 목록이 있었지만, 상세 공고 URL만 허용하는 지침 때문에 커리어리/리멤버를 골라 다시 로그인 제한에 막혔다. 채널톡만 두 번째 검색에서 Lever를 찾아 성공했다. 원본 실패 run을 보존했다.
2. 잡플랫폼 원본에서는 공식 경로 탐색을 우선하도록 안내했다. 상세 공고가 색인에 없으면 공식 채용 목록도 조사할 수 있게 하고, URL 도구의 외부 인자는 그대로 유지하면서 실행기가 회사·직무·위치를 Browser-use에 함께 제공한다. 브라우저는 해당 직무를 찾아 상세 → 지원 폼으로 이동한다. 다른 직무로 대체하지 않는다.
3. 수정 후 첫 3건 실행은 모두 검색 1회/브라우저 1회로 성공했다. 그러나 라이너의 필수·선택 개인정보 동의가 하나의 required 그룹으로 묶였다. 독립적인 필수 여부가 있는 항목은 별도 질문으로 추출하도록 공통 입력 계약을 보완했다. ‘읽기 전용이어서 제출하지 않음’ 자체를 접근 제한으로 적지 않도록 지침도 정리했다. 키워드 필터나 출력 덮어쓰기는 추가하지 않았다.
4. 공식 목록에서 시작할 수 있으므로 저장된 공고 URL에는 접근이 확인된 실제 지원 URL만 기록한다. 목록·로그인·접근 미확인 URL로 기존 공고를 덮어쓰지 않는다. 반복 테스트 프리셋은 source.id=null이므로 운영 공고를 전혀 갱신하지 않는다.

## 최종 검증 범위

- 실제 페이지 컴포넌트와 실제 `POST /api/internal/debug/application-form`를 로컬 harness에서 실행했다. Ops 로그인/주변 shell만 로컬 fixture로 대체했다. 운영 인증 통과 여부를 검증한 것은 아니다. API의 입력 검증·프리셋 선택·agent·Exa·Browser-use·NDJSON 응답·결과 렌더링은 실제 구현을 썼다.
- Security Engineer는 실제 화면에서 프리셋 선택 → 조사 버튼 → 결과 표까지 확인했다. 나머지 두 건도 동일 POST에 각 프리셋을 넣어 실제 실행했다. 드롭다운의 세 항목과 Wanted URL 표시, 실행 중 입력 잠금, 완료 후 8개 항목과 필수·선택 표시를 확인했다.
- 최종 세 건 모두 `read`, `supported`, 미확인 제한 없음; 각각 Exa 검색 1회와 Browser-use 1회. 이는 공개 폼에 접근했다는 뜻이며 제출 성공을 증명하지 않는다.
- 최종 세 Browser-use run은 completed를 확인했고 브라우저 PATCH 응답 3건 모두 stopped였다. 개인정보 입력·동의 선택·파일 업로드·지원서 제출은 하지 않았다. 프리셋 원본 ID와 savedUrl은 모두 null이며 운영 행 변경·배포는 없다.
- 관련 모의 테스트 42개 통과. 변경 실행 코드/화면 lint 통과. 전체 TypeScript 최종 검사는 이번 변경과 무관한 `career/simulation/server.ts:550`의 url/markdown 타입 오류 2건과 별도 수정 중인 `applicationManagedBrowser.ts`의 managed undefined 타입 오류 4건으로 실패했다. 변경 파일 자체의 타입 오류는 없었다.
