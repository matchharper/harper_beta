# External opportunity value 실험 결과 — 2026-09-12

## 결론

새 `roleFit + candidateFit + slate selector`는 동일 30개 후보에서 현재 방식과 실질적으로 다른 slate를 만들면서도 구조와 비용 조건을 충족했다. 따라서 **human blind review를 진행할 근거는 확보했다.** 아직 새 방식이 더 좋은 추천을 만든다고 결론 내릴 수 없으며 production 교체·rollout 근거도 아니다.

후속 selector architecture development에서 이 run의 `candidateFit=fit` hard gate는 current보다 나쁜 결과를 보여 폐기했다. 최신 설계 결정은 [2026-09-13 결과](RESULTS-2026-09-13.md)를 따른다. 이 문서는 첫 E1의 관찰값과 당시 결론 경계를 보존한다.

모델 판단의 품질 승패는 48-case blind slate review와 독립 12-case candidate recall audit이 끝난 뒤에만 낸다.

## 격리와 데이터

- Production module, Worker 설정, DB schema, 추천·fit·discovery·message row를 변경하지 않았다.
- Capture만 canonical read-only DB connection을 썼고 liveness도 `persist_expired=false`로 실행했다.
- Model run은 동결된 local fixture만 읽었다.
- Raw Profile, Brief, Behavior Context, role/company card, ID와 model output은 ignored owner-only `private/`·`runs/`에만 있다.
- `selection-random-v1`은 48명 × 30 roles이며 `pilot-v1` 6명과 talent 중복이 없다.
- 캡처 과정에서 30개 후보를 만들지 못한 non-pilot talent 32명을 제외했다. 따라서 결과는 current retrieval에서 최소 30개를 확보하는 population에 한정된다.
- 48명 중 23명은 rank 1–15 / 16–100 / 101–200을 15/10/5로 구성했다. 24명은 pool이 100개 이하라 15/15/0, 1명은 15/12/3이었다.

## Serving reliability와 비용 해석

최초 E1 프로세스는 40/48 case 뒤 SSL response read에서 약 2시간 47분 정체됐다. SDK의 read timeout은 응답이 조금씩 들어오는 상황에서 전체 wall-clock 경계가 되지 않았다. 40-case checkpoint를 보존하고 프로세스를 종료한 뒤, 완료 case를 건너뛰는 resume와 call별 child-process 180초 hard timeout을 구현해 48/48을 완주했다.

Control 경로 대조 중 C035의 rerank pool 3개가 2개 회사뿐인데 evaluation runner가 target 3을 요청한 차이를 발견했다. Production과 같은 distinct-company target 2로 해당 control selector만 재실행하고 이전 selector·수정 이유·추가 비용 $0.001177을 private correction trail에 보존했다. 선택은 전후 모두 empty여서 slate 차이 지표는 변하지 않았다.

최종 p50/p95 call latency는 33.653초 / 59.555초다. Resume 뒤 저장된 hard-timeout call은 0이지만, 강제 종료 시점의 in-flight 호출이 나중에 청구됐는지는 결과 파일에서 복원할 수 없다. 따라서 $1.530668은 lower bound다. 이미 비용이 확인된 incomplete/corrected-away case 호출 $0.159009는 총액에 포함했으나 어느 arm의 최종 case 결과에도 귀속하지 않았다.

당시 runner는 provider generation ID를 저장하지 않아 종료된 in-flight 요청의 사후 비용을 개별 조회할 수 없었다. 이후 eval 공용 response record에 `responseId`를 추가했으므로 새 run은 provider generation 단위 감사를 할 수 있다.

이 reliability 문제는 selector 품질과 별개다. Human quality가 통과하더라도 production shadow 전에 wall-clock timeout, idempotent retry, stage checkpoint와 provider tail latency를 운영 조건으로 검증해야 한다.

## 남은 human gold와 결정 규칙

Local-only review artifact는 다음을 포함한다.

- 48개 전체 A/B slate: arm, model rationale, score를 숨기고 3명이 독립 검토
- model output과 무관한 stable-hash 12개 case × 30 roles: 2명이 독립 label 후 adjudication
- candidate gold: `send_now | reserve | do_not_send | insufficient_context`, blocking issue, omission regret
- scorer: majority slate preference, one-sided exact sign test, 12-case micro-recall, critical blocking selection을 계산

Slate vote를 먼저 동결한 뒤 candidate audit을 진행한다. Scorer는 dataset/run 일치, 세 slate vote, 두 candidate reviewer label, adjudication, gold version과 review history가 모두 없으면 실행을 거부한다.

다음 조건을 모두 만족해야 `pass_for_shadow_prototype`이다.

1. Non-tie case 36개 이상
2. Treatment win rate 60% 이상이며 one-sided exact sign-test `p < 0.05`
3. Treatment critical blocking selection 0
4. 12-case candidate-audit micro-recall이 control보다 낮지 않음
5. 구조 gate 통과
6. Treatment/control attributed 비용 비율 1.25 이하

통과하더라도 다음 액션은 production 교체가 아니라 evaluator/selector shadow trace다. 실패하거나 inconclusive면 retrieval을 함께 바꾸기 전에 어느 label·case에서 문제가 났는지 먼저 분석한다.
