# Career conversation versions

Targeted local verification of the professional default and friendly dev selection. This is independent of the earlier A/B/C guidance experiment: both versions keep C's execution contract. This change is not deployed.

The evaluation unit is one complete text reply from the production `buildCareerConversationPromptPlan` → `runCareerChatAssistant` path. Frozen synthetic v1 inputs and review criteria are in `cases-v1.json`; no real candidate data is used. The canonical runner is `scripts/evalCareerConversationVersion.ts`. Run with `pnpm exec tsx --tsconfig scripts/tsconfig.json scripts/evalCareerConversationVersion.ts`. It uses the current default Career model/options, records source hashes, exact provider request bodies, system blocks, outputs and model configuration in owner-only ignored `runs/`. Network is restricted to model endpoints; tools have no external effects. One trial per case per version is a smoke check, not a broad benchmark.

Review both versions for faithful facts and useful responses. For friendly, check compact conversational 해요체, natural rather than mandatory punctuation, no unsolicited accounting of irrelevant actions not taken, and appropriate sensitivity. Prefer bubble splitting when the thought or conversational purpose shifts, keeping related content together; do not force counts or score tone with regexes. Any invented action, omitted material failure, or exposed delimiter in the rendered product blocks handoff. Browser rendering is separately checked using the real message component with synthetic content, partial streaming, version changes and choices.

Scope: ordinary Career text chat, including continuation of the same saved user turn. Onboarding, voice, scheduled email tone, and external-recipient writing retain their own contracts. Selection is browser-local and server-authorized via existing dev controls access. The root evaluation README is absent in both the existing checkout and HEAD; it is not restored as part of this task.

## 2026-11-04 semantic bubble boundaries and handbook expiry

The friendly display contract now directs separate bubbles at distinct thoughts or conversational moves, keeping related content together. The behavioral direction and existing rendering/marker constraints occupy two sentences. This adapts [NN/g's meaningful content grouping](https://www.nngroup.com/articles/chunking/) and [OpenDialog's separation of informational messages and actionable questions](https://docs.opendialog.ai/opendialog-platform/conversation-designer/message-design/message-types/text-message); it does not adopt character limits, fixed bubble counts or sentence-based splitting.

`cases-bubbles-v1.json` freezes two synthetic multi-turn cases, their execution facts and qualitative review criteria: a revision/status/next-step reply and a casual closing after paused work.
