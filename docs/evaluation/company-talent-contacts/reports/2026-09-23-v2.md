# 통합 회사–후보자 연락: 수정 및 5개 시나리오 재검증

문서 기준: 2026-09-23. 로컬 구현·격리 환경 검증이며 배포 결과가 아니다.

## 결론

새 fixture로 다시 실행한 다섯 시나리오에서 기대한 행동을 모두 확인했다. 후보자 연락 6건은 전부 `requestId=null`로 같은 도구 호출 안에서 회사 대화에 전달됐고, 회사 agent 후속 작업 6건이 완료됐다. 추가적인 역할 정정이나 초안 수정 지시는 필요하지 않았다. 회사 연락의 초안·승인 절차는 유지하지만, 후보자 연락은 발송 worker를 기다리는 흐름에서 제거했다.

첫 v2 회차에서 발견한 회사 연락 초안 품질 문제는 수정 후 재검증했다. 최종 회차에는 다른 시나리오의 동시 상태 변경을 오인한 테스트 장치 실패 한 건이 있었으며, 실제 연락은 성공했다. 아래에 원본 기록과 별도로 설명한다. 따라서 이 결과는 모든 CLI 실행이 오류 없이 끝났다는 의미가 아니라, 원문·도구 결과·최종 DB 상태를 대조한 다섯 행동 시나리오의 통과다.

## 근본 원인과 변경

- 후보자 도구의 `requestId`는 원래 선택 항목이었다. 모델이 생략하는 것은 계약 위반이 아닌데, 기존 미답변 질문 reader는 그 ID로 갱신하는 답변 필드를 요구했다. 정상 전달 뒤에도 옛 질문이 남는 서로 모순된 계약이었다.
- 후보자 계약은 `contact_company(connectionId, relayContent, documentId?)`로 정리했다. `connectionId`는 전달 대상과 권한을 확인하고, 원본 메시지 ID는 서버가 중복 방지에 사용한다. 후보자 모델이 과거 질문 ID나 질문 종류를 추론할 필요가 없다.
- `requestId`는 특정 회사 초안 수정·승인·발송, 서명된 파일 업로드 링크, 실제 이메일 reply alias의 출처를 식별할 때만 내부적으로 유지한다. 자유로운 연락 의미를 분류하는 필수 값으로 사용하지 않는다.
- 의미 판단은 회사 전달 후 기존 company agent가 한다. 앞선 회사 지시, 최근 양방향 연락, 현재 역할·후보자 상태를 보고 위임된 작업만 실행한다. 부분 답변·조건부 의향·거절을 별도 enum이나 classifier로 바꾸지 않는다. 최신 후보자 연락과 충돌하는 오래된 동의 증거는 재개에 사용할 수 없다.
- 후보자 연락은 저장 직후 공유 전달 서비스를 기다려 완료한다. 이메일 Worker도 같은 서비스를 즉시 호출한다. 회사 대화 기록과 후속 job 생성은 DB에서 함께 완료한다. 내부 outbox는 장애 재시도용으로만 남으며 후보자-facing 발송 대기 절차가 아니다. 전달문 재작성 전용 LLM도 제거했다.
- 단일 미답변 질문 대신 확인된 회사 연결과 최근 연락을 Career 기본 context로 제공한다. 회사명+역할명 복합 검색과 일정 없는 단계 이동의 불필요한 소개 이메일/CC 요구도 수정했다.
- 정상 연락을 “전달했습니다”라고 표현하는 것은 허용한다. 내부 queue 상태만으로 이를 품질 결함으로 세던 기준을 제거하고 workspace 지침에 남겼다. 회사가 읽었거나 채용 결정을 했다고 임의로 주장하는 것은 별개다.

## 실행 근거와 한계

- 최종 run: `runs/2026-09-23-immediate-v2-final/`. 실제 provider 요청 45회. 회사 모델 `gpt-5.6-terra`, 후보자·연락문 모델 `claude-sonnet-5`; runtime 설정을 사용하고 정확한 설정과 입력 hash는 호출별 비공개 기록에 보존했다. 한 company agent turn의 도구 loop는 provider 요청 여러 번을 포함할 수 있다.
- 지정된 두 fixture 계정과 Harper workspace의 최소 정보만 읽기 전용으로 복제했다. 실제 제품 도구 실행부, PostgreSQL 함수·제약·trigger를 사용했다. 회사→후보자 이메일은 로컬 transport capture이며 실제 메일함 도착이 아니다. 후보자→회사 웹 대화는 실제 격리 DB에 저장됐다.
- 후보자 연락 6건, 후속 job 6건. 종료된 질문의 stale reminder 0, fixture fit 0, 미팅 0. 후보자 연락 도구 자체가 채용 단계를 바꾸지 않으며 필요한 단계 변경은 이후 회사 agent가 수행했다.
- UCT01 완료 이벤트 재실행: 추가 LLM 호출 0, progress·relay·queue·회사 메시지 수 변화 0. UCT03 전달 재실행: job 6개, 회사 메시지 33개로 동일하여 중복 생성 없음.
- 최종 회사 메시지 33개, 후보자 메시지 17개, progress 15개. 원문과 도구 결과를 대조했고, UCT03 비공개 보상 내용이 모든 회사 측 model input과 전달문에 없는 것을 확인했다.
- 변경 관련 웹 단위 테스트 109개, 이메일 Worker 단위 테스트 167개, PGlite 연락·권한·동의·재시도 계약 검증 통과. PGlite 검증에서 기존 단계 변경 함수는 stub이며, 실제 단계 변경은 위 PostgreSQL 시나리오로 별도 확인했다.
- 실제 Slack·이메일 수신, Supabase Auth, 브라우저 렌더링, Storage 파일 업로드, 운영 queue 소비는 검증하지 않았다. 파일 공유 권한과 업로드 재시도 계약은 DB/단위 검증 범위다. 회사 job은 실제 durable job을 로컬에서 직접 소비했다. 로컬 vector 확장이 없어 예시 검색은 fail-open이었다.
- 전체 TypeScript 검사는 기존 Next 생성 캐시의 누락 페이지 참조 및 `growthTalentGtmReport.test.ts` 오류로 미통과다. 연락 테스트 전체 glob의 기존 5개 테스트는 삭제된 역사적 migration 파일 참조로 실패한다. 이번 변경에 대한 표적 검증과 구분한다.
- 다섯 사례는 회귀·도전 사례이지 전체 서비스의 성공률 추정이 아니다. 최종 회차 도중 오래된 queued 안내 prompt를 정리했고 마지막 UCT03 답장에 반영됐다. 호출별 실제 prompt hash를 남겼으며 전체 45회를 하나의 동일 prompt snapshot 비교 실험으로 주장하지 않는다.

## 실패 기록과 평가 장치 정정

1. 첫 v2 run(`2026-09-23-immediate-v2`)의 UCT05에서 연락문 생성 모델이 빈 필드, 다음 시도에서는 불완전한 예시 문자열을 반환했다. 상위 회사 agent에 실제 생성 본문을 주지 않아 이를 검토하지 못했다. 필수 필드의 구조 검증을 provider fallback 안으로 옮기고, 전체 발송문 생성 계약을 명확히 했다. 생성·수정 도구가 실제 제목·본문을 회사 agent에 반환하도록 변경해 기존 agent가 검토할 수 있게 했다. 특정 문자열 감지나 별도 검수 LLM은 추가하지 않았다. 최초 실패와 사용자의 수정 요청을 흉내 낸 후속 입력 기록을 보존했고, 최종 새 fixture 회차에서는 첫 초안부터 완료됐다.
2. 최종 UCT03 재답장과 다른 사례의 회사 후속 처리가 겹쳤다. 테스트 장치가 전체 pipeline의 전후 상태를 비교해 UCT01/02의 정상 단계 이동을 후보자 도구의 변경으로 오인했다. 원본 오류를 보존하고 비교를 현재 시나리오의 정확한 recommendation으로 한정했다. 이미 성공한 후보자 연락은 중복 발송하지 않았다. 별도 최종 `verify`에서 UCT03 초기/최종 상태와 여섯 연락·job, 다섯 사례의 기대 상태를 확인했다.
3. audit writer가 과거 v1 dataset 이름·hash를 고정 사용한 메타데이터 오류를 마지막에 발견했다. setup manifest와 실행 사례는 처음부터 v2였다. 원래 `llm-manifest.json`은 덮어쓰지 않고 각 v2 run에 `manifest-correction.json`을 추가했다. 호출 원문·hash·횟수는 변경하지 않았다. runner의 이후 출력도 v2로 수정했다.

## 정리

모든 역할은 생성 전 `testOnly=true`, 고정 `testFixture`, 전용 계정 allowlist를 가졌다. 두 v2 run의 fixture를 정확한 ID로 제거했고, 각 run의 잔존 역할·fit·queue는 0이다. 최종 run에서 제거한 역할은 6개이며 원문 검증 기록은 owner-only·gitignored 파일로 보존했다. 격리 DB와 로컬 REST 서버를 정상 종료했다. 운영 데이터 쓰기·실제 외부 수신함 발송·배포·운영 재시작·Notion 수정은 하지 않았다.
