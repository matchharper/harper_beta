# 통합 회사–후보자 연락 시나리오 검증

> 과거 v1 실행 기록이다. 수정 후 결과는 [v2 재검증](2026-09-23-v2.md)을 따른다. 아래의 발송 대기/완료 표현 비판은 사용자가 정한 정책과 달랐던 평가 오류이며 철회한다. 실제 실패와 원본 판정의 추적을 위해 본문은 보존한다.

## 결론

요청한 통합 연락 구조의 기본 경로는 실행되지만, 전체 완료 기준은 **미통과**다. 역할 선택 후 이동은 성공했고, 자발 연락의 후속 무동작도 확인했다. 그러나 종료된 진행의 자동 재개가 막히며, 여러 역할이 연결된 상황의 대상 선택과 기존 질문 상태에 문제가 남아 있다. 실제 모델 응답의 발송 완료 표현도 수정이 필요하다.

| 시나리오 | 관찰 결과 | 판정 |
| --- | --- | --- |
| UCT01: 두 역할 중 선택하고, 일정은 나중에 논의 | 후보자의 자유형식 연락을 받은 회사 agent가 현재 역할들을 조회하고 Customer Success의 대화 단계로 이동. Product Operations는 종료·아카이브. 미팅 없음. 같은 이벤트 재실행에도 추가 변경 없음. | 핵심 동작 성공. 발송 안내 표현은 별도 결함. |
| UCT02: 종료된 Backend Engineer 진행을 후보자 동의 후 재개 | 후보자 동의 전달과 회사 agent 호출은 성공. 정확한 동의 연락 ID를 넣어 단계 변경을 시도했지만 소개 이메일 CC 주소 요구에 막힘. 직접 연락 방식 요청과 재확인에도 추가 확인이 반복됐으며 최종 상태는 종료 유지. | 실패 |
| UCT03: 후보자가 먼저 재논의 시점을 제안하고, 비공개 정보는 제외 | 첫 연락은 이전 역할에 등록. 역할 정정 후 복합 검색이 기존 연결을 누락. 두 차례 정정 뒤 올바른 역할로 전달했고, 회사 답장 및 후보자 재답장까지 성공. 회사 agent는 두 연락 모두 무동작 종료. 비공개 정보는 회사 전달문·회사 모델 입력에 없음. | 복구 후 왕복 동작 성공, 최초 경험은 미통과 |

위 판정은 기능 결과와 대화 품질을 분리한 것이다. 기능 성공을 전체 E2E 통과로 집계하지 않았다.

## 확인한 실행 경로

회사 연락은 `contact_talent`, 후보자 연락은 `contact_company`를 사용했다. 선택 결과나 재개 의향을 positive/negative 필드로 전달하지 않았다. 후보자 연락을 전달 완료로 처리하기 전에는 단계 변화도 회사 후속 job도 없었다. 전달 완료 후 실제 DB trigger가 회사 후속 job을 만들었고 기존 `runOrgAgentWebActionTurn`을 실행했다. 이는 별도 분류 모델이 아닌 기존 company-side LLM의 tool loop다. 한 agent turn 안에서 도구 사용에 따른 여러 provider 요청은 발생할 수 있다.

UCT01에서는 후보자가 `requestId`를 생략해도 회사 agent가 이전 회사 지시와 새 연락을 읽고 다른 역할로 옮겼다. 따라서 질문 유형이나 긍정/부정 분류 없이도 역할 선택 자체는 처리할 수 있었다.

UCT03의 정상화된 연락에서는 기존 회사 질문 없이 `requestId=null`로 전달했다. 회사의 답장은 동일한 `contact_talent`의 직접 답장 경로로 등록됐으며, 후보자의 후속 답장도 같은 `contact_company`를 사용했다. 첫 후보자 연락과 마지막 답장 모두 회사 후속 결과는 `completed_silent`였다. 새 미팅, 종료, 단계 이동, 불필요한 자동 답장은 없었다.

## 수정이 필요한 원인

### 1. 재개 단계 변경이 소개 이메일 요구와 묶여 있음

`src/lib/org/agent/toolExecution.ts`의 `move_candidate_stage` 실행 경로는 일정 없는 이동에서 `skipAutomaticContact`를 현재 단계가 `pending_connection`일 때만 켠다. `process_stopped`에서 사용자 정의 단계로 이동할 때는 켜지지 않는다.

그 결과 `src/lib/org/server.ts`의 `setOrgCandidateStage`가 후보자 동의 확인 RPC에 도달하기 전에 소개 이메일 CC 수신자를 요구한다. 이는 일정 요청 없이 단계만 변경한다는 도구 설명과도 맞지 않는다. 회사가 조건부 이동을 이미 위임했고 후보자가 동의했는데도 새 연결 의사결정과 확인 질문으로 되돌아갔다.

### 2. 선택적 `requestId`와 기존 답변 대기 판정이 충돌

UCT01 연락은 정상 전달·역할 이동까지 완료됐지만 회사 질문의 `talent_source_message_id`는 비어 있었다. `create_company_talent_relay_v2`는 `p_request_id`가 있을 때만 기존 질문의 답변 필드를 갱신한다.

반면 `companyRequestStillActive(..., awaitingTalentOnly=true)`는 여전히 그 필드와 문서 존재 여부로 답변 유무를 판단한다. 최종 조회에서도 이미 처리한 Product Operations 질문이 답변 대기 질문으로 반환됐고, Career 기본 context에 주입됐다. UCT03에서 과거 역할 질문을 다시 꺼내고 그 연결로 먼저 전달 등록한 현상과 일치한다. 여러 연결 중 첫 요청의 역할이 명시되지 않았다는 모호함도 있었으므로, 잘못된 연결 선택의 단독 원인이라고 단정하지는 않는다.

새로운 시나리오별 분기를 추가하기보다 일반 연락 이력 reader와 기존 답변 대기 context 계약을 정리할 필요가 있다.

### 3. 회사명과 역할명을 함께 검색하면 연결을 누락

`fetchRelayableCompanyTalentConnections`는 query 전체 문자열이 회사명 또는 역할명 한 필드에 포함돼야 반환한다. 모델이 두 이름을 함께 넣으면 양쪽 어느 필드에도 전체 문자열이 없어 결과가 비었다. 같은 연결은 역할명만 검색했을 때 바로 나왔다.

모델은 빈 검색 결과를 관계가 없다는 단정으로 확대했다. 검색 필터/도구 계약과, 부분 검색 결과로 부재를 단정하지 않는 context·prompt 개선이 필요하다.

### 4. 발송 대기와 전달 완료 표현 불일치

일부 회사·후보자 응답은 도구 결과가 `queued`인데 이미 전달을 마쳤다고 설명했다. 이후 문장에서 아직 전송 중이라고 덧붙인 경우도 있었다. 모델의 발송 상태 표현이 일관되지 않아 품질 기준을 통과하지 못한다. 표현을 키워드로 덮어쓰는 방식이 아니라 도구 결과와 prompt 계약을 개선해야 한다.

## 검증 범위와 근거

- 최종 판정 run: `runs/2026-09-23-canonical-fixture/` (비공개, gitignored).
- 고정 사례·정답: `cases-v1.json`, `gold-v1.json`. 기대 결과를 실패 후 바꾸지 않았다.
- 실제 모델: 회사 `gpt-5.6-terra`, reasoning `xhigh`; Career `claude-sonnet-5`, effort `medium`; 연락문 생성도 현재 런타임 기본 모델 사용. 이 run의 기록된 provider 요청은 42회이며 설정·요청 hash는 `llm-manifest.json`에 있다.
- 실제 제품 함수와 PostgreSQL 17.6의 제약·함수·trigger를 사용했다. DB 변경이나 도구 성공을 가짜 결과로 대체하지 않았다.
- 최종 DB 스냅샷·원문 대화·도구 결과는 `final-audit.json`, turn별 `*-result.json`·`*-llm.json`에 보존했다. 관련 runtime source snapshot도 비공개로 보존했다.
- UCT01 완료 이벤트 재실행: 추가 모델 요청 0, progress·연락·queue·회사 메시지 수 변화 0.
- UCT03 두 전달 완료 RPC 재실행: 회사 job 4개 및 회사 메시지 24개로 동일, 추가 생성 0.
- 전체 미팅 0, fixture fit 0. UCT03 비공개 보상 정보는 전달문과 회사 모델의 대화 입력에 없음을 확인했다. 도구 JSON schema의 숫자 제한 값은 비공개 정보 노출로 세지 않았다.
- 초기 두 setup run은 단계 tag 형식 및 opportunity type fixture 오류가 있어 판정에서 제외하고 원본을 보존했다. 마지막 run 전에 회사 보드 노출과 양 후보자의 전달 가능한 연결을 실제 reader로 검증했다.

## 한계와 정리

운영 스키마에는 새 contact migration과 선행 회사 후속 job 테이블이 아직 없어 운영 end-to-end 검증이 아니다. 운영 접근은 읽기 전용이며, 최소 승인 계정·내부 workspace 정보만 격리 DB에 복제했다. 운영 DB 변경, 실제 사용자 메일·Slack 발송, 배포, production 재시작은 하지 않았다.

실제 이메일/Slack transport와 인증은 로컬 adapter를 사용했다. 전송 완료는 격리 환경에서 기록했으므로 실제 메일함 도착·Slack 표시·브라우저 렌더링·운영 queue 스케줄러까지 검증했다고 볼 수 없다. 복제 DB의 vector 검색은 사용할 수 없어 서비스 답변 예시 검색이 fail-open으로 진행됐다. 이에 따라 provider가 생성한 문구는 운영에서 같은 답변이 재현된다는 보장이 없다.

Supabase 및 테스트 격리 지침에 따라 모든 테스트 역할은 생성 시 `testOnly`, 고정 `testFixture`, 정확한 fixture 계정 allowlist를 가졌다. 종료 시 역할 4개와 관련 추천·연락·메시지 등을 로컬 DB에서 제거했고 역할·fit·queue 잔존 수가 각각 0임을 확인했다. 격리 DB·REST 서버도 종료했다. 원본 평가 기록은 비공개 파일로 남아 재현 근거로 사용할 수 있다.

이번 테스트 요청에서는 제품 동작 코드를 수정하지 않았다. 새 평가 runner의 lint와 sandbox syntax 검사는 통과했다. 전체 typecheck는 기존 생성된 Next type의 누락 페이지 참조와 기존 growth report 테스트 타입 오류로 미통과이며, 새 runner 타입 오류는 수정 후 재검사에서 없어졌다.
