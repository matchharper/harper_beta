# 좋은 후보를 먼저 평가하기 위한 순위 비교 — 2026-10-08

비용을 고려한 후속 도입 후보는 **SQL 순위와 가중 FTS 순위를 RRF로 합치는 방식**이다. 기존 미검토자 제외·갱신 예산·5% 넓은 탐색은 유지한다. 이번 다섯 역할의 별도 모델 표본 판단에서 평균 21.5% → 31.0%로 개선됐다. 임베딩까지 합치면 37.0%지만 초기 색인·저장·갱신과 API 비용이 추가된다. 다만 Wonderful의 첫 실행에서 과거 긍정 후보 발견이 감소했으므로, 사전 정의한 기본 정렬 전환 조건은 충족하지 못했다. 아래의 기본안은 후속 개발 후보를 뜻하며 운영 전환을 승인한 결과가 아니다.

이번 요청에서는 평가 runner·고정 입력·결과 문서를 구현했다. 실제 매칭의 기본 정렬은 아직 SQL이며, FTS/혼합 정렬 도입·운영 DB 변경·배포·연락은 실행하지 않았다.

## 어떻게 평가했나

- 같은 2026-10-07 격리 스냅샷의 온보딩 완료·내부 추천 허용 모집단 4,649명. 회사 차단 후 역할별 4,646~4,649명.
- 기존 v1 입력·gold를 보존하고 v2로 역할을 다섯 개로 확장했다. 새 역할은 localhost에서만 paused/testOnly fixture로 복제했고, JD·Hiring Brief·criteria 원문을 유지했다.
- 역할마다 SQL과 가중 검색어 계획을 각각 두 번 실제 configured planner로 생성했다. 검색 모델에는 후보자·과거 결과·gold를 넣지 않았다. 두 방식의 계획은 별도 호출이며, 한 호출로 합친 운영 prompt는 이번에 검증하지 않았다.
- 9가지 최초 방식과 2가지 후속 방식을 비교했다. 모든 방식은 미검토 원장을 인원 제한 전에 반영하고, 회당 100슬롯·6회 재생·5% 넓은 탐색을 유지했다. 고정 계획의 원장 재생이며 실제 6회 검색·fit·추천 실행은 아니다.
- 각 방식·역할·검색 계획의 첫 100명에서 hash로 20명을 고정 추출했다. Profile 전체와 전체 Brief를 읽는 GPT-6 Luna high/0.1에게 방식·순위·과거 결과·gold를 숨기고 “전체 fit 평가 비용을 쓸 가치가 있는가”를 물었다. Behavior는 모든 방법에서 제외했다.
- 표본에 겹치는 사람은 같은 역할에서 판정을 재사용했다. 최종 581개 서로 다른 역할×후보자 쌍을 검토했고 구조/coverage 오류는 0건이다. 아래 40개 표본 멤버십에는 두 계획 사이의 중복이 있을 수 있다.

## 첫 목록의 품질 — 별도 모델의 silver 판단

아래 비율은 실제 회사 긍정률·fit 통과율·추천 수락률이 아니다. 두 계획에서 각각 20명을 평가한 비율의 평균이며 다섯 역할의 가중치는 같다.

| 역할 | 현재 SQL | SQL + 가중 FTS 순위 결합 | SQL + FTS + 임베딩 결합 |
| --- | ---: | ---: | ---: |
| Wonderful 한국 FDE | 37.5% | 47.5% | 37.5% |
| SBVA 투자 | 30.0% | 27.5% | 52.5% |
| Sierra Agent Engineer | 12.5% | 25.0% | 20.0% |
| Config Robotics Systems Engineer | 12.5% | 40.0% | 60.0% |
| SBVA 커뮤니케이션 | 15.0% | 15.0% | 15.0% |
| 평균 | 21.5% | **31.0%** | **37.0%** |

기본안의 개선은 두 계획에서 각각 +11.0%p, +8.0%p였다. SBVA 투자에서는 평균 30.0% → 27.5%로 작은 감소가 있어 모든 역할의 개별 우월을 주장하지 않는다. 후보자/역할을 함께 재추출한 silver 표본의 개선 구간은 약 +3.0~15.9%p다. 이는 표본 불확실성만 다루며 모델 오판·두 번의 검색 계획 변동·역사적 gold 편향을 포함하지 않는다.

| 비교 방식 | 다섯 역할 평균 |
| --- | ---: |
| 현재 SQL 순위 | 21.5% |
| 전체 모집단 가중 FTS | 36.0% |
| SQL 범위 안 가중 FTS | 37.0% |
| SQL 범위 안 FTS + 문서 길이 정규화 | 29.5% |
| SQL 범위 안 FTS + 영어 어간·길이 정규화 | 27.5% |
| SQL 범위 안 임베딩 순위 | 37.5% |
| SQL + 가중 FTS 순위 결합 | 31.0% |
| SQL + 정규화 FTS + 임베딩 순위 결합 | 37.0% |
| SQL 80 + 전체 FTS 15 + 탐색 5 | 25.5% |
| SQL + 길이 정규화 FTS 순위 결합 | 28.0% |
| SQL 50 + 정규화 FTS 45 + 탐색 5 | 25.5% |

FTS/임베딩만으로 정렬하면 일부 직군에서 큰 이득이 있지만 커뮤니케이션 역할은 악화됐다. SQL의 우선순위를 함께 쓰는 기본안은 커뮤니케이션 표본 비율을 보존했고, 임베딩을 사용하는 결합안은 다섯 역할에서 SQL 이상의 평균 비율이었다. 후속 길이 정규화/RRF와 50:45 예산 실험은 각각 28.0%/25.5%로 최초 기본안보다 낮았다. 회사·직무별 예외 분기나 keyword 출력 후처리는 추가하지 않았다.

## 과거 회사 긍정 후보를 얼마나 빨리 발견했나

확인된 gold는 Wonderful 13명, SBVA 투자 4명이다. 나머지 세 역할의 연결 대기·공유 완료·아카이브는 회사 긍정으로 해석하지 않았다. 아래는 두 계획을 각각 표시한 발견 인원이다.

| 역할·방식 | 첫 100명: 계획 1 / 계획 2 | 3회: 계획 1 / 계획 2 | 6회: 계획 1 / 계획 2 |
| --- | ---: | ---: | ---: |
| Wonderful 한국 FDE · 현재 SQL 순위 | 4 / 0 | 4 / 0 | 4 / 0 |
| Wonderful 한국 FDE · SQL + 가중 FTS 순위 결합 | 0 / 0 | 4 / 0 | 5 / 1 |
| Wonderful 한국 FDE · SQL + 정규화 FTS + 임베딩 순위 결합 | 0 / 0 | 4 / 0 | 5 / 1 |
| SBVA 투자 · 현재 SQL 순위 | 0 / 3 | 0 / 4 | 0 / 4 |
| SBVA 투자 · SQL + 가중 FTS 순위 결합 | 1 / 2 | 3 / 4 | 3 / 4 |
| SBVA 투자 · SQL + 정규화 FTS + 임베딩 순위 결합 | 1 / 2 | 3 / 4 | 4 / 4 |

**첫 발견의 손해도 있다.** 정상 SQL인 Wonderful 계획 1은 첫 100명에 gold 4명이 있었지만 기본안은 0명이었고, 3회에 4명·6회에 5명이 됐다. 누적 발견이 좋아졌다는 것으로 첫 실행의 역사적 positive recall 개선을 주장하지 않는다. 실제 첫 추천을 중시하는 신규 역할의 독립 검토가 남아 있다. 모든 방식은 6회에 서로 다른 600명, 반복 평가 슬롯 0이었다.

## SQL 오류와 변동성

10개 SQL 생성 중 SBVA 투자 계획 2는 UNION의 NULL/timestamptz 타입 불일치로 1회 수정됐고, Wonderful 계획 2는 추정 실행 비용 상한을 넘어서 수정 뒤에도 fallback했다. 이를 제외하거나 0명의 적합자가 있는 결과로 숨기지 않았다. fallback은 일반 모집단 순위이며 동일 SQL 범위 비교는 그 실제 결과를 사용했다.

Wonderful fallback 계획을 제외하고 정상 계획만 남긴 역할별 평균으로 다시 계산해도 기본안의 평균은 SQL 22.0% → 30.5%였다. 따라서 전체 개선을 fallback 하나만으로 설명하지는 못하지만, SQL 생성 안정성과 원문 타입 설명은 별도의 개선 과제로 남는다. 계획 1의 Wonderful 첫 100명 gold 손실도 그대로 남는다.

## 비용·시간과 구현 판단

- 이번 기록의 검색 계획/SQL 모델 비용은 약 $0.0414, 581쌍 silver 검토의 추가 비용 합계는 약 $0.2950이다. 기존 후보자 embedding 생성 비용과 이번 검색문 embedding 비용은 이 합계에 포함하지 않는다. API usage 기반 추정이며 청구서 총액이 아니다.
- 실제 SQL planner 시간은 약 50.8~176.3초였다. 현재 평가의 가중 검색어 계획은 SQL과 별도 호출이어서 모델 비용·대기 시간이 추가된다. 운영에서는 기존 검색 계획 호출의 출력 확장이 필요하고, 합친 prompt도 새 run으로 검증해야 한다.
- 임베딩/FTS/순위 결합을 모두 계산한 비교는 역할·계획당 약 2.1~4.7초였다. 후보자 벡터는 기존 frozen cache를 재사용했으며 TEMP FTS 문서 초기 구축 시간은 이 수치 밖이다. 운영 색인 갱신·네트워크·전체 Worker latency를 측정한 값이 아니다.
- 기본안은 SQL의 역할 관련 범위 안에서 Profile와 Brief의 가중 FTS 순위를 만들고 SQL 순위와 RRF k=60으로 합친다. 미검토 제외, 신규/갱신 예산, 기존 fit 전체 합류는 유지한다. 이번에는 원문 Profile/Brief를 TEMP tsvector로 만들었고 운영 FTS 컬럼·index는 추가하지 않았다.
- 검색 순위는 fit이 아니다. 회사/후보자 수준·보상·현재 관심·명시적 조건을 읽는 공통 1/2차를 그대로 거친다. 추천 방향과 전달 판단도 이번 실험에서 바꾸지 않았다.

## 재현과 한계

- Canonical runner: `harper_worker/llm_evals/role_scoring_list_retrieval/ranking_eval.py`, `ranking_followup.py`, `ranking_summary.py`. 실제 외부 검색의 `fts_query_parts`와 현재 query planner/SQL executor, 기존 원장 merge를 재사용했다.
- V2 fixed inputs/gold: `gold-v2.json`, `manifest-v2.json`, ignored `private/v2`. 모든 private 파일은 0600이며 v1 gold의 SHA256은 이전과 동일하다.
- 실행: `20261008-ranking-v2-plans-r1`, `compare-r1/r2`, `quality-r1/r2/r3`, `followup-r1`, `summary-r2/r3`. Raw source/SQL/model output/후보자 UUID는 ignored runs/private에만 있다.
- 관련 21개 검증은 실제 격리 PostgreSQL의 평가 원장·embedding 경계와 external FTS 회귀·검색 범위/중복 방지를 포함해 통과했다. source fixture의 fit/추천/발송은 0이며 운영 DB·원본 역할·queue·서비스를 바꾸지 않았다.
- 과거 노출된 사람만 회사 결과가 있어 gold는 편향돼 있다. 현재 프로필이 과거 인터뷰 때와 달라졌을 수 있다. 나머지 세 역할은 human gold가 없고 모든 quality 판정은 하나의 별도 모델 silver다. 8명씩 묶은 판정의 맥락 영향과 기존 판정 재사용도 불확실성이다.
- 두 후속 방식은 최초 결과를 본 뒤 정한 development 실험이다. Gold를 바꾸거나 역할별로 결과가 좋은 방식을 따로 선택하지 않았다. 실제 생산 시스템의 일반 precision/반응률 또는 모든 역할에서의 우월을 확정하지 않는다.

FTS와 순위 결합의 동작은 [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/textsearch-controls.html)와 [Supabase hybrid search 문서](https://supabase.com/docs/guides/ai/hybrid-search)를 확인했다. 측정 숫자의 근거는 위 frozen 입력과 실제 실행 산출물이다.
