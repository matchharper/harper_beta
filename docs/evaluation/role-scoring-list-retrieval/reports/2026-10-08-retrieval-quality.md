# Scoring list 품질 평가 — 2026-10-08

이번 자료에서 가장 확실한 개선은 **같은 사람을 반복해서 가져오지 않고, 아직 이 역할의 fit을 평가하지 않은 사람을 인원 제한 전에 확보하는 것**이다. 역할 관련 검색으로 모집단을 만든 뒤 그 범위 안에서 벡터로 순서를 정하는 방식도 누적 발견을 개선했다. 전체 후보에게 JD 벡터 검색부터 적용하는 방식은 Wonderful에서 크게 나빠졌다.

| SBVA 투자 역할 | 4,647 | 4,645 | 2 |

현재 원본 역할에서 `fit 없는 사람만` 찾으면 Wonderful은 0명이다. 이는 검색 실패가 아니라 이미 전체를 검토한 원장의 상태다. 단, 과거 행이 있다는 것이 현재 공통 V2 계약과 입력을 충족하거나 캐시가 유효하다는 뜻은 아니다. 만료·입력 변경·legacy 계약의 fit은 **갱신 대상**으로 별도 가져와야 한다. 이런 사람을 새로 발견한 인원으로 집계하면 안 된다.

복제 역할의 fit이 0인 상태로 진행 정답을 다시 찾게 한 것은 이 혼동을 피하기 위한 통제다. 갱신과 신규 발견을 합한 end-to-end 추천 효과는 이번 평가에서 측정하지 않았다.

## 권장하는 범용 실행 구조

1. **역할별 새 평가 목록을 만든다.** 해당 역할의 성공 평가 기록이 없는 사람을 검색 단계에서 먼저 확보한다. 인원 제한 후에 이미 검토한 사람을 버리는 방식을 쓰지 않는다. 1차 reject도 성공한 검토이고, API 실패는 검토 완료가 아니다. 회사 전체 여러 역할의 수가 늘었다고 모든 사람×모든 역할을 평가하지 않는다.
2. **검색 조건은 관련 경험·전환 가능한 경험·현재 전체 Brief를 함께 읽는다.** 직함 일치나 유명 회사 하나가 최종 능력을 증명하지 않는다. 회사 bar는 검색 우선순위의 근거가 될 수 있지만 최종 판정은 공통 fit에 둔다. 언어·취업 자격의 unknown을 학교·이름·현재 위치로 탈락 처리하지 않는다.
3. **검색 계획은 재사용하고 실제 목록은 매회 다시 조회한다.** JD·Hiring Brief·회사 판단 맥락이 달라지면 새 계획을 만들고, 그렇지 않으면 안정된 계획으로 미검토 범위를 계속 넓힌다. 계획 재사용 중에도 새 가입·Profile·Brief 변경은 현재 검색 데이터에 반영된다. 새 계획을 승인할 때는 첫 100명뿐 아니라 3/6회 누적 발견을 함께 비교한다.
4. **벡터는 후보 전체의 단독 판단 기준으로 사용하지 않는다.** 역할 관련 pool의 순서 개선 또는 제한된 보완 경로로 비교한다. 역할 범위·새 평가 여부·차단·삭제 등의 조건을 top-k 전에 적용한다. 초기 전체 탐색 비중은 작게 실험하고, 후보 20%를 무조건 탐색으로 할당하지 않는다.
5. **기존 fit 갱신은 별도 예산이다.** 입력 변경·기간 만료·계약 불일치의 평가를 새 평가 슬롯과 구분한다. 유효한 기존 fit과 이번 새/갱신 fit을 모두 추천 후보 pool로 모은다. 이전 추천 이력은 추천 방향·중복 방지 판단에 사용하며 새 fit 검색 자체와 혼동하지 않는다.
6. **추천 rerank는 성공 평가 전체를 대상으로 한다.** 현재 역할·공유 권한·진행 상태를 통과한 유효 fit을 기존+신규로 합친 뒤 기존 bounded compact/rerank를 사용한다. 이번 목록에서 빠졌다는 이유로 좋은 기존 fit이 사라지면 안 된다. bad/unfit이 있는 fit의 기존 제외 계약은 유지한다.

이 구조는 회사·직무 이름별 분기를 만들지 않는다. 새 평가·갱신·추천을 실제 평가 원장과 현재 자료에서 구분하고, 검색 방법의 우열은 고정된 평가로 확인한다.

## DB의 FTS / embedding에 대한 결정

지금 운영 DB에 FTS·embedding 필드를 바로 추가할 근거는 부족하다. 실험에서 FTS를 더한 것이 벡터 단독 정렬보다 확실히 좋지 않았고, 역할마다 벡터의 효과가 달랐다.

추후 검색 index를 운영화한다면 **Profile의 수행 근거**와 **현재 Brief의 탐색 방향**은 분리해야 한다. 기존 `talent_contexts.embedding`은 이미 있으므로 활성 Brief 행의 검색에는 재사용 가능성을 먼저 검토한다. 이번 로컬 실험에서는 그 컬럼이 스냅샷에서 생략되어, 전체 Brief를 다시 embedding했으며 기존 row embedding의 성능을 측정한 것은 아니다. Profile 검색 문서는 기존 경력·학력·프로젝트 원본에서 재생성하고, 입력 fingerprint로 갱신한다. 새 선호·능력 판단 원본이나 별도 대화 상태 테이블을 만들 필요는 없다.

FTS의 `tsvector`는 단어 기반 검색용이고, 의미 유사도를 찾는 embedding과 다르다. 둘의 점수를 그대로 같은 능력 점수로 취급하지 않는다. 검색 경로를 결합하는 RRF는 [Supabase 공식 hybrid search 문서](https://supabase.com/docs/guides/ai/hybrid-search)의 일반적인 접근이며, 입력 문서·단어 질의의 동작은 [PostgreSQL text search 문서](https://www.postgresql.org/docs/current/textsearch-controls.html)를 확인했다. 이번 구현은 localhost TEMP FTS와 전체 exact cosine으로 평가했고, 운영 HNSW·ANN 속도/recall은 검증하지 않았다.

## 재현과 남은 경계

- canonical runner: `harper_worker/llm_evals/role_scoring_list_retrieval/eval.py`, `experiment.py`, `judge.py`. 실제 source hash·prompt·모델 usage·판정·검색 SQL·candidate 목록은 ignored `runs/20261008-*`에 저장되어 있다. 기본 실험, 범위 수정, 표본 judge 수정은 각각 별도 run을 남겼고 gold v1은 변경하지 않았다.
- 모델은 실제 configured GLM 5.3 Flash high query planner, OpenAI text-embedding-3-small, 별도 GPT-6 Luna high judge다. 기본 세 역할 planner의 기록 비용은 약 $0.01255, 첫/수정 silver review 비용은 각각 약 $0.09347/$0.09108이다. 원문 8,000자 한도의 최초 index embedding 입력은 약 776만 tokens이며, 처음 실패한 focused-query 호출 비용은 유실되었다. 따라서 전체 실험 총비용을 정확히 주장하지 않는다.
- 현재 프로필·Brief는 과거 인터뷰 때와 다를 수 있다. 과거에 노출된 사람에게만 회사 기록이 있어 선택 편향이 있다. 후보 13명·회사 미팅 4명은 정답 중 일부이며 전체 적합자 목록이 아니다. negative challenge 6명도 현재 전체 부적합자를 대표하지 않는다.
- 표본 silver 결과는 작성자 검토와 소수 사례 prompt 보완을 거쳤고 인간 정답은 아니다. 미래의 새 역할에서 독립 팀원 labels를 동결한 holdout 없이 전 역할 precision 향상이나 실제 추천 수락률 개선을 주장하지 않는다.
- 로컬 테스트 역할만 생성했고 운영 DB·원본 역할·추천·발송·배포는 바꾸지 않았다. 테스트 역할은 paused/testOnly 상태로 로컬에 보존해 재현할 수 있다. 이 보고서의 권장 운영 구조는 후속 구현 대상이며, 프로토타입 성능과 운영 적용 사실을 구분한다.

## 후속 구현과 재검증 — 아직 미배포

사용자 승인 후 운영 경로의 코드를 변경했다. 새 검토는 **fit 이력 없는 pair를 예산 전에** 확보한다. 회사당 100/150/200 새 pair와 최대 50 갱신 pair의 예산을 분리하고, 각 예산 약 5%를 넓은 탐색에 예약한다. 만료·이전 계약·모델 변경은 갱신 검색이며, 요청자는 기존 별도 검토 경로를 유지한다. 현재 stage-2 fit은 새 검색과 관계없이 전체 pool에 합치고, 실제로 admission된 역할만 추가 평가한다. cache-only pair의 입력이 달라졌으면 즉시 전량 재평가하지 않고 기존 fit을 만료 처리해 후속 갱신 예산으로 넘긴다. 공유 fit TTL 30일, 세 축의 bad/unfit 제외, 추천 방향·한도·전달 계약은 유지한다.

검색 plan은 물질적인 역할/회사 입력·prompt·모델이 같은 경우 **최초 작성일부터 최대 7일** 재사용한다. 재사용 기록을 다시 원본으로 삼아 기간을 무한히 늘리지 않는다. 실제 후보 목록·현재 권한은 매번 다시 조회한다. 검색된 한 후보자를 회사의 모든 sibling 역할에 자동 평가하지 않으며 예산 단위도 talent×role pair다.

벡터 구현은 canonical Profile의 8,000자 검색 projection과 `text-embedding-3-small` 1536차원 cache를 사용한다. 역할 관련 SQL pool 최대 5,000명 안에서 cosine 순위를 계산하고 여러 capability query의 순위를 RRF k=60으로 합친다. Profile hash가 바뀐 경우에만 embedding을 다시 생성한다. active Brief의 경력 전환 검색과 전체 Brief/Behavior를 읽는 공통 fit은 별도로 유지한다. FTS/전역 ANN 검색은 추가하지 않았다. Worker 전용 cache table의 migration만 작성했고 운영 DB에 적용하지 않았다.

**벡터 정렬은 기본 OFF**다. 합쳐 작성한 검색문의 v10, 영어/수행 범위를 보완한 v11, 동일 SQL에 기존 별도 capability query를 넣은 비교까지 다시 실행했지만 직군 전체의 gate를 통과하지 못했다. 의미 정렬을 사용하려면 runtime의 `semantic_ordering_enabled`를 명시적으로 켜야 한다. Default SQL 경로는 capability query 생성이나 embedding API를 호출하지 않는다.

| 동일 v11 SQL의 6회 ledger replay | Wonderful 발견 / 13 | SBVA 발견 / 4 |
| --- | ---: | ---: |
| SQL 순서 + 미검토 pair | 3 | 2 |
| SQL pool 안 벡터 + 미검토 pair | 1 | 4 |
| 벡터 + 미검토 pair + 5% 탐색 | 1 | 4 |

이 결과는 앞선 11/13 프로토타입을 일반 성능으로 주장할 수 없음을 보여준다. SQL pool과 검색문이 바뀌면 의미 유사도만으로 좋은 사람을 충분히 앞에 놓지 못했다. 별도로 생성된 기존 capability query를 같은 v11 SQL에 넣어도 Wonderful 1/13, SBVA 4/4였으므로 영어로 바꾸기만 하면 해결된다고 결론 내리지 않는다. Sierra는 여전히 회사 positive gold가 없어 recall 수치를 만들지 않는다.

최종 default v12의 Wonderful 실제 SQL은 3,306 eligible 후보를 찾았고 SQL repair/fallback 없이 완료했다(모델 71.99초, 조회 1.16초). 같은 쿼리를 매회 반복한 replay는 6회 100명·known positive 0/13, 미검토자 확보는 600명·3/13이었다. 실제 default의 5% 넓은 탐색도 600명·3/13이었다. 첫 100명에서 known positive를 찾지 못했으므로 초기 목록 품질이 충분하다고 주장하지 않는다. 고정 SQL 6회 replay는 실제 7일 plan 재작성·회사 feedback·fit 비용·추천 반응을 재현하지 않는다.

원문·새 실행·embedding 사용량·SQL과 manifest는 ignored `runs/20261008-runtime-*`에 보존했다. Frozen corpus/gold는 변경하지 않았다. 관련 **304개 테스트**는 격리 PostgreSQL의 novelty-before-budget·갱신 분리·원본 plan TTL·embedding cache 재사용/읽기 전용/접근 제한·삭제까지 통과했다. 추천/회사 연락/서비스 재시작/운영 migration/배포는 실행하지 않았다. 앞으로 개선할 검색 품질과 실제 반응률, 독립 팀원 labels 및 새 역할 holdout의 미완료 상태는 그대로다.
