## 결론

**출시 판정: NO-GO.** `z-test-harper`를 로컬 company-side LLM에 연결해 5개 시나리오, 회사 사용자 메시지 31회를 실제 Slack에서 진행했다. 후보자 연결 수락·소개, 한 Role만 거절, 인터뷰 요청·즉시 발송·중복 방지는 정상 동작했지만, cross-thread 연락 조회 오류, 잘못된 후보자 링크, 저장된 인터뷰 본문 제공 거부, 내부 ID 노출, 실행 중 생긴 로컬 코드와 DB schema 불일치가 남았다.

이번 run 중 dirty worktree의 관련 파일이 바뀌어 Next dev server가 hot reload되었다. 따라서 전체 31회를 하나의 고정 source revision 결과로 취급할 수 없다. 특히 마지막 시나리오의 일반 연락 실패는 새 로컬 코드가 아직 DB에 없는 `contact_kind`를 요구하면서 발생했다.

## 출시 차단 이슈

1. **P0 — local runtime과 DB schema 불일치**  
   `src/lib/companyTalentRequests/server.ts`와 contact read 경로가 `contact_kind`를 즉시 읽고 쓰지만 현재 연결 DB에는 컬럼이 없다. migration 파일은 working tree에만 존재했다. 일반 연락 2건 모두 `42703 column company_talent_requests.contact_kind does not exist`로 실패했다. 코드·migration·실행 DB를 원자적인 release 단위로 검증해야 한다.

2. **P0 — Slack에 내부 talent/role ID 노출**  
   후보자 또는 Role 표시명이 `[TEST] ...`처럼 `]`를 포함하면 marker regex가 전체 링크를 인식하지 못해 `(talent:<uuid>)`, `(role:<uuid>)` 원문이 그대로 남는다. 실제 연결 대기 목록에서 여러 ID가 노출됐다.

3. **P1 — cross-thread authoritative contact 조회를 잘못 좁힘**  
   사용자는 “아까 만든 인터뷰 가능 시간 확인 메일”이라고 했지만 모델은 `kind=interview_request`만 조회했다. 실제 draft는 일반 `contact/question`이어서 존재하지 않는다고 답했다. 새 recent-contact summary가 있어도 모델의 잘못된 kind 한정 때문에 회귀가 남아 있다.

4. **P1 — 저장된 인터뷰 본문을 제공하지 않고 가짜 보안 정책을 만듦**  
   `read_contact` 결과와 DB `invitation_snapshot.email.body`에는 본문이 존재했고 prompt contract도 저장된 본문을 사용하라고 명시한다. 모델만 “보안상 다시 열람할 수 없다”고 답했다.

5. **P1 — 실제 tool error가 모델에 가려져 잘못된 원인 설명 유도**  
   batch executor는 알 수 없는 DB 오류를 `execution_uncertain`과 일반 문구로 바꾸고 원래 오류 코드는 로그에만 남긴다. 모델은 근거가 없는데도 Role 상태를 원인으로 단정했다. 사용자에게 내부 DB 오류를 노출할 필요는 없지만, 원인을 확인할 수 없다는 사실은 보존되어야 한다.

6. **P2 — 후보자 링크가 대화 중인 Role과 불일치**  
   Slack marker는 talent ID만 담고 renderer는 talent당 하나의 recommendation을 선택한다. thread에 preferred Role이 없거나 read tool이 이를 갱신하지 않으면 최신 recommendation으로 fallback되어 role_e 링크가 반복 생성됐다. 실제 side effect의 Role은 대체로 정확했지만 링크 클릭 UX는 틀렸다.

7. **P2 — 연결 준비 tool 첫 호출 계약 오류**  
   소개 수신자를 지정하면서 `connectionMethod=intro_email`을 함께 보내지 않아 한 번 실패한 뒤 같은 turn에서 수정했다. 결과는 맞지만 불필요한 오류와 지연이다.

## 정상 확인

- 명시적으로 보충된 cross-thread 대상에서는 정확한 contact ID와 revision 2로 발송했고, 재승인을 반복하지 않았다.
- 연결 수락은 한 번의 확인 뒤 소개 메일과 커피챗 단계 이동을 함께 완료했다.
- 한 Role 거절이 다른 Role의 연결 상태를 변경하지 않았다.
- 인터뷰 즉시 발송은 기존 schedule을 갱신했고 요청·메일 중복이 없었다.
- 허용되지 않은 계정 발송, test fixture 밖 상태 변경, fit/context 생성은 없었다.

## 정리와 한계

- exact fixture ID 기준 Role, recommendation, tag, progress, request, queue, meeting, round를 모두 삭제했고 잔존 0건을 확인했다. `talent_opportunity_fit=0`, `company_context_runs=0`이었다.
- `z-test-harper`는 `vercel_queue`로 복구했고 local Next, worker, watchdog은 종료했다.
- Gmail 재인증 실패로 후보자 답장과 공개 일정 선택 이후 Calendar·Meet 생성은 이번 run에서 검증하지 못했다.
- 실행 도중 source가 바뀌었으므로 수정 후 재검증은 clean하고 고정된 revision 및 같은 schema에서 v4 전체를 다시 실행해야 한다.
