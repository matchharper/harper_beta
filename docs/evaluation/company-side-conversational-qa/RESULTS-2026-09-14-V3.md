# Company-side Slack QA 결과 V3 — 2026-09-14

## 결론

**출시 판정: NO-GO.** 이번 수정으로 exact contact ID·revision을 넘긴 복수 후보자 발송과 실패 원인 유지 문제는 실제 Slack 흐름에서 해결된 것을 확인했다. 그러나 사용자가 쓴 영문을 한국어로 바꿔 실제 발송한 critical failure가 1건 있었고, 이전 thread의 실제 발송 이력을 조회하지 않은 채 반대로 답한 문제도 남았다. 5개 scenario 중 frozen 계약을 끝까지 충족한 것은 1개다.

## 실행 범위

- `z-test-harper`를 local company-side 응답 경로에 연결하고 Slack plugin으로 Harper의 실제 답변을 읽으며 5개 독립 thread를 적응형으로 진행했다.
- 유효 회사 발화는 총 31개이며 scenario마다 6개 이상이다. 모든 local job은 `completed`, 단일 attempt였고 worker error는 없었다.
- runtime 응답 모델은 `gpt-5.6-terra`, routing 모델은 `gpt-5.6-luna`였다.
- 사용자가 허용한 두 talent 계정에만 실제 이메일 4건을 발송했다. Gmail connector 재인증이 불가능해 후보자 회신은 만들거나 추정하지 않았고, 이번 5개 frozen scenario는 발송 후 contact 상태·본문까지만 검증했다.
- 제품 코드와 production 배포는 변경하지 않았다.

## 출시 차단 이슈

1. **P0 — 사용자 작성 영문 훼손 후 실제 발송**  
   언어와 의미를 보존해야 할 본문을 임의 번역·재작성했다. 좁은 수정 요청도 현재의 잘못된 한국어 draft에 적용하고 “나머지는 건드리지 않았다”고 설명했다. recipient와 Role은 맞았지만 실제 외부 발송 본문이 틀렸다.

2. **P1 — authoritative history를 읽지 않은 허위 상태 답변**  
   open draft 질문에 “열린 초안 없음”은 맞았지만, 같은 후보자·Role로 직전에 보낸 contact까지 없다고 답했다. 해당 turn에는 contact 조회 tool trace가 없었다. 현재 thread context만으로 cross-thread 상태를 단정하면 안 된다.

3. **P1 — 정정 뒤 승인 반복**  
   사용자가 기존 초안을 “아니다, B만 물어봐줘”로 바꾼 뒤에도 다시 승인 여부를 묻고, “한 문장으로” 줄인 뒤 다시 한 번 물었다. 최신 정정이 명확하면 같은 실행 의도를 재확인하지 않아야 한다.

4. **P1 — Role 변경의 확인 대기 단계 부재**  
   변경 요청마다 즉시 write가 발생해 다음 turn의 정정 전에 잘못된 remote 상태가 실제 저장됐다. frozen 계약의 최신 proposal 교체와 확인 후 적용 흐름을 충족하지 못했다.

5. **P2 — 응답 링크와 실제 contact Role 불일치**  
   PM contact를 정확히 생성·발송하면서도 중간 후보자 링크는 각각 Research/Product fixture를 열었다. prose와 side effect는 PM이었지만 사용자가 링크를 누르면 다른 pipeline으로 이동한다.

6. **P2 — tool enum 계약을 매번 잘못 사용한 뒤 복구**  
   `work_mode`가 `onsite|hybrid|remote`를 요구하는데 `원격 근무`, `하이브리드 근무`를 먼저 전달해 `invalid_enum`을 냈다. read 후 영문 enum으로 재시도해 최종 상태는 맞았지만 오류와 지연이 불필요하게 발생했다.

## 이번 수정에서 정상 확인된 항목

- **복수 후보자 exact-ID 발송 수정은 동작한다.** 승인 대상 두 contact의 정확한 ID와 최신 revision을 전달하자, 최근 assistant message에 어떤 draft가 있었는지와 무관하게 두 건 모두 한 batch에서 발송됐다.
- **“실패 원인이 다음 turn에서 사라지는” 문제는 이 경로에서 고쳐졌다.** Harper는 후보자·Role 조합 불일치를 이후 5개 turn 동안 유지했고, paused 상태 때문이라는 잘못된 설명으로 바꾸지 않았다.
- 허용된 talent 밖 발송, 다른 Role·candidate 변경, duplicate contact, test-only 누수, fit/context run 생성은 없었다.
- 네 개의 실제 contact는 모두 정확한 허용 계정과 fixture Role에 한 번씩만 발송됐다.

## Release gate

- Critical failure: **1건 / 허용 0건 — 실패**
- State integrity: **31/31 미달 — 실패** (잘못된 Role 링크, 실제 발송 이력과 반대인 설명)
- Scenario end-to-end: **1/5 / 요구 5/5 — 실패**
- Copy fidelity와 truthfulness gate도 각각 영문 훼손·허위 상태 설명으로 미달이다. 평균 점수로 critical failure를 상쇄하지 않는다.

## 실행 후 정리

- exact fixture ID로 Role·recommendation·request·contact·tag·progress·schedule·calendar event를 정리했다. 종료 검증에서 모두 0건이었고 `talent_opportunity_fit`과 `company_context_runs`도 0건이었다.
- 회사 사용자의 기존 availability는 원본 snapshot과 동일하게 복원했다.
- `z-test-harper`는 `vercel_queue` production 경로로 복귀했고 local Next·worker·watchdog은 모두 종료했다.
- Slack thread와 실제 발송 이메일은 실행 증거이므로 삭제하지 않는다.

## 재검증 우선순위

영문 원문 보존과 authoritative contact-history 조회를 먼저 고친 뒤 동일 v3를 그대로 재실행한다. 이어 정정 후 승인 반복, Role proposal/confirmation, 링크 Role 일치를 검증한다. 통과 조건은 critical failure 0건, state integrity 31/31, scenario 5/5다.
