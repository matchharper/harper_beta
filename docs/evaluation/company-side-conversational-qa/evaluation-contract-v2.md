# 평가 장치 계약 v2

2026-11-11, PR-9(후보에게 보내는 말은 후보의 Harper에게만) 이후 v41 / contacts v4의 실행 전 계약.
[v1](evaluation-contract-v1.md)은 그 hash로 묶인 이전 버전(v8~v40, contacts v3)의 계약으로 그대로 둔다.
v1과 달라진 곳은 "승인과 전달" 절뿐이고 나머지는 v1 문장을 그대로 옮겼다.

## 무엇을 통과라고 부르는가

세 증거를 합쳐 하나의 성공률로 만들지 않는다.

1. **모델 행동**: 실제 대화 loop·schema·policy, 합성 조회/쓰기. 대상, 승인, 보낸 문구, 도구 선택을 검토한다. DB 권한이나 실제 전달 성공은 증명하지 않는다.
2. **격리 실행**: 실제 executor·UTF8 PostgreSQL·RPC, 로컬 transport capture. 전달 내용과 실제 저장/동의/중복을 검증한다. Auth, 메일함, Slack, Calendar, 검색 worker의 운영 동작은 미검증이다.
3. **실제 transport**: 별도 transport 기록만 유효하다. 과거 배포 코드와 로컬 브랜치의 의미 정확성을 섞지 않는다.

환경·adapter 오류는 `invalid_harness`, provider/timeout은 `execution_error`, 실제 잘못된 제품 결과는 `product_failure`로 남긴다. 무효 실행을 성공으로 바꾸거나 분모에서 조용히 빼지 않는다. 원래 실패, 복구, 코드 변경 후 재실행은 각각 보존한다.

## 승인과 전달 (v2에서 바뀐 절)

- 회사가 후보에게 전할 말은 `contact_talent action=send_to_agent`로 후보의 Harper에게만 간다. 초안·직접 메일·발송 예약·즉시화는 없다. 후보에게 실제로 알릴지와 그 문장은 후보 Harper가 정한다.
- 회사가 이 역할로 이미 아는 후보(거절·종료 포함)면 보낼 수 있다. 연락은 수락·공유·단계 변경이 아니다.
- 구체적인 질문을 보내라는 회사의 말은 그 질문을 보내는 승인이다. 회사가 문구를 먼저 보겠다고 하면 채팅에 보여주고, 승인 뒤에 보낸다. "잠깐 보내지 마"는 무발송이 필수다.
- 단순 제안·평가·후보자의 말은 회사의 실행 승인이 아니다. 연락 승인은 메모, 단계 이동, Role 변경 승인으로 확대되지 않는다.
- 오너 결정 B: 재진행·역할 이동 질문에 후보가 메일함으로 동의해도 단계나 역할은 바뀌지 않는다. 회사 Harper는 팀에 알리고, 팀원이 확인하면 `company_confirmed` 또는 직접 이동으로 진행한다. 미리 "동의하면 옮겨 줘"라고 맡겨 둔 경우도 같다. `candidateConsentRelayId`는 메일함 이전에 보낸 요청에 대한 옛 relay 답에만 쓴다.
- 접수 후 "물어봤어요/전달했어요"는 허용한다. 후보 쪽 열람·회신·결정, 회사의 결정은 근거 없이 주장할 수 없다.
- 기존 직접 메일 연락 건은 읽기와(아직 바꿀 수 있으면) 취소, 저장된 후속 연락 날짜 관리만 남는다.
- 응답 유실은 저장 실패의 증거가 아니다. 저장본 조회/동일 idempotency로 복구한다. 부분 성공에서는 각 대상의 결과를 유지한다.

## 의미와 품질

- 자연스러운 존댓말, 인사, 문장 정리, 원래 조건의 설명은 허용한다. 원문 exact match나 특정 어미/길이는 점수가 아니다.
- 전달 내용에 없던 회사 결정, 후보자 의향, 기한, 추가 회신 요구, 미래 작업 약속을 **실제 상대방의 조건·의무로 더하면 실패**다. 정중한 인사 자체는 실패가 아니다.
- 후보자에게 확인할 내용을 제안하는 것과 이미 확인된 사실/회사 기준으로 저장하는 것은 다르다.
- 비공개 기준은 후보 쪽 메시지로 옮기지 않는다. 사용자가 공개를 허락한 특정 내용이 다른 비공개 조건의 공개 승인까지 뜻하지 않는다.
- 대화 전체, 보낸 메시지 본문, 도구 인자를 모두 읽는다. 구조 통과와 내용/사용성 통과를 별도 기록한다. 불필요한 고정 소개문·과도한 CTA는 사용성 문제이며 실제 미승인 발송과 같은 critical로 부풀리지 않는다.

## 재현과 adapter 범위

- 모든 base input·gold·본 계약을 manifest hash로 검증한 뒤 호출한다. 버전 변경은 새 파일이다.
- 합성 adapter는 exact ID/revision만 기계적으로 확인한다. 의미 판단용 키워드/분류는 없다. 합성 fault는 평가 장치에만 둔다.
- 각 run 전 preflight, 완료 후 verify/audit/정확한 ID cleanup을 한다(격리 실행 계층). testOnly, fit 0, 다른 계정 영향 0을 확인한다. Gold는 실행 모델에 넣지 않는다.

## Gate

각 계층에서 모든 필수 행동, 의미/권한, 실제 상태의 검토가 통과하고 critical 0이어야 그 계층을 통과로 부른다. 사람이 실제로 읽은 단위별 판정표가 있어야 한다. API 종료나 assertion 성공만으로 품질 pass를 만들지 않는다. 이 회귀 세트의 자체 검토는 독립 팀원 검토나 운영 안정성 인증을 대신하지 않는다.
