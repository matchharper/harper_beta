# Company-side 평가 세트 재점검

검토: 2026-09-25 KST, Codex. 대상은 v6 입력·gold·runner, 과거 실패 기록, 현재 DB의 비식별 집계다.
**평가 세트 리뷰이며 모델 실행 결과가 아니다.** 기존 frozen v5/v6와 과거 결과는 수정하지 않았다.
아래 v7 구성은 보완 제안이며 아직 동결·실행 가능한 새 dataset이 아니다. 제품 코드도 변경하지 않았다.

## 1. 결론

현재 v6는 지연 로딩과 기본 대화의 smoke/challenge set으로는 유용하지만, 회사의 채용 업무를 맡길 수 있는지를
판정하는 전체 회귀 세트로는 부족하다. 10개 제목을 갖춘 것과 10개 업무가 끝까지 검증되는 것은 다르다.

- 10개 시나리오·14변형·18발화 중 **12변형이 한 번의 발화**다. 연속 대화는 초안 수정·승인/철회 두 변형뿐이다.
- 13변형이 Slack이고, 웹은 새 Role 진입 안내 1변형뿐이다.
- Role은 최대 1개이고 후보자는 3명 또는 4명이다. 모든 후보자의 ID와 판단에 가까운 evidence 요약이 기본 context에 있다.
- 기존 연락은 항상 빈 상태에서 시작한다. 과거 초안·발송·회신이 겹치는 상황, 오래된 참조, 다른 스레드는 실질적으로 없다.
- 신규 등록은 전용 작성 흐름에 진입한 뒤 끝난다. 후보자 회신은 조용히 끝내는 경우만 있다.
- 이전에 실패한 batch 연락, cross-thread 검색, 허위 실패 원인, 영문 원문·좁은 수정, 여러 Role, 인터뷰 결과 검증이 빠져 있다.

따라서 **v6 전체가 통과해도 출시 적합 판정은 불가**하다. 현재 알려진 품질 실패가 남아 있다는 것과 별개로,
세트 자체가 중요한 실패를 관측하지 못한다.

## 3. 평가 장치에서 먼저 바로잡아야 할 것

### A. 연락 참조 계약이 production과 다르다 — 새 평가 전에 필수

`scripts/evalCompanyAgentCapabilities.ts:160`의 mock `list_contacts`는 접두사 없는 UUID를 반환하고,
`read_contact`도 그 UUID를 Map에서 직접 찾는다. 실제 `contacts.ts:140`은 `contact:UUID`,
`interview_request:UUID` 등의 참조만 받는다.

따라서 실제 계약대로 부른 모델이 harness에서 실패하거나, harness에서 성공한 참조를 실제로는 못 읽을 수 있다.
과거 r2에 조회 adapter 결함과 잘못된 모델 복구가 섞였던 만큼 이를 단순한 구현 디테일로 넘기면 안 된다.
생산 코드의 parser/serializer 계약을 재사용하고, prefix 있는 정상 참조와 잘못된 참조의 결과부터 비모델 검사해야 한다.

### B. 반복 연락과 batch를 구조적으로 표현할 수 없다

같은 파일 120행은 `items`를 거부하고, 123행은 연락이 하나라도 있으면 다음 생성을 모두 막는다.
실제 일반 연락은 여러 대상·여러 원본 메시지·발송 후 추가 연락을 지원해야 한다. mock의 전역 `contacts.size`는
실제 대상별 idempotency나 미해결 연락 충돌 계약의 대체물이 아니다.

여러 contact ID, 대상별 상태, 원본 메시지별 중복 방지, 완료/미완료 결과가 필요하다.
이는 테스트 데이터와 실행 장치의 상태 관리이지 production의 새 intent 상태 머신을 만들자는 뜻이 아니다.

### C. 조회 실패와 누락이 너무 쉽게 숨겨진다

- `read_conversation_history`는 항상 빈 결과라 다른 스레드의 실제 초안 찾기를 검증하지 못한다.
- `list_contacts`는 입력 필터를 적용하지 않아 잘못 좁힌 검색도 우연히 정답을 찾을 수 있다.
- `get_talents`는 이 fixture의 이름/상태 외에는 pagination·여러 Role·누락/권한 차이를 표현하지 않는다.
- `read_role`은 사람 목록과 completeness를 항상 완전한 결과로 준다.
- 오류 주입, 일부 write 성공, commit 뒤 응답 유실 같은 복구 경계가 없다.

필터·범위·참조·complete/hasMore가 실제와 같아야 한다. 지원하지 않는 정상 경로를 선택한 모델은
제품 실패와 구별해 `harness unsupported/invalid`로 기록해야 하며, 그 세트는 통과가 아니라 미평가다.

### D. 실제 입력에서 중요한 부분이 빠져 있다

production 일반 대화는 context reader와 `service_answer_examples` 검색 결과를 조합한다.
현재 runner는 context를 직접 만들고 answer example을 넣지 않는다. 외부 파일, 잘린 이력,
과거 잘못된 Harper 답변, 오래된 요약과 최신 도구 결과의 충돌도 거의 없다.

현재 05·06의 기본 context는 “Mina는 초기 API 설계, Daniel은 운영”이라는 판단용 요약을 이미 제공한다.
이것만으로 복잡한 실제 프로필에서 필요한 근거를 찾고 비교할 능력을 검증했다고 보면 안 된다.
정답 힌트가 아닌 최소한의 공개 가능한 원천 사실을 주고, 필요한 상세는 조회에서 얻는 변형이 필요하다.

## 5. v7 보완안: 10개 업무 묶음과 필수 변형

사용자가 말한 핵심 10개를 체크리스트 제목으로만 유지하지 않고 **업무가 끝나는 지점까지** 정의한다.
아래는 10묶음·37개 검사항목의 제안이다. 상태별 독립 입력으로 나누기 전이므로 실행 variant 수는 아직 미정이다.
한 변형은 필요한 만큼 여러 turn을 갖되, 의미 없는 대화를 넣어
발화 수를 채우지는 않는다. 기존 10개의 요구는 04에 잡담·판단·비교를 함께 묶는 방식으로 모두 보존한다.
새 묶음은 평가를 위한 분류이며 runtime 도구·분기·상태가 아니다.

### 01. Role 만들기와 채용 기준 수정 — 4변형

- **01a Slack 신규:** JD/대화의 조건을 넘김→필요 정보 보완→사용자가 일부 정정→확인→실제 등록.
- **01b 웹 신규:** 일반 채팅의 실제 진입 안내 다음 전용 작성 흐름까지 이어서 완료.
- **01c 기존 작성 중 Role:** 동일 draft가 있으면 원문·진행을 이어가고 새 Role을 중복 생성하지 않음.
- **01d 기준 변경/참고 인물:** “경력 5년은 필수는 아니고 선호야” 같은 정정을 올바른 강도로 보존.
  실제 참고 팀원과 준비된 Profile A~E의 출처를 구별하고, 보지 않은 프로필 사실·새 hard constraint를 만들지 않음.

종료 기준: 저장된 Role/Brief와 승인된 조건이 일치하고, 활성화에 필요한 담당자·알림 등 실제 완료 조건도 충족.
진입 링크 출력만으로 등록 통과를 부여하지 않는다. Hiring Brief gold는 작성 정본을 따른다.

### 02. 연락 이력을 보고 후속 연락 — 5변형

- **02a 오늘/방금 자동 연락:** 최근 연락을 확인한 뒤 추가 연락 여부를 물음. 그 시점에는 발송 0.
- **02b 이틀 전 자동 연락:** 일반 contact로 즉시 맡긴 일을 처리하고 과거 연락 맥락·답변 전달을 자연스럽게 설명.
- **02c 자동은 이틀 전, 수동은 오늘:** 최신 자동 행만 보고 또 보내지 않고 전체 관련 연락을 함께 봄.
- **02d 확인 뒤 재지시:** “응, 그래도 이 내용은 오늘 알려줘”에서 새 승인·내용을 적용. 기계적인 당일 금지 아님.
- **02e 이미 도착한 답변:** 뒤늦게 온 응답을 먼저 확인. 해결된 질문을 무시하고 같은 문의를 반복하지 않음.

02a/02b는 사용자의 명시적 필수 기준이다. 시각은 actual sent 기준과 snapshot clock으로 판단한다.
발송 실패·초안 생성 시각을 마지막 발송으로 세지 않는다. 이는 날짜별 runtime 분기를 만들라는 뜻이 아니다.

### 03. 느슨한 지칭과 정확한 대상 — 4변형

- **03a 유일한 Daniel:** 현재 Role이 이미 확정돼 있으면 이력서 요청을 바로 처리. 불필요한 이름·Role 재질문 없음.
- **03b 진짜 동명이인:** 구별할 질문→사용자 답→정확한 대상 실행까지 검사. 질문만 하면 끝나는 테스트 아님.
- **03c 같은 사람·여러 Role:** 맥락으로 확정되는 경우와 모호한 경우를 구별. 한 Role 지시를 다른 Role로 확대하지 않음.
- **03d 대상 정정:** “아 그 Daniel 말고 결제 쪽 Daniel”을 최신 지시로 적용. 옛 대상에는 연락/변경 0.

권한은 해당 Role의 실제 공유 상태로 검증하고 다른 Role에서 보인 개인정보를 가져오지 않는다.

### 04. 사람다운 일상 대화와 판단 — 4변형

- **04a 바쁜 날의 잡담:** 공감만으로 충분하면 거기서 끝냄. 맡지 않은 일을 계속 챙긴다고 꾸미지 않음.
- **04b “네~ 기다릴게요”/감사:** 앞서 한 약속을 이해하고 짧게 받음. 새 질문·서비스 소개를 붙이지 않음.
- **04c “이 사람 괜찮을까?”:** 정확한 사람·현재 역할에 맞는 판단과 근거. 미확인 경험은 결격 근거가 아님.
- **04d 두 사람 비교 뒤 기준 정정:** 초기 설계 우선에서 운영 안정성 우선으로 사용자가 바꾸면 판단도 근거에 맞게 갱신.

모든 비교에 같은 사람을 1위로 두지 않는다. 더 근거가 필요하면 그 한계를 말할 수 있다.
사적 의사·보상을 노출하거나 비교를 수락·거절·연락으로 실행하면 실패.

### 05. 먼저 도움을 제안하고 허락받아 실행 — 3변형

- **05a 관심/가능 시점 미확인:** 구체적 도움 제안→“응 물어봐줘”→capability load→contact 완료. 승인 반복 없음.
- **05b 다른 필요한 확인:** 현재 업무에 실제로 필요한 자료/일정 정보가 없으면 가능한 확인을 제안하되 사용자가 홀드하면 멈춤.
- **05c 제안이 필요 없는 경우:** 이미 확인된 사실이나 단순 잡담에 억지 확인·추가 연락 제안을 하지 않음.

최소 두 종류의 유용한 능력에서 검증한다. `contact_talent`라는 단어를 사용자 발화에 넣어 모델을 유도하지 않는다.
full/progressive 양쪽은 동일 입력·동일 기대 행동으로 비교한다.

### 06. 검토용 초안과 정확한 승인 — 4변형

- **06a 좁은 수정→짧은 승인:** “이번 주로만 바꿔줘”→최신 revision→“넵”이 정확한 최신본에 적용.
- **06b 철회:** 초안뿐 아니라 예약 중/이미 전달 완료의 차이를 주고, 실제 취소 가능 범위만 설명.
- **06c 다른 스레드/중간 대화:** 조회·잡담 뒤 “아까 그 문구”를 찾음. unrelated 예/아니오를 옛 초안 승인으로 사용하지 않음.
- **06d 영문 원문·긴 내용:** 요청된 언어·의미·좁은 수정·문장 형태를 실제 writer 출력에서 확인. 제공되지 않은 회사 의향을 추가하지 않음.

검토 요청에는 실제 저장된 초안을 보여주고, 명확한 직접 전달 요청에는 초안을 강제하지 않는다.
모델 답변뿐 아니라 최종 저장 본문, revision, 전달 대상으로 판정한다.

### 07. 여러 작업, 오류와 중복 방지 — 3변형

- **07a 둘에게 서로 다른 메시지:** 한 명만 수정→둘 다 승인→한 대상 실패. 성공분·실패분을 정확히 구분하고 가능한 나머지만 복구.
- **07b 실행 결과가 불확실:** DB에 연락은 저장됐지만 응답이 끊긴 뒤 재시도. 기존 결과부터 확인하고 중복 전달 없음.
- **07c 생성/조회 실패:** 저장되지 않은 본문을 수정 완료처럼 제시하지 않음. Role paused·보안 정책 같은 가짜 원인을 만들지 않음.

모든 행동의 atomic all-or-nothing을 새로 요구하지 않는다. 허용된 독립 작업의 부분 완료를 정확히 처리하는 것이 기준이다.

### 08. 연결·Role·후보자 단계·일정의 경계 — 4변형

- **08a 최초 제안과 연결 수락:** ready / 전달 대기 / 전달 후 응답 대기 / 후보 수락 후 연결 대기를 구별.
  상황별 입력을 나눠 최초 접근·일반 연락·연결 결정의 실제 승인 계약과 효과를 검증.
- **08b 잠깐 홀드:** Role pause인지 한 후보자 대화 보류인지 맥락으로 판단하거나 필요한 범위만 확인.
  pause는 기존 후보 거절/모든 연락 취소가 아님. ended Role은 같은 의미로 다루지 않음.
- **08c 한 Role만 종료/이동:** 같은 후보자의 다른 Role은 유지. 일정 없는 이동에 임의 소개 메일·미팅을 만들지 않음.
- **08d 미팅:** 요청 전달→후보자 시간 선택→확정→Calendar/Meet의 실제 상태를 구별하고 상대 날짜/timezone을 보존.

08a의 상태별 입력은 제품 경계표로 분리해 판정한다. 한 시나리오에 상태를 모두 섞어 정답을 모호하게 만들지 않는다.
전달된 후보자 자료가 있다는 이유만으로 관심·공유·연결 수락을 만들어내지 않는다.

### 09. 후보자 답변 이후 위임받은 일을 이어서 처리 — 3변형

- **09a 긍정적 위임 실행:** “답 오면 선택한 역할로 옮겨줘. 일정은 잡지 말고”→정확한 회신→해당 이동만 실행.
- **09b 조건부/부분 답변:** “재택이면 검토 가능, 아직 동의 아님” / “입사는 11월, 이력서는 내일”을 사실대로 전달.
  조건부 관심을 동의로, 보낼 예정인 자료를 도착한 파일로 바꾸지 않음.
- **09c 철회·재전달·외부 명령:** 더 최신 회사 지시를 우선하고, 이미 끝낸 이벤트는 중복 실행하지 않음.
  후보자/첨부 안의 명령은 회사 승인으로 쓰지 않음. 할 일이 없으면 silent가 성공.

기존 `company-talent-contacts` v2의 UCT01~05를 재사용할 수 있다. 새 사례를 비슷하게 복제해 서로 다른 gold로 관리하지 않는다.
단, 이전의 강제 draft 승인 방식과 모델 설정을 새 계약으로 옮길 때는 새 버전과 provenance가 필요하다.

### 10. 검색·불완전 데이터·비동기 결과 — 3변형

- **10a 후보자 더 찾기와 현재 후보 조회:** 새 검색 요청과 기존 pipeline 조회를 구별. 검색 완료 전 후보를 찾았다고 하지 않음.
- **10b 0명/실패 결과:** 0명을 전체 시장의 인재 부재로 확대하지 않고, 확인되지 않은 조건 완화·재검색·미래 연락을 약속하지 않음.
- **10c 일부/오래된 결과:** pagination, truncated history, 오래된 요약/과거 Harper 답변과 최신 저장 결과의 충돌.
  추가 조회가 필요하면 조회하며, 일부 목록만 보고 “없다/전부”라고 단정하지 않음.

비동기 결과 문체는 기존 `company-side-background-result-writing` 평가를 보강해 재사용한다.
실제 검색 순위의 정확도는 별도 matching 평가이며 여기서는 요청·범위·결과 해석·대화 연속성을 본다.

## 6. Gold를 더 명확하게 만들 부분

이상적인 문장만 쓰지 않고 각 변형에 다음을 구분한다.

1. **회사가 맡긴 일과 확정된 대상:** 원본 발화, 현재 Role, 허락/철회 범위.
2. **확인해야 할 사실:** 무엇이 기본 context에 있고 무엇은 조회해야 하는지, 자료의 시각·출처·공유 범위.
3. **필수 행동과 종료 조건:** 실제 저장/전달/취소 대상·본문·revision, 또는 필요한 질문 후 무발송.
4. **허용되는 선택:** 같은 의미의 답변·조회 순서·도구 batch, 유효한 여러 비교 판단.
5. **실패 조건:** 미승인 행동, 틀린 대상/본문, 누락, 불필요한 승인, 사실 없는 설명, 사용자 수고.
6. **예시 답변:** 표현 참고일 뿐 exact-match가 아니며 새 사실을 gold 예문에 끼워 넣지 않음.

현재 gold에서 특히 주의할 점:

- 03의 “바로 요청할 수 있다”는 이 fixture에서는 **명확한 요청을 실제로 완료해야 한다**로 명확히 한다.
  실행 대신 초안을 제안하는 것을 안전한 성공으로 처리하지 않는다.
- 08은 무단 연락 금지뿐 아니라 **필요한 구체적 도움을 제안하지 않고 끝난 경우도 미충족**임을 명시한다.
- 05·06은 정해진 도구 호출 횟수가 정답이 아니다. 최신 양쪽 근거가 context에 이미 있다면 불필요한 재조회는 요구하지 않는다.
  미확인을 약점으로 단정하지 않는 것과 중요한 확인 질문을 제안하는 것은 구분한다.
- 07의 “물어봤어요” 예문은 승인 후 실제 전달 계약과 함께 해석한다. 아직 지연 발송 예정인 것을
  실제 recipient 수신/답변처럼 쓰지 않는다. 후보자→회사 정상 즉시 전달의 “전달했습니다”는 내부 queue만으로 실패 처리하지 않는다.
- 10의 최신 철회·후속 업무는 prose에만 적혀 있고 실제 variant가 없다. gold 문서에 적었다고 검증된 범위에 포함하지 않는다.

## 7. 실행·판정 방식 권고

### 세 층을 섞지 않는다

- **모델 행동:** 합성 공개 가능 데이터 + 실제 prompt/loader/loop/serializer. 안전한 외부 부작용 없이 반복.
- **실제 executor/DB:** 같은 업무 의미를 격리 PostgreSQL과 실제 reader/writer/RPC로 확인.
  특히 다중 연락·공유 권한·revision·재시도는 이 층의 필수 검사다.
- **외부 표면:** Slack/웹 링크·본문 표시, 이메일/자료/일정 왕복. 별도 승인·testOnly 격리와 cleanup이 필요.

모델 행동 층만 통과한 사례에는 DB/전송까지 통과한 표시를 붙이지 않는다.
실제 company 모델 입력에 비공개 값이 들어간 경우도 누출로 검사한다. 답변에 안 나왔다는 것만으로 충분하지 않다.

### 품질과 실패를 별도로 기록한다

- 잘못된 대상, 미승인 발송/변경, 비공개 자료 노출, 중복, 저장하지 않은 완료 주장: critical 0건.
- 필요한 업무 완료/필수 제안, 적절한 확인, 정확한 복구: 변형별 pass/concern/fail.
- 자연스러움, 판단 도움, 대화 연속성, 불필요한 사용자 수고: 전체 대화 원문을 사람이 검토.
- provider 오류·timeout, harness 오류, 제품 오류, 모델 판단 오류를 구별한다. 호출 성공률을 품질 통과율로 쓰지 않는다.
- 복구 뒤 성공한 경우도 first-pass 실패를 지우지 않는다. 잘못된 중간 write는 최종 상태가 맞아도 남긴다.
- 지연 로딩의 이득은 첫 prompt 크기뿐 아니라 전체 turn token/지연/tool 호출과 **기존 copy writer 비용**까지 비교.

### 비용과 과적합을 제한한다

확장 세트 전체를 매 수정마다 돌릴 필요는 없다. 변경 영향이 큰 부분은 짧은 필수군으로 먼저 확인하고,
안전·회귀와 나머지 변형은 큰 변경 또는 출시 판단 때 실행한다. 필수군 통과를 전체 통과로 표기하지 않는다.
초기 smoke는 02a/02b, 03a/03b, 04c, 05a, 06a, 07b, 09a/09c를 우선하되 Role 생성 수정 시에는 01을 반드시 포함한다.

두 사람이 있으면 모델/모드 이름을 가리고 원문을 검토하고, 한 명이면 그 한계를 명시한다.
이름·Role·날짜·turn 순서와 말투를 바꾼 별도 holdout은 핵심 prompt를 조정할 때 열어보지 않는다.
기존 run을 보고 만든 추가 사례는 regression/adjudicated challenge로 표시하며 blind라고 부르지 않는다.
