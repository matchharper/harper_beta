# 수동 조사에서 실제 pedigree·퀄리티 바를 Brief에 작성하기

2026-10-15 로컬 변경. 채용 시작·저장·발송·배포에는 연결하지 않았다.

## 문제와 수정

이전 수동 조사 prompt는 추가 판단을 우대 영역의 초기 탐색 제안으로만 두었다. 공통 source 보존
계약과 결합하면서 기존 조건은 복사해도, 어느 수준의 이력에 어느 정도 가산점을 줄지 직접 쓰는
업무가 약해졌다. 이는 사용자가 요구한 인재상 calibration을 충분히 구현한 상태가 아니었다.

책임 원본인 `hiringBriefAuthoringPrompt.ts`와 Hiring Brief 작성 가이드에서 일반 자격 문구 편집과
위임받은 조사·calibration을 구분했다. 후자는 확인한 전문 배경으로 회사·팀·학업군의 수준과
가산 강도·검토 우선순위 효과를 직접 제안한다. 회사가 이미 명시한 bonus의 보존만으로 완료하지 않는다.
`roleSearchResearch.ts`는 이 결과를 Brief 자체에 작성하고 회사 설명과 같은 강도로 전달하도록 했다.

대표 회사·팀·학교명이 비교 수준을 명확하게 하면 보존하며, pedigree를 일반적인 구현 경험이나
추상적 ownership으로 지우지 않는다. 회사 확정 기준과 Harper의 soft bonus 제안은 구별한다.
제안이 채택되면 실제 비교 우선순위를 높이지만 새 필수 탈락 기준·자동 저장 권한은 만들지 않는다.

## 평가 계약

기존 v1 입력·gold·결과는 그대로 보존했다. 사용자 정정 요청으로 [v2 gold](../research-preview-gold-v2.md)를
첫 호출 전에 작성하고 v1의 세 사례를 그대로 포함한 새 입력에 다른 직무 RSR04를 추가했다.
RSR04는 사전 pedigree 우대 없이 두 합성 팀원의 회사·팀·학업 배경을 조사하는 사례다.
실재 회사·학교명이 나와도 인물과 경력 조합은 모두 합성이며 실제 회사의 채용 선호를 뜻하지 않는다.

Canonical runner는 `scripts/runRoleSearchResearchPreview.ts`이며 dataset version 선택만 추가했다.
모델은 기존 `google/gemini-3.8-flash`, OpenRouter, reasoning medium, temperature 0.5다.
내부 read와 이번 선택 사례들의 웹은 합성 adapter다. 실제 DB·Slack·검색 Worker는 차단했다.
전체 결과와 도구 근거를 사람이 읽어 판정했으며 keyword 채점이나 생성 본문의 후처리는 없다.
Raw 출력·review·source snapshot은 ignored owner-only runs에만 보존한다.

| 사례 | 시간 / 도구 / completion | 확인한 변화 | 전체 의미 판정 |
| --- | --- | --- | --- |
| RSR01 | 60.4초 / 10 / 8 | Brief에 구체적인 배경군·강한 가산과 보조 가산의 효과를 작성 | 미통과: 미확인 환경 상세, 메시지의 필수 범위·가상 맥락과 학업 bonus 단정 문제 |
| RSR02 | 35.3초 / 6 / 3 | 기존 조건 보존과 개발자 pedigree 비상속 | 미통과: 관찰 경력이 없는 상태에서 산업·규모별 새 bonus를 만들고 미수집 기록을 부재로 설명 |
| RSR04 | 41.6초 / 11 / 6 | 두 프로필 자율 조회 후 핵심 엔진팀 pedigree·학업 가산을 실제 Brief에 도출 | 미통과: 미확인 대표 회사, 데이터 규모, 대체 경로와 학업 역량 보증을 추가 |

공통 calibration 지침에서 실제 관찰한 전문 범위로 peer group을 일반화하고, 추가 대표 이름은
검증하며, 미관찰 규모·성과·동등 경로를 채우지 않도록 정리했다. 관찰 경력이 없는 경우에는
제품 업무만으로 새 출신 산업·pedigree bonus를 만들지 않는다. 같은 frozen v2의 RSR02/04를
새 run으로 재검증하며 r1 원문과 실패 판정은 보존한다.

## 두 번째 실행과 업무 지시 정리

`20261015-role-research-caliber-v2-r2`는 RSR02(58.6초, 도구 7회/completion 5회)와
RSR04(69.1초, 12회/7회)를 실행했다. RSR04의 Brief에는 회사·팀 배경의 강한 가산과 학업 배경의
보조 가산·우선순위 효과가 유지됐고, 임의 데이터 규모와 학업 실력 보증은 제거됐다. 다만 추가 대표
회사 검증과 미수집 이력의 부재 단정은 남았다. RSR02는 여전히 업무 설명에서 새 산업 가산점을
만들고 물리적 환경을 추가했다. 두 문서의 전체 의미 판정은 미통과다.

공통 계약은 근거를 요구하지만 수동 업무 지시가 여전히 추가 기준 작성을 무조건 요구하던 충돌을
정리했다. 확인한 전문 경력·이유 있는 검토 근거가 있으면 퀄리티 바를 직접 도출하고, 없으면 기존
조건을 보존한 Brief와 미확인 범위만으로도 완료된 결과로 취급한다. 회사의 명시적 pedigree 선호를
기다리라는 뜻은 아니며, 관련 팀원 경력이 확인되면 그대로 자율 calibration을 수행한다.

`20261015-role-research-caliber-v2-r3`는 같은 모델·frozen v2로 실행했다. 생성 문서와 실제 도구
반환 근거를 전체 대조했다. 아래 판정은 작성자 검토이며 운영 채용 성과나 독립 평가가 아니다.

| 사례 | 시간 / 도구 / completion | 판정과 확인 내용 |
| --- | --- | --- |
| RSR02 | 38.3초 / 10 / 5 | 통과. 전문 경력 근거를 확보하지 못하자 기존 Brief를 보존했다. 새 산업·학교·회사 bonus를 만들지 않았고 조회 실패를 미확인 범위로 설명했다. |

최종 선택 사례 **2/2**의 필수 의미를 확인했다. 최종 prompt로 RSR01과 live 웹 RSR03은 다시
실행하지 않았으므로 전체 v2 **4/4 gate는 미확정**이다. 앞선 실패와 v1 결과는 유지한다.
이번 3개 run의 7세션은 같은 작은 입력을 반복 보완한 과정이며 독립 표본으로 합산하지 않는다.

구조·권한 관련 기존 검사 7/7(미리보기 경계 5개, 공통 prompt 구성 2개)을 통과했고, 이 결과를
생성 품질의 증거로 대체하지 않았다. 최종 실행의 source hash와 현재 두 prompt·runner가 같은지,
v1/v2 frozen hash와 v1 기존 사례 보존, ignored artifact의 owner-only 권한도 확인했다.
일반 작성의 저장 권한이나 운영 모델은 변경하지 않았다. 새 정성 validator·점수·문구 후처리·DB
테이블·활성화 hook은 없다. 실제 Brief 저장, Slack 전달, 운영 DB 읽기, 후보 매칭의 변화는 미검증이다.
