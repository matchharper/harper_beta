# 대화 이력 조회 효율 점검

2026-10-15. 앞선 production-proactive-v2 로컬 관찰의 저장된 trace와 현재 reader 코드를 대조했다.
운영 전체 호출량이나 동일 최종 소스의 성능 비교는 아니다. 이 점검에서는 조회 도구를 변경하지 않았다.
별도 모델·테이블·검색 엔진을 도입할 근거는 아직 없다.

동일 인자의 무한 반복이 주된 원인은 아니었다.

## 확인된 결함: 상세 페이지 커서가 새 페이지를 겹쳐 반환

`src/lib/org/agent/conversationHistory.ts`의 `fetchOneThreadDetail`은 최신순으로 읽은
`selectedRows`를 `reverse()`로 직접 변경한 뒤, `selectedRows.at(-1).id`를 다음 페이지의
`beforeMessageId`로 사용한다. 이때 마지막 값은 가장 오래된 메시지가 아니라 가장 최신 메시지다.
따라서 다음 조회의 `id < beforeMessageId`가 이미 전달한 대부분의 메시지를 다시 포함한다.

P05 원문에서 동일 스레드의 첫 상세 페이지는 13개, 다음 페이지는 18개였고, 실제 content·createdAt을
대조하면 12개가 겹치며 새 내용은 6개였다. 합계 19개 스레드에서 31개 메시지를 반환한 셈이다.
이 사례는 추가 페이지가 한 번 더 필요하다는 사실 자체는 정상이다. 버그의 확인된 영향은 중복
본문과 입력량이며, 이 사례의 호출 횟수 절감까지 입증하지 않는다. 더 긴 스레드는 경계가 조금씩만
이동해 반복 페이지가 늘어날 수 있다.

현재 exported reader에 19개 메시지와 두 단일 메시지 스레드를 넣은 in-memory query adapter로도
13개 → 18개, 교집합 12개를 재현했다. 첫 페이지의 oldest ID는 7이어야 하지만 cursor는 최신 ID 19였다.
재현에는 DB·모델·외부 통신을 사용하지 않았다.

수정 방향은 정렬 전 oldest ID를 보존하거나, 원본 배열을 변경하지 않고 역순으로 표시하는 것이다.
기존 일반 reader에서 페이지 간 교집합 0·전체 누락 0을 확인하면 된다. LLM 출력 판정 로직은 필요 없다.

## 설계상 탐색 비용

1. **좁힐 조건 부족.** 도구는 역할 하나와 `all/thread`, cursor만 받는다. 키워드·기간·후보자·회사
   발화 존재 여부로 찾는 기능이 없어 최근 목록부터 넘겨야 한다. P02는 세 목록 페이지,
   P05도 세 목록 페이지를 거쳐 긴 회사 대화를 찾았다.
2. **알림과 대화가 같은 목록에 있다.** 목록의 상당수가 Harper 메시지 하나인 스레드다. 실제
   회사 답변·위임을 찾으려는 목적에서도 이 목록을 지나간다. 이를 기본으로 전부 제거하면 안 된다.
   기존 후보 소개를 확인하는 데는 필요하므로 선택적 `hasCompanyReply` 같은 구조적 필터가 적합하다.
3. **첫 세 메시지만 미리 본다.** 최신 시각은 있지만 마지막 회사 발화나 변경 내용은 없다.
   목록의 본문은 모델 전달 시 500자로, 상세는 900자로 줄어든다. 후보 소개가 긴 단일 메시지여도
   더 읽으려면 상세 호출이 필요하고, 상세 역시 긴 본문 전체를 읽는 계약은 아니다.
   `messages_complete`는 페이지 기준이며 본문 길이의 완전성을 뜻하지 않는다.
4. **기본 맥락도 최근 알림에 밀릴 수 있다.** 평가 capture는 최근 역할 3개에서 각각 5메시지,
   실제 로컬 proactive loader는 최대 6개 역할에서 각각 4메시지를 넣는다. 두 경로는 같지 않다.
   P02/P05 평가 입력의 역할 메시지 5개는 모두 Harper 발화였다. 이 제한 때문에 회사의 최근
   지시·결정을 읽으려는 모델이 별도 목록 조회부터 시작할 이유가 있었다.

## 가장 작은 개선 순서

1. 커서 배열 변경 버그를 먼저 수정하고 짧은 페이지 겹침·누락 검증을 한다.
2. 기존 `read_conversation_history` 목록에 선택적 기간과 회사 발화 포함 여부 필터를 추가한다.
   회사 발화 수, 최근 회사 발화 시점·짧은 발췌를 목록에 제공하면 불필요한 상세 열기를 줄일 수 있다.
   더 복잡한 검색은 이 변경의 실제 효과를 본 다음 판단한다. 권한·역할·현재 시점 경계를 유지한다.
3. 기본 awareness에는 최근 알림만이 아니라 관련 역할의 최근 회사 발화와 연결된 Harper 답변을
   작게 함께 제공하는 방안을 확인한다. 전체 과거 이력을 매번 주입하지 않는다.
4. 목록/상세의 본문 잘림과 추가로 읽을 수 있는 범위를 명확히 한다. 후속 상세가 이미 제공한
   내용과 같은지 모델이 판단할 근거를 준다.

단순히 '적게 호출하라'는 prompt나 횟수 상한을 더하면 필요한 위임·거절 이력을 놓칠 수 있다.
새 요약 LLM, 판단 캐시 테이블, 상황별 전용 도구는 이 문제의 첫 해결책이 아니다.

## 외부 공고 설명 prompt

같은 요청의 문구 수정은 `proactiveReview.ts`의 기존 유입 요청 예시에만 반영했다.
채용 상황에 맞춰 LinkedIn 공고를 유동적으로 운영하고 더 많은 적절한 지원자를 모으기 위해
후보 풀을 넓힌다는 목적을 짧게 설명한다. 즉시 게시 완료·게시일·후보 수를 만들지는 않는다.
고정 입력의 선택 재실행은 `20261015-proactive-acquisition-copy-r1`이며 결과는 별도 기록한다.

첫 r1은 P03 실행 123.0초, 추정 $0.1479912, tool 오류 없이 완료했다. 추가 유입 목적은 말했지만
외부 공고를 유동적으로 운영해 지원자 풀을 넓히는 방식은 설명하지 않아 이번 문구 목표에는 미달했다.
원문을 보존하고, 처음 이 도움을 소개할 때 회사가 그 작동 방식을 이해할 수 있어야 한다는 결과
기준을 같은 prompt에 보완했다. 실제 게시 완료를 주장하지 않는 경계와 기존에 이해한 설명을
반복하지 않는 원칙은 유지한다. 동일 초기 입력의 후속 run은 `20261015-proactive-acquisition-copy-r2`다.

후속 r2는 P03 실행 102.1초, 추정 $0.1423692, 14회 도구 호출 중 대화 조회 7회, 오류·실제 외부
효과 0으로 완료했다. 모델은 외부 채용 플랫폼의 공고를 채용 상황에 맞춰 운영해 더 많은 사람이
역할을 보고 지원하도록 후보 풀을 넓히는 방식이라고 실제 출력에서 설명했다. 요청 저장과 게시
완료를 구분했다. 원문 전체·도구 결과를 수동 검토했으며 이번 공고 설명의 의미 목표는 충족했다.
단, 뒤따르는 제약 안내는 여전히 길다. 전체 대화 말투·후보 순위·실제 게시·전달 E2E의 통과를
뜻하지 않는다. 같은 초기 입력에 대한 새 run이고 추가 live read와 주변 변경이 있어 시간 차이를
prompt만의 성능 개선으로 해석하지 않는다. 문구만 로컬 반영했고 도구 수정·운영 쓰기·배포는 없다.
