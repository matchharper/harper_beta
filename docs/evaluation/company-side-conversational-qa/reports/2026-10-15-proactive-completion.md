# Company-side 선제 채용 지원: 로컬 구현 완료 기록

기준: 2026-10-15. 운영 배포 기록이 아니다. 운영 DB 변경, Slack·후보자 이메일 발송, Calendar 생성, LinkedIn 게시, push/deploy는 하지 않았다.

## 구현 결과

- 기존 dispatcher에서 명시적으로 설정된 Slack audience의 평일 16–18시 KST 점검을 하루 한 번 enqueue한다. 최근 30분 회사 대화가 있으면 미루고, 새 회사 발화·당일 실행 기한을 확인한다.
- 원본 company-side agent가 `gpt-6.1-sol/high`와 공통 도구로 역할·후보자·대화·연락 사실을 읽는다. 별도 판단 LLM이나 상황별 상태 머신을 추가하지 않았다. 할 일이 없으면 침묵할 수 있다.
- 사용자 요청의 구체적인 대화 예시를 prompt에 추가했다. 소수의 검토 후보, 최근 의사와 이전 종료 이력, 위임한 연락, 회사가 별도로 진행한 미팅, 공유 가능한 후보 정보 등을 맥락에 맞게 판단한다. 예시는 필수 발언이나 고정 템플릿이 아니다.
- `send_company_message`가 짧은 전체 안내, 역할별 루트, 같은 역할의 답글을 하나의 묶음으로 확정한다. 전달 경로는 메시지별 영수증과 Slack client message ID로 부분 전달을 복구한다.
- `job_posting_promote`는 기존 공개·홍보 허용 범위 안에서 공고 운영에 필요한 추가 유입 수요를 기존 역할에 기록한다. 운영자가 읽을 수 있는 readonly reader와 GTM 운영 문서를 연결했다. LinkedIn에 즉시 자동 게시하는 기능은 아니다.
- 회사명 비공개·홍보 중단 변경은 현재 일반 역할 도구로 직접 실행할 수 없다. 운영자에게 요청을 전달하거나 Role Settings에서 변경해야 하며, 완료되지 않은 설정 변경이나 기존 게시물 제거를 완료했다고 말하지 않는다.
- 시장 근거 조회 도구는 구현하지 않았다. 설계는 [구현 계획 8절](../../../company/company-side-proactive-recruiting-implementation-plan-ko.md)에 남겼다.

## 중단 지점에서 수정한 문제

1. 메시지 링크를 읽는 과정의 실패가 Slack 발송 시도처럼 기록되던 순서를 고쳤다. 링크 렌더링이 성공한 뒤 전달 시도를 기록한다.
2. 실제 회사 조회에서 `company-intro:` 형태의 식별자가 UUID 추천 조회에 섞여 후보 상세 읽기가 실패했다. 저장된 추천 식별자만 해당 조회에 넘기고 Intro reader는 유지한다. 동일 회사 재실행에서 오류가 사라졌다.
3. Slack 전달 복구 응답의 타입과 timestamp 존재 확인을 보완했다.
4. 실제 데이터 평가를 운영 읽기와 로컬 부수효과 모사로 분리했다. 운영에 아직 없는 `promotion_demand` 필드만 읽기 projection에서 제외하고, 기존 공고 유입 요청 이력을 확인할 수 없다는 제한을 모델에 제공했다. 실제 부수효과는 금지한다.
5. 합성 평가 runner가 Sol과 terminal message tool을 지원하도록 보완했다. 이전 실패 run은 덮어쓰지 않고 원인과 재실행 관계를 남겼다.

## 검증

### 변경 경로

- 관련 테스트 53/53 통과. 최종 후속 검증 28/28 통과: 메시지 묶음, proactive 실행, capability loop, pipeline stage, 부분 전달 복구, audience 권한 취소, 발송 전 조회 실패 재시도.
- 격리된 로컬 PostgreSQL에 migration과 fixture를 적용해 원자적 확정, replay, 잘못된 source의 무기록 실패, receipt 충돌, test-only·홍보 허용 경계, 전달 시도 replay와 RPC 실행 권한을 확인했다. 운영 DB에는 적용하지 않았다.
- 변경 초기 전체 TypeScript 검사는 통과했다. 마지막 전체 트리 검사는 동시에 변경 중인 다른 경로의 오류 두 건으로 실패했다: `src/lib/ops/externalSearchPreview.test.ts:72` mock 타입, `src/lib/org/agent/promptFormat.ts:2301`의 `set_role_notification` exhaustive 처리. 이 기록은 전체 트리가 현재 통과한다는 뜻이 아니다. 범위 밖 코드는 고치지 않았다.
- 실제 Slack·이메일·Calendar 전송 E2E는 수행하지 않았다. 전송 여부가 불확실하고 Slack 이력에서도 정확한 영수증을 찾지 못하면 중복 발송을 감수한 재전송을 하지 않는다.

### 실제 모델 실행

[production-proactive-v2](../production-proactive-v2.md) 계약으로 회사 5곳을 실제 조회했다. raw input/output·trace·후보자 정보는 ignored `runs/`에 owner-only로 보관했다.

| 평가 단위 | 채택 run | 시간 | 추정 비용 USD | 도구 호출 |
| --- | --- | ---: | ---: | ---: |
| P01 | resumed-r5 | 155.2초 | 0.2233810 | 16 |
| P02 | resumed-r3 | 98.6초 | 0.1926320 | 10 |
| P03 | resumed-r5 | 94.2초 | 0.1925982 | 12 |
| P04 | resumed-r5 | 190.7초 | 0.2780902 | 17 |
| P05 | resumed-r3 | 102.5초 | 0.1613094 | 10 |

전체 run 이름 접두사는 `20261015-proactive-`다. r3는 최초 다섯 회사, r5는 동일 초기 입력에서 수정 영향을 받는 세 회사만 재실행했다. 추가 도구 읽기는 각 실행 시점의 운영 데이터이므로 완전히 동결된 비교 실험이나 다섯 회사 모두 같은 최종 소스의 결과로 해석하지 않는다. 소스 fingerprint·시각은 각 manifest와 trace에 있다.

최종 채택 다섯 출력의 합계는 약 $1.0480, 회사당 평균 약 128초다. r3+r5의 실제 회사 실행 전체 비용은 약 $1.6029다. 합성 평가 비용은 별도다. 비용은 관측 usage와 [OpenAI 공식 요율](https://developers.openai.com/api/docs/models/gpt-6.1-sol)을 사용한 추정치이며 청구액이 아니다.

관찰된 결과:

- 연결 대기 16명을 그대로 나열하지 않고 최근 관심 표현과 과거 종료 이력을 함께 확인해 두 명의 우선 검토를 제안했다.
- 부족한 후보 유입에 대해 허용 범위 안의 공고 운영 요청을 선택했으며, 즉시 게시·게시 시점·후보 수를 보장하지 않았다. 평가 속 요청 저장과 메시지 발송은 로컬 모사다.
- 회신을 기다리는 것으로 기록된 후보를 찾아 회사의 외부 진행 상황을 물었다. 발송 없이 종료된 초안을 발송된 연락으로 취급하지 않았다.
- P03 초기 read 오류는 수정 후 재실행에서 해소됐다. 최종 채택 결과의 tool trace 오류는 없었다.
- 선택 후보의 우선순위는 모델 판단이며 정답 순위 검증은 아니다. 역할별 답글이 여전히 길고 실행 시간도 길다. 실제 반복 운영의 유용성·피로도는 이번 실행만으로 입증하지 않았다.

### 합성 의미 검증

v26의 변경 관련 세 사례(새 사실 없는 침묵, shortlist 후 명시적 연락 승인, 시장 근거 부족)를 Sol/high로 재실행해 3/3 수동 검토 통과했다. 승인된 후보자 연락은 추가 승인을 요구하지 않고 수행했고, 시장 근거 없이 경력 기준을 낮추거나 증가 후보 수를 만들지 않았다. 전체 v26 release gate를 실행한 것은 아니며 독립 평가자의 검토도 아니다.

비교 과정의 기본 Gemini run은 시장 근거 부족 사례에서 근거 없는 경력 기준 완화를 제안해 2/3였다. 첫 Sol run의 terminal tool 누락은 harness 오류로 분류하고 수정 후 새 run으로 재실행했다. 이 실패도 보존했다. 정기 실행의 모델은 명시적으로 Sol/high이며 일반 대화 기본 모델을 바꾸지는 않았다.

## 시장 매핑 설계 결론

새 집계 테이블이나 분석 agent부터 만들지 않는다. 기존 `read_role`에 선택적 근거 조회를 확장해 현재 기준 버전, 평가 시점, 실제 평가한 모집단과 미평가·오래된 비중, 기준별 확인 근거, 현재 소개 가능한 상태를 함께 읽는 것이 가장 작은 출발점이다.

현재 fit·소개 기록에는 전체 탈락 후보의 같은 기준별 판단이 완전하게 남아 있지 않다. 소개된 사람만 센 통계는 선택 편향이 있어 “기준 하나를 낮추면 N명 더 가능”을 증명할 수 없다. 비교 가능한 실제 근거가 있을 때만 특정 기준의 영향과 사례를 설명한다. 근거가 부족하면 확인되지 않은 시장 진단 대신 연봉 등 결정에 필요한 누락 정보를 묻는다. 후보자의 비공개 개인 사유·Brief·Memory를 회사에 노출하지 않는다.

## 운영 활성화에 남은 일

현재 요청에는 배포 승인이 없어 여기서 운영을 활성화하지 않았다. 별도 배포 요청 시 실제 운영 schema를 확인한 뒤 필요한 migration `20261015002600_company_proactive_recruiting.sql`, 웹 배포, 명시적 audience 설정을 순서대로 처리해야 한다. 운영에는 새 필드가 아직 없어 현재 코드만 먼저 배포하면 역할 조회가 실패할 수 있다.

실제 Slack ingress·역할 스레드·전달 복구 확인과 Calendar/메일 등 외부 부수효과는 해당 범위를 승인받은 테스트에서 확인해야 한다. 공고 수요 reader는 운영자에게 데이터를 제공하며 기존 LinkedIn 공고를 자동으로 게시·수정·삭제하지 않는다. 이번 로컬 작업에는 Notion 배포 문서 동기화를 수행하지 않았다.
