개발 브랜치 `codex/company-agent-capabilities`. 운영 앱 배포·worker 재시작 없음.
이 보고서는 작은 회귀 challenge의 관측 결과이며 전체 서비스 정확도나 완벽함의 증명이 아니다.

## 발견한 문제와 변경한 경계

### 1. 핵심 연락까지 숨기면 말로만 초안을 만든다

초기 r1/r2에서, 그리고 직전 도구 기능만 이어준 r4에서도 초안 작성/수정을 말로만 수행하는 실패가 있었다.
직전 turn에 도구 호출 자체가 없으면 다음 turn의 자동 복원만으로 해결할 수 없었다.

- 기본 집합을 조회 5개 + 연락 3개 + loader로 변경했다. `contact_talent`, `list_contacts`, `read_contact`는
  schema와 상세 policy를 함께 기본 제공한다.
- 역할 편집·보정·검색·일정 같은 무거운 기능은 여전히 선택적으로 로드한다.
- 직전 실제 Harper `toolResults`에 해당하는 기능만 다음 turn에서 유지한다. 사용자/후보자 문구로 추정하지
  않고 오래된 기능 전체를 누적하지 않는다. 실행 권한은 가용성과 별개다.
- r6의 706 전체와 707에서 실제 저장/수정/승인/취소·실패 복구가 관측됐다. 저장 실패 뒤에는 원본을 읽고
  재시도하여 성공한 경우만 수정 완료로 평가했다.
- 별개로 r8 이메일 writer가 내용 대신 placeholder를 반환한 실패가 있었다. schema 검사는 통과했고,
  serializer가 본문을 숨겨 주 모델은 확인조차 할 수 없었다. 단일/일괄 초안 결과에 실제 저장된 제목·본문과
  revision을 보존하도록 수정했다. 서버의 exact preview도 유지한다. 이 변경은 확인 가능성을 복구한 것이며,
  모든 의미 오류를 자동 차단한다고 주장하지 않는다. 단어 검사나 출력 대체 규칙은 추가하지 않았다.

### 2. 전달 요청을 새로운 약속으로 확대한다

DB 상태가 정상이더라도, 대화 재개 가능 여부를 전달하면서 향후 먼저 연락하겠다는 약속을 보태는
실패가 있었다. 실제 Gmail 왕복의 배포된 수신 처리에서도 원문에 없는 향후 안내 선호가 추가됐다.
transport 성공과 의미 보존 통과를 분리한다.

- 양방향 연락 schema와 이메일 writer가 공통 `AUTHORIZED_MESSAGE_CONTENT_CONTRACT`를 사용한다.
- 의미·조건·강도를 유지하고, 전달 가능한 날짜와 미래 실행 약속을 구별한다. 메일 writer의 중간 요약이
  원문보다 강해져도 원래 사용자 지시가 우선이다.
- 전달 후 답변도 별도 공통 계약을 사용한다. 회사가 언제 응답할지 예측하거나 단순 전달 뒤 인터뷰를 다시
  시작하지 않는다. 실제 회신 도착 시 공유하는 기능과 임의 미래 리마인더 약속은 구별한다.

### 3. Role의 기준을 작성하며 회사보다 까다롭게 만든다

UTF8 재현에서 단순 기술 경험 요건이 세부 튜닝 역량 등의 필수 조건으로 강화됐다. 이전 지침은
각 평가 항목에 최소 기준·대체 근거·우려까지 채우라고 요구했고, context에는 항목이 적다는 이유만으로
`draftRecommended=true`를 만드는 휴리스틱이 있었다.

- 공개 Description, 비공개 Brief, Evaluation Criteria에 하나의 근거/강도 보존 계약을 적용했다.
- 상세 template 채우기 지시를 제거했다. 이전 Harper 초안이나 다른 Role은 현재 회사 요구의 새 근거가 아니다.
- 항목 수로 추가 작성을 권하는 코드를 제거했다. 코드에는 0–6개라는 구조적 제한만 남기고 작성 판단은 모델이 한다.
- `update_role_draft` 성공 시 실제 저장 필드를 돌려주고, 실패 시 가능한 경우 현재 저장본을 다시 읽어 제공한다.
- r3에서 설정 동의와 검토 단계 요청을 실제 활성화 승인으로 잘못 해석했다. 활성화 도구의 효과와
  검토 도구의 효과를 명확히 구분했다. 미실행 시점에 `activated=true`를 반환하던 잘못된 결과도 수정했다.
- 추론을 high로 높인 r5도 기준 강화와 비공개 내용의 공개 JD 혼입을 해결하지 못했다. 이 설정은 되돌렸다.
  최종값은 같은 Gemini/0.5/medium이다.
- 기존 `update_role_draft`에 일반적인 exact `textEdits`를 추가했다. 수정할 원문이 한 번만 나타날 때
  그 부분만 변경하며, 없는/중복된 원문이나 같은 필드의 full replacement와 충돌하면 쓰기 전에 실패한다.
  새 도구·판단 상태·테이블 없이 후속 추가가 기존 문서 전체를 재생성하지 않게 했다. 이것은 의미 검증이나
  원자적 동시 편집 잠금을 새로 구현한 것은 아니다.
- 일반 Role 작성에는 원문 보존 계약만 전달하고, 전문 인물 calibration 지침은 기존 calibration 경로에서
  사용하게 분리했다. sparse JD도 근거 없는 상세 template 대신 확인된 사실로 시작한다.
- r6/r7에서는 후속 추가 시 기존 문구·비공개 경계가 보존되고 5번째 발화에서만 활성화됐다. **그러나 최초
  작성에서 PostgreSQL 경험을 설계·운영 조건으로 넓히고 업무 내용을 추가 필수 경력으로 만드는 실패가
  남았다. Role 의미 보존은 미통과다.** 부분 편집이 처음부터 잘못 작성된 기준을 교정해 주지는 않는다.

### 4. 실패·중단·부분 결과를 끝까지 보존한다

- 연락 batch의 실패 대상에도 talent/Role/contact ID와 전달 상태를 보존해 성공 대상 중복 없이 복구한다.
- 주 turn 중단 신호를 기존 이메일 writer와 fallback에 전달하고, 중단 후 DB 저장을 막는다.
- 후보자 회신을 이미 보여준 event는 새 결정/경고/완료 작업이 없으면 조용히 끝낼 수 있게 전달 계약을 정리했다.
- 연락과 별개인 메모·기준·단계 변경 권한을 core에서 분리했다. 위임을 기억하겠다는 이유로 후보자 메모를
  추가하던 실제 executor 실패를 수정했다.

## 평가 장치 자체의 오류도 보존

- 초기 합성 `get_talents` 결과가 production serializer의 nested candidate/role 계약과 달라 후보자 목록이
  비어 보였다. adapter와 pagination 인자를 맞춘 뒤 다시 평가했다. 이전 실패를 제품 실패나 통과로 세지 않는다.
- 초기 embedded PostgreSQL은 SQL_ASCII였다. 한국어 길이 제한을 바이트 수로 계산해 Role 저장이 실패했다.
  새 UTF8 cluster로 다시 실행하고 non-UTF8 환경은 시작 시 거부한다. 그 SQL 실패를 운영 결함으로 주장하지 않는다.
- v1 역할 fixture는 active Role 한도를 소진했다. v2에 정확한 테스트 Role만 잠시 중단하고 복구하는 조건을
  기록했다. 발화와 gold는 유지했고 v1을 덮어쓰지 않았다.
- UCT05 gold의 optional silence를 필수 silence로 강제하던 runner assertion을 gold에 맞췄다.
  UCT03의 필수 silence는 유지한다.

### 아직 해결되지 않은 것

1. **Role 최초 작성의 원문 충실도**: 실제 채용 대상을 바꾸므로 최우선 차단 항목이다. 후속 문구 수정이나
   추론량만으로 해결됐다고 볼 수 없다. 현재 공개 JD와 내부 기준의 최종 사용자 검토를 대체할 수준이 아니다.
2. **연락 작성기의 의미 확장과 드문 불완전 본문**: shared contract/readback은 개선이지만 의미 보증이 아니다.
   특히 승인 없이 바로 보내는 경로를 단순히 전부 draft로 바꿔 회피하지 않았다. 기본 원문 보존 능력 검증이 더 필요하다.
3. **답변의 절제**: 회사/후보자 답변 일부에 불필요한 CTA, 과한 확신, 회사가 오해하지 않을 것이라는 추측이 남는다.
   말투 정규식이나 정해진 문장 덮어쓰기로 숨기지 않았다.

다음 반복은 같은 동결 입력으로 이 세 실패를 다시 판정한다. 모델을 바꾸거나 사용자가 정답을 수정한다면
각각 새 run/새 dataset으로 분리한다. 현재 결과를 배포 승인이나 “전부 해결”로 해석하면 안 된다.

## 안전·한계

- 운영에 synthetic Role을 만들지 않았다. 테스트 Role은 격리 DB에만 `testOnly/testFixture/testTalentIds`를
  사전 기록했다. 운영 guard가 확인되지 않은 상태에서 테스트 편의를 위해 migration을 적용하지 않았다.
- 종료 시 exact fixture 정리 결과 Role/fit/queue 잔존 0건을 확인하고, 이번 작업이 시작한 격리 DB·REST·gateway와
  절전 방지 프로세스를 종료했다. 실패 원문과 정리 전 audit는 private run에 보존했다.
- 실제 transport는 사용자가 허용한 기존 계정/추천 하나만 사용했으며 Role/단계를 바꾸지 않았다.
  발송·회신 이력은 허용된 테스트 증거로 남기고 삭제하지 않는다.
- 격리 환경의 answer-example vector 검색과 Slack transport는 제공하지 않는다. 따라서 운영 DB의
  검색 답변 예시를 포함한 품질, 실제 Slack/Calendar/Meet, production matching을 통과했다고 주장하지 않는다.
- whole-project typecheck에는 기존 생성된 Next network import·private 검사 스크립트·growth test 오류가 있다.
  별도 작업 없이 전체 clean build라고 말하지 않는다.
- 배포에는 별도 명시적 승인이 필요하다. 이 결과는 현재 운영 동작의 변경 증거가 아니다.
