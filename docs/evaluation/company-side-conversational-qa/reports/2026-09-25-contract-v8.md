# 평가 계약 수정·v8 실행·개선

문서 기준: 2026-09-26. 기준 실행을 먼저 보존하고 수정 실험을 별도로 기록한다. 운영 배포 아님.

평가 장치 계약 수정 → 새 입력/정답 동결 → 기준 실행 → 실제 실패 분석 → 구조 개선 → 같은 입력
재시험을 완료했다. 실제 본문 손상, Role 조건 강화, 후보자 완료 답변의 허위 전망,
모호한 홀드 범위 확정 문제는 최종 회귀에서 재현되지 않았다.

## 순서와 동결

1. [평가 장치 계약](../evaluation-contract-v1.md)을 먼저 작성했다. 미예약 초안 보류/취소, 예약 중단, 전달 접수/수신, 재서술/조건 추가를 구분한다.
2. adapter의 고정 예약 시각, 다른 Role 이름, 미승인 draft의 immediate 우회, 잘못된 presentedDrafts 타입을 수정했다. production lifecycle resolver를 재사용한다.
3. 회사 배경과 빈 예시 검색을 명시적으로 고정하고 UTF8/fixture/검색 경계를 preflight로 검사한다. 격리 실행 중 소스 변경은 차단한다. source snapshot과 provider 원문을 private에 보존한다.
4. 회사 대화 v8(37변형·54발화), Role v3(5발화), contacts v3(5대화)를 hash 동결했다. 이전 input/gold/run을 수정하지 않았다. 그 뒤 첫 모델 호출을 시작했다.

정답: [v8](../gold-v8.md), [Role v3](../role-creation-v3.json), [contacts v3](../../company-talent-contacts/gold-v3.json).
이전 결과를 본 회귀 세트이며 독립 blind 평가가 아니다.

## 기준 실행에서 확인한 근본 원인

- Role 최초 작성은 회사 배경을 합성 값으로 고정해도 미래 업무를 과거 경력 우대조건으로 추가했다. 또한 넓은 기술 경험을 더 좁은 활용/운영 경험으로 적었다. 실제 저장본의 문제이며 adapter 오류로 면제하지 않는다.
- Role 등록 완료는 공통 목소리 지침이 아니라 별도의 긴 고정 안내문으로 작성됐다. 말투 프롬프트만으로 고칠 수 없는 경로다.
- 연락 기능 정책이 초안 표시 계약 외에 매번 대신 질문하고 답변을 알려주겠다는 서술까지 요구했다. 공통 UX/결과 작성 계약과 책임이 겹쳐 반복적인 응답을 유도했다.
- 기준 실행의 합성 연락과 실제 격리 연락은 분리해 판정한다. 양방향 전달 상태가 맞더라도 실제 본문과 전체 답변의 의미 검토가 추가로 필요하다.

## 실행 증거

- 모델 행동 기준 실행: `20260925-v8-contract-r1-a`, `20260925-v8-contract-r1-b`
- 실제 executor/DB 기준 실행 + Role: contacts task `20260925-contact-v3-contract-r1`
- 초기 구조 회귀: 174/174 tests, 격리 direct-contact SQL checks 통과. 최종 변경 후 결과는 아래에 별도 기록한다.
- 전체 TypeScript 검사는 기존 8개 오류(Next 생성 validator 2개, private 수동 검증 1개, 기존 growth test 5개)로 실패. 새 변경 파일 오류는 관측되지 않았다.

## 실제 본문에서 발견한 추가 실패와 수정

### 직접 연락은 원본 대화 모델이 끝까지 작성

기준 실행 UCT02에서 회사 agent는 올바른 메시지를 만들었으나, 내부 보조 writer가 HTTP 성공과
정상 JSON으로 제목·본문·요약 모두 임시 문자열을 반환했다. 그 문자열이 실제 DB 발송 본문에
저장됐다. 상태만 보면 성공이고 회사 답변도 정상이라, 실제 본문을 읽지 않으면 놓치는 실패였다.
이메일 writer prompt에는 이미 임시 문구 금지가 있었으므로 금지 문장을 추가하지 않았다.

직접 `send`는 원본 대화 모델의 최종 `messageContent`·`messageSubject`·`requestContext`를
그대로 저장한다. 수신자 언어는 reader로 제공하고 서명된 이력서 URL만 서버가 slot에 바인딩한다.
역할/권한/동의/idempotency는 기존 executor/RPC가 유지한다. 별도 연락 종류나 intent classifier는 없다.
검토용 draft/revision은 사용자가 실제 저장본을 보는 기존 writer 경로를 유지한다.

### Role은 중복 해석을 줄이고 확인된 원문을 보존

최초 Role prompt의 중복 진행 예문·설정 설명을 하나의 작성/질문/확인 계약으로 합쳤다.
측정 시점 system 입력은 22,985→15,505자로 줄었다(문자 수, 청구 토큰이나 비용 감소율 아님).
부분 변경은 기존 exact text edit 계약을 유지하며 회사가 말한 자격 요건을 source clause로 다룬다.

수정 후 r3에서도 선택 사항인 구조화 Criteria에 미래 업무를 과거 경력 조건으로 추가하는 실패가
남았다. 새 Role은 Description+Brief가 기본 작성물이고, 별도 평가표는 회사가 요청할 때 작성하도록
작성 책임을 정리했다. 기존 Criteria는 관련 수정 요청 없이 지우지 않는다. 코드로 자격 문구를
비교·교체하거나 시나리오별 분기를 만들지 않았다.

성공 후 약 800자 고정 안내문 경로도 제거했다. 공통 voice/outcome 계약에 실제 활성화·Slack 결과만
전달한다. 실제 실행하지 않은 검색 worker나 회사 열람을 완료로 주장하지 않는다.

### 후보자 완료 답변의 상위 지침 충돌 제거

r3의 전달 본문/상태는 정상이어도 후보자 완료 답변에 회사의 예상 반응이나 미래 자동 전달 약속이
붙었다. 일반 Career 지침이 모든 제약 언급을 상담 대상으로 분류하고 5단계 조언·향후 추천 반영을
요구하는 상위 충돌을 제거했다. 현재 요청과 검증된 결과를 우선하고 상담은 도움을 구할 때 제공한다.
연락할 문장에 들어 있는 사정을 별도 상담 요청으로 취급하지 않는다. 온보딩의 별도 지침은 유지한다.

모델 실행 이후에는 제거한 hidden writer를 기대하던 기존 unit test의 구조 기대만 수정하고 203개를 재실행했다.

r2와 r3의 통신 실패를 계기로 runner 종료 계약도 수정했다. 이제 오류·미완료·빈 실행은 exit 1이고,
exit 0도 실행 완료만 의미한다. 품질 판정은 별도다. 과거 manifest/종료 증거를 소급해서 고치지 않는다.

r4의 수동 순서 오류도 제품 탓으로 분류하지 않는다. 평가 전용 입력 protocol 검사를 추가해
첫 발화/후속 답장/전달/event 순서를 동결 case 구조로 검증하고, 전체 단계 완료 전 `verify`를 막았다.
동결 실행의 발화 덮어쓰기도 금지한다. 런타임에 시나리오 상태를 추가한 것이 아니다.

808의 모호한 범위는 공통 요청 해석 계약에서 다룬다. 실제 쓰기를 하지 않아도 임의로 해석한 범위를
사용자에게 확정해 주면 안 된다. 후보자 완료 답변 계약은 기존 원본에서 요청한 전달을 확인하고
끝내도록 정리했으며, 아직 답하지 않은 질문이 있을 때만 이어간다. 별도의 품질 분류·재작성 모델은 없다.

등록 완료 모델 호출 실패 시 이미 끝난 DB 활성화가 사용자에게 사라지지 않도록 웹과 Slack 모두
동일한 오류 복구 안내를 사용한다. 모델 문체가 마음에 들지 않는다는 이유로 답변을 덮어쓰는 경로는 아니다.

문체는 좋아진 부분과 남은 상투적 CTA를 따로 기록한다. 정상적인 정중한 재서술은 오류가 아니며,
내부 queue 상태만으로 “전달했다”를 실패로 판정하지 않았다. 모든 반복을 독립 holdout으로 주장하지 않는다.

Role은 r4와 r5에서 각각 전체 5발화를 통과했다. r5의 Brief에 미래 업무가 Hard constraints 아래
‘업무 수행’으로 들어간 배치상 개선 여지는 있다. 과거 경력 필수조건으로 바꾸지는 않았으며,
공개 JD 자격 요건과 선택 Criteria에도 그런 과거 경험을 추가하지 않았다. 이 결과를 모든 직무의
요건 추출 정확성으로 일반화하지 않는다.

- 후보자→회사 relay는 같은 도구에서 실제 inline 전달했다. request ID 없이도 읽기/회신 연결이 유지됐다.
- event replay: progress/relay/queue/company message 수 변화 0, 추가 LLM 호출 0.
- delivery replay: event job과 회사 메시지 증가 0.
- fit 0, 미팅 0, 오래된 미응답 질문 0. 모든 fixture Role에 testOnly/fixture/허용 계정 표시 확인.
- 종료 후 정확한 fixture ID로 정리: Role 0, fit 0, queue 0. 별도 생성 Role/channel도 정리했다.
- 실제 모델/provider 원문·입력 hash·소스는 private run에 보존했다. 이 판정은 독립 팀원 검토가 아니다.

## 지연 로딩의 현재 경계

9개 기본 도구와 가능한 기능의 짧은 목록을 먼저 제공하며, 필요한 기능을 load하면 해당 schema와
policy를 함께 추가한다. 명확한 일반 연락에 반복해서 로딩 비용을 내지 않도록 연락 기능은 기본이다.
외부 회신 후 역할 이동 같은 무거운 동작은 실제 r5에서 필요한 기능을 로드한 뒤 실행했다.
선제 제안도 회사 대화 805 묶음에서 별도로 평가한다. 전 도구를 숨기고 사용자 요청만 기다리는 구조가 아니다.

9월 26일 offline 정적 입력 측정: progressive 40,241자(기본 도구 9개), full 93,227자(25개).
system+schema 문자 수 기준 약 57% 차이다. 동적 context·추가 로딩·writer 호출·cache를 제외하므로
토큰/비용/지연이 57% 줄었다는 주장이 아니다. 품질 우열의 full-mode A/B 실험도 이번에는 하지 않았다.

## 최종 검증과 남은 개선 우선순위

25개 관련 test 파일의 203/203이 통과했다. 범위는 prompt 소유권, 지연 로딩·권한 노출,
직접 연락/relay의 단일 writer, privacy/idempotency, exact draft/Role 수정, 등록 확인/오류 복구,
후보자 완료 지침, 평가 장치의 lifecycle/순서/실행 실패 계약이다. 도구·prompt 구조 테스트는
LLM 출력의 의미를 regex로 평가하는 장치가 아니다.

전체 `tsc --noEmit --incremental false`는 기존 오류 8개로 실패했다:
Next 생성 validator의 사라진 network 모듈 2개, ignored 수동 검증의 Supabase Promise 타입 1개,
기존 growth report test 타입 5개. 변경한 제품 경로의 새 타입 오류는 관측하지 못했지만
전체 typecheck 성공이라고 보고하지 않는다.

1. **호출 안정성**: 최종 최초 실행에도 120초 timeout 두 건이 있다. 취소 저장 후 답변 실패는
   ‘업무 실패’와 ‘결과 설명 실패’가 다름을 보여 준다. 무조건 write 재시도가 아닌 저장 결과 확인 경계를
   유지해야 한다. 이번에는 frozen run의 제한이나 모델을 바꿔 실패를 감추지 않았다.
2. **대화 사용성**: 판단/초안/완료 뒤 긴 설명·상투적인 추가 제안, 일부 강한 기여 예측이 남았다.
   필수 행동 오류와 별도 경고로 기록했다. 말투가 완성됐다고 주장하지 않으며, 다음 개선은 실제
   service answer example을 포함한 별도 동결 세트와 팀원의 독립 원문 검토로 판단해야 한다.
3. **외부 표면**: 아래 미검증 경로는 별도의 전달 검증이다. 로컬 결과만으로 현재 운영 상태가
   바뀌었다거나 실제 메일이 도착했다고 말하지 않는다. 이 변경 묶음은 새 DB schema를 요구하지 않아
   추가 migration을 만들거나 운영 migration을 실행하지 않았다.

## 검증 범위의 한계

이번 실행의 변경은 로컬 브랜치와 loopback PostgreSQL에만 있다. 운영 migration·배포·실제 메일
발송은 하지 않았다. 후보자→회사 inline DB 전달과 회사의 후속 실행은 실제 코드/RPC다.
회사→후보자 경로는 저장된 본문을 로컬 후보자 thread로 넣고 queue 상태를 모사하는 capture이며,
메일 worker 실행이나 inbox 수신 증거가 아니다. Vercel queue dispatch는 인증 없는 격리 환경에서
실행할 수 없어 event runner를 명시적으로 호출했다. 실제 Slack 전송도 하지 않았다.

서비스 답변 예시 검색은 동결된 빈 배열이다. 실제 vector search, 파일 업로드/Storage, OAuth/Auth,
worker 스케줄링, Calendar/Meet, sparse JD 및 모든 직무, 운영 전체 분포 성능은 이번 결과 밖이다.
기존 실제 메일 smoke는 이전 보고서의 별도 버전 증거이며 이번 코드의 검증으로 재사용하지 않는다.
