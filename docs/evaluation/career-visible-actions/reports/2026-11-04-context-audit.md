# Career 홈 액션 목록 맥락 점검

사용자는 방문 전에 준비된 일을 홈에서 발견하고 필요한 확인이나 답변만 이어갈 수 있는 목록을 원했다. 이번 점검은 그 목적, 화면 정보와 실제 클릭 효과, 재방문/위임 작업의 입력 경로를 대상으로 했다.

## 운영 DB

운영 migration `20261104140800` (`career_action_items`) 적용 완료. 로컬 정본은 `20261104134635_career_action_items.sql`이다. 객체 부재를 먼저 확인하고 적용 후 함수 본문의 정확한 일치, RLS·본인 읽기·서버 전용 수정/RPC 권한과 제품 `listCareerActionItems`의 REST 조회를 확인했다. 목록 0건이며 테스트 사용자/항목 생성이나 기존 자료 이관은 없다. 보안 advisor 219개 finding 중 새 객체 관련 항목은 없다. 웹·Worker 배포/재시작은 하지 않았으므로 새 UI와 도구가 운영에 제공된다는 뜻은 아니다.

## 실제 입력 경로

- `manage_action_items`는 온보딩 이후 core 도구다. 일반 대화, 재방문, 위임 작업과 정기 background에서 원본 LLM이 같은 도구와 현재 목록을 받는다. 목록은 소유자별 DB 조회이며 도구 실행 뒤 다음 모델 입력에도 갱신된다. 조회 실패를 빈 목록으로 표현하지 않는다.
- 재방문은 사용자 발언/동의가 아닌 앱 사건이다. 작업/미해결 폼 index도 함께 읽는다. 실제 위임 작업은 정기 background와 달리 일반 chat prompt에 `workContext`를 더하는 경로이며 v2가 이 차이를 반영했다.
- 목록은 방문 직후 조회되고 조용히 끝난 재방문/작업도 query 갱신으로 반영된다. 폼·작업·목록의 저장과 화면 효과는 독립적이다.
- 서버가 읽은 정확한 선택 카드 snapshot이 사용자 메시지에 저장된다. history, 진행 중 inbox, 재개한 작업의 사용자 맥락에 보존되므로 카드가 수정/삭제되어도 짧은 답변의 대상이 사라지지 않는다.
- 최대 10개는 모델의 선정 기준이며 DB/UI 상한이나 품질 심사 분기는 없다. 소유권·revision·멱등성은 실행 경계다. 음성 전용 모델까지 새 도구를 확장한 작업은 아니다.

## 발견한 문제와 원본 수정

1. 재방문 지침에 과거 전용 chat action block 작성 계약이 남아 있었다. 준비된 검토를 그 버튼으로만 제안하고 홈에는 게시하지 않은 사례가 있었다. 해당 authoring 지침을 제거했다. 과거 메시지 파싱/표시는 유지한다.
2. 폼 제시와 홈 게시가 독립적이라는 UI 계약이 설명에 없었다. 모델이 폼 표시로 홈까지 준비된 것으로 취급했다. 홈은 `manage_action_items`의 저장 목록만 표시하며 다른 도구/메시지는 자동 게시하지 않는다는 사실을 원본 guide와 도구 설명에 반영했다.
3. `compose_reply`는 입력창에 제목/설명을 붙일 뿐인데 검토 내용을 바로 보여주는 버튼처럼 선택한 사례가 있었다. 두 모드의 실제 효과를 설명했다. 내부 참조를 보이는 send-message 문장에 넣도록 유도하던 공통 지침도 없애고 자연스러운 사용자 문장과 응답용 모델 맥락을 구분했다.
4. “사용자의 영속 목록”이라는 설명 때문에 이미 10개가 있으면 중요한 항목을 추가하지 않고 정리 허락을 구했다. 원래 목적에 맞게 Harper가 현재 강조할 행동을 선정하는 목록으로 수정했다. 강조 항목을 교체해도 저장한 공고·폼·작업은 보존된다는 실제 효과를 설명했다.

사례별 분기, 자동 삭제, 키워드/길이 필터, 별도 심사 모델이나 숨은 운영 재시도는 추가하지 않았다.

## 실제 모델 관측

v2의 동일한 고정 사례 6건으로 설명을 비교했다. 일반 chat/위임 작업은 `gpt-6.1-sol`, 재방문은 제품 모델 `claude-haiku-5-5`, temperature 0.8이다. 전체 eligible schema와 실제 capability/handbook loader를 노출했다. 새 목록 도구는 실제 executor와 메모리 fixture다. work/form 도구는 제품 schema/formatter를 쓰되 실행 receipt만 모사했다. 실제 외부 효과는 수행하지 않았다.

| 사례 | 최종 실행 관측 |
| --- | --- |
| 가벼운 자기소개 문장 요청 + 무관한 기존 검토 | 대화로 답하고 새 항목을 만들거나 기존 검토를 바꾸지 않음 |
| 위임 작업의 지원서 준비 완료 | 기존 폼 재사용, 홈 검토 항목 생성, 해당 작업을 사용자 검토 대기로 기록. 다른 회사가 준비됐다고 주장하지 않음 |
| 준비 완료·준비 중·제출 완료가 섞인 재방문 | 끝난 질문과 제출 완료 항목을 정리하고 준비된 검토만 메시지 전송형으로 게시 |
| 카드에 연결된 “12월 1일부터, 이 지원서에만” 답변 | 원문 메시지 602를 정확한 작업에 전달하고 폼/목록 질문을 정리. 일반 프로필이나 제출 동의로 확대하지 않음 |
| 구직 중지를 요청한 사용자의 재방문 | 목록과 대화를 새로 만들지 않고 조용히 완료 |
| 낮은 우선순위 항목 10개 + 준비된 검토 | 강조 항목 하나를 내리고 검토를 더 높은 우선순위로 게시. 총 10개이며 원본 공고는 보존 |

최종 실행은 `2026-11-04T14-19-16.365Z`다. 앞선 세 실행의 실패도 보존했다. 초기 실행은 가득 찬 목록에 검토를 누락했고, 첫 수정 실행은 혼합 상태에서 기존 항목만 지우고 검토를 게시하지 않았다. 다음 실행은 혼합 상태를 처리했지만 가득 찬 목록 정리를 다시 사용자에게 미뤘다. 입력/gold를 결과에 맞춰 바꾸지 않았다. 모든 run·소스 hash·설정은 [manifest-v2.json](../manifest-v2.json)에 있고 원본 입력/출력은 ignored `runs/`에만 있다.

## 남은 관측과 한계

혼합 상태의 재방문에서 진행 중인 Cedar 작업에 원래 지시를 다시 `manage_work update`로 전달한 부수 행동이 반복 관측됐다. 새 작업을 만들거나 제출한 것은 아니지만 불필요한 재실행 접수로 이어질 수 있다. 새 목록 결과가 맞았다고 전체 agent 행동까지 완벽하다고 판단하지 않는다. 기존 위임 작업의 update 의미/재방문 판단에 관한 후속 점검 대상이며 이번 목록을 위해 work 전용 상태 분기나 재접수 차단 휴리스틱을 추가하지 않았다. 모사 평가만으로 실제 원격 queue가 재실행되었다고 주장하지 않는다.

작은 개발 표본의 최종 목록 결과는 의도와 맞았지만 장기 품질이나 운영 성공률을 추정할 수 없다. selector 모델과 실제 외부 지원·메일·원격 queue E2E는 포함하지 않았다. 수정한 prompt 경로 테스트 17개, 타입 검사와 lint는 통과했다. 운영 UI/모델 경로는 미배포 상태다.
