# 추천 대비 실제 피드백 평가 계획

기준일: 2026-10-07. 상태: **평가 설계와 production 집계 확인 완료. 평가용 원본 capture, gold 동결, 모델 비교, 온라인 실험은 아직 실행하지 않았다.**

[통합 매칭 계획](../../unified-talent-role-matching-implementation-plan-ko.md)이 더 좋은 추천을 만드는지는 **실제로 전달한 추천 중 긍정·부정·명시 반응 없음의 비율**로 판단한다. 공통 fit의 사람 평가 점수, 인터뷰·채용 전환, 비용은 이 평가의 성과 지표가 아니다. [저장 기능](../../internal-role-keep-implementation-plan-ko.md)은 별도 반응으로 측정한다.

먼저 과거 실제 반응으로 새 선택 로직의 보존·제외 성향을 검증하고, 그다음 실제 추천 비교로 개선 여부를 확인한다. 과거에 전달하지 않은 역할의 반응을 LLM이 대신 예측해 정답으로 만들지 않는다.

## 2. 평가 대상과 분모

기본 단위는 **후보자 한 명에게 특정 내부 역할을 한 번의 제안으로 전달한 episode**다. 하나의 episode에는 첫 추천과 그에 대한 후속 연락이 포함된다.

| 상황 | 처리 |
| --- | --- |
| 역할 3개를 한 메일로 추천 | 역할별 3 episode. 메일에 답했다는 이유로 3개 모두에 긍정 label을 주지 않는다 |
| 같은 추천을 email과 chat으로 전달 | 하나의 episode, 가장 이른 정상 전달을 시작 시각으로 사용 |
| 같은 역할을 재전송하거나 리마인드 | 기존 episode. 추천 분모와 관찰 기간을 새로 시작하지 않는다 |
| Fit 계산, rerank 선택, matching review 생성 | 아직 추천 분모가 아니다 |
| 역할 카드만 사전 생성되고 실제 추천 메시지는 미전달 | 분모에서 제외. 선택에서 전달까지의 누락으로 별도 기록 |
| 성공적으로 발송했으나 사용자가 열지 않음 | 분모에 포함. 열어 본 사람만으로 평가하지 않는다 |
| Chat에 실제 추천 메시지와 카드가 게시됨 | 전달로 인정. `sent`는 게시 성공이지 사람이 읽었다는 증거가 아니다 |
| 전송 실패·skipped·queued만 있고 다른 정상 전달도 없음 | 전달 분모에는 제외. 온라인 후보자 전체 기준 집계에서는 해당 후보자를 계속 포함 |
| 추천 후 역할 마감, 회사 철회, 후보자 opt-out | 이미 전달한 episode를 소급 삭제하지 않는다. 반응은 그대로 집계하고 기간 중 종료 사실을 표시 |
| 후보자가 먼저 특정 역할을 찾아 검토·소개 요청 | 자기 선택이 강한 별도 cohort. 비요청 추천과 섞지 않는다 |
| 기존 Harper 추천 후 회사가 실제 Intro 요청 | 회사의 새 요청은 별도 episode·경로. 어느 제안에 대한 답인지 연결하고 같은 답을 양쪽에 중복 반영하지 않는다 |
| 마감 후 다른 실질적 제안으로 재개 | 실제 새 제안의 근거가 있는 경우만 별도 episode. 캐시 TTL 경과나 run 재실행만으로 분리하지 않는다 |

시작 시각 `t0`는 역할 포함이 확인된 첫 email 발송 또는 chat 추천 게시 시각이다. 이메일은 provider 접수 수준의 발송 기록이며 수신함 도달·열람으로 표현하지 않는다. Bounce가 나중에 확인되더라도 최초 발송 분모를 임의로 줄이지 않고 상태를 별도로 보여준다.

직접 추천 ID가 없는 오래된 데이터는 실제 전달 snapshot의 role 링크·메시지와 연결한다. 원장 생성 시각밖에 없는 경우는 `legacy_proxy`로 분리한다. 사용자 반응이 있다는 이유만으로 그 반응 시각을 `t0`로 만들어 깨끗한 평가 세트에 넣지 않는다.

## 3. 긍정 부정 무응답의 정의

주 관찰 기간은 **전달 후 14 × 24시간**으로 고정한다. 7일을 빠른 반응 참고치, 28일을 늦은 반응 참고치로 함께 제공하되 각 기간이 모두 지난 episode만 해당 표에 넣는다. 결과를 본 뒤 유리한 기간으로 주 지표를 바꾸지 않는다.

| Label | 14일 안의 관찰 | 포함하지 않는 것 |
| --- | --- | --- |
| P 긍정 | 해당 역할에 대한 후보자의 명시적 수락·진행 의사가 확인됨 | 회사의 수락, 추천 worker의 recommend=true, 팀원의 추정, 카드 열람, 질문에 대한 일반적인 동의 |
| N 부정 | 해당 역할에 대한 후보자의 명시적 거절이 확인됨 | 자동 dislike, 역할 마감, 회사의 거절, 연락 종료 |
| K 저장 | P/N 없이 명시적으로 저장·나중에 결정 의사를 표시 | 단순 조회, 시스템이 임의로 숨기거나 보관한 상태 |
| I 명시 반응 없음 | 기간 내 P/N/K가 관찰되지 않음 | 전달하지 않은 역할, 아직 14일이 안 된 추천, 기록 손실로 판정 불가능한 사례 |
| U 판정 불가 | 전달은 확인됐으나 반응 출처·시각·대상 또는 로그 누락 때문에 label 확정 불가 | 이를 I 또는 N으로 강제 환산하지 않음 |

`I`는 “사용자가 읽고 일부러 무시했다”가 아니다. 미열람, 나중에 확인, 역할 관련 질문만 한 상태 등이 포함된 **정해진 기간 내 명시 선택 미관측**이다. 질문에 답한 것과 추천을 수락한 것은 구분한다.

반응 변경은 다음으로 고정한다.

1. 14일 안의 **첫 P 또는 N**을 주 label로 사용한다. 이후 회사 불합격 때문에 P를 N으로 바꾸지 않는다.
2. Keep 뒤 14일 안에 수락하면 P, 거절하면 N, 결정하지 않았다면 K다.
3. Keep을 지웠다고 이미 확인했던 사실을 지우고 I로 되돌리지 않는다.
4. P 뒤 사용자가 마음을 바꾼 사례는 첫 피드백 P를 보존하고, 14일 종료 시점의 최신 명시 결정도 보조 표로 제공한다. 최신 상태의 부호가 주 결과와 반대 방향이면 이를 숨기고 개선을 선언하지 않는다.
5. 14일 이후 반응은 14일 label을 덮어쓰지 않고 28일 결과에 반영한다.
6. P/N 없이 회사 Intro로 교체된 옛 episode는 `I, superseded_during_window`로 남긴다. 새 Intro 답변을 옛 제안의 성공으로 이동하지 않는다. 경로 교체 없는 사례도 별도로 보여주되, 그 부분 집합을 주 결과로 대체하지 않는다.

U가 있으면 전체 전달 수 `D=P+N+K+I+U`를 먼저 공개하고 각 확정 label의 `건수/D`를 낸다. 긍정률은 하한 `P/D`, 상한 `(P+U)/D`도 함께 보여준다. U를 제외한 비율은 별도의 “판정 가능 표본 조건부” 수치다. U가 많은 상태에서 한 숫자만 전체 반응률로 발표하지 않는다.

신규 온라인 계측의 제안 gate는 U가 각 arm의 1% 이하, arm 간 U 비중 차이가 0.5%p 이하인 것이다. 이를 충족해도 U를 양쪽에 가장 불리하게 배분했을 때 개선 방향이 뒤집히면 확정 결론을 보류한다. 과거 자료가 이 기준을 못 맞춘다고 모호한 행을 삭제해 통과시키지 않는다. 원본 로그가 지워지거나 수집되지 않은 구간의 feedback=null은 곧바로 I의 증거가 아니다.

## 4. 지표와 더 좋아졌다는 판단

| 지표 | 계산 | 사용하는 이유 |
| --- | --- | --- |
| **주 지표인 14일 긍정률** | P / 실제 전달 D | 추천 하나가 명시적 긍정을 얻을 가능성 |
| 14일 부정률 | N / D | 사용자 거절 비중 |
| 14일 무응답률 | I / D | 명시 선택이 관찰되지 않은 비중 |
| 14일 저장률 | K / D | 확인했으나 결정하지 않은 비중. 긍정률에 합산하지 않음 |
| 명시 반응률 | (P+N+K) / D | 무응답 감소 확인. 거절만 늘어도 올라가므로 단독 성공 기준으로 쓰지 않음 |
| **긍정 기회 보존** | 실험 대상 후보자 100명당 28일간 전달한 추천에서 발생한 P 수 | 추천을 극소수에게만 보내 긍정률을 높이는 편법 방지. 추천 0건 후보자 포함 |
| 추천량 | 같은 후보자 100명당 전달 episode 수 | 긍정률 변화가 얼마나 더 적게·많이 보낸 결과인지 설명 |

온라인 주 지표의 분모는 해당 후보자별 28일 노출 기간의 전달 episode다. 각 episode에 추가 14일의 답변 시간을 준다. 따라서 후보자 한 명의 최종 주 결과는 등록 후 최대 42일이 필요하다. 긍정 기회 보존 지표도 **같은 episode의 P**를 사용한다.

`P/(P+N)`은 답한 사람 중 호감도일 뿐, 무응답을 버리므로 주 지표로 사용하지 않는다. `(P-N)/D`처럼 부정 1건과 긍정 1건의 가치를 임의로 상쇄하는 단일 점수도 만들지 않는다.

**제안하는 실험 성공 기준**은 다음과 같다. 실험 전 깨끗한 baseline·표본 수를 확인한 뒤 사전 등록하고, 시작 후 바꾸지 않는다.

- 목표 효과: 긍정률 **절대 +5%p**. 관측 차이가 이 이상이고 후보자 단위 신뢰구간의 하한이 0보다 커야 목표 달성으로 부른다.
- 후보자 100명당 P 수의 새/기존 비율에 대한 신뢰구간 하한이 **0.90 이상**이어야 한다. 10%는 통계 상수가 아니라 이번 계획에서 제안하는 최대 허용 감소폭이다.
- 부정·무응답·저장을 함께 공개한다. 예를 들어 I에서 N으로 이동한 것만으로 “추천이 더 좋아졌다”고 하지 않는다.
- 명시 반응률만 좋아지거나 표본 부족으로 차이를 구별할 수 없으면 각각 “반응 증가만 확인”, “판정 보류”로 결론낸다.
- 긍정률은 좋아졌지만 긍정 기회가 크게 줄면 “선별은 보수적으로 바뀌었으나 전체 추천 개선은 미확인”이다.

지표를 후보자별로 묶어 불확실성을 계산한다. 한 사람이 받은 10개의 추천을 서로 독립인 10명처럼 취급하지 않는다. 역할·회사 편중은 workspace를 하나씩 제외한 결과와 역할별 분포를 함께 보아 확인한다. 이 자료만으로 새 회사 전체에 같은 효과가 난다고 일반화하지 않는다.

| `talent_progress`, 기존 `talent_role_activity` | 수락·저장·거절에 관련된 사건, source, 실제 follow-up | legacy mirror가 같은 ID로 복제되는 경로는 중복 제거. 회사 사건과 후보자 사건 분리 |
| `company_intro_candidates` | ready, 회사 요청, 후보자 발송, 결정, close reason | ready 자체는 후보자 추천이 아님. privacy·자동 종료는 부정 아님 |
| `opportunity_discovery_run`, company run | trigger, 실제 선택, 버전, candidate pool·snapshot 존재 여부 | 저장된 모델 output을 원본 입력으로 착각하지 않음 |
| Profile, Brief, Memory 원본, Behavior, 역할/JD의 보존본 | 추천 결정 직전 알고 있던 사실 | 현재값이나 답변 이후 summary를 과거 입력에 사용하지 않음 |
| 당시 설정·동의·추천 및 대화 이력 | 내부 전용, 온보딩, 과거 응답성, 직전 연락, 개수와 순서 | 설정이 현재값밖에 없으면 당시 cohort를 추정해서 확정하지 않음 |

외부 추천 데이터는 내부 추천의 정답 수를 늘리는 용도로 섞지 않는다. 전달·응답 연결기의 검증, 사용자의 **당시 이전까지의** 연락·응답 이력, 별도 external 결과 분석에만 쓴다. External의 like는 내부 역할 수락과 다른 행동이다.

현재 Ops matching analytics는 진행 단계도 사용해 accepted/rejected를 계산한다. 이 평가에서는 해당 현재 상태 funnel을 재사용하지 않고, 위의 전달·후보자 반응 사건으로 다시 계산한다.

## 6. 과거 피드백 정제와 gold 작성

| 순서 | 구체적인 작업 | 완료 조건 |
| --- | --- | --- |

| 2 | 전달 snapshot으로 추천 포함 여부·`t0`·episode 연결 | 채널 중복·follow-up 중복 0, 불명은 proxy/unknown으로 분리 |
| 3 | 원본 피드백 사건을 시간순으로 결합 | 사용자 반응, 팀원 대리 입력, 시스템 종료의 source 구분 |

| 6 | 7/14/28일 label·최신 명시 결정·데이터 신뢰도를 산출 | 미래 반응을 이전 horizon에 사용하지 않음 |

200건 audit은 원래 분포를 유지한다. 드문 N·자동 종료·경로 교체·keep 의미 혼동 등은 추가 표본으로 검토하되 이 challenge 표본을 대표 반응률에 섞지 않는다. Audit에서 출처·episode·시간 기준 오류가 확인되면 해당 수집 경로를 전수 수정하고 새 표본으로 다시 검사한다.

LLM은 대화에서 근거를 찾아 reviewer에게 보여주는 보조 수단으로만 사용할 수 있다. 새 추천 모델의 출력이나 예상 호감도로 P/N/I 정답을 만들지 않는다. 원문 검토는 평가용 오프라인 작업이며 운영 대화에 별도 intent classifier를 추가하는 설계가 아니다.

70건 고정 시스템 사유 일치는 자동 종료의 확인 가능한 하한이다. 그 사유가 없다고 나머지를 전부 사용자 거절로 확정하지 않는다. 자동 종료 전 사용자가 실제 반응했던 사건이 있는지도 원본에서 확인한다.

## 8. 당시 입력 복원과 정답 누출 방지

**반응 label을 확보했다고 그 사례를 과거 모델 재실행에 바로 쓸 수 있는 것은 아니다.**

결정 시각 `decision_at` 이전의 Profile + 전체 Brief + 당시 사용 가능한 Behavior + 역할/JD + 앞선 추천·연락 상태를 복원해야 한다. 일반 Worker의 실제 builder와 동일한 계약을 사용하고, Memory는 승인된 builder의 원천이지 downstream 모델에 대화 원문을 추가 주입하는 핑계로 쓰지 않는다.

| 입력 상태 | 사용 |
| --- | --- |
| 당시 원본 snapshot이나 검증된 버전 이력이 있음 | 정식 replay 가능 |
| 현재값이 결정 이전부터 변하지 않았음을 전체 필수 원본에서 입증 가능 | 검증한 provenance와 함께 replay 가능 |
| 일부 정보만 복원, 나머지는 이미 덮어써짐 | 불완전 입력 진단용으로만 사용. 동일 입력 비교 성과에서 제외 |
| 현재 Brief·Behavior에 평가 대상 추천의 답변이 포함됨 | 사용 금지 |
| 역할 설명·회사 기준이 사후 변경됐는데 당시 버전 없음 | 그 역할의 과거 fit replay 불가 |
| candidate pool snapshot 없음 | 전체 retrieval/rerank replay 불가. 알려진 pair의 제한된 선택 진단만 가능 |

이번 최근 run 1,511개는 `user_brief`가 모두 빈 객체다. `llmRawOutputs`에서 확인한 top-level key는 `finalDelivery`이며, 이것은 출력 보관이다. `behavior_context_version`, fingerprint, chars/count만으로 당시 원문이 보존됐다고 보지 않는다. 다른 보존 원본의 복원 가능성을 전수 검사한 뒤 replay 가능 건수를 확정한다. 충분하지 않으면 과거 세트는 반응 baseline에 쓰고 앞으로 input snapshot을 모은다.

새 정책용 Behavior를 과거 시점으로 생성해야 한다면 그 시점 이전 원천만 사용한다. 이전 정책이 실제 쓴 cache와 새 builder가 재생성한 입력이 다르다는 사실도 표시한다. target 답변·후속 질문·회사 반응을 제외하는 것뿐 아니라 다른 역할에서 **그 결정 이후** 발생한 사실도 제외한다.

## 9. 과거 데이터로 새 로직을 어떻게 비교하는가

첫 비교는 **실제로 전달했던 추천 중 무엇을 유지하거나 제외하는가**다. 모델에게 정답을 숨기고 새 fit와 해당 경로의 실제 rerank/전달 선택을 실행한다. 새 fit 점수만으로 추천했다고 간주하지 않는다.

`S`를 새 로직이 유지한 과거 전달 episode 집합이라 하면 다음을 계산한다.

| 값 | 계산 |
| --- | --- |
| 과거 긍정 보존율 | S에 남은 P / 과거 P 전체 |
| 과거 부정 제외율 | S에서 빠진 N / 과거 N 전체 |
| 과거 무응답 제외율 | S에서 빠진 I / 과거 I 전체 |
| 유지한 추천의 관측 긍정률 | S에 남은 P / label을 관측한 S |
| 유지량 | S / 과거 전달 전체 |

이 다섯 값을 항상 같이 본다. 1개만 남겨 100% 긍정률을 만드는 시스템은 좋은 결과가 아니다. 개발 세트에서 제안 목표를 **과거 P 90% 이상 보존하면서 N/I 제외를 늘리는 것**으로 두고, 잠금 평가에서도 목표를 유지하는지 확인한다. 이 수치는 향후 실험으로 진입할 판단 재료이며 production uplift 증명이 아니다.

예시로, 과거 1,000건이 P 300 / N 100 / I 600이고 새 로직이 남긴 600건이 P 270 / N 60 / I 270이면 관측 긍정 비중은 30%에서 45%로 높고 P 90%를 보존한다. **이는 과거 기록의 선택 결과**이지 새 메일·새 시점으로 보냈을 때 긍정률 45%가 된다는 예측은 아니다.

실제 새 policy가 고른 결과는 다음 네 그룹으로 나눠 공개한다.

| 기존 실제 전달 | 신규 선택 | 해석 |
| --- | --- | --- |
| O | O | 기존 전달 아래의 실제 반응 label 존재 |
| O | X | 기존 긍정 기회를 잃는지, N/I를 제외하는지 관찰 가능 |
| X | O | **반응 정답 없음**. 신규 발견 사례이며 온라인 평가 필요 |
| X | X | 반응 정답 없음 |

알려진 반응이 있는 사례만의 결과에는 항상 전체 신규 선택 중 그 비중을 붙인다. Unknown 신규 선택을 삭제한 뒤 그 비율을 전체 신규 정책 긍정률로 발표하지 않는다. 같은 사람에게 보내는 역할 묶음·순서·시점을 바꾸면 과거 반응 자체도 달라질 수 있다.

로그의 실제 선택 확률이 확인되지 않은 상태에서 score를 propensity로 대신 쓰거나 임의 IPS 보정을 하지 않는다. 무작위 logging과 관측된 행동의 지지가 필요한 offline replay 조건은 [Li 등의 원 논문](https://arxiv.org/abs/1003.5956)을 참고한다. 현재 기록만으로 그러한 조건을 충족했다고 확인하지 않았으므로 위 비교는 조건부 진단으로 제한한다.

## 10. 온라인 검증의 범위와 운영

우선 검증할 것은 **후보자에게 전달하는 내부 추천 정책**이다. 기존 정책과 새 role-first/온보딩 검색 → 공통 fit → rerank → 후보자 전달 정책을 비교한다. 이는 이번 요청의 추천 대비 후보자 반응을 직접 측정한다. 회사에 보여줄 후보자 제안 정책 자체의 인과 효과는 별도의 평가다.

| 결정 | 구체적인 계획 |
| --- | --- |
| 배정 단위 | 후보자 단위 고정 배정. 같은 후보자의 여러 역할·온보딩·주기 추천을 같은 arm에서 처리 |
| 대상 | 실험 시작 전 공통 조건으로 정의한 내부 추천 수신 가능 후보자와 신규 온보딩 완료자. 기존/신규 모델이 선택한 사람으로 대상을 정의하지 않음 |
| 배정 비율 | 기존/신규 1:1, 고정 seed. 온보딩 신규/기존, internal-only/외부 병행, 실험 이전 응답 이력에 따라 층화 |
| 대조 정책 | 실험 시점의 동작을 고정한 기존 선택·전달 정책. 오래된 5월 모델을 대조군으로 삼지 않음 |
| 실험 정책 | 새 retrieval·공통 fit·rerank·전달 정책. 정답을 보고 개별 후보자 arm을 이동하지 않음 |
| 공통 요소 | 같은 저장 UI, feedback 의미, 동의·testOnly 경계, 발송 인프라. 모든 production V2는 전체 Brief와 같은 version Behavior 계약 유지 |
| 처치 범위 | 새 후보자 추천의 선택·연락 시점·개수. 회사 제안 정책과 회사가 직접 요청한 실제 Intro 처리·문구는 이 1차 실험에서 공통으로 유지 |
| 외부 추천 | 양쪽 같은 정책. 내부 추천과 함께 보내는지·기존 연락량을 기록하여 차이 해석 |
| 캐시와 실행 | 두 정책의 model/prompt/input/policy fingerprint를 기록. 비호환 fit를 같은 cache key로 덮어쓰지 않음. Shadow는 발송·공유·fit 원장 변경 없음 |
| 후보자별 관찰 | 배정 후 28일의 추천 + 마지막 추천 후 14일 답변. 추천 0건도 후보자 분모에 포함 |
| 판정 | 표본 수·모델·prompt를 사전 고정. 중간에 p-value가 좋아진 날 임의 종료하지 않음 |

과거의 legacy/behavior 50:50 cohort를 되살리는 실험이 아니다. 달라지는 것은 matching 정책이며 Behavior 사용 계약은 양쪽 모두 지킨다.

Role-first가 여러 후보자를 비교하므로 같은 role의 슬롯 경쟁에 양쪽이 간섭할 수 있다. 후보자 측 제안의 공통 hard limit과 이미 진행 중인 요청은 양쪽에서 동일하게 적용하고, arm별 선택·제외와 역할별 포화도를 남긴다. 단순히 회사 제안 예산을 양쪽에 두 배로 배정하거나 후보자를 양쪽 회사 목록에 중복 공개하지 않는다. **고정된 회사 운영 아래 후보자 정책 효과**라는 해석 범위를 유지한다.

실행기는 후보자 arm을 선택 전에 읽고 해당 정책만 후보자용 추천 선택·전달을 commit하게 한다. 비교용 다른 정책은 shadow다. Role-run의 회사 제안 결과는 공통 회사 정책만 처리하고, 후보자용 결과를 내보낼 때에도 수신자 arm과 실행 policy가 일치해야 한다. 실제 회사 Intro와 직접 사용자 요청은 공통 예외 처리로 유지하고 별도 cohort에 기록한다. 이 제한 때문에 회사 제안 정책까지 포함한 전체 통합의 인과 효과를 입증했다고 말하지 않는다.

회사 제안까지 한꺼번에 바꾸고 싶다면 위 실험 결과를 전체 양면 시장 효과로 확대하지 않는다. Workspace 단위로 회사 제안 정책을 고정 배정하고 후보자에게 여러 회사가 교차 노출되는 간섭을 별도 분석해야 한다. 현재 10개 workspace의 최근 표본으로 작은 차이까지 판별할 수 있다고 약속하지 않는다. 이 단계는 충분한 회사 표본·노출 기록이 쌓인 뒤 별도 사전 등록한다.

실험군이 더 적은 후보자에게 추천했다는 이유로 그 후보자들을 모집단에서 제거하지 않는다. 배정 누락·정책 우회·로그 유실을 점검하고, 1:1 배정 비율 이상은 원인 확인 전 성과 해석을 멈춘다. [Microsoft의 SRM 원문](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/)처럼 **배정 모집단**과 **실제로 추천을 받은 사람 집합**을 구분한다. 추천 수가 1:1이 아닌 것 자체는 정책 효과일 수 있다.

## 11. 필요한 표본과 현재 트래픽

계획용으로 baseline P=31.5%, 양측 유의수준 5%, 검정력 80%, 독립적인 이항 표본·동일 arm 크기를 가정하면 다음 규모다. **31.5%는 정제 전 최근 원장값에서 얻은 계산 예시이며 확정 baseline이 아니다.**

| 감지할 긍정률 차이 | 한 arm의 추천 수 약 | 양쪽 합계 약 |
| --- | ---: | ---: |
| +10%p | 363 | 726 |
| +5%p | 1,408 | 2,816 |
| +3%p | 3,856 | 7,712 |

계산은 `n = (1.96 × sqrt(2p̄(1-p̄)) + 0.842 × sqrt(p0(1-p0)+p1(1-p1)))² / (p1-p0)²`의 두 비율 비교 근사다. 후보자당 반복 추천·역할 편중·추천량 감소와 긍정 기회 보존 gate까지 고려한 최종 표본 수는 더 클 수 있다.

표의 80%는 차이 0을 기각하는 통계적 검출에 관한 가정이다. 관측 효과 +5%p 이상, 긍정 기회 보존, 데이터 품질을 모두 만족하는 전체 제품 gate의 통과 확률을 80%라고 의미하지 않는다. 분모가 0인 cohort의 비율과 기존 P가 0인 경우의 새/기존 비율은 계산 불가로 표시한다.

최근 조사 구간은 44일간 원장 1,519행이다. 이 정도 속도가 유지돼도 2,816건을 새로 모으는 데 단순 계산 약 82일이 걸리고 답변 관찰 기간도 필요하다. 신규 정책이 추천 수를 줄이면 더 길어진다. 최근 며칠의 추천 급증을 장기 트래픽으로 가정하거나 “일주일 테스트로 +3%p를 입증한다”고 계획하지 않는다.

정제 후 후보자별 전체 episode를 보존한 resampling으로 주 비율과 후보자당 P의 표본 크기를 함께 산정한다. 최종 시작 전에 목표 표본·모집 종료일 상한을 고정한다. 제안 상한은 모집 12주이며, 후보자별 42일 관찰을 마친 뒤에도 검정력이 부족하면 확정 결론 없이 추정치와 구간을 보고한다. 통계적 성공과 실험을 끝낼 운영 시점을 구분한다.

## 12. Keep 기능 때문에 비교가 왜곡되지 않게 하는 방법

**추천 정책 실험에서는 양쪽에 같은 keep UI·도구·설명을 제공한다.** 저장 버튼은 별도 제품 변경이므로 새 정책 arm에만 넣지 않는다. 호환 계측과 저장 기능을 양쪽에 먼저 적용하고 기록을 확인한 뒤 추천 정책 비교를 시작한다.

- Keep을 P에 더해 긍정률이 올랐다고 하지 않는다.
- Keep 때문에 I가 줄면 “확인 여부가 더 잘 관측됐다”고 말한다. fit나 추천 정책 개선과 구분한다.
- 과거 이메일의 “저장”이 like로 처리되었을 가능성은 원문 audit에서 확인한다. 현재 label을 그대로 신형 P와 비교하지 않는다.
- 2 × 2 실험으로 정책과 keep을 동시에 분리 추정할 수도 있지만 현재 내부 추천량에서는 표본이 더 분산된다. 첫 실험은 두 arm만 둔다.
- 회사에 keep 상태를 공개하는지 등 개인정보 동작을 실험군별로 바꾸지 않는다.

## 13. 분리해서 볼 cohort

| 구분 | 분리 이유 |
| --- | --- |
| 온보딩 첫 추천 / 기존 후보자 주기 추천 | 첫 방문과 오래된 계정의 반응 가능성이 다름 |
| Internal-only / 외부 추천도 받는 후보자 | 접속·메일 습관과 접촉 빈도가 다름 |
| Harper가 먼저 추천 / 실제 회사 Intro | 실제 회사 관심을 전달하는 제안은 응답 동기가 다름 |
| 후보자 명시 요청 / 비요청 추천 | 이미 관심을 표시한 역할을 추천한 결과를 신규 발견 성과로 세지 않음 |
| 과거 28일 내 명시 반응 있음 / 노출은 있으나 없음 / 과거 노출 없음 | 기존 응답성 높은 사용자만 고르는지 확인. 배정 이전 정보만 사용 |
| 회사 직접 사용 / Harper 대행 | 추천 경로와 연락 방식이 다름 |
| Email 포함 / chat-only, 역할 수와 순서 | 노출 방식·선택 부담 차이 |
| workspace·role·주차 | 특정 인기 역할이나 한 주의 유입으로 전체 수치가 바뀌는지 확인 |

주 결과는 실제 정책 전체의 P/N/K/I 분포다. 사전에 정한 온보딩·수신설정·과거 응답성에 대해서만 공통 가중치로 보정한 결과를 추가한다. **정책이 바꾼 후의 추천 경로·노출량을 기준으로 사람을 제외하거나 주 효과를 보정하지 않는다.** 그것도 정책 효과의 일부다.

작은 cohort에는 건수와 넓은 불확실성을 보여주고 승자를 선언하지 않는다. 여러 cohort 중 좋아진 것만 골라 전체 성공이라고 하지 않는다.

## 14. 회사에게 추천한 후보자의 반응률

후보자 반응과 별도의 표로 유지한다. 기본 단위는 workspace × role × talent의 회사 제안 episode다. 같은 회사의 여러 팀원이 보거나 Slack과 web에 함께 표시돼도 하나다.

| 회사 측 label | 기준 |
| --- | --- |
| P | 회사가 명시적으로 Intro/진행을 요청 |
| N | 회사가 해당 제안을 명시적으로 pass/거절 |
| I | 제안 전달 후 14일간 명시 선택 없음 |
| U | 전달·결정의 시각 또는 출처 불명 |

준비만 된 `ready` 행과 실제 공개·알림 시각을 구분한다. Privacy 철회, role 마감, 이미 후보자가 수락해서 route가 교체된 자동 closure는 N이 아니다. 후보자에게 보낸 추천 수와 회사에 보낸 후보자 제안 수를 합쳐 하나의 반응률을 만들지 않는다.

현재 Intro 원장만으로는 이 표의 충분한 성숙 표본을 만들 수 없다. 기존 회사 표시·알림·활동 이력을 더 연결해 coverage를 확인하고, 신규 run의 회사 공개 시각과 제안 ID 연결을 남겨 축적한다. 이번 후보자 정책 실험만으로 회사 반응 개선까지 입증했다고 하지 않는다.

## 15. 구현할 평가 도구와 최소 계측

2026-10-07 로컬 runner에 `inventory`, `capture`, `label`, `report`를 구현했다. 과거 gold 동결과 production 정책 replay는 아직 구현·실행 완료가 아니다. 실제 입력 snapshot이 없는 사례를 현재 프로필로 재실행하지 않는다.

| 산출물 | 구현 위치와 책임 |
| --- | --- |
| Canonical 평가 runner | `harper_worker/llm_evals/recommendation_feedback_outcomes/eval.py` |
| `inventory` | 읽기 전용 전수 집계, 전달/label/input coverage·제외 사유 산출 |
| `capture` | 실제 전달 ID·역할 링크·정형 feedback 사건과 run 입력 존재 여부를 private에 보존. canonical `connect_read_only()`의 일관된 snapshot. 당시 전체 입력 복원은 별도 필요 |
| `label` | 구조화 사건 연결과 horizon 계산, 의미가 불명확한 사례의 검토 packet 작성 |
| `freeze` | 미구현. reviewer 확정 label, candidate split, input/output hash와 source provenance 동결 필요 |
| `replay` | 미구현. 복원 가능한 입력 확보 후 기존/신규 production 선택 경로를 직접 import하고 저장·발송 차단 필요 |
| `report` | 비식별 P/N/K/I/U, 보존/제외, 후보자 단위 구간, cohort별 결과 |

계측은 기존 durable fact를 활용하며 평가를 위한 대화 판단 table을 만들지 않는다.

1. Delivery payload에 **최종 실제 포함 recommendation ID**, policy/experiment version, 후보자 arm, 메시지 묶음·순서를 보존한다. 이미 있는 ID는 재사용한다.
2. 기존 feedback writer에서 `talent_progress`에 이전/새 값, 후보자 명시 반응인지 시스템 작업인지, source message/tool invocation, server 시각을 기록한다. Keep 계획의 일반 feedback event와 통합하고 별도 중복 원장을 만들지 않는다.
3. Run trace에 결정에 실제 쓴 input snapshot 또는 복구 가능한 immutable version locator와 hash를 남긴다. Hash나 버전 번호만 있고 원문이 덮어써지는 구조는 replay를 해결하지 못한다.
4. 이미 처리한 feedback/tool 재시도는 같은 event identity로 중복 제거한다. legacy mirror도 같은 사건으로 합친다.
5. 실험 seed·공통 수신 가능 조건·배정 시각의 후보자 roster는 private manifest로 동결한다. 추천이 0건이어도 분석에 남아야 한다. 기존 실험 배정 기능을 재사용할 수 있는지 구현 시 확인하고, 재구성 가능한 배정만을 위해 새 제품 table을 만들지 않는다.

Snapshot과 feedback provenance는 일시적인 LLM 판단이 아니라 **그때 실제로 알고 있던 입력과 실제로 일어난 사용자 행동**이다. Reader는 replay runner와 outcome report다. 원문은 접근 제한된 기존 trace/storage에 보관하고 만료·삭제 정책을 따르며, 후보자/회사 기본 context에 평가 원본을 추가로 주입하지 않는다.

현재 runner는 모델 호출을 하지 않는다. 명시 출처가 없는 feedback은 U이며, 기록의 완전성을 검토하지 않은 구간을 I로 확정하지 않는다. episode 중복 여부 미검토 행은 분모 밖에서 별도 건수로 남긴다. Keep 해제 후에도 관찰된 keep 사실을 유지하고, 14일 내 첫 P/N와 최신 결정을 함께 제공한다. `report`는 후보자 단위 고정 seed bootstrap 구간과 U 포함 긍정률 하한·상한을 출력한다. `--selected`는 실행된 정책의 추천 ID 목록을 비교하는 입력이며 새 정책의 실제 선택을 생성하거나 인과 효과를 증명하지 않는다.

```sh
cd harper_worker
venv/bin/python llm_evals/recommendation_feedback_outcomes/eval.py inventory \
  --output ../harper_beta/docs/evaluation/recommendation-feedback-outcomes/runs/inventory-<run>.json
# capture: --from / --until / --cutoff는 timezone 포함, --exclude-talents는
# reviewer와 talentIds를 가진 검토된 fixture 제외 파일. 원문 출력은 registry private/runs만 허용.
# label: --input capture.json [--review coverage-review.json] --output private/labels-<run>.json
# report: --input private/labels-<run>.json [--selected private/policy-selection.json] --output reports/<run>.json
```

동일 출력 파일을 덮어쓰지 않으며 private 결과는 0600이다. 과거 cutoff로 capture하더라도 원장의 포함 대상은 현재 추천 행의 `recommended_at`이므로 당시 상태가 복원됐다고 해석하지 않는다. 실행 전 source·출처·중복·horizon 계약의 합성 회귀 8개를 통과했다. 운영 gold는 여전히 미동결이다.

## 16. 동결과 실행 계약

현재 `datasetVersion`과 `goldVersion`은 **미동결**이다. `outcomes-v1`, `replay-v1`은 향후 첫 동결의 이름이며 빈 gold를 만들어 완료로 표시하지 않는다.

| 파일 | 담을 내용 |
| --- | --- |
| `gold-outcomes-v1.json` | 비식별 case ref, 7/14/28일 label, source confidence, 검토 이력 |
| `manifest-outcomes-v1.json` | 실제 capture 시각, cutoff, 포함/제외·cohort 분포, split seed의 식별자, source revision·dirty hash, 파일 hash |
| `manifest-replay-v1.json` | outcome ref와 as-of input 완전성, 각 input의 source 시각·snapshot/version, 실행 가능한 policy 범위 |
| `private/` | UUID 연결, 실제 프로필/대화/회사 자료·input packet·enrollment roster. Git 제외, 디렉터리 0700/파일 0600 |
| `runs/` | 모델 raw input/output, provider usage·실패·run manifest. Git 제외, owner-only |
| `reports/` | 비식별 집계와 한계만 |

동일 dataset에 model/prompt만 바꾸면 새 run을 만든다. 입력·label·포함 기준이 바뀌면 새 dataset/gold 버전이며 변경 이유·reviewer·시각을 남긴다. 잠금 평가 결과를 본 뒤 정책을 수정하면 그 평가 세트는 이후 개발 이력으로 취급하고 독립 confirmatory 세트를 새로 확보한다.

모델 실행 시 manifest에 단계별 실제 model/provider/endpoint/reasoning/temperature/seed 지원 여부, token cap, timeout/retry/fallback, source commit+dirty diff hash, prompt·builder·normalizer fingerprint를 기록한다. 모델 이름을 이 문서의 오래된 추정으로 고정하지 않고 비교할 release 설정에서 읽는다. 실패 case를 조용히 제거하지 않고 실패·관측 반응을 함께 보고한다.

원문 외부 전송은 실행 전에 승인된 provider·endpoint·data handling 범위를 문서화한다. 이번 작업은 production metadata/비식별 집계 조회만 했으며 모델에 원본 평가 fixture를 보내지 않았다. 계획 수립은 온라인 추천 실험·발송·배포 승인을 포함하지 않는다.
