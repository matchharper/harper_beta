# Harper Career에서 구현할 핵심 변경

2026-11-13. [제품 목적](career-value-and-agent-direction-ko.md)과 [30개 시나리오](career-value-scenarios-ko.md)를 실제 구현 결정으로 압축한다. 5차 검토에서 화면의 대안을 비교하고 기회·선택적 묶음·후속 작업의 관계를 좁혔다. 아래는 제안하는 제품·개발 결정이며 운영에 적용된 기능을 뜻하지 않는다.

## 우리가 만들려는 서비스

Harper는 사용자가 원하는 커리어와 삶을 이해하고, 더 좋은 선택지를 발견하고, 그 선택을 실제로 얻도록 일한다. 사용자가 모르는 회사와 역할, 생각하지 못한 접근, 현재 직장 안에서 가능한 변화도 발견할 수 있어야 한다. 좋은 선택의 기준은 그 사람에게 돌아오는 보상·동료·평판·성장·다음 경력·생활의 가치다. 회사가 그 사람을 필요로 한다는 사실은 접근의 근거이며, 그곳에 가야 할 이유를 대신하지 않는다.

질문·조사·추천·자료 작성·연락·지원·협상·대기는 그 목적을 위한 수단이다. 사용자가 정답인 행동을 먼저 지시하지 않아도 Harper가 필요한 일을 찾아 수행하고 결과를 보고 이어가야 한다. 화면도 그 일을 판단하고 맡기기 좋은 형태로 구성한다. 단순한 문서 수정은 곧바로 끝낼 수 있어야 하며, 모든 요청을 커리어 전략 수립으로 확대하지 않는다.

제품은 원본 LLM의 판단에 필요한 맥락·지식·도구를 제공한다. 이미 조사한 회사, 이미 설명한 경험, 이미 실행한 일은 다시 쓸 수 있게 만든다. 사람이 읽을 원문과 새로운 가능성은 계속 열어 둔다. 정해진 채용 퍼널이나 전 직군의 공통 점수가 이 판단을 대신하지 않는다.

**우리가 줄일 것은 매번 자료·근거·화면·실행 상태를 새로 만드는 비용이다. 사용자가 무엇을 원하고 어떤 선택이 좋은지를 생각할 여지는 남긴다.** 코드가 처리할 반복과 LLM이 판단할 문제를 이 경계에서 나눈다.

## 제품에서 바꿀 것

### 기회를 사용자가 검토할 선택지로 만든다

기회의 단위는 ‘이 회사의 이 팀에서 다음 역할을 탐색해볼 만하다’처럼 사용자가 검토하거나 맡길 수 있는 선택지다. 공고가 있으면 연결하고, 없으면 회사·팀과 역할의 가능성에서 시작한다. 왜 이 사용자에게 좋은지, 확인한 근거, 가능한 다음 행동을 함께 연결한다. 기회라는 이름이 실제 채용 수요나 자리의 존재를 보장하지는 않는다.

회사·담당자·행사를 찾았다고 항상 세 개의 추천 카드를 만들지 않는다. 같은 회사에서 좋은 역할을 얻기 위한 담당자 연락과 행사 참석이라면 하나의 기회 안에 접근 방법으로 연결할 수 있다. 여러 회사에 공통으로 유용한 행사나 그 자체로 의미 있는 만남은 독립적으로 제안할 수 있다. 이 구분은 대상 종류별 규칙이 아니라 현재 사용자 목적에 따른 agent의 판단이다. 결과적으로 카드 개수를 늘리는 대신 왜 검토할 가치가 있는지를 분명하게 만든다.

### 추천과 내 기회를 나누되 추천은 시간순 피드로 만들지 않는다

기회 화면의 두 영역은 `추천`과 `내 기회`로 정한다. 추천은 Harper가 현재 검토할 가치가 있다고 제안하는 선택지, 내 기회는 사용자가 저장했거나 실제로 이어서 진행하도록 맡긴 선택지다. 상세를 열거나 단순 질문을 했다는 이유만으로 내 기회에 넣지 않는다. 기존 대화에서 직접 지원을 맡겨도 같은 내 기회로 연결하며 추천 화면부터 거치게 하지 않는다.

두 영역을 구분하는 이유는 ‘더 좋은 대안을 찾는 일’과 ‘이미 선택한 일을 놓치지 않고 이어가는 일’의 정렬 기준이 다르기 때문이다. 최신 추천이 회신해야 할 연락을 밀어내거나, 진행 기록이 발견 화면을 채우지 않게 한다. 저장만 한 것과 진행 중인 것은 내 기회의 필터/상태로 구분하고 별도 최상위 탭을 계속 추가하지 않는다.

추천의 기본 순서는 agent가 현재 사용자에게 먼저 검토할 가치가 있다고 판단한 순서다. 생성 날짜와 내부/외부 공고 구분을 기본 우선순위로 쓰지 않는다. 새로 찾은 사실은 같은 기회를 갱신할 수 있고, 지난주 제안도 여전히 좋다면 앞에 남을 수 있다. 같은 목표·근거가 유지되면 방문할 때마다 다시 평가해 순서를 바꾸지 않는다.

### 추천은 기회를 바로 보여 주고 묶음은 필요할 때만 쓴다

기본 화면은 우선순위가 있는 기회 목록이다. 기회가 하나면 하나를 보여주면 된다. 함께 봐야 선택하기 좋은 결과가 있으면 agent가 제목·설명을 붙여 같은 화면에서 묶을 수 있다. 묶음 관리 화면을 만들거나, 모든 기회에 view 소속을 요구하거나, view를 먼저 클릭해야 기회가 보이는 구조로 만들지 않는다.

넓은 시장을 보고 싶은 경우에는 별도의 탐색 목록을 같은 화면에서 펼쳐 볼 수 있게 한다. 이 목록은 미평가 회사 500개도 담을 수 있으며 추천을 모두 받았다는 뜻은 아니다. 검색/matching run을 연결하면 서버가 항목·필터·페이지를 제공한다. agent는 먼저 보여줄 대상이나 묶음만 정하고 모든 ID를 다시 출력하지 않는다. 기회 목록과 탐색 목록은 같은 항목 renderer와 상세를 재사용한다.

첫 구현에서 필요한 표현은 우선순위·선택적 그룹·밀도 조절·목록/표·상세 내용의 순서다. 화면 전체를 매번 생성하는 범용 page builder는 만들지 않는다. 실제 사용 사례에서 새로운 표현이 판단이나 수행을 개선할 때 해당 컴포넌트를 추가한다.

### 상세는 같은 장소에서 이유를 이해하고 다음 행동을 맡기는 곳으로 만든다

카드에는 대상과 제안, 지금 검토할 중요한 이유가 보인다. 누르면 데스크톱에서는 기존 작업 영역에 상세가 열리고 모바일에서는 같은 내용을 전체 화면으로 연다. 목록의 필터·스크롤·선택은 돌아왔을 때 유지한다.

상세 본문은 출처를 붙일 수 있는 설명과 기존 목록·자료·작업 컴포넌트로 구성한다. 보상, 실제 팀과 동료, 다음 경력, 회사의 사업 기반, 접근할 사람 중 무엇을 먼저 읽어야 하는지는 agent가 정한다. 조사한 내용을 기본 JD 화면 뒤에 숨기지 않는다. 추천 이유와 미확인 조건을 읽고 원문으로 들어갈 수 있어야 하며, 모든 기회에 동일한 항목을 채우도록 요구하지 않는다.

주요 버튼은 그 시점에 사용자가 Harper에게 맡길 만한 다음 행동 하나다. `지원 진행하기`, `연락 초안 준비하기`, `소개 요청 준비하기`처럼 실제 효과가 드러나게 한다. 보조 동작은 저장과 관심 없음이며, 질문은 선택한 기회를 표시한 기존 대화 입력창에서 한다. 새로운 기회마다 고립된 채팅방을 만들지 않는다.

클릭은 정확한 기회와 당시 보인 제안·행동을 원본 agent에게 전달한다. 이미 준 설명을 다시 묻지 않고 그 요청을 수행한다. 단순 자료 읽기와 이후에도 책임지고 진행할 위임은 구분하며, 실제 발송·제출은 기존 권한과 실행 계약을 따른다. 작업이 시작되면 같은 위치에서 진행이나 필요한 답변을 보여준다. 상대를 기다리는 동안 억지로 새로운 행동 버튼을 만들지 않는다.

추천 전에 Harper가 할 수 있고 판단에 필요한 기본 조사는 수행한다. 이미 가능한 조사를 ‘더 알아보기’ 버튼으로 넘겨 사용자가 요청해야만 진행되게 하지 않는다. 사용자 선택이나 비공개 접근이 실제로 필요한 다음 행동은 별도로 제안할 수 있다.

### 내 기회에는 현재 상황과 필요한 다음 행동을 남긴다

목록에서는 어떤 기회인지, 지금 어디까지 진행됐는지, 사용자가 할 일이 있는지를 읽는다. 사용자 답변이나 결정이 필요한 것은 찾아보기 쉽게 하고, 각 기회 안에 실제 작업·자료·연락 결과를 연결한다. 이것은 채용 단계를 칸으로 고정한 보드나 모든 내부 작업을 늘어놓은 목록일 필요가 없다.

바로 진행할 수 있으면 추가 준비 없이 진행한다. 집중할 기회에는 필요한 경험 조사·이력서 수정·접근 준비를 선택적으로 붙인다. 사용자에게 맡길 일, Harper가 하는 일, 상대 응답을 기다리는 일을 구분한다. 여러 기회에 쓰는 작업과 자료는 공동 참조하고, 특정 기회의 중단이 다른 기회에 필요한 작업을 취소하지 않게 한다.

### 이해와 조사는 다음 실행의 출발점으로 남긴다

비공개 경험 자료, 공개 회사 근거, 이 사용자를 위한 작업 메모를 기존 문서·Memory와 조사 기록에서 구분해 관리한다. agent가 무엇을 남기고 합칠지 판단하고, 실제 조사 범위와 원문 refs를 연결한다. 다음 지원·정기 탐색에서는 이전 자료와 작업 메모를 찾아 달라진 정보와 남은 질문부터 처리한다.

현재 탐색 기준은 추천 화면에서 열어 확인·수정할 수 있게 한다. 사용자 조건은 Brief, Harper가 채택한 방향과 가설은 연결된 설명에서 구분한다. 모든 사용자에게 전략 문서 작성을 먼저 요구하지 않는다. 기존 검색·조사·문서·실행 도구의 온보딩/Role 의존 제한도 실제 필요한 경계만 남겨, 이런 능력이 첫 요청부터 쓰이게 한다.

## 결론으로 남긴 여섯 변경

| 번호 | 구현할 것 | 완료됐을 때 달라지는 동작 |
| --- | --- | --- |
| 1 | 비공개 경험 자료의 검색·갱신·재사용과 원본 연결 | 메일에서 발견한 경험을 공개 Profile과 분리해 보존하고 다음 지원에서 재사용하며, 현재 탐색 기준도 이어 읽음 |
| 2 | 열린 검색과 Role에 종속되지 않는 사용자별 기회 | 내부 공고 없이도 회사를 발견하고, 추천·관심·자료·후속 작업이 같은 기회를 계속 가리킴 |
| 3 | 공개 조사 근거 재사용과 agent가 관리하는 작업 기록 | 같은 사실 수집뿐 아니라 같은 목적의 검색·검토도 반복하지 않고, 달라진 부분만 조사 |
| 4 | 우선순위 있는 기회 목록과 선택적 묶음, 근거·행동이 연결된 상세 | 기회를 바로 검토하고, 필요하면 검색 ID로 큰 집합을 탐색하며, 같은 상세에서 다음 일을 맡김 |
| 5 | 기회에 연결되는 선택적 할 일과 기존 백그라운드 실행 연결 | 필요한 준비만 제안·수행하고, 여러 지원의 공통 작업을 재사용하며 실제 완료·대기에서 이어감 |
| 6 | 검색·읽기 가능한 방법 자료와 사례 재실행을 묶은 개선 경로 | 모르는 접근을 실제로 읽어 사용할 수 있고, 잘못된 판단은 재현 가능한 개발 변경으로 고침 |

여섯 항목은 실행 순서가 아니다. 새 검색이 필요 없는 오퍼 비교는 1·4·5로 시작할 수 있고, 그 분야의 판단 지식이 부족할 때 6을 읽을 수 있다. 이미 조건이 분명한 지원은 기존 executor로 바로 진행할 수 있다.

## 1. 사용자 자료의 원본을 연결하고 필요한 부분을 바로 읽게 한다

### 결정

새로운 거대 프로필이나 매번 생성하는 전략 요약을 만들지 않는다. 기존 runtime은 이미 문서·프로필·작업 등의 색인을 제공한다. 여기에 **문서 내용 검색과 실제 경험 원본으로 이동하는 연결**을 추가한다. 기존 Profile·경력별 메모·Brief·Memory·Documents·실행 기록은 계속 원본이다.

색인에는 무엇에 관한 자료인지, 원본 ref와 revision, 원본/작성 결과의 관계, 현재 사용자가 선택한 대표 자료를 표시한다. 현재 Brief와 최근 정정, 진행 중 맡긴 일의 실제 결과는 기본 맥락으로 주고, 긴 문서와 세부 경험은 해당 ref로 읽는다. 문서의 설명·제목·본문 검색과 Profile의 경력 연결을 함께 사용할 수 있게 한다. 매번 별도 LLM이 전체 자료를 재요약하는 과정은 넣지 않는다.

### 실제로 만들어야 하는 부분

현재 기본 문서 색인은 파일명·종류·revision·primary 여부 중심이고, 목록 도구는 최신순 페이지를 제공한다. 이를 확장해 문서 설명을 활용하고 제목·본문으로 필요한 자료를 찾을 수 있게 한다. Profile의 특정 경력 메모와 이를 설명하는 프로젝트 문서, 그 문서를 사용한 이력서가 서로 연결될 수 있도록 문서 metadata의 쓰기·읽기 계약에 `source_refs`와 사용한 revision을 추가한다. 새 글을 쓸 때는 모델이 선택한 실제 원본 ref를 전달한다. 원본이 바뀌면 그 자료로 작성된 문서가 어떤 이전 사실에 기대고 있는지 읽을 수 있다. 기존 자료의 일괄 재요약·이관은 시작 조건으로 두지 않는다.

사용자가 장애 대응 경험을 자세히 설명했다면 그 내용과 공유 범위에 맞는 기존 Memory나 비공개 Documents에 보존한다. 이미 적절한 범위의 원본이 있으면 별도 복사본을 만들지 않는다. 경력 행과 연결할 수 있다는 이유로 Profile에 공개 가능한 내용이라고 간주하지 않는다. 나중에 이력서·소개 메일·면접 답변을 만들 때 이 원본을 읽고 외부에 전달할 내용을 별도로 작성한다. 생성된 이력서의 문장을 다시 경력 사실의 원본으로 취급하지 않는다. 기존 primary resume는 대표 이력서이며 모든 실제 경험을 담은 유일한 원본은 아니다.

사용자가 정한 현재 조건과 전제는 기존 Brief를 수정한다. Harper가 채택한 탐색 방향과 아직 확인하지 못한 가설은 사용자 선호와 구분한다. 계속되는 탐색에서 이어 읽고 사용자와 조정할 가치가 있으면 기존 비공개 문서에 그 방향·이유·미확인 사항을 적고 Brief 및 작업에 연결한다. 사용자가 계획 문서를 먼저 요청해야만 가능한 기능은 아니다. 모든 검색의 선행 문서나 일시적인 내부 추론을 저장하는 별도 strategy 테이블도 만들지 않는다.

이미 사용자에게 전달한 추천 이유·비교·선택과 맡긴 일의 결론도 기존 view·문서·메시지·실행 결과에서 읽는다. 해당 결과가 사용한 Brief와 자료의 revision을 연결해, 새 요청에서 무엇이 달라졌는지 확인할 수 있게 한다. 어제 같은 회사를 검토해 보상 때문에 제외했고 새 정보나 목표 변화가 없다면 그 결과를 출발점으로 삼는다. 오늘 목표나 보상 근거가 바뀌었다면 그 차이를 판단한다. 내부의 모든 생각을 저장하거나 과거 거절을 영구 제외 규칙으로 만드는 방식은 아니다.

### 왜 필요한가

사용자가 충분히 말한 연봉 기대와 원하는 회사 수준은 다음 검색에서도 읽혀야 한다. ‘경험이 맞는다’는 정보만 쉽게 회수되면 다시 잘못된 추천으로 돌아간다. 문서 작성에서는 반복적인 원문 탐색과 과거 버전의 혼용을 줄인다. 원본과 파생 자료의 관계를 보존하면 정정된 성과 수치가 예전 이력서에서 되살아나는 문제도 다룰 수 있다.

Memory importance는 이미 있다. 이것을 새로 만들거나 중요도 숫자로 모든 읽기를 대체하지 않는다. 새 구현의 중심은 **어떤 정보가 어디에 있고 어떤 원본으로 돌아가야 하는지**다. 일반 agent가 이미 가진 revision 기반 read cache도 재사용한다.

### ML Engineer의 경험을 FDE 지원에 다시 사용하는 예

현재 메일 경력 가져오기는 채용·지원·면접 등의 내역을 검색해 회사별 Memory를 만드는 경로다. 이 기능이 있다고 고객 요구 조율·현장 배포·장애 대응 같은 실제 업무 경험의 목적별 조사가 해결된 것은 아니다. 새로운 FDE 전용 extractor를 만드는 대신 기존 Gmail의 허용된 검색·thread 읽기를 원본 agent가 현재 정보 부족에 맞춰 사용할 수 있게 한다.

처음 지원할 때 Harper는 현재 자료에서 찾지 못한 경험을 메일과 연결 문서에서 찾는다. 발견한 기여·상황·성과와 이를 뒷받침하는 원문 ref를 비공개 경험 문서에 정리한다. 문서 이름과 묶음의 크기는 agent가 정한다. 한 경험을 FDE·Solutions Engineer·면접용으로 각각 복사하지 않고 같은 경험을 여러 결과물이 참조할 수 있게 한다. 짧은 사실은 기존 Memory로 충분하고, 원문과 맥락이 긴 경우 Documents를 사용한다.

나중에 다시 조사할 일을 줄이려면 결과만 저장해서는 부족하다. 메일 조회 도구는 실제 질의·조회 시점·대상 계정·읽은 기간과 thread refs·페이지가 남았는지 등의 실행 사실을 반환하고 해당 실행 ref를 남긴다. agent는 재사용에 필요한 조사 범위와 빈칸을 경험 문서 또는 연결된 작업 메모에 보존한다. 이 내용은 업무 경험의 의미를 강제하는 schema가 아니라 실제 조회 범위를 다시 확인할 수 있는 연결이다.

다음 FDE 지원에서는 관련 경험 문서를 먼저 찾고 재사용한다. 최근 활동이 필요하면 이전에 다룬 범위 이후를 확인한다. 새 공고가 이전에 찾지 않았던 역량을 요구하면 과거 기간도 다른 질의로 탐색할 수 있다. 마지막 조회 날짜가 있다고 모든 과거 경험을 조사했다고 간주하지 않는다. 조회한 계정에 없는 회사 메일·삭제된 자료·검색으로 발견하지 못한 경험도 있을 수 있으므로, 중요한 빈칸만 사용자에게 구체적으로 물을 수 있다.

비공개 저장과 공개는 서로 다른 쓰기다. 이 조사로 Profile이 자동 수정되거나 원본 메일이 지원 자료에 통째로 붙지 않는다. 문서 읽기·화면·외부 공유 writer에서 실제 접근 범위와 위임을 지킨다. 단순한 `is_public=false` 저장 하나로 충분하다고 보지 않고, 기존 공개 문서 경로가 이 비공개 자료를 포함하지 않는지 구현 시 확인한다.

### 현재 탐색 방향을 사용자가 확인하고 고칠 수 있게 하기

지속 탐색을 맡겼을 때는 ‘지금은 보상과 다음 경력의 선택지를 넓힐 수 있는 회사·팀을 우선 찾고, 특정 경험은 접근할 근거로 사용한다’처럼 현재 방향을 읽을 수 있어야 한다. 4번 화면에서 Brief와 연결 문서를 열거나 관련 부분을 보여 주고, 사용자의 정정은 원본 agent가 해당 원본에 반영한다. 모델의 가설이 사용자가 확인한 선호로 바뀌어 저장되지 않게 한다.

다음 정기 실행도 이 원본과 관련 조사 기록을 읽는다. 방향이 바뀌지 않았으면 새 전략 보고서를 다시 쓰지 않는다. 조건이 달라지면 관련 결론을 재검토하되 모든 회사의 공개 정보까지 다시 수집하지 않는다. 이것이 ‘현재 무엇을 기준으로 일하는지’의 지속성이지, 매 단계의 생각을 기록하는 시스템은 아니다.

## 2. 검색은 대상을 찾고 판단은 원본 agent가 한다

### 결정

미평가 대상을 반환하는 공통 검색 계약을 만든다. 질의와 실제 필터, 조회할 정보원을 받아 대상의 안정적인 ref, 간단한 설명, 출처와 확인 시점, 다음 페이지를 반환한다. 사용자 적합도 점수나 추천 목록 등록은 요구하지 않는다.

첫 adapter는 `company_db`의 공개 회사 정보, 접근 가능한 공개 Role, 공개 범위가 확인된 사람 정보, 외부 웹이다. 업종·지역·제품 설명과 같은 기존 필드와 검색 가능한 텍스트를 사용한다. 외부 결과는 URL만 있어도 읽고 화면에 넣을 수 있다. 내부 회사나 Role을 먼저 만들도록 강제하지 않는다. provider의 검색 결과 순위는 검색 편의를 위한 것이며 사용자의 추천 순위와 다르다.

### 실제로 만들어야 하는 부분

현재 이름과 LinkedIn URL로 workspace를 찾는 `search_companies`에서 넓은 회사 발견을 분리한다. 회사 원본의 텍스트 검색·필터와 외부 검색 adapter를 같은 결과 계약으로 제공한다. 현재 공고 검색 executor에서 후보 조회와 개인 평가가 결합된 경로는 분리해 조회 결과를 그대로 읽을 수 있게 한다. 기존의 검색+평가 묶음은 그 방식이 편리한 경우 선택할 수 있게 남기되 모든 탐색의 문턱으로 두지 않는다.

검색 결과의 종류는 회사·사람·공고만으로 닫지 않는다. 정형 adapter가 없는 교육기관·행사·작품·프로그램도 외부 URL과 설명, 출처로 시작할 수 있다. 정확한 객체가 필요한 기존 지원·팔로우·소개 executor를 호출할 때 해당 adapter로 연결한다. 사용자별 추천 문장을 저장하려고 가짜 Role을 만들지 않는다.

500개를 보고 싶으면 검색 집합을 서버에서 유지하고 페이지·필터·정렬로 탐색한다. 원본 LLM은 전체 500개 전문과 평가를 한 번에 받지 않는다. 집합 요약과 필요한 페이지를 읽고, 상세 조사는 중요한 대상에 집중할 수 있다. 저장 가능한 검색·matching run은 4번 view에서 그 ref를 직접 연결하고, 다시 읽을 원본 집합이 없는 결과는 서버가 view items로 일괄 저장할 수 있게 한다. 일시적인 provider cursor만 영구 집합 식별자로 쓰지 않는다. 별도 후보 집합 테이블을 다시 만들지 않는다. 단, 값싼 1차 검색이 누락한 유력 후보를 회복할 다른 질의·정보원과 직접 URL 입력은 열어 둔다.

### 사용자별 기회를 Role과 화면에서 독립시킨다

검색 결과의 URL을 화면에 넣을 수 있다는 것만으로는 부족하다. 공고 없는 회사에 대한 관심, 그 회사에 접근할 자료와 할 일, 다음 실행의 결과가 같은 대상을 계속 가리켜야 한다. 이를 위해 `talent_opportunities`를 사용자별로 계속 다룰 기회의 식별 단위로 제안한다. 새 durable 사실은 ‘이 사용자가 이 대상과 목적을 하나의 기회로 다루고 있다’는 관계다. reader는 기회 상세, 저장·관심 처리, 할 일, 후속 실행과 view resolver다.

기회는 사용자 소유 ID, 대상 refs, 사람이 읽을 제목·설명, 관련 자료·추천 설명의 ref와 revision을 갖는다. 대상은 기존 Role일 수도, 회사나 외부 URL일 수도 있다. Role은 필수가 아니다. 공개 회사 사실은 회사 원본에 남고, 같은 회사라도 지역 조직·역할·접근 목적이 다르면 agent가 별개의 기회로 관리할 수 있다. 이름이나 회사 ID 하나로 모두 합치지 않는다.

기회의 추천 순서와 설명은 view가 없어도 읽을 수 있어야 한다. 연결된 사람·행사·자료는 독립 기회가 될 수도, 이 기회를 얻는 데 쓰는 근거나 접근 방법일 수도 있다. 모든 외부 대상을 자동으로 하나씩 추천 관계로 만드는 변환은 두지 않는다.

기존 Role 추천·관심·지원 상태는 adapter를 통해 이 기회에서 읽는다. 전환 과정에서 같은 상태를 새 테이블과 기존 테이블에 따로 쓰지 않는다. 공고 없는 기회에는 개인의 관심·보류 등 실제 선택을 저장할 수 있고, 실제 연락·지원의 성공 여부는 해당 executor 기록에서 읽는다. 나중에 정식 공고를 발견하면 같은 기회에 Role ref를 연결해 이전 자료와 작업을 유지한다.

넓게 보여 주는 모든 회사가 개인 추천이나 추적 중인 기회가 되는 것은 아니다. 원본 검색 결과만으로 표시할 수 있고, 사용자가 저장하거나 Harper가 추천·진행 대상으로 유지할 때 해당 관계를 만든다. 면접 연습·문서 수정 등 독립 요청에 기회 생성도 강제하지 않는다.

### 무엇을 보장하지 않는가

설명 필드가 비어 있는 회사에 인덱스만 붙여도 좋은 회사 검색이 되지는 않는다. 넓은 내부 원본과 외부 발견을 함께 쓰고, 알려진 유력 후보가 검색되는지 개발 중 확인한다. candid에 이메일이 있다는 이유로 모든 사용자에게 연락처가 공개되거나 소개 관계가 생기는 것도 아니다. 해당 정보원의 실제 이용 범위 안에서 adapter를 노출한다.

핵심 변화는 ‘핀테크 경험과 일치하는 공고’만 찾던 경로에서, **그 사람이 가고 싶은 수준의 회사와 역할을 찾고 접근 방법을 생각할 수 있는 경로**가 생기는 것이다.

## 3. 회사 보고서 생성보다 재사용할 조사 근거를 만든다

### 결정

대상과 알고 싶은 질문, 요구되는 최신성, 사용할 수 있는 정보원을 받는 조사 서비스를 만든다. 출력은 보고서가 아니라 **확인한 내용·근거·아직 모르는 부분·실제 수행 결과**다. 같은 공개 사실은 여러 사용자가 읽고, 개인에게 좋은 선택인지의 판단은 현재 사용자 맥락에서 한다.

예를 들어 ‘이 회사가 어떤 제품을 팔고 누가 기술 조직을 이끄는가’, ‘이 팀의 해당 레벨 공개 보상 범위가 있는가’를 묶어 요청할 수 있다. 기본 회사 정보가 없으면 제품·사업·주요 팀·최근 변화에 대한 공개 검색을 묶는 빠른 경로를 제공한다. 파운더 이력이 중요한 작은 회사와 부서별 차이가 큰 병원에 동일한 질문 세트를 강제하지 않는다. 모델이 원하는 질문을 추가하거나 원문을 직접 조사할 수 있다.

빠른 회사 조사도 홈페이지 소개를 요약하는 데서 끝내지 않는다. 회사가 좋은 선택인지 볼 때 쓸 수 있도록 제품·고객·사업 기반, 주요 리더와 실제 팀의 경력, 해당 시장에서의 평판을 뒷받침하는 구체적 기록, 역할·지역·레벨에 맞는 보상 근거를 요청할 수 있게 한다. ‘유명하다’, ‘뛰어난 동료가 있다’, ‘성장성이 높다’를 provider가 단정한 문장은 사실 필드가 아니다. 누가 어떤 일을 했는지, 어떤 고객·제품·실적이 있는지 같은 근거를 원본 모델이 읽고 판단한다. 공개 회사 정보만으로 알 수 없는 실제 상사·팀 분위기·역할 권한은 담당자나 신뢰할 만한 관계의 확인으로 이어간다.

자료마다 적용 대상을 보존한다. 미국 본사의 급여를 한국 지사의 해당 직급 보상으로 사용하거나, 병원 전체의 평판을 특정 부서의 근무환경으로 대체하지 않는다. 회사·팀·역할·지역·시점이 출처에서 확인되는 범위만 기록한다. 단순히 회사 ID가 같다는 이유로 이런 범위를 합치지 않는다.

### 이미 있는 것에서 무엇을 바꾸는가

`web_search`는 이미 Exa 구조화 응답과 출처를 받고 `documents`에 URL 원문을 저장한다. `company_snapshot`에도 공개 검색 bundle이 있다. 다만 현재 회사 조사 경로는 cache가 있어도 개인화된 보고서 작성으로 이어진다. 이를 분리한다. **조사 근거를 읽는 호출에서는 보고서를 다시 쓰는 LLM을 실행하지 않는다.** 개인화 설명과 추천은 그 자료를 읽은 원본 agent가 현재 목적에 맞게 작성한다. 사용자가 회사 보고서를 원할 때만 그 결과물을 별도로 만든다.

기존 원문 cache와 공개 snapshot을 조사 서비스의 입력으로 재사용한다. 추가할 `research_records`는 대상 ref, 질문/조사 범위의 자유 텍스트, 결과 본문, 원문 refs와 관측 시점, 실행 상태를 저장한다. 새 durable 사실은 ‘이 대상을 이 범위에서 조사했을 때 이 근거를 확인했다’다. reader는 조사 도구와 검색·화면 resolver다. 기존 cache를 모두 이관한 다음에야 사용할 수 있는 구조로 만들지 않고, 기존 snapshot도 adapter로 읽는다.

원문 cache는 현재 내용을 덮어쓸 수 있으므로 과거 조사 결과에 URL과 cache ID만 남기지 않는다. 결과에 사용한 원문의 content hash·관측 시점과 해당 판단을 뒷받침하는 발췌를 보존한다. 나중에 페이지가 바뀌어도 당시 무엇을 확인했는지 알 수 있다. 공개 근거는 응답 언어가 다르다는 이유로 다시 수집하지 않고, 사용자에게 설명하는 언어는 원본 agent가 정한다.

### 한 요청이 처리되는 방식

1. 대상의 정확한 식별과 접근 범위를 확인하고, 요청한 내용에 관련된 기존 공개 근거와 개인 자료를 찾는다. 공유 가능한 원문과 개인의 질의·대화는 섞어 저장하지 않는다.
2. 이미 있는 내용과 확인 시점을 반환하거나, 아직 필요한 질문에 대한 수집을 수행한다. 같은 URL을 가져오는 작업과 정확히 같은 공개 조사 요청은 서버가 중복 실행을 합친다. 의미가 비슷한 질문을 같은 것으로 간주해 결과를 강제로 재사용하지 않는다.
3. 검색할 때 내용과 출처를 함께 받고, URL을 이미 아는 경우에는 여러 URL의 내용을 묶어 받는다. 서로 독립적인 수집은 병렬로 처리한다. provider 호출 횟수와 읽힌 원문 양, LLM 비용을 각각 기록한다.
4. 결과에는 출처 URL과 원문 ref, 조회 시점과 내용을 남긴다. 추출·요약은 source에 대한 해석임을 보존한다. 확인되지 않은 보상·담당자·채용 수요는 빈칸으로 남는다. 네트워크 실패를 ‘없음’으로 저장하지 않는다.
5. 오래된 부분이나 충돌하는 출처가 판단을 바꾸면 그 부분을 다시 확인한다. 더 깊은 조사가 필요하면 이어 실행할 수 있으며 원문 읽기·일반 웹 검색도 계속 사용할 수 있다.

서버의 중복 합치기는 실제 실행 계약이다. 공개 대상·요청 범위·최신성·provider 계약이 같은 수집에 대해 DB의 원자적 claim과 만료되는 실행 lease를 사용하고, 진행 중이면 같은 결과 ref를 돌려준다. 실패한 실행을 영구 cache hit로 처리하지 않는다. 개인 작업의 취소는 그 사용자에게 이어지는 행동을 중단하며, 다른 작업도 사용하는 공개 근거를 삭제하지 않는다. 의미적으로 비슷한 기존 조사 결과는 모델이 읽고 충분한지 판단한다.

공개 회사 identity와 기본 설명을 정리할 필요가 있으면 `company_db`를 조회·생성·수정하는 서버 adapter를 제공한다. 동일 회사 판별에는 기존 ID, 공식 URL 등 실제 식별 근거를 사용하고 애매하면 외부 ref 상태로 둘 수 있다. 회사 workspace의 소유권이나 비공개 hiring brief를 수정하는 권한은 포함하지 않는다. 공용 사실에는 출처를 붙이고 개인에게 적합하다는 판단과 개인 메일의 내용은 넣지 않는다.

### 비용을 줄이는 구체적인 이유

사용자 A를 위해 회사 X의 제품과 기술 책임자를 찾았다면 B는 그 공개 근거를 읽는 것으로 시작한다. B의 질문이 보상이라면 그 빈칸에 조사비를 쓴다. 같은 사용자가 다음 날 같은 목적을 이어갈 때는 이전 조사와 실제 진행을 읽고 중요한 변화만 확인한다. 모든 회사의 보고서를 매번 다시 쓰지 않으므로 작성 비용도 줄어든다.

Exa Search는 내용과 구조화 응답을 함께 받을 수 있고 Contents는 여러 URL의 내용을 한 요청으로 받는다. 구조화 응답은 추출 비용을 줄일 수 있지만 사실의 정확성을 보장하지 않는다. API 요청 한 번이 내부 검색 한 번이나 무료 전체 조사라는 뜻도 아니다. 실제 provider 응답의 비용과 결과 범위를 기록한다. [Exa Search](https://exa.ai/docs/reference/search), [Exa Contents](https://exa.ai/docs/reference/get-contents)

공유 cache는 공개 수집에만 사용한다. 사용자 이름·현재 보상·비공개 관계가 담긴 조사 요청과 개인화 결과는 개인 범위에 남긴다. query hash는 익명화가 아니다. 최신성도 회사 전체에 동일한 유효기간을 주기보다 필요한 사실과 현재 결정에 맞춰 요구한다.

`research_records`의 공유 범위와 소유자는 서버가 source의 접근 범위로 검증한다. 공개 조사 adapter는 개인 원문을 입력으로 받지 않고 공개 대상과 질문만 처리한다. 개인 자료를 포함한 조사 결과는 개인 소유로 저장한다. 공개 페이지의 원문은 기존 `documents`에 둘 수 있지만, 개인 자료와 섞은 요약을 그곳에 넣지 않는다. 자료를 삭제하거나 연결 권한을 철회하면 해당 원본과 파생 결과의 이후 조회에도 반영한다.

### 공개 사실 cache와 agent의 작업 메모는 다른 문제를 해결한다

‘카카오의 회사 소개를 다시 가져오지 않음’과 ‘사흘 전과 같은 목적의 검색 100번을 다시 하지 않음’은 다르다. 전자는 근거 cache가 해결하지만 후자는 **무엇을 위해 어디까지 조사했고, 어떤 결론과 미확인 사항이 남았는지** 회수할 수 있어야 해결된다. 기존 설계의 실행 기록 읽기만으로는 agent가 재사용할 중요 내용을 관리하는 방법이 불충분했다.

별도 저널 테이블 대신 기존 비공개 Documents를 일반 작업 메모로 읽고 쓰고 검색하게 한다. 회사·기회·검색 run·정기 작업 refs를 문서에 연결한다. 모델은 일반 문서 도구로 메모를 만들고 수정·통합·삭제하며 무엇을 남길지, 얼마나 자세히 쓸지 정한다. 모든 검색 후 필수 양식을 작성시키거나 ‘제외 이유/재검색 날짜/전략 단계’ 같은 의미 필드를 의무화하지 않는다. 도구의 실제 실행 ref와 조회 시점은 시스템이 제공하고, 재사용할 의미는 agent가 기록한다.

예컨대 ‘이번 미국 원격 Senior 탐색에서 공식 채용 페이지와 특정 채널을 확인했고, 보상 근거가 없는 세 회사는 결론을 보류했다. A사는 해당 지역 근무를 지원하지 않는다고 확인했다’는 기록을 남길 수 있다. 다음 run은 제목·설명·관련 refs로 이 메모를 찾아 필요한 부분만 읽는다. 달라진 목적과 공개 근거, 지난 확인 범위를 보고 같은 검색을 생략할지 결정한다. 과거의 검색 실패나 일시적 비추천을 영구적인 제외 규칙으로 바꾸지 않는다.

검색 비용뿐 아니라 기록을 읽는 비용도 관리한다. 일반 context에는 관련 메모의 색인·revision과 진행 중인 일에 필요한 요지만 제공하고, 본문은 필요할 때 읽는다. agent가 쓸모없어진 내용을 줄이거나 합칠 수 있게 하되 원본 refs는 유지할 수 있게 한다. 요약을 매 run마다 전용 LLM으로 다시 생성하지 않는다. 정보가 바뀌지 않은 같은 목적의 run에서 메모를 실제로 찾아 불필요한 재조사를 줄이는지 개발 중 확인해야 하며, 저장 도구가 있다는 사실만으로 재사용을 보장하지 않는다.

여러 사용자에게 공유할 회사 조사 사실은 `research_records`와 회사 원본에, 이 사용자의 목표·관계·결론이 담긴 작업 메모는 개인 문서에 둔다. 다른 사용자는 공개 사실을 재사용할 수 있지만 개인에게 내린 결론과 비공개 메일 내용을 공유 cache에서 읽지는 않는다.

## 4. 공고 카드 대신 원본을 연결하는 결과 화면을 저장한다

### 결정

추천 목록과 기회 상세가 기본이며, 저장해 다시 사용할 묶음이 필요한 경우 `career_views`와 `career_view_items`를 사용한다. 여기서 view는 선택적인 결과 집합과 그 표시 설정이다. 첫 구현의 범용 페이지 생성 DSL이나 모든 기회의 필수 부모가 아니다. 전자는 묶음의 제목·연결한 결과 집합·표시 설정·revision을, 후자는 명시적으로 포함한 항목과 집합에 대한 개별 강조·주석·배치·숨김을 저장한다. 데이터는 사용자 소유이며 기존 회사·공고·문서·실행 사실을 복사해 새 원본으로 만들지 않는다. 같은 기회는 여러 묶음에 나타날 수 있고, 묶음에서 숨기거나 지워도 기회의 자료·진행 기록은 유지된다.

이 저장이 필요한 이유는 채팅 응답이 지나간 뒤에도 사용자가 고른 묶음과 비교, 주석, 대상 선택을 다시 사용할 수 있어야 하기 때문이다. 임시 내부 계획을 저장하려는 테이블이 아니다. 결과를 저장할 필요가 없는 짧은 답변은 일반 대화로 끝낸다.

### 구현할 화면 계약

LLM은 React 코드를 매번 작성하지 않고 검증된 컴포넌트의 구성과 내용·참조를 작성한다. 첫 catalog의 중심은 **기회를 함께 제시하는 그룹, 중요한 항목의 강조와 순서, 검색 집합을 탐색하는 목록, 근거를 읽는 상세, 필요한 작업과 자료**다. 비교표는 가능한 표현 중 하나다. 지도처럼 실제로 다른 판단을 돕는 표현은 같은 catalog에 추가한다. 항목별 강조 내용과 비교 열은 사용자 목적에 맞게 바꿀 수 있으며 공통 적합도 칸은 필수가 아니다.

서버 resolver는 접근 가능한 원본과 현재 상태를 읽고 화면용 데이터를 만든다. 500개 항목은 원본 집합이나 저장된 item을 페이지로 읽고 필터링한다. 모델이 전체 JSON을 다시 작성해 한 칸을 바꾸지 않도록 부분 수정과 revision 확인을 지원한다. 화면에 표시한 추천 이유는 그 사용자를 위한 설명이고, 실제 지원·발송·팔로우 상태는 기존 실행 원본을 읽는다.

사용자가 대상을 선택하면 기회 또는 검색 항목의 정확한 ref, 당시 보인 내용의 revision, 사용자 입력을 원본 agent에게 전달한다. 묶음에서 선택했다면 view ref도 함께 전달한다. ‘이 사람에게 연락하는 내용을 준비해줘’는 관련 자료와 상대를 읽는 후속 요청이 된다. 이미 위임된 실제 발송은 기존 executor로 수행하고, 새로운 공개·연락에 필요한 결정은 해당 내용으로 받는다. 화면에 버튼을 그렸다는 이유로 실행 권한이 생기지 않는다.

### 가능한 결과

미국 엔지니어에게는 회사별로 실제 보상 근거·팀·다음 경력의 차이를 앞에 둔 비교를, 간호사에게는 부서별 급여와 근무표를, 프리랜서에게는 고객·제안·지급의 진행을 보여줄 수 있다. 공고 없는 회사와 그 회사의 공고, 만나볼 사람, 준비한 문서를 함께 연결할 수도 있다. ‘새 기회’ 목록에 모두 섞어 넣는 것만이 유일한 표현은 아니다.

기존 recommendation membership·저장·지원·회사 연결 상태는 그대로 원본으로 사용한다. 새 view가 같은 지원 상태를 별도로 쓰지 않게 한다. 최초 전환은 기존 화면을 지우는 대규모 이관보다 새 ref를 표시할 renderer를 연결하고 기존 카드도 그 안에서 사용할 수 있게 하는 범위로 잡는다.

### 여러 기회를 한 번에 제시하고 추천의 무게를 구분한다

‘이 묶음 중 관심 가는 곳이 있는지 살펴보기’, ‘먼저 볼 회사’, ‘추가로 넓게 탐색할 회사’, ‘당장은 보류한 곳’ 같은 구성을 agent가 만들 수 있게 한다. 이런 이름을 고정 카테고리 enum으로 만들지는 않는다. 그룹의 설명·순서와 항목의 표시 우선순위를 저장하므로 새로 수집된 순서가 항상 화면 순서를 결정하지 않는다. 우선순위는 정렬용 값일 수 있지만 보편적인 적합도 점수나 합격 확률을 뜻하지 않는다.

묶음은 함께 볼 이유가 있을 때 만든다. 기본 추천 목록은 기회의 사용자별 표시 순서를 읽고, 묶음은 필요한 경우 그 안의 순서와 설명을 제공한다. 모든 기회를 먼저 그룹으로 분류하거나 매 실행마다 새 view를 작성하는 단계는 추가하지 않는다. 현재 `NewOpportunityList`의 내부/외부 분류와 추천 날짜 정렬은 이 사용자별 우선순위로 대체할 대상이다. 실제 사용자 응답이 필요한 진행은 내 기회의 작업 사실에서 따로 표시한다.

필요하면 기회에 ‘특히 추천하는 이유’나 추천 강도를 자유로운 설명으로 남긴다. 같은 화면에서 단순 탐색 대상과 검토 후 추천을 구분할 수 있어야 한다. 모든 후보에 추천 정도를 평가하는 호출을 요구하지 않는다. 사용자 관심·보류와 Harper의 추천, 화면에서의 숨김도 각각 의미가 다르며, 숨김 하나가 관심 없음이나 연락 취소로 처리되지 않게 한다.

사용자가 여러 기회를 선택하면 정확한 refs와 실제 요청이 한 번에 agent로 전달된다. 서버가 집합에서 선택한 항목을 해석하므로 모델이 같은 목록을 다시 출력할 필요가 없다. 선택 이후에도 요청이 단순 관심인지, 자료 준비인지, 실제 지원 위임인지 원문과 기존 권한에서 판단한다.

### 검색 ID로 집합을 연결하고 일부만 수정한다

현재 inline UI에도 `matchingId`와 선택적인 `runId` 참조가 있다. 결과 묶음 조회 자체를 새로 만들기보다 이를 일반 view의 데이터 연결로 확장한다. view writer는 개별 refs를 넣는 방식과 `matching/run/search result ref + filter/sort`로 연결하는 방식을 모두 받는다. LLM은 ‘이 검색 집합을 이 섹션에 연결하고 A와 B를 강조’라고 지정할 수 있고, 나머지 항목의 조회와 페이지 처리는 서버가 한다.

고정된 추천 묶음은 특정 run의 결과를 참조하고, 계속 갱신되는 탐색 목록은 저장된 집합의 최신 결과를 읽는 것으로 구분한다. 단순히 화면을 열었다고 외부 검색을 다시 실행하지 않는다. 새로운 검색은 agent나 실제 예약 작업이 수행한다. 원본이 일시적 provider 결과라면 그 응답을 가진 서버가 view items에 일괄 저장한다. 목록 전체를 tool result로 모델에 건넨 뒤 같은 ID들을 입력받는 왕복을 만들지 않는다.

집합에 연결한 view에서는 모든 항목을 중복 저장하지 않고 명시적 추가·강조·순서 변경·숨김만 item으로 저장한다. 원본 결과가 바뀌어도 사용자 조작은 대상 ref에 연결돼 유지된다. 사용자가 실제 선택한 항목은 그 시점의 view revision과 대상 ref로 해석한다. 자유 SQL이나 클라이언트가 보낸 임의 query를 실행하지 않고, 서버가 지원하는 집합 resolver와 접근 권한 안에서 처리한다.

### 상세 화면까지 조사 근거와 추천 이유를 이어 보낸다

회사에 대한 공개 근거와 사용자별 추천 설명은 역할이 다르다. 공개 조사에는 출처·시점·적용 지역/팀 등이 있고, 사용자별 설명에는 왜 이 기회가 현재 목표에 유리한지, 어떤 손실이나 미확인 조건이 있는지가 담긴다. 설명은 기회에 연결한 기존 문서 또는 기존 추천 내용에서 읽고, 사용한 Brief·경험·조사 refs와 revision을 함께 연결한다. view에만 복사해 두어 다른 화면에서 사라지게 하지 않는다.

목록에서는 판단에 중요한 차이를 먼저 보여 주고, 클릭하면 그 설명과 근거를 이어 읽게 한다. 실제로 확인한 성장·보상·팀·지역 확장·역할 수준 등이 현재 목적에 중요하면 JD 위에 올릴 수 있다. 정보 순서는 구성 가능한 섹션과 참조로 정하며, JD는 연결된 자료 중 하나다. 공고가 없으면 회사·팀·접근할 사람과 확인할 조건으로 같은 상세를 구성할 수 있다.

설득은 장점만 강조하는 일이 아니다. 예컨대 ‘다음 경력에 유리한 회사와 팀이지만 이 지역의 보상은 아직 확인하지 못했다’면 그 상태를 그대로 전달한다. 왜 좋은 회사인가와 사용자의 경험이 어떻게 도움이 되는가는 모두 설명할 수 있지만 후자로 전자를 대신하지 않는다. 매번 상세를 열 때 전체 조사를 다시 하거나 긴 개인 보고서를 재작성하지 않는다. 현재 사실을 읽어 표시하고, 중요한 조건 변화가 설명을 바꾸면 원본 agent가 관련 설명을 갱신한다.

## 5. 첫 대화부터 후속 실행까지 같은 목적과 원본으로 이어간다

### 결정

새 agent 프레임워크나 새 workflow 엔진을 만들지 않는다. 기존 Career runtime·work·schedule·Gmail·browser·외부 실행 영수증을 재사용한다. 바꿀 것은 **어떤 시점과 대상에서 그 능력을 사용할 수 있는지, 다시 실행될 때 무엇을 읽는지**다.

첫 대화에서도 실제 권한과 연결 상태에 맞는 능력을 사용할 수 있게 한다. 온보딩 완료 여부로 자료 읽기·회사 조사·일반 작업을 잠그는 분기를 제거한다. 다음 행동은 현재 사용자 요청과 확보된 사실로 선택한다. 프로필 제출이 필요한 실제 신청과 첫 탐색을 같은 문턱으로 다루지 않는다.

### 실제로 연결할 부분

대화, view의 선택, 외부 작업 완료, 사용자 답변, 예약 시간이 같은 원본 agent의 진입 사건이 된다. 재개 입력에는 현재 요청과 정정, 해당 작업의 사용자 원문·권한, 관련 자료 ref와 현재 revision, 실제 완료·실패·대기 사실을 제공한다. 모든 과거 대화와 계획을 매번 다시 넣지 않는다. 기존 작업과 동일한 목적이면 새 작업을 중복 생성하지 않고 기존 책임을 이어간다.

후속 작업이 독립 실행돼도 개인에게 좋은 선택인지의 기준은 사라지지 않아야 한다. ‘회사 X에 연락한다’만 넘기지 않고 현재의 명시적 목적·조건과 그 근거 ref를 읽게 한다. 상대가 낮은 레벨의 자리만 제안하면 회사의 수요를 충족하는 쪽으로 계속 진행하지 않고, 사용자의 다른 선택과 비교할 수 있어야 한다. 실행에 필요한 권한과 사용자 조건은 최신 원본에서 읽고, 예전 문서의 동의 문구로 새 행동을 허용하지 않는다.

연락 이후의 처리는 기존 이메일·일정 도구를 사용하되, 특정 면접 제목 검색만으로 모든 후속 상황을 발견했다고 가정하지 않는다. 실제 맡긴 대화의 Gmail thread ID와 마지막 확인 위치를 해당 작업·예약의 source refs에 연결한다. 첫 범위는 알려진 thread를 맡긴 일정에 확인하는 방식으로도 완결할 수 있다. 즉시 수신 이벤트가 필요해지면 해당 connector가 실제로 지원하는 webhook과 중복 방지를 붙여 같은 진입 사건으로 전달한다. 아직 구현하지 않은 상시 inbox 감시는 능력으로 표시하지 않는다.

현재 browser와 일부 guide의 지원 중심 목적, ‘공고 탐색 몇 회 후 이메일’ 같은 고정 전제는 원본에서 수정한다. 이메일 작성·브라우저·문서 도구가 이미 Role 없이 작동하는 부분은 다시 만들지 않는다. 실제 실행 대상에 URL이나 문서 ref를 사용할 수 있게 설명과 후속 입력까지 연결한다.

Gmail 연결과 업로드는 기존 기능을 이용한다. Notion 등 새 정보원이 실제로 필요하면 인증→허용된 검색/읽기→원본 ref→변경/연결 해제 처리까지 갖춘 adapter를 추가한다. connector를 만들기 전에는 파일·붙여넣기·사용자가 고른 내보내기로 진행할 수 있다. 연결 화면에서 돌아오면 원래 부탁한 일을 계속한다.

### 실행의 완결 기준

조사·초안·발송·답장·합의는 각각 실제 결과로 읽는다. 권한 범위 안에서 맡긴 일은 실행하고, 외부에서 아직 받지 못한 결과는 기다리거나 적절하게 후속 행동한다. 일률적인 연락 횟수나 팔로업 간격은 만들지 않는다. 사용자에게 필요한 결정과 변화만 보여주고 조사 내부 단계마다 승인을 요구하지 않는다.

진행이 길다는 이유만으로 독립 agent를 반드시 만들지 않는다. 기존 원본 agent가 처리할 수 있고 맥락을 유지하는 편이 유리하면 그대로 수행한다. 별도의 큰 조사나 독립 책임이 실제로 유리할 때만 기존 delegation을 사용한다.

### 기회에 연결하는 할 일은 실제 작업을 이어가기 위한 선택적 데이터다

기존 `career_action_items`는 홈에 보여 줄 선택 가능한 제안 카드이고, `manage_work`는 독립된 실행 책임을 맡기는 도구다. 둘 중 하나를 그대로 기회별 할 일 목록이라고 부를 수는 없다. 한 카드가 사라져도 맡긴 일은 남아야 하고, 아직 제안인 할 일이 자동으로 실행되면 안 된다.

`career_tasks`를 추가해 실제 제안하거나 맡은 일을 저장하는 것으로 설계를 보완한다. 사용자 소유 ID, 할 일의 제목·내용, 연결된 기회 refs, 담당 주체, 실제 진행 상태, 필요한 자료·입력·실행 refs를 갖는다. 연결 기회는 선택적이고 여러 개일 수 있다. 자유 본문으로 작업 내용을 표현하고, 실제 UI·executor가 소비하는 식별·담당·진행·관계만 구조화한다. 직무별 checklist나 이력서→연락→지원의 필수 단계는 만들지 않는다.

이 저장의 이유는 ‘누가 어떤 일을 제안/위임받았고 무엇이 남았는가’를 화면과 다음 실행이 함께 읽어야 하기 때문이다. 모델이 잠깐 고려했다가 버린 모든 계획을 저장하지 않는다. 실제 사용자에게 제안하거나 실행 책임으로 유지할 필요가 있을 때 만든다. 필요한 준비가 없으면 바로 기존 executor를 실행할 수 있고, 할 일 0개인 지원도 정상이다.

할 일의 진행과 외부 실행 결과는 구분한다. 제안·진행 중·입력 대기·완료·취소는 실제 업무 조작에 필요한 범위에서 관리하지만, 제출 완료·메일 발송·상대 답장은 기존 실행 원본에서 가져온다. 실행 ref가 연결된 할 일은 그 결과와 충돌하는 완료 상태를 임의로 쓰지 않는다. 사용자가 직접 끝낸 일은 사용자 확인을 근거로 기록한다. 재시도·동시 실행·중복 제출은 기존 executor의 실행 계약으로 처리한다.

할 일 하나마다 별도 agent를 띄우지 않는다. 같은 맥락으로 처리할 문서 수정과 초안 작성은 한 실행에서 여러 할 일을 진행할 수 있고, 길거나 별도의 맥락이 필요한 일만 기존 work에 맡긴다. 질문·외부 회신 때문에 멈췄다면 원본 form/thread와 실제 대기 상태를 연결한다. 답변이나 작업 완료가 오면 5번의 같은 재개 경로로 이어진다. TODO 목록을 정기적으로 전부 읽고 작업을 추측하는 별도 엔진은 만들지 않는다.

### 투자할 노력도 사용자 목적에 맞게 달라진다

‘이 다섯 곳에 현재 이력서로 간단히 지원’이라는 요청에는 쓸 수 있는 자료와 지원 경로를 확인해 그 범위에서 진행한다. 공통 자료를 다섯 번 만들거나 다섯 개의 장기 프로젝트를 자동 생성하지 않는다. 반대로 ‘이 한 곳은 꼭 가고 싶다’면 필요한 경험 조사·자료 개선·담당자 접근 등을 선택적으로 제안하고 맡은 부분을 수행할 수 있다. 같은 직무라는 이유로 준비량을 고정하지 않는다.

이력서 보강 한 건이 여러 지원에 쓰이면 동일 할 일을 여러 기회에 연결한다. 각 제출은 사용한 문서 revision을 따로 참조하므로 나중에 이력서를 수정해도 이미 제출한 내용을 덮어쓰지 않는다. 특정 기회를 중단하면 그 기회만을 위한 대기와 작업을 중단하고, 다른 지원에도 필요한 공통 작업을 함께 취소하지 않는다.

사용자에게는 Harper가 하는 일, 사용자가 답해 줄 내용, 상대를 기다리는 일이 구분돼 보인다. Harper가 조사하거나 작성할 수 있는 것을 사용자용 체크리스트로 떠넘기지 않는다. 홈의 action item은 이 할 일 중 사용자의 선택이나 답변이 필요한 것을 가리킬 수 있고, 기회 상세에서는 전체 진행과 관련 자료를 읽는다. 이벤트 탐색·소개 준비·면접 자료 등도 같은 계약으로 다룰 수 있다.

## 6. 방법을 배우는 경로를 읽을 자료와 재실행 도구로 구현한다

### 결정

‘좋은 커리어 방법을 배운다’를 런타임의 모호한 요구로 남기지 않는다. 기존 handbook loader에 **찾아서 읽을 수 있는 방법 참고자료**를 연결하고, 실제 실패를 그 자료·원본 지침·도구의 변경과 비교 실행으로 이어가는 개발 경로를 만든다. 새 전략 결정 agent나 정성적 답변을 막는 심사 agent는 만들지 않는다.

### 자료를 어떤 형태로 만드는가

방법 자료는 repository의 버전 관리되는 Markdown으로 둔다. 제목과 짧은 설명, 본문, 출처·확인 날짜를 가진다. 본문은 그 방법이 풀려는 문제, 실제 근거와 적용 맥락, 가능한 대안과 한계, 필요한 자료와 사용할 수 있는 능력을 설명한다. 특정 직군이면 반드시 수행할 절차나 정해진 답변 대본으로 만들지 않는다.

예를 들어 ‘공고가 없어도 중요한 역할을 논의하는 방법’ 자료는 회사의 수요를 찾는 법만 담지 않는다. 그 회사와 역할이 사용자에게 매력적인지, 대화에서 무엇을 알아내야 하는지, 기존 경험을 어떻게 접근 근거로 사용할 수 있는지를 실제 사례와 출처로 설명한다. ‘보상과 커리어를 비교하는 방법’, ‘현 조직에서 역할과 평가를 협의하는 방법’, ‘전문직의 이동 경로’도 필요한 지식을 제공할 수 있다. 이 제목들이 전체 Career를 나누는 enum은 아니다.

### 원본 모델에게 어떻게 도달하는가

기존 `load_handbook`의 고정 catalog만 기다리지 않는다. 자료가 적을 때는 기본 능력 안내에 짧은 catalog를 제공하고, 자료가 늘면 `find/read` 계약으로 본문과 제목을 검색하게 한다. 별도 vector DB부터 도입하지 않고 repository 자료로 만든 검색 색인을 사용한다. 자료를 찾는 데 자연어 질의를 쓸 수 있고, 모델은 필요한 본문만 읽는다. 기능 선택 전에 발견할 수 있어야 하므로 application 도구를 이미 선택한 뒤에만 이 지식이 들어가는 구조는 피한다.

모든 요청에서 자료를 반드시 읽게 하지 않는다. 다만 핵심 목적과 사용자 이익의 판단은 원본 지침에서 분명해야 한다. 자료가 있어도 읽지 않거나 잘못 적용하는 실패는 실제 모델 입력과 출력을 보고 catalog 설명·retrieval·원본 맥락을 고친다. 직업 키워드를 보고 특정 playbook을 강제하는 분기는 추가하지 않는다.

### 실패가 실제 제품 변경으로 이어지는 과정

1. 팀원이 검토할 실제 실패에서 사용자 요청과 관련 원본, 모델 입력, 사용한 자료 version, 도구 결과, 최종 출력과 실행 사실을 함께 남긴다. 기존 trace·평가 저장소를 사용하며 개인정보는 허용 범위와 비식별 원칙을 따른다.
2. 잘못된 목표 이해, 중요한 근거 부재, 모르는 방법, 실행 능력 부재를 구분한다. 각각 기존 Brief/입력 원본, 조사 adapter, 방법 본문, executor를 고친다. 전부 ‘더 잘 판단하라’는 prompt로 처리하지 않는다.
3. 방법 지식이 부족했다면 공식 자료·해당 분야 전문가·확인 가능한 사례로 내용을 보강한다. 팀원이 출처와 적용 범위를 검토해 repository에 반영한다. 실제 성공 사례도 당시 조건과 불확실성을 보존한다.
4. 같은 고정 입력으로 기존/변경안을 개발에서 실행한다. 변경 사례뿐 아니라 다른 답이 맞는 인접 사례를 함께 읽는다. 좋은 회사에 접근하는 제안이 생겼는지, 부적절한 이동을 권하지 않는지, 이미 자료가 충분한 요청에 불필요한 조사를 늘리지 않는지 확인한다.
5. 사용자가 얻는 선택과 수행이 개선된 변경을 배포 대상에 포함한다. 배포 후 관련 요청에서 실제 선택과 결과를 관찰해 다음 수정의 근거로 삼는다. 자동으로 방법 순위를 올리거나 모델이 공용 지침을 무검토 수정하게 하지 않는다.

개발용 replay는 현재 Career runtime을 호출하고 입력·도구 결과·사용자 출력·비용을 저장한다. mock 외부 결과를 사용한 판단 비교와 실제 adapter 연결 검증은 구분한다. 기존 평가 runner와 registry를 확장하고 별도 실시간 심사 서비스를 만들지 않는다.

### 이번 사용자 지적을 고치는 예

실패 입력에는 높은 보상과 좋은 회사에서의 글로벌 경력을 원하는 엔지니어를 둔다. 선택지에는 경력은 정확히 맞지만 조건이 나쁜 회사와, 업종은 달라도 더 좋은 회사·팀·보상 가능성이 있는 자리를 함께 둔다. 잘못된 결과가 과거 경험 일치만 강조했다면 해당 원본 판단 지침과 근거 제공을 수정한다. 사용자가 실제로 특정 분야의 일 자체를 우선하는 반대 사례도 함께 확인한다. ‘핀테크를 추천하지 말 것’이나 ‘항상 유명한 회사부터’라는 규칙을 만들지 않는다.

## 구현 범위에서 남기지 않는 것

모든 사용자의 전략 문서를 필수로 만들지 않는다. 직군별 workflow와 추천 score schema를 늘리지 않는다. 새 Memory 중요도, 새 URL 원문 cache, 새 장기 작업 엔진도 만들지 않는다. 공용 회사 사실과 사용자별 판단, 사용자 자료와 외부 실행 권한을 한 저장소 의미로 합치지 않는다.

자유로운 조사와 표현을 위해 임의 SQL·React·외부 코드를 매번 생성할 필요도 없다. 검색·읽기·조사·부분 수정·화면 구성·실행의 일반 계약으로 먼저 넓은 범위를 연다. 실제로 부족한 실행 능력과 표현이 나타나면 같은 구조에 adapter와 renderer를 더한다.

## 실제 개발 산출물과 첫 완결 범위

### 새로 만들거나 확장할 저장과 실행

| 산출물 | 저장하는 실제 사실 또는 수행할 일 | 실제 소비자 |

표의 다섯 새 테이블은 이 안에서 제안하는 저장 단위다. 앞선 세 테이블 안에 없던 사용자별 기회 관계와 실제 할 일을 4차 검토에서 추가했다. 기존 추천 관계를 일반화해 같은 계약을 충분히 제공할 수 있으면 `talent_opportunities`는 기존 테이블 확장으로 구현해도 된다. 중요한 것은 개수가 아니라 Role 없이도 동일한 기회·자료·작업을 이어 읽을 수 있는 계약이다. 일시적인 판단·전략·직군 단계용 테이블은 추가하지 않는다.

경험 원본·작업 메모·탐색 방향·추천 설명은 기존 Documents/Memory/Brief와 추천 내용을 의미에 맞게 재사용한다. 새 종류마다 별도 문서 테이블을 만들지 않는다. 사용자별 기회는 공개 회사 사실을, task는 외부 발송 상태를, view는 기회의 실제 진행을 복사해 경쟁하는 원본으로 만들지 않는다. source refs는 단순 링크만으로 끝나지 않고 관련 자료의 검색·상세 표시·재개 입력에서 실제로 사용한다.

검색 색인과 cache는 원본에서 다시 만들 수 있는 파생 데이터다. 기존 테이블을 수정할 때 현재 reader와의 호환을 유지하고, 새 테이블은 실제 사용할 서버·사용자별 권한을 명시한다. Supabase Data API grant와 RLS는 서로 다른 경계이므로 필요한 권한을 migration에 함께 담는다. [Supabase 권한 계약](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically)

Vercel의 TypeScript API는 검색·읽기·부분 수정과 작업 접수를 처리하고, 오래 걸리는 수집과 외부 실행은 기존 비동기 runtime에 둔다. 기존 Exa client와 모델 API를 재사용한다. DB는 Supabase의 기존 원본과 위 저장·색인을 담당한다. 새 프레임워크, 별도 graph DB, 별도 vector SaaS가 이 설계의 선행 조건은 아니다. 다국어 검색과 의미 검색의 품질은 실제 자료로 비교하고 필요한 검색 색인만 추가한다. PostgreSQL은 텍스트 검색의 기본 기반을 제공하지만 그것만으로 검색 품질이 완성되는 것은 아니다. [Supabase 텍스트 검색](https://supabase.com/docs/guides/database/full-text-search)

### 무엇부터 구현하면 사용자 가치가 생기는가

첫 묶음은 **좋은 회사의 실제 기회를 발견해 사용자가 선택하고 다음 행동을 맡길 수 있는 경험**까지 연결한다. 회사 검색 endpoint만 만들거나 자유로운 view만 띄우고 끝내지 않는다.

- 충분한 자료를 가진 첫 방문 사용자가 추가 온보딩 없이 시작한다. 현재보다 좋은 회사를 찾되 업종 일치만으로 추천하지 않는다.
- 내부 Role이 없는 회사도 찾아 중요한 공개 근거를 읽는다. 과거의 공개 조사는 재사용하고 부족한 사실을 조사한다.
- 사용자에게 먼저 볼 이유가 있는 기회 묶음을 제시한다. 순서·그룹·상세 근거를 보고 고른 대상과 실제 요청을 원본 agent가 받아, 소개·지원·조건 확인 등 필요한 일만 준비하고 맡긴 범위에서 수행한다. 필요한 경우 기회에 할 일과 자료를 연결한다.
- 다음 실행에서는 실제 결과와 기존 자료를 읽어 이어간다. 사용자가 보상 기대를 바꾸면 공개 회사 조사는 그대로 쓰되 개인의 판단은 바뀔 수 있어야 한다.

이 묶음과 함께 **자료가 충분한 내일 면접 준비**를 대조한다. 검색·새 view·전략 문서를 만들 필요 없이 기존 자료를 읽고 실제 준비가 끝나야 한다. 이것이 성립하지 않으면 새 기반이 또 하나의 고정 퍼널이 된 것이다.

첫 묶음에는 필요한 원본 연결과 작은 renderer, 관련 방법 자료만 완성한다. 모든 개인 자료의 자동 구조화나 모든 서비스 connector, 전 직군의 지식 구축을 선행하지 않는다. 이어서 동일 사용자 경험의 다음 지원 재사용, 검색 ID를 통한 큰 집합 탐색, 동시 공개 조사 재사용을 확인하며 같은 구현의 범위를 넓힌다.

### 효율 때문에 받아들이는 제한

| 선택 | 얻는 것 | 남기는 자유와 실제 대가 |
| --- | --- | --- |
| 핵심 판단은 원본 모델, 사실 수집은 검색·묶음 추출 | 반복적인 탐색·전문 재독해·보고서 재생성을 줄임 | provider 요약이 놓칠 수 있으므로 원문·추가 질문·직접 조사 유지 |
| 미평가 검색과 필요 부분의 상세 조사 | 큰 시장을 저렴하게 다룸 | 앞단 검색의 누락 위험은 다른 질의·정보원과 개발 비교로 확인 |
| 공개 근거를 공유하고 개인 판단은 현재 맥락에서 수행 | 사용자 수가 늘어도 동일 수집을 반복하지 않음 | 개인화 판단 비용은 남음. 이것까지 공용 추천 점수로 대체하지 않음 |
| 검증된 컴포넌트 조합으로 UI 생성 | 접근성·모바일·조작 안정성·개발 비용을 관리 | 임의의 모든 UI를 즉시 만들 수는 없음. 필요한 renderer를 추가할 수 있음 |
| 중요한 실제 사건과 구체 예약으로 재개 | 이유 없는 전체 사용자 재조사와 알림을 줄임 | 즉시 이벤트 adapter가 없는 정보는 다음 확인까지 지연될 수 있음 |
| 방법 지식은 검토된 파일과 개발 replay로 개선 | 잘못된 한 사례가 전체 정책으로 자동 확산되는 일을 줄임 | 전문가 지식과 팀원의 검토 비용은 필요함 |

최적화의 비교 단위는 API 호출 수 하나가 아니다. 같은 목적에서 중요한 선택지와 근거를 유지했는지 먼저 보고, 사용자에게 첫 유용한 결과가 오는 시간·전체 소요·모델과 SaaS 비용·다시 요구한 입력·실제 완료한 일을 함께 비교한다. 아직 이 안의 절감률과 추천 개선율은 측정하지 않았다.

## 검토 기록

### 1차 검토 기존 구현과 중복되는 신설 항목 제거

초안은 도구 잠금 제거, 열린 검색, 조사 서비스, 결과 화면, 사용자 정본, 지속 실행, 방법 개선의 일곱 후보였다. 코드를 대조한 뒤 다음을 수정했다.

- Memory 중요도와 검색은 이미 있으므로 새 중요도 저장을 제외했다. Profile·Documents와 경쟁하는 사용자 정본 대신 자료 색인과 원본 연결로 바꿨다.
- Exa 구조화 응답과 URL 원문 cache가 이미 있으므로 신설 대상으로 잡지 않았다. 공유 `company_snapshot`도 확인해 기존 근거를 읽는 adapter로 재사용하도록 바꿨다.
- work·schedule·외부 실행 기록이 있으므로 새 지속 실행 엔진을 제외했다. 온보딩 해제와 같은 runtime의 첫 실행·후속 입력 연결을 하나의 변경으로 합쳤다.
- Role 조회+평가와 Role 중심 UI가 실제로 남아 있어 검색 분리와 결과 화면은 유지했다.

이 결과 여섯 변경으로 정리했다. 다음 검토에서는 시나리오 누락과 비용·운영 반례를 대입한다.

### 3차 검토 새 구조를 하나씩 빼고 비용과 실제 실행을 다시 확인

세 번째 검토에서는 여섯 이름이 그럴듯한 분류에 그치지 않는지, 이미 있는 기능을 다시 만드는지, 하나를 빼도 같은 결과가 나는지를 확인했다.

| 빼 본 변경 | 그대로 남는 구체적인 문제 | 최종 판단 |
| --- | --- | --- |
| 1 자료 내용 검색과 원본 연결 | 문서가 많을 때 파일명·최신순만으로 경험을 찾고, 작성한 이력서들을 다시 읽으며 정정 전 사실을 섞을 수 있음 | 유지하되 기존 resource index 확장으로 축소. 새 사용자 정본과 전체 자료 이관은 제외 |
| 2 미평가 열린 검색 | 외부 웹으로 일부 회사를 찾을 수는 있어도 내부 자산을 넓게 검색하거나 큰 집합을 평가 비용 없이 다루기 어려움 | 유지. 기존 검색+평가는 선택 가능한 빠른 경로로 재사용 |
| 3 질문별 조사와 재사용 | 원문 cache가 있어도 관련 조사 결과를 찾기 어렵고, 회사 조회가 새 개인화 보고서 생성으로 이어짐 | 유지. 기존 URL cache·snapshot을 읽고 필요한 수집만 보강 |
| 4 저장 가능한 결과 화면 | 좋은 조사를 채팅으로 설명할 수 있지만 큰 집합·비교·선택·후속 작업을 지속적으로 조작하기 어려움 | 유지. 기존 카드와 상태는 재사용하고 임의 UI 코드 생성은 제외 |
| 5 같은 실행으로의 연결 | 첫 방문의 도구 잠금과 좁은 후속 입력이 남아 새 능력을 필요한 때 쓰지 못함 | 유지. 새 runtime은 제외하고 실제 분기·입력·참조 연결을 수정 |
| 6 방법 자료와 재실행 | 도구가 있어도 잘못된 접근을 반복할 수 있고 실패가 어떤 입력·지식·능력의 수정으로 이어졌는지 확인하기 어려움 | 유지. 무제한 자동 학습·새 심사 agent·직군별 workflow는 제외 |

여기서 추가로 수정한 내용은 다음과 같다.

- 기존 `readCareerAgentResourceContext`가 문서·프로필 색인을 이미 제공한다는 것을 확인했다. 1번의 ‘공통 색인 신설’을 없애고 실제로 빠진 내용 검색과 source 관계로 범위를 좁혔다.
- 검색용 후보 집합과 view item을 별도 저장하는 중복을 없앴다. 당시에는 다시 사용할 집합을 view items로 저장하도록 정했다. 4차 검토에서 기존 matching/run 집합은 복사하지 않고 직접 참조하고, 영구 원본이 없는 결과에만 서버 일괄 저장을 사용하도록 보완했다.
- 기존 URL cache가 원문을 갱신하므로 과거 출처를 ID 하나로 참조하면 당시 근거가 달라질 수 있다. 조사 결과가 실제 사용한 시점·hash·발췌를 보존하도록 바꿨다.
- 같은 공개 조사에 대한 동시 요청이 실제로 합쳐지도록 원자적 claim과 실행 lease, 실패·취소의 범위를 명시했다. ‘캐싱한다’는 표현만으로 동시 중복 수집이 해결된다고 보지 않았다.
- Exa 한 요청, 500개 검색, 방법 자료 추가를 각각 저비용·검색 완전성·좋은 판단의 보장으로 해석하지 않도록 완료 기준을 바꿨다. 비용·품질은 실제 입력과 출력, 실행 결과로 비교한다.

### 4차 검토 사용자가 명시한 요구를 저장·조회·화면·재개까지 대조

‘넓은 방향에 들어 있다’는 답으로 충분하지 않아 각 요구가 다음 사용에서도 실제로 작동하는지 다시 대조했다. 아래의 기존 설계 평가는 이번 보완 이전 기준이다.

| 요구 | 기존 설계의 포함 수준과 빈칸 | 이번에 확정한 보완 |

추가로 세 반례를 대입했다. 첫째, 메일에서 FDE 경험을 찾은 뒤 다른 지원을 하면 새 문서가 아니라 같은 경험 원본이 읽혀야 한다. 둘째, 검색 결과 500개를 보여 주기 위해 모델이 500개 ID를 다시 출력하거나 전부 추천 관계로 만들어서는 안 된다. 셋째, 다섯 곳의 간단 지원을 한 곳의 집중 준비와 같은 할 일 묶음으로 만들면 안 된다. 이 반례 때문에 비공개 자료의 재사용, 집합 ref, 선택적인 task 생성과 공통 작업 연결을 각각 명시했다.

이 검토에서는 기존 Gmail 경력 가져오기의 채용 이력 중심 질의, inline UI의 matching/run 참조, action items의 표시 전용 계약과 work의 실행 계약을 로컬 코드에서 확인했다. 새 저장 구조나 실제 사용자 흐름을 구현·실행한 결과는 아니다.

### 5차 검토 두 탭과 view를 전제로 삼지 않고 제품 대안을 비교

단일 기회, 큰 미평가 집합, 직접 위임, 단순 질문, 실제 지속 업무가 같은 계약으로 다뤄지는지 확인했다. 이 과정에서 ‘메인 버튼을 누르면 무조건 내 기회로 이동’이라는 앞선 설명을 수정했다. 버튼은 표시된 요청을 수행하며, 내 기회에 남기는 것은 저장 또는 이어서 책임질 위임의 의미가 있을 때다. 단순 질문도 실제 조사가 필요할 수 있지만 그것이 자동으로 채용 진행이나 모니터링 위임을 뜻하지는 않는다.

#### 셋째 대조 첫 구현에서 덜어낼 것을 고른다

새 기회 목록 전체를 view로 바꾸는 작업, 대상 종류별 탭, 기회마다 별도 대화방, 범용 page builder, 공통 지원 checklist는 첫 구현에서 제외한다. 기존의 일반 문서·검색·조사·실행 능력을 연결하면서, 사용자별 기회 식별과 표시 우선순위, 선택적인 집합 연결, 근거·자료·다음 행동이 있는 상세, 필요한 할 일의 실행 연결에 집중한다.

첫 사용자 흐름은 ‘좋은 선택지를 발견 → 사용자가 이유를 이해 → 필요한 일을 맡김 → 같은 기회에서 결과 확인’이다. 전용 전략 문서나 view 작성, todo 생성이 이 흐름의 의무 단계가 되면 범위를 다시 줄인다. 이후 표현 확장은 예쁜 화면의 다양성보다 실제로 더 나은 선택이나 실행이 가능해지는지를 기준으로 추가한다.

이 검토는 제품 대안과 코드 계약의 비교다. 실제 사용자 실험으로 이 UI가 최선임을 입증한 결과는 아니다. 기존 구현을 선택한 구조로 바꿨다는 주장도 아니다.

| 모든 일을 SQL·브라우저·임의 UI 생성으로 해결 | 고정 capability가 적음 | 반복되는 데이터 접근·식별·권한·동시 수정·UI 동작을 매번 재구성하는 비용이 큼. 필요한 일반 능력만 안정적으로 제공 |
| 전략 agent→조사 agent→평가 agent→작성 agent | 책임이 나뉘어 관리하기 쉬워 보임 | 사용자 맥락이 전달 중 줄고 판단·보고서가 중복될 수 있음. 독립 작업이 필요한 경우에만 기존 delegation 사용 |
| 모든 회사의 상세 정보를 미리 완성 | 실행 중 조사 시간이 작아 보임 | 대부분 사용하지 않는 정보 수집·갱신 비용이 크고 사용자별 중요한 빈칸은 여전히 남음. 찾은 대상의 재사용 가능한 공개 사실부터 축적 |
| 직군별 성공 workflow를 늘림 | 알고 있는 사례의 결과가 빨리 나옴 | 새로운 목적·업계·사용자 조건에 같은 절차를 적용하기 쉬움. 방법은 자료로 읽고 실행은 일반 도구로 수행 |

이 비교에서 선택한 단순함은 테이블이나 함수가 무조건 가장 적다는 뜻이 아니다. **새로운 사용자 상황이 와도 기존 원본·검색·조사·화면·실행·방법 자료로 처리할 수 있고, 반복되는 일에는 비용을 다시 내지 않는 구조**를 뜻한다. 여섯 변경으로 30개 사례의 공통 실행 기반을 만들 수 있지만, 그 자체가 30개 모두의 판단과 실제 결과를 검증한 것은 아니다.

## 완료로 판단할 때 볼 것

이 문서의 다섯 차례 검토는 코드 대조와 설계 검토다. 제품 코드·DB를 바꾸거나 새 안으로 모델을 실행한 검증은 하지 않았다. 구현 완료는 아래와 같은 실제 경험과 근거로 판단한다.

- 원하는 보상·회사·팀·다음 경력이 읽힌 상태에서, 경험만 맞고 조건이 나쁜 회사를 좋은 기회로 추천하지 않는지 전체 모델 입력과 출력을 읽는다.
- 내부에 없고 Role도 없는 대상을 발견·조사·표현하고, 사용자가 고른 정확한 대상의 후속 일을 실제 executor까지 이어가는지 확인한다.
- 준비된 자료만으로 끝낼 요청에 불필요한 조사·질문·전략 문서·view를 추가하지 않는지 확인한다.
- 같은 회사의 같은 공개 질문을 여러 사용자가 요청하면 수집과 보고서 생성이 어떻게 달라지는지 관측한다. 새 질문·오래된 근거·변경된 사용자 조건에서 필요한 갱신은 여전히 일어나야 한다.
- 500개 탐색의 페이지·필터·선택·부분 수정이 실제 화면에서 작동하고, 새 상태와 이전 표시가 혼동되지 않는지 확인한다.
- 같은 검색 집합을 표시할 때 모델이 모든 ID를 다시 나열하지 않아도 되며, 단순 표시가 재검색을 실행하지 않는지 확인한다. 묶음·표시 우선순위·숨김이 다음 방문에도 유지돼야 한다.
- 첫 FDE 지원에서 조사한 비공개 경험이 다음 지원에 읽히고 공개 Profile에 자동 반영되지 않는지 확인한다. 새 역량을 요구하면 과거 기간도 추가로 찾을 수 있어야 한다.
- 같은 목적의 정기 run에서 작업 메모와 기존 조사 범위를 실제로 회수해 중복 검색을 줄이는지 본다. 캐시 hit 수뿐 아니라 불필요하게 다시 수행한 검색·판단을 확인한다.
- 공고 없는 기회에도 자료·할 일·실행을 연결하고, 간단한 다섯 지원과 집중할 한 지원에서 준비량이 적절히 달라지는지 읽는다. 공통 작업의 재사용과 취소, 실제 제출 당시 자료 revision도 확인한다.
- 목록에서 제시한 추천 이유가 상세에 이어지고, 사용자 조건 수정이 다음 탐색과 설명에 반영되는지 확인한다. 회사의 일반 장점이나 경험 유사성만으로 사용자에게 좋은 이동임을 주장하지 않아야 한다.
- 묶음이 없는 단일 기회도 바로 제안·선택·진행할 수 있고, 단순 상세 열기나 질문이 자동으로 진행 업무를 만들지 않는지 확인한다. 같은 기회의 접근 경로를 카드 여러 개로 불필요하게 늘리지 않는지도 실제 출력을 읽는다.
- 판단 품질을 바꾼 방법 자료가 실제 선택 전에 읽히고, 반대 사례에서 새로운 고정 절차를 만들지 않는지 같은 runtime으로 비교한다.

외부 회사의 채용 결정, 비공개 근무조건, 실제 관계의 신뢰, 고객의 구매 의사까지 소프트웨어 구조가 만들어낼 수는 없다. 이 경우 Harper가 해야 할 일은 빈칸을 숨기는 것이 아니라, 필요한 확인과 접근을 대신 수행하고 다른 좋은 선택도 유지하는 것이다.
