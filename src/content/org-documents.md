# Documents   <!-- id: documents -->



Harper를 처음 사용한다면 **Harper 소개 → 시작하기 → Slack → 역할 등록** 순서로 읽어보세요. 이미 사용 중이라면 지금 필요한 부분으로 바로 이동할 수 있습니다.

## Harper 소개 <!-- id: harper-introduction -->

Harper는 조건에 맞는 사람의 목록을 전달하는 데서 멈추지 않습니다. 후보자가 회사와 역할을 충분히 이해한 상태에서 실제 대화까지 이어질 수 있도록, **탐색부터 사전 확인과 소개까지** 함께합니다.

### Harper가 후보자를 소개하는 방식

추천되는 후보자는 단순히 검색 조건에 맞는 사람의 목록이 아닙니다. Harper는 회사가 알려준 역할 정보와 채용 기준을 바탕으로 후보자 풀을 살펴보고, 각 후보자의 경력에서 이번 역할과 이어지는 근거를 검토합니다.

프로필만으로 역할을 판단하는 데 중요한 정보가 부족하면, 필요한 경우 후보자에게 해당 내용을 먼저 묻습니다. 적합한 분을 찾으면 회사와 팀이 어떤 일을 하는지, 이번 역할에서 무엇을 맡게 되는지 대신 소개하고, 왜 후보자의 경험과 이 기회가 잘 이어지는지 구체적으로 설명합니다. 후보자의 궁금한 점에 답하고 실제로 이 회사와 대화해 보고 싶다는 의사를 확인한 뒤, Harper 팀의 마지막 검토까지 마친 분만 회사에 소개합니다.

많은 이름을 빠르게 채우기보다 **실제로 대화를 시작할 준비가 된 후보자를 신중하게 소개하는 방식**입니다. 추천이 도착했다면 처음부터 회사를 모르는 후보자에게 다시 설명하고 관심을 확인하는 단계는 이미 지나 있습니다. 회사는 검색 결과를 일일이 거르는 데 시간을 쓰기보다, 추천 이유와 자료를 읽고 실제로 만나볼 사람을 결정하는 데 집중할 수 있습니다.

### 연결 대기의 뜻

**연결 대기**는 후보자가 회사와 역할에 대한 설명을 듣고, 이 회사와 대화해 보고 싶다는 의사를 밝힌 상태입니다. 단순히 Harper가 적합하다고 판단했거나 검색에서 발견했다는 뜻이 아닙니다.

이때 후보자는 회사의 답을 기다립니다. 회사는 추천 이유와 경력 자료를 살펴본 뒤 연결을 수락해 대화를 시작하거나, 연결을 거절해 이번 역할에서 더 진행하지 않겠다는 결정을 알려야 합니다. 웹에서는 각각 **Connect**, **Reject** 버튼으로 표시됩니다. 아직 중요한 정보가 부족하다면 결정하기 전에 Harper를 통해 후보자에게 추가로 확인할 수 있습니다.

```callout
회사가 검토할 차례입니다

연결 수락과 연결 거절은 모두 후보자에게 영향을 주는 결정입니다. 특히 연결을 거절하면 회사가 더 진행하지 않기로 했다는 사실이 후보자에게 안내되고, 이미 보이거나 전달된 안내는 회수할 수 없습니다. 충분히 검토한 뒤 선택해 주세요.
```

## 시작하기 <!-- id: getting-started -->

처음에는 **회사 정보, 참여할 멤버, Slack 채널, 찾는 역할**만 준비하면 됩니다. 완성된 채용 공고나 모든 조건을 처음부터 갖출 필요는 없습니다. 후보자에게 꼭 알려야 할 회사와 역할의 기본 정보, Harper가 매칭에 사용할 실제 판단 기준부터 차례로 정리하면 됩니다.

### 처음 설정할 것

1. **회사 정보 확인.** 후보자에게 설명할 내용이 맞는지 [회사 정보](#org-company)를 확인합니다. 회사가 하는 일, 팀의 방향, 일하는 방식이 필요합니다.
2. **Slack 연결.** 추천 알림을 함께 볼 수 있도록 [Slack을 연결](#org-slack)하고, 실제 검토 팀이 있는 채널을 고릅니다.
3. **멤버 초대.** 후보자를 함께 검토하거나 소개 메일을 받을 사람을 [멤버로 초대](#org-members)합니다. 현업에서 결정을 함께할 동료도 포함하세요.
4. **역할 등록.** [첫 역할을 등록](#org-newRole)하고 맡길 일과 꼭 필요한 경험을 알려줍니다.

### 역할을 등록한 다음

1. **후보자 탐색.** 역할 등록이 끝나면 Harper가 후보자를 찾기 시작합니다. 화면을 계속 열어둘 필요는 없습니다.
2. **후보자 의사 확인.** 적합한 사람에게 회사, 역할, 제안 이유를 설명하고 대화할 마음이 있는지 확인합니다. 관심이 없는 사람은 검토 목록에 들어오지 않습니다.
3. **연결 대기.** 후보자가 만나보고 싶다고 답하고 필요한 자료가 준비되면 연결 대기로 들어옵니다. Slack과 [Inbox](#org-inbox)에 알림이 오며, 후보자는 회사의 답을 기다립니다.
4. **회사의 결정.** 추천 이유와 이력서를 보고 연결을 수락할지 거절할지 선택합니다. 웹의 첫 결정 버튼은 **Connect**, **Reject**로 표시됩니다. 정보가 부족하면 먼저 Harper를 통해 후보자에게 추가로 확인할 수 있습니다.

```callout
결정 이후

연결을 수락하면 선택한 방식으로 연결을 시작합니다. Email intro에서는 Harper가 후보자와 회사 담당자에게 소개 이메일을 보내요. 연결을 거절하면 회사가 더 진행하지 않기로 했다는 종료 결정이 후보자에게 표시되고 Harper가 이를 안내해요. 이미 후보자에게 보이거나 전달된 안내는 회수할 수 없습니다. 연결을 수락한 이후의 전형은 [Pipeline](#org-pipeline)에서 관리하세요.
```

```action
첫 역할 등록하기
org:newRole
```

## Slack <!-- id: slack -->

Slack에서는 **알림 확인, 후보자 검토, 연결 수락·거절, 후보자에게 추가로 확인하기**를 한곳에서 할 수 있습니다. 채용팀이 이미 일하는 채널에서 의견을 모으고 다음 행동까지 이어갈 수 있습니다.

### 연결 방법

1. **Integrations 열기.** [Organization의 Integrations](#org-slack)으로 이동합니다.
2. **회사 Slack 선택.** Slack 연결을 누르고 회사에서 사용하는 Slack을 선택합니다. 설치 승인이 필요하면 Slack 관리자에게 요청합니다.
3. **알림 채널 추가.** 후보자를 실제로 검토하고 결정할 사람들이 있는 채널을 고릅니다.
4. **비공개 채널 준비.** 아래 명령으로 Harper를 먼저 초대한 뒤 채널을 추가합니다.

```example
비공개 채널에서 입력

/invite @Harper
```

```callout
채널 선택

역할마다 담당 팀이 다르면 여러 채널을 연결할 수 있습니다. 후보자 정보가 올라오므로 **실제 채용에 참여하는 사람만 있는 채널**을 권합니다.
```

### 어떤 알림을 받나요?

- **연결 대기 알림.** 후보자가 회사와 역할을 이해했고 대화할 의사가 있다는 뜻입니다.
- **알림에 포함되는 내용.** 역할 이름, 후보자 정보, 추천 이유를 함께 볼 수 있습니다.
- **팀의 결정.** 답글에서 의견을 모으고, Owner나 Admin이 최종 선택합니다.

### 후보자가 도착하면

1. **후보자 검토하기**를 눌러 추천 이유, 경력, 학력, 이력서를 읽습니다.
2. 역할의 핵심 조건과 이어지는 경력, 아직 확인되지 않은 내용을 구분해 봅니다.
3. **연결 수락** 또는 **연결 거절**을 선택합니다. 연결 거절은 임시 보류가 아니며 후보자에게 회사의 종료 결정이 안내됩니다. 자세한 차이는 [연결 수락과 연결 거절](#accept-or-decline)에 정리했습니다.

### Slack에서 검토를 이어가기

새 질문이나 요청에는 **@Harper**를 붙입니다. 후보자 알림 아래에서는 답글로 이어서 물어보면 해당 후보자와 역할의 맥락을 함께 볼 수 있습니다. 여러 역할이나 후보자가 섞여 있다면 대상의 이름을 함께 적어 주세요.

```example
Slack 요청 예시

@Harper 지금 먼저 봐야 할 후보자가 누구야?
@Harper 백엔드 역할의 연결 대기 후보자를 비교해줘.
@Harper 이 역할은 시스템 설계 경험을 더 중요하게 봐줘.
```

```callout
후보자에게 질문하거나 자료를 요청할 때

후보자에게 질문하거나 이력서를 요청할 때는 Harper가 보낼 내용을 먼저 보여줍니다. **회사가 확인하기 전에는 발송하지 않습니다.**
```

```action
Slack 연결하기
org:slack
```

## 역할 등록 <!-- id: create-a-role -->

**공고 링크·파일**을 주거나, 지금 알고 있는 채용 배경과 찾는 사람을 몇 문장으로 설명하면 됩니다.

### 공고가 있을 때와 없을 때

- **공고가 있다면** 링크나 파일을 전달하세요. Harper가 역할 이름, 주요 업무, 자격 요건, 근무 조건을 먼저 정리합니다. 공고에 없는 실제 우선순위만 덧붙이면 됩니다.
- **공고가 없다면** 왜 지금 뽑는지, 어떤 문제를 맡길지, 기존 팀에서 어떤 역할을 할지부터 말해 주세요. 이 정도만 있어도 시작할 수 있습니다.

```callout
중요한 것

문장을 완벽하게 다듬는 것보다 **실제 판단 기준을 빠뜨리지 않는 것**이 중요합니다. 빠진 내용은 Harper가 이어서 묻습니다.
```

### 무엇을 알려주면 되나요?

사람을 뽑는 동료에게 설명하듯 말하면 됩니다. 먼저 아래 정도만 포함해 주세요.

```quote
입력 예시

“결제 플랫폼 팀의 백엔드 엔지니어를 찾고 있어. Java와 대규모 트래픽 경험이 중요하고, 서울에서 주 2회 함께 일했으면 해.”
```

기술 이름이나 연차만 적기보다 왜 그 경험이 필요한지도 같이 말해 주세요. 예를 들어 “React 5년”보다 “복잡한 상태를 설계하고 제품 구조를 주도해 본 사람”이 실제 기준에 더 가깝습니다.

- **맡길 일.** 입사 후 가장 먼저 맡게 될 일과 기대하는 결과
- **경험.** 반드시 해본 경험과 있으면 좋은 경험의 차이
- **팀.** 현재 인원, 함께 일할 사람, 채용하는 이유
- **조건.** 근무 지역, 출근 횟수, 고용 형태, 보상 범위
- **제외 기준.** 이번 역할에서 맞지 않는다고 판단할 분명한 조건

```callout
필수와 선호를 나누세요

모든 항목을 처음부터 답할 필요는 없습니다. 다만 **“있으면 좋다”**와 **“없으면 진행하기 어렵다”**를 구분해 주세요.
```

### Harper가 정리하는 내용

- 역할이 필요한 이유와 맡게 될 일
- 반드시 필요한 경험 / 있으면 좋은 경험
- 좋은 후보자를 구분할 기준 / 피해야 할 조건
- 후보자에게 설명할 회사·팀·역할의 매력
- 지역·근무 방식·고용 형태·보상 범위

```callout
Harper가 다시 묻는 경우

빠진 조건이 있거나 내용이 서로 다르면 다시 확인합니다. 예를 들어 공고에는 원격 근무, 대화에는 주 2회 출근이라고 되어 있다면 현재 기준이 무엇인지 묻습니다.
```

### 등록하기 전에 확인할 것

- **역할 설명.** 후보자에게 보여도 되는 이름과 내용인지 확인합니다.
- **우선순위.** 필수 조건과 선호 조건이 구분되어 있는지 봅니다.
- **담당자.** 후보자를 검토하고 소개 메일을 받을 멤버를 정합니다.
- **알림.** 새 후보자 알림을 받을 Slack 채널을 선택합니다.

### 등록한 뒤 기준을 바꾸려면

역할 대화에 **기존 기준에서 무엇이 달라졌는지** 말해 주세요.

```example
역할 대화 예시

시니어보다 직접 만드는 사람을 우선해줘.
핀테크 경험은 이제 필수가 아니야.
```

```callout
기준을 크게 바꿨다면

이미 연결 대기에 있는 후보자는 이전 기준으로 소개되었을 수 있습니다. 새 기준으로도 만나볼 사람인지 한 명씩 다시 확인하세요.
```

회사 전반의 설명이 바뀌었다면 먼저 [회사 정보](#org-company)를 수정하고, 특정 역할의 내용은 역할 대화에 남겨 주세요. 잠깐 쉬려면 **중단**, 더 이상 뽑지 않는다면 **종료**를 선택합니다.

```action
새 역할 등록하기
org:newRole
```

## 추천 확인 <!-- id: review-recommendations -->

연결 대기에는 **회사와 역할 설명을 듣고 대화할 의사를 밝힌 후보자**만 들어옵니다.

### 연결 대기에 오기까지

1. **탐색.** Harper가 역할의 필수 조건과 우선순위를 바탕으로 맞는 사람을 찾고, 이력과 경험을 살펴봅니다.
2. **역할 설명.** 후보자에게 회사가 어떤 곳인지, 어떤 일을 맡게 되는지, 왜 이 역할을 제안하는지 설명합니다.
3. **의사 확인.** 후보자가 관심을 보이면 궁금한 점에 답하고, 회사에 소개되어도 괜찮은지 확인합니다.
4. **연결 대기.** 연결에 필요한 확인을 마친 뒤 회사의 결정을 기다리는 연결 대기로 보냅니다.

```callout
핵심

연결 대기는 단순 추천 목록이 아닙니다. 후보자가 회사의 답을 기다리고 있으므로 검토한 뒤에는 **연결을 수락할지 거절할지** 답해 주세요.
```

### 프로필에서 볼 것

- **추천 이유**와 그 판단의 근거가 된 경력
- **실제로 맡았던 일**과 결과, 책임 범위
- **확인되지 않은 내용**과 다음 대화에서 물어볼 부분
- **이력서**와 지금까지의 진행 기록

회사 이름이나 기술 이름 하나보다 **어떤 문제를 맡았고 본인이 어디까지 책임졌는지**를 보세요. 분명하지 않은 내용은 사실로 단정하지 말고 확인할 질문으로 남깁니다.

### 결정 전에 더 확인하고 싶다면

후보자의 가능성은 보이지만 연결 수락 또는 연결 거절을 결정하기에 중요한 근거가 빠져 있을 수 있습니다. 이때는 추측해서 결정하거나 회사가 먼저 직접 연락할 필요 없이, [Harper를 통해 후보자에게 질문하거나 필요한 자료를 요청](#ask-harper)할 수 있습니다.

```example
요청 예시

@Harper 이 후보자가 결제 장애 대응을 직접 주도했는지, 당시 맡은 범위를 물어봐줘.
@Harper 최근 경력이 포함된 이력서를 받을 수 있는지 물어봐줘.
```

```callout
발송 전 확인

Harper가 어떤 후보자에게 어떤 역할과 관련해 보낼지, 실제 제목과 본문은 무엇인지 먼저 보여줍니다. 회사가 문구를 확인하고 보내도 된다고 명시적으로 답한 뒤에만 전달하며, 답변이 오면 요청을 시작한 대화에서 알려줍니다.
```

### 결정이 쌓이지 않게 해주세요

팀 안에서 검토할 사람과 최종 결정할 사람을 정하고, 알림이 오면 의견을 모아주세요. 모든 역할의 대기 항목은 [Inbox](#org-inbox)에서 모아볼 수 있습니다.

```callout
대기 후보자가 5명 이상이면

회사가 기존 후보자를 먼저 볼 수 있도록 새 연결이 잠시 멈춥니다. 연결을 수락하거나 거절해 대기 인원이 줄면 다시 이어집니다.
```

```action
연결 대기 확인하기
org:inbox
```

## 연결 수락과 연결 거절 <!-- id: accept-or-decline -->

**연결 수락**은 만나보고 싶을 때, **연결 거절**은 회사가 이번 역할에서 더 진행하지 않기로 결정했을 때 선택합니다. 웹에서는 각각 **Connect**, **Reject** 버튼으로 표시됩니다. 연결 거절은 후보자를 잠시 보류하는 기능이 아닙니다.

### 선택하기 전에

- **만나볼 근거.** 모든 조건을 완벽하게 충족하지 않아도 됩니다. 대화로 확인할 가치가 있는 강점이 있는지 봅니다.
- **첫 담당자.** 후보자와 함께 소개 메일을 받을 회사 담당자를 정합니다.
- **Connection note.** 선택 사항이며 후보자에게 그대로 전달되지 않습니다. 다음 추천에서 이어서 보고 싶은 강점을 짧게 남기면 됩니다.

```callout
후보자는 이미 동의했습니다

연결 대기 후보자는 회사와 역할 설명을 듣고, 이 회사와 대화해도 좋다고 답한 상태입니다. 연결을 수락한 뒤에는 다시 의사를 묻기보다 바로 첫 연락을 시작하면 됩니다.
```

### 연결 수락

1. 소개 메일을 받을 회사 멤버를 고릅니다. 보이지 않는 사람은 먼저 [멤버로 초대](#org-members)합니다.
2. Harper가 후보자와 선택한 회사 멤버를 한 메일에 연결한다고 안내하고, 발송 전에 확인을 받습니다.
3. 확인하면 Harper가 후보자에게 메일을 보내고 선택한 멤버를 참조에 넣습니다.
4. 회사 담당자가 전체 답장으로 인사하고 일정과 다음 순서를 안내합니다.

### 연결 거절

- 이번 역할에서 후보자 검토와 연결 흐름이 종료됩니다.
- 회사가 더 진행하지 않기로 했다는 종료 결정이 후보자에게 표시되고 Harper가 이를 안내합니다.
- 이미 후보자에게 보이거나 전달된 안내는 상태를 다시 열더라도 회수할 수 없습니다.
- 소개 이메일은 발송되지 않고 회사가 따로 연락할 필요도 없습니다.

```callout
연결 거절 이유

연결 거절 이유는 선택 사항이며 후보자에게 그대로 보내지지 않습니다. **“경험 범위가 좁음”**, **“이번에는 결제 경험을 우선함”**처럼 실제 판단 기준만 남겨주세요.
```

### 연결한 뒤 진행을 끝낼 때

1. 후보자의 진행을 종료하면 Harper가 종료 안내를 보냅니다.
2. 이미 발송된 소개 메일이나 회사가 보낸 연락은 없어지지 않습니다.
3. 대화 중이거나 일정이 잡혔다면 회사 담당자도 후보자에게 직접 알려야 합니다.
4. Pipeline을 최종 결과에 맞게 옮겨 마무리합니다.

```action
후보자 검토하기
org:inbox
```

## 후보자에게 추가로 확인하기 <!-- id: ask-harper -->

후보자의 가능성은 보이지만 연결을 수락하거나 거절하기에 정보가 부족하다면, 회사가 직접 연락을 시작하기 전에도 Harper를 통해 필요한 내용을 확인할 수 있습니다. 맡았던 일의 범위, 특정 경험의 깊이, 최근 경력이 포함된 이력서처럼 **이번 역할을 판단하는 데 필요한 질문이나 자료 요청**을 `/org` 대화나 Slack에 남겨 주세요.

Harper가 요청의 맥락을 후보자가 이해하기 쉽게 정리해 전달하고, 답변이 오면 요청을 시작한 대화에서 알려줍니다. 회사는 후보자에게 갑자기 직접 연락하지 않아도 되고, 후보자는 어느 회사의 어떤 역할과 관련된 확인인지 알고 답할 수 있습니다.

### 어떤 내용을 확인할 수 있나요?

- **경험의 실제 범위.** 특정 프로젝트를 직접 주도했는지, 팀에서 어디까지 책임졌는지처럼 프로필만으로 분명하지 않은 내용을 확인할 수 있습니다.
- **역할의 필수 조건.** 반드시 필요한 기술, 도메인, 근무 방식과 관련해 후보자의 최신 경험이나 의사를 물을 수 있습니다.
- **최신 자료.** 최근 경력이 빠져 있거나 자료가 오래되었다면 최신 이력서나 역할 판단에 필요한 자료를 요청할 수 있습니다.
- **후보자가 정할 정보.** 보상처럼 후보자의 허락이 필요한 내용은 공유 가능한 범위를 후보자가 직접 정할 수 있도록 질문합니다.

가능하면 **누구에게, 무엇을, 왜 확인하려는지** 함께 적어 주세요. 질문의 범위가 분명할수록 후보자도 답하기 쉽고, 회사도 답변을 바로 판단에 사용할 수 있습니다.

```example
요청 예시

@Harper 이 후보자가 결제 장애 대응을 직접 주도했는지, 당시 맡은 범위를 물어봐줘. 연결을 수락하기 전에 책임 범위를 확인하고 싶어.
@Harper 최근 1년 경력이 포함된 최신 이력서를 받을 수 있는지 물어봐줘.
@Harper 서울 주 2회 근무가 가능한지 확인해줘. 이 역할의 필수 조건이야.
```

### 후보자에게 전달되기 전

1. Harper가 후보자와 역할, 전달 채널, 이메일 제목과 본문을 포함한 **실제 보낼 문구**를 먼저 보여줍니다.
2. 회사는 질문이 정확한지 읽고 그대로 보내거나, 더 자연스럽고 필요한 범위에 맞게 고칠 수 있습니다.
3. 회사가 보내도 된다고 명시적으로 확인한 뒤에만 안내된 시각에 이메일과 Harper 채팅으로 같은 내용을 전달합니다.
4. 아직 전달 전이라면 발송 예정 상태를 안내하고, 실제 전달이 끝난 뒤에는 보냈다는 결과를 구분해 알려줍니다.

```callout
확인 전에는 보내지 않습니다

질문을 작성해 달라고 요청한 것만으로 후보자에게 바로 연락하지 않습니다. 실제로 보낼 제목과 본문을 회사가 확인하고 승인하기 전에는 발송하지 않습니다.
```

### 답변이 오면

후보자가 답하면 어느 후보자와 역할에 관한 답변인지 분명히 표시하고, 후보자가 전달한 의미를 바꾸지 않은 채 요청을 시작한 `/org` 대화나 Slack 스레드에서 알려줍니다. 회사는 새로 확인한 내용과 아직 확인되지 않은 부분을 구분해 본 뒤 연결을 수락할지 거절할지 결정하면 됩니다.

후보자는 답변할 내용과 공유 범위를 직접 선택할 수 있으며, 답하기 어렵다고 하거나 응답하지 않을 수도 있습니다. Harper가 자동으로 재촉하지는 않습니다. 답변이 오지 않았다면 더 기다릴지, 현재 자료로 결정할지 채용팀이 정하면 됩니다.

## Pipeline <!-- id: pipeline -->

연결을 수락한 후보자는 **Pipeline**에서 첫 대화부터 최종 결정까지 이어서 관리합니다.

### Pipeline에 들어오는 시점

```callout
Inbox와 Pipeline의 차이

**Inbox**는 아직 회사의 결정을 기다리는 후보자를 보는 곳입니다. **Pipeline**은 회사가 연결을 수락한 뒤의 채용 진행을 관리하는 곳입니다.
```

1. 연결 대기 후보자를 Connect하면 연결됨 단계로 들어옵니다.
2. Harper가 보낸 소개 메일에서 첫 일정을 잡습니다.
3. 실제 대화가 시작되면 회사의 전형에 맞춰 다음 단계로 옮깁니다.

### 후보자 진행 상태 관리하기

- **단계 준비.** 전화 대화, 1차 인터뷰, 과제, 최종 인터뷰처럼 회사 전형에 맞게 구성합니다.
- **단계 이동.** 인터뷰나 과제가 끝날 때마다 실제로 진행 중인 단계로 옮깁니다.
- **메모.** 확인한 사실, 남은 질문, 다음 담당자와 해야 할 일을 함께 남깁니다.
- **마무리.** 채용을 이어가지 않거나 최종 결정이 끝나면 결과에 맞게 종료합니다.

```quote
좋은 메모 예시

“결제 시스템 장애 대응 범위를 다음 인터뷰에서 확인”
```

### 여러 역할을 함께 볼 때

[전체 Pipeline](#org-pipeline)을 열면 모든 역할의 후보자를 한곳에서 볼 수 있습니다. 오래 머물러 있는 후보자부터 **다음 담당자와 예정된 일정**을 정리하세요. 역할별로 좁혀볼 수도 있습니다.

```action
Pipeline 열기
org:pipeline
```
